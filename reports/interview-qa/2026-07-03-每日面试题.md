#### 一、虚拟线程 vs 平台线程：核心区别（面试必答）

Java 21 引入的虚拟线程（Project Loom 产物）彻底改变了 Java 的并发模型。

| 对比维度 | 平台线程（Platform Thread） | 虚拟线程（Virtual Thread） |
|---------|---------------------------|---------------------------|
| **映射关系** | 与 OS 线程 1:1 绑定 | JVM 管理的轻量级线程，M:N 映射到少量平台线程 |
| **栈大小** | ~1MB（固定，不可伸缩） | ~2KB（可动态扩缩） |
| **创建成本** | 昂贵（~1ms，需要内核态系统调用） | 极低（~1μs，纯用户态） |
| **上下文切换** | 内核态切换，~1-10μs | 用户态切换，~0.1-1μs |
| **最大数量** | ~4000（16GB 内存下） | 数百万甚至上千万 |
| **阻塞行为** | 阻塞平台线程 → 资源被占用 | 阻塞时释放载体线程 → 资源高效复用 |

**一句话总结**：
> 平台线程是稀缺资源（1:1 映射 OS 线程），虚拟线程是廉价资源（大量虚拟线程共享少量平台线程）。

#### 二、虚拟线程的底层原理：M:N 调度模型

```
┌────────────────────────────────────────────────────────┐
│                  虚拟线程调度模型                         │
│                                                          │
│  Virtual Threads（M 个虚拟线程）                           │
│  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐              │
│  │ VT1 │ │ VT2 │ │ VT3 │ │ VT4 │ │ VT5 │ ...          │
│  └──┬──┘ └──┬──┘ └──┬──┘ └──┬──┘ └──┬──┘              │
│     │       │       │       │       │                  │
│     ▼       ▼       ▼       ▼       ▼                  │
│  ┌───────────────────────────────────────────┐         │
│  │       ForkJoinPool（载体线程池）              │         │
│  │  ┌──────┐ ┌──────┐ ┌──────┐                │         │
│  │  │ CT1  │ │ CT2  │ │ CT3  │ ← Carrier      │         │
│  │  └──┬───┘ └──┬───┘ └──┬───┘   Thread        │         │
│  └─────┼─────────┼─────────┼───────────────────┘         │
│        │         │         │                              │
│        ▼         ▼         ▼                              │
│  ┌───────────────────────────────────────────┐           │
│  │      OS Threads（N 个平台线程）              │           │
│  └───────────────────────────────────────────┘           │
└──────────────────────────────────────────────────────────┘
```

**关键机制：**

```
① 虚拟线程由 JVM 调度，而非 OS 调度
   所有虚拟线程运行在一个 ForkJoinPool 上（默认与 CPU 核数相同）

② 阻塞即释放（关键特性！）
   当虚拟线程执行 I/O 操作（数据库查询、HTTP 调用、文件读写）时，
   JVM 自动将载体线程释放出来执行其他虚拟线程
   → 不再有"线程阻塞导致资源浪费"的问题

③ 挂起（Yield）与恢复（Continue）
   阻塞点 → JVM 将虚拟线程的栈帧复制到堆内存 → 挂起
   I/O 就绪 → JVM 从堆恢复栈帧 → 分配载体线程继续执行
```

#### 三、为什么虚拟线程能提升 300% 吞吐量？

```
传统线程池模型（一请求一线程）：
  1000 个请求 → 1000 个平台线程 → 1000 个 OS 线程
  → 线程上下文切换开销巨大
  → 每个线程等待 I/O 时都在占用 OS 资源

虚拟线程模型：
  10000 个请求 → 10000 个虚拟线程 → 8 个 OS 线程（载体）
  → 虚拟线程切换几乎无开销
  → 阻塞时立即释放载体线程

压测数据（Spring Boot 3.2 + Tomcat）：
  传统线程池 → 3000 TPS（16 核，默认 200 线程池）
  虚拟线程   → 12000+ TPS（16 核，无需调参）
  → 吞吐量提升 300%，同时内存占用降低 40%
```

#### 四、Spring Boot 3.2+ 集成虚拟线程实战

**1. 最低配置（一行代码开启）**

```yaml
# application.yml
spring:
  threads:
    virtual:
      enabled: true  # ← 这行配置即可开启虚拟线程
```

**2. Java 配置方式**

```java
@Configuration
public class VirtualThreadConfig {
    
    @Bean
    public TomcatProtocolHandlerCustomizer<?> protocolHandlerVirtualThreadExecutor() {
        // Tomcat 请求处理线程切换为虚拟线程
        return protocolHandler -> {
            protocolHandler.setExecutor(Executors.newVirtualThreadPerTaskExecutor());
        };
    }
}

// 或者使用 Spring Boot 3.2+ 的自动配置
// 只需在 application.yml 中配置 spring.threads.virtual.enabled=true
```

**3. 自定义虚拟线程执行器**

```java
@Configuration
public class AsyncConfig {
    
    @Bean("virtualTaskExecutor")
    public Executor virtualTaskExecutor() {
        return Executors.newVirtualThreadPerTaskExecutor();
    }
    
    @Bean
    public AsyncTaskExecutor applicationTaskExecutor(
            @Qualifier("virtualTaskExecutor") Executor virtualExecutor) {
        return new TaskExecutorAdapter(virtualExecutor);
    }
}

// 在异步任务中使用
@Service
public class OrderService {
    
    @Async("virtualTaskExecutor")  // 每个异步任务跑在独立虚拟线程上
    public CompletableFuture<Order> createOrderAsync(OrderRequest request) {
        // 不再需要担心线程池耗尽
        return CompletableFuture.completedFuture(createOrder(request));
    }
}
```

**4. 生产环境注意事项**

```java
// ⚠️ 坑点 1：synchronized 会导致虚拟线程 pin 住载体线程
// 解决方案：使用 ReentrantLock 替代 synchronized
// ❌ 会导致 pinning（虚拟线程被固定在载体线程上，失去轻量优势）
public synchronized void doSomething() { ... }

// ✅ 推荐
private final Lock lock = new ReentrantLock();
public void doSomething() {
    lock.lock();
    try { ... }
    finally { lock.unlock(); }
}

// ⚠️ 坑点 2：ThreadLocal 在虚拟线程中需要谨慎使用
// 虚拟线程数量巨大 → ThreadLocal 对象数量也巨大 → 内存压力
// 解决方案：使用 ScopedValue（JDK 21+）

// ⚠️ 坑点 3：线程池调优已无必要
// 虚拟线程下，Executors.newFixedThreadPool() 不再适用
// 统一使用 Executors.newVirtualThreadPerTaskExecutor()
```

#### 五、2026 年大厂面试高频追问

```
追问 1："虚拟线程能不能替代所有线程池？"
  答：不能。CPU 密集型任务仍需平台线程（虚拟线程的挂起恢复有开销）。
      虚拟线程最适合 I/O 密集型（Web 服务、数据库访问、RPC 调用）。

追问 2："虚拟线程下还需要线程池吗？"
  答：创建虚拟线程几乎没有成本，所以不需要"池化"。
      但需要对并发数量做限流（防止虚拟线程过多导致 OOM）。

追问 3："虚拟线程与协程（如 Go goroutine）有什么区别？"
  答：本质都是 M:N 调度。区别在于 Go 的 goroutine 是语言原生调度，
      Java 虚拟线程运行在 JVM 之上，需要与操作系统和第三方库适配。
```

#### 一、秒杀系统的核心难点

```
秒杀系统的三大矛盾：

① 极高并发 vs 有限资源
   瞬时 QPS 可达数十万，但数据库连接池只有几十个
   → 必须在数据库前做多层削峰

② 强一致性 vs 高性能
   库存扣减必须准确（不能超卖），但分布式锁/行锁严重影响性能
   → 需要在一致性和性能间做权衡

③ 短时峰值 vs 常态容量
   秒杀持续只有几秒到几分钟，但系统按峰值扩容成本极高
   → 需要"降级"策略，秒杀期间牺牲非核心功能
```

#### 三、核心实现：Redis 库存预热 + Lua 原子扣减

**1. 库存预热**

```java
// 秒杀开始前，将数据库库存加载到 Redis
@Service
public class StockPreheatService {
    
    @Autowired
    private RedisTemplate<String, String> redisTemplate;
    
    @PostConstruct  // 项目启动时预热
    public void preheat() {
        List<SeckillProduct> products = seckillProductMapper.listAll();
        for (SeckillProduct product : products) {
            // 库存键格式：seckill:stock:{productId}
            String key = "seckill:stock:" + product.getId();
```

#### 一、三大缓存问题对比（面试必答表）

| 对比维度 | 缓存穿透 | 缓存击穿 | 缓存雪崩 |
|---------|---------|---------|---------|
| **问题本质** | 查询不存在的数据 | 热点 key 过期瞬间 | 大量 key 同时过期/Redis 宕机 |
| **流量走向** | 绕过缓存，直接打 DB | 单个热点 key 过期，并发回源 | 大量 key 过期，洪峰压向 DB |
| **DB 压力** | 持续低流量穿透 | 瞬时高流量 | 瞬时极高流量 |
| **主要原因** | 恶意攻击/代码缺陷 | 热点 key 过期无保护 | 批量过期/Redis 宕机 |
| **影响范围** | 单个不存在的数据 | 单个热点 key | 大面积业务瘫痪 |

#### 二、缓存穿透（Penetration）——查不存在的数据

**场景**：查询一个 ID = -1 或 ID 不存在的商品，Redis 里没有，DB 里也没有。

```
每次请求：
  ① 查 Redis → 没有
  ② 查 MySQL → 没有（也不回写 Redis）
  ③ 返回空 → 但下次请求又重复①→②
  → 绕过缓存，每次都打到数据库
```

**解决方案：**

```java
// 方案 1：缓存空值（实现简单，适合低频穿透）
public Product getProduct(Long id) {
    // 1. 查缓存
    String cacheKey = "product:" + id;
    String cached = redisTemplate.opsForValue().get(cacheKey);
    
    if (cached != null) {
        if ("NULL".equals(cached)) {
            return null;  // 缓存空值，直接返回
        }
        return JSON.parseObject(cached, Product.class);
    }
    
    // 2. 查数据库
    Product product = productMapper.selectById(id);
    
    // 3. 回写缓存
    if (product == null) {
        // 缓存空值，TTL 设置短一些（60s）
        redisTemplate.opsForValue().set(cacheKey, "NULL", 60, TimeUnit.SECONDS);
    } else {
        redisTemplate.opsForValue().set(cacheKey, JSON.toJSONString(product), 3600, TimeUnit.SECONDS);
    }
    
    return product;
}
```

#### 三、缓存击穿（Stampeding）——热点 key 过期

**场景**：某爆款商品（热搜第一）的缓存恰好过期，数千个并发请求同时发现缓存为空，全部回源查询数据库。

```
正常情况：
  1 个请求回源查 DB → 回写缓存 → 其余 999 个请求命中缓存
  
击穿情况：
  1000 个请求同时发现缓存过期 → 1000 个请求全部查 DB
  → 数据库连接池打满 → 数据库宕机
```

**解决方案：**

```java
// 方案 1：互斥锁（Mutex Key）——推荐
public Product getProductWithMutex(Long id) {
    String cacheKey = "product:" + id;
    String lockKey = "lock:product:" + id;
    
    // 1. 查缓存
    String cached = redisTemplate.opsForValue().get(cacheKey);
    if (cached != null) {
        if ("NULL".equals(cached)) return null;
        return JSON.parseObject(cached, Product.class);
    }
    
    // 2. 缓存未命中 → 尝试获取互斥锁
    String lockValue = UUID.randomUUID().toString();
    Boolean locked = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, lockValue, 5, TimeUnit.SECONDS);
    
    if (Boolean.TRUE.equals(locked)) {
        // 3. 拿到锁 → 查数据库
        try {
            // 双重检查（防止等待锁的过程中其他线程已经回写了缓存）
            cached = redisTemplate.opsForValue().get(cacheKey);
            if (cached != null) {
                return JSON.parseObject(cached, Product.class);
            }
            
            Product product = productMapper.selectById(id);
            if (product == null) {
                redisTemplate.opsForValue().set(cacheKey, "NULL", 60, TimeUnit.SECONDS);
            } else {
                redisTemplate.opsForValue().set(cacheKey, JSON.toJSONString(product), 3600, TimeUnit.SECONDS);
            }
            return product;
        } finally {
            // 释放锁（Lua 保证原子性）
            String unlockScript = """
                if redis.call('GET', KEYS[1]) == ARGV[1] then
                    return redis.call('DEL', KEYS[1])
                else
                    return 0
                end
                """;
            redisTemplate.execute(
                new DefaultRedisScript<>(unlockScript, Long.class),
                Collections.singletonList(lockKey),
                lockValue
            );
        }
    } else {
        // 4. 没拿到锁 → 自旋等待（50ms）
        try {
            Thread.sleep(50);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        return getProductWithMutex(id);  // 递归重试
    }
}
```

#### 四、缓存雪崩（Avalanche）——大面积失效

**场景 A：大量 key 同时过期**
```
问题：
  商品列表页的 10000 个商品缓存同时设置为 1 小时过期
  T+1 小时，10000 个 key 同时过期

  int ttl = 3600 + new Random().nextInt(600);  // 1h + 0~10min 随机

```

**场景 B：Redis 宕机**

#### 五、多级缓存架构设计（面试完整答案）

```java
/**
 * 多级缓存架构设计
 * 层级：Caffeine（本地） → Redis（分布式） → DB（兜底）
 */
@Component
public class MultiLevelCacheService {
    
    // 第一级：Caffeine 本地缓存（毫秒级响应）
    private final Cache<String, String> localCache = Caffeine.newBuilder()
        .maximumSize(10000)              // 最大缓存条目
        .expireAfterWrite(5, TimeUnit.MINUTES)  // 写入后 5 分钟过期
        .recordStats()                   // 记录命中率
        .build();
    
    @Autowired
    private RedisTemplate<String, String> redisTemplate;
    
    @Autowired
    private ProductMapper productMapper;
    
    public Product getProduct(Long id) {
        String cacheKey = "product:" + id;
        
        // 1. 查本地缓存（Caffeine）
        String localVal = localCache.getIfPresent(cacheKey);
        if (localVal != null) {
            if ("NULL".equals(localVal)) return null;
            return JSON.parseObject(localVal, Product.class);
        }
        
        // 2. 查 Redis（分布式缓存）
        String redisVal = redisTemplate.opsForValue().get(cacheKey);
        if (redisVal != null) {
            // 回填本地缓存
            localCache.put(cacheKey, redisVal);
            if ("NULL".equals(redisVal)) return null;
            return JSON.parseObject(redisVal, Product.class);
        }
        
        // 3. 查数据库（兜底）
        // 使用互斥锁防止击穿
        Product product = queryFromDBWithMutex(id);
        
        // 回填缓存
        if (product == null) {
            String nullVal = "NULL";
            localCache.put(cacheKey, nullVal);
            redisTemplate.opsForValue().set(cacheKey, nullVal, 60, TimeUnit.SECONDS);
        } else {
            String json = JSON.toJSONString(product);
            localCache.put(cacheKey, json);
            redisTemplate.opsForValue().set(cacheKey, json, 
                3600 + new Random().nextInt(600), TimeUnit.SECONDS);
        }
        
        return product;
    }
}
```

#### 六、热点 Key 治理（2026 年面试高频追问）

```
什么是热点 Key？
  某个 key 的 QPS 达到数万甚至数十万
  如：双十一大促的"秒杀商品详情"、微博热搜第一

热点 Key 的危害：
  ① 单台 Redis 节点 CPU 打满
  ② 网络带宽打满

治理方案：

① 本地缓存缓存热点 Key
  在应用层用 Caffeine 缓存热点 key
  减少对 Redis 的访问

② 读写分离 + 副本扩散
  热点 key 分散到多个 Redis 从节点
  客户端随机读取一个副本

③ 限流降级
  检测到热点 key 后，限流非核心业务的读取
  优先保障核心交易链路

④ 监控告警
  Redis 的 hotkeys 参数
  实时监控 key 的访问频率
```

```markdown
🎯 应对 AI 面试官的 5 个实战技巧：
```
