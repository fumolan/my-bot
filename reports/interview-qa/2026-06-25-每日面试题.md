## 题目 1：[Java并发] 请详细阐述 ThreadPoolExecutor 七大核心参数、执行流程及生产环境参数设计最佳实践

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-25 早间&午间报告 — "Java后端高频面试考点：线程池参数调优" + "大厂面试已从背诵八股转向源码原理+场景设计"
**相关岗位**：Java后端 / 高并发系统 / 基础架构

### 📖 参考答案

#### 一、为什么禁止使用 Executors 创建线程池？

很多开发者习惯用 `Executors.newFixedThreadPool(10)` 创建线程池，但这在生产环境是**高危操作**：

| Executors 方法 | 隐藏风险 | 后果 |
|---------------|---------|------|
| `newFixedThreadPool` | 使用无界队列 `LinkedBlockingQueue` | 任务堆积撑爆堆内存 → OOM |
| `newCachedThreadPool` | 最大线程数为 `Integer.MAX_VALUE` | 高并发下创建数十万线程 → CPU 100% |
| `newSingleThreadExecutor` | 同样使用无界队列 | 同 FixedThreadPool 风险 |

**结论**：必须使用 `ThreadPoolExecutor` 手动配置参数，精准控制线程池行为。

#### 二、七大核心参数详解

```java
public ThreadPoolExecutor(
    int corePoolSize,      // ① 核心线程数
    int maximumPoolSize,   // ② 最大线程数
    long keepAliveTime,    // ③ 空闲线程存活时间
    TimeUnit unit,         // ④ 时间单位
    BlockingQueue<Runnable> workQueue, // ⑤ 工作队列
    ThreadFactory threadFactory,       // ⑥ 线程工厂
    RejectedExecutionHandler handler   // ⑦ 拒绝策略
)
```

| 参数 | 含义 | 生产建议 |
|------|------|---------|
| **corePoolSize** | 核心线程数，即使空闲也保留 | CPU密集型：N+1；IO密集型：2N（N=CPU核数） |
| **maximumPoolSize** | 最大线程数 | 通常为 corePoolSize 的 2~4 倍 |
| **keepAliveTime** | 非核心线程空闲存活时间 | 默认 60s，短任务可缩短到 10~30s |
| **workQueue** | 存放等待执行任务的队列 | 优先用有界队列（如 `ArrayBlockingQueue`） |
| **threadFactory** | 创建线程的工厂 | 必须设置有意义的名字，方便排查 |
| **handler** | 队列和线程池都满时的处理策略 | 生产推荐 `CallerRunsPolicy` 或自定义策略 |

#### 三、任务执行完整流程

```
提交任务 execute(Runnable)
    │
    ▼
① 当前工作线程数 < corePoolSize？
    ├─ 是 → 创建核心线程执行任务
    └─ 否 → 进入步骤②
    │
    ▼
② 尝试将任务加入 workQueue？
    ├─ 成功 → 等待核心线程空闲后执行
    └─ 失败（队列已满） → 进入步骤③
    │
    ▼
③ 当前工作线程数 < maximumPoolSize？
    ├─ 是 → 创建非核心线程执行任务
    └─ 否 → 执行拒绝策略 handler
```

**关键理解**：线程池的"先入队，后创建非核心线程"的设计是为了避免创建过多线程。只有队列满了才创建新线程，这是一种**优先排队、适度扩容**的策略。

#### 四、四种内置拒绝策略

| 策略 | 行为 | 适用场景 |
|------|------|---------|
| **AbortPolicy**（默认） | 直接抛出 `RejectedExecutionException` | 必须告知调用方失败 |
| **CallerRunsPolicy** | 由提交任务的线程自己执行 | **生产推荐**，降级而非丢弃 |
| **DiscardPolicy** | 静默丢弃任务 | 不重要的日志/监控数据 |
| **DiscardOldestPolicy** | 丢弃队列中最旧的任务，重试提交 | 实时性要求高的场景 |

**生产推荐**：`CallerRunsPolicy` + 自定义监控告警。当触发拒绝策略时，由调用方线程执行任务（相当于反压），同时记录日志报警，让系统自动降级而非崩溃。

#### 五、核心线程数计算公式

```java
// CPU 密集型任务（计算为主，如加解密、压缩）
// 公式：N + 1（N = CPU 核心数）
// N+1 的原因：补偿页缺失等暂停导致的线程阻塞
int cpuCoreCount = Runtime.getRuntime().availableProcessors();
int corePoolSize = cpuCoreCount + 1;

// IO 密集型任务（网络/磁盘等待为主，如 DB 查询、RPC 调用）
// 公式：2N（或更大，取决于 IO 等待时间占比）
// 更精确的公式：线程数 = N * (1 + 等待时间 / 计算时间)
// 如果 IO 等待占 90%，计算占 10%，则线程数 = N * (1 + 9) = 10N
int corePoolSize = 2 * cpuCoreCount;
```

**实际生产做法**：公式只给初始值，通过压测（JMeter/Gatling）逐步调整，观察 CPU 利用率、线程池活跃度、任务排队时间等指标。

#### 六、execute() vs submit() 的区别

| 对比维度 | execute(Runnable) | submit(Callable/Runnable) |
|---------|-------------------|--------------------------|
| 返回值 | void | Future<T> |
| 异常处理 | 异常直接抛出，线程池捕获后内部处理 | 异常封装在 Future 中，调用 `future.get()` 时抛出 |
| 使用场景 | 不需要返回结果 | 需要获取结果或捕获异常 |

```java
// execute 的异常处理：线程池会创建新线程替换异常退出的线程
executor.execute(() -> {
    throw new RuntimeException("任务异常");
}); // 异常被线程池内部捕获，不会影响其他任务

// submit 的异常处理：异常被封装
Future<?> future = executor.submit(() -> {
    throw new RuntimeException("任务异常");
});
future.get(); // 抛出 ExecutionException，可获取原始异常
```

## 题目 2：[Java并发] 请详细阐述 AQS（AbstractQueuedSynchronizer）原理及 ReentrantLock 的公平/非公平锁源码实现

**难度**：⭐⭐⭐⭐⭐
**考点来源**：2026-06-25 午间报告 — "AQS工作原理（ReentrantLock源码级）" + "大厂面试已从背诵八股转向源码原理+场景设计"
**相关岗位**：Java后端 / 高并发系统 / 基础架构

### 📖 参考答案

#### 一、AQS 核心架构

AQS（AbstractQueuedSynchronizer）是 JUC 包的基石，ReentrantLock、CountDownLatch、Semaphore、ReentrantReadWriteLock 等同步组件都基于它构建。

```
AQS 三大核心要素：
┌─────────────────────────────────────────────┐
│  AQS                                         │
│                                              │
│  ① volatile int state       ← 同步状态       │
│     （0=未锁，>0=已锁，值=重入次数）            │
│                                              │
│  ② CLH 变体双向队列          ← 等待队列       │
│     ┌───┐  ┌───┐  ┌───┐                     │
│     │   │→│   │→│   │  (FIFO)               │
│     │   │←│   │←│   │                       │
│     └───┘  └───┘  └───┘                     │
│                                              │
│  ③ Node 节点（waitStatus）   ← 线程状态管理   │
│     CANCELLED=1 / SIGNAL=-1 / CONDITION=-2   │
└─────────────────────────────────────────────┘
```

**核心设计思想**：AQS 通过模板方法模式，将"获取/释放同步状态"的模板逻辑固定，子类只需实现 `tryAcquire`、`tryRelease` 等钩子方法。

#### 二、ReentrantLock 非公平锁加锁流程（源码级）

```java
// ReentrantLock 默认是非公平锁
ReentrantLock lock = new ReentrantLock(); // false=非公平

// lock() 调用链
public void lock() {
    sync.acquire(1);  // sync 是 Sync 类型，继承 AQS
}

// AQS.acquire() 模板方法
public final void acquire(int arg) {
    if (!tryAcquire(arg) &&              // ① 尝试获取锁
        acquireQueued(addWaiter(Node.EXCLUSIVE), arg)) // ② 失败则入队等待
        Thread.currentThread().interrupt();
}
```

**第一步：tryAcquire（非公平版）**

```java
// NonfairSync.tryAcquire()
protected final boolean tryAcquire(int acquires) {
    final Thread current = Thread.currentThread();
    int c = getState();
    if (c == 0) {
        // 非公平锁的核心：不管队列中是否有人在等，直接 CAS 抢锁
        if (compareAndSetState(0, acquires)) {
            setExclusiveOwnerThread(current);
            return true;
        }
    }
    else if (current == getExclusiveOwnerThread()) {
        // 可重入：当前线程已持有锁，state + 1
        int nextc = c + acquires;
        if (nextc < 0) // overflow
            throw new Error("Maximum lock count exceeded");
        setState(nextc);
        return true;
    }
    return false;
}
```

**第二步：addWaiter（入队）**

```java
// 获取锁失败 → 将当前线程封装为 Node 加入等待队列尾部
private Node addWaiter(Node mode) {
    Node node = new Node(Thread.currentThread(), mode);
    Node pred = tail;
    if (pred != null) {
        node.prev = pred;
        // CAS 设置尾节点
        if (compareAndSetTail(pred, node)) {
            pred.next = node;
            return node;
        }
    }
    enq(node); // 如果 CAS 失败或队列为空，自旋入队
    return node;
}
```

**第三步：acquireQueued（等待与自旋）**

```java
final boolean acquireQueued(final Node node, int arg) {
    boolean failed = true;
    try {
        boolean interrupted = false;
        for (;;) { // 自旋
            final Node p = node.predecessor();
            // 如果前驱节点是头节点，尝试获取锁
            if (p == head && tryAcquire(arg)) {
                setHead(node);
                p.next = null; // help GC
                failed = false;
                return interrupted;
            }
            // 获取锁失败 → 判断是否需要挂起线程
            if (shouldParkAfterFailedAcquire(p, node) &&
                parkAndCheckInterrupt())
                interrupted = true;
        }
    } finally {
        if (failed)
            cancelAcquire(node);
    }
}
```

#### 三、公平锁 vs 非公平锁的核心区别

```java
// FairSync.tryAcquire() — 多了一个 hasQueuedPredecessors() 检查
protected final boolean tryAcquire(int acquires) {
    final Thread current = Thread.currentThread();
    int c = getState();
    if (c == 0) {
        // 公平锁：先检查队列中是否有等待线程
        if (!hasQueuedPredecessors() &&  // ← 唯一区别
            compareAndSetState(0, acquires)) {
            setExclusiveOwnerThread(current);
            return true;
        }
    }
    // ... 可重入逻辑相同
}

// hasQueuedPredecessors() — 判断队列中是否有比当前线程等待更久的
public final boolean hasQueuedPredecessors() {
    Node t = tail;
    Node h = head;
    Node s;
    return h != t &&
        ((s = h.next) == null || s.thread != Thread.currentThread());
}
```

| 对比维度 | 非公平锁 | 公平锁 |
|---------|---------|--------|
| 获取锁策略 | 直接 CAS 抢锁，不管队列 | 先检查队列，排队在前才抢 |
| 吞吐量 | **高**（减少线程挂起/唤醒开销） | 低 |
| 线程饥饿 | 可能（新线程一直插队） | 不会（FIFO 保证） |
| 适用场景 | 大部分生产场景 | 对公平性有严格要求的场景 |

#### 四、解锁流程

```java
// ReentrantLock.unlock()
public void unlock() {
    sync.release(1);
}

// AQS.release()
public final boolean release(int arg) {
    if (tryRelease(arg)) {  // 释放锁（state - 1）
        Node h = head;
        if (h != null && h.waitStatus != 0)
            unparkSuccessor(h); // 唤醒头节点的后继节点
        return true;
    }
    return false;
}

// Sync.tryRelease()
protected final boolean tryRelease(int releases) {
    int c = getState() - releases;
    if (Thread.currentThread() != getExclusiveOwnerThread())
        throw new IllegalMonitorStateException();
    boolean free = false;
    if (c == 0) { // state 归零才真正释放锁
        free = true;
        setExclusiveOwnerThread(null);
    }
    setState(c);
    return free;
}
```

```
面试官问"ReentrantLock 实现原理"时，推荐按三层回答：

第一层（CAS 抢锁）：非公平锁直接 CAS 设置 state，公平锁先检查队列
```

## 题目 3：[数据结构/算法] 请手写 LRU 缓存：从 LinkedHashMap 一行实现到双向链表+哈希表完整实现

**难度**：⭐⭐⭐
**考点来源**：2026-06-25 午间报告 — "手写LRU缓存（LinkedHashMap / 双向链表+哈希表）" + "大厂面试必考手撕算法"
**相关岗位**：Java后端 / 全栈 / 基础架构

### 📖 参考答案

#### 一、LRU 缓存核心原理

LRU（Least Recently Used，最近最少使用）缓存淘汰策略：**当缓存容量满时，淘汰最久未被访问的数据**。

```
核心思想：最近被访问的数据，未来被访问的可能性更大。
```

**为什么需要"哈希表 + 双向链表"？**

| 操作 | 要求 | 实现方式 |
|------|------|---------|
| get(key) | O(1) 查找 | 哈希表（HashMap） |
| put(key, value) | O(1) 插入 | 哈希表定位 |
| 淘汰最久未使用的 | O(1) 删除尾部 | 双向链表维护访问顺序 |
| 访问后移到头部 | O(1) 移动节点 | 双向链表 O(1) 删除 + O(1) 插入 |

#### 二、方案一：LinkedHashMap 一行实现（面试慎用）

```java
public class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    
    public LRUCache(int capacity) {
        // accessOrder=true 启用访问顺序（而非插入顺序）
        super(capacity, 0.75f, true);
        this.capacity = capacity;
    }
    
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        // 当 size 超过容量时自动删除最老的元素
        return size() > capacity;
    }
}

// 使用
LRUCache<Integer, String> cache = new LRUCache<>(3);
cache.put(1, "A"); // {1=A}
cache.put(2, "B"); // {1=A, 2=B}
cache.put(3, "C"); // {1=A, 2=B, 3=C}
cache.get(1);      // 访问1 → {2=B, 3=C, 1=A}
cache.put(4, "D"); // 超过容量，淘汰最久未使用的2 → {3=C, 1=A, 4=D}
```

**优点**：代码极简
**缺点**：面试会被追问底层实现，不能展示对数据结构的理解

#### 三、方案二：手写双向链表 + HashMap（面试推荐）

```java
public class LRUCache<K, V> {
    // 双向链表节点
    private static class Node<K, V> {
        K key;
        V value;
        Node<K, V> prev;
        Node<K, V> next;
        
        Node(K key, V value) {
            this.key = key;
            this.value = value;
        }
    }
    
    private final int capacity;
    private final Map<K, Node<K, V>> map;  // 哈希表：O(1) 查找
    private final Node<K, V> head;          // 虚拟头节点（最近访问）
    private final Node<K, V> tail;          // 虚拟尾节点（最久未使用）
    
    public LRUCache(int capacity) {
        this.capacity = capacity;
        this.map = new HashMap<>(capacity);
        this.head = new Node<>(null, null);
        this.tail = new Node<>(null, null);
        head.next = tail;
        tail.prev = head;
    }
    
    /**
     * 获取缓存值
     * 时间复杂度：O(1)
     */
    public V get(K key) {
        Node<K, V> node = map.get(key);
        if (node == null) {
            return null;
        }
        // 访问后移到头部（最近使用）
        moveToHead(node);
        return node.value;
    }
    
    /**
     * 放入缓存
     * 时间复杂度：O(1)
     */
    public void put(K key, V value) {
        Node<K, V> node = map.get(key);
        if (node == null) {
            // 新增节点
            node = new Node<>(key, value);
            map.put(key, node);
            addToHead(node);
            
            // 超过容量，淘汰最久未使用的（尾部）
            if (map.size() > capacity) {
                Node<K, V> tail = removeTail();
                map.remove(tail.key);
            }
        } else {
            // 更新已有节点
            node.value = value;
            moveToHead(node);
        }
    }
    
    // ===== 双向链表操作（核心） =====
    
    private void addToHead(Node<K, V> node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }
    
    private void removeNode(Node<K, V> node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }
    
    private void moveToHead(Node<K, V> node) {
        removeNode(node);   // 从当前位置删除
        addToHead(node);    // 插入到头部
    }
    
    private Node<K, V> removeTail() {
        Node<K, V> node = tail.prev;
        removeNode(node);
        return node;
    }
}
```

#### 四、执行过程可视化

```
容量为 3 的 LRU 缓存执行过程：

put(1, A) → 缓存: [1:A]
put(2, B) → 缓存: [2:B] ↔ [1:A]
put(3, C) → 缓存: [3:C] ↔ [2:B] ↔ [1:A]
get(1)    → 访问1，移到头部 → [1:A] ↔ [3:C] ↔ [2:B]
put(4, D) → 超过容量，淘汰尾部2 → [4:D] ↔ [1:A] ↔ [3:C]
get(2)    → 2已被淘汰 → null
```

#### 五、面试追问与扩展

```
追问 1：为什么用双向链表而不是单向链表？
→ 双向链表可以在 O(1) 时间内删除任意节点（知道前驱节点）。
  单向链表删除节点需要遍历找到前驱，时间复杂度 O(n)。

追问 2：如何实现线程安全的 LRU 缓存？
→ 方案一：Collections.synchronizedMap() 包装（简单但并发低）
  方案二：ConcurrentHashMap + ReentrantLock（分段锁，推荐）
  方案三：使用 Caffeine 框架（工业级，基于 W-TinyLFU 算法）

追问 3：带过期时间的 LRU 如何实现？
→ 在 Node 中增加 expireTime 字段，get 时检查是否过期，
  后台定时扫描过期节点，或惰性删除（访问时删除）。
```

#### 一、Kafka 核心架构


**核心概念**：

| 组件 | 职责 | 类比 |
|------|------|------|
| **Producer** | 消息生产者，发送消息到 Topic | 快递发货员 |

#### 二、Kafka 为什么比传统消息队列吞吐量高？

Kafka 的高吞吐量源于三个核心设计：

**1. 顺序写（Sequential Write）**

```bash
# 传统消息队列：随机写磁盘（性能差）
# Kafka：追加写文件末尾（顺序写，性能接近内存）

# 机械硬盘性能对比：
# 随机写：约 100 IOPS
# 顺序写：约 200 MB/s（快 1000 倍以上）

# Kafka 所有消息都追加到 Partition 的日志文件末尾
# 不修改已写入的数据，充分利用磁盘顺序 IO
```

**2. 零拷贝（Zero Copy）**

```
传统读取流程（数据经过 4 次拷贝）：
  磁盘 → 内核缓冲区 → 用户缓冲区 → Socket 缓冲区 → 网卡

Kafka 零拷贝（数据经过 2 次拷贝）：
  磁盘 → 内核缓冲区（PageCache） → 网卡
  （使用 FileChannel.transferTo() / sendfile() 系统调用）

性能提升：减少 2 次上下文切换 + 2 次数据拷贝
```

**3. 批量与压缩**

```java
// Producer 批量发送配置
props.put("batch.size", 16384);       // 16KB 批量，满了才发
props.put("linger.ms", 5);            // 最多等待 5ms
props.put("compression.type", "snappy"); // 压缩减少网络 IO

// 批量带来的优势：
// 1. 减少网络请求次数（1000 条消息合并为 1 次请求）
// 2. 压缩率更高（批量压缩比单条压缩效率高）
// 3. Broker 端批量存储，Consumer 端批量拉取
```

#### 三、ISR 机制与数据可靠性

ISR（In-Sync Replica）是 Kafka 保证数据不丢失的核心机制：

```
ISR = Leader + 与 Leader 保持同步的 Follower 集合

写入流程：
  Producer → Leader Partition（写入完成）
       ↓
  Leader 等待 ISR 中的 Follower 同步完成
       ↓
  根据 acks 配置决定何时返回成功

acks 参数：
  acks=0     → 发出去就不管（最快，可能丢数据）
  acks=1     → Leader 写入成功即返回（默认，兼顾性能与可靠）
  acks=all   → ISR 全部同步完成才返回（最安全，延迟最高）
```

**Leader 选举**：当 Leader 宕机时，从 ISR 中选举一个 Follower 作为新 Leader，保证已同步的数据不丢失。

#### 四、分区策略与 Consumer Group

**分区规则**：

```java
// 默认分区器：基于 key 的哈希
// 相同 key 的消息进入同一个 Partition，保证顺序
// 没有 key 则轮询分配

// 自定义分区器
props.put("partitioner.class", "com.example.CustomPartitioner");

// 分区数设置原则：
// 1. 分区数 = max(Consumer 数, 目标吞吐量 / 单分区吞吐量)
// 2. 分区数不宜过多（过多增加 Leader 选举和文件句柄开销）
// 3. 建议：分区数 ≤ Broker 数 × 磁盘数
```

**Consumer Group 负载均衡**：

```
Topic 有 4 个 Partition，Consumer Group 有 3 个 Consumer：

Consumer A → Partition 0, Partition 1
Consumer B → Partition 2
Consumer C → Partition 3

关键规则：
  - 一个 Partition 只能被 Group 内的一个 Consumer 消费
  - 一个 Consumer 可以消费多个 Partition
  - Consumer 数 > Partition 数 → 部分 Consumer 空闲
```

#### 五、消息可靠性保障

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| **消息丢失** | Producer 发送失败 / Leader 宕机 | acks=all + 重试机制 |
| **重复消费** | Consumer 处理完未提交 offset 就挂了 | 幂等消费（业务键去重） |
| **消息积压** | Consumer 消费速度 < Producer 生产速度 | 增加分区 + 增加 Consumer |
| **顺序消费** | 多 Partition 无法保证全局有序 | 相同 key 进同一 Partition |

#### 四、生产落地关键挑战与解决方案

**挑战 1：无限循环**

```

  3. 关键信息提取：只传递任务相关的核心信息
```

```java
    // 2. 降级方案（主工具失败 → 备用工具）
    // 3. 超时控制（单次工具调用不超过 10s）
    // 4. 结果校验（工具返回结果是否符合预期格式）
    
    public ToolResult callWithRetry(ToolSpec spec, int maxRetries) {
        for (int i = 0; i < maxRetries; i++) {
            try {
                ToolResult result = spec.call();
                if (validateResult(result)) {
                    return result;
                }
            } catch (Exception e) {
                logger.warn("Tool call failed, retry {}/{}", i + 1, maxRetries);
                Thread.sleep(1000 * (long) Math.pow(2, i)); // 指数退避
            }
        }
        throw new ToolCallException("All retries exhausted");
    }
}
```
