**一、虚拟线程是什么？——Java 并发的"范式革命"**

虚拟线程（Virtual Threads，JEP 444）是 Java 21 正式发布的 Project Loom 核心特性。它让 Java 开发者可以用"同步代码写异步逻辑"——每个任务一个虚拟线程，代码是同步阻塞风格，但底层是非阻塞异步执行。

```
传统并发模型的困境：

  平台线程（Platform Thread）：
  ┌─────────────────────────────────────────────────────────┐
  │ Java Thread = OS Kernel Thread（1:1 映射）               │
  │                                                         │
  │ 问题：                                                   │
  │ ① 创建成本高：每个线程 ~1MB 栈空间 + OS 调度开销          │
  │ ② 数量受限：一台机器最多几千个线程                        │
  │ ③ 阻塞昂贵：线程阻塞 = OS 线程阻塞 = 上下文切换           │
  │                                                         │
  │ 后果：高并发场景只能用异步编程（CompletableFuture/WebFlux）│
  │       → 代码复杂、调试困难、堆栈不可读                     │
  └─────────────────────────────────────────────────────────┘

  虚拟线程（Virtual Thread）：
  ┌─────────────────────────────────────────────────────────┐
  │ Virtual Thread ≠ OS Thread（M:N 映射）                   │
  │                                                         │
  │ 优势：                                                   │
  │ ① 创建成本极低：每个虚拟线程 ~几百字节                    │
  │ ② 数量巨大：轻松百万级并发                                │
  │ ③ 阻塞无感：阻塞时自动"卸载"（unmount），释放 Carrier     │
  │                                                         │
  │ 效果：同步代码 + 异步性能 = 鱼与熊掌兼得                   │
  └─────────────────────────────────────────────────────────┘
```

**二、虚拟线程的架构——Carrier Thread + Continuation**

```
虚拟线程调度模型：

  ┌─────────────────────────────────────────────────────────┐
  │              ForkJoinPool（Work-Stealing）               │
  │                                                         │
  │  ┌──────────┐  ┌──────────┐  ┌──────────┐              │
  │  │ Carrier  │  │ Carrier  │  │ Carrier  │  ← 平台线程   │
  │  │ Thread-1 │  │ Thread-2 │  │ Thread-3 │     (CPU核数) │
  │  └────┬─────┘  └────┬─────┘  └────┬─────┘              │
  │       │              │              │                    │
  │       ▼              ▼              ▼                    │
  │  ┌──────────────────────────────────────┐               │
  │  │        虚拟线程队列（成千上万）         │               │
  │  │  VT-1  VT-2  VT-3  ...  VT-100000   │               │
  │  └──────────────────────────────────────┘               │
  └─────────────────────────────────────────────────────────┘

  关键概念：

  ① Carrier Thread（载体线程）：
     - 就是普通的平台线程（OS 线程）
     - 数量 = CPU 核心数（默认）
     - 负责"搬运"虚拟线程执行

  ② Continuation（续延）：
     - 虚拟线程的核心机制
     - 可以保存执行状态并"暂停"（yield）
     - 阻塞时自动 yield → 释放 Carrier Thread
     - 恢复时自动 continue → 重新挂载到 Carrier Thread

  ③ Mount/Unmount（挂载/卸载）：
     - Mount：虚拟线程被调度到 Carrier Thread 上执行
     - Unmount：虚拟线程遇到阻塞操作（IO/睡眠）→ 从 Carrier 卸载
     - Carrier 被释放，立即去执行其他虚拟线程
     - 阻塞结束后，虚拟线程重新排队等待 Mount
```

**三、为什么虚拟线程能支持百万级并发？**

```
平台线程 vs 虚拟线程的资源对比：

  ┌────────────────┬──────────────┬──────────────┐
  │      维度       │  平台线程     │  虚拟线程     │
  ├────────────────┼──────────────┼──────────────┤
  │ 栈内存          │ ~1MB（固定）  │ ~几百字节     │
  │                │              │（动态增长）    │
  │ 创建时间        │ ~1ms         │ ~1μs         │
  │ 上下文切换      │ OS 内核级     │ JVM 用户态    │
  │ 最大数量        │ ~5000        │ ~1000000+    │
  │ 阻塞代价        │ 线程阻塞      │ 自动卸载      │
  └────────────────┴──────────────┴──────────────┘

  100 万虚拟线程的内存占用：
  100 万 × 几百字节 ≈ 几百 MB（完全可行）
  
  100 万平台线程的内存占用：
  100 万 × 1MB ≈ 1TB（不可能）
```

```java
// 验证：创建 100 万个虚拟线程
public class VirtualThreadDemo {
    public static void main(String[] args) throws InterruptedException {
        long start = System.currentTimeMillis();
        
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 1_000_000; i++) {
                int taskId = i;
                executor.submit(() -> {
                    Thread.sleep(1000);  // 模拟 IO 等待
                    return taskId;
                });
            }
        }
        
        long cost = System.currentTimeMillis() - start;
        System.out.println("100 万虚拟线程耗时: " + cost + "ms");
        // 输出：约 2-3 秒（平台线程需要几十秒甚至 OOM）
    }
}
```

**四、虚拟线程的"Pinning"问题——面试高频追问**

Pinning（固定）是虚拟线程最容易被问到的坑：

```
Pinning 问题：

  当虚拟线程执行以下操作时，会被"固定"到 Carrier Thread 上：
  
  ① synchronized 块/方法内部发生阻塞（IO/睡眠）
     → 虚拟线程无法 unmount，Carrier 被"钉住"
     → 其他虚拟线程无法使用这个 Carrier
  
  ② 调用本地方法（JNI/Native Method）
     → JVM 无法控制本地代码的执行
     → 虚拟线程无法 yield

  Pinning 的危害：
  - Carrier Thread 被占用 → 虚拟线程调度能力下降
  - 大量 Pinning → 相当于退化到平台线程模型
  - 可能导致"虚拟线程饥饿"——大量虚拟线程等待 Carrier

  解决方案：
  ① 用 ReentrantLock 替代 synchronized（推荐！）
     ReentrantLock 使用 AQS 的 park/unpark，虚拟线程友好
  
  ② 避免在虚拟线程中调用本地方法
     如果必须调用，考虑用平台线程池隔离
  
  ③ 使用 -Djdk.tracePinnedThreads=full 检测 Pinning
     JVM 会在发生 Pinning 时打印堆栈
```

```java
// ❌ 坏代码：synchronized 导致 Pinning
public String fetchWithSynchronized() {
    synchronized (this) {  // ← Pinning！
        return httpClient.get("https://api.example.com/data");
        // 虚拟线程无法 unmount，Carrier 被占用
    }
}

// ✅ 好代码：ReentrantLock 替代
private final ReentrantLock lock = new ReentrantLock();

public String fetchWithLock() {
    lock.lock();
    try {
        return httpClient.get("https://api.example.com/data");
        // 虚拟线程可以正常 unmount/mount
    } finally {
        lock.unlock();
    }
}
```

```java
// Spring Boot 4.0 虚拟线程最佳实践

@Configuration
public class VirtualThreadConfig {
    
    // ① 自定义虚拟线程执行器
    @Bean("virtualThreadExecutor")
    public ExecutorService virtualThreadExecutor() {
        return Executors.newVirtualThreadPerTaskExecutor();
    }
    
    // ② 为数据库连接池等阻塞操作使用虚拟线程
    @Bean
    public JdbcClient jdbcClient(DataSource dataSource) {
        return JdbcClient.create(dataSource);
    }
}

@Service
public class OrderService {
    
    @Autowired
    @Qualifier("virtualThreadExecutor")
    private ExecutorService executor;
    
    // ③ 并发调用多个微服务
    public OrderDetail getOrderDetail(Long orderId) {
        try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
            // 三个虚拟线程并发执行
            Future<Order> orderFuture = scope.fork(() -> orderClient.getOrder(orderId));
            Future<User> userFuture = scope.fork(() -> userClient.getUser(userId));
            Future<List<Item>> itemsFuture = scope.fork(() -> itemClient.getItems(orderId));
            
            scope.join();           // 等待所有完成
            scope.throwIfFailed();  // 任一失败则抛异常
            
            return new OrderDetail(
                orderFuture.resultNow(),
                userFuture.resultNow(),
                itemsFuture.resultNow()
            );
        } catch (Exception e) {
            throw new RuntimeException("获取订单详情失败", e);
        }
    }
}
```

```
虚拟线程适用场景：

  ✅ 大量 IO 密集型任务（HTTP 调用、数据库查询、消息消费）
  ✅ "一个请求一个线程"的 Web 应用（Tomcat 线程池 → 虚拟线程）
  ✅ 微服务编排（并发调用多个下游服务）
  ✅ 消息消费（每个消息一个虚拟线程处理）

  ❌ CPU 密集型任务（计算、加密、压缩）→ 用平台线程池
  ❌ 需要线程局部变量精确控制的场景 → ThreadLocal 在虚拟线程中仍可用
  ❌ 大量使用 synchronized 的遗留代码 → 先迁移到 ReentrantLock
```

### 💡 延伸思考

1. **虚拟线程和 Kotlin 协程/Go Goroutine 有什么区别？** — 三者目标相同（轻量级并发），但实现不同。Go Goroutine 是语言级支持，有独立的栈管理；Kotlin 协程需要 suspend 关键字标记；Java 虚拟线程是 JVM 级支持，对代码无侵入——现有同步代码直接受益，不需要加任何关键字。这是 Java 虚拟线程最大的优势。
2. **虚拟线程是否意味着 Reactive 编程（WebFlux）过时了？** — 对于大多数业务场景，是的。虚拟线程让同步代码达到接近 Reactive 的吞吐量，且代码可读性、可调试性远优于 Reactive。但 Reactive 在流式处理（背压、数据流转换）场景仍有优势。Spring 官方的态度是"虚拟线程是默认选择，Reactive 是特殊场景的选择"。

**一、为什么需要 Resilience4j？——微服务容错的"安全气囊"**

在微服务架构中，服务间的调用链错综复杂。一个服务的故障可能像多米诺骨牌一样级联传播，最终导致整个系统崩溃（雪崩效应）。Resilience4j 提供了熔断、限流、重试、隔离、超时、缓存六大容错机制，是微服务高可用的基石。

```
微服务雪崩效应：

  用户 → 订单服务 → 库存服务 → 支付服务
                      │
                      ▼
                  库存服务故障（响应超时）
                      │
                      ▼
              订单服务线程池耗尽
                      │
                      ▼
              整个系统不可用！

  Resilience4j 的防御：
  - 熔断器：库存服务故障 → 快速失败，不再等待
  - 限流器：控制对库存服务的调用频率
  - 重试：网络抖动时自动重试
  - 隔离：库存服务的故障不影响其他服务
  - 超时：避免无限等待
```

**二、Resilience4j 六大核心模块**

| 模块 | 作用 | 典型场景 |
|------|------|---------|
| **CircuitBreaker** | 熔断器：故障时快速失败 | 下游服务不可用 |

| **Cache** | 缓存：缓存结果 | 减少重复调用 |

**三、熔断器（CircuitBreaker）——最核心的组件**

熔断器是 Resilience4j 的核心，模拟了电路断路器的行为：

```
熔断器三种状态：

  ┌──────────┐    失败率 ≥ 阈值     ┌──────────┐
  │  CLOSED  │ ──────────────────→ │   OPEN   │
  │ (正常)   │                      │ (熔断)   │
  │ 请求正常  │                      │ 快速失败  │
  │ 通过      │                      │          │
  └──────────┘                      └────┬─────┘
       ▲                                 │
       │                         等待时间到
       │                                 │
       │          ┌──────────┐           │
       └──────────│ HALF_OPEN │←─────────┘
                  │ (半开)    │
                  │ 放行少量  │
                  │ 请求试探  │
                  └────┬─────┘
                       │
              成功 → CLOSED
              失败 → OPEN（重新熔断）

  关键配置：
  - failureRateThreshold：失败率阈值（默认 50%）
  - slidingWindowSize：滑动窗口大小（默认 100 次调用）
  - waitDurationInOpenState：OPEN 状态持续时间（默认 60 秒）
  - permittedNumberOfCallsInHalfOpenState：HALF_OPEN 状态允许的试探请求数
  - minimumNumberOfCalls：最小调用次数（窗口内调用不足时不计算失败率）
```

```java
// Resilience4j 熔断器配置与使用
@Configuration
public class ResilienceConfig {
    
    @Bean
    public CircuitBreakerRegistry circuitBreakerRegistry() {
        CircuitBreakerConfig config = CircuitBreakerConfig.custom()
            .failureRateThreshold(50)           // 失败率 50% 触发熔断
            .slidingWindowType(SlidingWindowType.COUNT_BASED)  // 基于计数
            .slidingWindowSize(100)             // 窗口大小 100 次
            .minimumNumberOfCalls(10)           // 至少 10 次调用才计算
            .waitDurationInOpenState(Duration.ofSeconds(30))  // 熔断 30 秒
            .permittedNumberOfCallsInHalfOpenState(5)  // 半开时放行 5 个请求
            .recordExceptions(IOException.class, TimeoutException.class)  // 记录哪些异常
            .ignoreExceptions(BusinessException.class)  // 忽略业务异常
            .build();
        
        return CircuitBreakerRegistry.of(config);
    }
}

@Service
public class PaymentService {
    
    @Autowired
    private CircuitBreakerRegistry registry;
    
    private final CircuitBreaker circuitBreaker;
    
    public PaymentService(CircuitBreakerRegistry registry) {
        this.circuitBreaker = registry.circuitBreaker("paymentService");
    }
    
    public PaymentResult pay(PaymentRequest request) {
        // 方式一：函数式装饰
        Supplier<PaymentResult> supplier = CircuitBreaker
            .decorateSupplier(circuitBreaker, () -> paymentClient.pay(request));
        
        return Try.ofSupplier(supplier)
            .recover(CallNotPermittedException.class, e -> {
                log.warn("支付服务已熔断，使用降级方案");
                return PaymentResult.fallback();
            })
            .get();
    }
}
```

**四、限流器（RateLimiter）——令牌桶算法**

```
令牌桶算法原理：

  ┌─────────────────────────────────────┐
  │          令牌桶（容量 N）             │
  │  ┌───┐ ┌───┐ ┌───┐        ┌───┐   │
  │  │ T │ │ T │ │ T │  ...   │ T │   │
  │  └───┘ └───┘ └───┘        └───┘   │
  └─────────────────────────────────────┘
       │                          ▲
       │ 取令牌（每次请求）         │ 补充令牌（固定速率）
       ▼                          │
    请求处理                   定时器

  流程：
  ① 以固定速率向桶中补充令牌（如每秒 10 个）
  ② 桶满则丢弃多余令牌（防止突发流量透支）
  ③ 请求到达时从桶中取令牌
  ④ 有令牌 → 放行；无令牌 → 限流拒绝

  两种模式：
  - 令牌桶（Token Bucket）：允许一定突发（桶中积累的令牌可一次性消耗）
  - 固定窗口（Fixed Window）：严格按时间窗口计数
```

```java

    .limitForPeriod(10)              // 每个周期 10 个请求
    .limitRefreshPeriod(Duration.ofSeconds(1))  // 周期 1 秒
    .timeoutDuration(Duration.ofMillis(500))    // 等待令牌超时 500ms
    .build();

RateLimiter rateLimiter = RateLimiter.of("apiLimiter", config);

// 使用

    .decorateSupplier(rateLimiter, () -> callExternalApi());

// 等待令牌（最多 500ms），获取不到则抛异常

    .recover(RequestNotPermitted.class, e -> "限流，请稍后重试")
    .get();
```

### 📖 参考答案

**一、DDL 为什么是"高危操作"？——大表变更的痛点**

在 MySQL 5.5 及之前，执行 `ALTER TABLE` 会锁表——整个变更期间，表不可读写。对于千万级甚至亿级的大表，一个简单的加列操作可能需要数小时，期间业务完全不可用。这是生产环境最危险的数据库操作之一。

```
传统 DDL 的问题：

  ALTER TABLE orders ADD COLUMN remark VARCHAR(255);
  
  MySQL 5.5 行为：
  ① 创建临时表（新结构）
  ② 锁住原表（禁止读写！）
  ③ 逐行拷贝数据到临时表
  ④ 删除原表，重命名临时表
  ⑤ 释放锁
  
  1000 万行表 → 拷贝 ~10 分钟 → 业务中断 10 分钟！
```

**二、Online DDL 的三种算法——COPY vs INPLACE vs INSTANT**

MySQL 5.6 引入了 Online DDL，支持在不阻塞读写的情况下执行 DDL。MySQL 8.0 进一步引入了 INSTANT 算法。

```
三种算法对比：

  ┌────────────┬──────────────┬──────────────┬──────────────┐
  │    算法     │   执行方式    │  是否阻塞DML  │   MySQL版本   │
  ├────────────┼──────────────┼──────────────┼──────────────┤
  │ COPY       │ 创建临时表    │ ❌ 全程阻塞   │ 5.5 及之前    │
  │            │ 全量拷贝      │              │              │
  ├────────────┼──────────────┼──────────────┼──────────────┤
  │ INPLACE    │ 在原表上修改  │ ⚠️ 大部分不阻塞│ 5.6+         │
  │            │ 不创建临时表  │ 短暂元数据锁  │              │
  ├────────────┼──────────────┼──────────────┼──────────────┤
  │ INSTANT    │ 只修改元数据  │ ✅ 完全不阻塞 │ 8.0.12+      │
  │            │ 秒级完成      │              │              │
  └────────────┴──────────────┴──────────────┴──────────────┘
```

**三、Online DDL 的三个阶段——面试核心**

```
Online DDL 执行流程（INPLACE 算法）：

  Phase 1: Prepare（准备阶段）
  ┌─────────────────────────────────────────────────────────┐
  │ ① 获取 MDL（Metadata Lock）排他锁                        │
  │ ② 验证表结构、创建临时文件（frm/ibd）                     │
  │ ③ 初始化新索引结构                                      │
  │                                                         │
  │ ⚠️ 此阶段短暂阻塞读写（毫秒级）                           │
  └─────────────────────────────────────────────────────────┘
                            │
                            ▼
  Phase 2: Execute（执行阶段）
  ┌─────────────────────────────────────────────────────────┐
  │ ① 降级 MDL 为共享锁 → 允许并发 DML                       │
  │ ② 扫描原表数据，逐行构建新索引/新结构                     │
  │ ③ 同时记录 DML 产生的变更到 Online Log（在线日志）        │
  │                                                         │
  │ ✅ 此阶段不阻塞读写（耗时最长，可能数小时）                │
  └─────────────────────────────────────────────────────────┘
                            │
                            ▼
  Phase 3: Commit（提交阶段）
  ┌─────────────────────────────────────────────────────────┐
  │ ① 重新获取 MDL 排他锁                                    │
  │ ② 重放 Online Log 中的增量变更                           │
  │ ③ 替换旧的表结构/索引                                    │
  │ ④ 释放 MDL 锁                                           │
  │                                                         │
  │ ⚠️ 此阶段短暂阻塞读写（取决于 Online Log 大小）           │
  └─────────────────────────────────────────────────────────┘
```

```
关键面试点：

  Q: Online DDL 真的完全不阻塞吗？
  A: 不是。Prepare 和 Commit 阶段需要短暂的 MDL 排他锁。
     如果 Prepare 阶段有长事务持有 MDL 共享锁，DDL 会一直等待
     → 后续所有读写请求也会被阻塞（因为它们在等待 DDL 释放 MDL）
     → 这就是经典的"DDL 导致数据库雪崩"场景！

  Q: 如何避免 DDL 阻塞？
  A: ① 执行前检查是否有长事务（information_schema.innodb_trx）
     ② 设置 lock_wait_timeout（DDL 等待 MDL 锁的超时时间）
     ③ 低峰期执行
     ④ 用 pt-online-schema-change 或 gh-ost 工具
```

**四、常见 DDL 操作的算法支持矩阵**

| DDL 操作 | MySQL 5.6 | MySQL 5.7 | MySQL 8.0 |
|----------|-----------|-----------|-----------|
| 添加列（末尾） | INPLACE | INPLACE | **INSTANT** ✅ |
| 添加列（指定位置） | COPY | INPLACE | INPLACE |
| 删除列 | INPLACE | INPLACE | **INSTANT** ✅ |
| 修改列类型 | COPY | COPY/INPLACE* | COPY/INPLACE* |
| 重命名列 | INPLACE | INPLACE | **INSTANT** ✅ |

| 添加全文索引 | INPLACE | INPLACE | INPLACE |
| 修改默认值 | INPLACE | INPLACE | **INSTANT** ✅ |

```
*修改列类型：同类型扩展（VARCHAR(50)→VARCHAR(100)）支持 INPLACE；
  跨类型修改（VARCHAR→INT）必须 COPY
```

**五、大表变更的三种方案对比——生产环境必备**

对于千万级以上的大表，直接执行 Online DDL 仍有风险（主从延迟、磁盘空间、MDL 锁等待）。业界有三种主流方案：

```
方案对比：

  ┌──────────────┬──────────────────┬──────────────────┬──────────────────┐
  │    维度       │   Online DDL     │ pt-osc (Percona) │     gh-ost       │
  │              │   (MySQL 原生)    │                  │   (GitHub)       │
  ├──────────────┼──────────────────┼──────────────────┼──────────────────┤
  │ 原理          │ InnoDB 内部实现  │ 触发器同步增量    │ Binlog 同步增量  │
  │ 是否需要触发器 │ ❌               │ ✅ 需要          │ ❌ 不需要        │
  │ 对主库影响    │ 中等             │ 中等             │ 低（可暂停）     │
  │ 是否可暂停    │ ❌               │ ❌               │ ✅ 可随时暂停    │
  │ 是否可限速    │ ❌               │ ✅               │ ✅               │
  │ 磁盘空间      │ 需要临时文件     │ 需要临时表       │ 需要临时表       │
  │ 外键支持      │ ✅               │ ⚠️ 有限          │ ❌ 不支持        │
  │ 触发器风险    │ 无               │ 有（性能开销）    │ 无               │
  │ 推荐场景      │ 小表/非核心表    │ 传统方案          │ 大表/核心表 ⭐   │
  └──────────────┴──────────────────┴──────────────────┴──────────────────┘
```

```
gh-ost 工作原理（推荐方案）：

  ① 在从库上创建幽灵表（ghost table）_orders_gho
  ② 从主库 Binlog 中读取 orders 表的变更事件
  ③ 将原表数据分批拷贝到幽灵表（可限速、可暂停）
  ④ 同时将 Binlog 中的增量变更应用到幽灵表
  ⑤ 数据同步完成后，执行 CUT-OVER（原子切换表名）
  
  优势：
  - 不依赖触发器（无性能开销）
  - 可随时暂停和限速（对业务影响可控）
  - 切换瞬间完成（原子 rename）
  - 可在从库测试后再在主库执行
```

```bash

  --host=127.0.0.1 \
  --user=root \
  --database=mydb \

  --max-load=Threads_running=25 \  # 负载过高自动暂停
```

### 💡 延伸思考

1. **为什么 MySQL 8.0 的 INSTANT 算法这么快？** — INSTANT 算法只修改数据字典（Data Dictionary）中的表定义，不触碰实际数据。InnoDB 在读取数据行时，会根据数据字典动态"填充"新增列的默认值。所以 INSTANT 是真正的 O(1) 操作，与表大小无关。但 INSTANT 有次数限制（默认 64 次），超过后需要用 INPLACE 重建表。
2. **gh-ost 的 CUT-OVER 是怎么做到原子切换的？** — gh-ost 使用 MySQL 的原子 RENAME TABLE 操作：`RENAME TABLE orders TO _orders_del, _orders_gho TO orders`。这是一个原子操作，切换瞬间完成，不会出现"表不存在"的窗口期。

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-15 早间报告 — "Spring Boot = 2026年Java工程师生存必修课" + 午后报告 — "基础八股文仍然是面试必考"

### 📖 参考答案

**一、Redis 为什么需要持久化？——内存是易失的**

Redis 是内存数据库，所有数据在内存中。一旦进程退出或服务器宕机，内存中的数据全部丢失。持久化就是将内存数据保存到磁盘，以便重启后恢复。

```
Redis 持久化的两种方式：

  RDB（Redis Database）：快照持久化
  → 在某个时间点，将内存中所有数据生成一个二进制快照文件（dump.rdb）

  AOF（Append Only File）：追加日志持久化
  → 将每条写命令追加到日志文件中，重启时重放命令恢复数据

  混合持久化（Redis 4.0+）：
  → RDB 快照 + AOF 增量日志 = 恢复快 + 数据安全
```

**二、RDB 快照——SAVE vs BGSAVE**

```
RDB 的两种触发方式：

  ① SAVE（同步阻塞）：
     主线程执行快照 → 阻塞所有客户端请求 → 直到快照完成
     ❌ 生产环境禁用！数据量大时阻塞数秒甚至数分钟

  ② BGSAVE（异步非阻塞）：
     Fork 子进程 → 子进程执行快照 → 主线程继续处理请求
     ✅ 生产环境唯一选择

  BGSAVE 的 Copy-On-Write（写时复制）原理：
  
  ① Redis 调用 fork() 创建子进程
     - 父子进程共享同一块物理内存（页表标记为只读）
     - fork() 本身很快（复制页表，不复制数据）
  
  ② 子进程遍历内存数据，写入 RDB 文件
     - 子进程读取数据 → 读的是共享内存（不会触发复制）
  
  ③ 主线程继续处理写请求
     - 写操作 → 触发页异常 → 操作系统复制该内存页
     - 只有被修改的页才会复制（Copy-On-Write）
     - 未修改的页仍然共享
  
  ④ 子进程完成快照 → 退出 → 新的 RDB 文件替换旧的
```

```
RDB 配置：

  # redis.conf
  save 900 1      # 900 秒内至少 1 次修改 → 触发 BGSAVE
  save 300 10     # 300 秒内至少 10 次修改 → 触发 BGSAVE
  save 60 10000   # 60 秒内至少 10000 次修改 → 触发 BGSAVE
  
  dbfilename dump.rdb
  dir /var/lib/redis/

  RDB 优点：
  ✅ 文件紧凑（二进制压缩），适合备份和灾难恢复
  ✅ 恢复速度快（直接加载到内存）
  ✅ 对性能影响小（子进程操作，主线程不阻塞）

  RDB 缺点：
  ❌ 数据可能丢失（两次快照之间的数据）
  ❌ fork() 在大数据量时可能耗时较长（GB 级内存）
  ❌ 子进程占用额外内存（Copy-On-Write 的复制开销）
```

**三、AOF 日志——三种刷盘策略**

AOF 记录的是 Redis 的写命令（RESP 协议格式），重启时重放命令恢复数据。

```
AOF 三种刷盘策略（appendfsync）：

  ┌────────────┬──────────────────┬──────────────────┐
  │   策略      │      行为        │      权衡         │
  ├────────────┼──────────────────┼──────────────────┤
  │ always     │ 每条命令都 fsync  │ 最安全，性能最差   │
  │            │                  │ 最多丢 1 条命令   │
  ├────────────┼──────────────────┼──────────────────┤
  │ everysec   │ 每秒 fsync 一次  │ ⭐ 推荐！         │
  │ (默认)     │                  │ 最多丢 1 秒数据   │
  ├────────────┼──────────────────┼──────────────────┤
  │ no         │ 交给操作系统决定  │ 性能最好，最不安全 │
  │            │                  │ 可能丢 30 秒数据  │
  └────────────┴──────────────────┴──────────────────┘

  为什么 everysec 是最佳选择？
  - always：每次写入都 fsync → 磁盘 IO 成为瓶颈 → QPS 大幅下降
  - everysec：批量 fsync → 性能接近无持久化 → 最多丢 1 秒数据（可接受）
  - no：不可控 → 不推荐
```

**AOF 重写（Rewrite）——解决 AOF 文件膨胀**

```
AOF 重写原理：

  问题：AOF 文件会不断增长
  例：对同一个 key 执行 100 次 INCR → AOF 记录 100 条命令
      但实际只需要 1 条 SET key 100

  AOF 重写：
  ① fork 子进程
  ② 子进程根据当前内存数据，生成新的 AOF 文件（最小命令集）
  ③ 期间主线程的写命令同时写入 AOF 重写缓冲区
  ④ 子进程完成后，将缓冲区中的增量命令追加到新 AOF 文件
  ⑤ 原子替换旧的 AOF 文件

  触发条件：
  auto-aof-rewrite-percentage 100  # AOF 文件增长 100% 触发
  auto-aof-rewrite-min-size 64mb   # AOF 文件至少 64MB
```

**四、混合持久化（Redis 4.0+）——最佳实践**

混合持久化结合了 RDB 和 AOF 的优点：

```
混合持久化原理：

  AOF 文件结构：
  ┌─────────────────────────────────────────────────────────┐
  │                     AOF 文件                             │
  ├─────────────────────────────────────────────────────────┤
  │  [RDB 二进制数据]  │  [AOF 增量命令]  │  [AOF 增量命令]  │
  │  ← 重写时生成 →   │  ← 重写后的写命令 →                 │
  └─────────────────────────────────────────────────────────┘

  流程：
  ① AOF 重写时，子进程先生成当前数据的 RDB 快照
  ② 将 RDB 快照写入 AOF 文件头部
  ③ 将重写期间的增量命令以 AOF 格式追加
  ④ 后续的写命令继续以 AOF 格式追加

  优势：
  ✅ 恢复速度快（RDB 部分直接加载，比逐条重放 AOF 快）
  ✅ 数据安全（AOF 部分保证增量不丢失）
  ✅ 文件更小（RDB 二进制比 AOF 文本紧凑）
```

```conf
# redis.conf — 混合持久化配置
appendonly yes                    # 开启 AOF
appendfsync everysec              # 每秒刷盘
aof-use-rdb-preamble yes          # 开启混合持久化（Redis 5.0+ 默认开启）
```

**五、RDB vs AOF vs 混合持久化——如何选择？**

| 维度 | RDB | AOF | 混合持久化 |
|------|-----|-----|-----------|
| **数据安全性** | ⭐⭐ 可能丢几分钟 | ⭐⭐⭐⭐ 最多丢 1 秒 | ⭐⭐⭐⭐ 最多丢 1 秒 |
| **恢复速度** | ⭐⭐⭐⭐⭐ 极快 | ⭐⭐ 慢（逐条重放） | ⭐⭐⭐⭐ 快 |
| **文件大小** | ⭐⭐⭐⭐ 小 | ⭐⭐ 大 | ⭐⭐⭐ 中等 |
| **写入性能影响** | ⭐⭐⭐⭐ 小 | ⭐⭐⭐ 中等 | ⭐⭐⭐ 中等 |
| **fork 开销** | 有 | 有（重写时） | 有（重写时） |

```
推荐策略：

  ① 生产环境：混合持久化（默认推荐）
     appendonly yes + aof-use-rdb-preamble yes
  
  ② 缓存场景（数据可重建）：只开 RDB
     数据从数据库重建，持久化只是加速恢复
  
  ③ 高安全场景（如订单/支付）：混合持久化 + 主从复制
     持久化 + 副本 = 双重保障
```

### 💡 延伸思考

1. **Redis 宕机后恢复流程是怎样的？** — 如果开启了 AOF（含混合持久化），优先加载 AOF 文件（因为更完整）；如果只开了 RDB，加载 RDB 文件。加载顺序：检查 AOF 是否存在 → 存在则加载 AOF → 不存在则加载 RDB → 都没有则启动空数据库。
2. **fork() 在大内存场景下的风险？** — fork() 会复制父进程的页表，虽然不复制数据，但页表本身也占用内存。10GB 的 Redis 实例，页表约 20MB；100GB 实例，页表约 200MB。更危险的是 Copy-On-Write：如果子进程存续期间有大量写入，内存使用量可能翻倍。建议：① 预留 1.5-2 倍内存；② 在低写入时段触发 BGSAVE/AOF Rewrite。

**一、Agent 是什么？——从"回答问题"到"完成任务"**

传统 Chatbot（如 ChatGPT 早期版本）只能"对话"——你问它答，没有行动能力。AI Agent 则是一个能自主感知、思考、行动的智能体——它可以调用工具、查询数据库、发送邮件、操作 API，真正"完成任务"。

```
Chatbot vs Agent：

  Bot："抱歉，我无法获取实时天气信息。"

  Agent：

  Agent：

    ③ Observation：晴，25°C
    ④ Response："北京今天晴天，气温 25°C，适合出行！"

  核心差异：Agent 有"行动能力"——它不只是说话，而是做事。
```

**三、ReAct 模式——Agent 的"思考-行动"循环**

ReAct（Reasoning + Acting）是 Agent 最核心的工作模式，由 Google DeepMind 在 2022 年提出，2026 年已成为 Agent 开发的事实标准。

```
ReAct 循环：Thought → Action → Observation → Thought → ...

  用户："帮我查一下订单 ORD-12345 的状态，如果已发货就查物流"

  ┌─────────────────────────────────────────────────────────┐
  │ Step 1:                                                 │
  │   Thought: 用户想查订单状态，我需要调用订单查询工具       │
  │   Action: query_order(order_id="ORD-12345")             │
  │   Observation: {status: "已发货", tracking: "SF123456"} │
  ├─────────────────────────────────────────────────────────┤
  │ Step 2:                                                 │
  │   Thought: 订单已发货，用户还想查物流，我需要调用物流工具 │
  │   Action: query_logistics(tracking_no="SF123456")       │
  │   Observation: {location: "北京分拣中心", eta: "明天"}  │
  ├─────────────────────────────────────────────────────────┤
  │ Step 3:                                                 │
  │   Thought: 信息齐全，可以回复用户了                      │
  │   Response: "您的订单 ORD-12345 已发货（顺丰 SF123456），│
  │             目前在北京市分拣中心，预计明天送达。"         │
  └─────────────────────────────────────────────────────────┘
```

```
ReAct 的关键设计：

  ① 循环终止条件：
     - LLM 认为任务完成 → 输出最终回复
     - 达到最大步数限制（如 10 步）→ 强制终止
     - 连续失败 → 异常终止

  ② 防止死循环：
     - 设置 max_iterations（最大迭代次数）
     - 检测重复 Action（连续 3 次相同操作 → 终止）
     - 超时保护（单次循环超过 30 秒 → 终止）

  ③ 错误处理：
     - 工具调用失败 → 将错误信息作为 Observation 回传
     - LLM 看到错误后可以调整策略（换工具/换参数/告知用户）
```

**四、Function Calling 技术原理——Agent 的"手"**

Function Calling 是 LLM 调用外部工具的核心机制。以 OpenAI 兼容 API 为例：

```
Function Calling 完整流程：

  ① 定义工具（JSON Schema）
  ┌─────────────────────────────────────────────────────────┐
  │ {                                                       │
  │   "name": "get_weather",                                │
  │   "description": "查询指定城市的实时天气",                │
  │   "parameters": {                                       │
  │     "type": "object",                                   │
  │     "properties": {                                     │
  │       "city": {                                         │
  │         "type": "string",                               │
  │         "description": "城市名称，如北京、上海"           │
  │       }                                                 │
  │     },                                                  │
  │     "required": ["city"]                                │
  │   }                                                     │
  │ }                                                       │
  └─────────────────────────────────────────────────────────┘

  ② 用户消息 + 工具定义 → 发送给 LLM
  ③ LLM 返回 function_call（不是文本回复！）
     {
       "function_call": {
         "name": "get_weather",
         "arguments": "{\"city\": \"北京\"}"
       }
     }
  
  ④ 应用执行函数
     result = weatherApi.query("北京")  // → {temp: 25, desc: "晴"}
  
  ⑤ 结果回传给 LLM
     {
       "role": "function",
       "name": "get_weather",
       "content": "{\"temp\": 25, \"desc\": \"晴\"}"
     }
  
  ⑥ LLM 基于结果生成最终回复
     "北京今天晴天，气温 25°C"
```

```java
// Spring AI Function Calling 实现
@Configuration
public class AgentConfig {
    
    // 定义工具 —— 和写普通 Service 一样
    @Bean
    @Description("查询指定城市的实时天气")
    public Function<WeatherRequest, WeatherResponse> getWeather() {
        return request -> weatherService.query(request.city());
    }
    
    @Bean
    @Description("查询订单详情，参数为订单ID")
    public Function<OrderRequest, OrderResponse> queryOrder() {
        return request -> orderService.getById(request.orderId());
    }
}

// 使用
@RestController
public class AgentController {
    
    @Autowired
    private ChatClient chatClient;
    
    @GetMapping("/agent/chat")
    public String chat(@RequestParam String message) {
        // Spring AI 自动将 @Bean 方法注册为 Function Calling 工具
        return chatClient.prompt()
            .user(message)
            .call()
            .content();
    }
}
```

**五、多工具编排的常见模式**

```
① 顺序调用（Sequential）：
   一个工具的输出是下一个工具的输入
   
   用户："查订单 ORD-123 的收货人手机号，然后查这个手机号的会员等级"
   → query_order → 提取 phone → query_member_level
   
   实现：ReAct 循环自动处理

② 并行调用（Parallel）：
   多个工具互不依赖，同时调用
   
   用户："比较北京、上海、广州今天的天气"
   → get_weather("北京") + get_weather("上海") + get_weather("广州")
   → 三个调用同时发出，等待全部返回后汇总
   
   实现：识别独立调用 → 并发执行 → 结果聚合

③ 条件路由（Conditional）：
   根据中间结果决定下一步
   
   用户："帮我退款订单 ORD-123"
   → query_order → 检查状态
     → 已发货：先 create_return_order → 再 process_refund
     → 未发货：直接 cancel_order
   
   实现：LLM 在 Thought 阶段判断，选择不同 Action

④ 人机协作（Human-in-the-Loop）：
   敏感操作需要人类确认
   
   用户："给所有 VIP 用户发 100 元优惠券"
   → Agent："检测到批量操作，涉及 5000 个用户，总金额 50 万元，
            请确认是否执行？"
   → 用户确认 → 执行
```

### 💡 延伸思考

1. **Agent 的"幻觉"问题在行动场景中更危险——如何防范？** — Chatbot 的幻觉只是说错话，Agent 的幻觉可能真的去执行错误操作（如误删数据）。防范措施：① 敏感操作（写/删）必须 Human-in-the-Loop 确认；② 工具层做参数校验（金额 > 1000 拒绝）；③ 操作日志 + 审计（所有 Agent 操作可追溯）；④ 沙箱环境（先在测试环境验证）。
