## 题目 1：[Java基础/JVM] 请详细阐述 Java 类加载机制与双亲委派模型（Parent Delegation Model）的原理、作用及如何打破它

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-22 早间报告 — "Java面试高频考点：类加载机制（双亲委派模型）、JVM调优、Spring源码、并发编程"
**相关岗位**：Java后端 / 基础架构 / Android开发

### 📖 参考答案

#### 一、类加载过程回顾

一个 Java 类从被加载到 JVM 到卸载出内存，经历 7 个阶段：**加载（Loading）→ 验证（Verification）→ 准备（Preparation）→ 解析（Resolution）→ 初始化（Initialization）→ 使用（Using）→ 卸载（Unloading）**。其中验证、准备、解析统称为**连接（Linking）**。

关键阶段说明：
- **加载**：通过全类名获取二进制字节流（ZIP/JAR/网络/动态代理），将静态存储结构转为方法区运行时数据结构，在堆中生成 Class 对象
- **验证**：文件格式验证 → 元数据验证 → 字节码验证 → 符号引用验证
- **准备**：为类变量（static）分配内存并设零值（`public static int value = 111` → 准备阶段 value=0，初始化阶段才赋 111；但 `static final` 直接在准备阶段赋值）
- **解析**：将常量池中的符号引用替换为直接引用（内存指针或偏移量）
- **初始化**：执行 `<clinit>()` 方法，JVM 保证线程安全

#### 二、双亲委派模型

**三个默认类加载器（JDK 9+ 有调整，但委派逻辑一致）：**

```
Bootstrap ClassLoader（启动类加载器）
    ↑ 委派
Extension / Platform ClassLoader（扩展/平台类加载器）
    ↑ 委派
Application ClassLoader（应用类加载器）
```

**工作流程：**

当一个类加载器收到类加载请求时：
1. 它不会自己先加载，而是**先将请求委派给父类加载器**
2. 父类加载器同样委派给它的父类
3. 最终到达 Bootstrap ClassLoader
4. 如果父类加载器能加载，则直接返回；不能加载，才由子加载器尝试加载

```java
// ClassLoader.loadClass() 核心逻辑（简化）
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        // 1. 检查是否已加载
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                if (parent != null) {
                    // 2. 委派给父加载器
                    c = parent.loadClass(name, false);
                } else {
                    // 3. 没有父加载器 → Bootstrap ClassLoader
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 父加载器无法加载
            }
            if (c == null) {
                // 4. 自己尝试加载
                c = findClass(name);
            }
        }
        return c;
    }
}
```

#### 三、为什么需要双亲委派？

| 优势 | 说明 |
|------|------|
| **安全性** | 防止核心 API 被篡改。比如自定义 `java.lang.String` 会被委派到 Bootstrap 加载，保证 JDK 核心类不被替换 |
| **避免重复加载** | 父加载器加载过的类，子加载器不会重复加载 |
| **类唯一性** | 同一个类由同一个加载器加载，保证 `instanceof` 等判断正确 |

#### 四、如何打破双亲委派模型？

**方式 1：重写 loadClass() 方法（最常见）**

不遵循"先委派后自己"的顺序，直接调用 `findClass()` 或自定义加载逻辑：

```java
public class MyClassLoader extends ClassLoader {
    @Override
    public Class<?> loadClass(String name) throws ClassNotFoundException {
        // 打破委派：核心类还是交给父加载器，其他类自己加载
        if (name.startsWith("java.")) {
            return super.loadClass(name);
        }
        byte[] classData = loadClassFromCustomSource(name);
        return defineClass(name, classData, 0, classData.length);
    }
}
```

**方式 2：线程上下文类加载器（Thread Context ClassLoader）**

JCA/JNDI/JDBC/JPA 等 SPI 机制的核心。父加载器（Bootstrap/Extension）加载的代码需要调用子加载器（Application）才能看到的实现类时，通过 `Thread.currentThread().getContextClassLoader()` 获取：

```java
// JDBC DriverManager 获取驱动的典型场景
ServiceLoader<Driver> loadedDrivers = ServiceLoader.load(Driver.class);
// ServiceLoader 内部使用线程上下文类加载器加载第三方驱动实现
```

**方式 3：热部署/热替换（Tomcat 等 Web 容器）**

Tomcat 为每个 Web 应用创建独立的 WebAppClassLoader，优先加载 `/WEB-INF/lib/` 和 `/WEB-INF/classes/` 下的类，打破双亲委派。这样不同应用可以部署不同版本的同一依赖，互不干扰。

#### 五、面试常问场景

```
场景 1：能否自己写一个 java.lang.String 类并加载？
→ 不能。双亲委派会将其委派给 Bootstrap ClassLoader，它只加载 rt.jar 中的标准 String 类。
  即使你自定义 ClassLoader 并强制加载，JVM 也会在包名冲突时报 SecurityException。

场景 2：Tomcat 如何实现不同应用使用不同版本的 Spring？
→ 每个 WebAppClassLoader 优先加载本应用的类，打破了双亲委派。

场景 3：SPI 机制为什么需要打破双亲委派？
→ DriverManager（Bootstrap 加载）需要加载第三方 JDBC 驱动（Application 加载），
  父加载器看不到子加载器的类，必须通过线程上下文类加载器"逆向"获取。
```

## 题目 2：[Java并发] 请详细阐述 synchronized 底层实现原理与锁升级机制（偏向锁→轻量级锁→重量级锁）

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-22 早间报告 — "Java面试高频考点：并发编程"
**相关岗位**：Java后端 / 高并发系统

### 📖 参考答案

#### 一、synchronized 的三种使用形式

```java
// 1. 修饰实例方法 → 锁是当前实例对象
public synchronized void method() { ... }

// 2. 修饰静态方法 → 锁是当前类的 Class 对象
public static synchronized void staticMethod() { ... }

// 3. 修饰代码块 → 锁是指定的对象
public void block() {
    synchronized (this) { ... }
}
```

三种形式最终都对应**管程（Monitor）**的进入和退出，但底层实现不同。

#### 二、Java 对象头与 Mark Word

synchronized 的锁信息存储在 Java 对象的**对象头（Object Header）**中。对象头包含 Mark Word（标记字段）和 Klass Pointer（类指针）。

**Mark Word 在 64 位 JVM 中的布局（关键部分）：**

| 锁状态 | 标志位 | 存储内容 |
|--------|--------|---------|
| 无锁 | 01 | 偏向线程ID=0，epoch=0 |
| 偏向锁 | 01 | 偏向线程ID，epoch，是否可偏向 |
| 轻量级锁 | 00 | 指向栈中锁记录的指针 |
| 重量级锁 | 10 | 指向 Monitor（管程）的指针 |
| GC 标记 | 11 | 空（GC 使用） |

#### 三、锁升级全过程（JDK 6 优化后的核心机制）

JDK 6 之前，synchronized 是重量级操作（直接依赖 OS 互斥量）。JDK 6 引入**锁升级**机制，锁可以"膨胀"但不可降级（GC 除外）。

```
升级路径：无锁 → 偏向锁 → 轻量级锁 → 重量级锁（单向不可逆）
```

**阶段 1：偏向锁（Biased Locking）**

```
场景：只有一个线程反复进入同步块
原理：Mark Word 记录线程 ID，后续该线程进入时无需 CAS 操作
性能：几乎零开销

触发条件：
  - JDK 6 默认开启，JDK 15 默认关闭，JDK 21 已废弃
  - 可通过 -XX:+UseBiasedLocking 开启（JDK 15-20）

撤销条件：
  - 另一个线程尝试竞争锁 → 升级为轻量级锁
  - 偏向锁撤销需要等待全局安全点（STW），成本很高
```

**阶段 2：轻量级锁（Lightweight Locking）**

```
场景：多线程交替执行，没有实际竞争（或竞争不激烈）
原理：CAS 操作将 Mark Word 替换为指向栈中 Lock Record 的指针
性能：CAS 自旋，不阻塞线程

流程：
  1. 线程在自己的栈帧中创建 Lock Record
  2. CAS 尝试将对象头的 Mark Word 替换为指向 Lock Record 的指针
  3. CAS 成功 → 获取轻量级锁
  4. CAS 失败 → 检查 Mark Word 是否指向当前线程的 Lock Record
     - 是 → 重入（锁计数+1）
     - 否 → 存在真实竞争 → 膨胀为重量级锁
```

**阶段 3：重量级锁（Heavyweight Locking）**

```
场景：多线程真实竞争，CAS 自旋无法获取
原理：依赖操作系统互斥量（Mutex Lock），线程阻塞进入等待队列
性能：涉及用户态→内核态切换，开销最大

流程：
  1. 锁膨胀：JVM 为对象分配 Monitor 对象
  2. 未获取锁的线程被阻塞（BLOCKED 状态）
  3. 持有锁的线程释放时，唤醒等待队列中的线程
  4. 涉及操作系统调度，上下文切换成本高
```

#### 四、锁升级决策流程图

```
线程尝试进入 synchronized 块
        │
        ▼
  是否可偏向？
  ├─ 是 → CAS 设置偏向线程 ID
  │      ├─ 成功 → 偏向锁（直接执行）
  │      └─ 失败 → 撤销偏向 → 升级
  └─ 否 → 尝试轻量级锁
           ├─ CAS 替换 Mark Word 成功 → 轻量级锁
           └─ CAS 失败 → 检查是否重入
                ├─ 是 → 重入计数
                └─ 否 → 膨胀为重量级锁（线程阻塞）
```

#### 五、锁对比总结

| 锁类型 | 优点 | 缺点 | 适用场景 |
|--------|------|------|---------|
| 偏向锁 | 加锁解锁无额外开销 | 撤销需 STW | 单线程访问 |
| 轻量级锁 | 自旋等待，不阻塞 | 长时间自旋浪费 CPU | 线程交替执行，低竞争 |
| 重量级锁 | 线程阻塞不消耗 CPU | 上下文切换成本高 | 高竞争、长耗时操作 |

#### 六、JDK 21+ 的锁优化趋势

- **偏向锁已废弃**（JDK 21）：因为偏向锁的撤销逻辑复杂且需要 STW，维护成本高，现代高并发场景收益有限
- **虚拟线程 + synchronized**：虚拟线程遇到重量级锁时会发生"pinning"（钉住载体线程），建议用 `ReentrantLock` 替代
- **锁粗化与锁消除**：JIT 编译器的优化，自动合并相邻同步块或消除不必要的锁

**参考来源**：
- https://javaguide.cn/java/concurrent/synchronized-principle-and-lock-upgrade.html — synchronized 原理与锁升级
- 《深入理解 Java 虚拟机（第 3 版）》第 13 章 — 线程安全与锁优化

## 题目 3：[AI/大模型] 请详细阐述 AI Agent 系统设计的核心架构：从 Prompt 工程、工具调用（Function Calling）、记忆管理到多 Agent 协作

**难度**：⭐⭐⭐⭐⭐
**考点来源**：2026-06-22 午间报告 — "字节AI Agent开发暑期实习4面面经：Prompt工程、Agent系统设计、上下文与记忆管理"
**相关岗位**：AI应用开发 / Agent开发 / 全栈

### 📖 参考答案

#### 一、什么是 AI Agent？

AI Agent 是能够**自主感知环境、制定计划、调用工具、执行动作并记忆上下文**的智能体系统。与简单的 LLM 对话不同，Agent 具备"感知→思考→行动→观察"的循环能力。

```
传统 LLM：用户提问 → 模型回答（一次性）
AI Agent：用户目标 → 模型规划 → 调用工具 → 观察结果 → 调整计划 → 完成任务
```

#### 二、Agent 核心架构

```
┌─────────────────────────────────────────────┐
│                  Agent 系统                    │
│  ┌─────────┐  ┌─────────┐  ┌─────────────┐  │
│  │ 感知层   │→│ 规划层   │→│ 执行层       │  │
│  │ (Prompt  │  │ (ReAct/ │  │ (Tool Call  │  │
│  │  解析)   │  │  CoT)   │  │  /API)      │  │
│  └─────────┘  └─────────┘  └─────────────┘  │
│        │            │              │         │
│        ▼            ▼              ▼         │
│  ┌─────────────────────────────────────┐     │
│  │           记忆管理层                   │     │
│  │  (短期记忆 / 长期记忆 / 向量检索)      │     │
│  └─────────────────────────────────────┘     │
└─────────────────────────────────────────────┘
```

#### 三、Prompt 工程与输入理解

**核心目标**：将用户意图翻译成模型最容易理解的形式。

```java
// System Prompt 设计示例
String systemPrompt = """
你是一个智能编程助手 Agent。你的能力：
1. 代码生成与审查
2. 调用 Git API 管理仓库
3. 执行 Shell 命令

规则：
- 每次只执行一个工具调用
- 观察工具返回结果后再决定下一步
- 如果工具调用失败，尝试替代方案
- 如果不知道答案，直接说不知道
""";
```

**关键概念**：
- **System Prompt**：设定角色和行为边界，整个对话周期生效
- **Few-shot**：给模型看几个例子，比写一堆规则管用
- **Chain-of-Thought（CoT）**：让模型输出推理过程，减少复杂任务出错
- **上下文腐化（Context Degradation）**：多轮对话中早期上下文被稀释，模型注意力下降 → 需要做记忆压缩

#### 四、工具调用（Function Calling / Tool Use）

Agent 通过 Function Calling 获取实时数据或执行操作，这是 Agent 区别于纯 LLM 的核心能力。

```json
// Function Calling 定义示例
{
  "type": "function",
  "function": {
    "name": "search_code",
    "description": "搜索代码仓库中的文件",
    "parameters": {
      "type": "object",
      "properties": {
        "query": {"type": "string", "description": "搜索关键词"},
        "repo": {"type": "string", "description": "仓库路径"}
      },
      "required": ["query"]
    }
  }
}
```

**Function Calling vs RAG 的区别**：

| 维度 | Function Calling | RAG |
|------|----------------|-----|
| 数据来源 | 实时 API / 数据库 | 离线文档 / 知识库 |
| 数据结构 | 结构化数据 | 非结构化文本 |
| 典型场景 | 查天气、查股票、执行操作 | 查公司文档、产品手册 |
| 实现方式 | 模型选择函数并传参 | 向量检索 + 上下文注入 |

**实际项目中两者常结合使用**：RAG 提供知识背景，Function Calling 提供实时数据和执行能力。

#### 五、记忆管理（Memory Management）

记忆分层：

1. **上下文窗口有限** → 滑动窗口 + 关键信息摘要
2. **上下文腐化** → 优先保留 System Prompt 和最近的交互，丢弃中间冗余内容
3. **长期记忆** → 定期对历史对话做摘要压缩，存入向量数据库
4. **Lost in the Middle** → 重要信息放在开头和结尾，中间位置容易被忽略

- **限流与路由**：混合路由策略，根据任务类型分发到不同的子 Agent

## 题目 4：[安全/框架] 请详细说明 CVE-2026-42779 Apache MINA 反序列化漏洞的原理、影响范围及修复方案，并谈谈 Java 后端安全加固的实践

**难度**：⭐⭐⭐
**考点来源**：2026-06-22 早间 & 午间报告 — "CVE-2026-42779 Apache MINA反序列化漏洞，Java项目需排查升级"
**相关岗位**：Java后端 / 安全工程师 / 基础架构

### 📖 参考答案

#### 一、漏洞概述

CVE-2026-42779 是 Apache MINA 框架的反序列化远程代码执行（RCE）漏洞，CVSS 评分 **9.8（严重）**。它是对三个月前 CVE-2026-41635 的**补丁绕过**——官方初代修复只堵了 `resolveClass` 入口，攻击者改一个字节就能通过 `readClassDescriptor` 旁路绕过白名单。

**影响版本**：

**为什么初代补丁失效？**

Java 原生序列化数据流中，类描述符有两种处理路径：
- **resolveClass**：正常路径，初代补丁在这里加了白名单 ✅

#### 二、堆内存分配与对象生命周期

#### 三、GC 收集器选型对比

| 收集器 | 适用场景 | 原理 | 优缺点 |
|--------|---------|------|--------|
| **Serial** | 单核/客户端/小堆 | 单线程 STW | 简单高效，但停顿时间长 |
| **Parallel Scavenge** | 多核/高吞吐量 | 多线程并行 | 吞吐量优先，适合后台计算 |
| **G1**（JDK 9+ 默认） | 大堆（4G+）/低延迟 | Region 化，分区回收 | 可预测停顿，平衡吞吐和延迟 |
| **ZGC**（JDK 21+ 生产就绪） | 超大堆（TB级）/极低延迟 | 染色指针+读屏障 | 停顿 <1ms，几乎无感 |
| **Shenandoah** | 低延迟场景 | 转发指针+并发整理 | 与 ZGC 竞争，停顿同样极低 |

**选型建议**：
```
堆 < 4G    → Parallel Scavenge + Parallel Old（吞吐量优先）
堆 4G~64G  → G1（平衡策略，JDK 9+ 默认推荐）
堆 > 64G   → ZGC（极低延迟，JDK 21+ 生产推荐）
```

#### 四、OOM 排查实战

**OOM 类型**：
| 异常 | 原因 | 典型场景 |
|------|------|---------|
| Java heap space | 堆内存不足 | 内存泄漏、大对象过多 |
| Metaspace | 元空间不足 | 动态类加载（CGLIB/反射） |
| Direct buffer memory | 直接内存不足 | Netty/NIO 未释放 |
| GC overhead limit exceeded | GC 时间 > 98% 且回收 < 2% | 堆太小或内存泄漏 |
| Unable to create new native thread | 线程数超限 | 线程池未限制 |

**排查步骤**：
