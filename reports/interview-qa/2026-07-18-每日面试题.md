#### 三、Advisors 架构：可组合拦截器链

Advisor 是 Spring AI 2.0 最有工程价值的设计，类似 WebFlux 的 WebFilter，在请求 LLM 前后做拦截处理：

```java
// 自定义 Advisor：记录每次 LLM 调用的审计日志
@Component
public class AuditLogAdvisor implements CallAroundAdvisor {
    
    @Override
    public AdvisorResponse aroundCall(AdvisorRequest request, 
                                       CallAroundAdvisorChain chain) {
        long start = System.nanoTime();
        String userId = extractUserId(request);
        try {
            AdvisorResponse response = chain.nextAroundCall(request);
            long elapsed = (System.nanoTime() - start) / 1_000_000;
            log.info("User={}, Tokens={}, Latency={}ms", 
                userId, getTokenUsage(response), elapsed);
            return response;
        } catch (Exception e) {
            log.error("LLM call failed for user={}", userId, e);
            throw e;
        }
    }
}

// 生产级 Advisor 链配置
@Bean
ChatClient.Builder chatClientBuilder(
```

## 题目 2：[数据库/MySQL] 请详细解释 MySQL InnoDB 的 MVCC（多版本并发控制）原理及其在事务隔离中的应用

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-18 日报 — "后端面试高频考点：MySQL、Redis" + JavaGuide 面试指南高频题
**相关岗位**：Java后端 / 全栈 / DBA

### 📖 参考答案

#### 一、MVCC 的本质

MVCC（Multi-Version Concurrency Control）是 InnoDB 实现**一致性非锁定读**的核心机制。它通过为每行数据维护多个版本来实现读不阻塞写、写不阻塞读，从而大幅提升并发性能。

**核心思想：** 每个事务在修改数据时，不会直接覆盖旧数据，而是生成一个新版本。其他事务进行快照读（SELECT）时，根据 ReadView 判断应该读取哪个版本。

#### 二、三大核心依赖

```
MVCC 实现 = 隐藏字段 + Undo Log + ReadView
```

**1. 隐藏字段（每行数据附加）**

| 字段 | 大小 | 说明 |
|------|------|------|
| `DB_TRX_ID` | 6字节 | 最近一次插入/更新该行的事务 ID |
| `DB_ROLL_PTR` | 7字节 | 回滚指针，指向 Undo Log 中的上一个版本 |
| `DB_ROW_ID` | 6字节 | 隐式自增 ID（无主键时生成聚簇索引） |

**2. Undo Log 版本链**

每次 UPDATE 操作会产生一条 Undo Log，通过 `DB_ROLL_PTR` 串联成版本链：

```
记录行 (最新) → Undo Log v2 → Undo Log v1 → Undo Log v0 (最旧)
   ↑              ↑              ↑
DB_ROLL_PTR    DB_ROLL_PTR    DB_ROLL_PTR
```

- **insert undo log**：事务提交后可直接删除
- **update undo log**：需保留用于 MVCC，由 purge 线程在适当时机清理

**3. ReadView（读视图）**

ReadView 是事务执行 SELECT 时生成的"快照"，记录了当前活跃事务列表：

```java
class ReadView {
    trx_id_t m_low_limit_id;    // 下一个待分配的事务 ID（大于等于此值不可见）
    trx_id_t m_up_limit_id;     // 活跃事务中最小 ID（小于此值可见）
    trx_id_t m_creator_trx_id;  // 创建该 ReadView 的事务 ID
    ids_t    m_ids;             // 创建 ReadView 时的活跃事务 ID 列表
}
```

#### 三、可见性判断算法

```
比较记录行的 DB_TRX_ID 与 ReadView：

① DB_TRX_ID == m_creator_trx_id？
   → 是 → 可见（自己修改的）
   → 否 → 进入步骤 ②

② DB_TRX_ID < m_up_limit_id？
   → 是 → 可见（已提交的旧事务）
   → 否 → 进入步骤 ③

③ DB_TRX_ID ∈ m_ids？
   → 是 → 不可见（其他活跃事务修改的，未提交）
   → 否 → 可见（已提交的新事务）
   
④ 如果不可见 → 通过 DB_ROLL_PTR 沿 Undo Log 版本链回溯
   重复步骤 ①~③，直到找到可见版本或到达链尾
```

#### 四、在事务隔离级别中的应用

| 隔离级别 | ReadView 生成时机 | 效果 |
|---------|------------------|------|
| **READ COMMITTED** | 每次 SELECT 都重新生成 | 每次读到的都是已提交的最新数据 → 不可重复读 |
| **REPEATABLE READ**（默认） | 事务中第一个 SELECT 生成，复用 | 整个事务读到的是同一个快照 → 可重复读 |

**RR 下幻读的部分防护：**
- 普通 SELECT（快照读）：MVCC 保证读到一致快照，不会看到其他事务插入的新行
- 当前读（SELECT FOR UPDATE / UPDATE）：使用 Next-Key Lock 防止幻读

#### 五、生产场景示例

```
事务 A（TRX_ID=100）          事务 B（TRX_ID=101）
│                             │
├─ SELECT * FROM user         │
│  (生成 ReadView, m_ids=[101])│
│  读到 id=1, name='Alice'    │
│                             ├─ UPDATE user SET name='Bob'
│                             │  WHERE id=1
│                             │  (生成新版本, DB_TRX_ID=101)
│                             ├─ COMMIT
│                             │
├─ SELECT * FROM user         │
│  (复用 ReadView, m_ids=[101])│
│  DB_TRX_ID=101 ∈ m_ids      │
│  → 不可见，沿 Undo Log 回溯  │
│  读到 id=1, name='Alice' ✓  │
│  → 可重复读                  │
```

## 题目 3：[缓存/Redis] 请解释 Redis 缓存雪崩、缓存穿透、缓存击穿的区别及各自的解决方案

**难度**：⭐⭐⭐
**考点来源**：2026-07-18 日报 — "Redis 仍是后端面试必考，缓存三兄弟（雪崩/穿透/击穿）持续高频" + JavaGuide 面试指南
**相关岗位**：Java后端 / 全栈 / 架构师

### 📖 参考答案

#### 一、三种缓存异常的对比

| 维度 | 缓存穿透 | 缓存击穿 | 缓存雪崩 |
|------|---------|---------|---------|
| **问题本质** | 查询不存在的数据 | 热点 key 过期瞬间高并发 | 大量 key 同时过期 / Redis 宕机 |
| **现象** | 请求绕过缓存直达 DB | 单点压力打爆 DB | DB 被海量请求压垮 |
| **影响范围** | 单个不存在的 key | 单个热点 key | 大量 key / 全库 |
| **根本原因** | 缓存未命中 + 数据不存在 | 缓存过期 + 并发读 | 批量过期 / 服务不可用 |

#### 二、缓存穿透（Cache Penetration）

**场景：** 攻击者频繁请求一个数据库中也不存在的 ID（如 `id=-1`），每次请求都会穿透缓存直接查询数据库。

**解决方案：**

```java
// 方案 1：缓存空对象（最简单）
public User getUserById(Long id) {
    // 1. 查缓存
    User user = redis.get("user:" + id);
    if (user != null) {
        return user;  // 缓存命中
    }
    
    // 2. 查数据库
    user = userDao.findById(id);
    
    // 3. 写入缓存（包括空结果）
    if (user == null) {
        // 缓存空对象，TTL 设置短一些（如 5 分钟）
        redis.set("user:" + id, "NULL", 300, TimeUnit.SECONDS);
        return null;
    }
    redis.set("user:" + id, user, 3600, TimeUnit.SECONDS);
    return user;
}

// 方案 2：布隆过滤器（Bloom Filter）—— 更优雅
// 特点：一定不存在（100% 准确），可能存在（有误判率）
public class UserService {
    private BloomFilter<Long> bloomFilter = BloomFilter.create(
        Funnels.longFunnel(),  // 数据漏斗
        100_000,               // 预期数据量
        0.01                   // 误判率 1%
    );
    
    // 初始化：将所有有效 ID 加载到布隆过滤器
    @PostConstruct
    public void init() {
        List<Long> allIds = userDao.findAllIds();
        allIds.forEach(bloomFilter::put);
    }
    
    public User getUserById(Long id) {
        // 布隆过滤器判断不存在 → 直接返回（拦截 99% 无效请求）
        if (!bloomFilter.mightContain(id)) {
            return null;
        }
        // 可能存在 → 走正常缓存+DB 查询
        return getFromCacheOrDB(id);
    }
}
```

#### 三、缓存击穿（Cache Breakdown / Hotspot Invalid）

**场景：** 秒杀商品的库存信息缓存在 Redis 中，过期瞬间数万请求同时涌入。

**解决方案：**

```java
// 方案 1：互斥锁（Mutex Lock）
public String getProductStock(Long productId) {
    String key = "stock:" + productId;
    String stock = redis.get(key);
    if (stock != null) {
        return stock;  // 缓存命中
    }
    
    // 缓存失效，加锁只让一个线程去查 DB
    String lockKey = "lock:" + productId;
    if (redis.setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS)) {
        try {
            // 双重检查：可能别的线程已经重建了缓存
            stock = redis.get(key);
            if (stock != null) return stock;
            
            // 查数据库并重建缓存
            stock = productDao.getStock(productId);
            redis.set(key, stock, 3600, TimeUnit.SECONDS);
            return stock;
        } finally {
            redis.delete(lockKey);  // 释放锁
        }
    } else {
        // 其他线程等待，自旋或直接降级
        Thread.sleep(50);
        return getProductStock(productId);  // 递归重试
    }
}

// 方案 2：逻辑过期（永不过期 + 异步刷新）
// 缓存永不过期，但 value 中存一个逻辑过期时间
// 发现逻辑过期 → 异步线程去刷新缓存
// 当前线程返回旧数据（牺牲一致性换取可用性）
```

#### 四、缓存雪崩（Cache Avalanche）

**场景：** 晚上 0 点所有缓存同时过期，或者 Redis 集群宕机。

**解决方案：**

```java
// 方案 1：过期时间加随机偏移（避免批量过期）
// ❌ 所有 key 同时过期
redis.set("product:1", data, 3600);
redis.set("product:2", data, 3600);
redis.set("product:3", data, 3600);

// ✅ 过期时间加随机值（300-600 秒随机偏移）
int baseTTL = 3600;
int randomOffset = ThreadLocalRandom.current().nextInt(300, 600);
redis.set("product:1", data, baseTTL + randomOffset);

// 方案 2：多级缓存（本地缓存 + Redis）
// Guava Cache / Caffeine 作为一级缓存
// Redis 作为二级缓存
// DB 作为三级存储
// 即使 Redis 宕机，本地缓存还能扛住一部分流量

// 方案 3：服务降级与限流
// Sentinel / Hystrix 对 DB 查询接口做熔断降级
// 返回兜底数据或错误提示
```

#### 五、防御体系总结

```
缓存穿透 → 布隆过滤器 + 缓存空对象
缓存击穿 → 互斥锁 + 逻辑过期
缓存雪崩 → 过期时间随机化 + 多级缓存 + 服务降级
```

## 题目 4：[Java基础/集合] 请详细说明 Java HashMap 的底层数据结构、扩容机制以及 JDK 8 的核心优化

**难度**：⭐⭐⭐
**考点来源**：2026-07-18 日报 — "JavaGuide 后端高频考点：集合（HashMap 源码、ConcurrentHashMap）" + 2026 校招必问
**相关岗位**：Java后端 / 全栈

### 📖 参考答案

#### 一、JDK 8 HashMap 的底层数据结构

```
JDK 8 HashMap = 数组 + 链表 + 红黑树

                ┌──────┐
table[0]        │ Node │→ null
                ├──────┤
table[1]        │ null │
                ├──────┤
table[2]        │ Node │→ Node → Node → null（链表，长度 > 8 时转红黑树）
                ├──────┤
table[3]        │ Node │→ TreeNode → TreeNode（红黑树）
                ├──────┤
table[15]       │ null │
                └──────┘
```

**核心属性：**
```java
static final int DEFAULT_INITIAL_CAPACITY = 1 << 4;   // 默认容量 16
static final float DEFAULT_LOAD_FACTOR = 0.75f;        // 负载因子
static final int TREEIFY_THRESHOLD = 8;                // 链表→红黑树阈值
static final int UNTREEIFY_THRESHOLD = 6;              // 红黑树→链表阈值
static final int MIN_TREEIFY_CAPACITY = 64;            // 树化最小数组容量
```

#### 二、put() 方法执行流程

```
put(key, value)
  │
  ├─ ① 计算 hash：key.hashCode() ^ (h >>> 16)  // 扰动函数
  │
  ├─ ② (n - 1) & hash 计算数组下标
  │
  ├─ ③ 判断 table[i] 是否为空
  │   ├─ 空 → 直接插入
  │   └─ 非空 → 进入冲突处理
  │       ├─ 比较 hash 和 key 是否相同
  │       │   ├─ 相同 → 覆盖 value
  │       │   └─ 不同 → 遍历链表/红黑树
  │       │       ├─ 链表：尾插法插入，检查长度 ≥ 8 → 尝试树化
  │       │       └─ 红黑树：插入并平衡
  │
  └─ ④ size++，检查是否 > threshold（capacity × loadFactor）
      └─ 是 → 调用 resize() 扩容
```

#### 三、JDK 8 的核心优化（vs JDK 7）

| 优化点 | JDK 7 | JDK 8 | 优势 |
|-------|-------|-------|------|
| **数据结构** | 数组 + 链表 | 数组 + 链表 + 红黑树 | 链表过长时 O(n)→O(log n) |
| **插入方式** | 头插法 | 尾插法 | 避免多线程下环形链表（死循环） |
| **扩容 rehash** | 重新计算 hash | 原位置 or 原位置+旧容量 | 性能提升，位运算更快 |
| **hash 扰动** | 4 次位运算 | 1 次 (h ^ (h >>> 16)) | 性能更优 |
| **树化条件** | 无 | 链表长度 ≥ 8 且数组 ≥ 64 | 极端冲突下性能保障 |

**JDK 8 扩容时索引计算优化：**

扩容后容量翻倍（16→32），元素的新位置只有两种情况：
- **原索引不变**（hash 值新增的那一位为 0）
- **原索引 + 旧容量**（hash 值新增的那一位为 1）

```java
// 判断依据：e.hash & oldCap
// oldCap = 16 = 10000 (二进制)
// 如果 e.hash & 16 == 0 → 留在原位置
// 如果 e.hash & 16 == 1 → 移动到 原位置 + 16
// 不需要像 JDK 7 那样重新计算 hash 再 (n-1) & hash
```

#### 四、为什么容量总是 2 的幂？

```java
// 原因 1：高效取模运算（位运算代替取模）
// (n - 1) & hash 等价于 hash % n（当 n 是 2 的幂时）
// 位运算比取模快一个数量级

// 原因 2：均匀分布
// n=16: n-1=1111 (二进制)
// hash 值的低 4 位决定位置，高位通过扰动函数参与运算
// 如果 n 不是 2 的幂，n-1 的二进制会有 0 位，某些位置永远用不到
```

#### 五、树化与退化

```
链表长度 ≥ 8
    ↓
treeifyBin() 检查数组长度
    ├─ < 64 → resize() 扩容（链表自然分散）
    └─ ≥ 64 → 链表转红黑树
        
红黑树节点数 ≤ 6
    ↓
untreeify() → 红黑树转回链表
```

**为什么树化阈值选 8？**
- 基于泊松分布：在理想随机 hash 下，链表长度达到 8 的概率约为 0.00000006
- 长度 8 是空间换时间的合理阈值
- 树节点（TreeNode）约是普通节点（Node）的 2 倍空间开销

#### 二、RAG（检索增强生成）的核心链路

```

   └─ 去除冗余、提取关键段落，放入 Prompt

⑤ LLM 生成回答
```


#### 三、MCP（Model Context Protocol）协议详解

MCP 是 Anthropic 提出的开放协议，解决 AI 应用与外部工具之间的标准化接入问题。

**核心角色：**

```
Host（AI 应用）           MCP Client          MCP Server         Data Source
    │                        │                    │                  │
    │── 用户提问 ──→         │                    │                  │
    │                        │── initialize ──→   │                  │
    │                        │←── 能力列表 ────   │                  │
    │                        │                    │                  │
    │── 模型判断需调工具 ──→ │                    │                  │
    │                        │── tools/call ──→   │── SQL查询 ──→    │
    │                        │                    │←── 结果 ────     │
    │                        │←── 工具结果 ────   │                  │
    │←── 模型生成回答 ────   │                    │                  │
```

**MCP Server 暴露的三类能力：**
| 能力 | 说明 | 示例 |
|------|------|------|
| **Tools** | 可执行动作（主动调用） | 查询数据库、发送消息、创建工单 |
| **Resources** | 只读上下文（给模型看） | 日志片段、数据库 Schema、配置文件 |
| **Prompts** | 可复用的提示词模板 | 代码审查模板、故障复盘模板 |

