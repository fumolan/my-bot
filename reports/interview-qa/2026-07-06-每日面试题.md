## 题目 1：[框架/Spring] 请详细说明 Spring @Transactional 注解失效的 6 种常见场景及其底层原理，并给出每种场景的解决方案

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-06 午间报告 — "CSDN最新场景题训练：@Transactional失效的6种场景"
**相关岗位**：Java后端 / 全栈

### 📖 参考答案

Spring 声明式事务的核心原理是 **AOP 动态代理**——@Transactional 注解通过代理对象在方法前后织入事务开启、提交/回滚逻辑。**只要代理没生效，事务就会失效。** 理解这句话，下面 6 大场景都能推导出来。

#### 场景 1：同类自调用（Self-Invocation）—— 最常见，踩坑率 90%

```java
@Service
public class OrderService {

    public void createOrder() {
        // ❌ 直接通过 this 调用，绕过了代理对象
        this.insertOrder();
    }

    @Transactional(rollbackFor = Exception.class)
    public void insertOrder() {
        orderMapper.insert(order);
        // 异常时事务不会回滚！
    }
}
```

**原因**：Spring AOP 基于 JDK 动态代理或 CGLIB，只有外部调用（通过代理对象）才能触发切面逻辑。类内部 `this.insertOrder()` 是直接调用目标对象的方法，代理不参与，事务注解被忽略。

**解决方案**：
```java
// 方案 A：注入自身代理（需开启循环依赖或暴露代理）
@Service
public class OrderService {
    @Autowired
    private OrderService orderService;  // 注入自身代理

    public void createOrder() {
        orderService.insertOrder();  // ✅ 走代理对象
    }
}

// 方案 B：将事务方法移到另一个 Service 类
@Service
public class OrderInnerService {
    @Transactional
    public void insertOrder() { ... }
}

// 方案 C：通过 AopContext 获取代理（需 @EnableAspectJAutoProxy(exposeProxy = true)）
public void createOrder() {
    ((OrderService) AopContext.currentProxy()).insertOrder();
}
```

#### 场景 2：非 public 方法

```java
@Transactional
private void insertOrder() { ... }  // ❌ private 方法事务失效
```

**原因**：Spring AOP 默认只拦截 `public` 方法。CGLIB 无法代理 private 方法，JDK 动态代理基于接口，private 也不在接口中。

**解决**：确保事务方法为 `public`。

#### 场景 3：异常被 try-catch 吞掉

```java
@Transactional
public void createOrder() {
    try {
        // 业务操作
    } catch (Exception e) {
        // ❌ 异常被捕获，事务框架感知不到异常，不会回滚
        log.error("操作失败", e);
    }
}
```

**原因**：Spring 事务默认在 `RuntimeException` 或 `Error` 抛出时才回滚。如果异常被 catch 住没重新抛出，事务框架认为方法正常执行完毕，提交事务。

**解决**：
```java
// 方案 A：catch 中重新抛出异常
catch (Exception e) {
    log.error("操作失败", e);
    throw new RuntimeException(e);  // ✅ 让事务感知异常
}

// 方案 B：手动回滚
catch (Exception e) {
    TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
}
```

#### 场景 4：rollbackFor 未指定，异常不匹配

```java
@Transactional  // 默认只回滚 RuntimeException 和 Error
public void createOrder() throws CustomException {
    throw new CustomException("业务异常");  // ❌ 如果 CustomException 不是 RuntimeException，不回滚
}
```

**原因**：`@Transactional` 默认 `rollbackFor = {RuntimeException.class, Error.class}`，检查型异常（Exception 的子类但非 RuntimeException）不会触发回滚。

**解决**：
```java
@Transactional(rollbackFor = Exception.class)  // ✅ 回滚所有异常
public void createOrder() throws CustomException { ... }
```

#### 场景 5：多线程调用

```java
@Transactional
public void process() {
    new Thread(() -> {
        // ❌ 子线程中的操作不在父事务中
        orderMapper.insert(order);
    }).start();
}
```

**原因**：Spring 事务通过 `ThreadLocal` 绑定到当前线程。子线程有自己的 `ThreadLocal`，获取不到父线程的事务连接，子线程中的操作独立提交。

**解决**：避免在事务方法中开子线程；如需异步处理，使用 `@Async` + 独立事务管理。

#### 场景 6：传播机制设置不当

```java
@Service
public class ParentService {
    @Autowired
    private ChildService childService;

    @Transactional
    public void doParent() {
        childService.doChild();  // 子方法的事务传播行为可能影响整体
    }
}

@Service
public class ChildService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void doChild() {
        // 子方法开启独立新事务，父事务异常时不会回滚子事务
    }
}
```

**原因**：`REQUIRES_NEW` 会挂起当前事务、开启新事务；`NEVER` 在存在事务时会抛异常；`NOT_SUPPORTED` 会挂起当前事务以非事务方式执行。理解每种传播行为是正确使用的前提。

## 题目 2：[数据库/MySQL] 在并发下单场景下，请详细说明 MySQL 死锁的成因、排查方法以及预防措施

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-06 午间报告 — "MySQL 死锁排查——并发下单场景"
**相关岗位**：Java后端 / 全栈

### 📖 参考答案

#### 一、死锁的成因（以并发下单为例）

死锁的本质是**两个或多个事务互相等待对方释放锁资源**，形成循环等待。InnoDB 自动检测死锁并回滚其中一个事务（通常回滚代价较小的事务）。

**典型场景：用户同时下单同一商品（并发扣库存）**

```
时间线 | 事务 A（用户 1 下单）        | 事务 B（用户 2 下单）
───────┼────────────────────────────┼────────────────────────────
  T1   | UPDATE stock SET count-=1   |
      |   WHERE product_id=100      |
  T2   |                             | UPDATE stock SET count-=1
      |                             |   WHERE product_id=100
  T3   | INSERT INTO order VALUES    | ← 等待 A 释放 stock 行锁
      |   (user1, product100)        |
  T4   |                             | INSERT INTO order VALUES
      |                             |   (user2, product100)
  T5   | ← 等待 order 表索引锁        | ← 等待 stock 行锁
      |   死锁！                     |   死锁！
```

#### 二、死锁排查方法（面试重点）

**步骤 1：查看最近一次死锁日志**

```sql

```


**关键信息解读**：
- `HOLDS THE LOCK(S)`：当前持有哪些锁
- `LOCK WAIT`：正在等待哪个锁
- `WE ROLL BACK TRANSACTION (2)`：InnoDB 选择回滚的事务

**步骤 2：查看当前运行的事务**

```sql

```

**步骤 3：关联应用日志**

通过 `trx_mysql_thread_id` 关联到应用日志中的线程 ID，定位到具体的代码行和业务请求。

**步骤 4：复现并分析**

在高并发压测环境下复现，使用 `pt-deadlock-logger`（Percona Toolkit）持续监控死锁。

#### 三、预防死锁的六大措施

| 措施 | 说明 | 示例 |
|------|------|------|
| **统一加锁顺序** | 所有事务按相同顺序操作表/行 | 先锁 stock，再锁 order |
| **确保 SQL 走索引** | 不走索引的 UPDATE 会锁全表 | WHERE product_id 加索引 |
| **缩短事务时间** | 事务内不要做远程 RPC 或大量计算 | 只放数据库操作 |
| **拆分批量操作** | 大批量 UPDATE 拆成小批次 | 每次处理 1000 行 |
| **减小锁范围** | 使用唯一索引减少间隙锁 | WHERE order_no（唯一索引） |
| **设置超时重试** | 业务层捕获死锁异常后重试 | 重试 3 次，间隔 100ms |

**最佳实践代码：**

```java
// 统一的加锁顺序 + 死锁重试
@Service
public class OrderService {

    @Transactional(rollbackFor = Exception.class)
    public Order createOrder(Long userId, Long productId) {
        // 1. 先锁库存（统一顺序：先锁库存后创建订单）
        Stock stock = stockMapper.selectByProductIdForUpdate(productId);

        // 2. 扣减库存
        stock.setCount(stock.getCount() - 1);
        stockMapper.updateById(stock);

        // 3. 创建订单
        Order order = new Order(userId, productId);
        orderMapper.insert(order);
        return order;
    }
}

// 死锁重试切面
@Aspect
@Component
public class DeadlockRetryAspect {

    private static final int MAX_RETRIES = 3;

    @Around("@annotation(RetryOnDeadlock)")
    public Object retry(ProceedingJoinPoint joinPoint) throws Throwable {
        int retries = 0;
        while (true) {
            try {
                return joinPoint.proceed();
            } catch (DataIntegrityViolationException | CannotAcquireLockException e) {
                retries++;
                if (retries >= MAX_RETRIES) throw e;
                Thread.sleep(100 * retries);  // 退避等待
            }
        }
    }
}
```

## 题目 3：[缓存/Redis] 请详细说明 Redis 大 Key（Big Key）的定义、危害、排查工具与解决方案

**难度**：⭐⭐⭐
**考点来源**：2026-07-06 午间报告 — "Redis 大 Key 问题排查与解决"
**相关岗位**：Java后端 / 全栈 / 基础架构

### 📖 参考答案

#### 一、什么是大 Key（Big Key）？

大 Key 没有一个绝对的数值标准，通常认为满足以下任一条件即为大 Key：

| 类型 | 大 Key 定义 | 示例 |
|------|-----------|------|
| **String** | Value > 10KB | 缓存了 JSON 大对象、序列化后的图片 Base64 |
| **List** | 元素个数 > 10000 | 消息队列、历史记录 |
| **Hash** | 字段个数 > 10000 或总大小 > 1MB | 用户画像、配置表 |
| **Set** | 成员个数 > 10000 | 关注列表、标签集合 |
| **Sorted Set** | 成员个数 > 10000 | 排行榜、延时队列 |

#### 二、大 Key 的危害

```
大 Key 的危害链：

操作大 Key → 单线程阻塞（Redis 是单线程模型）
          → 其他请求排队等待 → 延迟飙升
          → 内存占用过高 → 内存碎片
          → 主从复制延迟 → 数据不一致
          → 集群分片不均 → 热点节点

具体影响：
① 查询慢：GET/LRANGE 一个 100 万元素的 List → 阻塞 Redis 主线程数十毫秒
② 删除慢：DEL 一个 100 万元素的 Set → Redis 直接卡死几秒
③ 内存碎片：频繁修改大 Hash 导致内存碎片率 > 1.5
④ 网络带宽：每次传输大 Key 消耗大量带宽
⑤ 主从延迟：大 Key 同步到从库耗时，主从复制延迟增大
```

#### 三、排查工具与方法

**方法 1：redis-cli --bigkeys（最常用）**

```bash
# 扫描整个 Redis 实例的大 Key（线上谨慎使用，建议低峰期）
redis-cli --bigkeys

# 输出示例：

# Biggest   list found 'history:user:1001' has 50000 items
# Biggest   hash found 'user:profile:batch' has 20000 fields
# -------- summary -------
```

**方法 2：memory usage 命令（精确分析）**

```bash
# Redis 4.0+ 提供，精确计算单个 key 的内存占用
redis-cli MEMORY USAGE "product:detail:100"  # 返回字节数
```

**方法 3：SCAN + DEBUG OBJECT 组合**

```bash
# 使用 SCAN 渐进式遍历，避免阻塞
redis-cli --scan --pattern "user:*" | head -1000 | \
  while read key; do echo "$key: $(redis-cli debug object $key | grep -o 'serializedlength:[0-9]*')"; done
```

**方法 4：Redis RDB Tools（离线分析）**

```bash

```

**方法 5：监控告警**

- 使用 Grafana + Redis Exporter 实时监控 key 大小分布
- 设置 `maxmemory` + 合理的淘汰策略

#### 四、解决方案

```java
/**
 * 方案一：大 Key 拆分（最推荐）
 * 将大 Hash 拆分为多个小 Hash，按分片键路由
 */
// 拆分前：一个大 Hash 存所有用户在线状态
// redisTemplate.opsForHash().putAll("online:users", allUsersMap);  // 100万字段

// 拆分后：按用户 ID 模 1000 分片
public void setUserOnline(Long userId, boolean online) {
    int shard = (int) (userId % 1000);
    String key = "online:users:" + shard;
    redisTemplate.opsForHash().put(key, String.valueOf(userId), online);
}

/**
 * 方案二：大 Value 压缩
 * 对 JSON 等文本数据使用 Snappy/LZ4 压缩
 */
public void setCompressed(String key, Object value) {
    byte[] json = JSON.toJSONBytes(value);
    byte[] compressed = Snappy.compress(json);  // 压缩率可达 70-80%
    redisTemplate.getConnectionFactory().getConnection()
        .set(key.getBytes(), compressed);
}

/**
 * 方案三：异步删除（Redis 4.0+）
 * 使用 UNLINK 替代 DEL，后台线程异步回收内存
 */
redisTemplate.unlink("big:key");  // 不阻塞主线程

/**
 * 方案四：限制单个 key 大小
 * 在写入层做校验拦截
 */
public void validateBigKey(String key, Object value) {
    byte[] bytes = JSON.toJSONBytes(value);
    if (bytes.length > 10 * 1024) {  // > 10KB
        log.warn("BigKey detected: {} size={}KB", key, bytes.length / 1024);
        // 触发告警或拆分逻辑
    }
}
```

## 题目 4：[微服务/分布式] 请详细说明消息队列（MQ）的四大经典问题——消息丢失、重复消费、消息积压、消息顺序性——的成因、解决方案和最佳实践

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-06 午间报告 — "消息队列四大经典问题" + 2026-07-06 早间报告 — "消息队列四大经典问题"
**相关岗位**：Java后端 / 微服务开发 / 全栈

### 📖 参考答案

#### 一、消息丢失（Message Loss）

**问题链路分析：**

```
消息从生产者到消费者的全链路：

生产者 → MQ Broker → 消费者

可能丢失的环节：
① 生产丢失：发送时网络闪断，Broker 未收到
② Broker 丢失：消息存入内存未落盘，宕机丢失
③ 消费丢失：消费者 auto-commit 后业务处理失败
```

**解决方案：**

```java
// 方案 1：生产者端——发送确认 + 重试
@Service
public class OrderProducer {

    @Autowired
    private RocketMQTemplate rocketMQTemplate;

    public void sendOrderMessage(OrderMessage msg) {
        // 同步发送（等待 Broker 确认）
        SendResult result = rocketMQTemplate.syncSend(
            "order-topic", msg, 3000  // 3s 超时
        );
        if (result.getSendStatus() != SendStatus.SEND_OK) {
            // 发送失败，落库重试
            failedMessageDao.insert(new FailedMessage(msg));
            log.error("消息发送失败, msgId={}", msg.getOrderId());
        }
    }
}

// 方案 2：Broker 端——持久化 + 副本
// 设置 flushDiskType = SYNC_FLUSH（同步刷盘）
// 设置 replicationMode = ASYNC_MASTER（主从同步）

// 方案 3：消费者端——手动 ACK + 幂等
@RocketMQMessageListener(topic = "order-topic", consumerGroup = "order-group")
public class OrderConsumer implements RocketMQListener<OrderMessage> {

    @Override
    public void onMessage(OrderMessage msg) {
        // 手动 ACK：业务处理成功后才提交消费位点
        try {
            orderService.processOrder(msg);
            // 处理成功 → 自动 ACK（非自动提交模式下手动调用）
        } catch (Exception e) {
            // 处理失败 → 不 ACK，消息会重新投递
            log.error("消费失败, msgId={}", msg.getOrderId(), e);
            throw e;  // RocketMQ 会重试
        }
    }
}
```

#### 二、重复消费（Duplicate Consumption）

**问题的本质**：MQ 的"至少一次（At-Least-Once）"语义保证消息不丢失，但无法保证不重复。网络重试、消费者重启、Rebalance 等都可能导致重复消息。

**解决方案：幂等设计**

```java
// 方案 1：业务唯一键去重（推荐）
@Service
public class OrderService {

    @Autowired
    private OrderMapper orderMapper;

    @Transactional
    public void processOrder(OrderMessage msg) {
        // 利用业务唯一键（如订单号）做幂等
        // 方案 A：数据库唯一索引
        try {
            orderMapper.insert(Order.builder()
                .orderNo(msg.getOrderNo())  // 唯一索引
                .userId(msg.getUserId())
                .amount(msg.getAmount())
                .build());
        } catch (DuplicateKeyException e) {
            // 已处理过，忽略
            log.info("重复消息已过滤, orderNo={}", msg.getOrderNo());
            return;
        }

        // 方案 B：先查后插（性能较低，但兼容性好）
        if (orderMapper.existsByOrderNo(msg.getOrderNo())) {
            return;  // 已存在，跳过
        }
        orderMapper.insert(...);
    }
}
```

**相关岗位**：Java后端 / AI应用开发 / 全栈

### 📖 参考答案

#### 一、流式输出的核心原理

**流式输出不是让模型变快了，而是让用户感觉变快了。**

```
传统非流式输出：
  用户发送问题 → [等待 5 秒] → 一次性显示完整回答
  首字节时间（TTFT）= 5 秒

流式输出：
  用户发送问题 → [等待 0.5 秒] → 逐字显示回答
  首字节时间（TTFT）= 0.5 秒
```

**底层本质**：流式输出基于 **HTTP 分块传输编码（Chunked Transfer Encoding）**。区别如下：

| 对比 | 普通响应 | 流式响应 |
|------|---------|---------|
| 响应头 | `Content-Length: 1024` | `Transfer-Encoding: chunked` |
| 发送方式 | 等全部数据生成后一次性发送 | 边生成边分段推送 |
| 前端体验 | 白屏等待 → 全部展示 | 逐字渲染，体验丝滑 |
| 关闭时机 | 数据全部发送后自动关闭 | 收到 `[DONE]` 标志后关闭 |

```
HTTP 分块传输的原始数据格式：

HTTP/1.1 200 OK
Content-Type: text/event-stream
Transfer-Encoding: chunked

data: {"text": "今"}

data: {"text": "天"}

data: {"text": "天"}

data: {"text": "气"}

data: {"text": "不"}

data: {"text": "错"}

data: [DONE]
```

#### 二、方案一：SSE（Server-Sent Events）

**原理**：浏览器通过 `EventSource` API 建立 HTTP 单向长连接，服务端按 `data: {}\n\n` 格式推送数据。

**前端代码：**
```javascript
// SSE 实现——简单但有限制
const eventSource = new EventSource('/api/chat/stream?question=天气如何');

eventSource.onmessage = (event) => {
    if (event.data === '[DONE]') {
        eventSource.close();
        return;
    }
    const chunk = JSON.parse(event.data);
    renderText(chunk.text);  // 逐字渲染
};

eventSource.onerror = (err) => {
    console.error('SSE error', err);
    eventSource.close();
};
```

**后端代码（Spring Boot + WebFlux）：**

**SSE 的局限：**
| 限制 | 说明 |
|------|------|
| 仅支持 GET | 参数拼在 URL，对话历史过长时 URL 超限 |
| 无法传请求体 | 不能传递复杂 JSON 请求体 |

| 浏览器限制 | 同一域名最多 6 个 SSE 连接 |

#### 三、方案二：Fetch + ReadableStream（项目主流）

**原理**：使用 `fetch` API 的 `POST` 方法发送请求，通过 `response.body.getReader()` 读取流式响应分片。

**前端代码：**
```javascript
// 主流方案：POST + ReadableStream
async function streamChat(messages) {
    const controller = new AbortController();

    const response = await fetch('/api/chat/stream', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ messages }),
        signal: controller.signal  // 支持用户点击停止
    });

    const reader = response.body.getReader();
    const decoder = new TextDecoder();

    while (true) {
        const { done, value } = await reader.read();
        if (done) break;

        const text = decoder.decode(value, { stream: true });
        const lines = text.split('\n');

        for (const line of lines) {
            if (line.startsWith('data: ')) {
                const data = line.slice(6);
                if (data === '[DONE]') {
                    reader.cancel();
                    return;
                }
                try {
                    const parsed = JSON.parse(data);
                    renderText(parsed.text);
                } catch (e) {
                    // 忽略解析错误（可能是不完整的 chunk）
                }
            }
        }
    }
}

// 用户点击停止
function stopStream(controller) {
    controller.abort();  // 中断 fetch 请求
}
```

#### 四、两种方案对比与选型

| 对比维度 | SSE（EventSource） | Fetch + ReadableStream |
|---------|-------------------|----------------------|
