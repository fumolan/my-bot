## 题目 1：[Java基础] == 与 equals 的区别深度解析 + hashCode 契约 + String 常量池机制

**难度**：⭐⭐⭐⭐
**考点来源**：2026-05-24 早间报告 — 百度一面真题：「==和equals区别」  
**相关岗位**：Java后端 / 全栈

### 📖 参考答案

**一、先破后立——别只答"==比地址，equals比内容"**

这题是 Java 面试「出场率 TOP3」的基础题，但 90% 的人只答得出表面，一追问就翻车。面试官真正考察的是三个层次：

| 层次 | 考察点 | 加分项 |
|------|--------|--------|
| 基础层 | == 和 equals 的基本区别 | 能清晰区分基本类型和引用类型 |
| 进阶层 | equals 和 hashCode 的契约关系 | 能解释 HashMap/HashSet 为什么要求同时重写 |
| 实战层 | String 常量池、包装类缓存、实际踩坑经验 | 能列出 3+ 个生产环境中的坑 |

**二、== 的双重标准**

```java
// 基本类型：直接比较值
int a = 10;
int b = 10;
System.out.println(a == b); // true，栈中直接存值

// 引用类型：比较内存地址（是否指向堆中同一个对象）
String s1 = new String("hello");
String s2 = new String("hello");
System.out.println(s1 == s2); // false！两个不同的堆对象

String s3 = "hello";
String s4 = "hello";
System.out.println(s3 == s4); // true！字面量 → 常量池复用
```

**核心结论**：== 比较的是「栈中的值」——基本类型是数值本身，引用类型是指向堆的地址指针。不存在什么"引用类型就比地址"，本质一样：比特位比较。

**三、equals() 的重写逻辑**

Object 类的默认 equals() 源码：
```java
public boolean equals(Object obj) {
    return (this == obj); // 默认就是 == 比较！
}
```

String 类重写后的核心逻辑（JDK 17+ 简化版）：
```java
public boolean equals(Object anObject) {
    if (this == anObject) return true;      // 地址相同直接返回
    if (anObject instanceof String s) {
        return this.length() == s.length()
            && this.value().equals(s.value()); // 逐字符比较
    }
    return false;
}
```

**本质上**：equals() 的行为由代码决定。String/Integer/Date 等 JDK 类都重写了 equals() 实现「内容相等」，而你没有重写的自定义类默认走 Object 实现（即 ==）。

**四、hashCode 三大契约（面试必考延伸）**

> 为什么重写 equals 必须重写 hashCode？

这是面试官最爱的追问。答案在于 HashMap/HashSet 的底层结构：

```java
// HashMap 查找逻辑（简化）
public V get(Object key) {
    int hash = key.hashCode();           // 1. 先计算哈希找到桶
    Node<K,V> node = table[hash & (n-1)];
    while (node != null) {
        if (node.key.equals(key))        // 2. 再用 equals 精确匹配
            return node.value;
    }
}
```

**三大契约规则（来自 Object 类 Javadoc）**：

| 规则 | 内容 | 违反后果 |
|------|------|----------|
| 一致性 | 同一个对象多次调用 hashCode() 必须返回相同值（对象没变） | HashMap 定位不稳定 |
| 相等必须同哈希 | a.equals(b) == true → a.hashCode() == b.hashCode() | **HashMap 中存进去取不出来！** |
| 哈希相同不一定相等 | a.hashCode() == b.hashCode() 不要求 a.equals(b) | 哈希冲突，正常现象 |

**致命案例**：重写了 equals 但没重写 hashCode，导致两个「逻辑相等」的对象哈希码不同，HashMap 存入和取出时定位到不同桶——数据丢失。

**五、六大踩坑点**

| 坑 | 说明 | 规避 |
|----|------|------|
| 用 == 比较 String 内容 | `s1 == s2` 依赖常量池优化，不可靠 | 永远用 equals() |
| 重写 equals 不重写 hashCode | HashMap/HashSet 失效 | IDE 自动生成，或用 `Objects.hash()` |
| null 调用 equals() | `str.equals("abc")` 当 str 为 null 抛 NPE | 用 `"abc".equals(str)` 或 `Objects.equals(a,b)` |
| 包装类 == 踩缓存边界 | `Integer a = 128; Integer b = 128; a == b` → false | 用 equals()，缓存范围仅 -128~127 |
| 可变对象做 HashMap key | 对象属性变了 hashCode 也变 | 用不可变对象做 key（如 String、LocalDate） |
| Lombok @Data 自动生成 | 默认包含所有字段的 equals/hashCode | 理解 @EqualsAndHashCode 的 include/exclude |

## 题目 2：[云原生/框架] Docker 容器化与 Kubernetes 编排核心概念全景：从容器本质到 Pod/Deployment/Service 三级抽象，再到生产环境最佳实践

**难度**：⭐⭐⭐⭐
**考点来源**：2026-05-24 早间+午间报告 — "云原生三件套：Docker(34%)+Kubernetes(34%)+微服务(31%)为后端必备技能"  
**相关岗位**：Java后端 / DevOps / 云原生工程师

### 📖 参考答案

**一、Docker 解决的真正问题**

Docker 不是「轻量虚拟机」，它是一套**应用交付和运行标准**。核心价值：把应用、运行时、依赖库、环境变量、启动方式一起打包成镜像，用容器运行，实现「开发/测试/生产环境一致」。

```
传统部署：        Docker 部署：
开发 → "我电脑能跑"    →  Dockerfile → 镜像 → 任何地方跑
测试 → "环境缺依赖"    →  同一镜像 → 依赖全打包
生产 → "配置不一致"    →  环境变量注入 → 标准化运行
```

**Docker vs 虚拟机**：

| 维度 | Docker 容器 | 虚拟机 |
|------|------------|--------|
| 隔离级别 | 进程级隔离（共享内核） | OS 级隔离（独立内核） |
| 启动速度 | 秒级 | 分钟级 |
| 资源开销 | MB 级别 | GB 级别 |
| 镜像大小 | 通常 10MB~1GB | 通常 2GB~40GB |

**二、Docker 核心三要素**

```
┌──────────────┐    docker build     ┌──────────────┐    docker run     ┌──────────────┐
│  Dockerfile  │ ──────────────────→ │   镜像 Image  │ ───────────────→ │  容器 Container │
└──────────────┘                     └──────────────┘                   └──────────────┘
     构建蓝图                          只读模板                          运行实例
```

**Dockerfile 关键指令**：
```dockerfile
FROM openjdk:21-slim           # 基础镜像
WORKDIR /app                    # 工作目录
COPY target/app.jar app.jar     # 复制构建产物
ENV JAVA_OPTS="-Xmx512m"        # 环境变量
EXPOSE 8080                     # 声明端口
HEALTHCHECK --interval=30s \    # 健康检查
  CMD curl -f http://localhost:8080/actuator/health || exit 1
ENTRYPOINT ["java", "-jar", "app.jar"]
```

**三、Kubernetes 核心架构**

K8s 是一个容器编排平台，解决「如何管理成百上千个容器」的问题。

```
┌──────────────────────────────────────────────────────┐
│                   Control Plane (Master)              │
│  ┌─────────┐ ┌──────────┐ ┌──────────┐ ┌─────────┐  │
│  │API Server│ │Scheduler │ │Controller│ │  etcd   │  │
│  └─────────┘ └──────────┘ └──────────┘ └─────────┘  │
└──────────────────────┬───────────────────────────────┘
                       │
┌──────────────────────┼───────────────────────────────┐
│                 Worker Node                           │
│  ┌──────────┐  ┌──────────────┐  ┌──────────────┐   │
│  │ kubelet  │  │   Pod(Pod)   │  │   Pod(Pod)   │   │
│  │          │  │  container1  │  │  container2  │   │
│  │ kube-proxy│ │  container2  │  │  container1  │   │
│  └──────────┘  └──────────────┘  └──────────────┘   │
└──────────────────────────────────────────────────────┘
```

**四、三级抽象（必背）**

| 抽象层 | 作用 | 关键特性 | 类比 |
|--------|------|----------|------|
| **Pod** | 最小部署单元 | 共享网络/存储，同 Pod 内 localhost 通信 | 豆荚（含多颗豆子=容器） |
| **Deployment** | 管理 Pod 副本 | 滚动更新、回滚、扩缩容、自愈 | 监工 |
| **Service** | 服务发现与负载均衡 | 固定虚拟 IP + DNS，Pod 销毁重建不影响调用方 | 前台/负载均衡器 |

**声明式配置（Deployment + Service）**：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-service
spec:
  replicas: 3                    # 3 个 Pod 副本
  selector:
    matchLabels:
      app: user-service
  template:
    metadata:
      labels:
        app: user-service
    spec:
      containers:
      - name: app
        image: user-service:v1.2
        resources:
          requests:               # 调度依据
            memory: "256Mi"
            cpu: "250m"
          limits:                 # 硬上限
            memory: "512Mi"
        readinessProbe:           # 就绪探针
          httpGet:
            path: /actuator/health/readiness
            port: 8080
        livenessProbe:            # 存活探针
          httpGet:
            path: /actuator/health/liveness
            port: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: user-service
spec:
  type: ClusterIP
  selector:
    app: user-service
  ports:
  - port: 8080
    targetPort: 8080
```

**五、Spring Boot 在 K8s 上的关键优化**

| 优化点 | 具体做法 | 效果 |
|--------|---------|------|
| Graceful Shutdown | `server.shutdown=graceful` + `spring.lifecycle.timeout-per-shutdown-phase=30s` | 避免 Pod 终止时丟请求 |
| 健康检查 | Spring Actuator `/health/readiness` + `/health/liveness` | K8s 感知应用真实状态 |
| 配置外置 | ConfigMap 挂载 application.yml | 不重建镜像即可改配置 |
| 资源限制 | JVM 感知容器内存：`-XX:MaxRAMPercentage=75.0` | 防止 OOMKilled |
| 日志集中 | STDOUT 输出 → Fluentd/Filebeat → ELK | 容器销毁后日志仍可查 |

**六、高频面试追问**

**Q：Pod 挂了怎么办？**
→ Deployment 控制器检测到 `replicas` 不满足，自动调度新 Pod。配合 Readiness Probe 避免流量打到未就绪的 Pod。

**Q：Service 如何找到 Pod？**
→ 通过 Label Selector 匹配，而不是 Pod IP（Pod IP 会变）。Service 维护 Endpoints 列表，kube-proxy 在每个 Node 上转发流量。

**Q：滚动更新怎么做的？**
→ Deployment 逐步创建新版本 Pod、等待就绪、再终止旧版本 Pod。通过 `maxSurge`（超过副本数的上限）和 `maxUnavailable`（不可用上限）两个参数控制节奏。

## 题目 3：[数据库/MySQL] InnoDB 三大行锁算法深度解析：记录锁、间隙锁、临键锁（Next-Key Lock）及如何解决幻读问题

**难度**：⭐⭐⭐⭐⭐
**考点来源**：2026-05-24 午间报告 — "分布式事务、分库分表、高并发一致性" + MySQL 锁机制为高频考点  
**相关岗位**：Java后端 / DBA / 基础架构

### 📖 参考答案

**一、前置知识：为什么需要锁？**

MySQL InnoDB 默认隔离级别为**可重复读（RR）**。MVCC（多版本并发控制）解决了快照读下的幻读，但**当前读**（SELECT ... FOR UPDATE / UPDATE / DELETE / INSERT）仍然需要锁来防止幻读。InnoDB 的行锁基于索引实现——没有索引则退化为表锁。

**二、三大行锁算法对比**

```
| 记录锁(Record Lock) |     间隙锁(Gap Lock)   |     临键锁(Next-Key Lock)   |
|    只锁一行记录        |   锁住索引记录间的间隙    |   = 记录锁 + 间隙锁          |
|                       |                         |   左开右闭区间               |
     ●                       [  区间  )             [  区间  ●  ]
```

**1. 记录锁（Record Lock）**

```sql
-- 对 id=5 这一行加 X 锁，其他事务不能修改
SELECT * FROM user WHERE id = 5 FOR UPDATE;
```

**前提**：`id` 必须是**唯一索引**且是**等值查询**，否则会升级为临键锁。

**2. 间隙锁（Gap Lock）**

锁住索引记录之间的**间隙**（不含记录本身），阻止其他事务在间隙中 INSERT。

```sql
-- 假设 user 表中 id 有 1, 5, 10 三条记录
-- 间隙锁会锁住 (-∞, 1), (1,5), (5,10), (10,+∞) 中与条件匹配的区间
SELECT * FROM user WHERE id > 5 AND id < 10 FOR UPDATE;
-- 锁住间隙 (5, 10)，其他事务不能插入 id=6,7,8,9 的数据
```

**关键特性**：
- 间隙锁与间隙锁**不冲突**（都是锁一个范围防止插入，目的相同）
- 仅 RR 隔离级别下有间隙锁，RC 级别**无间隙锁**
- 间隙锁是导致**死锁的头号元凶**

**3. 临键锁（Next-Key Lock）**

= **记录锁 + 前开后闭间隙锁**，是 InnoDB RR 级别的默认行锁算法。

```sql
-- 假设当前有 id=5, id=10 两条记录
SELECT * FROM user WHERE id = 7 FOR UPDATE;
-- 锁定区间：(5, 10] —— 即 (5,10) 间隙锁 + id=10 记录锁
-- 效果：不能插入 6/7/8/9，不能修改 id=10 的行
```

**三、为什么临键锁能解决幻读？**

幻读的定义：同一事务内，两次相同的范围查询，第二次查出了之前不存在的新行。

**MVCC 的局限**：
```sql
-- 事务 A
BEGIN;
SELECT * FROM user WHERE age > 20;  -- 快照读，查到 3 条

-- 事务 B（已提交）
INSERT INTO user VALUES (4, '张三', 25);
COMMIT;

-- 事务 A
SELECT * FROM user WHERE age > 20;  -- 快照读，还是 3 条 ✅（MVCC 工作）
SELECT * FROM user WHERE age > 20 FOR UPDATE; -- 当前读，查到 4 条 ❌ 幻读！
```

**临键锁方案**：
```sql
-- 事务 A 用 FOR UPDATE 加临键锁
SELECT * FROM user WHERE age > 20 FOR UPDATE;
-- age 列有索引时，锁住 [20, +∞) 区间的临键锁
-- 事务 B 尝试 INSERT age=25 的行 → 被阻塞！
```

**四、加锁规则速查表**

| 查询条件 | 索引类型 | 等值查询（命中） | 等值查询（未命中） | 范围查询 |
|---------|---------|----------------|-------------------|---------|
| 主键/唯一索引 | 唯一索引 | 记录锁 | 间隙锁 | 临键锁 |
| 普通索引 | 非唯一索引 | 临键锁 | 间隙锁 | 临键锁 |
| 无索引 | — | 表锁（所有行+间隙） | 表锁 | 表锁 |

**五、死锁典型案例及排查**

```sql
-- 场景：两个事务互相等待间隙锁释放
-- 表数据：id 有 5, 10，name 有普通索引

-- T1：
SELECT * FROM user WHERE name = 'A' FOR UPDATE;  -- 临键锁，锁 name 索引的某个区间

-- T2：
SELECT * FROM user WHERE name = 'B' FOR UPDATE;  -- 临键锁，锁另一个区间

-- T1：
INSERT INTO user VALUES (7, 'B');  -- 等待 T2 释放间隙锁

-- T2：
INSERT INTO user VALUES (8, 'A');  -- 等待 T1 释放间隙锁
-- → 死锁！MySQL 自动检测并回滚其中一个事务
```

**排查命令**：
```sql
-- 查看当前锁等待
SELECT * FROM information_schema.INNODB_TRX;
SELECT * FROM information_schema.INNODB_LOCK_WAITS;

-- 查看最近的死锁日志
SHOW ENGINE INNODB STATUS;
```

**六、为什么间隙锁在企业中是"性能杀手"？**

1. **并发度骤降**：间隙锁锁住的是一个范围，即使目标行不存在，也无法插入该范围内的任何数据
2. **死锁风险**：多个事务操作不同的间隙，但 INSERT 时可能互相阻塞
3. **RC 级别的权衡**：很多互联网公司选用 RC + 行级 binlog 格式，牺牲幻读保护换取更高并发

2. 在实际项目中，什么场景你选择 RR + 临键锁，什么场景选择 RC + 业务层保证幂等？

## 题目 4：[缓存/Redis] 缓存穿透、缓存击穿、缓存雪崩的完整对比与工业级解决方案（含布隆过滤器、互斥锁、多级缓存）

**难度**：⭐⭐⭐⭐
**考点来源**：2026-05-24 早间报告 — "Redis高频考点全解析，基于字节/阿里/腾讯/京东/拼多多2024-2026面经"  
**相关岗位**：Java后端 / 中间件 / 架构

### 📖 参考答案

**一、三兄弟对比——面试官一听就知道你懂不懂**

很多候选人把三者混为一谈，面官一听就 pass。核心区别：

| 维度 | 缓存穿透 | 缓存击穿 | 缓存雪崩 |
|------|---------|---------|---------|
| **定义** | 查询不存在的 key，缓存和DB都没有 | 热点 key 突然过期，大量请求打 DB | 大量 key 同时过期或 Redis 宕机 |
| **触发条件** | 恶意攻击 / 查询不存在的 ID | 热点数据缓存失效瞬间 | key 过期时间集中在同一时刻 |
| **后果** | 每个请求都穿透到 DB | 瞬时并发直冲 DB | DB 被打爆，雪崩式宕机 |
| **核心解法** | 布隆过滤器 + 空值缓存 | 互斥锁 + 逻辑过期 | 随机过期 + 多级缓存 + 熔断 |
| **类比** | 有人一直敲你家门问"张三在吗"（根本不在） | 演唱会开门瞬间，万人涌入 | 整栋楼同时停电 |

**二、缓存穿透解决方案**

```
请求 → 布隆过滤器 → 不在 → 直接拒绝（不查缓存和DB）
                  → 可能存在 → 查缓存 → 命中 → 返回
                                          → 未命中 → 查DB → 有数据 → 回写缓存
                                                           → 无数据 → 缓存空值（短期TTL）
```

**方案对比**：

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **布隆过滤器**（推荐） | 位图 + 多哈希函数，快速判断 key 是否可能存在 | 内存极小、性能极高 | 有误判率（不存在判为可能存在） |
| **缓存空值** | 对不存在的 key 也缓存 null/空对象 | 实现简单 | 内存浪费（需短期 TTL） |
| **参数校验** | 接口层拦截非法 ID（负数、超范围等） | 零成本 | 只能拦截明显非法请求 |

**三、缓存击穿解决方案**

```
热点 key 过期瞬间，1000 个请求打到 DB
→ 方案 1（互斥锁）：只有 1 个线程去查 DB 重建缓存，999 个等待
→ 方案 2（逻辑过期）：永不过期，后台异步刷新
```

**互斥锁实现（推荐中小场景）**：
```java
public Product getProduct(Long id) {
    String key = "product:" + id;
    Product product = (Product) redisTemplate.opsForValue().get(key);
    if (product != null) return product;
    
    // 获取分布式锁
    String lockKey = "lock:product:" + id;
    RLock lock = redisson.getLock(lockKey);
    try {
        // 等待 3 秒，锁 30 秒自动释放
        if (lock.tryLock(3, 30, TimeUnit.SECONDS)) {
            // 双重检查：可能前面线程已重建缓存
            product = (Product) redisTemplate.opsForValue().get(key);
            if (product != null) return product;
            
            // 查 DB
            product = productMapper.selectById(id);
            if (product != null) {
                // 写入缓存，添加随机过期时间防雪崩
                redisTemplate.opsForValue().set(key, product, 
                    30 + ThreadLocalRandom.current().nextInt(10), TimeUnit.MINUTES);
            }
            return product;
        }
    } finally {
        if (lock.isHeldByCurrentThread()) lock.unlock();
    }
    // 获取锁失败，稍后重试或返回降级数据
    return fallbackProduct(id);
}
```

**逻辑过期方案（推荐高并发场景）**：

```java
// 数据对象封装
class RedisData {
    private Object data;
    private LocalDateTime expireTime; // 逻辑过期时间
}

public Product getProductLogical(Long id) {
    String key = "product:" + id;
    RedisData redisData = (RedisData) redisTemplate.opsForValue().get(key);
    if (redisData == null) return null;
    
    Product product = (Product) redisData.getData();
    LocalDateTime expireTime = redisData.getExpireTime();
    
    // 未过期直接返回
    if (expireTime.isAfter(LocalDateTime.now())) return product;
    
    // 逻辑过期，异步刷新
    String lockKey = "lock:product:" + id;
    if (redisson.getLock(lockKey).tryLock()) {
        // 提交异步任务重建缓存
        threadPoolExecutor.execute(() -> {
            Product newProduct = productMapper.selectById(id);
            RedisData newData = new RedisData(newProduct, 
                LocalDateTime.now().plusMinutes(30));
            redisTemplate.opsForValue().set(key, newData);
            redisson.getLock(lockKey).unlock();
        });
    }
    // 直接返回旧数据（保证可用性优于一致性）
    return product;
}
```

**四、缓存雪崩解决方案**

| 策略 | 实现方式 | 核心思想 |
|------|---------|---------|
| **随机过期时间** | `TTL = base + random(0, 30%)` | 避免同时过期 |
| **多级缓存** | Nginx 本地缓存 → Redis → DB | 层层兜底 |
| **熔断降级** | Sentinel/Hystrix 限流熔断 | 宁可部分不可用，不能全挂 |
| **Redis 高可用** | 哨兵/集群，多机房异地多活 | Redis 本身不挂 |
| **缓存预热** | 启动时预加载热点数据 | 避免冷启动击穿 |

```java
@Component
public class AuthFilter implements GlobalFilter {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String path = exchange.getRequest().getURI().getPath();
        
        // 白名单路径
        if (isWhiteList(path)) return chain.filter(exchange);
        
        // 提取 Token
        String token = extractToken(exchange);
        if (token == null) {
            return unauthorized(exchange, "缺少令牌");
        }
        
        try {
            // JWT 验证（本地验签，无需每次请求都调认证中心）
            Claims claims = Jwts.parserBuilder()
                .setSigningKey(publicKey)
                .build()
                .parseClaimsJws(token)
                .getBody();
            
            // 将用户信息写入请求头，透传给下游服务
            exchange.getRequest().mutate()
                .header("X-User-Id", claims.getSubject())
                .header("X-User-Roles", String.join(",", roles));
            
            return chain.filter(exchange);
        } catch (JwtException e) {
            return unauthorized(exchange, "令牌无效或已过期");
        }
    }
}
```
