```java
@RestController
public class AiController {

    private final ChatClient chatClient;
    private final VectorStore vectorStore;

    // 注入 ChatClient，自动配置底层模型
    public AiController(ChatClient.Builder builder, VectorStore vectorStore) {
        this.chatClient = builder.build();
        this.vectorStore = vectorStore;
    }

    @PostMapping("/rag/ask")
    public Flux<String> ask(@RequestBody Question question) {
        // 1. 检索相关文档
        List<Document> docs = vectorStore.similaritySearch(
            SearchRequest.query(question.text()).withTopK(3)
        );
        // 2. 构建增强 Prompt
        String context = docs.stream()
            .map(Document::getText)
            .collect(Collectors.joining("\n---\n"));
        // 3. 流式回答
        return chatClient.prompt()
            .system("你是一个基于以下上下文回答问题的助手：\n" + context)
            .user(question.text())
            .stream()
            .content();
    }
}
```

#### 四、Agent 编排注解化

```java
@Agent(description = "智能客服 Agent")
public class CustomerSupportAgent {

    @Plan   // 任务规划阶段——拆解用户意图
    public Plan decomposeTask(UserMessage msg) {
        return Plan.of(
            new Intent("query_order", "查询订单"),
            new Intent("check_inventory", "检查库存"),
            new Intent("suggest_alternative", "推荐替代方案")
        );
    }

    @Act   // 执行阶段——调用工具
    public ActResult executeStep(Step step) {
        return switch (step.intent()) {
            case "query_order" -> orderTool.execute(step.params());
            case "check_inventory" -> inventoryTool.execute(step.params());
            case "suggest_alternative" -> recommendTool.execute(step.params());
            default -> ActResult.fail("未知意图");
        };
    }

    @Observe  // 观察阶段——分析执行结果
    public Observation observe(ActResult result) {
        if (result.isSuccess()) {
            return Observation.continuePlan(result);  // 继续执行
        }
        return Observation.retryOrFallback(result);   // 重试或兜底
    }
}
```

**考点来源**：2026-07-04 报告 — "高频考点 TOP3：synchronized 锁升级" + "并发领域：AQS、锁优化、ThreadLocal 替代方案"
**相关岗位**：Java后端 / 基础架构 / 全栈

### 📖 参考答案

#### 一、synchronized 锁升级概述

JDK 6 对 synchronized 做了重大优化，引入了**锁升级（锁膨胀）**机制，目的是在保证线程安全的前提下，尽量减少重量级锁（OS 互斥量）的使用，从而提升并发性能。

```
锁升级的路径（不可逆）：
  无锁 → 偏向锁 → 轻量级锁 → 重量级锁
  (biased)  →  (spin)  →  (mutex)
```

| 锁状态 | Mark Word 内容 | 适用场景 | 性能开销 |
|--------|---------------|---------|---------|
| **无锁** | 对象的 hashCode、分代年龄 | 无竞争 | 零 |
| **偏向锁** | 线程 ID + 偏向模式标志 | 单线程反复获取同一把锁 | 极低（一次 CAS） |
| **轻量级锁** | 指向栈中锁记录的指针 | 少量线程交替获取锁 | 较低（自旋 + CAS） |
| **重量级锁** | 指向互斥量（Monitor）的指针 | 多线程激烈竞争 | 高（内核态阻塞/唤醒） |

#### 二、锁升级过程详解

##### 1. 偏向锁（Biased Locking）

```
触发条件：
  首次获取锁时，对象头 Mark Word 记录当前线程 ID
  后续同一线程再次进入同步块时，无需任何 CAS 操作

偏向锁的撤销：
  当其他线程尝试竞争偏向锁时：
  → 等待全局安全点（SafePoint）
  → 暂停拥有偏向锁的线程
  → 检查该线程是否存活：
     - 已结束：将锁对象重置为无锁状态
     - 存活中：升级为轻量级锁或重量级锁
  → 恢复线程执行
```

##### 2. 轻量级锁（Lightweight Locking）

```
触发条件：
  当第二个线程尝试获取已被偏向的锁时，偏向锁撤销后升级为轻量级锁

实现机制：
  ① 线程在自己的栈帧中创建锁记录（Lock Record）空间
  ② 通过 CAS 尝试将对象头的 Mark Word 替换为指向锁记录的指针
  ③ 如果 CAS 成功 → 成功获取锁
  ④ 如果 CAS 失败 → 检查是否当前线程已持有锁
     - 是 → 重入计数 +1（锁重入）
     - 否 → 自旋等待 + 膨胀为重量级锁
```

##### 3. 重量级锁（Heavyweight Locking）

```
触发条件：
  自旋次数超过阈值（默认 10 次或自适应自旋）或自旋线程数过多

实现机制：
  ① 轻量级锁 CAS 持续失败
  ② 锁膨胀为重量级锁
  ③ 未获取锁的线程进入阻塞状态（BLOCKED）
  ④ 操作系统 Mutex 互斥量管理等待队列
  ⑤ 锁释放时，操作系统唤醒等待线程（内核态切换）
```

#### 三、锁升级的核心数据结构：对象头 Mark Word

```
64位 JVM 下 Mark Word 结构（无锁状态）：
|--------------------------- 64 bits --------------------------|
| unused:25 | identity_hashcode:31 | unused:1 | age:4 | biased:0 | 01 |

偏向锁状态：
| thread:54 | epoch:2 | unused:1 | age:4 | biased:1 | 01 |

轻量级锁状态：
| ptr_to_lock_record:62 | 00 |

重量级锁状态：
| ptr_to_heavyweight_monitor:62 | 10 |

GC 标记：
| (空) | 11 |
```

#### 四、JDK 15+ 偏向锁的废弃

**重要变化**：JDK 15 起默认禁用偏向锁（JEP 374），JDK 21 彻底移除了偏向锁的实现代码。

**废弃原因**：
```
① 偏向锁的撤销（Revocation）必须在全局安全点执行
   → 暂停所有线程，影响 STW 停顿时间
② 高并发应用中偏向锁的撤销成本高于其带来的收益
③ 现代应用使用更精细的锁策略，偏向锁优化收益递减
```

**对开发者的影响**：

| 场景 | JDK 15 之前 | JDK 21 之后 |
|------|-------------|-------------|
| 无竞争同步块 | 偏向锁，零开销 | 轻量级锁（CAS 一次） |
| 少量竞争 | 轻量级锁 + 自旋 | 同左（无变化） |
| 激烈竞争 | 重量级锁 | 同左（无变化） |
| 高并发容器 | ConcurrentHashMap 仍为首选 | 同左 |

**面试建议**：面试官问偏向锁时，既要答清楚锁升级机制，也要展示你对 JDK 版本变更的跟进——"偏向锁已在 JDK 21 中移除，当前锁的优化重点在轻量级锁的自旋优化和自适应自旋策略上"。

**相关岗位**：Java后端 / 全栈

### 📖 参考答案

#### 一、HashMap 的线程不安全表现

| 问题 | JDK 7 | JDK 8 |
|------|-------|-------|
| **死循环** | ✅ 扩容时头插法导致环形链表 | ❌ 已修复（尾插法） |
| **数据丢失** | ✅ put 并发覆盖 | ✅ 仍可能发生 |
| **size 不准确** | ✅ 非原子操作 | ✅ 非原子操作 |
| **get 获取 null** | ✅ 扩容时 transient 状态 | ✅ 仍可能发生 |
| **modCount 异常** | ✅ 并发修改触发 ConcurrentModificationException | ✅ 同左 |

#### 二、JDK 7 HashMap 死循环问题（经典面试题）

**成因**：JDK 7 的扩容采用 **头插法**（rehash 时，将旧链表的节点依次插入新桶的头部）。

```
假设两个线程同时触发扩容：

扩容前（桶数组大小从 2 扩容到 4）：
  table[1] → A → B → C

线程1 扩容过程（执行到一半被挂起）：
  e = A, next = B
  → 将 A 头插到 newTable[3] → newTable[3] = A

线程2 完成扩容（头插法）：
  newTable[3] → C → B → A  （链表反转）

线程1 恢复执行：
  e = B, next = A  （此时线程2 已经反转了链表）
  → 将 B 头插到 newTable[3] → newTable[3] = B → A → ??
  → e = A, next = null
  → 将 A 头插到 newTable[3] → A.next = B → 形成环形链表！

结果：get(key) 遍历链表时陷入死循环，CPU 100%
```

#### 三、JDK 8 的优化

```java
// JDK 8 HashMap.resize() 关键变更
// 1. 尾插法：新节点追加到链表尾部，保持原有顺序
// 2. 红黑树：链表长度 > 8 时转为红黑树（O(n) → O(log n)）

// 扩容时的尾插法伪代码
void transfer(Node<K,V>[] newTab) {
    // 将原链表的节点拆分为高位链和低位链
    // 低位链：hash & oldCap == 0 → 留在原索引
    // 高位链：hash & oldCap != 0 → 移到 原索引 + oldCap
    Node<K,V> loHead = null, loTail = null;
    Node<K,V> hiHead = null, hiTail = null;
    Node<K,V> next;
    do {
        next = e.next;
        if ((e.hash & oldCap) == 0) {
            // 低位链——尾插法
            if (loTail == null) loHead = e;
            else loTail.next = e;
            loTail = e;
        } else {
            // 高位链——尾插法
            if (hiTail == null) hiHead = e;
            else hiTail.next = e;
            hiTail = e;
        }
        e = next;
    } while (e != null);
    // 将低位链放到原索引位置
    if (loTail != null) {
        loTail.next = null;
        newTab[j] = loHead;
    }
    // 将高位链放到 (原索引 + oldCap) 位置
    if (hiTail != null) {
        hiTail.next = null;
        newTab[j + oldCap] = hiHead;
    }
}
```

**JDK 8 的优化总结**：

| 优化项 | JDK 7 | JDK 8 |
|-------|-------|-------|
| 插入方式 | 头插法（导致死循环） | 尾插法（保持顺序） |
| 扩容后元素位置 | 全部 rehash | 低位链/高位链拆分 |
| 链表过长 | O(n) 遍历 | ≥8 转红黑树 O(log n) |
| 死循环 | ✅ 存在 | ❌ 已修复 |
| 数据丢失 | ✅ 存在 | ⚠️ 仍可能（putVal 非原子） |

## 题目 4：[JVM] 请详细说明 JVM 元空间（Metaspace）的架构设计、与永久代的区别，以及生产环境中的 MetaspaceSize 参数调优策略和常见问题排查

**难度**：⭐⭐⭐
**考点来源**：2026-07-04 报告 — "元空间参数调优：生产级 JVM 调优实战（MetaspaceSize 设置策略）"
**相关岗位**：Java后端 / 基础架构

### 📖 参考答案

#### 一、元空间 vs 永久代：架构革命

JDK 8 最大的 JVM 变更之一：**永久代（PermGen）→ 元空间（Metaspace）**

| 对比维度 | 永久代（PermGen，JDK 7 及之前） | 元空间（Metaspace，JDK 8+） |
|---------|-------------------------------|---------------------------|
| **内存位置** | JVM 堆内存内部 | 本地内存（Native Memory，不由 JVM 堆管理） |
| **默认大小** | 32MB（32位）/ 64MB（64位） | 无上限（受物理内存限制） |
| **最大大小** | -XX:MaxPermSize 控制 | -XX:MaxMetaspaceSize 控制 |
| **存储内容** | 类元数据、方法数据、常量池、字符串常量池 | 类元数据、方法数据（字符串常量池移到了堆） |
| **GC 触发** | Full GC 才回收 | 类加载器卸载时触发回收 |
| **OOM 风险** | 类加载过多时易 OOM（PermGen Space） | 无上限时不会 OOM，但会吃掉物理内存 |


#### 五、元空间 GC 触发机制

```
元空间 GC 的触发条件：

① 当前元空间使用量 > MetaspaceSize（默认约 21MB）

② 元空间使用率达到当前阈值
   → 调整算法：
      新阈值 = 当前使用量 × (1 + MinMetaspaceFreeRatio / 100)

③ -XX:MaxMetaspaceSize 设置过小
   → 抛出 OutOfMemoryError: Metaspace
```

#### 二、Reactor 核心：Flux 和 Mono

#### 三、背压（Backpressure）机制

背压是响应式编程的核心概念：**下游告诉上游"慢一点，我处理不过来"**。

```
没有背压的情况：
  生产者 ──────── 高速发射 ────────→ 消费者（被压垮 ❌）

有背压的情况（基于 Reactive Streams 规范）：
  生产者 ────── 按需发射 ←──── request(n) ── 消费者（健康 ✅）
```

```java
// 背压的四种策略

// 1. BUFFER（默认）——缓冲所有元素
Flux.interval(Duration.ofMillis(1))     // 每 1ms 发射一个
    .onBackpressureBuffer(1000)          // 缓冲 1000 个
    .delayElements(Duration.ofMillis(10)) // 每 10ms 消费一个
    .subscribe();

// 2. DROP——丢弃无法处理的元素
Flux.interval(Duration.ofMillis(1))
    .onBackpressureDrop(dropped -> log.warn("丢弃: {}", dropped))
    .delayElements(Duration.ofMillis(10))
    .subscribe();

// 3. LATEST——只保留最新的
Flux.interval(Duration.ofMillis(1))
    .onBackpressureLatest()
    .delayElements(Duration.ofMillis(10))
    .subscribe();

// 4. ERROR——超出时抛异常
Flux.interval(Duration.ofMillis(1))
    .onBackpressureError()
    .delayElements(Duration.ofMillis(10))
    .subscribe();
```

#### 五、WebFlux 性能优势与注意事项

**性能优势**：

```
传统 MVC（Tomcat，200 线程池）：
  200 个请求同时执行 I/O → 200 个线程全部阻塞 → 第 201 个请求等待

WebFlux（Netty，EventLoop 线程数 = CPU 核数）：
  10000 个请求同时执行 I/O → 少量线程处理所有请求 → 无阻塞

吞吐量对比（典型场景：网关/代理/流式 API）：
  MVC  : ~5000 req/s（受线程池限制）
  Flux : ~30000 req/s（非阻塞 I/O）
```

**注意事项**：

```
① 数据库驱动必须用响应式（R2DBC / MongoDB Reactive / Redis Reactive）
   如果使用 JDBC，WebFlux 的优势会消失（JDBC 是阻塞 I/O）

② 避免在响应式链中调用阻塞方法
   ❌ .map(user -> Thread.sleep(1000))  // 阻塞 EventLoop
   ✅ .publishOn(Schedulers.boundedElastic())
      .map(user -> blockingCall(user))   // 切换到阻塞线程池

③ WebFlux 适合 IO 密集型，不适合 CPU 密集型
   CPU 密集型任务仍然需要传统线程模型

④ 调试困难：响应式调用链堆栈信息较复杂
   可使用 checkpoint() 或 ReactorDebugAgent 辅助调试
```
