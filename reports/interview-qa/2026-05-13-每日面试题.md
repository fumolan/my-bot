## 题目 1：[Java基础/并发] 请详细解释 Java 线程池 ThreadPoolExecutor 的七大核心参数与工作流程，并给出 CPU 密集型与 IO 密集型场景的线程数计算公式，以及如何避免生产环境中的 OOM 问题

**难度**：⭐⭐⭐⭐
**考点来源**：2026-05-13 报告 — "线程池大小计算逻辑（IO密集=Ncpu×2）、volatile/CAS/AQS原理" + "场景化面试：多线程下HashMap扩容会发生什么"  
**相关岗位**：Java后端 / 高并发系统开发

### 📖 参考答案

**一、为什么需要线程池？**

直接 `new Thread().start()` 的三大致命缺陷：

| 问题 | 说明 |
|------|------|
| **创建开销大** | 每个线程涉及 JVM 栈分配（~1MB）、OS 内核线程创建、调度器注册 |
| **资源不可控** | 无限制创建 → 10000 个线程 ≈ 10GB 内存 → OOM |
| **无法统一管理** | 任务无排队、无线程复用、无拒绝机制 |

线程池通过**线程复用 + 任务队列 + 拒绝策略**解决了以上问题。

**二、七大核心参数**

```java
public ThreadPoolExecutor(
    int corePoolSize,              // ① 核心线程数（常驻线程）
    int maximumPoolSize,           // ② 最大线程数
    long keepAliveTime,            // ③ 非核心线程空闲存活时间
    TimeUnit unit,                 // ④ 时间单位
    BlockingQueue<Runnable> workQueue,  // ⑤ 任务队列
    ThreadFactory threadFactory,   // ⑥ 线程工厂
    RejectedExecutionHandler handler   // ⑦ 拒绝策略
)
```

**逐参数深度解析：**

| 参数 | 作用 | 面试加分点 |
|------|------|-----------|
| **corePoolSize** | 常驻线程数，即使空闲也不回收（除非 `allowCoreThreadTimeOut`） | 比喻"餐厅固定服务员"——没客人也留岗 |
| **maximumPoolSize** | 最大线程数 = 核心 + 非核心 | 队列满时才创建非核心线程 |
| **keepAliveTime** | 非核心线程空闲多久后被回收 | 业务高峰期过后自动缩容 |
| **workQueue** | 存放等待执行的任务 | 三种常用队列（见下） |
| **threadFactory** | 自定义线程名、优先级、守护 | 生产必备：`new ThreadFactoryBuilder().setNameFormat("order-pool-%d").build()` |
| **handler** | 线程+队列都满时怎么处理 | AbortPolicy/CallerRunsPolicy/DiscardPolicy |

**三种队列对比：**

| 队列类型 | 容量 | 适用场景 | 风险 |
|---------|------|---------|------|
| **ArrayBlockingQueue** | 有界（推荐） | 通用场景，防 OOM | 需合理设置容量 |
| **LinkedBlockingQueue** | 默认无界（Integer.MAX_VALUE） | 不适合高并发 | ⚠️ 易 OOM |
| **SynchronousQueue** | 无容量（不存任务） | 秒杀（需配合大 maximumPoolSize） | 无队列缓冲 ∛ 

**三、核心工作流程（面试高频！）**

```
提交任务 → execute(task) / submit(task)

① 当前线程数 < corePoolSize？
   → YES → 创建新线程执行任务（即使有空闲核心线程）
   → NO  → 进入 ②

② 任务队列 workQueue 满了吗？
   → NO  → 任务入队列，等待核心线程取出执行
   → YES → 进入 ③

③ 当前线程数 < maximumPoolSize？
   → YES → 创建非核心线程执行任务
   → NO  → 进入 ④

④ 执行拒绝策略 handler.rejectedExecution()

核心公式：
  线程数 < 核心 → 新建线程 → 队列 → 新建非核心线程 → 拒绝
```

**⚠️ 常见误区纠正：** 核心线程满时，新任务**先入队列**，队列满了才创建非核心线程。很多人背成"先满核心→再满最大→最后队列"是错误的！

**验证代码：**

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    2, 4, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(3),  // 队列容量=3
    new ThreadFactoryBuilder().setNameFormat("test-%d").build(),
    new ThreadPoolExecutor.AbortPolicy()
);

// 提交 8 个任务（每个任务 sleep 1 秒）
for (int i = 0; i < 8; i++) {
    final int n = i;
    try {
        executor.execute(() -> {
            System.out.println(Thread.currentThread().getName() + " 执行任务" + n);
            try { Thread.sleep(1000); } catch (Exception e) {}
        });
        System.out.println("任务" + n + " 提交成功");
    } catch (RejectedExecutionException e) {
        System.out.println("任务" + n + " 被拒绝!");
    }
}
// 输出分析：
// 任务0→创建线程1，任务1→创建线程2（核心已满）
// 任务2/3/4→入队列（队列容量3已满）
// 任务5→创建线程3，任务6→创建线程4（最大线程已满）
// 任务7→队列+线程全满 → 被拒绝！
```

**四、线程数配置公式**

```java
int cpuCores = Runtime.getRuntime().availableProcessors();

// CPU 密集型（计算、加密、压缩）
// 线程数 = CPU核心数 + 1
// 原因：CPU利用率已近100%，过多线程只会增加上下文切换代价
int cpuThreads = cpuCores + 1;

// IO 密集型（数据库、HTTP、文件读写）
// 线程数 = CPU核心数 × 2
// 原因：线程大部分时间阻塞等待IO，CPU空闲，多开线程提高吞吐
// 更精确公式：Ncpu × (1 + 平均等待时间/平均计算时间)
int ioThreads = cpuCores * 2;

// 混合型
// 线程数 = Ncpu × 目标CPU利用率 × (1 + W/C)
// W=等待时间, C=计算时间, 可通过 Profiling 获取
```

**五、拒绝策略选型**

| 策略 | 行为 | 适用场景 |
|------|------|---------|
| **AbortPolicy**（默认） | 抛 `RejectedExecutionException` | 通用，快速失败 |
| **CallerRunsPolicy**（推荐） | 由提交任务的线程执行，起到"背压"作用 | 需要限流保护下游 |
| **DiscardPolicy** | 静默丢弃 | 允许丢失的日志采集等 |
| **DiscardOldestPolicy** | 丢弃最老任务 | 追求"新数据优先" |

**六、为什么阿里禁止 `Executors` 创建线程池？**

```java
// ❌ 禁止

Executors.newCachedThreadPool();    // 线程数无界 → OOM
Executors.newSingleThreadExecutor();// 队列无界 → OOM

// ✅ 正确
new ThreadPoolExecutor(
    cpuCores * 2, cpuCores * 4,
    60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),  // 有界队列
    new ThreadFactoryBuilder().setNameFormat("biz-pool-%d").build(),
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

### 💡 延伸思考

1. **线程池 + CompletableFuture 的最佳实践？** — 如果不传入自定义线程池，`CompletableFuture.supplyAsync()` 默认使用 `ForkJoinPool.commonPool()`（并行度=CPU核心数-1），多业务共享可能导致线程饥饿。生产环境务必传入自定义线程池。
2. **动态线程池如何实现？** — 美团开源的 DynamicTp 通过配置中心（Nacos/Apollo）动态调整 corePoolSize/maximumPoolSize，无需重启。核心是通过 `ThreadPoolExecutor.setCorePoolSize()` 和 `setMaximumPoolSize()` 方法动态生效。

**二、BeanPostProcessor vs BeanFactoryPostProcessor（面试必问！）**

| 维度 | BeanFactoryPostProcessor | BeanPostProcessor |
|------|-------------------------|-------------------|
| **执行时机** | 所有 Bean **实例化之前**，容器启动阶段 | 每个 Bean **初始化前后**，Bean 创建阶段 |
| **操作对象** | BeanDefinition（元数据） | Bean 实例（已创建好的对象） |
| **执行次数** | 每个 BFP 执行一次 | 每个 Bean 创建时各执行一次 |
| **典型应用** | 修改 Bean 作用域、注册新 BeanDefinition | 创建 AOP 代理、属性增强、初始化回调 |
| **经典实现** | `ConfigurationClassPostProcessor`（解析 @Configuration） | `AbstractAutoProxyCreator`（AOP 代理） |

**核心区别：BeanFactoryPostProcessor 管"配方"，BeanPostProcessor 管"成品"**

**三、BeanPostProcessor 的两个核心方法**

```java
public interface BeanPostProcessor {
    
    // ★ Before：在 @PostConstruct 和 InitializingBean.afterPropertiesSet() 之前
    @Nullable
    default Object postProcessBeforeInitialization(Object bean, String beanName) {
        return bean;  // 可返回原始 Bean 或包装/代理
    }
    
    // ★ After：在初始化完成后，AOP 代理在此创建
    @Nullable
    default Object postProcessAfterInitialization(Object bean, String beanName) {
        return bean;  // ★ 返回的可能是代理对象！
    }
}
```

**Spring 内置的关键 BeanPostProcessor：**

| BPP | 作用 | 阶段 |
|-----|------|------|
| **AutowiredAnnotationBeanPostProcessor** | 处理 @Autowired | 属性填充 |
| **CommonAnnotationBeanPostProcessor** | 处理 @PostConstruct / @PreDestroy / @Resource | Before/After |
| **AbstractAutoProxyCreator** | 创建 AOP 动态代理 | After 阶段 |
| **ApplicationContextAwareProcessor** | 处理 Aware 接口回调 | Before 阶段 |

**四、实战：自定义 BeanPostProcessor 实现日志注入**

```java
@Component
public class LogInjectBeanPostProcessor implements BeanPostProcessor {
    
    // 在初始化前：给所有 Controller 注入 Logger
    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName) {
        if (bean.getClass().isAnnotationPresent(RestController.class)) {
            try {
                Field logField = bean.getClass().getDeclaredField("log");
                logField.setAccessible(true);
                logField.set(bean, LoggerFactory.getLogger(bean.getClass()));
            } catch (Exception e) {
                // 没有 log 字段就跳过
            }
        }
        return bean;
    }
    
    // 在初始化后：打印 Bean 创建耗时
    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        System.out.println("Bean [" + beanName + "] 初始化完成 → " + bean.getClass().getName());
        return bean;
    }
}
```

**六、场景化面试实例（2026 新趋势）**

面试官："订单模块发生内存泄漏，如何在不拖垮整个系统的情况下隔离问题？"

**答案思路：** 用到 Bean 生命周期知识——
1. 给订单模块的 Bean 设置 `@Scope("prototype")`，每次获取新实例，避免单例积压
2. 自定义 `BeanPostProcessor.postProcessAfterInitialization()` 中检测 Bean 大小
3. 利用 `BeanFactoryPostProcessor` 在启动时动态调整订单模块相关 Bean 的 `@Lazy` 属性
4. 结合 JVM 参数 `-XX:+HeapDumpOnOutOfMemoryError` 兜底

### 💡 延伸思考

1. **`@PostConstruct` 和 `afterPropertiesSet()` 谁的优先级更高？** — `@PostConstruct` 更早执行（由 `CommonAnnotationBeanPostProcessor` 的 before 阶段触发），`afterPropertiesSet()` 在初始化阶段执行。如果两者并存，执行顺序是 `@PostConstruct` → `afterPropertiesSet()`。
2. **为什么 `@Configuration` 类中的 `@Bean` 方法不会创建多个实例？** — 因为 `@Configuration` 默认使用 `proxyBeanMethods = true`（CGLIB 代理），容器会拦截 `@Bean` 方法调用，返回的是已有的容器单例，而不是真的再调一次方法。`@AutoConfiguration` 则默认 `proxyBeanMethods = false` 以加速启动。

**一、慢 SQL 优化闭环（五步法）**

```
① 发现 → 慢查询日志定位具体 SQL
② 分析 → EXPLAIN 查看执行计划
③ 优化 → 索引优化 / SQL 重构 / 架构调整
④ 验证 → 对比优化前后执行计划
⑤ 监控 → 持续观察，防止新的慢 SQL
```

**1.1 开启慢查询日志**

**二、EXPLAIN 执行计划深度解读**

**只需重点看 4 个字段：**

| 字段 | 含义 | 判断标准 |
|------|------|---------|
| **type** | 访问类型（最重要！） | system > const > eq_ref > ref > range > index > ALL |
| **key** | 实际使用的索引 | NULL = 没用到索引 |
| **rows** | 预估扫描行数 | 越小越好，与实际返回行数偏差大 = 需要优化 |
| **Extra** | 额外信息 | Using filesort / Using temporary = 性能杀手 |

**2.1 type 字段全解（从优到差）：**

| type | 含义 | 示例 |
|------|------|------|
| **const** | 主键/唯一索引命中一行 | `WHERE id = 1` |
| **eq_ref** | JOIN 时被驱动表用主键/唯一索引 | `JOIN b ON a.id = b.id` |
| **ref** | 普通索引匹配 | `WHERE name = 'Tom'` |
| **range** | 索引范围扫描 | `WHERE id > 100 AND id < 200` |
| **index** | 扫描整个索引树（不扫描数据行） | `SELECT id FROM t`（覆盖索引） |
| **ALL** | 全表扫描 ⚠️ | 没有可用索引或优化器选择全表 |

**看到 ALL→加索引；看到 index→检查能否优化为 range；看到 range→检查区分度。**

**2.2 Extra 字段关键值：**

| Extra 值 | 含义 | 优化方向 |
|----------|------|---------|
| **Using index** | ✅ 覆盖索引，无需回表 | 理想状态 |
| **Using where** | 使用 WHERE 过滤 | 正常 |
| **Using index condition** | 使用 ICP（索引下推） | MySQL 5.6+ 优化特性 |
| **Using filesort** | ⚠️ 额外排序 | 给 ORDER BY 字段加索引 |
| **Using temporary** | ⚠️ 使用临时表 | 给 GROUP BY/DISTINCT 字段加索引 |
| **Using join buffer** | ⚠️ JOIN 无索引 | 给 JOIN 字段加索引 |

**三、7 种常见索引失效场景（背下来！）**

```
① 违背最左前缀原则
  索引：(a, b, c)
  WHERE b = 1 AND c = 2  → 不走索引 ❌（跳过了 a）
  WHERE a = 1 AND c = 2  → 只用 a，c 不走（a 后的 b 断了）

② 索引列使用函数或表达式
  WHERE YEAR(create_time) = 2026     → 不走索引 ❌
  WHERE create_time >= '2026-01-01'  → 走索引 ✅
  WHERE age + 1 = 20                 → 不走索引 ❌

③ 隐式类型转换
  phone VARCHAR(20)
  WHERE phone = 13800138000          → 不走索引 ❌（整型→字符串隐式转换）
  WHERE phone = '13800138000'        → 走索引 ✅

④ LIKE 以 % 开头
  WHERE name LIKE '%Tom'   → 不走索引 ❌
  WHERE name LIKE 'Tom%'   → 走索引 ✅

⑤ OR 连接非索引列
  WHERE id = 1 OR name = 'Tom'
  → id 走索引但 name 没索引 → 最终可能全表扫描 ❌
  → 改 UNION ALL：SELECT ... WHERE id = 1 UNION ALL SELECT ... WHERE name = 'Tom'

⑥ 负向查询
  WHERE id != 100      → 不走索引 ❌
  WHERE id NOT IN (1,2,3) → 不走索引 ❌
  WHERE id > 100 OR id < 100 → 走索引 ✅（范围查询但走索引）

⑦ 优化器认为全表扫描更快
  当结果集 > 约 30% 时，优化器放弃索引
  SELECT * FROM user WHERE gender = 'M'  → 50% 数据可能全表扫描
```

**四、大表深度分页优化（面试高频场景题）**

**问题：** `SELECT * FROM orders ORDER BY id LIMIT 1000000, 20`，千万数据量执行超过 5 秒。

**为什么慢？** MySQL 需要扫描前 1000020 条数据，再丢弃前 1000000 条。

```
四种优化方案（按推荐度排序）：

方案 1：游标分页（推荐，本质是"记住上次的位置"）
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 20;
→ 直接定位到 id > 1000000 开始取 20 条 → 毫秒级
→ 限制：只能上一页/下一页，不能跳页；非自增ID不适用

方案 2：覆盖索引 + 子查询
SELECT * FROM orders 
WHERE id >= (SELECT id FROM orders ORDER BY id LIMIT 1000000, 1)
ORDER BY id LIMIT 20;
→ 子查询用覆盖索引只扫描索引树（快），外层再用主键回表
→ 仍然扫描了 1000000 条索引记录，但比全表扫描快得多

方案 3：延迟关联
SELECT o.* FROM orders o
INNER JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 20) t
ON o.id = t.id;
→ 子查询只取 id（覆盖索引），再通过 id JOIN 回表获取完整数据

方案 4：ES / 搜索引擎（终极方案）
→ 搜索场景不走 MySQL 分页，走 Elasticsearch 的 search_after
```

**五、EXPLAIN 实战示例**

```sql
-- 错误示例：慢 SQL
EXPLAIN SELECT * FROM orders 
WHERE user_id = 10086 AND delete_flag = 0 
AND create_time >= '2026-01-01' AND create_time < '2026-04-01'
ORDER BY id DESC LIMIT 20;

-- 可能输出：

-- 诊断：全表扫描 + 文件排序 → 严重性能问题！

-- 优化：建联合索引
CREATE INDEX idx_uid_flag_time ON orders(user_id, delete_flag, create_time);

-- 优化后 EXPLAIN：
-- type: range, key: idx_uid_flag_time, rows: 1200, Extra: Using index condition
-- 扫描从 500 万降到 1200 行！
```

### 💡 延伸思考

1. **为什么 `ORDER BY id` 时 Extra 出现 `Using filesort` 但 `id` 明明是主键？** — 因为 `WHERE` 条件中的范围查询（如 `create_time >=`）导致联合索引在该字段处中断，`ORDER BY` 无法利用索引有序性，需要额外排序。解决：调整联合索引顺序，把 ORDER BY 字段放在范围查询字段前面。
2. **Online DDL 如何给大表加索引不锁表？** — MySQL 5.6+ 默认使用 Online DDL（`ALGORITHM=INPLACE`），大部分索引操作（添加普通索引、联合索引）不锁表。但仍会占用磁盘 IO 和临时空间，建议在业务低峰期操作。如果用 `pt-online-schema-change` 工具，可以更安全地控制负载。

## 题目 4：[缓存/Redis] 请详细解释 Redis 分布式锁的实现原理与从 SETNX 到 Redisson 的演进路径，重点分析看门狗（Watchdog）自动续期机制、RedLock 算法的争议，以及 Redis 锁与 ZooKeeper 锁的区别与选型

**考点来源**：2026-05-13 午间报告 — "消息队列：Kafka 集成、工作原理、高并发场景优化" + "场景化面试成为主流"  
**相关岗位**：Java后端 / 分布式系统 / 电商/金融

### 📖 参考答案

**一、分布式锁的四代演进**

```
第一代：SETNX + EXPIRE（两条命令，不原子！）
  问题：SETNX 成功 → 宕机 → EXPIRE 未执行 → 死锁！

第二代：SET key value NX EX 30（原子命令）
  解决：加锁 + 过期一条命令完成
  新问题：业务执行超过 30 秒 → 锁过期 → 其他线程拿锁 → 并发！

第三代：Lua 脚本释放锁（解决误删）
  问题：锁过期 → B 拿到锁 → A 执行完释放了 B 的锁！

第四代：Redisson 完整框架（看门狗 + 可重入 + 公平锁 + 读写锁）
```

**二、第二代：SET NX EX 原子命令**

```java
// 正确加锁方式
public boolean tryLock(String key, String requestId, int expireSeconds) {
    // SET key value NX EX seconds  → 一条原子命令
    String result = jedis.set(key, requestId, 
        SetParams.setParams().nx().ex(expireSeconds));
    return "OK".equals(result);
}

// 释放锁 —— Lua 脚本保证原子性（防止误删别人的锁）
String script = """
    if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1])
    else
        return 0
    end
    """;
jedis.eval(script, Collections.singletonList(key), 
           Collections.singletonList(requestId));
```

**三、第三代 → 第四代：Redisson 看门狗机制**

Redisson 解决了"锁过期但业务未完成"的致命问题：

```
Redisson 加锁流程（RLock.lock()）：

  ① Lua 脚本加锁：
     if (redis.call('exists', key) == 0) then
         redis.call('hincrby', key, threadId, 1);  -- Hash 结构，支持可重入
         redis.call('pexpire', key, 30000);        -- 初始过期 30 秒
         return nil;  -- 加锁成功
     end;
     if (redis.call('hexists', key, threadId) == 1) then
         redis.call('hincrby', key, threadId, 1);  -- 重入：计数 +1
         redis.call('pexpire', key, 30000);
         return nil;
     end;
     return redis.call('pttl', key);  -- 加锁失败，返回剩余过期时间

  ② 加锁成功后启动"看门狗"定时任务：
     每隔 10 秒（lockTimeout/3，即 30/3 = 10 秒）
     → 检查锁是否还被当前客户端持有
     → 是 → 重置过期时间为 30 秒（续期！）
     → 否 → 停止看门狗

  ③ 解锁时：
     → 取消看门狗任务
     → Lua 脚本：hincrby -1，计数归 0 则 del key
     → 发布 UNLOCK_MESSAGE，通知等待的线程
```

**看门狗的关键参数：**

```java
// 默认锁超时 30 秒，看门狗每 10 秒续期
Config config = new Config();
config.setLockWatchdogTimeout(30000);  // 默认 30 秒

// 自定义锁超时（指定了时间就不启动看门狗！）
lock.lock(10, TimeUnit.SECONDS);  // ← 10 秒后自动释放，无看门狗
lock.lock();                      // ← 默认 30 秒 + 看门狗自动续期
```

**四、RedLock 算法及其争议**

**RedLock 解决什么问题？** 主从架构下，主节点宕机可能丢锁：

```
场景：客户端 A 在主节点加锁成功
     主节点宕机，锁数据未同步到从节点
     从节点提升为新主节点
     客户端 B 在新主节点加同一把锁 → 成功！
     → A 和 B 同时持有锁！并发！
```

**RedLock 算法（基于 N 个独立 Redis 节点）：**

```
加锁流程（N=5，quorum=3）：
  ① 获取当前时间 t1
  ② 依次向 5 个独立 Redis Master 节点申请加锁
     （每个 SET NX PX，超时时间远小于锁的 TTL）
  ③ 如果 ≥ 3 个节点加锁成功（quorum），且总耗时 < 锁的有效期
     → 加锁成功！
  ④ 锁的有效期 = 初始 TTL - (t2 - t1)  // 减去申请耗时
  ⑤ 如果加锁失败 → 向所有节点发送解锁请求
```

**RedLock 的争议（Martin Kleppmann 的批判）：**

| 争议点 | 说明 |
|--------|------|
| **时钟跳跃** | RedLock 依赖过期时间，系统时钟跳跃（NTP 校时）可能导致锁提前过期 |
| **GC 停顿** | 客户端 Full GC 导致锁在不知情的情况下过期 |
| **fencing token** | 即使加锁成功，数据存储层（如数据库）无法感知锁的状态——写入仍需 fencing token 防冲突 |
| **复杂度代价** | 维护 5 个独立 Redis 节点增加了运维成本 |

**Antirez（Redis 作者）的回应：** RedLock 是"尽力而为"的方案，主要防止客户端崩溃 + 时钟正常场景下的并发。极端场景（时钟跳跃）概率极低且可监控。

**五、Redis 锁 vs ZooKeeper 锁终极对比**

| 维度 | Redis 分布式锁 | ZooKeeper 分布式锁 |
|------|--------------|-------------------|
| **CAP 定位** | AP（高可用 + 最终一致） | CP（强一致 + 可能不可用） |
| **实现原理** | SET NX EX + 看门狗 | 临时顺序节点 + Watcher |
| **锁释放** | TTL 过期 / 主动 DEL | Session 断开自动删除临时节点（天然防死锁） |
| **阻塞等待** | 客户端自旋/订阅通知 | Watcher 监听前一个节点删除事件 |
| **可重入** | Redisson Hash 计数器 | Curator InterProcessMutex |
| **性能** | ⭐⭐⭐⭐⭐ 极高 | ⭐⭐⭐ 中等（ZAB 协议开销） |
| **一致性** | ⭐⭐⭐ 主从切换可能丢锁 | ⭐⭐⭐⭐⭐ 强一致，绝不丢锁 |
| **运维复杂度** | ⭐⭐ 低（已有 Redis 集群可复用） | ⭐⭐⭐⭐ 高（需单独 ZK 集群） |
| **典型场景** | 高性能、允许极端情况下的"尽力而为" | 金融、支付、资金操作（对一致性要求极高） |

**选型建议：**

```
秒杀扣库存、防止重复提交 → Redis（Redisson）
资金转账、对账、金融核心 → ZooKeeper（Curator）
资源不紧张但有 Redis → 直接用 Redisson（够用 99% 场景）
```

### 💡 延伸思考

1. **分布式锁一定是必须的吗？** — 不一定。很多场景可以用**乐观锁**（数据库版本号）或 **CAS**（Redis INCR + 前值判断）替代。只有真正需要"互斥访问"的场景才需要分布式锁。过度使用分布式锁反而降低系统吞吐。
2. **Redisson 的看门狗如果也因网络问题没能续期怎么办？** — Redisson 会不断重试，但如果锁已过期，`pexpire` 命令返回 0（key 不存在），框架会感知锁丢失。业务代码可以做二次检查（如数据库 `version` 字段），实现**锁 + 乐观锁**的双重保障。

**一、Function Calling 的核心原理**

**本质：Function Calling 是 LLM 与外部工具之间的"契约"——你告诉 LLM 有什么工具可用（函数名、参数描述），LLM 决定什么时候调用哪个工具并输出结构化参数，你的代码负责真正执行并把结果返回给 LLM。**

```
传统 AI 对话：                    Function Calling：
  用户："北京今天天气？"            用户："北京今天天气？"
  模型：(猜一个...)                模型："我需要调用 getWeather('北京')"
    ↓                               ↓
  无用/错误的回答                   ［你的代码执行 getWeather］
                                    ↓
                                   返回：{"city":"北京","temp":25,"desc":"晴"}
                                    ↓
                                  模型："北京今天晴，25°C" ✅
```

@RestController
class HybridController {
    
    @GetMapping("/agent")
    public String ask(@RequestParam String q,
                      @RequestParam(defaultValue = "5") int topK) {

        List<Document> docs = vectorStore.similaritySearch(
            SearchRequest.query(q).withTopK(topK));
        String context = docs.stream()
            .map(Document::getContent)
            .collect(Collectors.joining("\n\n"));

        return chatClient.prompt()
            .system("参考资料：\n{context}")

            .call()
            .content();

### 💡 延伸思考

1. **Function Calling 和 MCP 协议是什么关系？** — Function Calling 是 LLM 层面的"工具调用能力"（模型能理解需要调用什么工具），MCP 是架构层面的"工具统一接入协议"（让工具可以标准化暴露）。简单类比：Function Calling 是"我能用螺丝刀"，MCP 是"所有螺丝刀都长一个标准接口"。
2. **Agent 会不会"乱调用"工具导致安全问题？** — 会。生产环境需要：① 工具分级（读操作默认开放，写操作需用户二次确认）；② 参数校验（SQL 注入、非法输入）；③ 调用频率限制（防止无限循环）；④ 审计日志（记录每次工具调用的输入输出）。
