**一、JVM 运行时数据区全景图**

JVM 在执行 Java 程序时，将管理的内存划分为若干个不同的数据区域。JDK 8 之后，永久代被元空间取代。

```
JVM 运行时数据区（JDK 8+）：

  ┌─────────────────────────────────────────────────────────┐
  │                    线程共享区域                           │
  │  ┌──────────────────────┐  ┌──────────────────────────┐ │
  │  │       堆 (Heap)       │  │    方法区 (Method Area)   │ │
  │  │  ┌──────────────────┐│  │   ┌────────────────────┐ │ │
  │  │  │ 新生代 (Young)    ││  │   │ 运行时常量池         │ │ │
  │  │  │ Eden:S0:S1       ││  │   │ 类元数据             │ │ │
  │  │  │ = 8:1:1          ││  │   │ 方法字节码           │ │ │
  │  │  ├──────────────────┤│  │   └────────────────────┘ │ │
  │  │  │ 老年代 (Old)      ││  │  实现：元空间(Metaspace) │ │
  │  │  └──────────────────┘│  │  使用本地内存，非堆内存   │ │
  │  └──────────────────────┘  └──────────────────────────┘ │
  ├─────────────────────────────────────────────────────────┤
  │                    线程私有区域                           │
  │  ┌──────────┐ ┌──────────┐ ┌──────────────┐            │
  │  │程序计数器 │ │虚拟机栈   │ │ 本地方法栈    │            │
  │  │(PC Register)│(VM Stack)│ │(Native Stack)│            │
  │  │无OOM/无SOF│ │StackOverflow│ │同虚拟机栈    │            │
  │  └──────────┘ └──────────┘ └──────────────┘            │
  └─────────────────────────────────────────────────────────┘
```

**各区域详解**：

| 区域 | 线程共享 | 存储内容 | 异常 |
|------|---------|---------|------|
| **程序计数器** | 私有 | 当前线程执行的字节码行号指示器 | 无（唯一不抛 OOM 的区域） |
| **虚拟机栈** | 私有 | 栈帧（局部变量表、操作数栈、动态链接、返回地址） | StackOverflowError / OOM |
| **本地方法栈** | 私有 | Native 方法的栈帧 | StackOverflowError / OOM |
| **堆** | 共享 | 对象实例和数组 | OOM: Java heap space |
| **方法区/元空间** | 共享 | 类元数据、运行时常量池、方法字节码 | OOM: Metaspace |

**二、堆内存的分代结构——为什么分代？**

```
堆内存分代结构：

  ┌────────────────────────────────────────────────┐
  │                  Heap (堆)                       │
  │  ┌──────────────────────┐  ┌──────────────────┐ │
  │  │   新生代 (Young Gen)  │  │ 老年代 (Old Gen)  │ │
  │  │  ┌────┬─────┬─────┐  │  │                  │ │
  │  │  │Eden│ S0  │ S1  │  │  │  长期存活的对象   │ │
  │  │  │ 80%│ 10% │ 10% │  │  │  大对象          │ │
  │  │  └────┴─────┴─────┘  │  │                  │ │
  │  │  新对象首先分配到这里   │  │                  │ │
  │  └──────────────────────┘  └──────────────────┘ │
  └────────────────────────────────────────────────┘

分代的原因：
  - 大部分对象"朝生夕死"（98% 的对象在 Minor GC 后死亡）
  - 不同生命周期的对象用不同的回收策略，效率更高
  - 新生代用复制算法（存活对象少，复制成本低）
  - 老年代用标记-清除/标记-整理（存活对象多，复制成本高）
```

**三、对象的完整生命周期**

```
对象从生到死的完整旅程：

  ① 新对象 → Eden 区分配
     - 大多数对象在 Eden 区诞生
     - 大对象（如大数组）可能直接进入老年代

  ② Eden 区满 → Minor GC（Young GC）
     - 标记 Eden + S0 中的存活对象
     - 将存活对象复制到 S1
     - 清空 Eden + S0
     - 存活对象年龄 +1

  ③ S0 和 S1 交替使用
     - 每次 Minor GC 后，Eden 和其中一个 Survivor 被清空
     - 两个 Survivor 始终有一个是空的

  ④ 年龄达到阈值（默认 15）→ 晋升老年代
     - 或动态年龄判断：同龄对象总大小超过 Survivor 50% → 提前晋升
     - 或 Survivor 空间不足 → 通过分配担保机制提前进入老年代

  ⑤ 老年代满 → Full GC（Major GC）
     - 回收整个堆（新生代 + 老年代）+ 方法区
     - STW（Stop The World）时间长，应尽量避免

  ⑥ 对象被回收 → 内存释放
```

```java
// 验证对象分配过程
// VM参数：-Xms20M -Xmx20M -Xmn10M -XX:+PrintGCDetails
public class GCTest {
    private static final int _1MB = 1024 * 1024;
    
    public static void main(String[] args) {
        byte[] a1 = new byte[2 * _1MB];  // Eden 分配
        byte[] a2 = new byte[2 * _1MB];  // Eden 分配
        byte[] a3 = new byte[2 * _1MB];  // Eden 不足 → Minor GC
        // a1, a2 存活 → 进入 Survivor（但可能太大直接进老年代）
        byte[] a4 = new byte[4 * _1MB];  // 大对象直接进老年代
    }
}
```

**四、GC 算法——三种经典算法**

### 1. 标记-清除（Mark-Sweep）

```
标记-清除：
  ① 标记：从 GC Roots 出发，标记所有可达对象
  ② 清除：遍历堆，回收未标记的对象

  优点：不需要移动对象
  缺点：
    ❌ 效率低（标记和清除两个阶段都慢）
    ❌ 产生内存碎片（碎片太多可能导致无法分配大对象）

  适用：老年代（CMS 的基础算法）
```

### 2. 标记-复制（Mark-Copy）

```
标记-复制：
  ① 将内存分为两块（如 Eden:S0:S1 = 8:1:1）
  ② 标记存活对象
  ③ 将存活对象复制到另一块区域
  ④ 清空原区域

  优点：
    ✅ 无内存碎片
    ✅ 实现简单，效率高
  缺点：
    ❌ 内存利用率低（一半空间闲置）
    ❌ 存活对象多时复制成本高

  适用：新生代（存活对象少，复制成本低）
```

### 3. 标记-整理（Mark-Compact）

```
标记-整理：
  ① 标记：从 GC Roots 出发，标记所有可达对象
  ② 整理：将所有存活对象移动到内存的一端
  ③ 清理边界外的内存

  优点：
    ✅ 无内存碎片
    ✅ 内存利用率高
  缺点：
    ❌ 移动对象需要 STW，且更新引用开销大

  适用：老年代（存活对象多，不适合复制）
```

**五、垃圾回收器——选型指南**

```
HotSpot 垃圾回收器演进：

  Serial → Parallel → CMS → G1 → ZGC → Shenandoah
  (单线程) (并行)   (并发) (区域化) (超低延迟)

  2026 年主流选择：
  - JDK 8：Parallel（默认）/ CMS（已废弃）
  - JDK 11-17：G1（默认）
  - JDK 17+：ZGC（低延迟首选）
```

| 回收器 | 目标 | 算法 | STW | 适用场景 |
|--------|------|------|-----|---------|
| **Serial** | 单线程 | 复制/整理 | 长 | 客户端、小内存 |
| **Parallel** | 吞吐量优先 | 复制/整理 | 较长 | 后台计算、批处理 |
| **CMS** | 低延迟 | 标记-清除 | 较短 | JDK 8 老年代（已废弃） |
| **G1** | 平衡延迟与吞吐 | 区域化+复制 | 可控 | **JDK 9+ 默认**，4G-64G 堆 |
| **ZGC** | 超低延迟 | 染色指针+复制 | **<1ms** | JDK 17+，大堆（TB 级） |
| **Shenandoah** | 超低延迟 | 并发复制 | <10ms | 大堆，与 ZGC 竞争 |

**G1 的核心原理**：

```
G1（Garbage First）不再按新生代/老年代物理划分，而是将堆分为多个 Region：

  ┌───┬───┬───┬───┬───┬───┬───┬───┐
  │ E │ E │ S │ O │ E │ H │ O │ O │  E=Eden, S=Survivor
  ├───┼───┼───┼───┼───┼───┼───┼───┤  O=Old, H=Humongous
  │ O │ E │ E │ O │ O │ E │ S │ E │
  └───┴───┴───┴───┴───┴───┴───┴───┘

  G1 的核心策略：
  ① 优先回收垃圾最多的 Region（Garbage First）
  ② 每次 GC 只回收部分 Region（Mixed GC）
  ③ 通过 -XX:MaxGCPauseMillis 控制最大停顿时间
  ④ 标记阶段与用户线程并发执行
```

**ZGC 的革命性**：

```
ZGC 的核心技术——染色指针（Colored Pointers）：

  64 位指针中，ZGC 用其中 4 位存储元数据：
  ┌──────┬─────┬─────┬─────┬─────┬──────────┐
  │ 未使用 │Final│Remap│Mark0│Mark1│  对象地址  │
  │ 16位  │ 1位 │ 1位 │ 1位 │ 1位 │   44位    │
  └──────┴─────┴─────┴─────┴─────┴──────────┘

  优势：
  ✅ 并发整理（移动对象时不 STW，通过读屏障自愈）
  ✅ STW 时间 < 1ms（与堆大小无关）
  ✅ 支持 TB 级堆
  ✅ JDK 21+ 分代 ZGC 进一步提升吞吐量
```

**六、GC 选型决策树**

```
GC 选型决策：

  你的场景是什么？

  ├─ 客户端 / 小内存（< 1GB）
  │   → Serial GC（简单高效）
  │
  ├─ 后台批处理 / 吞吐量优先
  │   → Parallel GC
  │   目标：最大化吞吐量（GC 时间占比 < 5%）
  │
  ├─ 通用服务端（4GB - 64GB）
  │   → G1 ✅（JDK 9+ 默认）
  │   设置 -XX:MaxGCPauseMillis=200
  │
  ├─ 低延迟服务（< 10ms 停顿要求）
  │   → ZGC ✅（JDK 17+）
  │   设置 -Xms 和 -Xmx 相同（避免动态调整）
  │
  └─ 超大堆（> 64GB）
      → ZGC 或 Shenandoah
```

### 💡 延伸思考

1. **为什么 Survivor 区是两个而不是一个？** — 如果只有一个 Survivor，Minor GC 时 Eden 的存活对象复制到 Survivor，但 Survivor 本身也有存活对象需要清理，会产生碎片。两个 Survivor 交替使用，每次 GC 后总有一个是空的，存活对象都复制到空的那个，始终保持"标记-复制"的简洁性，避免碎片。
2. **ZGC 的"染色指针"把 4 位用于元数据，那最大堆只有 16TB（44 位地址），够用吗？** — 2026 年来看够用。16TB 堆已经远超绝大多数应用需求。如果未来不够，JDK 团队可以通过减少元数据位数或使用更大的指针来扩展。而且 ZGC 也支持不染色指针的"Generational ZGC"模式。

**二、IOC 容器与依赖注入**

### IOC 的核心思想

```
传统方式 vs IOC：

  传统：类 A 自己 new 类 B → 强耦合
  IOC：类 A 声明需要类 B → 容器注入 → 松耦合

  "控制反转"的含义：
  - 控制：对象创建和管理的权力
  - 反转：从"自己控制"反转为"交给容器控制"
```

### @Autowired vs @Resource

| 维度 | @Autowired | @Resource |
|------|-----------|-----------|
| 来源 | Spring 内置 | JDK JSR-250 |
| 默认注入方式 | **byType**（按类型） | **byName**（按名称） |
| 多实现处理 | 需要 @Qualifier 指定 | 可通过 name 属性指定 |
| 是否必须 | required=true（默认必须） | 默认必须 |
| 支持位置 | 构造器/方法/字段/参数 | 字段/setter |

```java
// @Autowired 注入逻辑
// ① 先按类型匹配 → 找到唯一 Bean → 直接注入
// ② 找到多个同类型 Bean → 按名称匹配（字段名 = Bean 名）
// ③ 名称也不匹配 → 抛出 NoUniqueBeanDefinitionException

// 示例
@Autowired
private UserService userService;  
// 按类型找 UserService → 如果只有一个实现 → 注入
// 如果有 UserServiceImpl1 和 UserServiceImpl2 → 按名称 "userService" 匹配 → 都匹配不上 → 报错

@Autowired
@Qualifier("userServiceImpl1")  // 显式指定 Bean 名称
private UserService userService;

// @Resource 注入逻辑
@Resource
private UserService userService;
// ① 先按名称 "userService" 匹配
// ② 找不到再按类型 UserService 匹配
// ③ 多个同类型 → 报错

@Resource(name = "userServiceImpl1")  // 显式指定名称
private UserService userService;
```

**三、AOP 的两种代理方式**

### JDK 动态代理 vs CGLIB

```
JDK 动态代理：
  ┌──────────┐
  │ 接口      │ ← UserService（接口）
  ├──────────┤
  │ 实现类    │ ← UserServiceImpl
  └──────────┘
       ↑
  ┌──────────┐
  │ 代理对象  │ ← $Proxy0（实现 UserService 接口）
  │ InvocationHandler.invoke() │
  └──────────┘

  条件：目标类必须实现接口
  实现：java.lang.reflect.Proxy + InvocationHandler
  原理：运行时动态生成一个实现相同接口的代理类

CGLIB 代理：
  ┌──────────┐
  │ 目标类    │ ← UserService（没有接口的普通类）
  └──────────┘
       ↑
  ┌──────────┐
  │ 代理对象  │ ← UserService$$EnhancerByCGLIB（继承目标类）
  │ MethodInterceptor.intercept() │
  └──────────┘

  条件：目标类不能是 final（因为需要继承）
  实现：ASM 字节码框架
  原理：运行时动态生成目标类的子类，重写方法
```

| 维度 | JDK 动态代理 | CGLIB |
|------|------------|-------|
| 代理方式 | 实现接口 | 继承类 |
| 要求 | 必须有接口 | 类不能是 final |
| 性能（创建） | 快 | 慢（需要生成字节码） |
| 性能（调用） | 反射调用，略慢 | FastClass 机制，略快 |
| Spring 默认 | Spring Boot 1.x | **Spring Boot 2.x+** |
| final 方法 | 不影响（接口方法） | **不能被代理** |

**Spring Boot 2.x 为什么默认用 CGLIB？**

```
原因：
① 不需要强制写接口（更灵活）
② CGLIB 调用性能更好（FastClass 索引机制）
③ 避免接口代理的类型转换问题

但注意：
- @Transactional 的 self-invocation 问题依然存在
  → 同类中方法互调不走代理 → 事务失效！
  → 解决：注入自己（@Autowired private XxxService self）或用 AspectJ
```

### 💡 延伸思考

1. **Spring Boot 3.x 的自动配置有什么变化？** — Spring Boot 3.x 用 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 文件替代了 `spring.factories` 中的自动配置注册。同时用 `@AutoConfiguration` 替代了 `@Configuration`（语义更明确）。这些变化让自动配置的加载更快、更可预测。
2. **为什么 @Transactional 在同类方法调用时会失效？** — 因为 Spring AOP 是基于代理的。当你在类内部调用 `this.methodB()` 时，调用的是原始对象的方法，而不是代理对象的方法，因此 AOP 切面（事务拦截器）不会生效。解决方案：① 注入自己 `@Autowired private XxxService self`，用 `self.methodB()` 调用；② 将方法拆分到不同的类中；③ 使用 AspectJ 编译时织入（不推荐，太重）。

**考点来源**：2026-06-06 早间报告 — "数据库 + Redis + JVM「三连杀」" + 午后报告 — "微服务架构（Spring Cloud）" + 数据库扩展是后端面试必考 TOP 领域

### 📖 参考答案

**一、为什么需要分库分表？—— 单库单表的极限**

```
单库单表的瓶颈：

  ① 存储瓶颈：单表数据量超过千万级 → B+Tree 高度增加 → IO 次数增加
  ② 写入瓶颈：单库写入 QPS 上限约 2000-5000（取决于硬件）
  ③ 连接瓶颈：单库最大连接数有限（通常 2000-5000）
  ④ 备份瓶颈：数据量越大，备份和恢复时间越长

  分库分表 vs 读写分离：
  - 读写分离：解决读并发问题（主写从读）
  - 分库分表：解决存储容量和写入并发问题
```

**二、垂直分库 vs 水平分库**

```
垂直分库（按业务拆分）：

  单一数据库 → 拆分为多个业务数据库

  ┌──────────────┐     ┌──────┐ ┌──────┐ ┌──────┐
  │  单库         │     │用户库│ │订单库│ │商品库│
  │  user        │ →   │user  │ │order │ │product│
  │  order       │     └──────┘ └──────┘ └──────┘
  │  product     │
  └──────────────┘

  优点：业务清晰，各库独立扩展
  缺点：无法解决单表数据量过大的问题

水平分库（按数据行拆分）：

  单表 → 拆分为多个结构相同的表（分布在不同库）

  order 表（1 亿行）→ order_0（0-5000万） + order_1（5000万-1亿）

  ┌──────────┐  ┌──────────┐
  │ DB0      │  │ DB1      │
  │ order_0  │  │ order_1  │
  │ order_2  │  │ order_3  │
  └──────────┘  └──────────┘

  优点：解决单表数据量问题，写入性能线性扩展
  缺点：带来分布式事务、跨库查询等复杂问题
```

**三、四种分片算法——核心选型**

### 1. 哈希取模

```java
// 最简单的分片方式
int shardIndex = Math.abs(shardingKey.hashCode()) % shardCount;

// 优点：数据分布均匀
// 缺点：扩容时需要全量数据迁移（取模基数变了）
// 示例：3 个库 → 扩容到 4 个库
//   原来 user_id=7 → 7%3=1 → DB1
//   扩容后 user_id=7 → 7%4=3 → DB3
//   数据位置全变了！需要迁移所有数据
```

### 2. 范围分片

```sql
-- 按时间范围分片
-- order_2026_q1: 2026-01-01 ~ 2026-03-31
-- order_2026_q2: 2026-04-01 ~ 2026-06-30

-- 优点：天然支持范围查询，扩容简单（新增时间区间即可）
-- 缺点：热点数据问题（最新数据都在同一个库）
```

### 3. 一致性哈希

```
一致性哈希：

  将哈希空间组织成环形（0 ~ 2^32-1）
  节点和数据都映射到环上
  数据归属：顺时针找到第一个节点

  ┌─────────────────────────┐
  │    0                    │
  │    ● Node A             │
  │         \               │
  │          \  data1 → A   │
  │           \             │
  │    ● Node C    ● Node B │
  │  2^32-1                 │
  └─────────────────────────┘

  扩容时（新增 Node D）：
  只有 Node D 和下一个节点之间的数据需要迁移
  → 迁移量大幅减少！

  优点：扩容时只需迁移少量数据
  缺点：可能数据分布不均（需要虚拟节点优化）
```

### 4. 映射表路由

```
映射表路由：

  维护一张独立的路由表：
  ┌──────────┬──────────┐
  │ user_id  │ db_index │
  ├──────────┼──────────┤
  │ 1-10000  │ DB0      │
  │ 10001-20000│ DB1    │
  │ ...      │ ...      │
  └──────────┴──────────┘

  优点：极其灵活，可以按任意规则路由
  缺点：路由表本身成为单点和性能瓶颈
```

**分片算法对比**：

| 算法 | 数据均匀 | 扩容友好 | 范围查询 | 实现复杂度 |
|------|---------|---------|---------|-----------|
| 哈希取模 | ⭐⭐⭐⭐⭐ | ❌ | ❌ | 低 |
| 范围分片 | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 低 |
| 一致性哈希 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ❌ | 中 |
| 映射表路由 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 高 |

**四、分片键设计原则**

```
分片键选择的四大原则：

① 共性能（覆盖绝大多数查询）
   - 分片键应该出现在 WHERE 条件中
   - 理想情况：80% 以上的查询都带分片键
   - 反例：用 user_id 分片，但经常按 order_id 查询 → 需要全库扫描

② 离散性（数据均匀分布）
   - 分片键的值应该均匀分布
   - 反例：用 gender（男/女）分片 → 只有 2 个分片，严重倾斜

③ 稳定性（分片键值不变）
   - 分片键的值不应该被修改
   - 反例：用 status 分片 → 订单状态会变 → 数据需要迁移

④ 扩展性（支持动态扩容）
   - 分片方案应该支持未来增加分片
   - 一致性哈希在这方面优于简单取模
```

        if (timestamp < lastTimestamp) {
            throw new RuntimeException("时钟回拨！");
        }
        if (timestamp == lastTimestamp) {

            if (sequence == 0) {

             | (datacenterId << 17)
             | (workerId << 12)

    }

### 💡 延伸思考

1. **ShardingSphere-JDBC 和 ShardingSphere-Proxy 怎么选？** — JDBC 模式：引入 jar 包，性能好（无额外网络开销），但只支持 Java，升级需要重启应用。Proxy 模式：独立部署的数据库代理，支持任何语言，但多一层网络开销。中小团队推荐 JDBC 模式（简单），大团队多语言环境推荐 Proxy 模式（解耦）。

**一、Cache-Aside 模式——最常用的缓存模式**

```
Cache-Aside（旁路缓存）模式：

  读流程：
  ① 先查缓存 → 命中 → 直接返回 ✅
  ② 未命中 → 查数据库 → 写入缓存 → 返回

  写流程：
  ① 更新数据库
  ② 删除缓存（不是更新缓存！）

  为什么是"删除缓存"而不是"更新缓存"？
  - 更新缓存可能产生并发问题（两个写请求的缓存更新顺序不可控）
  - 删除缓存是幂等的（删多次和删一次效果一样）
  - 缓存应该按需加载（懒加载），不常用的数据不应该占缓存空间
```

```
Cache-Aside 读写流程：

  读请求                          写请求
    │                               │
    ▼                               ▼
  ┌──────────┐                ┌──────────┐
  │ 查缓存    │                │ 更新数据库 │
  └────┬─────┘                └────┬─────┘
       │                           │
   ┌───┴───┐                       ▼
   │ 命中？ │                  ┌──────────┐
   └───┬───┘                  │ 删除缓存  │
    Y  │  N                   └──────────┘
       │   │
       ▼   ▼
   返回  查数据库 → 写缓存 → 返回
```

**二、数据不一致的根因分析——并发场景**

### 场景 1：先删缓存，再更新数据库

```
时间线：
  T1: 写请求 A → 删除缓存
  T2: 读请求 B → 缓存未命中 → 查数据库（读到旧数据）
  T3: 写请求 A → 更新数据库（写入新数据）
  T4: 读请求 B → 将旧数据写入缓存

  结果：缓存中是旧数据，数据库是新数据 → 不一致！
  持续时间：直到缓存过期或被再次删除
```

### 场景 2：先更新数据库，再删缓存

```
时间线：
  T1: 写请求 A → 更新数据库（写入新数据）
  T2: 读请求 B → 查缓存（命中旧数据）→ 返回旧数据
  T3: 写请求 A → 删除缓存

  结果：读请求 B 读到了旧数据，但缓存最终被删除
  不一致持续时间：极短（T2 到 T3 之间）

  但还有另一种情况：
  T1: 读请求 B → 缓存未命中 → 查数据库（读到旧数据）
  T2: 写请求 A → 更新数据库（写入新数据）
  T3: 写请求 A → 删除缓存
  T4: 读请求 B → 将旧数据写入缓存

  结果：缓存中又变成了旧数据！
  概率：极低（需要读请求在写请求更新数据库之前查了库，
        又在写请求删除缓存之后才写缓存）
```

**三、"先删缓存还是先更新数据库？"——面试标准推导**

```
标准答案：先更新数据库，再删除缓存

  推导过程：

  ① 从概率角度：
     先删缓存再更新数据库 → 不一致窗口 = 删缓存到更新数据库之间的时间
     先更新数据库再删缓存 → 不一致窗口 = 更新数据库到删缓存之间的时间
     两者窗口时间相近，但后者出现不一致的条件更苛刻
     （需要读请求恰好卡在两个写操作之间）

  ② 从影响范围：
     先删缓存 → 所有并发读请求都会 miss 缓存 → 全部打到数据库
     先更新数据库 → 只有极少数读请求可能读到旧数据

  ③ 从可恢复性：
     先删缓存再更新数据库 → 不一致可能持续到缓存过期（很长）
     先更新数据库再删缓存 → 缓存被删除后，下次读会重新加载正确数据

  结论：先更新数据库，再删除缓存
```

**四、延迟双删——给"先删缓存"加一道保险**

```
延迟双删策略：

  ① 先删除缓存
  ② 更新数据库
  ③ 延迟 N 毫秒（如 500ms）
  ④ 再次删除缓存

  原理：
  第③步的延迟是为了覆盖"读请求在步骤①和②之间查了旧数据并写入缓存"的时间窗口。
  延迟时间 > 读请求的"查数据库 + 写缓存"的耗时。

  缺点：
  ❌ 延迟时间不好确定（太短无效，太长影响用户体验）
  ❌ 第二次删除可能失败（需要重试机制）
  ❌ 只是降低概率，不能 100% 保证一致性
```

```java
// 延迟双删实现
@Service
public class CacheService {
    
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    
    public void updateWithDoubleDelete(String key, Object newData) {
        // ① 先删缓存
        redisTemplate.delete(key);
        
        // ② 更新数据库
        databaseMapper.update(newData);
        
        // ③ 延迟后再删一次
        CompletableFuture.runAsync(() -> {
            try {
                Thread.sleep(500);  // 延迟 500ms
                redisTemplate.delete(key);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });
    }
}
```

**五、Canal + MQ 异步最终一致性——生产级方案**

延迟双删只是"降低概率"，生产环境需要更可靠的方案。

```
Canal + MQ 方案架构：

  ┌─────────┐     ┌─────────┐     ┌─────────┐     ┌─────────┐
  │ 应用服务 │     │  MySQL  │     │  Canal  │     │  MQ     │
  │ (写请求) │────→│ (主库)  │────→│ (binlog)│────→│(RocketMQ)│
  └─────────┘     └─────────┘     └─────────┘     └────┬────┘
                                                       │
                                              ┌────────┴────────┐
                                              ▼                  ▼
                                        ┌──────────┐      ┌──────────┐
                                        │ 缓存更新  │      │ ES 同步  │
                                        │ Consumer │      │ Consumer │
                                        └──────────┘      └──────────┘

  流程：
  ① 应用只负责更新数据库，不操作缓存
  ② Canal 伪装成 MySQL 从库，订阅 binlog
  ③ Canal 解析 binlog → 提取变更数据 → 发送到 MQ
  ④ 缓存消费者消费 MQ 消息 → 删除/更新对应的缓存
  ⑤ ES 消费者消费 MQ 消息 → 更新搜索引擎索引

  优势：
  ✅ 应用层解耦（业务代码不需要关心缓存更新）
  ✅ 可靠性高（MQ 保证消息不丢，可重试）
  ✅ 最终一致性（即使有延迟，最终一定一致）
  ✅ 一箭多雕（同时同步缓存、ES、数据仓库等）
```

```java
// Canal 消费者示例
@Component
public class CanalCacheConsumer {
    
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    
    @KafkaListener(topics = "canal-order-topic")
    public void handleBinlogEvent(CanalMessage message) {
        // 解析 Canal 消息
        String table = message.getTable();
        String type = message.getType();  // INSERT / UPDATE / DELETE
        
        if ("order".equals(table)) {
            // 提取变更的数据
            Map<String, String> data = message.getData();
            String orderId = data.get("id");
            
            // 删除对应的缓存
            String cacheKey = "order:" + orderId;
            redisTemplate.delete(cacheKey);
            
            log.info("缓存已删除: {}", cacheKey);
        }
    }
}
```

### 💡 延伸思考

1. **为什么不用"更新缓存"代替"删除缓存"？** — 两个原因：① 并发写场景下，两个写请求的缓存更新顺序可能和数据库不一致（A 先更新数据库，B 后更新数据库，但 B 的缓存更新可能先于 A 到达 Redis）；② 很多缓存数据是计算/聚合的结果（如"用户订单总数"），不是简单的字段映射，更新成本高。删除缓存 + 懒加载是最简单可靠的方案。
2. **Canal 方案有没有延迟？延迟多大？** — 有延迟，通常在毫秒到秒级。延迟来源：MySQL binlog 写入 → Canal 拉取 → 解析 → 发 MQ → 消费者处理。正常情况延迟 < 100ms，高峰期可能到秒级。如果业务不能接受这个延迟，需要强制读主库。

### 💡 延伸思考

1. **LangChain4j 的 AiServices 和 Spring AI 的 ChatClient 有什么区别？** — AiServices 是声明式（定义接口 → 自动实现），类似 Feign 的思路，代码最简洁；ChatClient 是编程式（Builder 模式），更灵活但代码多。两者都支持 Tool Calling 和流式输出。选择取决于团队偏好：喜欢声明式的用 AiServices，喜欢编程式的用 ChatClient。
2. **Java AI 开发中，MCP 协议的价值是什么？** — MCP（Model Context Protocol）让 AI 模型能安全地访问外部工具和数据源。Spring AI 1.0 和 LangChain4j 都支持 MCP。它的价值在于：① 标准化（不同框架的工具可以互通）；② 安全（工具独立部署，权限隔离）；③ 跨语言（Python 写的 MCP Server 可以被 Java 的 MCP Client 调用）。2026 年 MCP 正在成为 AI 工具集成的事实标准。
