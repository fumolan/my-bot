**一、AQS 是什么？——JUC 的"地基"**

AQS（AbstractQueuedSynchronizer）是 JUC 并发包的底层核心框架，ReentrantLock、Semaphore、CountDownLatch、ReadWriteLock、CyclicBarrier 等所有同步工具全部基于 AQS 实现。理解 AQS 是突破 Java 并发面试的核心关键。

```
AQS 的设计哲学：

  "如果让你设计一个通用的同步框架，能同时支撑 Lock、Semaphore、CountDownLatch，
   你会怎么做？"

  AQS 的答案：模板方法模式
  - AQS 封装了"线程排队、等待、唤醒"这一套通用逻辑
  - 子类只需要实现"怎么抢锁"和"怎么释放锁"的个性化逻辑
  - tryAcquire/tryRelease（独占）和 tryAcquireShared/tryReleaseShared（共享）

  这就是"面向框架编程"的经典案例：
  框架做 80% 的通用工作，开发者只需关注 20% 的业务逻辑。
```

**二、AQS 核心结构——state + CLH 双向队列**

```
AQS 三大核心组件：

  ┌──────────────────────────────────────────────────────────┐
  │                      AQS 核心结构                         │
  │                                                          │
  │  ① state（volatile int）——同步状态                        │
  │     - ReentrantLock: state=0（无锁）→ state=1（有锁）     │
  │       重入时 state++，释放时 state--                      │
  │     - Semaphore: state = 剩余许可证数量                   │
  │     - CountDownLatch: state = 初始计数值                  │
  │     - volatile 保证多线程可见性                           │
  │                                                          │
  │  ② CLH 变体双向队列——等待队列                             │
  │     ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐   │
  │     │  head   │←──│ Node-1 │←──│ Node-2 │←──│ tail   │   │
  │     │(哨兵节点)│  →│Thread A│  →│Thread B│  →│(新加入)│   │
  │     └────────┘   └────────┘   └────────┘   └────────┘   │
  │     - 每个 Node 包含：thread（等待线程）、waitStatus     │
  │       （等待状态）、prev/next（前驱/后继指针）             │
  │     - FIFO：先到先得，保证公平性                          │
  │     - 双向链表：支持从中间取消节点（前驱通知后继）         │
  │                                                          │
  │  ③ 独占/共享两种模式                                      │
  │     - 独占模式（EXCLUSIVE）：同一时刻只有一个线程能获取    │
  │     - 共享模式（SHARED）：多个线程可以同时获取            │
  └──────────────────────────────────────────────────────────┘
```

```java
// AQS 核心源码片段（简化）
public abstract class AbstractQueuedSynchronizer {
    
    // 核心：volatile 修饰的同步状态
    private volatile int state;
    
    // CAS 修改 state
    protected final boolean compareAndSetState(int expect, int update) {
        return U.compareAndSwapInt(this, STATE, expect, update);
    }
    
    // 入队操作（抢锁失败后进入队列）
    private Node enq(final Node node) {
        for (;;) {
            Node t = tail;
            if (t == null) {
                if (compareAndSetHead(new Node())) // 初始化哨兵节点
                    tail = head;
            } else {
                node.prev = t;
                if (compareAndSetTail(t, node)) {
                    t.next = node;
                    return t;
                }
            }
        }
    }
    
    // 子类实现的方法（模板方法模式）
    protected boolean tryAcquire(int arg) { throw new UnsupportedOperationException(); }
    protected boolean tryRelease(int arg) { throw new UnsupportedOperationException(); }
    protected int tryAcquireShared(int arg) { throw new UnsupportedOperationException(); }
    protected boolean tryReleaseShared(int arg) { throw new UnsupportedOperationException(); }
}
```

**三、独占模式详解——ReentrantLock + AQS**

```
ReentrantLock 的加锁流程（非公平锁）：

  ┌────────────────────────────────────────────────────────┐
  │  Thread-1 调用 lock.lock()                             │
  │                                                         │
  │  ① 尝试 CAS 将 state 从 0 改为 1                       │
  │     ├─ 成功 → 设置当前线程为独占线程 → 加锁成功 ✅       │
  │     └─ 失败 → 进入 acquire(1)                          │
  │                                                         │
  │  ② acquire(1) 内部调用 tryAcquire(1)                   │
  │     ├─ state == 0 → CAS 抢锁                           │
  │     ├─ state != 0 && 当前线程 == 持有者 → 重入，state++ │
  │     └─ 否则 → 抢锁失败                                  │
  │                                                         │
  │  ③ 抢锁失败 → addWaiter(Node.EXCLUSIVE) 入队          │
  │     └─ 创建 Node，CAS 插入队尾                          │
  │                                                         │
  │  ④ acquireQueued(node, 1) —— 自旋 + 阻塞               │
  │     ┌─ 前驱是 head → 再次尝试抢锁                       │
  │     ├─ 抢锁成功 → 自己变成 head → 返回                  │
  │     └─ 抢锁失败 → shouldParkAfterFailedAcquire          │
  │            → 前驱 waitStatus 设为 SIGNAL               │
  │            → parkAndCheckInterrupt() → LockSupport.park()│
  │            → 线程阻塞，等待唤醒                          │
  └────────────────────────────────────────────────────────┘

  释放锁流程：
  Thread-1 调用 lock.unlock() 
  → tryRelease(1) → state-- 
  → state == 0 → 唤醒 head.next 线程（unparkSuccessor）
  → 被唤醒线程继续自旋抢锁
```

**四、公平锁 vs 非公平锁——源码级区别**

```java
// 非公平锁的 tryAcquire（默认）——直接 CAS 抢锁
final boolean nonfairTryAcquire(int acquires) {
    final Thread current = Thread.currentThread();
    int c = getState();
    if (c == 0) {
        // 直接 CAS 抢！不管队列中有没有等待的线程
        if (compareAndSetState(0, acquires)) {
            setExclusiveOwnerThread(current);
            return true;
        }
    } else if (current == getExclusiveOwnerThread()) {
        int nextc = c + acquires;
        setState(nextc);
        return true;
    }
    return false;
}

// 公平锁的 tryAcquire——先看有没有排队
protected final boolean tryAcquire(int acquires) {
    final Thread current = Thread.currentThread();
    int c = getState();
    if (c == 0) {
        // 关键！先判断队列中是否有等待更久的线程
        if (!hasQueuedPredecessors() &&
            compareAndSetState(0, acquires)) {
            setExclusiveOwnerThread(current);
            return true;
        }
    } else if (current == getExclusiveOwnerThread()) {
        int nextc = c + acquires;
        setState(nextc);
        return true;
    }
    return false;
}

// hasQueuedPredecessors() —— 判断队列是否有前驱
public final boolean hasQueuedPredecessors() {
    Node t = tail;
    Node h = head;
    Node s;
    return h != t && 
           ((s = h.next) == null || s.thread != Thread.currentThread());
    // 队列不为空 && (head.next 为空 或 head.next 不是当前线程)
}
```

```
公平锁 vs 非公平锁的关键差异：

  非公平锁：
  lock() → CAS 抢一次 → 失败 → acquire → tryAcquire（再抢一次）
  → 失败 → 入队
  总共 2 次抢锁机会！新来的线程有机会"插队"

  公平锁：
  lock() → 直接 acquire → tryAcquire（先检查队列没人等再抢）
  → 失败 → 入队
  总共 1 次抢锁机会，且必须排队

  为什么默认非公平？
  ✅ 性能更好：减少线程切换开销
  ✅ 吞吐量更高：新线程可能直接拿到锁，避免唤醒阻塞线程的延迟
  ❌ 可能导致"饥饿"：某些线程可能一直抢不到锁
```

**五、共享模式详解——Semaphore**

```
Semaphore（信号量）基于 AQS 共享模式：

  ┌────────────────────────────────────────────────────────┐
  │  Semaphore(3) —— 允许 3 个线程同时访问                 │
  │                                                         │
  │  Thread-A acquire() → state: 3→2 ✅ 获取成功             │
  │  Thread-B acquire() → state: 2→1 ✅ 获取成功             │
  │  Thread-C acquire() → state: 1→0 ✅ 获取成功             │
  │  Thread-D acquire() → state: 0→? ❌ 入队等待             │
  │                                                         │
  │  Thread-A release() → state: 0→1 → 唤醒 Thread-D        │
  │  Thread-D 被唤醒 → CAS state: 1→0 ✅ 获取成功            │
  └────────────────────────────────────────────────────────┘

  共享模式与独占模式的核心区别：
  ① tryAcquireShared 返回 int（剩余资源数），而非 boolean
  ② 释放锁后会唤醒后续的多个共享节点（传播机制）
  ③ 独占模式：释放后只唤醒 head.next
     共享模式：释放后唤醒 head.next，如果下一个也是共享节点则继续传播
```

**六、CompletableFuture——从 Future 到异步编排**

传统的 Future 有三大硬伤：① 阻塞获取结果（get() 阻塞）；② 无法链式编排；③ 不支持异常处理和回调。

```java
// ❌ 传统 Future 的痛点
public UserProfile getUserProfile(Long userId) {
    ExecutorService executor = Executors.newFixedThreadPool(5);
    
    Future<User> userFuture = executor.submit(() -> userService.get(userId));
    Future<List<Order>> ordersFuture = executor.submit(() -> orderService.getOrders(userId));
    Future<List<Coupon>> couponFuture = executor.submit(() -> couponService.getCoupons(userId));
    
    try {
        User user = userFuture.get();       // 🔴 阻塞等待！
        List<Order> orders = ordersFuture.get();  // 🔴 阻塞等待！
        List<Coupon> coupons = couponFuture.get(); // 🔴 阻塞等待！
        return new UserProfile(user, orders, coupons);
    } catch (Exception e) {
        throw new RuntimeException(e);      // 🔴 异常处理丑陋
    }
}

// ✅ CompletableFuture 优雅编排
public CompletableFuture<UserProfile> getUserProfile(Long userId) {
    CompletableFuture<User> userFuture = 
        CompletableFuture.supplyAsync(() -> userService.get(userId));
    
    CompletableFuture<List<Order>> ordersFuture = 
        CompletableFuture.supplyAsync(() -> orderService.getOrders(userId));
    
    CompletableFuture<List<Coupon>> couponFuture = 
        CompletableFuture.supplyAsync(() -> couponService.getCoupons(userId));
    
    // 三个异步任务并行执行，全部完成后组合结果
    return CompletableFuture.allOf(userFuture, ordersFuture, couponFuture)
        .thenApply(v -> {
            User user = userFuture.join();        // 非阻塞（因为 allOf 保证已完成）
            List<Order> orders = ordersFuture.join();
            List<Coupon> coupons = couponFuture.join();
            return new UserProfile(user, orders, coupons);
        })
        .exceptionally(e -> {
            log.error("获取用户主页失败", e);
            return UserProfile.empty();           // 优雅降级
        });
}
```

```
CompletableFuture 四大核心能力：

  ① 任务创建：
     - supplyAsync(Supplier) → 有返回值
     - runAsync(Runnable) → 无返回值
     - 默认用 ForkJoinPool.commonPool()，可传入自定义线程池

  ② 链式转换：
     - thenApply(Function) → 转换结果（同步）
     - thenApplyAsync(Function) → 转换结果（异步）
     - thenCompose(Function) → 扁平化（避免 Future<Future<T>> 嵌套）

  ③ 任务组合：
     - thenCombine(otherFuture, BiFunction) → 两个任务结果合并
     - allOf(futures...) → 等待全部完成
     - anyOf(futures...) → 任意一个完成

  ④ 异常处理：
     - exceptionally(Function) → 捕获异常，返回默认值
     - handle(BiFunction) → 无论成功失败都处理（类似 finally）
     - whenComplete(BiConsumer) → 完成后的回调

  CompletableFuture 状态流转：
  ┌─────────┐    ┌──────────┐    ┌──────────┐    ┌────────────┐
  │ NEW     │───→│ RUNNING  │───→│ NORMAL   │ 或 │ EXCEPTIONAL│
  │ (刚创建) │    │ (执行中)  │    │ (正常完成)│    │ (异常完成)  │
  └─────────┘    └──────────┘    └──────────┘    └────────────┘
```

### 💡 延伸思考

1. **CompletableFuture 的自定义线程池怎么选？** — 默认使用 ForkJoinPool.commonPool()（CPU 核心数 - 1 个线程），这在 I/O 密集型场景下严重不足。最佳实践：I/O 密集型任务用自定义线程池（核心线程数 = CPU 核数 × 2），CPU 密集型任务用默认池。务必在 supplyAsync 的第二个参数传入自定义线程池。
2. **synchronized 和 ReentrantLock 怎么选？** — JDK 6 之后，synchronized 经过大量优化（偏向锁、轻量级锁、锁粗化），性能与 ReentrantLock 不相上下。选 ReentrantLock 的理由：① 需要公平锁；② 需要可中断的锁获取（lockInterruptibly）；③ 需要尝试获取锁（tryLock）；④ 需要 Condition 实现精确唤醒（synchronized 只能 notify/notifyAll）。

**二、BaseMapper 通用 CRUD——"零 SQL"的秘密**

```java
    // 自定义 SQL 可以在这里加，BaseMapper 已提供 17 个通用方法
```

```
BaseMapper 提供的 17 个通用方法：

  增：insert(T entity)
```

**三、分页插件——拦截器链改写 SQL**

```java
// 分页插件配置
@Configuration
public class MybatisPlusConfig {
    
    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        
        // ① 分页插件（必须指定数据库类型）
        PaginationInnerInterceptor paginationInterceptor = 
            new PaginationInnerInterceptor(DbType.MYSQL);
        
        // 配置分页合理化：pageNum < 1 → 查第一页；pageNum > pages → 查最后一页
        paginationInterceptor.setOverflow(true);
        
        // 单页最大 500 条限制（防止恶意请求拖垮数据库）
        paginationInterceptor.setMaxLimit(500L);
        
        interceptor.addInnerInterceptor(paginationInterceptor);
        
        // ② 乐观锁插件
        interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor());
        
        return interceptor;
    }
}
```

```
分页插件的 SQL 改写原理（以 MySQL 为例）：

  原始 SQL：
  SELECT id, user_name, age FROM user WHERE age > 18 ORDER BY create_time DESC

  插件拦截后改写为两条 SQL：

  ① COUNT 查询（计算总记录数）：
  SELECT COUNT(*) FROM user WHERE age > 18

  ② LIMIT 查询（分页数据）：
  SELECT id, user_name, age FROM user 
  WHERE age > 18 
  ORDER BY create_time DESC 
  LIMIT 0, 10  ← 插件自动添加！

  拦截链路：
  Executor.query() → MybatisPlusInterceptor 拦截器链
  → PaginationInnerInterceptor 检测到分页参数（IPage）
  → 生成 COUNT SQL → 执行 → 得到 total
  → 改写原 SQL 添加 LIMIT → 执行 → 得到 records
  → 封装为 Page 对象返回
```

```java
// 使用分页
@Service
public class UserService {
    
    public IPage<User> queryByPage(int pageNum, int pageSize, String keyword) {
        Page<User> page = new Page<>(pageNum, pageSize);
        
        LambdaQueryWrapper<User> wrapper = new LambdaQueryWrapper<>();
        wrapper.like(StringUtils.hasText(keyword), User::getUserName, keyword)
               .ge(User::getAge, 18)
               .orderByDesc(User::getCreateTime);
        
        // 分页查询
        IPage<User> result = userMapper.selectPage(page, wrapper);
        
        // 返回结果：
        // result.getTotal() → 总记录数
        // result.getRecords() → 当前页数据
        // result.getPages() → 总页数
        // result.getCurrent() → 当前页码
        return result;
    }
}
```

**四、乐观锁插件——@Version 注解的原理**

```java
// 实体类添加 @Version
@Data
public class Product {
    private Long id;
    private String name;
    private Integer stock;
    
    @Version
    private Integer version;  // 版本号字段
}

// 更新操作
@Service
public class ProductService {
    
    public boolean reduceStock(Long productId, int quantity) {
        // ① 先查询（获取当前版本号）
        Product product = productMapper.selectById(productId);
        if (product.getStock() < quantity) {
            return false;
        }
        
        // ② 扣减库存（不手动改 version！）
        product.setStock(product.getStock() - quantity);
        
        // ③ 更新（MyBatis-Plus 自动处理 version）
        int rows = productMapper.updateById(product);
        return rows > 0;  // rows=0 → 版本号冲突 → 更新失败
    }
}
```

```
乐观锁插件的 SQL 改写：

  原始 updateById：
  UPDATE product SET name=?, stock=?, version=? WHERE id=?

  插件拦截后改写为：
  UPDATE product 
  SET name=?, stock=?, version = version + 1
  WHERE id=? AND version = ?  ← 关键！WHERE 条件加上版本号校验

  如果 version 不一致 → WHERE 条件不匹配 → affected rows = 0
  → 说明数据被其他线程修改过 → 业务层重试或提示用户

  完整流程：
  ① 查询 → version = 3
  ② 线程A更新 → SET version = 4 WHERE version = 3 → 成功
  ③ 线程B查询到 version = 3（已过期）→ 更新 → WHERE version = 3 → 失败
  ④ 线程B重试：重新查询 version = 4 → 再次更新 → 成功
```

1. **MyBatis-Plus 的分页插件在大数据量场景下会有什么问题？** — COUNT 查询在千万级表中可能极慢（需要全表扫描）。解决方案：① 关闭 COUNT（page.setSearchCount(false)）；② 用 EXPLAIN 的预估行数代替精确 COUNT；③ 使用 Redis 维护计数；④ 大数据量下的分页用"游标分页"替代传统页码分页。

```
✅ 完整回答框架（逐层展开）：

第一层：快速止血（先止损再排查）

  "发现 CPU 飙升后，第一反应不是排查而是止血：

第二层：定位分析（从表象到根因）
```

```
  │ ③ 语义去重：                                             │
  │    多个文档内容高度重叠 → 去重后只保留最权威的版本         │
  └─────────────────────────────────────────────────────────┘

  第二层：生成侧约束（解决"怎么用"的问题）
  ┌─────────────────────────────────────────────────────────┐
  │ 问题：即使检索到的文档是正确的，LLM 也可能过度推断或曲解   │
  │                                                         │
  │ 优化策略：                                               │
  │ ① System Prompt 约束（最关键！）：                        │
  │    "你只能根据以下文档回答问题。如果文档中没有相关信息，   │
  │     请明确表示'无法回答'，不要编造任何内容。"             │
  │                                                         │
  │ ② 引用增强生成（Citation-Augmented Generation）：        │
  │    Prompt 中要求每个关键陈述必须标注引用来源：             │
  │    "根据文档[1]第 3 段，..."                              │
  │    这样用户可以追溯每句话的来源                           │
  │                                                         │
  │ ③ 拒绝回答机制：                                         │
  │    "如果检索到的文档与用户问题不相关，直接回答'抱歉，      │
  │     当前知识库中没有相关信息'"                           │
  │    避免 LLM 在找不到相关信息时"脑补"                     │
  └─────────────────────────────────────────────────────────┘

  第三层：后处理校验（解决"最后一道防线"的问题）
  ┌─────────────────────────────────────────────────────────┐
  │ 问题：即使前两层都做对了，LLM 仍然可能"撒谎"               │
  │                                                         │
  │ 优化策略：                                               │
  │ ① 引用校验（Citation Verification）：                    │
  │    用规则或小模型检查回答中的引用是否真的存在于文档中      │
  │    例："根据文档[3]..." → 校验文档[3]中是否有这句内容     │
  │                                                         │
  │ ② NLI（自然语言推理）校验：                              │
  │    用一个校验模型判断"生成回答"与"检索文档"是否一致       │
  │    如果矛盾 → 标记为幻觉 → 返回"无法确认"或重新生成      │
  │                                                         │
  │ ③ 人工反馈闭环：                                         │
  │    用户点"踩" → 记录该问答对 → 定期人工审核               │
  │    → 发现幻觉模式 → 优化 Prompt 或检索策略               │
  └─────────────────────────────────────────────────────────┘
```

### 💡 延伸思考

1. **微调（Fine-tuning）能解决幻觉吗？** — 微调可以改善特定格式的幻觉（如让模型学会只引用文档内容），但无法解决根本的"知识缺失"导致的事实性幻觉。微调相当于给模型"补课"，但知识是无限的，微调成本高。RAG + 幻觉治理的策略更灵活、可更新、可追溯。最佳实践：RAG 解决知识幻觉 + 微调优化输出格式和领域表达。

2. **大模型评测（Evaluation）和幻觉治理的关系？** — 没有好的评测，就无法量化幻觉治理的效果。工业界常用的 RAG 评测指标包括：Faithfulness（忠实度）、Answer Relevance（回答相关性）、Context Recall/Precision（上下文召回/精确度）。面试中如果主动提到"我们上线了自动评测 Pipeline"，会大幅加分。

**一、ReAct 是什么？——Agent 的"大脑"**

ReAct（Reasoning + Acting）是当前工业界最主流的 AI Agent 执行框架，核心是一个三步循环：**Thought（思考）→ Action（行动）→ Observation（观察）**，直到任务完成。

```
ReAct 的完整工作流程：

  用户：明天北京天气怎么样？帮我查一下我的待办事项。

  ┌────────────────────────────────────────────────────────┐
  │                    ReAct 循环                           │
  │                                                         │
  │  Round 1：                                              │
  │  💭 Thought: 用户问了两件事。先查天气，需要调用天气工具    │
  │  🔧 Action: get_weather(city="北京", date="明天")        │
  │  👁️ Observation: {"city":"北京","weather":"中雨","temp":"14-20°C"}
  │                                                         │
  │  Round 2：                                              │
  │  💭 Thought: 天气查到了，中雨。还需要查用户的待办事项      │
  │  🔧 Action: get_todos(user_id="current")                │
  │  👁️ Observation: [{"task":"9:00 开会","status":"未完成"},...]
  │                                                         │
  │  Round 3：                                              │
  │  💭 Thought: 两个信息都拿到了，可以给用户完整回答          │
  │  🔧 Action: FINISH                                      │
  │  📝 Final Answer:                                       │
  │    "明天北京有中雨，气温 14-20°C，建议带伞☔。            │
  │     您的待办事项：① 9:00 开会（未完成）② …"             │
  └────────────────────────────────────────────────────────┘

  ReAct = Reasoning（推理：想清楚做什么）+ Acting（执行：调用工具获取反馈）
```

**二、为什么不能"直接让 LLM 输出 Tool Call JSON"？——字节面试核心追问**

这是 2026 年字节跳动 ReAct 面试题中最高频的追问点：**"如果直接去掉 Thought，让 LLM 一次性输出结构化工具调用 JSON，不仅响应更快、还能节省大量 Token 开销，这种极简方案为什么没法落地？"**

```
直接输出 Tool Call vs ReAct 的差异：

  方案 A（直接 Tool Call）：
  Q: "明天北京天气怎么样？帮我查待办"
  A: {"tool_calls": ["get_weather(...)", "get_todos(...)"]}
  
  这种方案看起来更快，但实际存在致命问题：

  致命缺陷 1：无法处理条件依赖
  "先查我的信用卡额度，如果大于 5000，就帮我订明天去上海的机票"
  
  直接 Tool Call：
  {"tool_calls": ["get_credit_limit()", "book_flight(...)"]}
  → 还没查额度就订机票了！因为无法条件判断！

  ReAct：
  Round 1: Thought "先查额度" → Action: get_credit_limit()
  Round 2: Thought "额度 8000，大于 5000，可以订票" → Action: book_flight(...)
  ✅ ReAct 通过"思考-观察-再思考"实现了条件分支决策

  致命缺陷 2：无法处理异常和修正
  直接 Tool Call：调了天气 API → 返回 ERROR → 不知道怎么办
  ReAct：调了天气 API → Observation: ERROR "服务超时"
       → Thought: "天气服务挂了，我问用户城市名，手动查备用的吧"
       → 可以自主选择替代方案

  致命缺陷 3：无法动态调整工具参数
  直接 Tool Call：调用 search_database(query="最新订单")
  → 返回了 1000 条结果 → 无能为力

  ReAct：
  Round 1: 查询 → 返回 1000 条 → Thought: "太多了，需要加过滤条件"
  Round 2: 用更精确的条件再查 → 返回 5 条 → 完成
```

```
核心结论（面试金句）：

  "ReAct 和直接 Tool Call 的根本差异不是'多了一步思考'，
   而是有没有给 LLM 观察结果后重新决策的机会。

   直接 Tool Call 是'一次性决策'——一次性决定所有工具调用，无法应对变化。
   ReAct 是'循环决策'——每走一步都观察结果，根据反馈调整下一步。

   这对应到人类解决问题的模式：
   一次性决策：把所有问题列出来，一次性给出所有答案（没人这么做！）
   循环决策：做一步 → 看看结果 → 决定下一步 → 直到完成（这才是正常思维）
   
  多出来的 Token 开销，换来的是任务的正确完成率。这才是工程上的正确取舍。"
```

**三、ReAct vs Function Calling vs 传统 Workflow**

```
三种范式的核心区别：

  ┌────────────────┬──────────────────┬──────────────────┬──────────────────┐
  │      维度       │  Function Calling │     ReAct        │  传统 Workflow   │
  ├────────────────┼──────────────────┼──────────────────┼──────────────────┤
  │ 决策方式        │ LLM 决定调哪个工具 │ LLM 循环推理+行动  │ 预先定义的流程    │
  │ 灵活性          │ 中等              │ 高               │ 低（固定步骤）    │
  │ 多步骤任务      │ 需手动编排        │ 自动拆解+执行     │ 手动编排         │
  │ 异常处理        │ 依赖应用层        │ 自主修正          │ 预定义异常处理    │
  │ Token 消耗      │ 低                │ 中高              │ 无 LLM 消耗      │
  │ 适用场景        │ 简单工具调用       │ 复杂多步任务      │ 标准化流程        │
  │ 正确率          │ 单一任务高         │ 复杂任务高        │ 最高（无 LLM）   │
  └────────────────┴──────────────────┴──────────────────┴──────────────────┘

  选型建议：
  - 简单查询、单步工具调用 → Function Calling（更经济）
  - 多步推理、条件分支、需要动态决策 → ReAct（更可靠）
  - 步骤固定、不需要 LLM 决策 → 传统 Workflow（最稳定）
```

**四、Java 代码实战——Spring AI / LangChain4j 实现 ReAct Agent**

### LangChain4j 方式（最成熟）

```java
// ① 定义工具
public class WeatherTools {
    
    @Tool("查询指定城市的天气信息")
    public String getWeather(
        @P("城市名称，如北京") String city,
        @P("日期，如明天") String date) {
        // 实际调用天气 API
        return weatherService.query(city, date);
    }
}

public class TodoTools {
    
    @Tool("获取当前用户的待办事项列表")
    public String getTodos(@P("用户ID") String userId) {
        return todoService.getTodos(userId);
    }
}

// ② 创建 ReAct Agent
@Service
public class ReActAgentService {
    
    private final Assistant assistant;
    
    public ReActAgentService(ChatLanguageModel model) {
        // 注册工具
        List<Object> tools = Arrays.asList(
            new WeatherTools(),
            new TodoTools()
        );
        
        // 创建 ReAct Agent
        this.assistant = AiServices.builder(Assistant.class)
            .chatLanguageModel(model)
            .tools(tools)
            .chatMemory(MessageWindowChatMemory.withMaxMessages(10))
            .build();
    }
    
    public String process(String userMessage) {
        return assistant.chat(userMessage);
    }
}

// ③ Agent 接口
public interface Assistant {
    String chat(String userMessage);
}
```

```java
public class AgentController {
```

**五、2026 面试高频追问——吃透 ReAct 的核心边界**

```
追问 1：Thought-Action-Observation 的边界问题

  Q: "什么时候该继续思考？什么时候该结束循环？"
  A: "两个终止条件：
      ① LLM 判断任务已完成 → 生成 Final Answer（不再调用工具）
      ② 达到最大循环次数（如 10 轮）→ 强制终止，返回当前最佳结果
      工业界还加入了'反思门'：如果连续两轮的 Observation 相似或为空，
      说明陷入了死循环，主动触发终止。"

追问 2：Action 失败怎么处理？

  Q: "如果 get_weather 返回 timeout 怎么办？"
  A: "Observation 不是总是成功的。框架层面需要做三层处理：
      ① 工具调用层面：重试机制（最多 3 次，指数退避）
      ② ReAct 循环层面：Observation 返回 ERROR → LLM 重新 Thought，
        决定是换工具、换参数还是告知用户
      ③ 降级机制：工具彻底不可用 → LLM 告诉用户'抱歉，天气服务暂时不可用'"

追问 3：不同场景的 Agent 推理模式怎么选？

  Q: "除了 ReAct，你还知道哪些 Agent 推理模式？"
  A: "① Plan-and-Execute（先规划再执行）→ 适合步骤可预见的任务
      ② Reflexion（反思模式）→ 任务完成后再检查一次结果质量
      ③ ReWOO（Reason Without Observation）→ 提前规划全部工具调用，减少 LLM 轮次
      ④ Tree-of-Thought（思维树）→ 多路径并行探索，适合创造性任务
      ⑤ ReAct → 最通用，90% 场景够用
      
      选型关键：看任务的'不确定性'程度。
      越不确定（需要边做边看）→ 越适合 ReAct；
      越确定（步骤清晰）→ 越适合 Plan-and-Execute"
```

### 💡 延伸思考

1. **ReAct Agent 的最大实践坑是什么？** — Token 消耗失控。因为每轮 Thought 都要携带完整的对话历史 + 工具调用结果，随着轮次增加，Prompt 越来越长。一个复杂的 10 轮 Agent 任务可能消耗数万 Token。解决方案：① 对话摘要（Summarize Memory）——定期压缩历史对话；② 上下文窗口管理——只保留最近 N 轮；③ 任务分解——大任务拆成多个小 Agent，减少单 Agent 的轮次。

2. **MCP 协议和 ReAct 的关系？** — MCP 负责"工具怎么标准化接入"，ReAct 负责"用什么策略调用这些工具"。两者是互补关系：MCP 提供统一的工具发现和调用协议，ReAct 提供智能的工具选择和调用策略。2026 年的趋势是：MCP Server 提供工具池 → ReAct Agent 智能调度工具 → 完成复杂任务。
