## 题目 1：[框架/Spring] 请详细阐述 Spring Boot Starter 的设计思想，并手写一个企业级自定义 Starter（含自动配置、条件注解、配置属性绑定）

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-28 早间&午间报告 — "Spring Boot 4.x Starter 设计思想成为2026面试高频考点" + "手写企业级 Starter 是分水岭级面试题"
**相关岗位**：Java后端 / 基础架构 / 全栈

### 📖 参考答案

#### 一、Starter 的本质是什么？

Starter 不是"一个 jar 包"，而是 **Spring Boot 的集成标准化协议**。它解决了 Spring 时代最痛苦的问题——配置地狱。

```
Spring 时代（无 Starter）：
  pom.xml 引入 5-8 个依赖（版本号手动管理）
  XML 配置 30-50 行（数据源、事务、AOP...）
  不同项目重复劳动，版本冲突频发

Spring Boot Starter 时代：
  一行依赖：spring-boot-starter-data-redis
  零配置即可使用（自动配置兜底）
  按需覆盖（application.yml 覆盖默认值）
```

**Starter = 依赖坐标 + 自动配置 + 配置属性绑定** 三位一体。

#### 二、Starter 的命名约定

| 类型 | 命名规则 | 示例 |
|------|---------|------|
| **官方 Starter** | `spring-boot-starter-{module}` | `spring-boot-starter-web` |
| **第三方 Starter** | `{module}-spring-boot-starter` | `mybatis-spring-boot-starter` |
| **自定义 Starter** | `{project}-spring-boot-starter` | `sms-spring-boot-starter` |

#### 三、自动配置的核心机制

**入口：@SpringBootApplication → @EnableAutoConfiguration**

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Inherited
@AutoConfigurationPackage
@Import(AutoConfigurationImportSelector.class)  // ← 核心！
public @interface EnableAutoConfiguration {
    String ENABLED_OVERRIDE_PROPERTY = "spring.boot.enableautoconfiguration";
    Class<?>[] exclude() default {};
    String[] excludeName() default {};
}
```

**AutoConfigurationImportSelector 的工作流程**：

```
① 扫描 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
② 读取所有自动配置类的全限定名
③ 按 @Order / @AutoConfigureOrder / @AutoConfigureBefore / @AutoConfigureAfter 排序
④ 逐一检查 @Conditional 条件注解
⑤ 条件满足 → 创建 Bean；条件不满足 → 跳过
```

**条件注解体系**（面试必问）：

| 注解 | 含义 | 典型场景 |
|------|------|---------|
| `@ConditionalOnClass` | 类路径存在指定类才生效 | 引入某个依赖后才加载配置 |
| `@ConditionalOnMissingBean` | 容器中没有指定 Bean 才创建 | 允许用户自定义覆盖 |
| `@ConditionalOnProperty` | 配置项满足条件才生效 | 通过开关启用/禁用功能 |
| `@ConditionalOnBean` | 容器中有指定 Bean 才生效 | 依赖其他组件时使用 |
| `@ConditionalOnWebApplication` | Web 环境下才生效 | Web 相关自动配置 |
| `@ConditionalOnExpression` | SpEL 表达式为 true 才生效 | 复杂条件组合 |

#### 四、手写企业级自定义 Starter（短信发送）

**项目结构**：

```
sms-spring-boot-starter/
├── sms-spring-boot-autoconfigure/    # 自动配置模块
│   ├── src/main/java/com/example/sms/
│   │   ├── autoconfigure/
│   │   │   ├── SmsProperties.java        # 配置属性类
│   │   │   ├── SmsAutoConfiguration.java  # 自动配置类
│   │   │   └── SmsHealthIndicator.java   # 健康检查
│   │   └── SmsTemplate.java              # 核心业务类
│   └── src/main/resources/META-INF/spring/
│       └── org.springframework.boot.autoconfigure.AutoConfiguration.imports
└── sms-spring-boot-starter/          # Starter 聚合模块（空 jar，仅 pom）
    └── pom.xml
```

**Step 1：配置属性类**

```java
@ConfigurationProperties(prefix = "sms")  // 绑定 sms.* 配置
public class SmsProperties {
    
    /** 供应商：aliyun / tencent / huawei */
    private String provider = "aliyun";
    
    /** Access Key */
    private String accessKey;
    
    /** Secret Key */
    private String secretKey;
    
    /** 签名名称 */
    private String signName = "默认签名";
    
    /** 连接超时（毫秒） */
    private int connectTimeout = 5000;
    
    /** 读取超时（毫秒） */
    private int readTimeout = 10000;
    
    // getters & setters ...
}
```

**Step 2：核心业务类**

```java
public class SmsTemplate {
    
    private final SmsProperties properties;
    private final SmsClient client;  // 具体短信供应商客户端
    
    public SmsTemplate(SmsProperties properties) {
        this.properties = properties;
        this.client = SmsClientFactory.create(properties);
    }
    
    /**
     * 发送短信
     * @param phone 手机号
     * @param templateCode 模板编码
     * @param params 模板参数
     * @return 发送结果
     */
    public SmsResult send(String phone, String templateCode, Map<String, String> params) {
        // 参数校验
        Assert.hasText(phone, "手机号不能为空");
        Assert.hasText(templateCode, "模板编码不能为空");
        
        // 调用供应商 SDK
        try {
            SendSmsResponse response = client.sendSms(
                new SendSmsRequest()
                    .setPhoneNumbers(phone)
                    .setSignName(properties.getSignName())
                    .setTemplateCode(templateCode)
                    .setTemplateParam(JSON.toJSONString(params))
            );
            
            return SmsResult.success(response.getBizId());
        } catch (Exception e) {
            log.error("短信发送失败，phone={}, template={}", phone, templateCode, e);
            return SmsResult.fail(e.getMessage());
        }
    }
    
    /**
     * 批量发送
     */
    public List<SmsResult> batchSend(List<String> phones, String templateCode, 
                                      Map<String, String> params) {
        return phones.parallelStream()
            .map(phone -> send(phone, templateCode, params))
            .collect(Collectors.toList());
    }
}
```

**Step 3：自动配置类**

```java
@AutoConfiguration  // Spring Boot 4.x 推荐使用 @AutoConfiguration 替代 @Configuration
@EnableConfigurationProperties(SmsProperties.class)
@ConditionalOnClass(SmsClient.class)  // 类路径有 SmsClient 才生效
public class SmsAutoConfiguration {
    
    @Bean
    @ConditionalOnMissingBean  // 用户未自定义 SmsTemplate 时才创建
    public SmsTemplate smsTemplate(SmsProperties properties) {
        return new SmsTemplate(properties);
    }
    
    @Bean
    @ConditionalOnProperty(prefix = "sms", name = "health-enabled", 
                           havingValue = "true", matchIfMissing = true)
    public SmsHealthIndicator smsHealthIndicator(SmsTemplate smsTemplate) {
        return new SmsHealthIndicator(smsTemplate);
    }
}
```

**Step 4：注册自动配置类**

```
# META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.example.sms.autoconfigure.SmsAutoConfiguration
```

**Step 5：Starter 模块的 pom.xml**

```xml
<!-- sms-spring-boot-starter/pom.xml -->
<project>
    <artifactId>sms-spring-boot-starter</artifactId>
    
    <dependencies>
        <!-- 仅依赖 autoconfigure 模块 -->
        <dependency>
            <groupId>com.example</groupId>
            <artifactId>sms-spring-boot-autoconfigure</artifactId>
        </dependency>
    </dependencies>
</project>
```

#### 五、Spring Boot 4.x 对 Starter 体系的重构

| 变化 | Spring Boot 3.x | Spring Boot 4.x |
|------|----------------|----------------|
| **自动配置注解** | `@Configuration` | `@AutoConfiguration`（新注解） |
| **注册文件路径** | `spring.factories` | `AutoConfiguration.imports`（推荐） |
| **条件注解** | 基础条件注解 | 新增 `@ConditionalOnVirtualThread` 等 |
| **Jakarta EE** | Jakarta EE 9+ | Jakarta EE 11（Servlet 6.1） |
| **最低 JDK** | JDK 17 | JDK 25 |

**参考来源**：
- https://luoyong.blog.csdn.net/article/details/162209431 — Spring Boot Starter 设计思想深度解析
- https://cloud.tencent.com/developer/article/2666029 — Spring Boot 4.x 自动配置机制

## 题目 2：[面试技巧/综合] 2026 年大厂面试已进入"反八股"时代，请详细说明如何用 STAR 结构准备项目深度面，并给出一个完整的技术故事模板

**难度**：⭐⭐⭐
**考点来源**：2026-06-28 早间&午间报告 — "字节阿里美团全面转向项目实战考核，背题时代结束" + "项目深度面成为分水岭"
**相关岗位**：Java后端 / Python后端 / 全栈 / 所有技术岗

### 📖 参考答案

#### 一、为什么八股文失效了？

```
2024-2025：面试问"HashMap put 流程" → 候选人背答案
2026：面试问"你写过最爽的代码片段，讲讲设计思路" → 候选人懵了

核心原因：
  ① AI 平权：大模型能输出完美八股答案，面试官无法区分"真懂"和"背的"
  ② 行业期望变了：面试官要的不是"知道很多"，而是"能解决未知问题"
  ③ 业务复杂度：后端系统接大模型 API、做 RAG、处理不确定输出，没有八股可背
```

**字节某组真实开场白**："我们不问八股，你就挑一个你写得最爽的代码片段，给我讲讲怎么设计的。"

**阿里二面真实场景**：扔一个 GitHub 线上 bug，限时 10 分钟分析。

**美团新增环节**：HR 面之前加一轮"项目深度面"，专门问上线情况、难点和解决方案。

#### 二、STAR 结构：技术故事的"四节点"框架

```
S - Situation（场景）
  │  什么时间？什么系统？什么业务？
  ▼
T - Task（任务）
  │  要解决什么问题？目标是什么？
  ▼
A - Action（行动）
  │  怎么排查的？几个方案？为什么选这个？
  ▼
R - Result（结果）
  │  效果如何？数据说话！
```

#### 三、完整技术故事模板

**题目**：讲一个你印象最深的线上故障排查经历

**❌ 错误示范（背题型）**：
> "有一次登录功能报 500 错误，后来发现是数据库连接池满了，改大就好了。"

问题：只有结论，没有过程。面试官无法判断你的排查能力。

**✅ 正确示范（STAR 结构）**：

```
场景（Situation）：
  "今年 3 月，我们订单系统的 P99 延迟突然从 50ms 飙升到 3 秒，
  线上告警群炸了，用户反馈下单失败。"

任务（Task）：
  "需要在 30 分钟内定位根因并给出修复方案，恢复线上服务。"

行动（Action）—— 完整排查链路：
  "第一步，我先用 top 看进程资源，发现 CPU 正常但 IO wait 偏高。
   
   第二步，用 Arthas 的 trace 命令逐层追踪调用链，
   发现热点在一个数据库聚合查询上，占总耗时的 85%。
   
   第三步，用 explain 分析 SQL，发现查询条件里有 LIKE '%keyword%'
   的前缀通配符，导致索引失效、全表扫描了 300 万行数据。
   
   第四步，我权衡了两个方案：
     A. 引入 Elasticsearch（成本高，周期长）
     B. 改造查询逻辑为后缀匹配 + Redis 缓存（成本低，见效快）
   最终选择方案 B，因为紧急线上问题需要快速止血。"

结果（Result）：
  "上线后 P99 延迟降到 200ms 以内，QPS 恢复稳定。
  后续我加了一个慢查询监控告警，防止类似问题再次发生。
  这次排查让我深刻理解了 MySQL 索引失效的几种典型场景。"
```

#### 四、准备 3 个技术故事

每个候选人至少准备 3 个故事，覆盖不同场景：

| 故事类型 | 示例 | 考察点 |
|---------|------|--------|
| **印象最深的 Bug** | 线上死锁 / OOM / 数据不一致 | 排查能力、工具使用 |
| **性能优化** | 接口从 2s 优化到 50ms | 分析能力、方案权衡 |
| **技术选型** | 为什么用 Redis 而不用 Memcached | 技术判断力、工程思维 |

#### 五、项目深度面的典型追问链

面试官会沿着一个项目追问 4-5 轮：

```
Q1: "你这个项目上线了吗？多少用户？"
    → 验证项目真实性

Q2: "上线后遇到过什么真实问题？"
    → 验证是否真的在维护

Q3: "你怎么发现的？用什么工具排查的？"
    → 验证排查能力

Q4: "你当时有几个方案？为什么选了这个？"
    → 验证工程判断力

Q5: "如果让你重做，你会改哪里？"
    → 验证复盘和反思能力
```

**每个问题都要能接住**，否则会被判定为"跟网课做的项目"。

#### 一、GLM-5.2 开源的意义

**MIT 协议的影响**：

| 维度 | 闭源模型 | GLM-5.2（MIT 开源） |

| **成本** | 按 Token 付费 | 一次性硬件成本 |
| **商业集成** | 需遵守服务商条款 | 可嵌入商业产品 |

#### 二、AI 重写后端开发工具链的三大趋势

**趋势 1：AI 代码生成 → AI 代码维护**

```
2024-2025：AI 辅助写代码（Copilot / Cursor）
  写 CRUD、生成单元测试、补全代码块

2026：AI 自主维护代码（SWE-agent / Devin）
  读 Issue → 定位 Bug → 生成修复 → 提 PR
  GLM-5.2 62.1% 的 SWE-bench 得分证明了这一点
```

**趋势 2：传统 CI/CD → AI Agent 驱动的开发流水线**

```
传统流程：
  开发者写代码 → 手动 Code Review → CI 跑测试 → 手动部署

AI Agent 驱动的流程：
  Issue 创建 → Agent 分析代码库 → Agent 生成修复代码
  → AI Code Review → 自动跑测试 → 人工确认 → 自动部署
```

**趋势 3：后端开发者的角色转变**

```
旧角色：写 SQL、写接口、写业务逻辑（CRUD 工程师）
新角色：设计 AI Agent 工作流、编写工具定义、调试 Agent 行为
        定义数据流和权限边界、评估 AI 输出质量
```

## 题目 4：[职业发展/AI] 2026 年程序员薪资洗牌：大模型开发月薪 35k 起，传统后端仅 30k。请分析 AI 赛道的薪资结构、转型路径及后端开发者如何抓住这波红利

**考点来源**：2026-06-28 早间&午间报告 — "2026程序员薪资大洗牌：AI > 后端 > 前端 > 测试" + "75%+ 大模型从业者从传统岗位转型"

### 📖 参考答案

#### 一、2026 年薪资分层


```python
# Python 版本（可维护、可测试、可扩展）
#!/usr/bin/env python3
"""日志归档脚本"""
import gzip
import shutil
from datetime import datetime, timedelta
from pathlib import Path
import httpx
import structlog

logger = structlog.get_logger()

class LogArchiver:
    """日志归档器"""
    
    def __init__(self, log_dir: str, archive_dir: str, retention_days: int = 30):
        self.log_dir = Path(log_dir)
        self.archive_dir = Path(archive_dir)
        self.retention_days = retention_days
        
    def archive_old_logs(self) -> int:
        """归档过期日志文件"""
        archive_count = 0
        cutoff_date = datetime.now() - timedelta(days=self.retention_days)
        
        # 遍历日志文件
        for log_file in self.log_dir.glob("*.log"):
            if datetime.fromtimestamp(log_file.stat().st_mtime) < cutoff_date:
                self._compress_and_move(log_file)
                archive_count += 1
                
        self._cleanup_empty_dirs()
        return archive_count
    
    def _compress_and_move(self, file_path: Path) -> None:
        """压缩并移动单个文件"""
        # 创建目标目录（按日期分层）
        date_str = datetime.now().strftime("%Y/%m")
        target_dir = self.archive_dir / date_str
        target_dir.mkdir(parents=True, exist_ok=True)
        
        # gzip 压缩
        gz_path = target_dir / f"{file_path.name}.gz"
        with open(file_path, 'rb') as f_in:
            with gzip.open(gz_path, 'wb') as f_out:
                shutil.copyfileobj(f_in, f_out)
        
        # 删除原文件
        file_path.unlink()
        logger.info("归档完成", file=str(file_path), target=str(gz_path))
    
    def _cleanup_empty_dirs(self) -> None:
        """清理空目录"""
        for dir_path in sorted(self.log_dir.rglob("*"), reverse=True):
            if dir_path.is_dir() and not any(dir_path.iterdir()):
                dir_path.rmdir()
    
    def send_notification(self, message: str) -> bool:
        """发送通知"""
        try:
            with httpx.Client() as client:
                resp = client.post(
                    "http://alert.example.com/notify",
                    json={"message": message}
                )
                resp.raise_for_status()
                return True
        except Exception as e:
            logger.error("通知发送失败", error=str(e))
            return False


if __name__ == "__main__":
    archiver = LogArchiver(
        log_dir="/var/log/myapp",
        archive_dir="/data/archive",
        retention_days=30
    )
    count = archiver.archive_old_logs()
    archiver.send_notification(f"日志归档完成，共处理 {count} 个文件")
```
