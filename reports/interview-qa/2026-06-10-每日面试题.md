**一、分代回收模型——JVM 的核心设计哲学**

HotSpot JVM 将堆内存划分为不同的区域，基于"弱分代假说"（大多数对象朝生夕死）和"强分代假说"（熬过多次 GC 的对象更难消亡）进行分代管理。

```
JVM 堆内存结构（JDK 8+）：

  ┌─────────────────────────────────────────────────────────┐
  │                       堆内存                             │
  │  ┌──────────────────────────────────────────┐           │
  │  │            新生代（Young Generation）      │           │
  │  │  ┌──────┬──────────┬──────────┐          │           │
  │  │  │ Eden │ Survivor0│ Survivor1│          │           │
  │  │  │ (8)  │   (1)    │   (1)    │          │           │
  │  │  └──────┴──────────┴──────────┘          │           │
  │  └──────────────────────────────────────────┘           │
  │  ┌──────────────────────────────────────────┐           │
  │  │          老年代（Old Generation）          │           │
  │  │          Tenured / Old Gen               │           │
  │  └──────────────────────────────────────────┘           │
  └─────────────────────────────────────────────────────────┘
  ┌─────────────────────────────────────────────────────────┐
  │          元空间（Metaspace，直接内存）                    │
  │          存放类的元数据（替代永久代）                      │
  └─────────────────────────────────────────────────────────┘

  Eden:Survivor0:Survivor1 = 8:1:1（默认比例，可通过 -XX:SurvivorRatio 调整）
```

**对象分配与晋升规则**：

```
对象的生命周期：

  ① new 对象 → Eden 区分配
  ② Eden 区满 → 触发 Minor GC（Young GC）
  ③ Minor GC 后存活 → 进入 Survivor 区（S0 或 S1），年龄=1
     注意：两个 Survivor 区始终有一个是空的
  ④ 每次 Minor GC 存活 → 年龄 +1，在 S0/S1 之间来回复制
  ⑤ 年龄达到阈值（默认 15，CMS 默认 6）→ 晋升到老年代
  ⑥ 动态年龄判定：同年龄对象大小之和超过 Survivor 区 50%
     → 取该年龄和 MaxTenuringThreshold 的较小值作为新阈值
  ⑦ 大对象（如大数组）→ 直接进入老年代（避免在 Eden 区来回复制）
  ⑧ 老年代满 → 触发 Full GC（清理整个堆 + 元空间）
```

**关键 JVM 参数**：

| 参数 | 含义 | 建议值 |
|------|------|--------|
| `-Xms` / `-Xmx` | 初始/最大堆大小 | 物理内存的 50%-75%，两者设为相同避免扩容 |
| `-Xmn` | 新生代大小 | 堆总大小的 1/4 到 1/3 |
| `-XX:SurvivorRatio` | Eden/Survivor 比例 | 默认 8 |
| `-XX:MaxTenuringThreshold` | 晋升老年代年龄阈值 | 默认 15 |
| `-XX:PretenureSizeThreshold` | 大对象阈值 | 超过该值直接进老年代 |
| `-XX:+PrintGCDetails` | 打印 GC 详细日志 | 生产环境建议开启 |
| `-XX:+PrintGCDateStamps` | GC 日志带时间戳 | 便于问题追踪 |

**二、七种垃圾回收器对比**

| 回收器 | 工作区域 | 算法 | 特点 | STW 时间 | 适用场景 |
|--------|---------|------|------|---------|---------|
| **Serial** | 新生代 | 标记-复制 | 单线程，暂停所有用户线程 | 长 | 客户端、小内存（<100MB） |
| **Parallel Scavenge** | 新生代 | 标记-复制 | 多线程并行，吞吐量优先 | 中 | 后台计算、批处理 |
| **Parallel Old** | 老年代 | 标记-整理 | 多线程并行 | 中 | 配合 Parallel Scavenge |
| **CMS** | 老年代 | 标记-清除 | 并发收集，低延迟 | ⚠️ 两次短暂 STW | JDK 9 废弃，JDK 14 移除 |
| **G1** | 全堆 | 标记-整理+复制 | Region 模型，可控 STW | 低（可设置目标） | JDK 9+ 默认，大堆（4GB+） |
| **ZGC** | 全堆 | 染色指针+多映射 | **亚毫秒级 STW**（<1ms） | 极低 | JDK 15+，超大堆（TB级） |
| **Shenandoah** | 全堆 | 转发指针+并发整理 | 并发压缩，与 ZGC 类似 | 极低 | 需要低延迟的场景 |

**三、G1 收集器——JDK 9+ 默认收集器**

G1（Garbage-First）是 2026 年生产环境最主流的垃圾回收器，核心设计是 **Region 化** 和 **可控的 STW 时间**。

```
G1 的 Region 内存模型：

  ┌───┬───┬───┬───┬───┬───┬───┬───┬───┬───┐
  │ E │ E │ S │ S │ O │ O │ E │ H │ O │ E │ ... （每个 Region 默认 1-32MB）
  └───┴───┴───┴───┴───┴───┴───┴───┴───┴───┘
    E = Eden    S = Survivor    O = Old    H = Humongous（巨型对象区域）

  核心特点：
  ✅ 不再有连续的新生代/老年代物理区域
  ✅ Region 角色可以动态变化（Eden→Survivor→Old）
  ✅ 巨型对象：超过 Region 大小 50% 的对象 → 分配在连续的 Humongous Region
  ✅ STW 时间可预测：-XX:MaxGCPauseMillis=200（目标暂停时间 200ms）
```

**G1 的 Mixed GC——区别于 CMS**：

```
G1 的 GC 类型：

  ① Young GC（Minor GC）：只回收新生代 Region → STW（短）
  ② Mixed GC：
     - 回收所有新生代 Region + 部分老年代 Region
     - 选择"垃圾最多"的老年代 Region 优先回收（Garbage-First 的含义）
     - 在 -XX:MaxGCPauseMillis 时间内尽可能多回收
  ③ Full GC：
     - 当 Mixed GC 无法跟上内存分配速度时触发
     - STW，单线程，时间长（应尽量避免！）
```

**G1 vs CMS 对比**：

| 对比维度 | CMS | G1 |
|----------|-----|-----|
| 内存模型 | 连续的新生代+老年代 | Region 化，动态调整 |
| 老年代回收 | **标记-清除**（碎片严重） | **标记-整理+复制**（无碎片） |
| 并发失败 | 退化为 Serial Old（单线程） | 退化为 Full GC（单线程） |
| 可预测性 | 不可控 | `-XX:MaxGCPauseMillis` |
| 压缩 | 需要单独 Full GC | Mixed GC 自带压缩 |
| 官方状态 | JDK 14 已移除 | JDK 9+ 默认 |

**四、CMS 的三色标记与漏标问题**

理解 CMS 需要理解"三色标记法"，这也是 ZGC 和 G1 的基础。

```
三色标记法：

  ⚪ 白色：尚未被标记（GC 开始时所有对象都是白色，GC 结束后白色对象被回收）
  ⬜ 灰色：自身已被标记，但引用字段尚未处理完
  ⬛ 黑色：自身和引用字段都已处理完

  并发标记期间的问题：
  用户线程在标记过程中可能修改引用关系 → 导致漏标（活对象被误回收）

  漏标的两个条件（缺一不可）：
  ① 新增一个从黑色对象到白色对象的引用
  ② 删除所有从灰色对象到该白色对象的引用

  CMS 解决方案——增量更新（Incremental Update）：
  当黑色对象新增对白色对象的引用时，将黑色对象重新标记为灰色
  → 最终这个白色对象会被正确标记
  
  G1 解决方案——原始快照（SATB, Snapshot At The Beginning）：
  在标记开始时记录所有引用的快照
  → 任何被删除的引用（灰色→白色）都被视为"存活的"
  → 宁可多留（浮动垃圾），不可误杀
```

**五、ZGC——亚毫秒级 STW**

ZGC（Z Garbage Collector）是 JDK 15+ 的低延迟垃圾回收器，目标是 **STW 不超过 1ms**，支持 TB 级堆。

```
ZGC 核心技术：

  ① 染色指针（Colored Pointers）：
     在 64 位指针中嵌入元数据（Finalizable/Remapped/Marked1/Marked0）
     → 不需要额外开销就能知道对象状态

  ② 多映射（Multi-Mapping）：
     同一个物理内存映射到多个虚拟地址
     → 对象移动时只需更新虚拟地址映射，不需要修改指针

  ③ 并发整理（Concurrent Compaction）：
     对象移动和应用线程并发进行
     → 通过"读屏障"（Load Barrier）在读取时自动修复指针

  ZGC 适用场景：
  ✅ 超大堆（TB 级）
  ✅ 需要亚毫秒级暂停的延迟敏感应用（交易系统、实时竞价）
  ❌ 小堆（< 4GB）— G1 表现更好
```

**各 GC 组合选择建议（2026）**：

| 场景 | 推荐组合 |
|------|---------|
| JDK 8 兼容 | Parallel Scavenge + Parallel Old（`-XX:+UseParallelGC`） |
| JDK 9-16 大堆低延迟 | G1（默认，`-XX:+UseG1GC`） |
| JDK 15+ 极低延迟 | ZGC（`-XX:+UseZGC`） |
| JDK 15+ 极低延迟备选 | Shenandoah（`-XX:+UseShenandoahGC`） |

**六、Full GC 频发排查思路**

```
生产环境 Full GC 频发的排查步骤：

  ① 看 GC 日志 → 确认是 Full GC 还是 Young GC
     jstat -gcutil <pid> 1000（每秒输出一次 GC 统计）
     关注：FGC（Full GC 次数）、FGCT（Full GC 总耗时）

  ② 生成 Heap Dump → 分析内存分布
     jmap -dump:live,format=b,file=heap.hprof <pid>
     或 JVM 参数 -XX:+HeapDumpOnOutOfMemoryError

  ③ 用 MAT / JProfiler 分析 heap dump
     - Leak Suspects Report（泄漏嫌疑报告）
     - Dominator Tree（支配树，找出大对象）
     - Histogram（按类统计对象数量和大小）

  ④ 常见 Full GC 原因：
     ① 老年代空间不足 → 调大 -Xmx 或优化代码
     ② 元空间不足 → 调大 -XX:MaxMetaspaceSize
     ③ System.gc() 显式调用 → -XX:+DisableExplicitGC
     ④ 大对象频繁分配 → 优化数据结构
     ⑤ 内存泄漏（如 ThreadLocal 未清理）→ 修复代码

  ⑤ 典型 GC 日志解读：
     [GC (Allocation Failure) [PSYoungGen: 81920K->10240K(92160K)]
     → Young GC，由 Eden 区分配失败触发，回收前 80MB→回收后 10MB

     [Full GC (Ergonomics) [PSYoungGen: 10240K->0K(92160K)]
     [ParOldGen: 204800K->102400K(409600K)]
     → Full GC，新生代清空，老年代从 200MB 降至 100MB
```

### 💡 延伸思考

1. **为什么 CMS 被移除了而 G1 成为默认？** — CMS 基于标记-清除算法，老年代碎片化是致命缺陷。碎片严重到一定程度时，即使老年代总空间充足，也可能因找不到连续空间而触发 Full GC。G1 通过 Mixed GC 的复制/压缩消除碎片，且可预测 STW 时间。ZGC 虽然更先进，但在 JDK 15 才稳定，还需要更多的生产验证。
2. **G1 的 `-XX:MaxGCPauseMillis` 设小了会怎样？** — 设太小（如 10ms）会导致 G1 每次只回收很少的老年代 Region，回收速度跟不上分配速度，最终退化为 Full GC。一般建议设 100-200ms，根据实际业务需求权衡。

### 📖 参考答案

**一、为什么会有缓存不一致？——两种写入时序的陷阱**

在所有读写分离的缓存架构中，缓存和数据库是两份独立的数据副本。当数据更新时，总会存在一个"窗口期"，缓存和数据库的数据不一致。

```
经典的"先删缓存，再更新数据库"——为什么是错的？

  时间线：
  T1：线程 A 删除缓存
  T2：线程 B 读缓存 → 未命中 → 读数据库（拿到旧值）→ 写入缓存（旧值！）
  T3：线程 A 更新数据库（新值）
  T4：缓存中永远都是旧值！

  结论：这是最危险的模式，因为缓存中的脏数据可能永远存在（除非过期淘汰）。

"先更新数据库，再删除缓存"——为什么更好？

  时间线：
  T1：线程 A 更新数据库（新值）
  T2：线程 B 读取 → 可能缓存未失效 → 读到旧值（短暂不一致）
  T3：线程 A 删除缓存
  T4：后续请求 → 缓存未命中 → 读数据库（新值）→ 写入缓存（新值）

  结论：不一致窗口期更短（T2-T3 之间），且缓存过期或下一次读取时会自动修复。
  极端情况：T2在T3之后才写入缓存（概率极低）→ 仍然会短暂不一致，但会随时间自动修复。
```

**二、Cache-Aside Pattern——最经典的缓存模式**

```
Cache-Aside（旁路缓存）读写流程：

  读流程：
  ① 先查缓存 → 命中直接返回
  ② 未命中 → 查数据库 → 写入缓存 → 返回结果

  写流程（推荐）：
  ① 先更新数据库
  ② 再删除缓存（不是更新缓存！）
  → 原因：删除缓存比更新缓存更简单、更安全
    - 如果更新缓存值，写操作的计算逻辑可能与读操作不一致
    - 如果是多步计算的结果，更新缓存需要知道计算逻辑
    - 删除后等下次读取时再生成，保证数据一致性
```

```java
// Cache-Aside 实现示例
@Service
public class UserService {
    
    @Autowired
    private UserMapper userMapper;
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    // 读：先缓存后数据库
    public User getUser(Long id) {
        String cacheKey = "user:" + id;
        // ① 查缓存
        String json = redisTemplate.opsForValue().get(cacheKey);
        if (json != null) {
            return JSON.parseObject(json, User.class);
        }
        // ② 查数据库
        User user = userMapper.selectById(id);
        if (user != null) {
            // ③ 写缓存（带随机过期时间防止缓存雪崩）
            redisTemplate.opsForValue().set(
                cacheKey, 
                JSON.toJSONString(user),
                30 + ThreadLocalRandom.current().nextInt(10),  // 30-40 分钟随机
                TimeUnit.MINUTES
            );
        }
        return user;
    }
    
    // 写：先数据库后删缓存
    @Transactional
    public void updateUser(User user) {
        // ① 更新数据库
        userMapper.updateById(user);
        // ② 删除缓存
        redisTemplate.delete("user:" + user.getId());
        // 注意：删除失败怎么办？→ 需要重试或异步消息
    }
}
```

**三、延迟双删——解决高并发下的极端情况**

即使"先更新数据库再删除缓存"，在极端并发下仍可能出现不一致：

```
先更新数据库再删除缓存的不一致场景：

  T1：线程 A 删除缓存（上一步遗留或手动）
  T2：线程 B 读缓存 → 未命中 → 读数据库（旧值，此时 A 还没更新完成）
  T3：线程 A 更新数据库（新值）
  T4：线程 B 写入缓存（旧值！）
  T5：线程 A 删除缓存
  T6：缓存中已经是旧值 → 不一致！

  延迟双删解决方案：
  T1：删除缓存
  T2：更新数据库
  T3：延迟 N 毫秒（如 200-500ms）
  T4：再次删除缓存
  → 覆盖了"读线程在更新期间写入旧值"的窗口期
```

```java
// 延迟双删实现
public void updateUserWithDoubleDelete(User user) {
    // 第一次删除
    redisTemplate.delete("user:" + user.getId());
    
    // 更新数据库
    userMapper.updateById(user);
    
    // 延迟第二次删除（异步执行，不阻塞主线程）
    CompletableFuture.runAsync(() -> {
        try {
            Thread.sleep(500);  // 等待读请求完成
            redisTemplate.delete("user:" + user.getId());
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    });
}
```

**延迟双删的局限性**：
- 第二次删除如果失败，缓存仍然是脏数据
- 延迟时间难以精确确定（单位业务读耗时 × 2 作为经验值）
- 增加了系统复杂度
- 2026 年最佳实践：**延迟双删是兜底方案，Canal 订阅 Binlog 是最终方案**

**四、Canal + Binlog 异步订阅——生产级最终一致性方案**

延迟双删只能降低概率，无法彻底解决缓存一致性问题。生产环境的最佳实践是通过 **MySQL Binlog 订阅**，让缓存的更新与数据库变更"解耦但同步"。

```
Canal（阿里巴巴开源）方案架构：

  ┌─────────┐     ┌──────────┐     ┌──────────────┐     ┌─────────┐
  │ 应用服务 │────▶│  MySQL   │────▶│ Canal Server │────▶│  MQ     │
  │（写DB）  │     │ (Binlog) │     │（解析Binlog） │     │(RocketMQ)│
  └─────────┘     └──────────┘     └──────────────┘     └────┬────┘
                                                             │
                          ┌───────────────────────────────────┘
                          ▼
                    ┌──────────┐
                    │ 缓存同步  │──▶ Redis（更新/删除缓存）
                    │ Consumer │──▶ ES（更新搜索引擎索引）
                    └──────────┘──▶ 其他数据源

  流程：
  ① 应用只需更新数据库，不关心缓存
  ② Canal 伪装成 MySQL Slave，订阅 Binlog
  ③ 解析 Binlog → 提取变更的数据（表名、操作类型、变更字段）
  ④ 发送到 MQ → 缓存消费者异步更新/删除缓存
  ⑤ 即使缓存更新失败，MQ 可以重试，保证最终一致性
```

```java
// Canal 消费者示例
@Component
public class CacheSyncConsumer {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    // 监听 Canal 发来的 Binlog 消息
    @KafkaListener(topics = "canal-user-topic")
    public void handleBinlogEvent(CanalMessage message) {
        String table = message.getTable();
        String type = message.getType();  // INSERT / UPDATE / DELETE
        
        if ("user".equals(table)) {
            Map<String, String> data = message.getData();
            Long userId = Long.valueOf(data.get("id"));
            String cacheKey = "user:" + userId;
            
            switch (type) {
                case "UPDATE":
                case "DELETE":
                    // 直接删除缓存，等下次读取时重建
                    redisTemplate.delete(cacheKey);
                    break;
                case "INSERT":
                    // 预加载缓存
                    String json = JSON.toJSONString(data);
                    redisTemplate.opsForValue().set(
                        cacheKey, json, 30, TimeUnit.MINUTES);
                    break;
            }
        }
    }
}
```

**Canal 方案的优势**：
- ✅ **完全解耦**：业务代码不需要关心缓存更新逻辑
- ✅ **最终一致**：MQ 重试机制保证消息不丢失
- ✅ **可扩展**：同一份 Binlog 可以同步到多个目标（Redis/ES/其他）
- ✅ **无侵入**：不改动业务代码

**五、各方案对比总结**

| 方案 | 一致性 | 复杂度 | 性能 | 适用场景 |
|------|--------|--------|------|---------|
| **先更DB再删缓存** | ⭐⭐⭐ | ⭐ | ⭐⭐⭐⭐⭐ | 并发不高的业务 |
| **延迟双删** | ⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐⭐ | 高并发读多写少 |
| **Canal + Binlog** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | **生产环境推荐** |
| **分布式锁强一致** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ | 金融/交易核心链路 |
| **设置合理过期时间** | ⭐⭐⭐ | ⭐ | ⭐⭐⭐⭐⭐ | 作为所有方案的兜底 |

### 💡 延伸思考

1. **为什么不直接在更新数据库的事务里更新缓存？** — 如果把缓存操作放在数据库事务里，会引入分布式事务的复杂性（数据库和 Redis 是两个独立的系统）。而且缓存是性能优化手段，不应该和事务绑定——缓存更新失败不应该导致事务回滚。正确做法是：数据库事务提交 → 异步更新缓存。
2. **Canal 消费延迟会导致长时间不一致吗？** — Canal 的延迟通常在毫秒级。加上 MQ 消息堆积，最差情况下延迟可能到秒级。如果业务要求读到的数据必须和数据库完全一致（如账户余额），那就不能依赖缓存，应该直接读数据库并在接口上灰度验证。

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-10 午间报告 — "Kafka消息可靠性" + "系统设计：监控治理、稳定性优化、参数调优"

### 📖 参考答案

**一、Kafka 消息丢失的三个环节——全链路分析**

Kafka 消息从 Producer 到 Consumer 经过三个环节，每个环节都可能丢失消息：

```
消息丢失的三个环节：

  Producer → Broker → Consumer
     ①         ②         ③

  ① Producer 端：消息没发出去/发送了但未确认
  ② Broker 端：Leader 宕机，数据未同步给 Follower
  ③ Consumer 端：消息没消费完就提交了 offset，然后宕机
```

**二、Producer 端可靠性——acks + 幂等性 + 事务**

### acks 参数

| acks | 含义 | 可靠性 | 延迟 | 适用场景 |
|------|------|--------|------|---------|
| **acks=0** | 不等待确认，发送即成功 | ❌ 最低（可能丢失） | 最低 | 日志收集、监控数据 |
| **acks=1** | 等待 Leader 确认写入 | ⚠️ 中（Leader 宕机可能丢失） | 低 | 可容忍少量丢失的场景 |
| **acks=-1 (all)** | 等待所有 ISR 副本确认 | ✅ 最高 | 高 | 订单、支付、金融 |

```
acks=all 的安全性分析：

  Producer 发送 → Leader 写入 → 等待所有 ISR 副本同步完成 → 返回 ACK

  ISR（In-Sync Replicas）：与 Leader 保持同步的副本集合
  - Leader 始终在 ISR 中
  - Follower 在 ISR 中的条件：与 Leader 的 lag < replica.lag.time.max.ms（默认 30s）

  配合 min.insync.replicas（默认 1）：
  replication.factor=3（3 个副本）
  min.insync.replicas=2（至少 2 个副本确认）
  → 即使一个副本宕机，仍然有 2 个副本有数据
  → 保证了强可靠性
```

### 幂等性（Idempotence）

```java
// 开启幂等性
Properties props = new Properties();
props.put("enable.idempotence", true);  // 默认 false
props.put("acks", "all");               // 幂等性要求 acks=all
```

```
幂等性实现原理：

  ① Producer 启动时分配 Producer ID（PID，全局唯一）
  ② 每条消息带 Sequence Number（从 0 递增，每个分区独立）
  ③ Broker 维护每个 PID 的 Seq 号，收到消息时检查：
     - seq == brokerSeq + 1 → 正常，接受
     - seq <= brokerSeq → 重复消息，丢弃（幂等！）
     - seq > brokerSeq + 1 → 丢失消息，报错 OutOfOrderSequenceException

  幂等性的作用：
  ✅ 防止 Producer 重试导致的重复消息（如网络抖动后重试）
  ❌ 不能跨 Producer 实例（重启后 PID 变化）
  ❌ 不能跨分区（每个分区独立维护 Seq 号）
```

### 事务——跨分区/跨会话的精确一次语义

```java
// Kafka 事务 API
producer.initTransactions();
try {
    producer.beginTransaction();
    producer.send(record1);  // 分区 0
    producer.send(record2);  // 分区 1
    producer.sendOffsetsToTransaction(...);  // 包含 Consumer offset
    producer.commitTransaction();            // 原子提交
} catch (Exception e) {
    producer.abortTransaction();
}
```

```
Kafka 事务实现原理：

  ① 基于幂等性（必须先开启 enable.idempotence=true）
  ② 引入 Transaction Coordinator（事务协调器，运行在 Broker 上）
  ③ TC 分配 Transactional ID → 维护事务状态
  ④ 即使 Producer 重启，Transactional ID 不变，事务状态可恢复
  ⑤ 典型场景：消费-处理-生产（流处理中的精确一次语义）
```

**三、Broker 端可靠性——副本同步与 ISR**

```
Kafka 副本概念：

  AR（Assigned Replicas）：为分区分配的所有副本
  ISR（In-Sync Replicas）：与 Leader 保持同步的副本
  OSR（Out-of-Sync Replicas）：同步滞后的副本

  关系：AR = ISR + OSR

  副本同步机制：
  ① Producer 只向 Leader 写入
  ② Follower 从 Leader 拉取数据（fetch）进行同步
  ③ ISR 条件：(lastCaughtUpTimeMs - currentTimeMs) < replica.lag.time.max.ms

  Leader 选举：
  ① Leader 宕机 → 从 ISR 中选择新 Leader（优先选择 AR 中最新的）
  ② unclean.leader.election.enable = false（默认）：
     不允许 OSR 中的副本成为 Leader → 宁可不可用，也不丢数据
  ③ unclean.leader.election.enable = true：
     允许 OSR 成为 Leader → 可能导致数据丢失
```

```
生产环境推荐配置：

  # Broker 配置
  replication.factor=3              # 3 个副本
  min.insync.replicas=2             # 至少 2 个 ISR 副本确认
  unclean.leader.election.enable=false  # 不允许非 ISR 选举
```

**四、Consumer 端可靠性——手动提交 Offset**

```java
// ❌ 自动提交：消息可能没消费就提交了
props.put("enable.auto.commit", "true");
props.put("auto.commit.interval.ms", "1000");

// ✅ 手动提交：消费完再提交
props.put("enable.auto.commit", "false");

@KafkaListener(topics = "order-topic")
public void consume(ConsumerRecord<String, String> record, Acknowledgment ack) {
    try {
        // 处理业务逻辑
        processOrder(record.value());
        // 手动确认
        ack.acknowledge();
        
    } catch (Exception e) {
        log.error("消息处理失败，offset: {}", record.offset(), e);
        // 不确认 → 消息会被重新消费
        // 注意：需要保证业务幂等，否则重复消费会导致问题
    }
}
```

**五、消息不丢失全景配置**

```properties

enable.idempotence=true                     # 开启幂等，防止重复
retries=2147483647                          # 最大重试（Integer.MAX_VALUE）
max.in.flight.requests.per.connection=5     # 未确认请求数（幂等下可设 >1）

# === Broker 端 ===

# === Consumer 端 ===
enable.auto.commit=false                    # 关闭自动提交
isolation.level=read_committed              # 只读已提交的事务消息
```

**六、重复消费——如何保证最终一致性**

Kafka 只能保证"至少一次"（At-Least-Once），无法天然保证"精确一次"（Exactly-Once）。重复消费需要业务层保证幂等。

```
处理重复消费的常见方案：

  ① 数据库唯一键去重：
     INSERT INTO order_log (message_id, ...) VALUES (?, ...) ON DUPLICATE KEY UPDATE ...
     → 用 message_id 或业务唯一标识（订单号）做唯一约束

  ② Redis 去重：
     SETNX("msg:processed:" + offset, "1", 3600, TimeUnit.SECONDS)
     → 消息处理前先检查是否已处理过

  ③ 业务状态机：
     订单状态：CREATED → 支付中 → 已支付
     只有 CREATED 状态才能处理支付消息，已支付的直接忽略

  ④ 数据库乐观锁：
     UPDATE order SET status='PAID', version=version+1 
     WHERE id=123 AND version=5
     → 版本号不匹配则忽略（已处理过）
```

### 💡 延伸思考

1. **`max.in.flight.requests.per.connection` 为什么在未开启幂等时必须设为 1？** — 如果 >1，多个未确认的请求可能乱序到达 Broker。假设请求1和请求2依次发送，请求1失败重试、请求2成功写入。请求1重试成功后，Broker 上消息的顺序是 2→1，乱序了。开启幂等后，Broker 通过 Seq 号检查可以处理这种情况，所以可以 >1 以提高吞吐。
2. **ISR 缩小到只有 Leader 了怎么办？** — 如果 min.insync.replicas=2，但 ISR 缩小到 1（只有 Leader），Producer 将收到 NOT_ENOUGH_REPLICAS 异常，拒绝写入。这是"宁可不可用，也不丢数据"的设计。可以通过监控 ISR 变化，在 ISR 缩小到危险值时提前告警处理。

  └─────────────────────────────────────────────┘

**二、行锁的三种形态——Record / Gap / Next-Key**

```
记录锁、间隙锁、临键锁的关系：

  表数据（主键 id）：5, 10, 15, 20

  记录锁（Record Lock）：
  锁住 id=10 这一行
  → SELECT * FROM t WHERE id = 10 FOR UPDATE;

  间隙锁（Gap Lock）：
  锁住 (5, 10) 这个区间（不包含边界）
  → SELECT * FROM t WHERE id > 5 AND id < 10 FOR UPDATE;
  → 其他事务不能在这个区间 INSERT
  → 间隙锁之间不冲突！多个事务可以锁同一个间隙

  临键锁（Next-Key Lock）：
  锁住 (5, 10] 这个左开右闭区间（Record Lock + Gap Lock）
  → SELECT * FROM t WHERE id <= 10 FOR UPDATE;
  → 默认的行锁策略在 RR 隔离级别下就是 Next-Key Lock
```

```sql
-- 不同 SQL 触发的锁类型（RR 隔离级别）

-- ① 唯一索引等值查询，命中 → Record Lock
SELECT * FROM t WHERE id = 10 FOR UPDATE;  -- 只锁 id=10 这一行

-- ② 唯一索引等值查询，未命中 → Gap Lock
SELECT * FROM t WHERE id = 7 FOR UPDATE;  -- 锁住 (5, 10) 间隙

-- ③ 唯一索引范围查询 → Next-Key Lock（左开右闭）
SELECT * FROM t WHERE id >= 10 AND id <= 15 FOR UPDATE;
-- 锁住 (5, 10] + (10, 15] + 下一个间隙 (15, 20)

-- ④ 普通索引等值查询 → Next-Key Lock + 下一个间隙
-- 假设 age 是普通索引，值为 20, 30, 30, 40
SELECT * FROM t WHERE age = 30 FOR UPDATE;
-- 锁住 (20, 30] + (30, 30] + (30, 40) ← 多锁一个间隙！
```

**三、共享锁与排他锁的兼容矩阵**

```
锁兼容矩阵：

        | S Lock | X Lock | IS Lock | IX Lock |
  ──────┼────────┼────────┼─────────┼─────────┤
  S     |  ✅    |  ❌    |  ✅     |  ❌     |
  X     |  ❌    |  ❌    |  ❌     |  ❌     |
  IS    |  ✅    |  ❌    |  ✅     |  ✅     |
  IX    |  ❌    |  ❌    |  ✅     |  ✅     |

  关键规则：
  - S 和 X 互斥（读写互斥）
  - X 和 X 互斥（写写互斥）
  - IS/IX 之间兼容（意向锁不冲突）
  - S 和 IS 兼容（读读不冲突）
```

**意向锁的作用——为什么需要表级意向锁？**

```
场景：事务 A 对某一行加了 X 锁，事务 B 要对整个表加 X 锁

  没有意向锁：
  事务 B 必须遍历所有行检查是否有行锁 → 效率极低！

  有意向锁：
  事务 A 加行 X 锁 → 先加表 IX 锁
  事务 B 要对表加 X 锁 → 检查表是否有 IX 锁 → 有！冲突！→ 等待
  → O(1) 时间判断，不需要遍历所有行
```

**四、死锁——典型场景与排查**

```sql
-- 经典死锁场景：两个事务互相等待

-- 事务 A：
BEGIN;
UPDATE t SET name='A' WHERE id = 1;  -- 对 id=1 加 X 锁
-- 此时事务 B 执行...

UPDATE t SET name='A2' WHERE id = 2;  -- 等待 id=2 的 X 锁 → 死锁！

-- 事务 B：
BEGIN;
UPDATE t SET name='B' WHERE id = 2;  -- 对 id=2 加 X 锁
UPDATE t SET name='B2' WHERE id = 1;  -- 等待 id=1 的 X 锁 → 死锁！

-- InnoDB 检测到死锁 → 回滚其中一个事务（持锁少的/undo代价小的）
-- 被回滚的事务收到 Deadlock found 错误
```

**死锁排查命令**：

```sql
-- ① 查看当前锁等待情况
SHOW ENGINE INNODB STATUS\G

-- 关键字段解读：
-- ------------------------
-- LATEST DETECTED DEADLOCK
-- ------------------------
-- 2026-06-10 15:30:00
-- *** (1) TRANSACTION:                          ← 事务 1
-- UPDATE t SET name='A2' WHERE id = 2           ← 事务 1 等待的语句
-- *** (1) HOLDS THE LOCK(S):                    ← 事务 1 持有的锁
-- RECORD LOCKS space id 10 page no 3 n bits 72  ← 锁住的记录
-- *** (2) TRANSACTION:                          ← 事务 2
-- UPDATE t SET name='B2' WHERE id = 1           ← 事务 2 等待的语句
-- *** (2) HOLDS THE LOCK(S):                    ← 事务 2 持有的锁
-- *** WE ROLL BACK TRANSACTION (2)              ← InnoDB 回滚了事务 2

-- ② 查看当前锁信息（MySQL 8.0+）
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;

-- ③ 查看当前事务和锁等待
SELECT * FROM information_schema.INNODB_TRX;           -- 当前事务
SELECT * FROM information_schema.INNODB_LOCKS;         -- 当前锁（8.0 前）
SELECT * FROM information_schema.INNODB_LOCK_WAITS;    -- 锁等待（8.0 前）
```

**五、死锁避免策略**

```
死锁避免的最佳实践：

  ① 统一加锁顺序（最重要！）：
     - 多个表操作 → 固定顺序（如按表名字母序）
     - 同一表多行操作 → 按主键 ID 升序更新
     
     // ❌ 事务 A 先锁 id=2 再锁 id=1，事务 B 反过来 → 死锁
     // ✅ 始终按主键 ID 升序操作
     List<Long> ids = Arrays.asList(2L, 1L);
     Collections.sort(ids);  // 排序！

  ② 缩短事务时间：
     - 不在事务中做 RPC 调用、文件 IO
     - 把非数据库操作放在事务之外

  ③ 合理使用索引：
     - 无索引 → 行锁退化为表锁 → 并发度低，容易死锁
     - EXPLAIN 确认 SQL 使用了正确的索引

  ④ 减少锁范围：
     - 用乐观锁代替悲观锁（version 字段）
     - 用 select ... for update 时尽量带主键精确查询

  ⑤ 设置死锁重试：
     @Transactional
     public void updateUser(User user) {
         int retryCount = 3;
         while (retryCount > 0) {
             try {
                 userMapper.updateById(user);
                 return;
             } catch (DeadlockLoserDataAccessException e) {
                 retryCount--;
                 if (retryCount == 0) throw e;
                 Thread.sleep(100);  // 短暂等待后重试
             }
         }
     }
```

### 💡 延伸思考

1. **为什么 RR 隔离级别下要加 Gap Lock？** — Gap Lock 的唯一目的就是**防止幻读**（其他事务在间隙中插入新数据）。但 Gap Lock 的代价是降低了并发插入性能。所以如果业务不需要 RR 隔离级别，可以考虑使用 RC（Read Committed）并开启 `binlog_format=ROW`，RC 下不会加 Gap Lock，死锁概率大幅降低。
2. **死锁避免的最佳实践中最容易被忽略的是什么？** — **索引**。很多开发者以为 `WHERE status = 1` 能命中索引，但实际上 `status` 字段只有 3 个值（选择性极低），MySQL 优化器可能选择全表扫描。全表扫描时所有行都会被锁，并发度降到最低，死锁概率暴增。务必用 EXPLAIN 确认加锁 SQL 的执行计划。

### 💡 延伸思考

1. **MCP 和传统的 REST API 有什么区别？为什么不能直接用 REST API？** — REST API 的问题是：① 需要人类开发者理解 API 文档和参数；② 不同服务的 API 格式不统一；③ LLM 需要单独的适配代码来处理每个 API。MCP 将工具的"描述"标准化（工具名称、参数类型、参数描述），让 LLM 能自主理解和调用，不需要人类写适配代码。
2. **Spring AI Alibaba 和 LangChain4j 怎么选？** — 如果你的团队是 Spring 技术栈，选 Spring AI Alibaba（注解风格、依赖注入、与 Spring Boot 无缝集成）。如果团队有多语言需求或用了 Quarkus/Micronaut，选 LangChain4j（更轻量、更多 LLM 厂商支持）。2026 年两者生态都在快速成熟，差异在缩小。
