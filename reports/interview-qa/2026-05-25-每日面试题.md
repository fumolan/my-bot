**一、面试破题：自动配置 ≠ 魔法**

很多候选人在面试中被问到"自动配置原理"时，只能说出"启动类上的注解会自动扫描"——这是致命的浅层回答。面试官真正想听的是你对三层机制的理解：

| 层次 | 考察点 | 加分项 |
|------|--------|--------|
| 注解层 | @SpringBootApplication 里有哪些元注解？各自作用？ | 能说出 @EnableAutoConfiguration 与另外两者关系 |
| 选择器层 | selectImports 如何决定加载哪些配置类？ | 能对比 spring.factories 和 AutoConfiguration.imports 的演进 |
| 过滤层 | @Conditional 注解怎么精确控制"某类只是否加载"？ | 能举例说明 @ConditionalOnMissingBean 的经典踩坑场景 |

**二、@SpringBootApplication 三层注解拆解**

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Inherited
@SpringBootConfiguration          // 层①：标识这是 Spring Boot 的配置类
@EnableAutoConfiguration          // 层②：开启自动配置（核心！）
@ComponentScan(excludeFilters = {  // 层③：组件扫描
    @Filter(type = FilterType.CUSTOM, classes = TypeExcludeFilter.class),
    @Filter(type = FilterType.CUSTOM, classes = AutoConfigurationExcludeFilter.class)
})
public @interface SpringBootApplication {
    // ...
}
```

三层各有独立职责：

```
@SpringBootConfiguration
  └─ 本质就是 @Configuration + @Indexed
     → 让启动类成为 Spring 容器的配置入口

@EnableAutoConfiguration
  └─ 核心！触发 Spring Boot 的"约定大于配置"魔法
     → 内部通过 @Import(AutoConfigurationImportSelector.class) 导入选择器
     → 选择器决定加载哪些自动配置类

@ComponentScan
  └─ 扫描启动类所在包及子包下的 @Component/@Service/@Controller
     → 默认包路径 = 启动类所在包
     → excludeFilters 排除 TypeExcludeFilter 和 AutoConfigurationExcludeFilter
```

**四、spring.factories → AutoConfiguration.imports 的演进（必考点）**

```java
// ⚠️ 旧版（Spring Boot 2.7 之前）
// META-INF/spring.factories
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
  com.example.MyAutoConfiguration

// AutoConfigurationImportSelector 通过 SpringFactoriesLoader 读取
// SpringFactoriesLoader.loadFactoryNames(EnableAutoConfiguration.class, classLoader)

// ⭐ 新版（Spring Boot 2.7+，3.0 推荐）
// META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
// 每行一个配置类全限定名，纯文本格式：
com.example.MyAutoConfiguration
com.example.AnotherAutoConfiguration

// 为什么要改？
// ① spring.factories 是"一个大文件装所有 SPI"的共享空间
//     → 解析所有 key-value 开销大，查找目标 key 需要遍历
// ② AutoConfiguration.imports 是专用文件
//     → 只包含自动配置类 → 解析更快
//     → ImportCandidates.load(AutoConfiguration.class, classLoader)
//     → 内部按行读取，无需解析 properties 格式
// ③ 兼容性：Spring Boot 3.x 仍向后兼容 spring.factories，但会打 WARN 日志
```

**五、@Conditional 条件注解过滤链（面试分层回答）**

```
真正的自动配置"智慧"在于一系列 @Conditional 注解，让配置类只在条件满足时才生效：

第一层：类级别条件（某类存在才生效）
  @ConditionalOnClass(name = "com.mysql.cj.jdbc.Driver")
  → 只有 MySQL 驱动在 classpath 中，DataSourceAutoConfiguration 才加载
  → 这就是"不加 MySQL 依赖就自动放弃 MySQL 配置"的原理！

  @ConditionalOnMissingClass("org.springframework.web.servlet.DispatcherServlet")
  → 没有 SpringMVC → 启用 WebFlux 自动配置

第二层：Bean 级别条件（某 Bean 存在/不存在才生效）
  @ConditionalOnBean(DataSource.class)
  → 已经有数据源了才配置 JdbcTemplate

  @ConditionalOnMissingBean(RedisConnectionFactory.class)
  → 用户没自定义 Redis 连接工厂 → 自动创建默认的
  → ⚠️ 经典坑：如果有 @Configuration 类同时通过 @ConditionalOnBean 和 @Bean
     产生循环依赖 → 因为 @ConditionalOnBean 校验发生在 Bean 创建期间

  推荐替代方案：
  @Configuration
  @AutoConfigureAfter(DataSourceAutoConfiguration.class)  // 强制顺序
  public class MyConfig {
      @Bean
      @ConditionalOnMissingBean
      public JdbcTemplate jdbcTemplate(DataSource ds) { ... }
  }

第三层：属性级别条件（配置属性值决定）
  @ConditionalOnProperty(prefix = "spring.redis", name = "enabled", havingValue = "true", matchIfMissing = true)
  → spring.redis.enabled=true（或不配置）→ 加载 Redis 配置
  → spring.redis.enabled=false → 跳过

  @ConditionalOnExpression("${my.feature.enabled:false}")
  → 支持 SpEL 表达式，更灵活

第四层：运行时条件
  @ConditionalOnJava(JavaVersion.SEVENTEEN) — JDK 版本
  @ConditionalOnWebApplication(type = SERVLET) — Web 环境类型
  @ConditionalOnResource(resources = "classpath:my-config.properties") — 资源文件存在

条件注解求值底层：
  Spring 的 ConditionEvaluator.shouldSkip() → matches()
  → 遍历每个 @Conditional 注解的 Condition 实现类
  → 依次调用 condition.matches(conditionContext, annotatedTypeMetadata)
  → 任意一个返回 false → 跳过整个配置类/方法
```

**六、自定义 Starter（面试加分项）**

```java
// ========== 步骤1：定义自动配置类 ==========
@AutoConfiguration  // Spring Boot 3.x 新注解，替代 @Configuration 增强语义
@EnableConfigurationProperties(MyServiceProperties.class)
@ConditionalOnClass(MyService.class)   // 只在 classpath 有该类时生效
@ConditionalOnProperty(prefix = "myservice", name = "enabled", matchIfMissing = true)
public class MyServiceAutoConfiguration {

    private final MyServiceProperties properties;

    public MyServiceAutoConfiguration(MyServiceProperties properties) {
        this.properties = properties;
    }

    @Bean
    @ConditionalOnMissingBean
    public MyService myService() {
        return new MyService(properties.getUrl(), properties.getTimeout());
    }
}

// ========== 步骤2：定义配置属性类 ==========
@ConfigurationProperties(prefix = "myservice")
public class MyServiceProperties {
    private String url = "http://localhost:8080";
    private int timeout = 5000;
    // getter/setter...
}

// ========== 步骤3：注册到 SPI ==========
// 文件: META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
// 内容：
com.example.mystarter.MyServiceAutoConfiguration

// ========== 步骤4：提供 spring-configuration-metadata.json ==========
// 通过 spring-boot-configuration-processor 自动生成
// 让 IDEA 具备 YAML/Properties 的自动提示功能

// ========== 使用方只需 ==========
// ① 引入 starter 依赖
// ② 在 application.yml 中配置：
//    myservice:
//      url: https://api.example.com
//      timeout: 3000
// ③ 直接 @Autowired 注入 MyService！
```

**一、Platform Thread vs Virtual Thread — 理解本质差异**

虚拟线程是 JDK 21 正式发布的革命性特性（Project Loom），它在 2026 年已成为面试中区分"会用 Java"和"懂 Java"的关键题。

```
传统线程模型（Platform Thread）：

  应用层          操作系统
  ┌─────┐        ┌──────────┐
  │Java  │  1:1   │OS Thread │  ← 一对一绑定！
  │Thread│ ←───→ │(~2MB栈)  │
  └─────┘        │(内核调度) │
  └─────┘        └──────────┘
  
  → 10000 个线程 = 10000 × 2MB = 20GB 内存（仅栈空间！）
  → 上下文切换需要内核态切换（~1μs级别）
  → 大部分时间线程在等 IO，白白占用 OS 资源

虚拟线程模型（Virtual Thread）：

  应用层                    操作系统
  ┌──────────┐             ┌──────────┐
  │VT1  VT2  │  M:N 映射   │Carrier 1 │  ← 少量 OS 线程作为"载体"
  │VT3  VT4  │ ←───────→  │Carrier 2 │
  │...       │             │(少量~CPU核数)│
  │VT100万   │             └──────────┘
  └──────────┘
  
  → 100万个虚拟线程 = 100万 × ~几KB = 几百MB 内存
  → 上下文切换是 JVM 内的对象指针切换（~ns级）
  → IO 阻塞时虚拟线程自动 unmount，释放 Carrier 处理其他任务
```

**对比总结：**

| 维度 | Platform Thread | Virtual Thread |
|------|----------------|----------------|
| **绑定关系** | 1:1 绑定 OS 线程 | M:N 映射到少量 Carrier |
| **内存开销** | ~2MB（默认栈） | ~几KB（堆内对象） |
| **创建速度** | ~1ms | ~1μs（快 1000 倍） |
| **上下文切换** | 内核态切换（~1-10μs） | JVM 内对象切换（~ns） |
| **最大数量** | 数千 | 数百万 |
| **适用场景** | CPU 密集计算 | IO 密集等待 ⭐ |
| **调度器** | OS 内核调度 | JVM ForkJoinPool 调度 |

**二、Carrier Thread 与 Mount/Unmount 核心机制**

```
虚拟线程的生命周期：

  ① Mount（挂载）：
     虚拟线程被分配给一个 Carrier Thread（平台线程）
     → 虚拟线程的栈帧被拷贝到 Carrier 的栈上
     → 开始执行虚拟线程的任务
  
  ② 运行中...
     虚拟线程在 Carrier 上运行 Java 代码
  
  ③ 遇到 IO 阻塞 → Unmount（卸载）⭐ 核心！
     虚拟线程调用阻塞 IO 操作（如 Socket read / HTTP 请求）
     → JVM 检测到 IO 是"可 park 的"
     → 虚拟线程的栈帧从 Carrier 栈上拷贝回堆（Continuation 快照）
     → Carrier 被释放，可以接管其他虚拟线程
     → 虚拟线程进入"等待"状态，存在堆中
  
  ④ IO 完成 → 重新 Mount
     IO 操作完成 → JVM 调度器将虚拟线程重新分配给可用的 Carrier
     → 栈帧从堆拷贝回 Carrier 栈
     → 虚拟线程从阻塞后的代码继续执行（无感知！）
```

**为什么虚拟线程不是"更快的线程"？**

> 虚拟线程的目的不是让单个任务跑得更快（speed），而是让系统容纳更多的并发任务（scale/throughput）。
> 一个 virtual thread 运行代码的速度和一个 platform thread 一样——它只是避免了 OS 线程的饥饿和资源浪费。

**三、Continuation — 实现 Mount/Unmount 的底层引擎**

```java
// Continuation 的本质：可暂停、可恢复的执行单元
// 虚拟线程内部基于 Continuation 实现（JDK 内部 API，非公开）

// 简化理解：
class VirtualThread extends Thread {
    private Continuation cont;        // 延续体
    private Runnable task;            // 用户任务
    private Carrier carrier;          // 当前挂载的平台线程
    
    void run() {
        cont = new Continuation(() -> {
            task.run();  // 执行用户任务
        });
        
        while (!cont.isDone()) {
            // 继续执行 continuation
            cont.run();
            
            // 如果 continuation 暂停（yield/park）
            // 当前 carrier 被释放
            // 后续由调度器重新 mount 到某个 carrier 上继续
        }
    }
}

// Continuation.yield() 的本质：
// → 保存当前栈帧到堆（冻结）
// → 返回到 cont.run() 的调用点
// → 调用者（虚拟线程的载体会员）释放 carrier

// 当 IO 可读时：
// → 调度器获取到一个可用的 carrier
// → 将冻结的栈帧拷贝回去（解冻）
// → 从 yield() 调用处继续执行
// → 对上层代码透明！
```

**四、synchronized -> Pin 的经典问题与解决**

```java
// ⚠️ 坑！虚拟线程在 synchronized 块内阻塞 IO → Pin（钉住）
// Pin 意味着：虚拟线程无法 unmount，整个 carrier 被白白占用

// ❌ 问题代码：
synchronized (lock) {
    String data = httpClient.send(request);  // IO 阻塞！
    // → 虚拟线程被 Pin 在 OS 线程上，无法释放 carrier
    // → 别的虚拟线程只能排队等这个 carrier
}
// Carrier Thread 被占用 → 调度器无法把其他虚拟线程挂到它上面

// ✅ 正确做法：用 ReentrantLock 替代 synchronized
// JDK 21+ 的 ReentrantLock 支持虚拟线程的友好 parking
Lock lock = new ReentrantLock();
lock.lock();
try {
    String data = httpClient.send(request);  // IO 阻塞 → 虚拟线程正常 unmount！
    // → carrier 释放，别的虚拟线程可以继续
} finally {
    lock.unlock();
}

// 另一个 Pin 场景（JDK 24+ 已修复）：
// `synchronized` 在 JDK 24 中已移除 Pin 限制！
// 但 Native Method / Foreign Function 调用仍然会 Pin
```

**五、虚拟线程的使用方式**

```java
// 方式1：直接创建（最简单）
Thread vt = Thread.ofVirtual()
    .name("my-virtual-thread")
    .start(() -> {
        System.out.println("Running in virtual thread");
    });
vt.join();

// 方式2：Thread.Builder 批量创建
Thread.Builder builder = Thread.ofVirtual().name("worker-", 1);
Thread t1 = builder.start(task1);
Thread t2 = builder.start(task2);  // name="worker-2"

// 方式3：虚拟线程的 ExecutorService（⭐ 推荐）
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    // 每 submit 一个任务 → 自动创建一个新的虚拟线程
    Future<String> f1 = executor.submit(() -> callApi("user-1"));
    Future<String> f2 = executor.submit(() -> callApi("user-2"));
    Future<String> f3 = executor.submit(() -> callApi("user-3"));
    
    // 等待所有结果
    String r1 = f1.get();
    String r2 = f2.get();
    String r3 = f3.get();
}

// 方式4：Structured Concurrency（JDK 21 预览，24 正式）
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Future<String> user = scope.fork(() -> fetchUser());
    Future<List<Order>> orders = scope.fork(() -> fetchOrders());
    
    scope.join();     // 等待两个子任务完成
    scope.throwIfFailed();
    
    // 两个任务在虚拟线程中并行执行
    return new UserWithOrders(user.resultNow(), orders.resultNow());
}
```

**六、虚拟线程在 AI Agent 场景的应用**

```
为什么 2026 年 AI Agent 后端格外需要虚拟线程？

场景：一个 Agent 请求需要调用 3 次 LLM API（每次 2-5 秒）

传统方案（Platform Thread + 线程池）：
  Tomcat 线程池 200 个线程
  → 每个 Agent 请求占一个线程 5-10 秒
  → 并发 200 个 Agent 请求就满了！
  → 扩容 → 2000 个线程 → 内存爆炸

虚拟线程方案：
  → 10000 个 Agent 请求 → 10000 个虚拟线程
  → 只需 ~10 个 carrier 线程
  → 内存：~几百MB
  → 吞吐量：传统方案的 50 倍+
```

### 💡 延伸思考
1. **虚拟线程能不能用于 CPU 密集型任务？** — 不推荐。虚拟线程的强项是 IO 等待时"让出载体"。CPU 密集任务没有 IO 阻塞点，虚拟线程会一直占用 carrier，而且 Mount/Unmount 还有额外开销。CPU 密集任务仍然适合 Platform Thread + ForkJoinPool。
2. **虚拟线程如何影响 ThreadLocal 的使用？** — 虚拟线程数量可能达到百万级，每个 ThreadLocal 变量会在每个虚拟线程上创建一个 Entry → 严重内存浪费。JDK 21 引入 `ScopedValue`（预览）作为不可变替代方案，更适合虚拟线程时代。

**二、Spring Cloud Gateway 三要素路由模型**

Gateway 的路由 = Predicate（谓词）+ Filter（过滤器）+ URI（目标地址）：

```
┌────────────────────────────────────────────────────────┐
│              Gateway 请求处理流程                         │
│                                                        │
│  请求到达 → Gateway Handler Mapping                     │
│     ↓                                                  │
│  匹配路由：遍历所有 Route，用 Predicate 判断是否匹配       │
│     ↓                                                  │
│  Route 匹配成功 → 执行 Filter Chain（前置过滤器）          │
│     ↓                                                  │
│  转发请求到目标 URI（通过 Netty 异步 HTTP 客户端）         │
│     ↓                                                  │
│  接收后端响应 → 执行 Filter Chain（后置过滤器）            │
│     ↓                                                  │
│  返回响应给客户端                                       │
└────────────────────────────────────────────────────────┘
```

**四、Gateway 基于 Netty 的异步非阻塞 IO**

```
为什么 Gateway 性能远高于 Zuul 1.x？

Zuul 1.x（同步阻塞 servlet）：
  一个请求 → 受限于 Tomcat 线程池（200 线程）
  → 后端慢 → 一个线程被阻塞 → 200 并发就满了

Gateway（基于 Netty + Reactor 异步非阻塞）：
  一个请求 → 不占线程（只需少量 event loop 线程）
  → 后端慢 → 不阻塞网关线程 → 轻松处理 10000+ 并发连接

核心流程：
  ① Netty Server 接收请求 → 组装 ServerHttpRequest/Response
  ② RoutePredicateHandlerMapping 匹配路由
  ③ FilteringWebHandler 构建过滤器链
  ④ Netty HttpClient 异步转发到后端
  ⑤ 异步等待后端响应 → 继续处理后置 Filter → 返回
```

**五、自定义 GlobalFilter**

```java
@Component
@Order(-1)  // 数值越小，优先级越高
public class AuthGlobalFilter implements GlobalFilter, Ordered {

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        ServerHttpRequest request = exchange.getRequest();
        
        // ① 白名单路径跳过认证
        String path = request.getURI().getPath();
        if (path.startsWith("/api/auth/login") || path.startsWith("/api/public")) {
            return chain.filter(exchange);  // 直接放行
        }
        
        // ② 从请求头提取 Token
        String token = request.getHeaders().getFirst("Authorization");
        if (StringUtils.isEmpty(token)) {
            ServerHttpResponse response = exchange.getResponse();
            response.setStatusCode(HttpStatus.UNAUTHORIZED);
            return response.setComplete();  // 直接返回 401
        }
        
        // ③ 验证 Token → 解析用户信息 → 写入请求头
        try {
            UserInfo user = JwtUtil.parseToken(token);
            ServerHttpRequest newRequest = request.mutate()
                .header("X-User-Id", user.getUserId())
                .header("X-User-Name", URLEncoder.encode(user.getUserName(), "UTF-8"))
                .build();
            
            return chain.filter(exchange.mutate().request(newRequest).build());
        } catch (Exception e) {
            ServerHttpResponse response = exchange.getResponse();
            response.setStatusCode(HttpStatus.UNAUTHORIZED);
            return response.setComplete();
        }
    }
    
    @Override
    public int getOrder() {
        return -1;  // 数字越小优先级越高
    }
}
```

**六、Sentinel 集成 — 三大防护体系**

Sentinel 是阿里开源的流量防卫兵，核心能力：**流控、熔断、降级**。

```
Sentinel 工作原理：

  资源调用 → Entry（SphU.entry("资源名")）
    │
    ├── 1. 流控规则检查（FlowRule）
    │      ├── QPS 超过阈值？→ BlockException
    │      ├── 线程数超过阈值？→ BlockException
    │      └── 通过 → 继续
    │
    ├── 2. 熔断规则检查（DegradeRule）
    │      ├── 慢调用比例 > 阈值？→ 熔断（OPEN）
    │      ├── 异常比例 > 阈值？→ 熔断（OPEN）
    │      ├── 异常数 > 阈值？→ 熔断（OPEN）
    │      └── 正常 → 继续
    │
    └── 3. 执行被保护的业务逻辑
    
  熔断器状态机：
  CLOSED → 指标超过阈值 → OPEN
  OPEN → 等待熔断时长 → HALF-OPEN
  HALF-OPEN → 试探请求成功 → CLOSED
  HALF-OPEN → 试探请求失败 → OPEN
```

**流控模式对比：**

| 流控模式 | 原理 | 适用场景 |
|---------|------|---------|
| **直接拒绝** | QPS 超限 → 直接抛出异常 | 保护系统不被冲垮 |
| **Warm Up**（预热） | 从阈值 1/3 开始，逐步升到全量 | 防止冷启动被大流量打挂 |
| **匀速排队** | QPS 超限 → 排队等待（不拒） | 需要处理瞬时脉冲流量 |
| **关联流控** | 关联资源超限 → 限制自己 | 支付接口影响商品查询时 |

**三、Redis Lua 脚本 — 原子库存扣减的核心**

这是秒杀系统的灵魂——单机 Redis 可以扛住 10w+ QPS 的库存扣减，关键在于 Lua 脚本保证原子性：

```lua
-- seckill.lua：Redis 库存预减脚本
-- KEYS[1] = 秒杀商品库存 key（如 seckill:stock:123）
-- KEYS[2] = 已购买用户集合 key（如 seckill:users:123）防重复
-- ARGV[1] = 用户 ID
-- ARGV[2] = 限购数量

local stockKey = KEYS[1]
local userKey  = KEYS[2]
local userId   = ARGV[1]
local limit    = tonumber(ARGV[2])

-- ① 检查用户是否已购买（防重复）
local bought = redis.call('SISMEMBER', userKey, userId)
if bought == 1 then
    return -1  -- 已购买，不可重复抢
end

-- ② 检查库存
local stock = tonumber(redis.call('GET', stockKey))
if stock == nil or stock <= 0 then
    return 0   -- 已售罄
end

-- ③ 扣减库存 + 记录用户
redis.call('DECR', stockKey)                        -- 库存 -1
redis.call('SADD', userKey, userId)                 -- 记录用户已购买
redis.call('EXPIRE', userKey, 86400)                -- 24小时过期

return 1  -- 抢购成功
```

```java
// Java 调用 Lua 脚本
@Service
public class SeckillService {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    private final DefaultRedisScript<Long> seckillScript;
    
    public SeckillService() {
        seckillScript = new DefaultRedisScript<>();
        seckillScript.setLocation(new ClassPathResource("lua/seckill.lua"));
        seckillScript.setResultType(Long.class);
    }
    
    /**
     * 执行秒杀
     * @return 1=成功, 0=已售罄, -1=已购买
     */
    public Long doSeckill(Long productId, Long userId) {
        List<String> keys = Arrays.asList(
            "seckill:stock:" + productId,      // KEYS[1]
            "seckill:users:" + productId       // KEYS[2]
        );
        
        Long result = redisTemplate.execute(
            seckillScript,
            keys,
            userId.toString(),
            "1"  // 限购数量
        );
        
        if (result == 1) {
            // 发送下单消息到 MQ（异步）
            rocketMQTemplate.asyncSend("seckill-order", 
                new SeckillMessage(productId, userId), 
                new SendCallback() {
                    @Override
                    public void onSuccess(SendResult result) { /* OK */ }
                    
                    @Override
                    public void onException(Throwable e) {
                        // MQ 发送失败 → 回滚 Redis 库存！
                        rollbackStock(productId, userId);
                    }
                });
        }
        
        return result;
    }
    
    private void rollbackStock(Long productId, Long userId) {
        redisTemplate.opsForValue().increment("seckill:stock:" + productId, 1);
        redisTemplate.opsForSet().remove("seckill:users:" + productId, userId.toString());
    }
}
```

**四、订单号生成 — 雪花算法 + 号段模式**

秒杀场景订单号必须：**全局唯一 + 趋势递增 + 高性能**。

```java
// 雪花算法（Snowflake）— 本地生成，无网络开销
// 格式: 1bit(保留) + 41bit(毫秒) + 10bit(工作机器) + 12bit(序列号)
// 
// 每秒最多生成 4096 × 1000 = 409万个 ID，够用！

public class SnowflakeIdGenerator {
    private final long workerId;
    private final long datacenterId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;
    
    private static final long EPOCH = 1700000000000L;  // 自定义起始时间
    private static final long WORKER_ID_BITS = 5L;
    private static final long DATACENTER_ID_BITS = 5L;
    private static final long SEQUENCE_BITS = 12L;
    
    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis();
        
        // 时钟回拨检测
        if (timestamp < lastTimestamp) {
            throw new RuntimeException("Clock moved backwards!");
        }
        
        if (timestamp == lastTimestamp) {
            sequence = (sequence + 1) & ((1 << SEQUENCE_BITS) - 1);
            if (sequence == 0) {
                // 序列号用完 → 等待下一毫秒
                timestamp = waitNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0L;
        }
        
        lastTimestamp = timestamp;
        
        return ((timestamp - EPOCH) << (WORKER_ID_BITS + DATACENTER_ID_BITS + SEQUENCE_BITS))
             | (datacenterId << (WORKER_ID_BITS + SEQUENCE_BITS))
             | (workerId << SEQUENCE_BITS)
             | sequence;
    }
}
```

**五、最终一致性保障**

**二、EXPLAIN 执行计划 — 12 个关键字段精讲**

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 10086 AND status = 'PAID';
```

| 字段 | 含义 | 重点关注值 |
|------|------|-----------|
| **id** | SELECT 序号 | 相同 id 从上到下执行；不同 id 越大越先执行 |
| **select_type** | 查询类型 | SIMPLE（简单） / PRIMARY（主查询） / SUBQUERY（子查询） / DERIVED（派生表） |
| **table** | 访问的表名 | `<derivedN>` 表示使用了派生表（性能杀手！） |
| **partitions** | 命中分区 | NULL = 未分区 |
| **type** ⭐ | 访问类型（最重要！） | **范围从好到差**：system > const > eq_ref > ref > range > index > ALL |
| **possible_keys** | 可能用到的索引 | NULL = 没有可用索引 |
| **key** ⭐ | 实际使用的索引 | NULL = 未使用索引 → **排查点！** |
| **key_len** | 索引使用长度 | 越大说明联合索引用的列越多 |
| **ref** | 索引列比较的对象 | const（常量）/ 关联表的字段 |
| **rows** ⭐ | 预估扫描行数 | 越小越好，过万需优化 |
| **filtered** | 过滤后行数占比 | 越小说明索引区分度越差 |
| **Extra** ⭐ | 额外信息 | **Using index**（覆盖索引 ✅）/ **Using filesort**（额外排序 ❌）/ **Using temporary**（临时表 ❌）/ **Using where**（回表查询） |

**type 字段详解（面试高频）：**

```
性能排序（从左到右越来越差）：
NULL → system → const → eq_ref → ref → range → index → ALL

  const：主键或唯一索引等值查询，最多返回 1 行 → 最优！
  示例：SELECT * FROM user WHERE id = 1;
  
  eq_ref：联表查询中被驱动表使用主键或唯一索引关联
  示例：SELECT * FROM order o JOIN user u ON o.user_id = u.id;
        → user 表 type = eq_ref
  
  ref：非唯一索引等值查询
  示例：SELECT * FROM user WHERE email = 'abc@test.com';
        → email 有普通索引 → type = ref
  
  range：索引范围扫描（>、<、BETWEEN、IN）
  示例：SELECT * FROM order WHERE create_time > '2026-01-01';
        → type = range
  
  index：全索引扫描（扫描整个索引树）
  示例：SELECT user_id FROM order;  → user_id 有索引 → 只需扫索引树
        比 ALL 好（只扫索引树），但仍慢！
  
  ALL：全表扫描 → 最差！必须优化！
```

**三、索引失效的 11 种常见场景**

```sql
-- 假设：KEY idx_name_age_status (name, age, status)

-- ❌ 1. 最左前缀原则违背

SELECT * FROM user WHERE status = 'A';      -- 跳过了 name 和 age！

-- ❌ 2. 索引列上做函数运算
SELECT * FROM user WHERE YEAR(create_time) = 2026;
-- ✅ 改为：
SELECT * FROM user WHERE create_time >= '2026-01-01' 
                    AND create_time < '2027-01-01';

-- ❌ 3. 索引列上做运算
SELECT * FROM user WHERE age + 1 = 26;
-- ✅ 改为：
SELECT * FROM user WHERE age = 25;

-- ❌ 4. 隐式类型转换
-- phone 是 VARCHAR 类型
SELECT * FROM user WHERE phone = 13800138000;   -- 数字 → MySQL 会先将 phone 转数字！
-- ✅ 改为：
SELECT * FROM user WHERE phone = '13800138000';

-- ❌ 5. LIKE 以 % 开头
SELECT * FROM user WHERE name LIKE '%张三';     -- 左模糊，索引失效！
-- ✅ 改为（如果真的需要）：
SELECT * FROM user WHERE name LIKE '张三%';     -- 右模糊可以走索引

-- ❌ 6. OR 条件中存在非索引列
SELECT * FROM user WHERE name = '张三' OR email = 'abc@test.com';
-- 如果 email 没有索引 → 全表扫描！
-- ✅ 改为 UNION：
SELECT * FROM user WHERE name = '张三'
UNION
SELECT * FROM user WHERE email = 'abc@test.com';  -- email 建索引

-- ❌ 7. NOT IN / != / <> 可能不走索引
SELECT * FROM user WHERE status != 'DELETED';
-- ✅ 如果 status 值很少，强迫走索引：
SELECT * FROM user FORCE INDEX(idx_status) WHERE status != 'DELETED';

-- ❌ 8. IS NULL / IS NOT NULL（取决于数据分布）
-- 如果大部分行都是 NULL → 可能走索引
-- 如果只有少数行是 NULL → 全表扫描

-- ❌ 9. 联合索引中间断档
SELECT * FROM user WHERE name = '张三' AND status = 'A';  -- age 断了 → 只用 name

-- ❌ 10. IN 列表过长
```
