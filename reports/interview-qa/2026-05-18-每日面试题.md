## 题目 1：[缓存/Redis] 请详细解释 Redis 缓存穿透、缓存击穿、缓存雪崩的区别，并结合实际代码说明各自的完整解决方案

**难度**：⭐⭐⭐⭐
**考点来源**：2026-05-18 早间报告 — "Redis缓存治理（高频考点）：穿透（布隆过滤器+缓存空值）、击穿（互斥锁+逻辑过期+热点永不过期）、雪崩（TTL随机抖动+多级缓存+限流降级）"  
**相关岗位**：Java后端 / 高并发系统开发 / 电商

### 📖 参考答案

**一、三者的本质区别**

```
口诀：穿透是假请求，击穿是真热门，雪崩是集体挂！

缓存穿透：查询不存在的数据（缓存没有，数据库也没有）
           → 每次请求都穿透缓存直达数据库

缓存击穿：热点数据缓存刚好过期，瞬间大量请求打到数据库
           → 同一时刻对一个 key 的并发冲击

缓存雪崩：大量缓存同时过期或 Redis 宕机
           → 大面积 key 失效导致数据库被压垮
```

**二、缓存穿透详解与解决方案**

**问题本质**：攻击者或异常请求查询根本不存在的数据（如 id=-1、随机 UUID），缓存中没有，数据库中也没有，每次请求都打到数据库。

```
正常请求：Client → Redis(✅命中) → 返回
穿透请求：Client → Redis(❌未命中) → DB(❌也没有) → 每次都查DB！
```

**方案一：缓存空值（最简单有效）**

```java
public User getUserById(Long userId) {
    String cacheKey = "user:" + userId;
    
    // 1. 查缓存
    String cached = redisTemplate.opsForValue().get(cacheKey);
    if (cached != null) {
        // 判断是否为空值标记
        if ("NULL".equals(cached)) {
            return null;  // 直接返回，不查数据库
        }
        return JSON.parseObject(cached, User.class);
    }
    
    // 2. 查数据库
    User user = userMapper.selectById(userId);
    
    if (user != null) {
        // 正常数据：缓存较长时间
        redisTemplate.opsForValue().set(cacheKey, JSON.toJSONString(user), 
                                         30, TimeUnit.MINUTES);
    } else {
        // 空值也缓存，但TTL要短（防止占用过多内存）
        redisTemplate.opsForValue().set(cacheKey, "NULL", 
                                         60, TimeUnit.SECONDS);
    }
    return user;
}
```

```java
public class BloomFilterGuard {

// ✅ 判断"不存在"一定准确 → 可以安全拦截非法请求
```

**穿透方案对比：**

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| 缓存空值 | 实现简单、零依赖 | 空值占内存（需短TTL） | key 空间有限 |
| 布隆过滤器 | 内存效率高 | 有误判率、不支持删除 | 大量可能存在的key |

**三、缓存击穿详解与解决方案**

**问题本质**：一个热点 key（如秒杀商品、热门新闻），在过期瞬间有大量并发请求同时查询，全部打到数据库。

```
时间线：
  T0: 热点 key "hot:product:100" 在 Redis 中有效
  T1: key 刚好过期！
  T2: 10000 个并发请求同时查这个 key → Redis 未命中 → 全部去打 DB！
  → 数据库瞬间压力爆表 💥
```

**方案一：互斥锁（最常用）**

```java
public Product getHotProduct(Long productId) {
    String cacheKey = "hot:product:" + productId;
    
    // 1. 先查缓存
    String cached = redisTemplate.opsForValue().get(cacheKey);
    if (cached != null) {
        return JSON.parseObject(cached, Product.class);
    }
    
    // 2. 缓存未命中 → 加分布式锁重建缓存
    String lockKey = "lock:product:" + productId;
    String lockValue = UUID.randomUUID().toString();
    
    try {
        // 尝试获取锁（setnx + 过期时间，原子操作）
        Boolean locked = redisTemplate.opsForValue()
            .setIfAbsent(lockKey, lockValue, 10, TimeUnit.SECONDS);
        
        if (Boolean.TRUE.equals(locked)) {
            // 获取锁成功 → 查 DB 重建缓存
            Product product = productMapper.selectById(productId);
            if (product != null) {
                // 设置随机过期时间（避免下次集中过期）
                int ttl = 30 * 60 + ThreadLocalRandom.current().nextInt(300);
                redisTemplate.opsForValue().set(cacheKey, 
                    JSON.toJSONString(product), ttl, TimeUnit.SECONDS);
            } else {
                // 缓存空值防穿透
                redisTemplate.opsForValue().set(cacheKey, "NULL", 
                    60, TimeUnit.SECONDS);
            }
            return product;
        } else {
            // 没抢到锁 → 等一会儿重试
            Thread.sleep(50);
            // 递归重试（此时缓存大概率已重建好）
            return getHotProduct(productId);
        }
    } finally {
        // 释放锁（用 Lua 脚本保证原子性：判断 value 匹配才删除）
        String script = "if redis.call('get',KEYS[1]) == ARGV[1] then " +
                        "return redis.call('del',KEYS[1]) else return 0 end";
        redisTemplate.execute(
            new DefaultRedisScript<>(script, Long.class),
            Collections.singletonList(lockKey), lockValue);
    }
}
```

**方案二：逻辑过期（热点永不过期 + 异步更新）**

```java
// 定义带逻辑过期时间的数据包装类
public class LogicalExpireData<T> {
    private T data;
    private long expireTime;  // 逻辑过期时间戳
}

public Product getHotProductLogical(Long productId) {
    String cacheKey = "hot:product:" + productId;
    LogicalExpireData<Product> cached = getFromRedis(cacheKey);
    
    // 缓存未命中 → 直接返回 null（热点key应预热，不应出现此情况）
    if (cached == null) return null;
    
    // 判断是否逻辑过期
    if (cached.getExpireTime() > System.currentTimeMillis()) {
        return cached.getData();  // 未过期，直接返回
    }
    
    // 逻辑过期 → 获取锁异步更新
    String lockKey = "lock:product:" + productId;
    if (tryLock(lockKey)) {
        // 开启独立线程异步更新缓存（不阻塞当前请求！）
        threadPoolExecutor.submit(() -> {
            Product product = productMapper.selectById(productId);
            LogicalExpireData<Product> newData = new LogicalExpireData<>();
            newData.setData(product);
            newData.setExpireTime(System.currentTimeMillis() + 30 * 60 * 1000);
            saveToRedis(cacheKey, newData);  // 永不过期（Redis层面不设TTL）
            unlock(lockKey);
        });
    }
    
    // 返回旧数据（宁可返回旧数据，也不能让请求直接打到DB）
    return cached.getData();
}
```

**四、缓存雪崩详解与解决方案**

**问题本质**：大量 key 同时过期，或 Redis 服务宕机，导致所有请求打到数据库。

```
雪崩的两个触发场景：

场景一：批量设置缓存用了相同的 TTL
  → 100个热门商品的缓存都设了 30 分钟过期
  → 30 分钟后同时失效 → 全部请求涌向 DB 💥

场景二：Redis 集群/实例宕机
  → 所有缓存瞬间不可用
  → 流量全部打到数据库 💥
```

```java
// 方案一：过期时间加随机值（最简单、最有效）
public void setWithRandomTTL(String key, Object value, int baseTTLSeconds) {
    // 在基础 TTL 上添加随机因子（如 ±20%）
    int randomDelta = ThreadLocalRandom.current()
        .nextInt(baseTTLSeconds / 5);  // ±20%
    int actualTTL = baseTTLSeconds + randomDelta;
    redisTemplate.opsForValue().set(key, value, actualTTL, TimeUnit.SECONDS);
}

// 方案二：多级缓存（本地缓存 + Redis + DB）
// Caffeine 本地缓存作为 Redis 的前置缓存
@Configuration
public class MultiLevelCacheConfig {
    
    @Bean
    public Cache<String, Object> localCache() {
        return Caffeine.newBuilder()
            .maximumSize(10_000)           // 最多缓存 1 万条
            .expireAfterWrite(5, TimeUnit.MINUTES)  // 5 分钟过期
            .recordStats()                 // 开启统计
            .build();
    }
}

@Service
public class MultiLevelCacheService {
    
    private Cache<String, Object> localCache;  // Caffeine
    private RedisTemplate redisTemplate;
    
    public Object get(String key) {
        // L1: 本地缓存（JVM 内，速度最快）
        Object value = localCache.getIfPresent(key);
        if (value != null) return value;
        
        // L2: Redis（网络IO，速度次之）
        value = redisTemplate.opsForValue().get(key);
        if (value != null) {
            localCache.put(key, value);  // 回填 L1
            return value;
        }
        
        // L3: 数据库
        value = queryDB(key);
        if (value != null) {
            redisTemplate.opsForValue().set(key, value, 
                30 + ThreadLocalRandom.current().nextInt(10), TimeUnit.MINUTES);
            localCache.put(key, value);
        }
        return value;
    }
}

// 方案三：限流降级（Resilience4j 兜底）
// 当缓存全部失效时，对数据库请求做限流，保护DB
@RateLimiter(name = "dbRateLimiter", fallbackMethod = "dbFallback")

    return queryDB(key);
}

    // 限流触发时返回默认值或友好提示
    return "系统繁忙，请稍后重试";
}
```

**五、三大问题终极对比表**

| 维度 | 缓存穿透 | 缓存击穿 | 缓存雪崩 |
|------|---------|---------|---------|
| **原因** | 查不存在的数据 | 热点key过期 + 并发 | 大量key同时过期 / Redis宕机 |
| **影响范围** | 特定不存在的key | 单个热点key | 大范围key |
| **数据库压力** | 持续性的 | 瞬间尖刺 | 全面冲击 |
| **核心方案** | 布隆过滤器 + 缓存空值 | 互斥锁 + 逻辑过期 | TTL随机化 + 多级缓存 |
| **难度** | ⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ |
| **面试频率** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |

### 💡 延伸思考

1. **布隆过滤器的数据删除了怎么办？** — 标准布隆过滤器不支持删除。解决方案：① 计数布隆过滤器（Counting Bloom Filter），对每个 bit 位改为计数器，删除时计数器减 1；② 布谷鸟过滤器（Cuckoo Filter），原生支持删除，Redis 7.0+ 通过 RedisBloom 模块支持。
2. **Redis 集群模式下互斥锁（setnx）会有什么问题？** — 主从切换时锁可能丢失（主节点宕机，从节点提升但锁数据未同步）。解决方案：Redisson 的 RedLock 算法（向 N 个独立 Redis 实例加锁，半数以上成功才算加锁成功）。

### 📖 参考答案

**一、为什么需要线程池？**

```
问题：每个请求都 new Thread() 会怎样？
  → 线程创建/销毁开销大（栈内存分配、上下文切换）
  → 线程数不可控 → 高并发时 OOM
  → 线程管理混乱

线程池的价值：
  ① 复用线程：降低创建/销毁开销
  ② 控制并发数：防止资源耗尽
  ③ 任务队列：削峰填谷
  ④ 线程管理：统一监控和调优
```

**二、ThreadPoolExecutor 七大核心参数**

```java
public ThreadPoolExecutor(
    int corePoolSize,          // ① 核心线程数
    int maximumPoolSize,       // ② 最大线程数
    long keepAliveTime,        // ③ 空闲线程存活时间
    TimeUnit unit,             // ④ 时间单位
    BlockingQueue<Runnable> workQueue,  // ⑤ 工作队列
    ThreadFactory threadFactory,       // ⑥ 线程工厂
    RejectedExecutionHandler handler   // ⑦ 拒绝策略
)
```

| 参数 | 含义 | 关键理解 |
|------|------|---------|
| **corePoolSize** | 核心线程数（常驻线程） | 即使空闲也不会被回收（除非设置 allowCoreThreadTimeOut） |
| **maximumPoolSize** | 最大线程数 | = 核心线程 + 临时线程的最大值 |
| **keepAliveTime** | 临时线程空闲存活时间 | 只有临时线程超此时间被回收，核心线程不受影响 |
| **unit** | keepAliveTime 的时间单位 | TimeUnit.SECONDS / MILLISECONDS 等 |
| **workQueue** | 任务等待队列（阻塞队列） | 核心线程满时新任务进队列；队列满时创建临时线程 |
| **threadFactory** | 线程创建工厂 | 可自定义线程名、是否为守护线程、优先级等 |
| **handler** | 拒绝策略 | 线程池 + 队列都满时，新任务的处理方式 |

**三、任务提交执行流程（面试必画！）**

```
新任务提交到线程池后：

  ┌─────────────────────────────────┐
  │         execute(task)            │
  └────────────┬────────────────────┘
               ↓
       ┌───────────────┐
       │ 核心线程满了？   │
       └───┬───────┬───┘
           │NO     │YES
           ↓       ↓
    ┌──────────┐ ┌──────────────┐
    │ 创建核心   │ │ 工作队列满了？  │
    │ 线程执行   │ └──┬───────┬──┘
    └──────────┘    │NO     │YES
                    ↓       ↓
             ┌──────────┐ ┌──────────────┐
             │ 任务入队   │ │ 最大线程满了？ │
             │ 等待执行   │ └──┬───────┬──┘
             └──────────┘    │NO     │YES
                             ↓       ↓
                      ┌──────────┐ ┌──────────┐
                      │ 创建临时   │ │ 执行拒绝   │
                      │ 线程执行   │ │ 策略！     │
                      └──────────┘ └──────────┘

核心逻辑摘要：
  ① 线程数 < corePoolSize → 创建新线程（即使有空闲核心线程）
  ② 线程数 ≥ corePoolSize → 任务入队列
  ③ 队列满 && 线程数 < maximumPoolSize → 创建临时线程
  ④ 队列满 && 线程数 = maximumPoolSize → 执行拒绝策略
```

**关键源码逻辑（execute 方法）：**

```java
public void execute(Runnable command) {
    int c = ctl.get();
    // Step 1: 当前线程数 < 核心线程数 → 直接创建核心线程
    if (workerCountOf(c) < corePoolSize) {
        if (addWorker(command, true)) return;
        c = ctl.get();  // 创建失败，重新检查状态
    }
    // Step 2: 线程数 ≥ 核心线程数 → 尝试入队列
    if (isRunning(c) && workQueue.offer(command)) {
        int recheck = ctl.get();
        // 二次检查：如果线程池刚好关闭，从队列中移除任务并拒绝
        if (!isRunning(recheck) && remove(command))
            reject(command);
        // 如果工作线程数为0，创建一个非核心线程兜底
        else if (workerCountOf(recheck) == 0)
            addWorker(null, false);
    }
    // Step 3: 队列满了 → 尝试创建临时线程
    else if (!addWorker(command, false))
        // Step 4: 临时线程也创建失败（已达 max） → 拒绝！
        reject(command);
}
```

**四、四种拒绝策略**

| 策略 | 行为 | 适用场景 |
|------|------|---------|
| **AbortPolicy**（默认） | 抛出 RejectedExecutionException | 需要感知任务被拒绝，通常配合监控告警 |
| **CallerRunsPolicy** | 由提交任务的线程自己执行 | 既不想丢任务，又能自然降速（调用者线程被占用后会阻塞提交） |
| **DiscardPolicy** | 直接丢弃，不抛异常 | 允许丢任务的场景（如非关键日志上报） |
| **DiscardOldestPolicy** | 丢弃队列中最旧的任务，重新提交新任务 | 优先处理最新任务 |

```java
// 自定义拒绝策略：记录日志 + 告警
public class LogAndAlertPolicy implements RejectedExecutionHandler {
    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
        // 1. 记录日志
        log.error("任务被拒绝！当前线程数={}, 队列大小={}, 已完成任务={}",
            executor.getPoolSize(),
            executor.getQueue().size(),
            executor.getCompletedTaskCount());
        
        // 2. 发送告警（企业微信/钉钉/邮件）
        alertService.send("线程池繁忙", executor.toString());
        
        // 3. 兜底处理（写入持久化队列，后续重试）
        fallbackQueue.offer(r);
    }
}
```

**五、为什么禁止使用 Executors 工厂方法？**

阿里巴巴 Java 开发手册明确规定：

```java
// ❌ 禁止！
ExecutorService pool1 = Executors.newFixedThreadPool(10);
ExecutorService pool2 = Executors.newCachedThreadPool();
ExecutorService pool3 = Executors.newSingleThreadExecutor();
ExecutorService pool4 = Executors.newScheduledThreadPool(5);

// ✅ 正确！手动通过 ThreadPoolExecutor 构造
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    10,                          // corePoolSize
    20,                          // maximumPoolSize
    60L, TimeUnit.SECONDS,       // keepAlive
    new LinkedBlockingQueue<>(1000),  // 有界队列！
    new ThreadFactoryBuilder().setNameFormat("biz-pool-%d").build(),
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

禁止原因：

| 工厂方法 | 风险 | 原因 |
|---------|------|------|
| `newFixedThreadPool` / `newSingleThreadExecutor` | **OOM 风险** | 使用的 `LinkedBlockingQueue` 默认容量 = `Integer.MAX_VALUE`（约 21 亿），任务堆积会撑爆内存 |
| `newCachedThreadPool` | **CPU 100%** | `maximumPoolSize = Integer.MAX_VALUE`，每个任务创建线程，高并发下瞬间创建数万线程 |
| `newScheduledThreadPool` | **OOM 风险** | 同 Fixed，队列无界 |

**六、生产环境线程池参数配置公式**

```
① CPU 密集型任务（计算为主，几乎没有 IO 等待）：
   corePoolSize = CPU 核数 + 1
  
   → 原因：CPU 密集型任务线程一直在计算，多线程切换反而降低效率
   → 核数 + 1 是为了某线程偶尔因缺页中断暂停时另一个能顶上

② IO 密集型任务（数据库查询、RPC 调用、网络 IO）：
   corePoolSize = CPU 核数 × 2
   
   更精确的公式（考虑 IO 等待时间）：
   最佳线程数 = CPU 核数 × (1 + 平均等待时间 / 平均计算时间)
   
   例如：CPU 核数 8，任务中 70% 时间在等数据库，30% 时间计算
        → 8 × (1 + 0.7/0.3) = 8 × 3.33 ≈ 26 线程

③ 混合型任务：
   核心业务线程池 + 普通线程池分离
   → 核心池：线程少（≤CPU核数），任务少，响应快
   → 普通池：线程多，用于异步日志/通知等非核心任务
```

**七、线程池监控（生产必备）**

```java
@Component
public class ThreadPoolMonitor {
    
    @Scheduled(fixedDelay = 10000)  // 每 10 秒采集一次
    public void monitor() {
        ThreadPoolExecutor pool = (ThreadPoolExecutor) executor;
        
        ThreadPoolMetrics metrics = ThreadPoolMetrics.builder()
            .corePoolSize(pool.getCorePoolSize())
            .maximumPoolSize(pool.getMaximumPoolSize())
            .activeCount(pool.getActiveCount())       // 当前活跃线程
            .poolSize(pool.getPoolSize())             // 当前线程数
            .queueSize(pool.getQueue().size())        // 队列中等待的任务数
            .completedTaskCount(pool.getCompletedTaskCount())
            .taskCount(pool.getTaskCount())           // 总任务数
            .largestPoolSize(pool.getLargestPoolSize()) // 历史最大线程数
            .build();
        
        // 告警规则
        if (metrics.getQueueSize() > 1000) {
            alert("线程池队列堆积！queueSize=" + metrics.getQueueSize());
        }
        if (metrics.getActiveCount() >= metrics.getMaximumPoolSize()) {
            alert("线程池满载！activeCount=" + metrics.getActiveCount());
        }
        
        // 上报到 Prometheus / Grafana
        meterRegistry.gauge("threadpool.active", metrics.getActiveCount());
        meterRegistry.gauge("threadpool.queue.size", metrics.getQueueSize());
    }
}
```

### 💡 延伸思考

1. **`execute()` 和 `submit()` 的区别？** — `execute()` 提交 Runnable，无返回值，异常会直接抛出；`submit()` 提交 Callable/Runnable，返回 Future，异常被封装在 Future 中（调用 `future.get()` 时才抛出 ExecutionException）。推荐核心业务用 `submit()` 以便捕获异常。
2. **核心线程数设置成 0 可以吗？** — 可以。`corePoolSize=0` + 有界队列（如 SynchronousQueue）+ `maximumPoolSize>0`，效果是所有线程都是临时线程，空闲时全回收。但生产不推荐，因为第一个任务来时必须等待线程创建，有冷启动延迟，且通过 `Executors.newCachedThreadPool()` 创建的正是这种配置，队列无界极易 OOM。

**一、为什么需要熔断和降级？—— 服务雪崩的起因**

```
┌──────────────────────────────────────────────┐
│            服务雪崩（Cascading Failure）        │
│                                              │
│  Gateway ──→ Service A ──→ Service B ──→ DB  │
│                              │               │
│                              ↓ (B 挂了)       │
│  Gateway ──→ Service A ──→ Service B ❌       │
│                │                             │
│                ↓ (A 的线程全卡在等 B)           │
│  Gateway ──→ Service A ❌ (A 也挂了)           │
│                │                             │
│                ↓ (Gateway 超时)               │
│  Gateway ❌ 整个链路瘫痪！                     │
└──────────────────────────────────────────────┘

熔断器的作用：在 B 出现问题时，A 快速失败（fail-fast），
不阻塞自己的线程，阻止雪崩扩散。
```

**三、熔断器（CircuitBreaker）—— 三种状态转换**

```
                 ┌─────────────────┐
                 │     CLOSED      │  正常状态：请求正常通过
                 │   (熔断关闭)     │
                 └────────┬────────┘
                          │ 失败率 > threshold
                          ↓
                 ┌─────────────────┐
                 │      OPEN       │  熔断状态：所有请求直接拒绝
                 │   (熔断打开)     │  快速失败，不调用下游
                 └────────┬────────┘
                          │ 等待 waitDurationInOpenState
                          ↓
                 ┌─────────────────┐
                 │   HALF_OPEN     │  半开状态：允许少量探测请求
                 │   (熔断半开)     │
                 └──┬──────────┬───┘
                    │          │
            探测成功 │          │ 探测失败
                    ↓          ↓
              CLOSED          OPEN
             (恢复正常)      (继续熔断)

状态转换关键参数：
  → slidingWindowSize=10：基于最近 10 次请求判断
  → failureRateThreshold=50：失败率超过 50% 则 OPEN
  → waitDurationInOpenState=10s：OPEN 状态持续 10s 后 → HALF_OPEN
  → permittedNumberOfCallsInHalfOpenState=3：半开时允许 3 次探测请求
  → 3 次探测成功 → CLOSED；3 次中有失败 → 回 OPEN
```

**滑动窗口算法（两种类型）：**

```
① COUNT_BASED（基于请求次数）：
  窗口 = 最近 N 次请求
  例如 slidingWindowSize=10
  → 统计最近 10 次请求的失败率
  → 简单、开销低，适合 QPS 稳定的场景

② TIME_BASED（基于时间）：
  窗口 = 最近 N 秒内的所有请求
  例如 slidingWindowSize=60（秒）
  → 统计最近 60 秒内所有请求的失败率
  → 能更准确地反映"当前"系统状态
  → 适合 QPS 波动大的场景（推荐！）
```

```java
@FeignClient(name = "inventory-service", 
             fallbackFactory = InventoryFallbackFactory.class)
public interface InventoryClient {
    
    @GetMapping("/inventory/{productId}")
    InventoryResponse getInventory(@PathVariable Long productId);
}

// 降级工厂（推荐方式：可获取异常信息）
@Component
public class InventoryFallbackFactory implements FallbackFactory<InventoryClient> {
    @Override
    public InventoryClient create(Throwable cause) {
        log.error("库存服务调用失败，触发降级", cause);
        
        return new InventoryClient() {
            @Override
            public InventoryResponse getInventory(Long productId) {
                // 降级逻辑：返回默认库存或缓存数据
                if (cause instanceof CallNotPermittedException) {
                    log.warn("熔断器 OPEN，直接降级！");
                }
                return InventoryResponse.builder()
                    .productId(productId)
                    .stock(-1)  // 降级标记
                    .message("库存服务暂不可用，请稍后重试")
                    .build();
            }
        };
    }
}

// 也可以在 Controller 层使用注解方式
@RestController
public class OrderController {
    
    @Autowired
    private InventoryClient inventoryClient;
    
    @GetMapping("/order/check/{productId}")
    @CircuitBreaker(name = "inventory", fallbackMethod = "inventoryFallback")
    @Retry(name = "inventory")  // 熔断里面套重试（先重试，重试多次失败才熔断）
    public OrderCheckResult checkStock(@PathVariable Long productId) {
        InventoryResponse inv = inventoryClient.getInventory(productId);
        return OrderCheckResult.from(inv);
    }
    
    public OrderCheckResult inventoryFallback(Long productId, Throwable e) {
        return OrderCheckResult.builder()
            .available(false)
            .reason("库存服务暂时不可用: " + e.getMessage())
            .build();
    }
}
```

**四、Bulkhead（舱壁隔离）—— 线程池 vs 信号量**

```
比喻：船舱分多个隔间，一个隔间进水不影响其他隔间。

Bulkhead 确保：一个下游服务出问题只占用分配给它的资源，
不会耗尽整个服务的线程。
```

| 隔离方式 | 实现原理 | 优点 | 缺点 |
|---------|---------|------|------|
| **线程池隔离** | 每个下游服务分配独立线程池 | 完全隔离，一个服务线程池满了不影响其他 | 线程切换开销，内存占用大 |
| **信号量隔离** | 用 Semaphore 限制并发数 | 轻量级，无线程切换开销 | 不隔离超时（一个慢调用可能一直占着信号量） |

```yaml
# 线程池隔离：为库存服务分配独立线程池
resilience4j:
  thread-pool-bulkhead:
    instances:
      inventoryService:
        maxThreadPoolSize: 10    # 最多 10 个线程处理库存请求
        coreThreadPoolSize: 5    # 核心 5 个线程
        queueCapacity: 20        # 等待队列 20
        keepAliveDuration: 60s

# 信号量隔离：简单限制并发数
resilience4j:
  bulkhead:
    instances:
      inventoryService:
        maxConcurrentCalls: 10   # 同时最多 10 个并发
        maxWaitDuration: 100ms   # 超过 10 后最多等 100ms
```

**选型建议**：信号量隔离适合大多数场景（轻量）；线程池隔离适合需要完全隔离的场景（如第三方不可靠的 API）。

**六、配置最佳实践**

```
① 重试：仅对幂等操作使用！
  ✅ GET 请求 → 可以重试
  ✅ PUT（幂等更新）→ 可以重试
  ❌ POST（非幂等创建）→ 不重试！可能重复创建订单！

② 超时配置：金字塔模型
  Gateway 超时 > Service A 超时 > Service B 超时
  例如：Gateway 30s → Service A 10s → Service B 5s
  → 确保下游先超时，上游才能做出正确的降级决策

③ 熔断和重试的组合：
  熔断器中内嵌重试 → 先重试 N 次，N 次都失败才计入熔断统计
  → 避免偶发网络抖动触发熔断

④ 降级策略的降级：
  本地缓存 → Redis → 默认值 → 错误提示 → 限流兜底
  每一层都可以降级到下一层
```

**一、RAG 是什么？为什么需要它？**

RAG（Retrieval-Augmented Generation，检索增强生成）是当前 LLM 应用最主流的技术架构，核心思想：**在 LLM 生成回答之前，先从外部知识库中检索相关信息，注入到 Prompt 中**。

```
没有 RAG 的 LLM：
  用户："公司最新的请假流程是什么？"
  LLM：根据训练数据编一个 → ❌ 可能过时或不准确

有了 RAG 的 LLM：
  用户："公司最新的请假流程是什么？"
  ↓
  ① 检索（Retrieve）：从公司文档库中找到《请假制度v3.2》
  ↓
  ② 增强（Augment）：将文档片段插入 Prompt
     "请根据以下公司文档回答：{检索到的文档内容} \n 用户问题：..."
  ↓
  ③ 生成（Generate）：LLM 基于真实文档生成答案
  ↓
  用户收到基于真实文档的准确回答 ✅
```

**RAG 解决的四大问题：**

| LLM 缺陷 | RAG 如何解决 |
|---------|------------|
| 知识截止（训练数据过时） | 实时检索外部知识库 |
| 幻觉（一本正经胡说八道） | 基于真实检索结果生成 |
| 上下文限制（Token 窗口有限） | 只检索最相关的片段 |
| 领域专业知识不足 | 外挂垂直领域知识库 |

**三、文档分段策略（Chunking）—— RAG 最关键的一步**

分段质量直接决定检索质量。分太大 → 噪声多、不精准；分太小 → 语义不完整。

| 策略 | 做法 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **固定长度** | 按 N 个 token/字符切分 | 简单、快速 | 可能切断句子语义 | 初步实验 |
| **语义分段** | 按句子边界+语义相似度切分 | 保持语义完整性 | 实现复杂 | 长文档 |
| **递归分割** | 按段落→句子→词逐级切分 | 自适应文档结构 | 可能产生不均匀chunk | 通用场景⭐推荐 |
| **小大窗口** | 小块检索 + 大块返回（检索用小块，LLM看大块上下文） | 精准+完整兼得 | 存储冗余 | 需要完整上下文的场景 |
| **标题感知** | 将标题信息附加到每个 chunk | 保留文档结构信息 | 需要文档有清晰标题 | 结构化文档 |

```python
# 递归分割示例（LangChain RecursiveCharacterTextSplitter）
from langchain.text_splitter import RecursiveCharacterTextSplitter

text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,        # 每块 500 字符
    chunk_overlap=50,      # 块间重叠 50 字符（防止切断关键语义）
    separators=["\n\n", "\n", "。", ".", " ", ""],  # 递归分隔符
    length_function=len,
)

chunks = text_splitter.split_text(document)

# chunk_overlap 的作用：
# Chunk 1: "...数据库连接池的大小需要根据"
# Chunk 2: "据库连接池的大小需要根据业务场景配置..."
# ← 重叠部分保证"数据库连接池"不会被切成两块！
```

**分段大小建议：**
- 问答场景：256-512 token
- 长文档摘要：1024-2048 token
- 代码检索：按函数/类级别分段

**六、Rerank 重排序 —— 提升 RAG 质量的关键**

```
为什么需要 Rerank？

向量检索（粗排）：
  用 Embedding 计算语义相似度，速度快但精度不够
  
Rerank（精排）：
  用专门的 Cross-Encoder 模型对粗排结果逐一打分，精度高但速度慢

粗排 + 精排 两阶段架构：
  向量检索 Top-100 → Rerank 精排 → 取 Top-5 给 LLM
  ↑ 快但粗糙               ↑ 慢但精准     ↑ 最终效果最好！
```

| Rerank 模型 | 特点 |
|------------|------|
| **BGE-reranker-v2-m3** (BAAI) | 多语言，适合中文场景 ⭐ |
| **Cohere Rerank v3** | 商业最好，效果 SOTA |
| **bge-reranker-large** | 开源中文最佳 |
| **Jina Reranker v2** | 多语言，支持长文本 |

```java
// Spring AI Rerank 示例
@Bean
public DocumentRetriever retriever(VectorStore vectorStore) {
    return VectorStoreDocumentRetriever.builder()
        .vectorStore(vectorStore)
        .topK(20)              // 粗排取 Top-20
        .similarityThreshold(0.5)
        .build();
}

// RAG 完整链路（含 Rerank）
public String advancedQuery(String question) {
    // ① 粗排：向量检索 Top-20
    List<Document> candidates = vectorStore.similaritySearch(
        SearchRequest.query(question).withTopK(20)
    );
    
    // ② 精排：Rerank 后取 Top-5
    // Spring AI 可通过 Cohere/Transformers 等实现 Rerank
    List<Document> reranked = rerankModel.rerank(question, candidates, 5);
    
    // ③ 生成
    return generateWithContext(question, reranked);
}
```

**七、降低幻觉的五大策略**

```
① 高质量知识库：文档清洗、去除噪声、结构化处理
② Prompt 约束："如果参考资料中没有相关信息，请直接说明"
③ Rerank 重排序：确保给 LLM 的是最相关的文档
④ 强制引用：要求 LLM 在答案中标注来源段落
⑤ 输出校验：用规则/NLI模型验证答案是否与检索文档一致
```

### 💡 延伸思考

1. **RAG vs Fine-tuning 怎么选？** — RAG 是给 LLM 配顾问（动态、可控、可更新），Fine-tuning 是让 LLM 去上学（内化知识、适合固定风格/格式）。生产推荐"RAG 为主 + Fine-tuning 为辅"：RAG 处理动态领域知识，Fine-tuning 优化模型对特定格式/风格的输出。
2. **RAG 的评测指标有哪些？** — ① 检索质量：Hit Rate、MRR（Mean Reciprocal Rank）、NDCG；② 生成质量：Faithfulness（答案是否忠实于检索文档）、Answer Relevance（答案是否切题）、Context Relevance（检索到的文档是否相关）。RAGAS 框架是目前最流行的 RAG 评估工具。

### 📖 参考答案

**一、MCP 解决了什么核心问题？**

在 MCP 出现之前，每个 AI 应用集成工具的方式都不同：

```
传统方式：N 个模型 × M 个工具 = N×M 个适配器

  ChatGPT ──→ 自定义插件系统
  Claude  ──→ 自定义工具系统
  Gemini  ──→ 自定义扩展系统

每次换个模型就要重写所有工具集成代码！😱
```

```
MCP 方式：1 个标准协议，所有模型和工具互联

  所有 LLM ←→ MCP 协议 ←→ 所有工具
  (Claude、GPT、Gemini...)    (数据库、API、文件系统...)

一次开发 MCP Server，所有支持 MCP 的 AI 应用都能直接复用！✅
```

MCP 的全称 Model Context Protocol，由 Anthropic 于 2024 年 11 月发布，2025 年捐赠给 Linux 基金会，现已成为行业标准。

**二、MCP 的 Client-Server 分层架构**

```
┌────────────────────────────────────────────────────┐
│              MCP 架构（Client — Server）              │
│                                                    │
│  ┌──────────────────┐    ┌──────────────────────┐  │
│  │  MCP Host        │    │  MCP Server (工具端)   │  │
│  │  (如 Claude Code │    │                      │  │

│  │                  │    │  │ (文件、数据库    │  │  │
```

**三、MCP 四大核心能力**

```
① Resources（资源） — "给模型看什么数据"
   把文件、数据库记录、API响应等暴露为可读取的资源
   例如：file://documents/请假制度.md、postgres://users/table
   
   模型可以：读取资源内容、列出可用资源、订阅资源变更

② Prompts（提示模板） — "给模型提供什么模板"
   预定义的提示词模板，支持参数化
   例如："请根据 {company_policy} 回答用户的请假问题"
   
   模型可以：获取 Prompt 列表、使用指定模板

③ Tools（工具） — "模型可以做什么"
   模型可以调用的功能，如查询数据库、发送邮件、执行计算
   这是 MCP 最核心的能力！
   
   模型可以：列出可用工具 → 按需调用 → 接收结果

④ Sampling（采样） — "Server 反向请求 LLM"
   允许 MCP Server 在需要时请求 LLM 生成内容
   例如：Agent 在处理任务时，遇到不确定性可以请求 LLM 帮助决策
```

**四、MCP 工作流程（以 Tool 调用为例）**

```python
# MCP Server 端（Python 示例）
from mcp.server import Server, stdio_server
from mcp.types import Tool, TextContent

server = Server("database-server")

@server.list_tools()
async def list_tools():
    """声明该 Server 提供哪些工具"""
    return [
        Tool(
            name="query_employees",
            description="查询员工信息，支持按部门、姓名筛选",
            inputSchema={
                "type": "object",
                "properties": {
                    "department": {"type": "string", "description": "部门名称"},
                    "name": {"type": "string", "description": "员工姓名"}
                }
            }
        ),
        Tool(
            name="create_leave_request",
            description="创建请假申请",
            inputSchema={
                "type": "object",
                "properties": {
                    "employee_id": {"type": "string"},
                    "start_date": {"type": "string"},
                    "end_date": {"type": "string"}
                },
                "required": ["employee_id", "start_date", "end_date"]
            }
        )
    ]

@server.call_tool()
async def call_tool(name: str, arguments: dict):
    """实际执行工具调用"""
    if name == "query_employees":
        # ⚠️ 安全关键：参数校验 + 鉴权 + 限流在这里做！
        results = db.query(
            "SELECT * FROM employees WHERE department = ? AND name LIKE ?",
            arguments.get("department", "%"),
            f"%{arguments.get('name', '')}%"
        )
        return [TextContent(type="text", text=str(results))]
    
    elif name == "create_leave_request":
        # 写操作需要更严格的权限控制
        validate_permission(arguments["employee_id"])
        leave_id = db.insert("leave_requests", arguments)
        return [TextContent(type="text", text=f"请假申请已创建，ID: {leave_id}")]
```

```
用户："研发部有哪些员工？"
  ↓
① LLM 分析意图 → 需要调用 query_employees 工具
  ↓
② MCP Client 向 MCP Server 发起请求：
```

**六、Agent 工具调用的安全治理原则（2026 面试关键！）**

> **核心原则：LLM 绝不直连数据库！所有工具由后端服务提供，并在工具层实施鉴权、限流、审计。**

```
┌──────────────────────────────────────────────────────┐
│            Agent 安全治理三层模型                        │
│                                                      │
│  LLM（不可信）                                         │
│    ↓  只负责"决策要调用哪个工具"                         │
│                                                        │
│  ┌──────────────────────────────────────────────┐    │
│  │  工具网关（安全边界 — 这里是你的代码！）          │    │
│  │                                              │    │
│  │  ① 鉴权（Authentication）                     │    │
│  │     → 谁在调用？是否是合法用户/会话？              │    │
│  │     → 用户 A 只能查自己的数据，不能查用户 B 的     │    │
│  │                                              │    │
│  │  ② 授权（Authorization）                      │    │
│  │     → 这个操作被允许吗？                         │    │
│  │     → 普通用户：只读查询 ✅ | 删除操作 ❌          │    │
│  │     → 管理员：全部操作 ✅                        │    │
│  │                                              │    │
│  │  ③ 限流（Rate Limiting）                      │    │
│  │     → 单个用户每秒最多查询 10 次                 │    │
│  │     → 防止 LLM 循环调用导致的服务过载             │    │
│  │                                              │    │
│  │  ④ 审计（Audit Logging）                      │    │
│  │     → 记录所有工具调用：谁、什么时候、调了什么、结果 │    │
│  │     → 关键：记录 LLM 决策 + 工具调用 的关联       │    │
│  │                                              │    │
│  │  ⑤ 输入校验（Input Validation）               │    │
│  │     → LLM 产出的参数不可信！必须服务端校验！       │    │
│  │     → SQL注入防护、参数类型检查、范围限制          │    │
│  │                                              │    │
│  └──────────────────────────────────────────────┘    │
│    ↓  校验通过后                                      │
│  数据库 / 外部服务                                     │
│------------------------------------------------------│
│                                                      │
│  ⚠️ 面试高分说法：                                     │
│  "LLM 是不可信的调用者，所有工具调用必须经过             │
│   服务端的鉴权/限流/审计，这和传统 API 安全              │
│   治理是一样的原则，只是调用方从人类变成了 AI。"          │
└──────────────────────────────────────────────────────┘
```

**七、A2A（Agent-to-Agent）—— 多 Agent 协作协议**

MCP 解决"模型↔工具"，A2A 解决"Agent↔Agent"：

```
┌──────────────────────────────────────────┐
│          A2A 多 Agent 协作场景              │
│                                          │
│  ┌──────────────┐                        │
│  │ 客服 Agent    │  用户："我要退第5个订单"    │
│  └──────┬───────┘                        │
│         │ A2A 通信                        │
│         ↓                                │
│  ┌──────────────┐   ┌──────────────┐    │
│  │ 订单 Agent    │   │ 风控 Agent    │    │
│  │ 查订单详情     │   │ 检查是否可疑    │    │
│  └──────────────┘   └──────────────┘    │
│         │                    │           │
│         ↓                    ↓           │
│  ┌──────────────────────────────────┐   │
│  │ 客服 Agent 汇总结果 → 帮用户处理退款   │   │
│  └──────────────────────────────────┘   │
└──────────────────────────────────────────┘
```

| 维度 | MCP | A2A |
|------|-----|-----|
| **定位** | 模型 ↔ 工具/资源 的标准化 | Agent ↔ Agent 的通信协议 |
| **发布方** | Anthropic（2024.11） | Google（2025.04） |
| **核心能力** | Resources / Prompts / Tools / Sampling | 任务委派 / 能力发现 / 协商同步 |
| **类比** | USB-C（外设统一接口） | HTTP（服务间通信协议） |
| **关系** | 互补！MCP 让 Agent 能调用工具，A2A 让 Agent 之间能协作 |

**八、MCP vs Function Calling 对比**

| 维度 | Function Calling | MCP |
|------|-----------------|-----|
