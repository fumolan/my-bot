**一、为什么需要虚拟线程？传统线程的两大痛点**

传统 Java 并发模型（Thread-Per-Request）存在根本性限制：

| 痛点 | 原因 | 后果 |
|------|------|------|
| **平台线程昂贵** | 每个 `Thread` = 1 个 OS 内核线程，默认栈 ~1MB | 几千线程就 OOM，无法支撑万级并发 |
| **异步编程心智负担重** | CompletableFuture、Reactive 编程模型割裂 | 代码难以调试、堆栈不可读、排查问题噩梦 |

```
传统 Tomcat 的局限：
  → 默认最大线程池 200 个线程
  → 每个请求占一个线程，在线程返回前什么都做不了
  → 200 个并发就到极限 → 剩下请求排队等待
  → 即使 99.9% 时间在等数据库 IO，线程也在空耗

而 Go 语言的 goroutine 早已支持百万级并发...
Java 终于用虚拟线程追上了！
```

**二、核心原理：M:N 调度模型**

虚拟线程是 **Project Loom** 的旗舰特性，JDK 19 预览 → JDK 21 正式发布（2023.09）。

```
传统线程（1:1 模型）：
  Java Thread → 直接映射到 OS 内核线程
  1000 个 Java Thread = 1000 个 OS 线程（昂贵！）

虚拟线程（M:N 模型）：
  Java Virtual Thread → JVM 用户态调度 → 少量 OS 线程（Carrier Thread）
  
  ┌──────────────────────────────────────────────┐
  │            M:N 调度模型                        │
  │                                              │
  │  ┌────┐┌────┐┌────┐┌────┐┌────┐  ... ×10000 │
  │  │VT 1││VT 2││VT 3││VT 4││VT 5│  虚拟线程    │
  │  └──┬─┘└──┬─┘└──┬─┘└──┬─┘└──┬─┘              │
  │     │     │     │     │     │                 │
  │     ↓     ↓     ↓     ↓     ↓                 │
  │  ┌──────────────────────────────────────┐    │
  │  │     ForkJoinPool（调度器）              │    │
  │  └──┬──────────┬──────────┬─────────────┘    │
  │     │          │          │                   │
  │     ↓          ↓          ↓                   │
  │  ┌────┐    ┌────┐    ┌────┐                  │
  │  │CT 1│    │CT 2│    │CT 3│   Carrier Thread  │
  │  └────┘    └────┘    └────┘   （平台线程）      │
  │     ↓          ↓          ↓                   │
  │  OS Thread  OS Thread  OS Thread              │
  └──────────────────────────────────────────────┘

  核心机制：
  ① 虚拟线程被 mount（挂载）到 Carrier Thread 上执行
  ② 当虚拟线程遇到阻塞操作（IO、sleep、lock）
     → 自动 unmount（卸载），释放 Carrier Thread 去执行其他虚拟线程
  ③ 阻塞结束后，虚拟线程被重新 mount 到某个空闲的 Carrier Thread 上
```

**三、Continuation 与 Carrier Thread 的协作机制**

```java
// 虚拟线程的核心数据结构（简化版）
class VirtualThread {
    private Continuation cont;       // 保存执行状态
    private CarrierThread carrier;   // 当前挂载的平台线程
    private volatile int state;      // NEW → RUNNING → PARKED → TERMINATED
}

// Continuation 保存了两个关键信息：
// ① 程序计数器（PC）：当前执行到哪一行代码
// ② 栈帧：所有局部变量和方法调用链

// 关键流程：当虚拟线程执行 IO 操作时
ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();

executor.submit(() -> {
    // ① VT 被 mount 到 Carrier Thread A
    String data = readFromDB();  // ② 阻塞！→ VT 自动 unmount
    //    ↑ Carrier Thread A 被释放，去执行其他 VT
    //    ↑ VT 的 Continuation 保存当前状态（冻结在 readFromDB 这一行）
    
    // ③ IO 完成 → VT 被重新 mount 到 Carrier Thread B（不一定是 A！）
    process(data);  // ④ 从 Continuation 恢复 → 从 readFromDB 之后继续执行
});
```

**四、虚拟线程 vs 平台线程：性能基准对比**

| 维度 | 平台线程 | 虚拟线程 | 倍数 |
|------|---------|---------|------|
| **创建成本** | ~1ms（1000μs） | ~1μs | **1000 倍** |
| **内存占用（栈）** | ~1MB（固定） | ~2KB（初始，按需增长） | **500 倍** |
| **上下文切换** | 系统调用（内核态切换） | JVM 内切换（用户态） | **零系统调用** |
| **最大线程数** | 几千（受 OS 限制） | **百万级** | 数量级差异 |
| **栈溢出风险** | 高（固定大小） | 低（动态增长） | — |

```java
// 实战验证：创建 100 万个虚拟线程
public class VirtualThreadDemo {
    public static void main(String[] args) {
        // ❌ 平台线程：100 万个 → OOM 或系统崩溃
        // for (int i = 0; i < 1_000_000; i++) {
        //     new Thread(() -> { ... }).start();
        // }
        
        // ✅ 虚拟线程：100 万个 → 轻松搞定！
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 1_000_000; i++) {
                int taskId = i;
                executor.submit(() -> {
                    Thread.sleep(Duration.ofSeconds(1));  // 模拟 IO
                    return "Task " + taskId + " done";
                });
            }
        }
        // 100 万个虚拟线程全部并发执行，总内存仅 ~2GB
        System.out.println("100 万虚拟线程创建完毕！");
    }
}
```

**五、创建虚拟线程的三种方式**

```java
// 方式 1：通过 Thread.ofVirtual() — 手动创建
Thread vt = Thread.ofVirtual()
    .name("my-virtual-thread")
    .start(() -> {
        System.out.println("Hello from Virtual Thread!");
    });
vt.join();  // 等待虚拟线程结束

// 方式 2：通过 Executors.newVirtualThreadPerTaskExecutor() — 推荐！
// 每个任务自动创建一个新的虚拟线程，无需管理线程池
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<String> future = executor.submit(() -> {
        // 执行任务
        return "result";
    });
    String result = future.get();
}

// 方式 3：Spring Boot 3.2+ 启用虚拟线程（零代码改动！）
// application.yml
spring:
  threads:
    virtual:
      enabled: true  # ← 就这么一行！Tomcat/Jetty 的请求处理线程全变成虚拟线程
```

**六、适用场景 vs 不适合场景（面试核心！）**

| ✅ 适合 | ❌ 不适合 |
|--------|----------|
| **IO 密集型**：Web 服务请求、数据库查询、RPC 调用、消息队列消费 | **CPU 密集型**：加密计算、视频编码、持续数学运算（虚拟线程不能变出更多 CPU，反而增加调度开销） |
| **高并发短任务**：大量并发 IO 等待（如微服务网关） | **需要固定线程资源**：如持有 ThreadLocal 状态的长生命周期任务 |
| **阻塞式 API 调用**：传统的同步 JDBC、HTTP 客户端 | **pin 住的场景**：synchronized 块内调用阻塞方法 → 虚拟线程被 pin 在 Carrier Thread 上，无法 unmount |

**⚠️ pin 问题详解（高频考点）：**

```java
// ❌ 错误：synchronized 内 + IO 阻塞 → pin 住了！
synchronized (this) {
    // 虚拟线程在 synchronized 内执行 IO
    // → 无法 unmount！Carrier Thread 被锁定！
    String data = httpClient.send(request);  // 阻塞！
    // 后果：Carrier Thread 被这个 VT 独占，其他 VT 无法使用
}

// ✅ 正确：用 ReentrantLock 代替 synchronized
lock.lock();
try {
    String data = httpClient.send(request);  // VT 可以正常 unmount！
} finally {
    lock.unlock();
}
```

**七、虚拟线程 vs 响应式编程（WebFlux/Reactor）的选型**

| 维度 | 虚拟线程 | 响应式编程 |
|------|---------|-----------|
| **编程模型** | 同步、命令式（简单！） | 异步、函数式（复杂！） |
| **学习曲线** | 低（和传统 Java 一样） | 高（需要理解 Mono/Flux/背压） |
| **调试体验** | ⭐⭐⭐⭐⭐ 堆栈清晰 | ⭐⭐ 堆栈不可读 |
| **吞吐量** | 高（百万级并发） | 高 |
| **内存效率** | 好（动态栈） | 好（事件循环） |
| **CPU 密集型** | 无优势 | 无优势 |
| **生态兼容性** | 完美兼容所有 Java 库 | 需要"Reactive 化"（JDBC → R2DBC） |

> **2026 面试金句**："在虚拟线程出现之前，响应式编程是高并发 Java 的唯一解；虚拟线程出现之后，99% 的场景不再需要 WebFlux。除非你需要背压（Backpressure）或流式处理，否则虚拟线程是更简单、更可维护的选择。"

### 💡 延伸思考

1. **Spring Boot 3.2+ 启用虚拟线程后，ThreadLocal 还能用吗？** — 能，但要注意：虚拟线程会在阻塞时卸载、恢复时挂载到不同的 Carrier Thread，但虚拟线程自身不会变，所以 `ThreadLocal` 在虚拟线程生命周期内仍然有效（它是绑定到虚拟线程的，不是 Carrier Thread）。但推荐使用 `ScopedValue`（JDK 21+ 的不可变 ThreadLocal 替代）以获得更好的性能。
2. **虚拟线程能解决数据库连接池不够用的问题吗？** — 不能。虚拟线程增加了请求处理的并发度，但数据库连接池大小是独立的瓶颈。如果连接池只有 20 个连接，即使有 10000 个虚拟线程在等，也只有 20 个能同时和数据库交互。此时应该配合连接池调优或读写分离。

**三、ChatClient — 统一聊天入口**

@RestController
@RequestMapping("/ai")
public class AIController {

```java
// 自定义 Advisor：实现安全防护
public class SafeGuardAdvisor implements CallAroundAdvisor {
    
    @Override
    public AdvisedResponse aroundCall(AdvisedRequest request, 
                                       CallAroundAdvisorChain chain) {
        String userText = request.userText();
        
        // 检测敏感内容
        if (containsSensitiveContent(userText)) {
            return AdvisedResponse.builder()
                .response(new org.springframework.ai.chat.model.ChatResponse(
                    List.of(new org.springframework.ai.chat.model.Generation(
                        new org.springframework.ai.chat.messages.AssistantMessage(
                            "抱歉，该问题涉及敏感内容，无法回答。")))))
                .build();
        }
        
        // 放行正常请求
        return chain.nextCall(request);
    }
}
```

**二、Explain 执行计划 — 性能分析的显微镜**

这是面试必考内容，必须能逐字段解读：

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 10086 AND status = 'PAID';
```

| 字段 | 含义 | 关注重点 |
|------|------|---------|
| **id** | 查询序号 | 数字越大越先执行；相同则从上到下 |
| **select_type** | 查询类型 | SIMPLE（简单查询）/ PRIMARY（主查询）/ SUBQUERY（子查询）/ DERIVED（派生表） |
| **table** | 访问的表 | 表名或 `<derived2>`（派生表） |
| **type** | **访问类型（最重要！）** | system > const > eq_ref > ref > range > index > **ALL** |
| **possible_keys** | 可能使用的索引 | 显示 MySQL 认为可以使用的索引 |
| **key** | 实际使用的索引 | `NULL` = 没用索引！ |
| **key_len** | 使用索引的长度 | 可判断联合索引用了几列 |
| **ref** | 索引比较的对象 | const（常量）/ 字段名 / func |
| **rows** | 预估扫描行数 | **越小越好！** 与实际行数偏差大说明统计信息过期 |
| **filtered** | 按 WHERE 过滤后剩余百分比 | 100% = 无额外过滤 |
| **Extra** | **额外信息（非常重要！）** | Using index / Using where / Using temporary / Using filesort |

**type 从好到差（面试必背！）：**

```
system   >  const    >  eq_ref   >  ref   >  range   >  index   >  ALL
⭐×5       ⭐×5        ⭐×4        ⭐×4     ⭐×3        ⭐×1        ⭐×0

const:   主键或唯一索引等值查询，最多 1 行
         WHERE id = 1

eq_ref:  连表查询时，被驱动表走主键/唯一索引
         JOIN orders ON user.id = orders.user_id

ref:     非唯一索引等值匹配
         WHERE user_id = 10086（user_id 有普通索引）

range:   索引范围扫描
         WHERE id > 100 / WHERE create_time BETWEEN ... / WHERE name LIKE '张%'

index:   全索引扫描（比全表好一点但不多）
         SELECT user_id FROM users（user_id 有索引，不需要回表）

ALL:     全表扫描（最差！）
         WHERE status = 'PAID'（status 没索引）
```

**Extra 关键信息解读：**

| Extra 值 | 含义 | 好坏 |
|----------|------|------|
| **Using index** | 覆盖索引，不需要回表 | ✅ 好！ |
| **Using index condition** | 索引下推（ICP） | ✅ 好！ |
| **Using where** | 使用了 WHERE 过滤 | 正常 |
| **Using temporary** | 使用临时表（GROUP BY/DISTINCT） | ⚠️ 需要优化 |
| **Using filesort** | 文件排序（ORDER BY 没走索引） | ⚠️ 需要优化 |
| **Using join buffer** | 连表使用 Join Buffer | ⚠️ 可能需要优化 |

**MySQL 8.0 黑科技：EXPLAIN ANALYZE**

```sql
-- 不仅告诉你"计划怎么执行"，还告诉你"实际怎么执行"！
EXPLAIN ANALYZE 
SELECT * FROM orders WHERE user_id = 10086;

-- 输出包含实际耗时、实际行数、循环次数
-- → 解决了传统 EXPLAIN "预估不准"的问题
```

**三、索引失效的 7 大魔鬼场景**

| # | 场景 | 错误示例 | 正确写法 |
|---|------|---------|---------|
| 1 | **隐式类型转换** | `WHERE user_id = '10086'`（user_id 是 int） | `WHERE user_id = 10086` |
| 2 | **索引列使用函数** | `WHERE YEAR(create_time) = 2026` | `WHERE create_time BETWEEN '2026-01-01' AND '2026-12-31'` |
| 3 | **LIKE 左模糊** | `WHERE name LIKE '%张三'` | `WHERE name LIKE '张三%'`（右模糊走索引） |
| 4 | **OR 条件未全覆盖** | `WHERE a=1 OR b=2`（a,b 各自独立索引可能失效） | 分别建联合索引或用 UNION |
| 5 | **不满足最左前缀** | 联合索引(a,b,c)，`WHERE b=2 AND c=3` | `WHERE a=1 AND b=2` 或建 (b,c) 索引 |
| 6 | **!= / <> / NOT IN** | `WHERE status != 'DELETED'` | 考虑用 `IN ('ACTIVE','PENDING')` 或应用层过滤 |
| 7 | **IS NULL / IS NOT NULL** | 大量 NULL 值时索引失效 | 设置 NOT NULL 默认值 |

**最左前缀原则详解：**

```
联合索引 (a, b, c) —— B+ 树按 a→b→c 排序

✅ WHERE a = 1                     → 走索引（只用 a）
✅ WHERE a = 1 AND b = 2           → 走索引（用 a,b）
✅ WHERE a = 1 AND b = 2 AND c = 3 → 走索引（用全部 3 列）
✅ WHERE a = 1 AND c = 3           → 走索引但只用 a 列（c 被跳过！）
❌ WHERE b = 2 AND c = 3           → 不走索引（最左列 a 缺失！）
⚠️ WHERE a > 1 AND b = 2           → 走索引但只用 a 列（a 是范围，b 失效）

key_len 可以验证用了哪几列：
  key_len = 4   → 只用 a（int = 4 字节）
  key_len = 12  → 用了 a,b（int×2 + 允许 NULL×2）
  key_len = 24  → 用了 a,b,c（int×3 + 允许 NULL×3）
```

**四、覆盖索引与回表查询**

```
InnoDB B+ 树结构：

聚簇索引（主键索引）：
  B+ 树的叶子节点 = 完整数据行
  [id=1 | name, age, email, ...]
  [id=2 | name, age, email, ...]

二级索引（非主键索引）：
  B+ 树的叶子节点 = 主键值（不存其他列！）
  [user_id=100, id=1]
  [user_id=200, id=2]

回表查询：
  SELECT name, age FROM users WHERE user_id = 100;
  ① 查二级索引 → 找到 id=1（不需要回表已经拿到 id？不，还要查 name 和 age）
  ② 用 id=1 回表查聚簇索引 → 拿到 name, age
  → 两次 B+ 树查找！成本翻倍

覆盖索引：
  SELECT user_id, id FROM users WHERE user_id = 100;
  ① 查二级索引 → user_id=100, id=1 都在叶子节点中！
  → 不需要回表！一次查找完成 ✅

  Extra 显示：Using index ← 这就是覆盖索引的标志！
```

**为什么 SELECT * 不推荐用于生产？**

```
SELECT * FROM orders WHERE user_id = 10086;

问题 1：无法使用覆盖索引
  → * 需要全部列，必须回表

问题 2：网络传输负担
  → 表中可能有 TEXT/BLOB 大字段，不需要也传回来了

问题 3：表结构变更风险
  → 新增字段可能导致应用报错（如 JSON 反序列化失败）

问题 4：无法利用索引下推（ICP）
  → ICP 只能对索引中的列做过滤

✅ 正确做法：只 SELECT 需要的列
  SELECT id, order_no, amount FROM orders WHERE user_id = 10086;
```

**五、ICP（Index Condition Pushdown，索引下推）**

ICP 是 MySQL 5.6 引入的优化——把 WHERE 过滤下推到存储引擎层：

```
⚠️ 注意：ICP 是索引下推，不是条件下推。
ICP 只能对索引包含的列做过滤。

SELECT * FROM users WHERE name LIKE '张%' AND age > 18;
-- 联合索引：(name, age)

没有 ICP：
  ① 存储引擎通过 name LIKE '张%' 找到所有匹配行 → 返回 Server 层
  ② Server 层再过滤 age > 18
  → 大量不符合 age > 18 的行也被返回了 Server 层！

有 ICP：
  ① 存储引擎通过 name LIKE '张%' 找到匹配行
  ② ⭐ 直接在存储引擎层过滤 age > 18！
  ③ 只有 name+age 都满足的行才返回 Server 层
  → Extra: Using index condition ✅
```

**六、完整优化流程图**

```
接口慢 ↓
① SkyWalking 定位到具体 SQL
   ↓
② EXPLAIN 分析执行计划
   ├── type=ALL → 加索引！
   ├── Extra=Using filesort → ORDER BY 列建索引！
   ├── Extra=Using temporary → 优化 GROUP BY/DISTINCT！
   ├── rows 很大 → 索引设计不合理，调整！
   └── key=NULL → 索引失效！检查 7 大场景
   ↓
③ 确认优化方案
   ├── 建正确索引（遵循最左前缀）
   ├── 覆盖索引（减少回表）
   ├── 改写 SQL（消除隐式转换/函数）
   └── 大表考虑分库分表
   ↓
④ EXPLAIN 验证优化效果
   ↓
⑤ 压测验证 + 上线
```

### 💡 延伸思考

1. **`COUNT(*)` 和 `COUNT(1)` 和 `COUNT(column)` 有什么区别？** — InnoDB 中 `COUNT(*)` 和 `COUNT(1)` **完全一样**，MySQL 优化器会选择最小的索引来统计行数。`COUNT(column)` 不统计 NULL 值行，如果列可为 NULL 则结果更小。生产中 `SELECT COUNT(*)` 对 InnoDB 大表很慢（需要全索引扫描），考虑用 `SHOW TABLE STATUS` 获取近似值或 Redis 计数器。
2. **分页越往后越慢怎么优化？** — `LIMIT 1000000, 10` 需要扫描前 1000000 行再丢弃，很慢。优化方案：① 子查询 + 覆盖索引：`SELECT * FROM orders WHERE id > (SELECT id FROM orders ORDER BY id LIMIT 1000000,1) LIMIT 10`；② 使用 ES 做搜索，MySQL 只做精确查询。

## 题目 4：[缓存/Redis] 请详细阐述 Redis 高可用架构的三层演进路径：主从复制（数据备份 + 读写分离）、哨兵模式（自动故障转移）、Cluster 分片集群（水平扩展 + 高可用）。重点对比三种方案的核心原理、关键机制（全量/增量复制、主观/客观下线、哈希槽）、以及生产环境选型依据

**难度**：⭐⭐⭐⭐
**考点来源**：2026-05-19 早间报告 — "Redis、中间件面试高频" + 2026 Java 面试体系  
**相关岗位**：Java后端 / 基础架构 / SRE

### 📖 参考答案

**一、Redis 高可用演进全景图**

Redis 高可用是逐层进化的，每一层解决上一层最核心的痛点：

```
单机 Redis
  ├── 问题：单点故障 → 数据全丢、服务全挂
  │
  ▼
第一层：主从复制（数据备份 + 读写分离）
  ├── 解决：单点数据丢失 + 读压力
  ├── 新问题：主节点挂了需手动切换（分钟级不可用）
  │
  ▼
第二层：哨兵 Sentinel（自动故障转移）
  ├── 解决：自动检测 + 自动切换（秒级恢复）
  ├── 新问题：所有数据在一台机器，容量/性能上限
  │
  ▼
第三层：Cluster 分片集群（水平扩展）
  ├── 解决：数据分片，突破单机内存/性能瓶颈
  └── 同时具备高可用（每个分片有主从副本）
```

**核心定位一句话：**

| 模式 | 核心目标 | 类比 |
|------|---------|------|
| **主从复制** | 数据备份 + 读写分离 | 给主机配了个备份机 |
| **哨兵模式** | 自动故障转移 | 雇了个 24h 值班的运维 |
| **Cluster** | 水平扩展 + 高可用 | 数据分库分表 + 每库都有备库 |

**二、第一层：主从复制 — 高可用的基石**

**全量复制流程：**

```
Slave 首次连接 Master：

  ① Slave → SYNC/PSYNC → Master
  ② Master 执行 BGSAVE → 后台生成 RDB 快照
  ③ Master 将 RDB 文件发送给 Slave
  ④ Slave 清空自身数据 → 加载 RDB 文件
  ⑤ Master 将 RDB 生成期间的写命令缓存在 replication buffer
  ⑥ 发送 buffer 给 Slave → Slave 执行这些命令
  ⑦ 复制完成 → 进入增量复制阶段
```

**增量复制流程（Redis 2.8+ PSYNC）：**

```
Master 维护 replication offset（复制偏移量）和 replication backlog（环形缓冲区）

正常情况下：
  Master 每执行一个写命令 → offset + 1 → 同步给 Slave
  Slave 执行后 → 自己的 offset + 1

断线重连后：
  Slave: "我的 offset=1000"
  Master: "backlog 里有 800-1500，给你 1000-1500"
  → 只传输增量部分，不需要全量复制！

但注意：如果 Slave 的 offset 不在 backlog 范围内 → 退化到全量复制
```

**主从复制配置：**

```bash
# slave.conf
replicaof 192.168.1.100 6379   # Redis 5.0+ 用 replicaof 替代 slaveof
masterauth "your_password"
replica-read-only yes           # 从节点只读

# 优点：简单、可靠、支持读写分离
# 缺点：主节点宕机需要手动切换（停机时间 = 人工响应时间）
```

**三、第二层：哨兵 Sentinel — 自动化运维**

Sentinel 本质是一个独立的监控进程（或多个组成集群），在主从架构之上增加自动故障转移能力。

**Sentinel 三大功能：**

```
① 监控（Monitoring）
  → 定期 PING Master 和 Slave，检查存活

② 自动故障转移（Automatic Failover）
  → Master 宕机 → 选新 Master → 通知其他 Slave  → 通知客户端

③ 配置提供者（Configuration Provider）
  → 客户端连 Sentinel 获取当前 Master 地址
  → 不直接写死 Master IP
```

**主观下线 vs 客观下线（面试必问！）：**

```
主观下线（SDOWN）：
  单个 Sentinel 认为 Master 挂了
  条件：PING 在 down-after-milliseconds 内无响应
  → 但这可能是网络问题（Sentinel 与 Master 之间的网断了而已）

客观下线（ODOWN）：
  多个 Sentinel（≥ quorum）都认为 Master 挂了
  → 此时才确认 Master 真的挂了
  → 触发故障转移！

quorum 配置：
  sentinel monitor mymaster 127.0.0.1 6379 2
  → 至少 2 个 Sentinel 认为挂了才确认
  
  建议：quorum = N/2 + 1（N 为 Sentinel 数量）
```

**故障转移完整流程：**

```
① 多个 Sentinel 一致确认 Master ODOWN
  ↓
② Sentinel Leader 选举（Raft 算法，选出一个 Sentinel 来执行切换）
  ↓
③ Leader 从 Slave 中选择新 Master
  选择规则（优先级从高到低）：
  ① replica-priority 低的优先（数字越小优先级越高）
  ② 复制偏移量最大的（数据最新）
  ③ runid 最小的（确保确定性）
  ↓
④ Leader 向新 Master 发送 SLAVEOF NO ONE（升级为 Master）
  ↓
⑤ Leader 向其他 Slave 发送 SLAVEOF new_master_ip new_master_port
  ↓
⑥ Leader 将旧 Master 设为新 Master 的 Slave（等它活过来）
  ↓
⑦ 通知所有客户端：新 Master 地址是 xxx
```

**哨兵配置：**

```bash
# sentinel.conf
port 26379

# 监控 master，quorum=2（Sentinel 集群至少 3 个实例）
sentinel monitor mymaster 192.168.1.100 6379 2

# 主观下线判定时间（毫秒）
sentinel down-after-milliseconds mymaster 30000

# 故障转移超时时间
sentinel failover-timeout mymaster 180000

# 同时向新 Master 同步的 Slave 数量（1 表示串行同步）
sentinel parallel-syncs mymaster 1

# 启动 Sentinel
redis-sentinel /path/to/sentinel.conf

# 哨兵部署建议：至少 3 个 Sentinel（分布在不同物理机/机架上！）
```

**四、第三层：Cluster 分片集群 — 突破单机极限**

当单机内存到达瓶颈（如 64GB），无论是主从还是哨兵都不能解决容量问题。Cluster 通过数据分片实现水平扩展。

**核心原理：16384 个哈希槽**

```
Cluster 将整个键空间划分为 16384 个哈希槽（slot）

  slot = CRC16(key) % 16384

每个 Master 节点负责一部分 slot：

  ┌─────────────────────────────────────────┐
  │       Redis Cluster (3 Master + 3 Slave) │
  │                                          │
  │  Master-1          Master-2   Master-3   │
  │  slot: 0-5460     slot: 5461-10922  10923-16383 │
  │  Slave-1           Slave-2    Slave-3   │
  └─────────────────────────────────────────┘

  SET user:1001 "张三"
  → CRC16("user:1001") % 16384 = 8723
  → 属于 slot 8723 → 路由到 Master-2
```

**请求重定向（MOVED vs ASK）：**

```
客户端连接任意节点，发送请求：

正确节点：
  SET user:1001 "张三"  → Master-2 直接处理 ✅

错误节点（连到了 Master-1）：
  SET user:1001 "张三"
  → Master-1: "这个 key 的 slot=8723，归 Master-2 管"
  → 返回 MOVED 8723 192.168.1.102:6379
  → 客户端缓存 slot 分布 → 下次直连 Master-2

客户端库（Jedis/Lettuce/Redisson）自动处理 MOVED 重定向：
  → 你基本感受不到重定向的存在
```

**数据分片后的事务限制：**

```
Cluster 模式下的事务限制：
  → 只能对同一个 slot 内的 key 做事务（MULTI/EXEC）
  → 跨 slot 的事务不支持！

解决方法：使用 Hash Tag
  → {user:1001}:name, {user:1001}:age, {user:1001}:email
  → CRC16 只计算 "user:1001" → 同一个 slot！
  → 可以在同一事务中操作
```

**五、脑裂问题与解决方案**

```
脑裂场景：
  ① Master 与 Sentinel 集群之间网络故障
  ② Sentinel 认为 Master 挂了 → 选 Slave 为新 Master
  ③ 旧 Master 还没挂！两段网络不通而已！
  ④ 此时有两个 Master 同时接受写入 → 数据不一致！

解决方案（主从/哨兵架构）：
  min-replicas-to-write 1       # 至少 1 个 Slave 在线才接受写入
  min-replicas-max-lag 10       # Slave 复制延迟不超过 10 秒
  
  如果条件不满足 → Master 拒绝写入
  → 网络分区期间旧 Master 失去写入能力
  → 只有新 Master 能写入 → 避免脑裂数据冲突
```

**二、PagedAttention — vLLM 的核心创新**

PagedAttention 借鉴操作系统的虚拟内存分页机制，是 vLLM 成为 2026 年 LLM 推理事实标准的关键：

```
传统 KV Cache（连续分配）：
  请求 1: [████████░░░░░░░░░░░░░░░░░░░░]  分配 4096，只用 8 blocks
  请求 2: [██░░░░░░░░░░░░░░░░░░░░░░░░░░]  分配 4096，只用 2 blocks
  请求 3: [████████████████░░░░░░░░░░░░]  分配 4096，只用 16 blocks
  → 3 个请求占了 12288 blocks，实际只用 26 blocks → 利用率 21%！

PagedAttention（分页分配）：
  物理 Block 池： [B0][B1][B2][B3][B4][B5][B6][B7][B8][B9]...
                    ↓    ↓         ↓    ↓    ↓    ↓
  请求 1 逻辑页表： [B0, B3, B6, B8, ...]  ← 非连续！
  请求 2 逻辑页表： [B1, B4, ...]
  请求 3 逻辑页表： [B2, B5, B7, B9, ...]
  → 按需分配，利用率从 21% 提升到 90%+！
  → 同样显存能处理的并发请求数提升 4-5 倍！

每个 Block 默认 16-32 tokens 的 KV Cache
```

**PagedAttention 的三大优势：**

```
① 零碎片化
  → Block 大小固定，不存在"分配大块用不完"的问题
  → 所有空闲 Block 组成统一池，按需分配

② 内存共享（Prefix Caching）
  → 多个请求共享相同的 System Prompt
  → System Prompt 的 KV Cache 只需存一份！
  → 例如：所有请求都用同一个 2K token 的 system prompt
  → 传统方案：10 个请求 × 2K = 20K cache
  → PagedAttention：只需 1 × 2K = 2K cache（节省 90%！）

③ 与 Attention Kernel 兼容
  → vLLM 修改了 FlashAttention 等 Kernel
  → 支持从非连续的物理 Block 中读取 KV Cache
  → 性能几乎无损失
```

**三、Continuous Batching — 动态批调度**

传统静态批处理 vs Continuous Batching：

```
静态批处理：
  Batch = [req1, req2, req3]
  → 必须等 req1 + req2 + req3 全部完成才能组成新 batch
  → req1（100 tokens 就结束） 干等 req3（还在生成第 500 token）

Continuous Batching（vLLM 实现）：
  调度器维护三个队列：

  WAITING 队列  →  新到达的请求
  RUNNING 队列  →  正在生成 token 的请求
  SWAPPED 队列  →  因显存不足暂时挂起的请求

  每个迭代步骤：
  ① 检查 RUNNING 中的请求是否完成 → 移出
  ② 从 WAITING 中取出新请求 → 加入 RUNNING
  ③ 如果显存不够 → 挂起部分 RUNNING 到 SWAPPED
  ④ 对 RUNNING 中的请求执行一轮推理（每个生成 1 个 token）

  关键：请求完成一个就立即移出一个，新请求立即加入！
  → 无需等待整个 batch 完成
  → GPU 利用率大幅提升
```
