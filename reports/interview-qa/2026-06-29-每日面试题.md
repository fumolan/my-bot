#### 一、GMP 调度模型——Go 高并发的底层基石

Go 的并发模型不是操作系统线程 1:1 映射，而是实现了 **M:N 调度**（M 个 goroutine 调度到 N 个 OS 线程上）。核心是 GMP 三元组：

```
┌──────────────────────────────────────────────────────┐
│                   GMP 调度模型                         │
│                                                        │
│  G (Goroutine)：轻量级"协程"                            │
│    - 栈初始 2KB（可动态扩缩）                            │
│    - 状态：Waiting → Runnable → Executing              │
│                                                        │
│  M (Machine)：OS 线程（工作线程）                        │
│    - 与内核线程 1:1 绑定                                │
│    - 数量上限 10000（默认 10000）                        │
│                                                        │
│  P (Processor)：逻辑处理器（调度上下文）                  │
│    - 拥有本地运行队列（Local Run Queue）                 │
│    - GOMAXPROCS 决定 P 数量（通常 = CPU 核数）          │
│    - 默认 10000 个 P 上限                               │
└──────────────────────────────────────────────────────┘
```

**调度流程（关键！）**：

```
① 创建 G：go func() 创建一个 G，放入当前 P 的本地队列
   └─ 本地队列满（256个）→ 一半 G 移入全局队列

② M 获取 G：M 绑定 P，从 P 的本地队列取 G 执行
   └─ 本地队列空 → 从全局队列偷 / 从其他 P 偷（Work Stealing）

③ G 阻塞（系统调用）：
   └─ G 进入阻塞 → M 与 P 解绑 → P 找新 M 继续执行
   └─ 阻塞结束 → G 进入全局队列等待

④ G 阻塞（Channel/锁）：
   └─ G 进入 Waiting → M 继续执行其他 G（不阻塞 M）
   └─ 条件满足 → G 变为 Runnable → 放回队列
```

**为什么 goroutine 比线程轻量？**

| 对比维度 | OS 线程 | Goroutine |
|---------|---------|-----------|
| 栈大小 | ~1MB（固定） | ~2KB（动态扩缩，可达 1GB） |
| 创建成本 | ~1μs（内核态） | ~0.1μs（用户态） |
| 切换成本 | ~1-10μs（内核态上下文切换） | ~0.1-1μs（用户态切换） |
| 最大数量 | ~4000（16GB 内存） | 数百万 |
| 调度方式 | 内核抢占式调度 | Go 运行时协作式调度 |

#### 二、goroutine + channel 最佳实践

**1. 基本原则**

```go
// 原则 1：Don't communicate by sharing memory; share memory by communicating.
// 不要通过共享内存来通信，而要通过通信来共享内存。

// 原则 2：Goroutine 的创建者负责退出
// 谁创建，谁负责停止

// 原则 3：用 done channel 控制生命周期
func worker(done <-chan struct{}, input <-chan int) <-chan int {
    output := make(chan int)
    go func() {
        defer close(output)
        for {
            select {
            case <-done:
                return  // 收到退出信号
            case v, ok := <-input:
                if !ok {
                    return  // 输入通道关闭
                }
                // 处理数据
                select {
                case output <- process(v):
                case <-done:
                    return
                }
            }
        }
    }()
    return output
}
```

**2. 常见模式：Fan-Out / Fan-In**

```go
// Fan-Out（扇出）：一个输入，多个 goroutine 并行处理
func fanOut(input <-chan int, numWorkers int) []<-chan int {
    outputs := make([]<-chan int, numWorkers)
    for i := 0; i < numWorkers; i++ {
        outputs[i] = worker(done, input)
    }
    return outputs
}

// Fan-In（扇入）：合并多个 channel 为一个
func fanIn(channels ...<-chan int) <-chan int {
    output := make(chan int)
    var wg sync.WaitGroup
    wg.Add(len(channels))
    
    for _, ch := range channels {
        go func(c <-chan int) {
            defer wg.Done()
            for v := range c {
                output <- v
            }
        }(ch)
    }
    
    // 等待所有输入 channel 关闭后，关闭输出 channel
    go func() {
        wg.Wait()
        close(output)
    }()
    
    return output
}
```

**3. 超时控制**

```go
func doWithTimeout(timeout time.Duration) error {
    result := make(chan error, 1) // 缓冲 1 防止 goroutine 泄漏
    
    go func() {
        result <- doSomething()
    }()
    
    select {
    case err := <-result:
        return err
    case <-time.After(timeout):
        return fmt.Errorf("操作超时 %v", timeout)
    }
}
```

#### 三、死锁排查（面试必问）

**典型死锁场景**：

```go
// 场景 1：无缓冲 channel 只发送不接收
func deadlock1() {
    ch := make(chan int)
    ch <- 1  // 阻塞，没有 goroutine 接收
    // fatal error: all goroutines are asleep - deadlock!
}

// 场景 2：channel 未关闭导致循环不退出
func deadlock2() {
    ch := make(chan int)
    go func() {
        for v := range ch { // range 不关闭会一直等待
            fmt.Println(v)
        }
    }()
    ch <- 1
    ch <- 2
    // main goroutine 退出后，子 goroutine 永远等待
    // 不 close(ch) 就会泄漏
}

// 场景 3：select 中无 default 且所有 case 都不满足
func deadlock3() {
    ch := make(chan int)
    select {
    case v := <-ch: // ch 为空且无 default → 永久阻塞
        fmt.Println(v)
    }
}
```

```java
// 1. Record 替代 Lombok @Data
// Java 8 写法
@Data
@AllArgsConstructor
public class User {
    private Long id;
    private String name;
    private String email;
}

// Java 17+ 写法
public record User(Long id, String name, String email) {}

// 2. Text Block 替代字符串拼接
// Java 8 写法
String sql = "SELECT id, name, email FROM users " +
             "WHERE status = 'ACTIVE' " +
             "ORDER BY created_at DESC";

// Java 17+ 写法
String sql = """
    SELECT id, name, email
    FROM users
    WHERE status = 'ACTIVE'
    ORDER BY created_at DESC
    """;

// 3. Switch Expression 替代 if-else
// Java 8 写法
String result;
switch (day) {
    case MONDAY:
    case FRIDAY:
        result = "工作日";
        break;
    case SATURDAY:
    case SUNDAY:
        result = "周末";
        break;
    default:
        result = "未知";
}

// Java 17+ 写法
String result = switch (day) {
    case MONDAY, FRIDAY -> "工作日";
    case SATURDAY, SUNDAY -> "周末";
    default -> "未知";
};

// 4. Pattern Matching
// Java 8 写法
if (obj instanceof String) {
    String s = (String) obj;
    System.out.println(s.length());
}

// Java 17+ 写法
if (obj instanceof String s) {
    System.out.println(s.length());
}

// 5. 虚拟线程（JDK 21+）
// Java 8 写法
ExecutorService executor = Executors.newFixedThreadPool(10);

// Java 21+ 写法
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    // 每个请求一个虚拟线程，无需担心线程池耗尽
}
```

#### 三、死循环检测与恢复

**1. 为什么 Agent 会死循环？**

```
典型死循环场景：

① 工具调用结果未改变状态
  Agent 调用 getWeather("北京") → 返回"晴"
  Agent 再调用 getWeather("北京") → 返回"晴"
  ...无限循环，因为每次结果一样，Agent 不知道下一步

② 工具返回错误导致重试死循环
  Agent 调用 deleteFile("/tmp/test") → 失败（文件不存在）
  Agent 重试 deleteFile("/tmp/test") → 又失败
  ...无限重试同一个工具

③ Agent 的推理陷入局部最优
  Agent 认为"需要先调用工具A，然后工具B"
  但工具B的执行结果又触发了工具A的重新调用
```

**2. 死循环检测算法**

```java
public class AgentLoopDetector {
    
    // 记录工具调用历史
    private final Map<String, List<ToolCall>> toolCallHistory = new ConcurrentHashMap<>();
    
    // 检测死循环的核心算法
    public boolean detectLoop(ToolCall currentCall) {
        String agentId = currentCall.getAgentId();
        List<ToolCall> history = toolCallHistory.computeIfAbsent(
            agentId, k -> new ArrayList<>()
        );
        
        // ① 最大迭代次数检测
        if (history.size() >= MAX_ITERATIONS) {
            log.warn("Agent {} 达到最大迭代次数 {}", agentId, MAX_ITERATIONS);
            return true;
        }
        
        // ② 重复工具+参数检测（精确匹配）
        int repeatCount = 0;
        for (ToolCall call : history) {
            if (call.getToolName().equals(currentCall.getToolName()) &&
                call.getParams().equals(currentCall.getParams())) {
                repeatCount++;
            }
        }
        if (repeatCount >= MAX_REPEAT_COUNT) {
            log.warn("Agent {} 重复调用 {}({}) 超过 {} 次",
```

#### 一、GIL 的历史与局限——Python 三十年的"枷锁"

**GIL（Global Interpreter Lock，全局解释器锁）** 是 CPython 解释器中的一个互斥锁，确保在任何时刻只有一个线程执行 Python 字节码。

```
GIL 存在的理由（历史原因）：
  CPython 的引用计数（Reference Counting）内存管理机制
  如果没有 GIL，每次对象引用增减都要加锁
  单线程性能会显著下降 2-3 倍

GIL 的代价（30 年的限制）：
  多核 CPU 上，Python 多线程只能利用一个核心
  多线程 CPU 密集型任务 = 单线程性能 + 线程切换开销
```

**GIL 的经典症状**：

```python
    return fib(n)
```
