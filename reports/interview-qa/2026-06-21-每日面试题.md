## 题目 1：[框架/Spring Boot] Spring Boot 4.1.0 三大架构变革深度解析：虚拟线程默认开启、惰性连接获取与原生 gRPC

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-21 早间 & 午间报告 — "Spring Boot 4.1.0 GA发布——Java生态里程碑"，三大改变（虚拟线程默认开启、惰性连接获取、原生 gRPC）成2026面试新考点
**相关岗位**：Java后端 / 微服务开发 / 基础架构

### 📖 参考答案

#### 一、背景：为什么 Spring Boot 4.1 是 2026 年最重要的 Java 版本

2026 年 6 月 10 日，Spring Boot 4.1.0 正式 GA。这是 Spring Boot 历史上第一次将三个深度改变运行时行为的能力打包成「默认开启」推给开发者：
- **虚拟线程（Virtual Threads）**：Project Loom 正式进入 Spring Boot 默认配置
- **惰性连接获取（Lazy Connection）**：数据库连接的使用方式被彻底重想
- **原生 gRPC**：Spring 官方第一次把 gRPC 纳入 Starter 体系

#### 二、虚拟线程默认开启——范式级转变

**原理**：虚拟线程是 JVM 层面的轻量级线程，不与 OS 线程 1:1 绑定。每个虚拟线程仅占用几百字节，可在单进程中创建数十万个。遇到阻塞操作（I/O、DB 查询）时，JVM 自动将其从载体线程卸载，让载体线程调度其他虚拟线程。

Spring Boot 4.1 在 Java 21+ 环境下自动将 `spring.threads.virtual.enabled` 设为 `true`，无需修改业务代码。

```yaml
# Spring Boot 4.1 默认等效配置（无需手动设置）
spring:
  threads:
    virtual:
      enabled: true
```

```java
// 传统平台线程模式：Tomcat 最多 200 线程
// 200 个请求同时查 DB 2 秒 → 200 个线程全堵着
@GetMapping("/users")
public List<User> getUsers() {
    return userService.findAll(); // 2s I/O 等待
}

// 虚拟线程模式：可同时挂起数万请求
// 等 DB 时自动让出载体线程，吞吐量提升 5-10 倍
// 代码完全不变
```

**🚨 陷阱：连接池击穿**。虚拟线程下 Tomcat 可挂起数万请求，但如果 5000 个请求全要查 DB，HikariCP 默认 10 个连接根本不够。解决方向：

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 50  # 从默认10调高
      connection-timeout: 3000  # 从30s缩短到3s，快速失败
    connection-fetch: lazy  # 4.1新功能：真正执行SQL时才获取连接
```

**🚨 陷阱：synchronized pinning**。虚拟线程在持有 `synchronized` 锁时遇到阻塞，JVM 无法卸载该线程（Java 21 有该问题，Java 24 已修复）。检测命令：

```bash
java -Djdk.tracePinnedThreads=full -jar myapp.jar
```

#### 三、原生 gRPC Starter

4.1 将 gRPC 纳入官方 `spring-boot-starter-grpc`，依赖 Spring 生命周期管理，统一配置方式：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-grpc</artifactId>
</dependency>
```

```protobuf
service UserService {
    rpc GetUser (GetUserRequest) returns (User);
}
```

```java
@GrpcService
public class UserGrpcService extends UserServiceGrpc.UserServiceImplBase {
    private final UserRepository userRepository;
    // 业务实现...
}
```

#### 四、惰性连接获取（Lazy Connection）

传统模式下，事务一开启就占用连接。4.1 的懒连接特性只有在真正执行 SQL 时才从连接池获取物理连接——对"开启事务但先读缓存命中就返回"的场景效果显著。

## 题目 2：[数据库/MyBatis] 请详细阐述 MyBatis SQL 执行完整流程与一级/二级缓存机制原理

**难度**：⭐⭐⭐
**考点来源**：2026-06-21 早间报告 — "MyBatis面试真题：SQL执行流程、缓存机制、MyBatis-Plus全考点"
**相关岗位**：Java后端 / 全栈开发

### 📖 参考答案

#### 一、MyBatis SQL 执行完整流程

MyBatis 的执行流程可用以下链路概括：

```
应用程序调用 Mapper 接口方法
        ↓
Mapper 动态代理（JDK Proxy）拦截调用
        ↓
SqlSession 根据 Mapper 接口全限定名 + 方法名定位 MappedStatement（XML 或注解中的 SQL 定义）
        ↓
解析 MappedStatement，获取 SQL、参数映射、结果映射信息
        ↓
BoundSql 组装：将参数绑定到 SQL 占位符（#{} / ${}），生成可执行 SQL
        ↓
Executor 执行器（SimpleExecutor / ReuseExecutor / BatchExecutor）
        ↓
  ├─ 查看一级缓存（SqlSession 级别）是否命中
  ├─ 查看二级缓存（namespace 级别）是否开启且命中
  ├─ 若缓存未命中 → StatementHandler 创建 JDBC Statement / PreparedStatement
  ├─ ParameterHandler 设置参数
  ├─ TypeHandler 处理类型转换
  ├─ 执行 JDBC SQL
  └─ ResultSetHandler 将结果集映射为 Java 对象（ORM 映射）
        ↓
返回结果（缓存结果）
```

**关键组件**：
| 组件 | 职责 |
|------|------|
| **SqlSession** | 顶层 API，提供 CRUD 操作入口 |
| **Executor** | 执行器，调度缓存和 JDBC 操作 |
| **MappedStatement** | 封装 SQL 定义、参数、结果映射等元数据 |
| **StatementHandler** | 封装 JDBC 操作（编译 SQL、执行 SQL） |
| **ParameterHandler** | 将 Java 参数映射到 JDBC 预编译参数 |
| **ResultSetHandler** | 将 JDBC ResultSet 映射为 Java 对象 |
| **TypeHandler** | Java 类型与 JDBC 类型的双向转换 |

#### 二、一级缓存（SqlSession 级别）

**特点**：
- **默认开启**，不可关闭（可设置为 statement 级别，即查询完清空）
- SqlSession 生命周期内有效，相同查询条件共享缓存
- 执行增删改操作（INSERT/UPDATE/DELETE）后自动清空

```java
try (SqlSession session = sqlSessionFactory.openSession()) {
    UserMapper mapper = session.getMapper(UserMapper.class);
    
    // 第一次查询：查数据库，结果放入一级缓存
    User user1 = mapper.selectById(1);
    
    // 第二次查询：命中一级缓存（key = 1），不走数据库
    User user2 = mapper.selectById(1);
    // user1 == user2 为 true
    
    // 执行 update 操作，清空一级缓存
    mapper.updateName(1, "新名字");
    
    // 第三次查询：缓存已清空，再次查数据库
    User user3 = mapper.selectById(1);
}
```

**缺点**：默认 `SqlSession` 生命周期短（每次请求创建），实际作用有限；分布式环境下多 SqlSession 间不共享。

#### 三、二级缓存（namespace 级别）

**特点**：
- **默认关闭**，需通过 `cache` 标签或 `@CacheNamespace` 注解开启
- 跨 SqlSession 共享，粗粒度（按 namespace / Mapper 接口）
- 缓存对象需实现 `Serializable` 接口
- 通过装饰器模式（CachingExecutor 装饰 Executor）实现

```xml
<!-- Mapper XML 中开启二级缓存 -->
<mapper namespace="com.example.mapper.UserMapper">
    <cache eviction="LRU" flushInterval="60000" size="512" readOnly="true"/>
    <select id="selectById" useCache="true">
        SELECT * FROM user WHERE id = #{id}
    </select>
</mapper>
```

**⚠️ 注意事项**：
1. 二级缓存是 **namespace 隔离** 的，多表关联查询容易产生脏数据（A 表 Mapper 更新了数据，B 表 Mapper 的二级缓存未清空）
2. 项目中通常使用 Redis 等外部缓存替代 MyBatis 二级缓存（MyBatis 集成 Redis 二级缓存）
3. 分布式环境下建议**禁用二级缓存**，改用业务层缓存（如 Redis）

#### 四、MyBatis-Plus 核心增强

MyBatis-Plus 在 MyBatis 基础上提供了：
- **通用 CRUD**：`BaseMapper<T>` 提供 `insert/deleteById/updateById/selectById` 等开箱即用方法
- **条件构造器**：`LambdaQueryWrapper` / `QueryWrapper` 动态拼接查询条件
- **分页插件**：`PaginationInnerInterceptor` 自动拦截并改写分页 SQL
- **代码生成器**：根据数据库表自动生成 Entity/Mapper/Service/Controller 代码

```java
// MyBatis-Plus 示例
@TableName("user")
public class User {
    @TableId(type = IdType.ASSIGN_ID)
    private Long id;
    @TableField("user_name")
    private String userName;
}

// 无条件构造器，链式调用
List<User> users = userMapper.selectList(
    new LambdaQueryWrapper<User>()
        .eq(User::getUserName, "张三")
        .orderByDesc(User::getId)
        .last("LIMIT 10")
);
```

## 题目 3：[缓存/Redis] 请详细阐述 Redis 缓存雪崩、缓存穿透与缓存击穿的区别、原因及解决方案

**难度**：⭐⭐⭐
**考点来源**：2026-06-21 午间报告 — "后端面试高频考点更新：数据库+Redis+RabbitMQ" + 面试场景题中常涉及的高并发缓存问题
**相关岗位**：Java后端 / 高并发系统

### 📖 参考答案

#### 一、三种缓存异常的概念与区别

| 对比维度 | 缓存雪崩 | 缓存穿透 | 缓存击穿 |
|---------|---------|---------|---------|
| **表现** | 大量缓存同时失效，请求全部打到 DB | 请求不存在的数据，缓存始终查不到 | 热点 key 过期，高并发请求直击 DB |
| **原因** | 缓存大面积过期 / Redis 宕机 | 恶意攻击 / 非法参数 / 不存在数据 | 某个热点 key 刚好过期 |
| **影响范围** | 全局性，可能拖垮整个 DB | 单个 key 持续失效 | 某个热点 key 失效瞬间 |
| **DB 压力** | 超高（全量请求） | 持续（每次都查 DB） | 瞬时高（集中在过期瞬间） |

```
三种异常的图解：

缓存雪崩（大面积失效）：
  时间线 → 
  ┌──────┬──────┬──────┬──────┐
  │ KeyA │ KeyB │ KeyC │ KeyD │ ← 在同一时间段集体过期
  └──────┴──────┴──────┴──────┘
       ↓↓↓↓ 全部请求 → MySQL（瞬间被击穿）

缓存穿透（不存在的数据）：
  请求 → Redis（miss）→ MySQL（miss 也返回空）
  每次请求都绕开缓存直接查 DB，DB 空转

缓存击穿（热点 key 过期）：
  热点 Key（如微博热搜#1）过期 → 10000 QPS 同时打 DB
  DB 单机抗不住，引发连锁故障
```

#### 二、缓存雪崩解决方案

**方案 1：过期时间打散（最常用）**
```java
// 在基础过期时间上加上随机偏移量，避免集体过期
int baseExpire = 3600; // 1小时
int randomOffset = new Random().nextInt(600); // 0-10分钟随机
redisTemplate.opsForValue().set(key, value, baseExpire + randomOffset, TimeUnit.SECONDS);
```

**方案 2：多级缓存** — 本地缓存（Caffeine/Guava）作为第一道防线，Redis 作为第二级，DB 作为最终存储。

**方案 3：Redis 高可用** — 哨兵模式 / Redis Cluster 避免单点故障；熔断降级（Sentinel/Resilience4j）在 DB 压力过大时快速失败。

**方案 4：提前预热 + 互斥锁** — 缓存失效后，第一个请求获取分布式锁并重建缓存，其他请求等待或返回旧值。

#### 三、缓存穿透解决方案

**方案 1：布隆过滤器（Bloom Filter）**
```java
// 预处理：将数据库中所有存在的 ID 写入布隆过滤器
BloomFilter<Integer> bloomFilter = BloomFilter.create(
    Funnels.integerFunnel(), expectedInsertions, fpp);

// 查询前置过滤
if (!bloomFilter.mightContain(requestId)) {
    return null; // 肯定不存在，直接返回
}
// 布隆过滤器判断可能存在 → 查缓存/数据库
```
布隆过滤器特点：说"不存在"就一定不存在，说"存在"可能存在误判。

**方案 2：缓存空值（Null Object Pattern）**
```java
Object value = redisTemplate.opsForValue().get(key);
if (value == null) {
    value = database.query(key);
    if (value == null) {
        // 将 null 值也缓存，设置较短过期时间（如 60s）
        redisTemplate.opsForValue().set(key, "NULL", 60, TimeUnit.SECONDS);
    } else {
        redisTemplate.opsForValue().set(key, value, expire, TimeUnit.SECONDS);
    }
}
```

#### 四、缓存击穿解决方案

**方案 1：互斥锁（Mutex Key）**
```java
public Object getProductById(Long id) {
    String cacheKey = "product:" + id;
    Object value = redisTemplate.opsForValue().get(cacheKey);
    
    if (value == null) {
        // 尝试获取分布式锁，只有一个线程能成功
        String lockKey = "lock:product:" + id;
        if (redisTemplate.opsForValue().setIfAbsent(lockKey, "1", 3, TimeUnit.SECONDS)) {
            try {
                // 双重检查：避免其他线程已经重建了缓存
                value = redisTemplate.opsForValue().get(cacheKey);
                if (value == null) {
                    value = database.query(id);
                    redisTemplate.opsForValue().set(cacheKey, value, 3600, TimeUnit.SECONDS);
                }
            } finally {
                redisTemplate.delete(lockKey); // 释放锁
            }
        } else {
            // 没拿到锁的线程休眠后重试
            Thread.sleep(50);
            return getProductById(id);
        }
    }
    return value;
}
```

**方案 2：逻辑过期（不设物理过期时间）** — 缓存永不过期，在 value 中存储逻辑过期时间，后台异步线程检测到逻辑过期后主动更新缓存。

**方案 3：本地缓存 + Redis 双缓存** — 热点数据在本地缓存也保留一份，即使 Redis key 过期，本地缓存仍可短时间兜底。

#### 五、生产环境最佳实践组合

```
缓存雪崩 → 过期时间打散 + Redis 高可用 + 熔断降级
缓存穿透 → 布隆过滤器（前置拦截） + 缓存空值（兜底）
缓存击穿 → 互斥锁（首选） + 逻辑过期（次选，适合不要求强一致的场景）
```

## 题目 4：[系统设计/秒杀] 请详细阐述高并发秒杀系统的全链路设计：从限流、削峰、异步扣库存到最终一致性保障

**难度**：⭐⭐⭐⭐⭐
**考点来源**：2026-06-21 午间报告 — "面试场景题成主流：电商秒杀+内容社区" + "Spring Boot 4.1 面试高频考点：秒杀系统设计"
**相关岗位**：Java后端 / 高并发系统 / 微服务架构

### 📖 参考答案

#### 一、秒杀系统的核心挑战

秒杀场景（如双11、限量抢购）的核心矛盾是：**瞬时流量极高（十万级 QPS）vs 后端资源有限（DB 只能抗几千 QPS）**。

```
挑战清单：
1. 高并发读：商品详情页瞬间被千万人访问
2. 高并发写：库存扣减必须原子且不超卖
3. 热点数据：秒杀商品是典型的热点 Key，容易击穿缓存
4. 系统雪崩：流量控制不当 → DB 被打垮 → 上下游链式故障
5. 作弊/脚本：黄牛机器人刷单
```

#### 二、分层架构设计

```
客户端（App / Web）
    ↓
CDN 静态资源（商品图片/H5静态页）
    ↓
Nginx / 反向代理层（限流 + WAF 防刷）
    ↓
Spring Cloud Gateway（令牌桶限流 + 用户鉴权）
    ↓
秒杀业务服务层（Redis 预扣库存 + MQ 削峰）
    ↓
消息队列（Kafka / RabbitMQ 异步消费）
    ↓
Worker 服务（批量落库 + 订单创建）
    ↓
MySQL + Redis Cluster
```

#### 三、各层关键设计

**1. 前端 & CDN 层**
- 静态资源（商品详情页）全量推 CDN，动态数据异步加载
- 按钮置灰 + 倒计时，减少无效请求
- 验证码/滑块拼图拦截机器流量

**2. 网关限流层**

**5. 最终一致性保障**
```
订单状态流转：
  SEALING（排队中）→ 根据库存扣减结果 → SUCCESS（成功） / FAILED（失败）
  
补偿机制：
  1. 死信队列：消费失败的消息 → 死信队列 → 人工介入/自动补偿
  2. 定时任务：扫描"已扣库存但未创建订单"的记录 → 补偿订单或回退库存
  3. 幂等表：使用唯一业务键（userId + productId + token）保证 MQ 消息幂等消费
```

#### 四、防超卖方案对比

| 方案 | 原理 | 并发能力 | 复杂度 | 推荐场景 |
|------|------|---------|-------|---------|
| 数据库乐观锁（version） | UPDATE ... WHERE stock > 0 AND version = ? | 低 | 低 | 低并发 |
| Redis 预扣+Lua | 原子 DECR，MQ 异步落库 | 极高 | 中 | **秒杀首选** |
| 数据库悲观锁（FOR UPDATE） | SELECT ... FOR UPDATE | 低 | 低 | 不推荐秒杀场景 |
| 本地内存扣减 | JVM 内原子计数 | 极高 | 低 | 单机/对账异步 |

## 题目 5：[微服务/分布式] 请详细阐述分布式事务的核心方案对比与选型策略：从 2PC（XA）到 TCC、Saga、Seata AT、本地消息表与 MQ 事务消息

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-21 午间报告 — "Spring Cloud 微服务组件面试高频：分布式事务 + Resilience4j + Sidecar" 
**相关岗位**：Java后端 / 微服务架构 / 分布式系统

### 📖 参考答案

#### 一、为什么需要分布式事务？

微服务架构下，一个操作涉及多个服务各自的数据库：

```
下单业务流程（分布式事务场景）：
  订单服务（订单库）→ 库存服务（库存库）→ 支付服务（支付库）
  
要保证：订单创建 + 库存扣减 + 支付扣款 → 要么全成功，要么全回滚
```

单体数据库的 `@Transactional` 无法跨数据库，因此需要分布式事务方案。

#### 二、核心方案详解

**1. 2PC（两阶段提交）/ XA —— 刚性事务**

| 阶段 | 动作 | 说明 |
|------|------|------|
| 准备阶段（Vote） | TM 向所有 RM 发送 prepare，RM 锁资源并返回 Yes/No | 资源锁定、局部可用 |
| 提交阶段（Commit） | TM 收到全部 Yes → 发送 commit；任一 No → 发送 rollback | 全局决策 |

```
2PC 的执行流程：

          TM（事务管理器）
        ┌────┴────┐
        ▼         ▼
      RM-A      RM-B
    (订单库)   (库存库)

① Prepare  → RM-A: "准备扣库存？" → RM-A 锁行 + 写 Undo → OK
② Prepare  → RM-B: "准备减订单？" → RM-B 锁行 + 写 Undo → OK
③ Commit   → RM-A: "提交！" → RM-A 释放锁 + 提交
④ Commit   → RM-B: "提交！" → RM-B 释放锁 + 提交
```

**优点**：强一致性、业务代码无侵入
**缺点**：同步阻塞（prepare 阶段锁资源）、协调者单点、性能差
**适用**：金融/账务等短事务强一致场景

**2. TCC（Try-Confirm-Cancel）—— 补偿型事务**

TCC 是业务侵入性方案，需要业务接口提供三个方法：

| 阶段 | 动作 | 示例（下单场景） |
|------|------|-----------------|
| Try | 预留资源 | 冻结库存 + 预扣金额 |
| Confirm | 确认执行 | 实际扣减库存 + 生成订单 |
| Cancel | 回滚补偿 | 释放冻结库存 + 回退金额 |

```java
// TCC 接口示例（基于 Seata）
@LocalTCC
public interface OrderTccService {
    @TwoPhaseBusinessAction(
        name = "createOrder",
        commitMethod = "confirmCreateOrder",
        rollbackMethod = "cancelCreateOrder"
    )
    boolean tryCreateOrder(BusinessActionContext ctx, 
                           @BusinessActionContextParameter(paramName = "orderId") Long orderId);
    
    boolean confirmCreateOrder(BusinessActionContext ctx);
    boolean cancelCreateOrder(BusinessActionContext ctx);
}
```

**优点**：性能高（无资源锁定）、最终一致
**缺点**：业务侵入大、需要实现 Try/Confirm/Cancel 三组逻辑
**适用**：账户冻结、库存预留、优惠券锁定等需要资源预留的场景

**3. Seata AT（Auto Transaction）—— 介于 XA 与 TCC 之间**

Seata AT 模式自动生成反向 SQL 实现回滚：

```sql
-- 用户执行的业务 SQL
UPDATE product SET stock = stock - 1 WHERE id = 1;

-- Seata 自动生成的回滚 SQL（记录前镜像和后镜像）
-- 前镜像：stock = 10
-- 后镜像：stock = 9
-- 回滚时执行：UPDATE product SET stock = 10 WHERE id = 1
```

**优点**：对业务代码侵入低，接近无感
**缺点**：对数据库表结构有要求（必须有主键）、全局锁影响并发、复杂 SQL 可能不支持
**适用**：希望少改造但用数据库的事务场景

**4. 本地消息表 —— 最终一致性方案**

```
核心思想：利用本地数据库事务 + MQ 实现最终一致性

订单服务（本地事务）：
  ① INSERT INTO orders ...            -- 创建订单
  ② INSERT INTO msg_local ...         -- 插入消息表（同事务）
  ③ 事务提交后，异步将消息发送到 MQ
  ④ 定时任务扫描未发送的消息 → 重试发送
  
库存服务（MQ 消费者）：
  ⑤ 收到消息 → 扣减库存 → 消费成功确认
  ⑥ 消费失败 → 自动重试 / 死信队列 / 人工介入
```

**优点**：简洁、可靠（依赖本地事务）
**缺点**：消息表与业务表耦合、定时扫描有延迟
**适用**：订单履约、积分发放、物流状态更新等

**5. MQ 事务消息（RocketMQ）**

RocketMQ 提供了原生的事务消息支持（Kafka 通过 EOS 也能实现，但更复杂）：

```java
// 1. 发送半消息（Half Message）—— 消费者暂时不可见
TransactionMQProducer producer = new TransactionMQProducer("order_group");
producer.setTransactionListener(new TransactionListener() {
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        // 2. 执行本地事务（如创建订单）
        boolean success = orderService.createOrder(arg);
        return success ? LocalTransactionState.COMMIT_MESSAGE 
                       : LocalTransactionState.ROLLBACK_MESSAGE;
    }
    
    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // 3. 回查：如果 MQ 未收到 commit/rollback，主动回查本地事务状态
        return orderService.checkOrderStatus(msg.getKeys()) 
               ? LocalTransactionState.COMMIT_MESSAGE 
               : LocalTransactionState.ROLLBACK_MESSAGE;
    }
});
producer.sendMessageInTransaction(msg, null);
```

**优点**：消息与事务绑定，无需额外消息表
**缺点**：依赖 RocketMQ、需实现回查接口
**适用**：同本地消息表场景，但要求更高的解耦性

#### 三、方案选型对比

| 方案 | 一致性 | 业务侵入 | 性能 | 适用场景 |
|------|-------|---------|------|---------|
| XA/2PC | 强一致 | 低 | 低（锁） | 金融转账、账务系统 |
| TCC | 最终一致 | **高** | 高 | 库存冻结、资源预留 |
| Seata AT | 最终一致 | 低 | 中 | 少改造的增删改场景 |
| 本地消息表 | 最终一致 | 中 | 高 | 订单履约、积分发放 |
| MQ 事务消息 | 最终一致 | 中 | 高 | 同本地消息表（更解耦） |
| Saga | 最终一致 | 高 | 高 | 长事务链路、旅行预订 |

#### 四、选型决策树

```
是否需要强一致性？
 ├─ 是 → 能用单库事务吗？
 │      ├─ 能 → 本地 @Transactional（最简单）
 │      └─ 不能 → XA / 2PC（性能代价大）
 └─ 否 → 能接受业务侵入？
        ├─ 是 → TCC（高绩效链路短） / Saga（长链路）
        └─ 否 → Seata AT（少改代码） / MQ 事务消息（解耦好）
```
