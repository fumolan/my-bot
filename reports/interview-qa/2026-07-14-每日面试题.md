#### 一、Java 26 三大核心方向（2026年3月发布）

Java 26 虽为非 LTS 版本，但带来的 10 项 JDK 增强提案（JEP）聚焦三大方向，是未来技术演进的重要风向标。

**1. AI 集成：Vector API 正式版（JEP 485）**

Vector API 从 JDK 16 开始孵化，历经 11 轮迭代，终于在 Java 26 中转为正式特性。它让 Java 开发者无需 JNI 或第三方库即可直接使用 CPU 的 SIMD（单指令多数据流）指令集进行向量计算。

```java
// Java 26 Vector API — AI 推理场景中的向量计算
import jdk.incubator.vector.*;

public class VectorDemo {
    static final VectorSpecies<Float> SPECIES = FloatVector.SPECIES_256;
    
    // 传统的标量计算（逐个元素处理）
    public static float[] softmaxScalar(float[] input) {
        float max = Float.NEGATIVE_INFINITY;
        for (float v : input) max = Math.max(max, v);
        
        float sum = 0;
        float[] exp = new float[input.length];
        for (int i = 0; i < input.length; i++) {
            exp[i] = (float) Math.exp(input[i] - max);
            sum += exp[i];
        }
        
        for (int i = 0; i < input.length; i++) {
            exp[i] /= sum;
        }
        return exp;
    }
    
    // Vector API 向量化计算（SIMD，一次处理 8 个 float）
    public static float[] softmaxVector(float[] input) {
        float max = Float.NEGATIVE_INFINITY;
        // 向量化求最大值
        for (int i = 0; i < input.length; i += SPECIES.length()) {
            FloatVector v = FloatVector.fromArray(SPECIES, input, i);
            max = Math.max(max, v.reduceLanes(VectorOperators.MAX));
        }
        
        float sum = 0;
        float[] exp = new float[input.length];
        // 向量化求 exp 和 sum
        for (int i = 0; i < input.length; i += SPECIES.length()) {
            FloatVector v = FloatVector.fromArray(SPECIES, input, i);
            FloatVector e = v.sub(max).lanewise(VectorOperators.EXP); // 向量化 exp
            e.intoArray(exp, i);
            sum += e.reduceLanes(VectorOperators.ADD);
        }
        
        // 归一化
        for (int i = 0; i < input.length; i++) {
            exp[i] /= sum;
        }
        return exp;
    }
}
// 实测：Vector API 版本比标量版本快 3-5 倍，AI 推理场景提速 50%+
```

**1. 虚拟线程核心原理**

```

虚拟线程（用户态）         平台线程（内核态）
┌─────────────────┐       ┌─────────────────┐

└─────────────────┘    │

```

## 题目 2：[分布式/微服务] 分布式事务与数据一致性：从 CAP/BASE 理论到 Seata/TCC/消息队列的完整方案对比

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-14 日报 — "场景题压倒八股文：面试官追问'分布式环境下如何保证数据一致性'"
**相关岗位**：Java后端 / 全栈 / 架构师

### 📖 参考答案

#### 一、CAP 理论与分布式事务的困境

```
CAP 定理核心：分布式系统最多同时满足两个特性

        一致性 (C)
        所有节点看到相同数据
            /\
           /  \
          /    \
         /______\
可用性 (A)      分区容忍性 (P)
每次请求都能    系统能容忍网络分区
得到响应         （分布式系统必选）

实际选择：
  CP 系统（放弃可用性）：ZooKeeper、Etcd
  AP 系统（放弃强一致性）：Eureka、大部分微服务
  CA 系统（放弃分区容忍）：单体数据库（分布式中不存在）
```

**BASE 理论：AP 系统的妥协方案**

```
BASE = Basically Available（基本可用）
     + Soft State（软状态）
     + Eventually Consistent（最终一致性）

核心思想：放弃强一致性，允许一段时间内的数据不一致，
          但保证最终所有副本数据一致。
```

#### 二、五大分布式事务方案对比

| 方案 | 一致性 | 性能 | 复杂度 | 适用场景 | 典型框架 |
|------|:------:|:----:|:------:|---------|:--------:|
| **XA（2PC）** | 强一致 | 低 | 低 | 短事务、跨库 | Atomikos |
| **AT（Seata）** | 最终一致 | 中 | 中 | 通用微服务 | Seata |
| **TCC** | 最终一致 | 高 | 高 | 高并发、短事务 | Seata TCC |
| **Saga** | 最终一致 | 高 | 中 | 长事务、异步 | Seata Saga |
| **本地消息表** | 最终一致 | 高 | 中 | 异步解耦 | RocketMQ |

#### 三、Seata AT 模式（自动补偿型）

**工作原理：**
```
Seata AT 模式的核心：两阶段 + 反向 SQL 自动生成回滚

阶段一（业务阶段）：
  ① TM（事务管理器）向 TC（事务协调器）开启全局事务
  ② RM（资源管理器）执行业务 SQL，Seata 自动拦截
  ③ 生成 undo log（快照前镜像 + 后镜像）
  ④ 本地事务提交，锁资源保留

阶段二（提交/回滚阶段）：
  ✅ 提交：TC 通知各 RM 删除 undo log，释放资源锁
  ❌ 回滚：TC 通知各 RM，根据 undo log 生成反向 SQL 恢复数据
```

```java
// Seata AT 模式使用示例
@GlobalTransactional(name = "create-order", rollbackFor = Exception.class)
public void createOrder(CreateOrderRequest request) {
    // 1. 扣减库存（Seata 自动管理本地事务）
    inventoryService.deduct(request.getProductId(), request.getQuantity());
    
    // 2. 扣减余额
    accountService.debit(request.getUserId(), request.getAmount());
    
    // 3. 创建订单
    orderService.insert(request);
    
    // 任一环节失败 → 全局回滚
    // Seata 自动根据 undo log 生成补偿 SQL
}
```

**AT 模式的优缺点：**
- ✅ 对业务代码侵入小（类似声明式事务）
- ✅ 自动生成回滚 SQL（无需手动写补偿逻辑）
- ❌ 阶段一锁定资源时间长（不适合长事务）
- ❌ 不适合跨行大量数据操作（undo log 膨胀）

#### 四、TCC 模式（手动补偿型）

**TCC 三阶段：**
```
Try（预留资源）→ Confirm（确认执行）→ Cancel（回滚释放）

以"下单扣库存"为例：

┌──────────┐    ┌──────────┐    ┌──────────┐
│   Try    │───→│ Confirm  │───→│  完成    │
│ 冻结库存  │    │ 扣减冻结  │    │          │
│ 冻结余额  │    │ 扣减冻结  │    │          │
└──────────┘    └──────────┘    └──────────┘
       │
       ▼
  ┌──────────┐
  │  Cancel  │
  │ 释放冻结  │
  │ 回滚操作  │
  └──────────┘
```

```java
// TCC 模式实现
@LocalTCC
public class InventoryTccAction {

    @TwoPhaseBusinessAction(
        name = "deductStock",
        commitMethod = "confirm",
        rollbackMethod = "cancel"
    )
    public boolean tryDeduct(BusinessActionContext ctx,
                             @BusinessActionContextParameter("productId") Long productId,
                             @BusinessActionContextParameter("quantity") Integer quantity) {
        // Try：冻结库存（不直接扣减）
        return inventoryMapper.freezeStock(productId, quantity) > 0;
    }

    public boolean confirm(BusinessActionContext ctx) {
        // Confirm：确认扣减（将冻结转为实际扣减）
        Long productId = (Long) ctx.getActionContext("productId");
        Integer quantity = (Integer) ctx.getActionContext("quantity");
        return inventoryMapper.confirmDeduct(productId, quantity) > 0;
    }

    public boolean cancel(BusinessActionContext ctx) {
        // Cancel：释放冻结
        Long productId = (Long) ctx.getActionContext("productId");
        Integer quantity = (Integer) ctx.getActionContext("quantity");
        return inventoryMapper.unfreezeStock(productId, quantity) > 0;
    }
}
```

**TCC 的优缺点：**
- ✅ 资源锁只在 Try 阶段短暂持有，性能优于 AT
- ✅ 适合高并发场景
- ❌ 业务侵入大，需手动实现 Try/Confirm/Cancel 三个方法
- ❌ Cancel 方法必须幂等（可能重复调用）

#### 五、本地消息表 + 消息队列（最终一致性）

```
最佳实践：RocketMQ 事务消息

┌──────────┐     ┌──────────┐     ┌──────────┐
│ 订单服务  │     │ RocketMQ │     │ 库存服务  │
│          │     │          │     │          │
│ ① 发送半消息│───→│ 半消息   │     │          │
│ ② 执行本地 │     │ (不可见) │     │          │
│    事务   │     │          │     │          │
│ ③ 提交/回滚│───→│ 提交→可见│───→│ ④ 消费消息│
│    事务消息│     │ 回滚→删除│     │ 扣减库存  │
└──────────┘     └──────────┘     └──────────┘
```

```java
// RocketMQ 事务消息（最佳实践）
@Component
public class OrderTransactionListener implements TransactionListener {

    @Autowired
    private OrderMapper orderMapper;

    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            // 执行本地事务（创建订单）
            CreateOrderRequest request = (CreateOrderRequest) arg;
            orderMapper.insert(request);
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }

    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // 回查：根据订单号检查本地事务是否成功
        String orderId = msg.getKeys();
        Order order = orderMapper.selectById(orderId);
        return order != null ? 
            LocalTransactionState.COMMIT_MESSAGE : 
            LocalTransactionState.ROLLBACK_MESSAGE;
    }
}
```

### 💡 延伸思考
1. **Seata AT 模式的全局锁和本地锁如何避免死锁？** — Seata 使用全局锁（Global Lock）配合本地锁，所有分支事务按顺序获取全局锁，避免循环等待。但在高并发下仍可能出现锁冲突超时，建议控制全局事务的执行时间。
2. **Saga 模式的补偿操作如何保证幂等？** — 补偿操作必须设计为幂等，可以通过唯一业务流水号 + 状态机来实现，确保同一补偿操作执行多次结果一致。

## 题目 3：[微服务/云原生] 微服务全链路追踪设计与实现：Trace/Span 模型、OpenTelemetry 规范与 SkyWalking 实践

### 📖 参考答案

#### 一、为什么需要全链路追踪？

```
微服务架构下的排查困境：

用户下单慢 → 涉及 5 个服务、3 个数据库、2 个缓存
┌────────┐    ┌────────┐    ┌────────┐
│ 网关   │───→│ 订单服务 │───→│ 库存服务 │
└────────┘    └────────┘    └────────┘
                  │               │
                  ▼               ▼
             ┌────────┐    ┌────────┐
             │ 用户服务 │    │ 支付服务 │
             └────────┘    └────────┘
                  │               │
                  ▼               ▼
             ┌────────┐    ┌────────┐
             │ MySQL  │    │ Redis  │
             └────────┘    └────────┘

问题：一个请求到底慢在哪里？
- 是订单服务 SQL 慢？→ 慢查询日志
- 是库存服务调用慢？→ HTTP 耗时
- 是 Redis 访问慢？→ 缓存命中率
- 还是网关本身？→ 网络延迟

没有链路追踪：逐台机器翻日志，大海捞针
有链路追踪：一键查看调用链，精准定位瓶颈
```

#### 二、核心数据模型：Trace 与 Span

```
Trace（一次完整请求的全链路）：

一个 Trace = N 个 Span 组成的有向无环图（DAG）

时间线 →
┌────────────────────────────────────────────────────┐
│ TraceID: a1b2c3d4                                  │
│                                                    │
│ Span A [网关]  ──────────────────────               │
│  ├─ Span B [订单服务] ────────────                  │
│  │    ├─ Span D [MySQL: 查询订单]                   │
│  │    └─ Span E [Redis: 查询缓存]                   │
│  └─ Span C [库存服务] ────────────                  │
│       └─ Span F [RPC: 远程调用]                     │
└────────────────────────────────────────────────────┘
```

#### 三、上下文传播机制

**TraceId 如何在服务间传递？**


## 题目 4：[Java并发/JDK] Java 21 虚拟线程的 Pinning 问题、ThreadLocal 陷阱及生产避坑指南

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-14 日报 — "Java 21 LTS 全面落地：虚拟线程进入生产环境" + 2026-07-13 日报 — "JDK17+SpringBoot3 新特性"
**相关岗位**：Java后端 / 全栈 / 基础架构

### 📖 参考答案

#### 一、虚拟线程的 Pinning（固定）问题

**什么是 Pinning？**

当虚拟线程进入 `synchronized` 代码块时，它会被"固定"（Pinned）到当前的载体线程（Carrier Thread），无法被卸载和迁移。

```
正常情况（无 Pinning）：

时间线 →
VirtualThread-A: [运行]──[I/O 阻塞]──[卸载]──[恢复运行]──[完成]
Carrier-1:      [VT-A  ]──[VT-B   ]──[VT-C ]──[VT-A   ]
Carrier-2:      [VT-C  ]──[VT-A   ]──[VT-B ]──[VT-C   ]

虚拟线程可以灵活挂载/卸载到不同载体线程
一个载体线程阻塞时，其他虚拟线程仍可运行

Pinning 情况（synchronized 块中）：

VirtualThread-A: [synchronized{...}]────[I/O 阻塞]────[...]
Carrier-1:      [VT-A(pinned)       ]────[VT-A 被阻塞]──[...]
Carrier-2:      [VT-B               ]──[VT-C          ]

synchronized 块中的 I/O 阻塞会同时阻塞载体线程！
载体线程无法去执行其他虚拟线程 → 吞吐量骤降
```

**Pinning 产生的两个条件：**

```
条件 1：synchronized 块 + 阻塞操作
  synchronized (lock) {
      Thread.sleep(1000);     // ❌ Pinning！阻塞操作在锁内
      httpClient.send(...);   // ❌ Pinning！I/O 在锁内
  }

条件 2：synchronized 块 + 类初始化
  class MyClass {
      static { /* 耗时初始化 */ }  // ❌ 类加载时的 Pinning
  }
```

**JDK 26 的改进：**
- 修复了虚拟线程在等待其他线程执行类初始化器时的 pinning 问题
- 虚拟线程现在会从载体线程卸载，而非固定住
- 但仍需注意 `synchronized` 块中的阻塞操作

**如何诊断 Pinning？**

```bash
# 使用 JFR 录制（JDK 21+）
-XX:StartFlightRecording=filename=flight.jfr,duration=60s,settings=profile

# JMC 中查看 "Virtual Thread Pinning" 事件
# 定位到被固定的虚拟线程和对应的 synchronized 代码
```

**如何避免 Pinning？**

```java
// ❌ 有 pinning 风险
public synchronized void processOrder(Order order) {
    validate(order);
    Thread.sleep(100);  // 阻塞操作在锁内 → Pinning
    deductStock(order);
}

// ✅ 方案一：用 ReentrantLock 替代 synchronized
private final Lock lock = new ReentrantLock();

public void processOrder(Order order) {
    lock.lock();
    try {
        validate(order);
        Thread.sleep(100);  // ReentrantLock 不会 Pinning
        deductStock(order);
    } finally {
        lock.unlock();
    }
}

// ✅ 方案二：缩小 synchronized 范围
public void processOrder(Order order) {
    synchronized (this) {
        validate(order);
    }
    Thread.sleep(100);  // 阻塞操作在锁外
    deductStock(order);  // 非线程安全操作，但可接受
}

// ✅ 方案三：使用 java.util.concurrent 工具
private final Semaphore semaphore = new Semaphore(10);

public void processOrder(Order order) {
    semaphore.acquire();  // 不会 Pinning
    try {
        validate(order);
        Thread.sleep(100);
        deductStock(order);
    } finally {
        semaphore.release();
    }
}
```

#### 二、ThreadLocal 陷阱：百万虚拟线程下的 OOM

**问题根源：** 虚拟线程池中的线程不会被回收，ThreadLocal 值会持续累积。

```java
// ❌ 危险代码：虚拟线程 + ThreadLocal
private static final ThreadLocal<UserContext> contextHolder = new ThreadLocal<>();

// 每个虚拟线程设置 context
public void handleRequest(Request request) {
    UserContext ctx = buildContext(request);
    contextHolder.set(ctx);  // ❌ 虚拟线程结束后，ThreadLocal 值不会被清理
    try {
        process(ctx);
    } finally {
        // 容易忘记 remove()
        // contextHolder.remove();  // ✅ 必须手动清理
    }
}
```

**为什么传统线程池没这问题？**

```
传统线程池（10 个平台线程）：
  ThreadLocal 最多 10 个值 → 内存可控 ✅

虚拟线程池（100 万个虚拟线程）：
  ThreadLocal 可能积累 100 万个值 → OOM ❌
```

**最佳实践：**

```java
// ✅ 方案一：try-finally 确保 remove()
private static final ThreadLocal<UserContext> contextHolder = new ThreadLocal<>();

public void handleRequest(Request request) {
    UserContext ctx = buildContext(request);
    contextHolder.set(ctx);
    try {
        process(ctx);
    } finally {
        contextHolder.remove();  // 必须清理！
    }
}

// ✅ 方案二：用 try-with-resources 模式（JDK 21+）
// 自定义 AutoCloseable 封装
public class CloseableContext implements AutoCloseable {
    private final ThreadLocal<UserContext> holder;
    private final UserContext ctx;
    
    public CloseableContext(ThreadLocal<UserContext> holder, UserContext ctx) {
        this.holder = holder;
        this.ctx = ctx;
        holder.set(ctx);
    }
    
    @Override
    public void close() {
        holder.remove();  // 自动清理
    }
}

// 使用
try (var ctx = new CloseableContext(contextHolder, buildContext(request))) {
    process(ctx.getContext());
}  // 自动 remove() ✅
```

#### 三、虚拟线程适用/不适用场景速查表

| 场景 | 是否适合 | 原因 |

## 题目 5：[Python后端/全栈] FastAPI 异步编程与 asyncio 原理详解：协程、事件循环与 ASGI 架构

**难度**：⭐⭐⭐
**考点来源**：2026-07-14 日报 — "Python后端必备：FastAPI/Django + 异步编程(asyncio)" + "Python+Vue全栈、Python+AI方向薪资 20-40k"

#### 一、异步编程的本质：同步 vs 异步

```
同步编程（一个人做三件事）：
  开始做菜 → 等水烧开（发呆10分钟）→ 切菜 → 等饭煮熟（发呆20分钟）→ 吃饭
  总时间：30分钟 + 实际干活时间

异步编程（合理安排三件事）：
  开始烧水 → 等水烧开时切菜 → 水开了下锅 → 等饭煮熟时做别的 → 吃饭
  总时间：≈ 实际干活时间
```

```
同步 vs 异步的代码对比：

同步（Synchronous）：           异步（Asynchronous）：
def fetch_data(url):            async def fetch_data(url):
    resp = requests.get(url)        resp = await http_client.get(url)
    return resp.text                return resp.text
    
顺序执行，每步阻塞          遇到 await 挂起，事件循环调度其他任务
```

**核心优势：** 在 I/O 密集型场景下，异步编程可以在等待 I/O 时执行其他任务，大幅提升吞吐量。

#### 二、asyncio 三大核心组件

**1. 协程（Coroutine）**
```python
import asyncio

# 定义一个协程函数
async def fetch_data(url: str) -> dict:
    print(f"开始请求: {url}")
    await asyncio.sleep(1)  # 模拟 I/O 等待
    print(f"完成请求: {url}")
    return {"url": url, "data": "mock_data"}

# 协程不会自动执行，需要 await 或创建 Task
# coro = fetch_data("http://example.com")  # 创建协程对象，不执行
# result = await coro  # 执行协程，等待结果
```

**2. 事件循环（Event Loop）**
```python
# 事件循环的工作流程
async def main():
    # 创建多个协程任务
    task1 = asyncio.create_task(fetch_data("https://api1.example.com"))
    task2 = asyncio.create_task(fetch_data("https://api2.example.com"))
    task3 = asyncio.create_task(fetch_data("https://api3.example.com"))
    
    # 并发执行三个任务
    results = await asyncio.gather(task1, task2, task3)
    return results

# 运行事件循环
asyncio.run(main())
```

```
事件循环调度原理：

时间线 →
Task-A: [请求1]──[await 等待]──────[恢复]──[完成]
Task-B: [请求2]──[await 等待]──[恢复]──[完成]
Task-C:         [请求3]──[等待]──[恢复]──[完成]
        ↑                                          ↑
   事件循环调度                                  所有完成

实际耗时 ≈ 最慢的任务耗时（3个任务各1秒 → 总耗时约1秒）
同步执行：3秒 → 异步执行：1秒 ✅
```

**3. Task（任务）**
```python
# Task 是对协程的进一步封装
async def main():
    # create_task：将协程包装为 Task，立即调度执行
    task = asyncio.create_task(fetch_data("https://example.com"))
    
    # 可以检查任务状态
    print(f"任务已完成: {task.done()}")
    print(f"任务已取消: {task.cancelled()}")
    
    # 等待任务完成并获取结果
    result = await task
    
    # 超时控制
    try:
        result = await asyncio.wait_for(task, timeout=5.0)
    except asyncio.TimeoutError:
        print("请求超时")
```

#### 三、FastAPI + ASGI 架构

FastAPI 基于 Starlette（ASGI 框架），采用 ASGI（Asynchronous Server Gateway Interface）协议替代传统的 WSGI。

```
传统 WSGI vs 现代 ASGI：

WSGI（同步，如 Flask/Django 传统模式）：
  Client → Nginx → Gunicorn(WSGI) → Flask App
  一个请求占用一个工作线程，线程数有限

ASGI（异步，如 FastAPI）：
  Client → Nginx → Uvicorn(ASGI) → FastAPI App
  一个事件循环处理所有请求，I/O 等待时切换
```

**FastAPI 请求处理流程：**
```
FastAPI 并发模型：

Uvicorn（ASGI Server）
    │ 事件循环
    ▼
┌─────────────────────────────────────────┐
│  FastAPI Application                     │
│                                          │
│  请求 1 → async def handler()            │
│            └─ await db.fetch() ← 挂起    │
│               └─ 处理请求 2              │
│                   └─ await redis.get()   │
│                      └─ 恢复请求 1       │
│                          └─ 返回响应     │
└─────────────────────────────────────────┘
```

**FastAPI 实战代码：**
```python
from fastapi import FastAPI, Depends, HTTPException
from fastapi.concurrency import run_in_threadpool
import asyncpg  # 异步 PostgreSQL 驱动
import aiohttp  # 异步 HTTP 客户端

app = FastAPI(title="Async API Service")

# 异步路由处理函数

    # 异步数据库查询（非阻塞）
    user = await db.fetch_user(user_id)
    if not user:
        raise HTTPException(status_code=404, detail="User not found")
    
    # 并发请求多个外部 API
    async with aiohttp.ClientSession() as session:
        tasks = [
            fetch_user_orders(session, user_id),
            fetch_user_profile(session, user_id)
```

### 💡 延伸思考
1. **async/await 和生成器（yield）的关系？** — 协程本质上是"增强版生成器"，`await` 类似于 `yield from`。事件循环类似于驱动生成器的 `send()` 方法，但协程可以嵌套调用，语法更简洁。
