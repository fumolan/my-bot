## 题目 1：[Java基础] 请详细说明 HashMap 的底层数据结构、put 方法执行流程、JDK 1.8 的核心优化点以及扩容机制

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-07 午间报告 — 腾讯后端面经 "HashMap冲突解决/Java8优化"
**相关岗位**：Java后端 / 全栈

### 📖 参考答案

#### 一、底层数据结构

HashMap 底层采用 **数组 + 链表 + 红黑树** 的复合结构（JDK 1.8+）：

```
table数组 (Node<K,V>[])
  ├── 桶0: Node(hash, key, val, next) → null
  ├── 桶1: null
  ├── 桶2: Node → Node → Node  (链表，长度≤7)
  ├── 桶3: TreeNode ←→ TreeNode ←→ TreeNode  (红黑树，链表长度≥8且数组长度≥64)
  └── ...
```

- **Node<K,V>[] table**：哈希桶数组，长度必须为 2 的 n 次方
- **Node**：链表节点，包含 hash、key、value、next 四个字段
- **TreeNode**：红黑树节点（继承自 LinkedHashMap.Entry），当链表长度 >= 8 且数组长度 >= 64 时链表树化

#### 二、put 方法执行流程

```java
public V put(K key, V value) {
    return putVal(hash(key), key, value, false, true);
}
```

**Step 1：计算 key 的 hash 值（扰动处理）**

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

将 hashCode 的高 16 位与低 16 位进行异或，让高 16 位也参与取模运算，减少哈希碰撞。

**Step 2：计算桶下标**

```java
// 等价于 hash % table.length，但位运算效率更高
int index = (table.length - 1) & hash;
```

**Step 3：putVal 完整流程**

```
put(key, value)
  │
  ├─ 1. table 为 null 或长度为 0 → resize() 初始化（默认容量 16）
  │
  ├─ 2. 计算 index = (n - 1) & hash(key)
  │
  ├─ 3. 判断 table[index] 是否为空
  │    ├─ 是 → 直接插入新 Node
  │    └─ 否 → 发生哈希冲突
  │         ├─ 3.1 检查头节点 hash 和 key 是否匹配 → 匹配则直接覆盖
  │         ├─ 3.2 如果头节点是 TreeNode → 调用红黑树的 putTreeVal
  │         └─ 3.3 否则遍历链表
  │              ├─ 找到匹配 key → 覆盖 value
  │              ├─ 遍历到链表尾部 → 尾插法插入新 Node
  │              └─ 如果链表长度 >= 8 → 调用 treeifyBin() 尝试树化
  │
  └─ 4. 检查 ++size > threshold → 是则 resize() 扩容
```

#### 三、JDK 1.8 的核心优化（对比 JDK 1.7）

| 优化点 | JDK 1.7 | JDK 1.8 |
|--------|---------|---------|
| 数据结构 | 数组 + 链表 | 数组 + 链表 + 红黑树 |
| 链表插入 | 头插法（多线程死循环） | 尾插法（避免死循环） |
| Hash 计算 | 4 次位运算 + 5 次异或 | 1 次异或 (h >>> 16) |
| 扩容后元素迁移 | 重新 hash 计算 | 原位置 or 原位置+旧容量 |
| 扩容条件 | 容量超阈值且当前桶非空 | 容量超阈值即可 |

**红黑树引入条件**：
- 链表长度 >= 8 **且** 数组长度 >= 64 → 树化
- 链表长度 >= 8 **但** 数组长度 < 64 → 优先扩容
- 红黑树节点数 <= 6 → 退化为链表

#### 四、扩容机制

```java
final Node<K,V>[] resize() {
    // 新容量 = 旧容量 << 1（翻倍）
    // 新阈值 = 新容量 × 0.75
    // 元素迁移：e.hash & oldCap == 0 → 留在原位
    //                               != 0 → 移动到 原位置 + oldCap
}
```

**JDK 1.8 扩容优化**：由于容量总是 2 的 n 次方，扩容翻倍后，元素的新索引要么在原位置，要么在"原位置 + 旧容量"。通过 `hash & oldCap` 即可判断，无需重新计算 hash，高效且保持了均匀分布。

```
示例（容量从 16 扩容到 32）：
  oldCap = 16 = 0b10000
  hash & 16 == 0  → 索引不变
  hash & 16 != 0  → 索引 + 16
```

### 💡 延伸思考
1. **为什么 HashMap 的容量必须是 2 的 n 次方？** — 因为 `(n - 1) & hash` 等价于取模运算，且扩容时元素迁移只需判断 `hash & oldCap`，高效且分布均匀
2. **为什么树化阈值是 8？** — 泊松分布下，负载因子 0.75 时链表长度达到 8 的概率极低（约 0.00000006），在时间和空间上做了权衡
3. **HashMap 的线程安全问题如何解决？** — 使用 ConcurrentHashMap（分段锁/CAS）或 Collections.synchronizedMap

## 题目 2：[并发编程] 请详细说明 synchronized 的锁升级过程、底层实现原理，以及与 ReentrantLock 的核心区别

**难度**：⭐⭐⭐⭐⭐
**考点来源**：2026-07-07 午间报告 — 腾讯后端面经 "synchronized vs ReentrantLock"
**相关岗位**：Java后端 / 全栈

### 📖 参考答案

#### 一、synchronized 锁升级过程（JDK 1.6+ 偏向锁 → 轻量级锁 → 重量级锁）

JDK 1.6 引入锁升级机制后，synchronized 的性能已经不输 ReentrantLock。锁升级是**单向的**：只能从低到高，不能降级。

```
无锁 → 偏向锁 → 轻量级锁（自旋锁） → 重量级锁（OS 互斥量）
                                    ↑ 升级不可逆
```

**1. 偏向锁（Biased Locking）**

- **适用场景**：只有一个线程访问同步块
- **原理**：在对象头 Mark Word 中存储偏向线程 ID，后续该线程进入无需 CAS 操作
- **撤销条件**：当有其他线程尝试竞争时，偏向锁被撤销（需等待全局安全点 STW）
- **JDK 15 默认关闭**（高维护成本，撤销时需 STW，在并发场景下反而降低性能）

```
Mark Word (偏向锁):
| 线程ID (23bit) | Epoch (2bit) | 分代年龄 (4bit) | 偏向锁=1 | 锁标志位=01 |
```

**2. 轻量级锁（Lightweight Locking）**

- **适用场景**：多线程交替执行，竞争不激烈
- **原理**：在栈帧中创建 Lock Record，通过 CAS 尝试将对象头的 Mark Word 替换为指向 Lock Record 的指针
- **膨胀条件**：CAS 失败（有竞争）→ 自旋一定次数后升级为重量级锁

```
Mark Word (轻量级锁):
| 指向栈中Lock Record的指针 (30bit) | 锁标志位=00 |
```

**3. 重量级锁**

- **适用场景**：多线程竞争激烈，自旋等待不划算
- **原理**：依赖 OS 的 Mutex Lock，线程被阻塞挂起，涉及用户态/内核态切换
- **特点**：等待线程不消耗 CPU，但上下文切换成本高

```
Mark Word (重量级锁):
| 指向Monitor (管程) 的指针 (30bit) | 锁标志位=10 |
```

#### 二、synchronized 底层实现

synchronized 基于 **Monitor（管程）** 实现：

```java
// Java 代码
synchronized (obj) {
    // 临界区
}

// 对应的字节码（monitorenter / monitorexit）
monitorenter  // 获取 obj 的 Monitor 锁
// 临界区代码
monitorexit   // 释放 Monitor 锁
```

**ObjectMonitor 核心结构**（C++ 实现）：

```
ObjectMonitor {
    _owner        // 当前持有锁的线程
    _cxq          // 竞争队列（Contention Queue）
    _EntryList    // 等待获取锁的线程队列
    _WaitSet      // 调用了 wait() 的线程等待队列
    _recursions   // 重入次数
    _count        // 锁计数器
}
```

#### 三、synchronized vs ReentrantLock 核心区别

| 对比维度 | synchronized | ReentrantLock |
|---------|-------------|---------------|
| **实现方式** | JVM 层面（关键字） | JDK 层面（API） |
| **锁类型** | 非公平锁 | 公平锁 / 非公平锁（默认） |
| **锁获取** | 隐式获取/释放 | 需手动 lock()/unlock() |
| **可中断** | 不支持（不可中断等待） | 支持 lockInterruptibly() |
| **超时等待** | 不支持 | 支持 tryLock(timeout, unit) |
| **条件变量** | 每个对象一个条件（wait/notify） | 支持多个 Condition（精准唤醒） |
| **性能** | JDK 1.8+ 已非常接近 | 高并发下略有优势 |
| **锁升级** | 内置偏向→轻量→重量 | 无锁升级，直接使用 AQS |
| **调试** | 支持（JVM 锁信息 dump） | 支持（更方便） |

**选择建议**：
- 大多数场景用 **synchronized**（代码简洁，JVM 自动优化）
- 需要超时、可中断、多条件变量时用 **ReentrantLock**

#### 四、ReentrantLock 底层原理（AQS）

ReentrantLock 基于 **AbstractQueuedSynchronizer (AQS)** 实现：

```java
// 核心：CAS 操作 state 状态变量 + CLH 变体队列
public class ReentrantLock {
    private final Sync sync;  // 内部类，继承 AQS
    
    // 非公平锁实现
    static final class NonfairSync extends Sync {
        final void lock() {
            if (compareAndSetState(0, 1))  // CAS 尝试直接获取
                setExclusiveOwnerThread(Thread.currentThread());
            else
                acquire(1);  // 加入等待队列
        }
    }
    
    // 公平锁实现
    static final class FairSync extends Sync {
        final void lock() {
            acquire(1);  // 直接 acquire，排队获取
        }
        // hasQueuedPredecessors() 检查是否有前驱线程等待
    }
}
```

AQS 核心是 **CLH 队列 + state 状态**：
- **state = 0**：锁未被持有
- **state = 1**：锁被持有
- **state = N（N>1）**：可重入计数

### 💡 延伸思考
1. **为什么 JDK 15 默认关闭偏向锁？** — 偏向锁撤销需要在全局安全点暂停所有线程，在高并发场景下维护成本高，关闭后性能反而更好
2. **CAS 的 ABA 问题如何解决？** — 通过版本号（AtomicStampedReference）或时间戳
3. **锁粗化与锁消除** — JVM 编译优化：合并连续的同步块（粗化），消除不存在竞争的锁（消除）

> 🔗 参考来源：Java 官方文档 / 《深入理解Java虚拟机》/ AQS 源码分析

## 题目 3：[数据库/MySQL] 请详细说明 MySQL InnoDB 聚簇索引与非聚簇索引的数据存储结构、区别及最佳实践

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-07 午间报告 — 腾讯后端面经 "聚簇vs非聚簇索引"
**相关岗位**：Java后端 / 全栈 / DBA

### 📖 参考答案

#### 一、聚簇索引（Clustered Index）

**定义**：聚簇索引的**叶子节点直接存储完整行数据**，数据行物理上按索引顺序存储。

**InnoDB 规则**：
1. 有主键 → 主键作为聚簇索引
2. 无主键但有唯一非空索引 → 第一个唯一索引作为聚簇索引
3. 都无 → 隐式生成 6 字节的 ROWID（DB_ROW_ID）作为聚簇索引

**结构示意**（B+ 树）：

```
聚簇索引 B+ 树
                    ┌──────────────────────────────┐
                    │        [主键范围: 1-100]       │  ← 非叶子节点
                    │    [30]       [60]      [90]  │     存主键值
                    └─────┬──────────┬──────────┬──┘
                          │          │          │
         ┌────────────────┘          │          └────────────────┐
         ▼                           ▼                           ▼
┌───────────────────┐   ┌───────────────────┐   ┌───────────────────┐
│  [1] [2]...[30]   │   │ [31][32]...[60]   │   │ [61][62]...[90]   │  ← 叶子节点
│ id=1, name=张三   │   │ id=31, name=李四   │   │ id=61, name=王五   │     存完整行数据
│ age=25, salary=15k│   │ age=30, salary=18k │   │ age=28, salary=20k│
└───────────────────┘   └───────────────────┘   └───────────────────┘
```

**特点**：
- 表中只能有一个聚簇索引（数据只能按一种顺序物理存储）
- 叶子节点包含所有列数据，查询直接返回（**无需回表**）
- 数据按主键顺序物理排列，**范围查询高效**
- 插入速度受主键顺序影响（**自增主键推荐**）

#### 二、非聚簇索引（Secondary Index / 辅助索引）

**定义**：非聚簇索引的**叶子节点存储主键值**（InnoDB），而非行数据。

**结构示意**：

```
非聚簇索引 B+ 树（以 age 字段为例）
                    ┌──────────────────────────────┐
                    │     [age 范围: 1-100]         │  ← 非叶子节点
                    │   [25]      [30]      [35]    │     存 age 值
                    └─────┬──────────┬──────────┬──┘
                          │          │          │
         ┌────────────────┘          │          └────────────────┐
         ▼                           ▼                           ▼
┌───────────────────┐   ┌───────────────────┐   ┌───────────────────┐
│ [25][25][27][30]  │   │ [30][31][31][32]  │   │ [35][36][38][40]  │  ← 叶子节点
│ 主键:1,3,5,7     │   │ 主键:2,8,9,12    │   │ 主键:4,6,10,15   │     存主键值
└───────────────────┘   └───────────────────┘   └───────────────────┘
                              │
                              ▼ (回表)
                    ┌───────────────────┐
                    │ 主键索引          │
                    │ id=2, 完整行数据  │
                    └───────────────────┘
```

**特点**：
- 一个表可以有多个非聚簇索引（最多 64 个）
- 叶子节点存储 **主键值 + 索引列值**
- 查询非索引列需要 **回表**（通过主键到聚簇索引中查找完整行）
- 索引列占用额外存储空间

#### 三、核心区别对比

| 对比维度 | 聚簇索引 | 非聚簇索引 |
|---------|---------|-----------|
| 叶子节点内容 | 完整行数据 | 主键值 + 索引列值 |
| 每表数量 | 1 个 | 多个 |
| 数据排序 | 物理排序 | 逻辑排序 |
| 查询效率 | 直接返回数据（无需回表） | 需回表（除非覆盖索引） |
| 插入速度 | 受主键顺序影响大 | 受主键顺序影响小 |
| 占用空间 | 数据本身，无额外空间 | 额外索引空间 |
| 范围查询 | 高效（物理连续） | 需多次回表，效率较低 |

#### 四、覆盖索引（Covering Index）—— 避免回表的优化技巧

当查询所需的所有列**都在索引中**时，无需回表：

```sql
-- 假设有联合索引 (name, age)
CREATE INDEX idx_name_age ON user(name, age);

-- 以下查询无需回表（覆盖索引）
SELECT name, age FROM user WHERE name = '张三';
-- 索引叶子节点已包含 name 和 age，直接返回

-- 以下查询需要回表（非覆盖索引）
SELECT name, age, salary FROM user WHERE name = '张三';
-- salary 不在索引中，需回表查主键索引
```

#### 五、最佳实践

1. **主键建议使用自增 ID**：UUID/雪花 ID 作为主键会导致 B+ 树频繁页分裂，降低插入性能
2. **尽量使用覆盖索引**：减少回表次数，大幅提升查询性能
3. **索引列选择性要高**：区分度高的列（如手机号 > 性别）更适合建索引
4. **联合索引遵循最左前缀原则**：`(a, b, c)` 联合索引，`WHERE a=?` 和 `WHERE a=? AND b=?` 能使用，`WHERE b=?` 不能
5. **避免对大字段建索引**：TEXT/BLOB 类型不适合直接建索引（使用前缀索引）
6. **索引数量不要过多**：写操作需维护所有索引，过多索引影响写入性能

### 💡 延伸思考
1. **为什么 InnoDB 非聚簇索引要存主键值而不是行地址？** — 避免聚簇索引重组（如页分裂）时大量更新非聚簇索引的行地址
2. **MyISAM 的索引与 InnoDB 有何不同？** — MyISAM 的索引叶子节点存行数据的物理地址，且主键索引与辅助索引无区别（都是非聚簇）
3. **如何通过 EXPLAIN 判断是否回表？** — `Extra` 列出现 `Using index` 表示覆盖索引，出现 `Using index condition` 表示 ICP（索引下推）

> 🔗 参考来源：《高性能MySQL》/ MySQL 官方文档 InnoDB Index Architecture

## 题目 4：[缓存/Redis] 请详细说明 Redis 的过期策略、内存淘汰机制及 LRU/LFU 算法的实现原理

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-07 午间报告 — 腾讯后端面经 "Redis过期策略"
**相关岗位**：Java后端 / 全栈 / 缓存开发

### 📖 参考答案

#### 一、Redis 过期策略

Redis 对设置了过期时间的 key 采用 **两种策略组合**：**惰性删除 + 定期删除**。

**1. 惰性删除（Lazy Deletion）**

- **机制**：每次访问 key 时，检查该 key 是否过期，过期则删除
- **触发点**：`get`, `set`, `exists` 等所有读写命令
- **优点**：CPU 友好，只在必要时检查
- **缺点**：已过期但长期不访问的 key 会残留，占用内存（内存不友好）

```c
// 源码简化（expireIfNeeded 函数）
int expireIfNeeded(redisDb *db, robj *key) {
    if (!keyIsExpired(db, key)) return 0;  // 未过期
    // 如果是 slave 节点，不执行删除，等待主节点通知
    if (server.masterhost) return 1;
    // 删除过期 key
    deleteExpiredKeyAndPropagate(db, key);
    return 1;
}
```

**2. 定期删除（Active Expiration / 定时抽样）**

- **机制**：Redis 主循环中的 `serverCron` 定时任务，每秒执行 10 次（默认 hz=10）
- **流程**：
  1. 从过期字典中随机抽取 20 个 key
  2. 删除其中已过期的 key
  3. 如果过期比例超过 25%，重复步骤 1
  4. 单次循环耗时上限 25ms（防止阻塞）
- **优点**：弥补惰性删除的内存泄漏问题
- **缺点**：删除不够及时（最多浪费 1 秒的过期时间）

```
Redis 过期策略组合
         ┌─────────────────────┐
         │      set key        │
         │   EXPIRE key 3600   │
         └─────────┬───────────┘
                   │
         ┌─────────┴───────────┐
         ▼                     ▼
  ┌─────────────┐      ┌──────────────┐
  │ 惰性删除    │      │ 定期删除     │
  │ (访问时检查) │      │ (每秒10次)   │
  │ CPU友好     │      │ 弥补惰性删除 │
  └─────────────┘      └──────────────┘
         │                     │
         └─────────┬───────────┘
                   ▼
          ┌──────────────────┐
          │ 如果已过期key仍残留│
          │ → 触发内存淘汰    │
          └──────────────────┘
```

#### 二、Redis 内存淘汰机制（Eviction Policy）

当 Redis 内存达到 `maxmemory` 上限时，触发淘汰策略。Redis 8 种淘汰策略：

| 策略 | 描述 | 适用场景 |
|------|------|---------|
| **noeviction**（默认） | 不淘汰，直接返回 OOM 错误 | 数据不可丢失的场景 |
| **allkeys-lru** | 所有 key 中淘汰最近最少使用的 | ✅ 最常用，缓存场景 |
| **allkeys-lfu** | 所有 key 中淘汰最不常使用的 | 访问频率差异大的场景 |
| **volatile-lru** | 有过期时间的 key 中淘汰最近最少使用的 | 混合存储场景 |
| **volatile-lfu** | 有过期时间的 key 中淘汰最不常使用的 | 混合存储场景 |
| **volatile-ttl** | 有过期时间的 key 中淘汰即将过期的 | 极少使用 |
| **allkeys-random** | 所有 key 中随机淘汰 | 缓存均匀分布场景 |
| **volatile-random** | 有过期时间的 key 中随机淘汰 | 极少使用 |

**推荐配置**：大部分缓存场景使用 `maxmemory-policy allkeys-lru`

#### 三、LRU 算法的 Redis 实现（近似 LRU）

Redis **没有实现标准的 LRU**（维护完整链表成本太高），而是使用 **近似 LRU**：

```c
// 近似 LRU 采样淘汰流程
1. 从数据库中随机抽取 maxmemory-samples 个 key（默认 5 个）
2. 比较它们的 idle time（最近未访问时长）
3. 淘汰 idle time 最大的 key
4. 如果内存仍然不足，重复以上步骤
```

**为什么是"近似"？**

- 标准 LRU：维护双向链表，每次访问都移动到链表头部（O(1) 但内存开销大）
- 近似 LRU：随机采样 5 个 key 中淘汰最旧的，用概率保证整体接近 LRU 效果
- 采样数越大，越接近标准 LRU，但 CPU 消耗也越高（默认 5 是合理平衡点）

```
标准 LRU vs 近似 LRU 对比（引用《Redis设计与实现》数据）：
  采样5个 → 近似LRU淘汰准确率 ≈ 80%
  采样10个 → 近似LRU淘汰准确率 ≈ 90%
  标准LRU → 100%
```

**Redis 4.0 改进**：引入 **LFU 模式**，淘汰策略新增 `allkeys-lfu` 和 `volatile-lfu`

#### 四、LFU 算法的 Redis 实现

LFU（Least Frequently Used）淘汰**访问频率最低**的 key。

**核心机制**：使用 **Morris Counter（概率计数器）** 来估算访问频率，而非精确计数：

```c
// 访问频率更新算法（counter 0-255，约 8bit）
// 每次访问时，counter 以概率 p 递增
// counter 越大，递增概率越低（对数增长）
uint8_t LFULogIncr(uint8_t counter) {
    if (counter == 255) return 255;  // 上限
    double r = (double)rand() / RAND_MAX;
    double p = 1.0 / (counter * 2 + 1);  // counter越大，递增概率越小
    if (r < p) counter++;
    return counter;
}
```

**频率衰减**：Redis 会基于 `lfu-decay-time`（默认 1 分钟）对 counter 进行衰减——长时间不访问的 key，counter 逐渐减小，避免"历史热度"锁定问题。

#### 五、实际配置建议

```bash
# redis.conf 配置
maxmemory 4gb                         # 最大内存
maxmemory-policy allkeys-lru          # 淘汰策略
maxmemory-samples 10                  # 采样数（提高LRU精度）
lfu-log-factor 10                     # LFU 对数因子
lfu-decay-time 1                      # LFU 衰减时间（分钟）
```

### 💡 延伸思考
1. **为什么不用标准 LRU？** — 标准 LRU 需要维护一个全量双向链表，Redis 作为单线程服务，每次操作都需加锁修改链表，性能和内存开销不可接受
2. **缓存淘汰与过期删除的区别？** — 过期删除是 key 到了 TTL 时间主动/被动删除；淘汰是内存不够时被动删除。两者互不依赖
3. **allkeys-lru vs volatile-lru 如何选择？** — 如果所有 key 都可接受淘汰，用 allkeys-lru；如果只有部分可淘汰，用 volatile-lru + 只对部分 key 设置过期时间

#### 一、为什么需要任务拆分？

AI Agent 在处理复杂任务时，面临三大挑战：

1. **LLM 上下文窗口限制**：单次 Prompt 无法容纳全部信息
2. **单步推理精度有限**：一步完成复杂推理，错误率随复杂度指数上升
3. **工具调用约束**：单次调用能调用的工具数量有限

#### 二、三种任务拆分策略

│                                              │

```

**实现方式**：

##### 2. 动态拆分（Dynamic Decomposition）

**原理**：Agent 根据任务内容动态决定如何拆分，拆分的子任务可以基于上一步结果动态调整。

```

```

**实现方式**：

- 可能陷入无限递归或子任务膨胀

**实现方式（核心伪代码）**：

class AdaptiveTaskDecomposer:
    def __init__(self):
        self.meta_knowledge = MetaKnowledgeBase()  # 元认知知识库
        self.execution_history = []
    
    def decompose(self, task: str) -> List[SubTask]:
        # 1. 元认知评估
        complexity = self.assess_complexity(task)
        similar_tasks = self.meta_knowledge.find_similar(task)
        
        # 2. 策略选择
        if complexity == "low":
            return self.static_decompose(task)
        elif complexity == "medium":
            return self.dynamic_decompose(task)
        else:
            # 高复杂度 → 自适应混合策略
            initial_plan = self.hybrid_decompose(task, similar_tasks)
            return self.execution_loop(initial_plan)
    
    def execution_loop(self, plan: List[SubTask]) -> List[SubTask]:
        while not plan.is_complete():
            subtask = plan.get_next()
            result = self.execute(subtask)
            
            # 3. 实时监控和调整
            if result.status == "failed":
                plan.add(SubTask("fix", f"修复{subtask.name}"))
            if self.detects_missing_requirement(result):
                plan.add(SubTask("new", self.generate_subtask(result)))
            if plan.is_over_budget():
                plan.merge_parallel_tasks()  # 合并并行任务
                
            # 4. 记录经验
            self.execution_history.append(result)
        
        # 5. 更新元认知知识库
        self.meta_knowledge.learn(task, plan, self.execution_history)
        return plan.get_all()
```
