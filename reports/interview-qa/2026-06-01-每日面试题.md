### 📖 参考答案

**一、2026 年面试为什么开始问这个问题？**

2026 年面试风向变了：面试官不再问"你用过什么技术"，而是问"你的系统在极端情况下会怎样"。这背后是 AI 时代对工程师的新要求——**AI 能写代码，但不能替你对生产事故负责**。

> 面试官内心 OS："我招你来不是写 CRUD 的，是让你在凌晨 2 点系统崩了的时候，能 15 分钟内定位到根因。"

**二、面试回答框架（场景话术）**

```
面试官："你们系统 QPS 峰值是多少？突然涨十倍会挂在哪里？"

60 分回答（背八股）：
  "我们系统 QPS 大概 5000，涨十倍可以用 Redis 缓存 + MQ 削峰解决。"
  （面试官：太浅了，没有具体分析）

80 分回答（有数据、有分析）：
  "我们核心交易接口 QPS 峰值约 3000，经过压测单机瓶颈在 800 QPS，
   4 台机器理论承载 3200，预留 20% 冗余。涨十倍到 30000 的话，
   首先数据库连接池会爆（当前 200 连接，需要 2000+），
   其次 Redis 热 key 会打爆单分片，最后是 MQ 积压导致消费延迟。
   扩容方案是：数据库读写分离 + 分库分表、Redis 热 key 多副本、
   MQ 动态增加 Consumer 实例。"

95 分回答（完整的容量评估体系）：
  "我们建立了一套完整的容量评估闭环："
  （然后讲下面这套方法论）
```

**三、容量评估的核心公式**

```
容量规划的基础数学模型：

QPS = (PV × 峰值系数) / (86400 × 峰值时间占比)

示例：
  日 PV = 5000 万
  峰值系数 = 3（晚高峰流量是平均的 3 倍）
  峰值时间占比 = 0.2（峰值集中在 4-5 小时内）
  
  峰值 QPS = (50000000 × 3) / (86400 × 0.2) ≈ 8680 QPS

单机容量 = 压测得到的单机最大 QPS（如 800）
所需机器数 = 峰值 QPS / (单机容量 × 0.7)  // 0.7 是安全水位线
  = 8680 / (800 × 0.7) ≈ 15.5 → 至少 16 台
```

**四、全链路压测的六大核心环节**

```
┌──────────────────────────────────────────────────────────────────┐
│                    全链路压测六步闭环                               │
├──────────────────────────────────────────────────────────────────┤
│                                                                   │
│  ① 流量染色（压测流量标记）                                        │
│     ├─ 在 Header 中注入压测标记（如 x-stress-test: true）          │
│     ├─ 全链路透传：RPC / MQ / HTTP 逐跳传递                       │
│     └─ 关键：不能被中间件丢掉（如 Gateway 过滤时需白名单）          │
│                                                                   │
│  ② 数据隔离（影子库/影子表）                                       │
│     ├─ 影子库：压测流量读写独立的压测数据库                         │
│     ├─ 影子表：在同一库中创建 _stress 后缀的表                      │
│     └─ 关键：压测数据绝对不能污染真实业务数据！                     │
│                                                                   │
│  ③ 场景建模（模拟真实流量）                                        │
│     ├─ 从生产日志中提取真实请求比例（如 30% 浏览 + 20% 搜索 + 15% 下单） │
│     ├─ 用流量回放工具（GoReplay / TCPCopy）复刻真实流量            │
│     └─ 关键：不是无脑打满，而是按比例混合                           │
│                                                                   │
│  ④ 梯度加压（逐步提升直到瓶颈）                                    │
│     ├─ 起点：当前峰值的 50%                                        │
│     ├─ 步长：每次增加 20%                                          │
│     ├─ 每梯度持续 5-10 分钟，观察系统指标                          │
│     └─ 目标：找到第一个瓶颈点 → 扩容 → 继续加压 → 找到下一个瓶颈    │
│                                                                   │
│  ⑤ 瓶颈定位（找到木桶最短的板）                                    │
│     ├─ 应用层：CPU / 内存 / 线程池 / 连接池                       │
│     ├─ 中间件：Redis 热 key / MQ 积压 / Nginx 连接数              │
│     ├─ 数据库：连接数 / 慢查询 / 锁竞争 / 主从延迟                 │
│     └─ 工具：Prometheus + Grafana + SkyWalking + Arthas           │
│                                                                   │
│  ⑥ 容量模型（建立扩容公式）                                        │
│     ├─ 记录每个瓶颈点的阈值和扩容方案                               │
│     ├─ 建立"QPS → 资源需求"的映射表                               │
│     └─ 关键：变成可复用的文档，而不是每次压测重新摸索               │
└──────────────────────────────────────────────────────────────────┘
```

**五、常见瓶颈点速查表**

| 瓶颈点 | 典型表现 | 根因 | 扩容方案 |
|--------|---------|------|---------|
| **数据库连接池** | 获取连接超时，大量线程 BLOCKED | 连接数不够 | 增大连接池 + 读写分离 |
| **Redis 热 key** | 单分片 CPU 100%，其他分片空闲 | 热点数据集中 | 热 key 多副本 + 本地缓存 |
| **MQ 积压** | 消费 Lag 持续增长 | 消费速度 < 生产速度 | 增加 Consumer 实例 + 批量消费 |
| **GC 停顿** | 接口间歇性超时 | Full GC 频繁 | 调大堆内存 + 优化 GC 策略 |
| **线程池满** | 请求被拒绝，RejectedExecutionException | 核心线程数不够 | 增大线程池 + 隔离线程池 |
| **带宽打满** | 网卡流量接近上限 | 数据传输量大 | 压缩 + CDN + 升级带宽 |
| **Nginx 连接数** | 502/504 错误 | worker_connections 不够 | 增加 worker 数 + 加机器 |

**六、扩容阈值四维指标体系**

```yaml
# 不是"CPU 到 80% 就扩容"这么简单
扩容决策四维指标:

  CPU 维度:
    - 水位线: 70%（预警）/ 85%（扩容）
    - 注意: CPU 高 ≠ 需要扩容，可能是 GC 或死循环

  内存维度:
    - 水位线: 75%（预警）/ 85%（扩容）
    - 注意: 关注 Old Gen 使用率，不是堆总大小

  响应时间维度:
    - 水位线: P99 > 500ms（预警）/ P99 > 1s（扩容）
    - 注意: P99 比平均值更能反映真实问题

  错误率维度:
    - 水位线: 1%（预警）/ 5%（扩容）
    - 注意: 区分业务错误和系统错误
```

**八、面试加分项：能说出"反直觉"的经验**

```
① CPU 不是越高越好
   → 50% CPU 但 P99 很高 → 可能 IO 等待或锁竞争，需要看线程栈

② 加了机器不一定能提升 QPS
   → 瓶颈在数据库的话，加应用服务器反而增加数据库压力 → 雪崩

③ 压测通了 ≠ 生产没问题
   → 压测环境数据量少（索引全在内存），生产数据量大（索引要磁盘 IO）

④ 容量规划不是一次性的
   → 业务增长、数据积累、代码变更都会改变容量基线
   → 需要建立定期压测 + 容量 review 机制
```

### 💡 延伸思考

1. **如何在不影响线上业务的前提下做全链路压测？** — 核心是流量染色 + 数据隔离。① 压测流量在网关层打上特殊 Header；② 全链路组件（RPC/MQ/DB）识别这个 Header 后路由到影子服务/影子库；③ 凌晨低峰期执行，梯度加压，一旦核心指标异常立即停止。京东/阿里双十一前的压测就是这套方案。
2. **Kubernetes HPA 能替代人工容量规划吗？** — 只能部分替代。HPA 解决的是"快速扩容"的问题，但不能解决"瓶颈在哪"的问题。如果瓶颈在数据库，HPA 扩应用 Pod 是没用的，甚至有害。容量规划是找到瓶颈，HPA 是为已知瓶颈配置弹性策略。

## 题目 2：[JVM/性能调优] 请详细阐述 JVM 线上故障排查方法论：包括 CPU 飙升（死循环/GC 频繁/上下文切换）、内存泄漏（堆/元空间/直接内存/线程栈四类 OOM）的根因定位流程、Arthas/jstack/jmap/MAT 工具链的实战用法，以及从"发现问题→保留现场→定位根因→修复→验证"的完整闭环

**难度**：⭐⭐⭐⭐⭐
**考点来源**：2026-06-01 早间报告技能清单 — "Java 方向：JVM 调优、并发编程" 被列为必备技能 + 2026 面试不再问八股参数，而是"线上 JVM 问题你怎么排查？"  
**相关岗位**：Java后端 / 基础架构 / SRE

### 📖 参考答案

**一、JVM 故障排查的完整闭环**

2026 年面试官问 JVM 已经不再是"请背一下 GC 算法"，而是"线上 CPU 飙到 100% 你怎么排查？"考核的是**实战故障处理能力**，不是理论知识。

```
JVM 故障排查五步闭环：

  ① 发现问题 → 监控告警 / 用户反馈 / 日志异常
  ② 保留现场 → 快速 dump 关键信息（堆/线程/GC日志）
  ③ 定位根因 → 工具链分析 → 找到具体代码
  ④ 修复上线 → 代码修复 / 参数调整 / 架构优化
  ⑤ 验证闭环 → 压测/灰度验证 → 更新监控阈值
```

**二、CPU 飙升排查（最高频场景）**

```
场景：凌晨收到告警，生产服务器 CPU 飙到 100%

排查流程（5 分钟快速定位）：

Step 1: 找到 CPU 最高的进程
  $ top -c
  # PID=12345 的 Java 进程 CPU 99%

Step 2: 找到进程中 CPU 最高的线程
  $ top -H -p 12345
  # PID=12390 的线程 CPU 80%
  # 将 12390 转为十六进制：printf '%x\n' 12390 → 0x3066

Step 3: 查看线程在做什么
  $ jstack 12345 | grep -A 20 0x3066
  # 输出：
  "http-nio-8080-exec-15" #38 daemon prio=5 os_prio=0 tid=0x... nid=0x3066 runnable
    at com.example.service.ReportService.generateReport(ReportService.java:156)
    at com.example.controller.ReportController.getReport(ReportController.java:42)
  # → 定位到 ReportService.java:156 行！

Step 4: Arthas 进一步诊断（更强大）
  $ arthas-boot 12345
  [arthas]$ dashboard           # 看整体：线程/内存/GC 实时大盘
  [arthas]$ thread -n 5         # 看 CPU 最高的 5 个线程
  [arthas]$ thread -b           # 看是否有死锁（BLOCKED 线程）
  [arthas]$ watch com.example.service.ReportService generateReport \
            '{params, returnObj, throwExp}' -x 3
  # 监控方法入参/返回值/异常，不影响线上业务！
```

**CPU 飙升的三大根因 + 解决方案**：

| 根因 | 判断方法 | 解决方案 |
|------|---------|---------|
| **死循环/密集计算** | 线程栈显示某个业务方法一直在 RUNNABLE | 检查循环条件、加超时机制 |
| **频繁 GC** | `jstat -gc` 显示 FGC 频繁，`top` 显示 GC 线程 CPU 高 | 调大堆内存 / 优化代码减少对象创建 |
| **频繁上下文切换** | `vmstat` 显示 cs（context switch）极高 | 减少线程数 / 优化锁粒度 |

**三、内存泄漏 / OOM 排查（最致命场景）**

```
OOM 四大类型 + 排查口诀：

  ① Heap space → 堆满了，对象太多
  ② Metaspace → 类加载太多（动态代理/CGLIB 滥用）
  ③ Direct buffer memory → 堆外内存泄漏（NIO/Netty 未释放）
  ④ unable to create new native thread → 线程数超限

排查口诀：OOM 先看异常信息 → 堆溢出 dump 分析 → 
         元空间看类数量 → 直接内存看 ByteBuffer → 
         线程超限看-Xss 和 ulimit
```

**堆内存溢出排查实战**：

```bash
# ① 先配置 JVM 参数（预防性——生产环境必须配！）
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dump/
-XX:+ExitOnOutOfMemoryError  # 可选：OOM 后自动退出，让 K8s 重启

# ② 手动导出堆转储（不重启也能导出）
jmap -dump:format=b,file=/data/dump/heap.hprof <PID>

# ③ 用 MAT（Memory Analyzer Tool）分析
# 打开 heap.hprof → Leak Suspects Report → 自动找到疑似泄漏对象
# 关键指标：
#   - Histogram：按类统计对象数量和大小
#   - Dominator Tree：按对象占用内存排序
#   - Path to GC Roots：追踪对象为什么没被回收
```

**常见内存泄漏场景**：

```java
// 场景 1：ThreadLocal 未清理（经典！）
public class UserContext {
    private static final ThreadLocal<User> currentUser = new ThreadLocal<>();
    
    public static void setUser(User user) {
        currentUser.set(user);
    }
    // ❌ 没有 remove()！线程池复用线程 → ThreadLocal 永远不释放
    // ✅ 修复：在 finally 中调用 currentUser.remove()
}

// 场景 2：静态集合无限增长
public class MetricCollector {
    private static final List<Metric> metrics = new ArrayList<>();  // ❌ 只增不减
    // ✅ 修复：定时清理 或 用 RingBuffer 固定大小
}

// 场景 3：未关闭的资源
try (Connection conn = dataSource.getConnection()) {  // ✅ try-with-resources
    // ...
} // 自动关闭
// 如果忘记关闭 → 连接泄漏 → 最终导致连接池耗尽

// 场景 4：HashMap 的 key 没正确实现 equals/hashCode
// 自定义对象当 key 但只重写了 equals 没重写 hashCode
// → 同一个"逻辑对象"存了多份，Map 越来越大
```

**元空间溢出（Metaspace OOM）**：

```
元空间溢出常见于：
  → 动态生成大量类：CGLIB 代理、Groovy 脚本、JSP 编译
  → 类加载器泄漏：热部署后旧的 ClassLoader 没被回收

排查：
  jstat -gc <PID>  → 看 MU（Metaspace Used）是否持续增长
  jmap -clstats <PID> → 看每个 ClassLoader 加载了多少类

修复：
  -XX:MaxMetaspaceSize=512m  → 显式限制元空间大小
  升级到 JDK 17+：默认就有限制且 GC 更积极
```

**六、面试回答框架**

```
面试官问"线上 CPU 飙到 100%，你怎么排查？"

① 先止损（10秒）：
   "先确认影响范围。如果是单台 → 从负载均衡摘掉，如果是集群 → 先扩容扛住"

② 快速定位（20秒）：
   "top -H 找到问题线程 → jstack 看线程栈 → 定位到具体代码行。
    如果是 GC 线程 CPU 高 → jstat 看 GC 频率 → 调整堆参数或优化代码"

③ 深度诊断（20秒）：
   "如果 jstack 不够，用 Arthas 的 dashboard + thread 命令实时看，
    watch 命令监控可疑方法，trace 看调用耗时"

④ 如果是 OOM（20秒）：
   "先看 OOM 类型：heap → dump 后 MAT 分析；
    metaspace → 检查动态代理/CGLIB 使用；
    direct memory → 检查 Netty/DirectByteBuffer 释放"

⑤ 事后闭环（10秒）：
   "修复后压测验证，更新监控告警阈值，写事故复盘文档"
```

### 💡 延伸思考

1. **容器环境下 JVM 内存如何设置？** — 容器中 JVM 默认看到的是宿主机内存，不是容器的 limits。必须开启 `-XX:+UseContainerSupport`（JDK 8u191+），同时显式设置 `-XX:MaxRAMPercentage=75.0`（而不是 `-Xmx`），让 JVM 基于容器内存限额动态计算堆大小。另外，堆外内存（Metaspace、Direct Memory、Thread Stack）也必须显式限制，否则容器 OOMKilled 时 JVM 一脸懵。
2. **Arthas 的 watch/trace 命令对线上性能影响大吗？** — watch 和 trace 本质上是字节码增强，会在方法入口和出口插入代码。对于高频调用方法（如 QPS 10000+），监控开销可能达到 10-20%，建议只在排查时临时开启，确认后立即关闭。更安全的方式是用 `profiler` 命令做采样，开销极小。

**四、结构化 Prompt 模板的工程化设计**

2026 年真正的竞争力来自**系统化、可维护**的 Prompt 工程：

```python
from dataclasses import dataclass, field
from typing import Optional
from string import Template

@dataclass
class PromptTemplate:
    """可版本化、可测试的 Prompt 模板"""
    name: str
    version: str = "1.0"
    description: str = ""
    template: str = ""
    required_vars: list[str] = field(default_factory=list)
    optional_vars: dict[str, str] = field(default_factory=dict)
    
    def render(self, **kwargs) -> str:
        """渲染模板，自动校验必填变量"""
        # 校验必填变量
        missing = [v for v in self.required_vars if v not in kwargs]
        if missing:
            raise ValueError(f"缺少必填变量: {missing}")
        
        # 填充默认值
        for key, default in self.optional_vars.items():
            kwargs.setdefault(key, default)
        
        return Template(self.template).safe_substitute(**kwargs)

# 使用示例
rag_prompt = PromptTemplate(
    name="rag-qa-v2",
    version="2.1",
    description="基于知识库的 QA 模板",
    template="""
# 角色
你是一位专业的技术支持工程师。

# 约束
- 只基于提供的上下文回答，不要编造信息
- 如果上下文中没有答案，请明确说"根据现有资料无法回答"
- 回答要简洁，不超过 200 字

# 上下文
${context}

# 问题
${question}

# 回答
""",
    required_vars=["context", "question"],
    optional_vars={"language": "中文"}
)
```

public class MyTranslator implements Translator<String, float[]> {
    
    // 输入预处理：文本 → Tensor
    @Override
    public NDList processInput(TranslatorContext ctx, String input) {
        // 分词 + 编码 + 转 Tensor
        NDManager manager = ctx.getNDManager();
        // 假设已有一个 tokenizer
        long[] tokenIds = tokenizer.encode(input);
        NDArray array = manager.create(tokenIds);
        return new NDList(array);

    // 输出后处理：Tensor → 业务对象
    @Override
    public float[] processOutput(TranslatorContext ctx, NDList list) {

        return output.toFloatArray();  // 转为 Java float[]
    }

**四、Kafka 为什么快？**

```
① 顺序写入磁盘
   → 日志型存储，所有消息追加写入，避免了随机 IO
   → 机械硬盘顺序写 600MB/s，接近内存速度

② Page Cache（操作系统页缓存）
   → 消息先写到 Page Cache，由 OS 异步刷盘
   → 消费时优先从 Page Cache 读 → 内存速度

③ 零拷贝（Zero-Copy）
   → sendfile() 系统调用，数据从磁盘直接到网卡
   → 绕过用户态，减少 2 次 CPU 拷贝

④ 批量处理
   → Producer 批量发送（batch.size + linger.ms）
   → Consumer 批量拉取（fetch.min.bytes）
   → 批量压缩（gzip/snappy/lz4）

⑤ 分区并行
   → 一个 Topic 多个 Partition → 并行读写
   → 水平扩展：加机器 = 加 Partition = 加吞吐
```

```java
// RocketMQ 事务消息：分布式事务的半消息机制
public class OrderTransactionListener implements TransactionListener {
    
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        // 执行本地事务（如创建订单）
        try {
            orderService.createOrder((Order) arg);
            return LocalTransactionState.COMMIT_MESSAGE;  // 提交
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;  // 回滚
        }
    }
    
    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // 回查：Broker 定期检查未确认的半消息
        // 查本地事务状态，返回 COMMIT / ROLLBACK / UNKNOW
        String orderId = msg.getKeys();
        Order order = orderService.getById(orderId);
        if (order != null && order.getStatus() == OrderStatus.CREATED) {
            return LocalTransactionState.COMMIT_MESSAGE;
        }
        return LocalTransactionState.ROLLBACK_MESSAGE;
    }
}

// 发送事务消息
TransactionMQProducer producer = new TransactionMQProducer("order-group");
producer.setTransactionListener(new OrderTransactionListener());
producer.sendMessageInTransaction(msg, order);
```

**事务消息流程**：
```
① Producer 发送半消息（Half Message）→ Broker 存储但不投递
② Producer 执行本地事务
③ 成功 → COMMIT → Broker 投递消息给 Consumer
④ 失败 → ROLLBACK → Broker 删除半消息
⑤ 超时未确认 → Broker 回调 checkLocalTransaction() 回查
```

### 💡 延伸思考

1. **Kafka 的 Rebalance 风暴怎么避免？** — Rebalance 是 Kafka 的经典痛点。Consumer Group 中 Consumer 加入或离开时，所有 Partition 重新分配，期间消费暂停。解决方案：① 使用增量 Cooperative Rebalance（Kafka 2.4+）；② 增大 `session.timeout.ms` 和 `max.poll.interval.ms` 避免误判下线；③ 使用静态 Group Membership（`group.instance.id`），Consumer 重启后恢复原来的 Partition 分配。
2. **RocketMQ 的延迟消息和 RabbitMQ 的延迟队列有什么区别？** — RocketMQ 原生支持 18 个延迟级别（1s/5s/10s/30s/1m/2m/.../2h），只需设置 `message.setDelayTimeLevel(3)` 即可。RabbitMQ 需要安装 `rabbitmq_delayed_message_exchange` 插件，或者用 TTL + 死信队列变通实现。RocketMQ 的实现更简洁，可靠性也更高。
