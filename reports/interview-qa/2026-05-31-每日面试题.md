### 📖 参考答案

**一、三大特性的设计理念**

Java 17 作为 LTS 版本，引入了 Records、Sealed Classes、Pattern Matching 三大特性。它们不是为了"炫技"，而是为了解决 Java 长久以来的三大痛点：

| 痛点 | 旧写法 | 新特性 |
|------|--------|--------|
| 数据载体类样板代码多 | POJO 写 getter/setter/equals/hashCode/toString | **Records** |
| 类型层次不可控 | 任何人都能实现你的接口 | **Sealed Classes** |
| 类型判断后强转冗余 | `instanceof` + 手动强转 | **Pattern Matching** |

**二、Records — 不可变数据载体**

Records 本质上是一种特殊的 `final` 类，编译器自动生成构造器、`equals()`、`hashCode()`、`toString()` 以及字段访问方法。

```java
// 旧写法：30+ 行样板代码
public final class User {
    private final String name;
    private final int age;
    
    public User(String name, int age) {
        this.name = name;
        this.age = age;
    }
    public String name() { return name; }
    public int age() { return age; }
    public boolean equals(Object o) { /* ... */ }
    public int hashCode() { /* ... */ }
    public String toString() { /* ... */ }
}

// Records：一行搞定！
public record User(String name, int age) {}
// 自动获得：规范构造器、name()、age()、equals()、hashCode()、toString()
```

**Records 的关键约束**：
- 隐式 `final`，不可被继承
- 所有字段隐式 `final`（不可变）
- 可以实现接口，但不能继承其他类（默认继承 `java.lang.Record`）
- 可以定义实例方法和静态方法

```java
// Records 实战：DDD 值对象
public record Money(BigDecimal amount, Currency currency) {
    // 紧凑构造器（Compact Constructor）：参数校验
    public Money {
        Objects.requireNonNull(amount);
        Objects.requireNonNull(currency);
        if (amount.compareTo(BigDecimal.ZERO) < 0) {
            throw new IllegalArgumentException("金额不能为负");
        }
    }
    
    // 自定义方法
    public Money add(Money other) {
        if (!this.currency.equals(other.currency)) {
            throw new IllegalArgumentException("币种不一致");
        }
        return new Money(this.amount.add(other.amount), this.currency);
    }
}

// Records 实战：DTO 转换（Spring Boot）
public record UserDTO(Long id, String name, String email) {
    // 从 Entity 转换
    public static UserDTO from(UserEntity entity) {
        return new UserDTO(entity.getId(), entity.getName(), entity.getEmail());
    }
}
```

**三、Sealed Classes — 精确控制类型层次**

Sealed Classes 让你明确声明"哪些类可以继承/实现我"——其他任何类都不行。这对领域建模极其有用。

```java
// 密封接口：支付类型只有三种
public sealed interface Payment permits AlipayPayment, WechatPayment, UnionPayment {
    PayResult pay(Order order);
}

public record AlipayPayment(String appId) implements Payment {
    public PayResult pay(Order order) { /* 支付宝支付逻辑 */ }
}

public record WechatPayment(String mchId) implements Payment {
    public PayResult pay(Order order) { /* 微信支付逻辑 */ }
}

public record UnionPayment(String merId) implements Payment {
    public PayResult pay(Order order) { /* 银联支付逻辑 */ }
}

// 如果其他人写 class CreditCardPayment implements Payment → 编译错误！
```

**Sealed Classes 与 Pattern Matching 的组合拳**（最强大的用法）：

```java
// 配合 switch 模式匹配 → 编译器检查穷举性！
public String getPaymentChannel(Payment payment) {
    return switch (payment) {
        case AlipayPayment a -> "支付宝(" + a.appId() + ")";
        case WechatPayment w -> "微信(" + w.mchId() + ")";
        case UnionPayment u -> "银联(" + u.merId() + ")";
        // 编译器强制要求覆盖所有允许的子类！
        // 漏掉任何一个 → 编译错误！
    };
}
```

**四、Pattern Matching — 告别冗余强转**

### instanceof 模式匹配（Java 16 正式）

```java
// 旧写法
if (obj instanceof String) {
    String s = (String) obj;  // 冗余强转
    System.out.println(s.length());
}

// 新模式匹配
if (obj instanceof String s) {  // 一步到位：判断 + 绑定变量
    System.out.println(s.length());
}

// 复杂条件组合
if (obj instanceof String s && s.length() > 5) {
    System.out.println(s.toUpperCase());
}

// 嵌套匹配（Java 21 Record Patterns）
if (order instanceof Order(long id, Customer(var name, var email), Money(var amount, var currency))) {
    System.out.println(name + " 消费 " + amount + " " + currency);
}
```

### Switch 模式匹配（Java 21 正式）

```java
// 旧写法
String result;
if (obj instanceof Integer i) {
    result = "整数: " + i;
} else if (obj instanceof String s) {
    result = "字符串: " + s;
} else if (obj instanceof Long l) {
    result = "长整数: " + l;
} else {
    result = "未知类型";
}

// Java 21 switch 模式匹配
String result = switch (obj) {
    case Integer i    -> "整数: " + i;
    case String s     -> "字符串: " + s;
    case Long l       -> "长整数: " + l;
    case null         -> "null值";
    default           -> "未知类型";
};

// 带守卫条件（when 子句）
String desc = switch (obj) {
    case Integer i when i > 0  -> "正整数";
    case Integer i when i < 0  -> "负整数";
    case Integer i             -> "零";
    default                    -> "非整数";
};
```

**五、编译原理：Records 的底层实现**

Records 不是"语法糖"那么简单。`javap -v User.class` 可以看到：

```
Records 编译产物：
  → final class User extends java.lang.Record
  → private final String name;  // 字段
  → private final int age;
  → public User(String name, int age);  // 规范构造器
  → public String name();  // 访问器（不是 getName()！）
  → public int age();
  → public final boolean equals(Object);
  → public final int hashCode();
  → public final String toString();
```

关键：访问器方法是 `name()` 而不是 `getName()`，这是为了与 JavaBeans 规范解耦，明确表达"这是不可变数据，不是可变 Bean"。

**六、生产环境最佳实践**

```
✅ 推荐使用 Records：
  - DTO / VO（API 响应对象）
  - DDD 值对象（Money、Address、PhoneNumber）
  - 配置对象（不可变的配置绑定）
  - 方法返回多值（替代 Pair/Tuple）
  - 事件对象（领域事件、消息体）

✅ 推荐使用 Sealed Classes：
  - 支付类型、订单状态等有限状态机
  - 命令模式（有限的命令子类）
  - AST 节点（语法树节点类型固定）
  - 结果类型（Success | Failure）

✅ 推荐使用 Pattern Matching：
  - 替代冗长的 if-else instanceof 链
  - 配合 Sealed Classes 做穷举匹配
  - 数据解构（Record Patterns 嵌套提取）
```

### 📖 参考答案

**一、Spring AI 解决的核心问题**

传统 Java 项目集成 AI 能力的三大痛苦：

```
痛点 1：模型碎片化
  OpenAI API ≠ 通义千问 API ≠ Claude API ≠ Ollama API
  → 切换模型 = 重写所有调用代码

痛点 2：向量数据库碎片化
  Redis ≠ Milvus ≠ PGVector ≠ Pinecone
  → 换存储 = 改所有检索逻辑

痛点 3：AI 代码与业务代码耦合
  Prompt 拼接、向量检索、上下文管理全塞在 Service 层
  → 难以维护、难以测试、难以复用
```

Spring AI 的答案：用 Spring 一贯的"抽象层"策略，统一所有 AI 模型和向量存储的 API。

**二、核心架构：两大抽象层**

```
┌──────────────────────────────────────────────────────────────┐
│                    应用层                                     │
│  ChatClient（流式接口）  │  EmbeddingClient │  ImageClient   │
├──────────────────────────────────────────────────────────────┤
│                    模型抽象层                                 │
│  ChatModel ←── OpenAI / 通义千问 / Claude / Ollama / ...     │
│  EmbeddingModel ←── OpenAI / 通义千问 / BGE / ...            │
│  ImageModel ←── OpenAI DALL·E / Stability AI / ...           │
├──────────────────────────────────────────────────────────────┤
│                    数据抽象层                                 │
│  VectorStore ←── Redis / PGVector / Milvus / Chroma / ...    │
│  DocumentReader ←── PDF / JSON / Text / ...                  │
│  DocumentSplitter ←── TokenTextSplitter / ...                │
├──────────────────────────────────────────────────────────────┤
│                    辅助组件                                   │
│  Advisor（拦截器链） │ ETL Pipeline │ Prompt Template         │
└──────────────────────────────────────────────────────────────┘
```

**ChatClient vs ChatModel 的区别**：

```java
// ChatModel：底层 API，手动管理一切
@Autowired
private ChatModel chatModel;

public String ask(String question) {
    Prompt prompt = new Prompt(new UserMessage(question));
    ChatResponse response = chatModel.call(prompt);
    return response.getResult().getOutput().getContent();
}

// ChatClient：高层 API，支持 Fluent 风格 + Advisor 拦截器链
@Autowired
private ChatClient.Builder builder;

public String ask(String question) {
    return builder.build()
        .prompt()
        .user(question)
        .advisors(new QuestionAnswerAdvisor(vectorStore, SearchRequest.defaults()))
        .call()
        .content();
}
```

**三、VectorStore 接口契约与五种实现**

```java
// Spring AI 定义的 VectorStore 接口（核心方法）
public interface VectorStore {
    void add(List<Document> documents);                    // 写入向量
    List<Document> similaritySearch(String query);         // 相似度搜索
    List<Document> similaritySearch(SearchRequest req);    // 带参数搜索
    Optional<Document> get(String id);                     // 按 ID 获取
    void delete(List<String> ids);                         // 删除
}
```

| 实现 | 类型 | 性能 | 适用场景 |
|------|------|------|---------|
| **Redis** (RediSearch) | 内存 | ⭐⭐⭐⭐⭐ 亚毫秒 | 低延迟实时 RAG、语义缓存 |
| **PGVector** | 数据库内嵌 | ⭐⭐⭐ | 已有 PostgreSQL，不想引入新组件 |
| **Milvus** | 专用向量库 | ⭐⭐⭐⭐⭐ | 十亿级向量、纯向量场景 |
| **Chroma** | 轻量嵌入式 | ⭐⭐⭐ | 原型开发、本地测试 |
| **Pinecone** | 云服务 | ⭐⭐⭐⭐ | 不想自己运维 |

**四、RAG 完整 Pipeline（7 步全流程）**

```
阶段一：索引（离线/启动时执行一次）

  Document（原始文档：PDF/JSON/HTML）
    ↓ DocumentReader（PDFReader / JsonReader / TextReader）
  解析后文本
    ↓ DocumentSplitter（TokenTextSplitter：按 token 数切块）
  文本片段 List<Document>
    ↓ EmbeddingModel（embed() → float[] 向量）
  向量 List<float[]>
    ↓ VectorStore.add()
  Redis / PGVector / Milvus 中持久化

阶段二：检索+生成（每次查询执行）

  用户问题
    ↓ EmbeddingModel.embed(question) → 问题向量
  VectorStore.similaritySearch(questionVector, topK=5)
    ↓ 余弦相似度计算 → 返回最相关的 K 个文档片段
  相关文档片段
    ↓ Prompt 模板拼接：系统提示 + 文档片段 + 用户问题
  增强后的 Prompt
    ↓ ChatModel.call()
  LLM 生成答案 → 返回给用户
```

**Spring AI 代码实现（完整示例）**：

```java
@Configuration
public class RagConfig {

    @Bean
    public VectorStore vectorStore(EmbeddingModel embeddingModel, 
                                    RedisVectorStoreProperties props) {
        // Spring AI 自动注入 RedisVectorStore
        return new RedisVectorStore(props, embeddingModel);
    }

    @Bean
    public QuestionAnswerAdvisor ragAdvisor(VectorStore vectorStore) {
        return new QuestionAnswerAdvisor(
            vectorStore,
            SearchRequest.builder()
                .topK(5)                         // 检索前5个相关片段
                .similarityThreshold(0.7)         // 相似度阈值
                .build()
        );
    }
}

@RestController
public class RagController {

    @Autowired
    private ChatClient.Builder builder;
    @Autowired
    private QuestionAnswerAdvisor ragAdvisor;

    @GetMapping("/rag/ask")
    public String ask(@RequestParam String question) {
        return builder.build()
            .prompt()
            .user(question)
            .advisors(ragAdvisor)  // ← 注入 RAG Advisor
            .call()
            .content();
    }
}
```

**五、QuestionAnswerAdvisor 拦截器机制**

`QuestionAnswerAdvisor` 是 Spring AI 中 RAG 的核心实现。它实现了 `Advisor` 接口，在 ChatClient 调用链中自动嵌入检索逻辑：

```
ChatClient 请求 → Advisor 链拦截：

  RequestAdvisor（请求前）
    ↓
  QuestionAnswerAdvisor.before():
    ① 提取用户问题
    ② 调用 EmbeddingModel 向量化
    ③ 调用 VectorStore.similaritySearch()
    ④ 将检索到的文档片段注入 Prompt 上下文
    ↓
  ChatModel.call()（LLM 带着上下文回答）
    ↓
  ResponseAdvisor（响应后）
    ↓
  返回最终答案
```

**一、面试场景还原**

2026 年大厂面试的真实对话：

**二、五步排查 SOP（标准操作流程）**

```
Step 1: 发现（Discovery）        → 怎么知道有慢 SQL？
Step 2: 定位（Localization）     → 哪条 SQL 慢了？
Step 3: 根因（Root Cause）       → 为什么会慢？
Step 4: 优化（Optimization）     → 怎么修？
Step 5: 验证（Verification）     → 修好了吗？
```

**三、Step 1：发现 — 慢查询日志配置**

```sql
-- MySQL 8.0 生产级慢查询日志配置

-- ① 开启慢查询日志
SET GLOBAL slow_query_log = ON;

-- ② 设置阈值（生产建议 1s，核心接口 0.5s）
SET GLOBAL long_query_time = 1;

-- ③ 记录未走索引的 SQL（辅助排查，注意日志量）
SET GLOBAL log_queries_not_using_indexes = ON;

-- ④ 设置最小扫描行数（避免大量微小查询撑爆日志）
SET GLOBAL min_examined_row_limit = 1000;

-- ⑤ 查看当前配置
SHOW VARIABLES LIKE '%slow_query%';
SHOW VARIABLES LIKE 'long_query_time';
```

**pt-query-digest 分析工具**（Percona Toolkit）：

```bash
# 分析慢查询日志，按耗时排序输出 TOP 10
pt-query-digest /var/log/mysql/slow.log --limit=10

# 输出示例：
# Rank  Query ID            Response time  Calls  R/Call  V/M
# 1     0xABCD...          1200.0000 80.0%  5000   0.2400  0.02 SELECT orders
# 2     0xEF01...           200.0000 13.3%  2000   0.1000  0.01 SELECT user
# 
# 重点关注：Response time 占比 + Calls 次数 + R/Call 平均耗时
```

**四、Step 2：定位 — EXPLAIN 快速诊断法**

拿到慢 SQL 后，直接跑 EXPLAIN，重点看 4 个字段：

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 10086 AND status = 'paid' ORDER BY create_time DESC LIMIT 10;
```

| 字段 | 正常信号 | 危险信号 | 含义 |
|------|---------|---------|------|
| **type** | const/eq_ref/ref/range | ALL/index | 全表扫描/全索引扫描 |
| **key** | 索引名 | NULL | 没用索引 |
| **rows** | < 1000 | > 10000 | 扫描行数过多 |
| **Extra** | Using index | **Using filesort** / **Using temporary** | 额外排序/临时表 |

```
快速诊断口诀：
  type ALL → 没走索引，先加索引
  key NULL → 索引失效，查失效原因
  rows 很大 → 索引区分度不够 或 数据倾斜
  Using filesort → ORDER BY 不在索引中
  Using temporary → GROUP BY / DISTINCT 需要临时表
```

**五、Step 3：根因 — 十大索引失效场景**

这是慢 SQL 最常见的原因，也是面试高频考点：

| # | 场景 | SQL 示例 | 根因 | 修复 |
|---|------|---------|------|------|
| 1 | **最左前缀缺失** | `WHERE age=25` (索引是 name,age) | 联合索引跳过了第一列 | 调整索引或 SQL |
| 2 | **索引列上做运算** | `WHERE YEAR(create_time)=2026` | 函数破坏了索引有序性 | `WHERE create_time BETWEEN '2026-01-01' AND '2026-12-31'` |
| 3 | **隐式类型转换** | `WHERE phone=13800138000` (phone 是 VARCHAR) | 字符串与数字比较触发转换 | `WHERE phone='13800138000'` |
| 4 | **LIKE 前导模糊** | `WHERE name LIKE '%张三'` | 前缀通配符无法利用 B+Tree | 改用全文索引或 ES |
| 5 | **OR 条件混合** | `WHERE id=1 OR name='张三'` | name 没索引 → 全表扫描 | 改为 UNION ALL 或给 name 加索引 |
| 6 | **NOT / != / <>** | `WHERE status != 'deleted'` | 否定条件索引效率低 | 用 IN 列举正向值 或 调整业务逻辑 |
| 7 | **IS NULL / IS NOT NULL** | `WHERE deleted_at IS NOT NULL` | 索引不存储 NULL（取决于引擎） | 用默认值替代 NULL |
| 8 | **范围查询右边失效** | `WHERE name='张三' AND age>25 AND city='北京'`（索引 name,age,city） | age 是范围 → city 不走索引 | 调整索引列顺序 |
| 9 | **SELECT \*** | `SELECT * FROM orders WHERE ...` | 无法使用覆盖索引 → 必须回表 | 只查需要的列 |
| 10 | **数据量过大不走索引** | 优化器认为全表扫描更快 | MySQL 优化器的代价估算偏差 | 用 FORCE INDEX 或 ANALYZE TABLE |

**六、Step 4：优化 — SQL 改写与索引重构**

```
优化策略优先级（从易到难）：

  P0（立即生效）：
    ✅ 改写 SQL：函数包裹 → 直接比较，LIKE '%x' → 全文索引
    ✅ 加索引：单列索引 / 联合索引（注意最左前缀）
    ✅ 覆盖索引：SELECT 字段全在索引中 → 不回表

  P1（需要测试）：
    ✅ 分页优化：LIMIT 100000,20 → 子查询 + 覆盖索引延迟关联
    ✅ JOIN 优化：小表驱动大表，被驱动表 JOIN 字段加索引
    ✅ 子查询 → JOIN 改写（部分场景）

  P2（架构层面）：
    ✅ 读写分离：查询走只读从库
    ✅ 分库分表：单表 > 500 万行考虑水平拆分
    ✅ 冷热分离：历史数据归档
```

**分页深翻优化实战**：

```sql
-- ❌ 慢：OFFSET 100000 → 需要扫描并丢弃 100000 行
SELECT * FROM orders WHERE user_id = 10086 
ORDER BY create_time DESC LIMIT 100000, 20;

-- ✅ 优化方案：覆盖索引 + 延迟关联
SELECT o.* FROM orders o
INNER JOIN (
    SELECT id FROM orders 
    WHERE user_id = 10086 
    ORDER BY create_time DESC 
    LIMIT 100000, 20
) tmp ON o.id = tmp.id;
-- 子查询只扫描索引（覆盖索引），找到 20 个 id 后再回表
```

**三、Redis + Lua 原子库存扣减（最核心环节）**

为什么必须用 Lua？因为"判断库存 + 扣减库存"必须原子执行，否则在并发下必然超卖：

```lua
-- seckill.lua：原子性库存扣减脚本
-- KEYS[1] = 秒杀商品库存 key（如 seckill:stock:10086）
-- KEYS[2] = 秒杀成功用户集合 key（如 seckill:users:10086）
-- ARGV[1] = 用户 ID

local stockKey = KEYS[1]
local usersKey = KEYS[2]
local userId = ARGV[1]

-- ① 检查用户是否已抢过（防重复下单）
local hasOrdered = redis.call('SISMEMBER', usersKey, userId)
if hasOrdered == 1 then
    return -1  -- 已抢过，拒绝
end

-- ② 检查库存
local stock = redis.call('GET', stockKey)
if not stock or tonumber(stock) <= 0 then
    return 0  -- 库存不足
end

-- ③ 扣减库存
redis.call('DECR', stockKey)

-- ④ 记录已抢用户
redis.call('SADD', usersKey, userId)

return 1  -- 秒杀成功
```

```java
// Java 端调用
@RestController
public class SeckillController {

    @Autowired
    private StringRedisTemplate redisTemplate;
    @Autowired
    private RocketMQTemplate rocketMQTemplate;

    // 预加载 Lua 脚本
    private final DefaultRedisScript<Long> seckillScript;

    public SeckillController() {
        seckillScript = new DefaultRedisScript<>();
        seckillScript.setLocation(new ClassPathResource("lua/seckill.lua"));
        seckillScript.setResultType(Long.class);
    }

    @PostMapping("/seckill")
    public Result seckill(@RequestParam Long productId, 
                          @RequestHeader("userId") Long userId) {
        // 执行 Lua 脚本（原子操作！）
        Long result = redisTemplate.execute(
            seckillScript,
            List.of(
                "seckill:stock:" + productId,
                "seckill:users:" + productId
            ),
            userId.toString()
        );

        if (result == -1) {
            return Result.error("请勿重复抢购");
        }
        if (result == 0) {
            return Result.error("已抢光");
        }

        // 扣减成功 → 发送 MQ 异步创建订单
        SeckillMessage msg = new SeckillMessage(productId, userId);
        rocketMQTemplate.send("seckill-order-topic", msg);

        return Result.success("抢购成功，订单生成中...");
    }
}
```

**四、RocketMQ 异步削峰 — 订单创建**

```
为什么需要 MQ？

  如果秒杀成功直接写数据库：
    1000 并发 INSERT → 数据库连接池耗尽 → 雪崩

  通过 MQ 削峰：
    秒杀接口（低延迟，只写 Redis）→ RocketMQ → 消费者（匀速消费）
    
    消费者处理速率：可调节（如 100 TPS）
    → 数据库压力始终可控
```

```java
// MQ 消费者：异步创建订单
@Component
@RocketMQMessageListener(
    topic = "seckill-order-topic",
    consumerGroup = "seckill-order-consumer"
)
public class SeckillOrderConsumer implements RocketMQListener<SeckillMessage> {

    @Override
    public void onMessage(SeckillMessage msg) {
        // ① 幂等性检查（Redis 记录已处理的 msgId）
        String dedupKey = "order:dedup:" + msg.getMsgId();
        Boolean isNew = redisTemplate.opsForValue()
            .setIfAbsent(dedupKey, "1", Duration.ofHours(24));
        if (Boolean.FALSE.equals(isNew)) {
            return;  // 已处理过，跳过
        }

        // ② 创建订单（数据库事务）
        orderService.createSeckillOrder(msg.getProductId(), msg.getUserId());

        // ③ 发送通知（短信/App推送）
        notificationService.notify(msg.getUserId(), "秒杀成功！");
    }
}
```

**二、HNSW 算法原理 — 为什么 RediSearch 向量搜索这么快**

HNSW（Hierarchical Navigable Small World）是 Redis 默认的向量索引算法：

```
HNSW 的分层结构（类比：高速公路→省道→街道）：

  第 2 层（稀疏，长距离跳转）
  ● ──────────────────────────── ●
  │                               │
  第 1 层（中等密度，区域导航）
  ● ──── ● ──── ● ──── ● ──── ●
  │       │       │       │
  第 0 层（最密，精确搜索）
  ●─●─●─●─●─●─●─●─●─●─●─●─●─●─●

  搜索流程：
  ① 从顶层（第 2 层）入口点开始
  ② 贪心导航到当前层最近的节点
  ③ 降到下一层，从当前节点继续搜索
  ④ 重复直到第 0 层 → 返回 K 个最近邻

  复杂度：O(log N)，比暴力搜索 O(N) 快几个数量级
```

```bash
# RediSearch 创建 HNSW 向量索引
FT.CREATE idx:documents ON HASH PREFIX 1 doc:
  SCHEMA
    content TEXT                          # 文本字段
    content_vector VECTOR HNSW 6          # 向量字段，HNSW 索引
      TYPE FLOAT32                        # 向量类型
      DIM 1536                            # 向量维度（如 OpenAI text-embedding-3-small）
      DISTANCE_METRIC COSINE              # 余弦相似度
      M 16                                # 每层最大连接数（控制图密度）
      EF_CONSTRUCTION 200                 # 构建时的搜索宽度
```

**FLAT vs HNSW 对比**：

| 维度 | FLAT（暴力搜索） | HNSW |
|------|----------------|------|
| 搜索速度 | O(N)，慢 | **O(log N)**，快 |
| 召回率 | **100%**（精确） | ~95-99%（近似） |
| 内存占用 | 低（只需存向量） | 高（需存图结构） |
| 构建时间 | 快 | 慢（需构建多层图） |
| 适用场景 | < 10 万向量 + 要求精确 | **百万级向量 + 低延迟** |

**四、语义缓存（Semantic Caching）— Redis 的降本利器**

这是 2026 年 Redis AI 能力中最具商业价值的特性：

```
传统缓存：精确匹配
  Q: "什么是Redis？" → 缓存命中
  Q: "Redis是什么？" → 缓存未命中！（文字不同）
  Q: "请介绍Redis"  → 缓存未命中！

语义缓存：向量相似度匹配
  Q: "什么是Redis？" → 向量化 → 缓存命中
  Q: "Redis是什么？" → 向量化 → 余弦相似度 0.97 → 语义缓存命中！
  Q: "请介绍Redis"  → 向量化 → 余弦相似度 0.92 → 语义缓存命中！
  
  效果：LLM 调用减少 70-90%，延迟降低 10-100 倍，成本降低 80%+
```

```java
// Spring AI 语义缓存实现
@Component
public class SemanticCacheService {

    @Autowired
    private VectorStore vectorStore;
    @Autowired
    private EmbeddingModel embeddingModel;
    @Autowired
    private ChatClient chatClient;

    public String ask(String question) {
        // ① 向量化用户问题
        float[] queryVector = embeddingModel.embed(question);

        // ② 语义搜索缓存
        List<Document> cached = vectorStore.similaritySearch(
            SearchRequest.builder()
                .query(question)
                .topK(1)
                .similarityThreshold(0.92)  // 相似度阈值
                .filterExpression("type == 'cache'")
                .build()
        );

        // ③ 缓存命中 → 直接返回（不调 LLM！）
        if (!cached.isEmpty()) {
            return cached.get(0).getContent();
        }

        // ④ 缓存未命中 → 调 LLM → 存入缓存
        String answer = chatClient.prompt().user(question).call().content();
        Document cacheDoc = new Document(answer, Map.of("type", "cache"));
        vectorStore.add(List.of(cacheDoc));
        return answer;
    }
}
```
