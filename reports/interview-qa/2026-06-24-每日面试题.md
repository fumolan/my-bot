## 题目 1：[AI/大模型] 请详细阐述 RAG（检索增强生成）系统的完整链路与生产级优化方案

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-24 早间&午间报告 — "阿里Agent开发一面面经：RAG系统优化、大模型评测、幻觉治理" + "大模型面经汇总高频考点"
**相关岗位**：AI应用开发 / Java后端（AI方向） / 全栈

### 📖 参考答案

#### 一、RAG 的核心动机

RAG（Retrieval-Augmented Generation）解决的是大模型的两个核心痛点：
1. **知识时效性差**：模型训练数据有截止日期，无法回答最新信息
2. **幻觉（Hallucination）**：模型可能"一本正经地胡说八道"

类比理解：RAG 就像"开卷考试"——先翻书（检索外部知识库），再答题（基于检索结果生成答案），答案更准、更可信。

#### 二、RAG 完整链路

```
用户提问
    │
    ▼
┌─────────────────────────────────────────────┐
│              查询理解与改写                     │
│  - 查询重写（Query Rewriting）                 │
│  - 多查询扩展（Multi-Query）                   │
│  - HyDE（假设文档嵌入）                         │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│              文档分块（Chunking）               │
│  - 固定大小分块（256/512 tokens）              │
│  - 语义分块（Sentence Splitter）               │
│  - 递归分块（Recursive Character Splitter）    │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│              向量化（Embedding）               │
│  - 文本 → 向量（text-embedding-3 / bge）      │
│  - 存入向量数据库（Milvus / FAISS / Qdrant）   │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│              混合检索（Hybrid Search）          │
│  - 向量检索（语义相似度）                       │
│  - 关键词检索（BM25 / TF-IDF）                 │
│  - 融合排序（RRF / 加权融合）                   │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│              重排序（Rerank）                   │
│  - Cross-Encoder 模型逐对打分                  │
│  - 精排 Top-K（通常取 3-5 个片段）              │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│              上下文组装 + 生成                  │
│  - 拼接 Prompt（System + 检索结果 + 问题）      │
│  - LLM 生成最终答案                            │

└─────────────────────────────────────────────┘
```

#### 三、各环节关键优化

**1. Chunk 策略**

| 策略 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| 固定大小（256 tokens） | 简单、速度快 | 语义断裂 | 通用场景 |
| 语义分块 | 保持语义完整性 | 块大小不固定 | 长文档/论文 |
| 递归分块 | 层级嵌套，兼顾粗细粒度 | 复杂度高 | 技术文档 |
| 滑动窗口重叠 | 避免边界信息丢失 | 存储膨胀 | 高精度场景 |

**最佳实践**：`chunk_size=512, chunk_overlap=50` 作为基线，再根据业务调整。

**2. Embedding 模型选型**

```python
# 中文场景推荐
# 1. BAAI/bge-large-zh-v1.5（国产，中文最优）
# 2. text-embedding-3-small（OpenAI，多语言通用）
# 3. m3e-base（国产轻量，适合部署）

# 维度选择：768d 平衡精度与性能，1536d 精度更高但检索更慢
```

**3. 混合检索（Hybrid Search）**

纯向量检索的问题：语义相似 ≠ 关键词匹配。比如搜"苹果公司股价"，向量检索可能召回"水果价格"，而 BM25 能精确命中"苹果"关键词。

```python
# RRF（Reciprocal Rank Fusion）融合排序
def rrf(rank, k=60):
    return 1 / (k + rank)

# 向量检索得分 + BM25 得分加权融合
final_score = 0.3 * vector_score + 0.7 * bm25_score
```

**4. Rerank 重排序**

检索阶段（Retriever）取 Top-50，Rerank 阶段精排取 Top-3~5。Rerank 使用 Cross-Encoder 模型（如 BAAI/bge-reranker-v2），对每对（query, doc）逐对打分，精度远高于向量检索的双编码器（Bi-Encoder）。

#### 四、RAG 幻觉治理

```
幻觉来源：
  1. 检索结果不相关 → 改进检索质量
  2. 检索结果冲突 → 引入冲突检测
  3. LLM 忽略检索结果 → 强化 Prompt 约束

治理方案：
  ├─ 检索层：Hybrid Search + Rerank 提高召回质量
  ├─ 生成层：Self-RAG（自反思，检索结果不可用时拒绝回答）
  ├─ 验证层：Factual Consistency Check（事实一致性校验）
  └─ 兜底层：Confidence Threshold（低置信度时输出"无法确定"）
```

#### 五、Agentic RAG 与 Naive RAG 对比

| 维度 | Naive RAG | Agentic RAG |
|------|-----------|-------------|
| 检索次数 | 单次 | 多轮迭代 |
| 查询改写 | 无 | 自动改写/扩展 |
| 工具调用 | 无 | 可调用 API/DB |
| 自反思 | 无 | Self-Reflective |
| 适用场景 | 简单问答 | 复杂推理/多跳问题 |

## 题目 2：[Java并发] 请详细阐述 CAS（Compare-And-Swap）原理、ABA 问题及手写自旋锁实现

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-24 午间报告 — "手写底层实现：线程安全工具类手写、CAS原理、锁机制成为分水岭题目"
**相关岗位**：Java后端 / 高并发系统 / 基础架构

### 📖 参考答案

#### 一、CAS 核心原理

CAS（Compare-And-Swap）是一种**无锁编程算法**，核心思想是：**比较当前值与期望值，如果相等则更新为新值，否则不操作**。

```
CAS 操作的三要素：
  V（内存地址）  → 要修改的变量
  E（期望值）    → 当前线程认为变量应该的值
  N（新值）      → 要设置的新值
  
  执行逻辑：if (V == E) then V = N else 失败重试
```

**Java 中的 CAS 实现链路**：

```
AtomicInteger.compareAndSet()
    ↓
Unsafe.compareAndSwapInt()    ← sun.misc.Unsafe 类
    ↓
JVM 内联（C++ 实现）
    ↓
CPU cmpxchg 指令              ← 硬件层面保证原子性
    ↓
总线锁定 / 缓存锁定           ← 多核 CPU 缓存一致性协议（MESI）
```

关键点：CAS 是**硬件级别**的原子操作，不需要 Java 层面的加锁，比 `synchronized` 轻量得多。

#### 二、CAS 的三大问题

**问题 1：ABA 问题**

```
线程 1：读取 V = A
线程 2：将 V 从 A → B → A（中间被修改过又改回来了）
线程 1：CAS 检查 V == A → 成功更新（但 V 其实已经被改过了）

危害：在某些场景下会导致严重问题
  - 链表操作：头节点被修改又恢复，但链表结构已变
  - 内存回收：指针指向的对象已被回收重用
```

**解决方案**：

```java
// 方案 1：AtomicStampedReference（带版本号）
AtomicStampedReference<Integer> ref = new AtomicStampedReference<>(100, 0);
int[] stampHolder = new int[1];
Integer value = ref.get(stampHolder);  // value=100, stamp=0
ref.compareAndSet(100, 200, stampHolder[0], stampHolder[0] + 1);

// 方案 2：AtomicMarkableReference（带布尔标记位）
// 适用于只关心"是否被修改过"的场景
```

**问题 2：自旋开销（CPU 空转）**

CAS 失败后通常自旋重试，如果竞争激烈，CPU 会一直空转：

```java
// 典型的自旋 CAS
public final int getAndIncrement() {
    for (;;) {
        int current = get();
        int next = current + 1;
        if (compareAndSet(current, next))
            return current;
    }
}
```

优化：`Thread.onSpinWait()`（Java 9+）或自适应自旋次数。

**问题 3：只能保证单个共享变量的原子操作**

无法同时对多个变量做 CAS。解决方案：
- 使用 `AtomicReference` 包装多个变量
- 使用锁

#### 三、手写自旋锁（Spin Lock）

```java
import java.util.concurrent.atomic.AtomicReference;

/**
 * 基于 CAS 的可重入自旋锁
 */
public class SpinLock {
    // 持有锁的线程
    private final AtomicReference<Thread> owner = new AtomicReference<>();
    // 重入计数
    private int reentrantCount = 0;
    
    public void lock() {
        Thread currentThread = Thread.currentThread();
        // 如果当前线程已经持有锁 → 重入
        if (currentThread == owner.get()) {
            reentrantCount++;
            return;
        }
        // 自旋等待，直到成功获取锁
        while (!owner.compareAndSet(null, currentThread)) {
            // Java 9+ 可插入 Thread.onSpinWait() 提示 CPU 优化
            Thread.onSpinWait();
        }
    }
    
    public void unlock() {
        Thread currentThread = Thread.currentThread();
        if (currentThread != owner.get()) {
            throw new IllegalMonitorStateException("未持有锁的线程不能释放");
        }
        if (reentrantCount > 0) {
            reentrantCount--;
            return;
        }
        // 释放锁
        owner.set(null);
    }
}
```

**自旋锁 vs 互斥锁对比**：

| 维度 | 自旋锁 | 互斥锁（synchronized） |
|------|--------|----------------------|
| 等待方式 | CPU 空转 | 线程阻塞（上下文切换） |
| 适用场景 | 锁持有时间极短 | 锁持有时间长 |
| 优点 | 无上下文切换 | 不浪费 CPU |
| 缺点 | 浪费 CPU 资源 | 有切换开销 |

#### 四、面试追问

```
追问 1：CAS 和 synchronized 的区别？
→ CAS 是乐观锁（无阻塞），synchronized 是悲观锁（阻塞）。
  CAS 适合短操作，synchronized 适合长操作。
  CAS 需要处理 ABA 问题，synchronized 不需要。

追问 2：LongAdder 和 AtomicLong 的区别？
→ AtomicLong 在高并发下 CAS 竞争激烈，性能下降。
  LongAdder 将热点分散到多个 Cell，最后 sum() 汇总，
  适合"写多读少"的高并发计数场景。
```

## 题目 3：[AI/Agent] 请详细阐述 MCP（Model Context Protocol）协议的原理、架构设计及 Agent 工具调用机制

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-24 早间&午间报告 — "Agent开发面试新热点：MCP协议、Skills、Harness" + "大模型面经汇总：Agent、RAG、MCP协议"
**相关岗位**：AI应用开发 / Agent开发 / 全栈

### 📖 参考答案

#### 一、MCP 是什么？

MCP（Model Context Protocol）是 Anthropic 于 2024 年底推出的**开放协议**，旨在标准化 AI 模型与外部工具/数据源之间的通信接口。类比理解：

```
HTTP 是 Web 的基础协议  →  浏览器  ↔  Web 服务器
TCP/IP 是互联网的基石   →  设备    ↔  设备
MCP 是 Agent 的"USB 接口" →  AI 模型 ↔  工具/数据源
```

2026 年，MCP 已成为 AI Agent 生态的事实标准——任何工具只需实现一次 MCP Server，就能被 Claude、Cursor、OpenClaw 等所有主流 Agent 框架调用。

#### 二、MCP 三层架构

```
┌─────────────────────────────────────────────────┐
│                  MCP Host                        │
│  （运行 LLM 的应用，如 Claude Desktop、Cursor）     │
│  负责协调多个 Server 连接，管理安全权限             │
└────────────────────┬────────────────────────────┘
                     │ MCP Protocol（JSON-RPC 2.0）
                     ▼
┌─────────────────────────────────────────────────┐
│                 MCP Client                       │
│  （嵌入在 Host 中的协议客户端）                    │
│  维护与 Server 的持久连接，处理消息路由             │
└────────────────────┬────────────────────────────┘
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
┌─────────────┐ ┌─────────┐ ┌─────────────┐
│ MCP Server A │ │ MCP    │ │ MCP Server C│
│ （数据库）    │ │ Server B│ │ （文件系统）  │
│              │ │（API）  │ │              │
│ Tools:       │ │         │ │ Tools:       │
│  - query_db  │ │  - call │ │  - read_file │
│  - insert    │ │  - send │ │  - write_file│
│ Resources:   │ │         │ │              │
│  - schema:// │ │         │ │              │
└─────────────┘ └─────────┘ └─────────────┘
```

**三个核心角色**：

| 角色 | 职责 | 示例 |
|------|------|------|
| **MCP Host** | 运行 LLM 的主程序，协调连接 | Claude Desktop、Cursor、OpenClaw |
| **MCP Client** | 嵌入 Host 的协议客户端，1:1 连接 Server | 每个 Server 对应一个 Client |
| **MCP Server** | 暴露特定能力的轻量级服务 | 数据库 Server、API Server |

#### 三、MCP 核心能力

MCP Server 暴露三种能力：

**1. Tools（工具）** — 模型可调用的函数
```json
{
  "name": "search_code",
  "description": "搜索代码仓库中的文件",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": {"type": "string", "description": "搜索关键词"},
      "repo": {"type": "string", "description": "仓库路径"}
    },
    "required": ["query"]
  }
}
```

**2. Resources（资源）** — 模型可读取的结构化数据
```
资源 URI 示例：
  file:///logs/app.log
  database://customers/schema
  git://repo/commits
```

**3. Prompts（提示模板）** — 预定义的 Prompt 模板
```json
{
  "name": "code_review",
  "description": "代码审查模板",
  "arguments": [
    {"name": "code", "description": "待审查的代码"}
  ]
}
```

#### 四、Agent 工具调用机制（Function Calling → MCP）

```
Agent 工具调用的完整流程：

用户："帮我查一下北京今天的天气"
    │
    ▼
① LLM 接收用户请求 + 工具描述（MCP Server 注册的 Tools）
    │
    ▼
② LLM 判断需要调用天气查询工具
    │  返回结构化 JSON：
    │  {
    │    "tool_calls": [{
    │      "id": "call_abc123",
    │      "function": {
    │        "name": "get_weather",
    │        "arguments": "{\"city\": \"北京\"}"
    │      }
    │    }]
    │  }
    ▼
③ MCP Client 将请求转发给对应的 MCP Server
    │
    ▼
④ MCP Server 执行实际逻辑（调用天气 API）
    │
    ▼
⑤ 返回结果给 LLM
    │
    ▼
⑥ LLM 基于工具返回结果生成最终回答

```

#### 五、MCP 在 2026 年 Agent 生态中的位置

```
传统方式（2024）：
  每个 Agent 框架自己写适配器 → 每个工具写 N 次

MCP 方式（2026）：
  工具写一次 MCP Server → 所有框架都能用

2026 年生态全景：
  MCP（工具调用标准） + A2A（Agent间通信标准） + AG-UI（UI 交互标准）
```

| 资源管理 | 无 | 支持 Resources 和 Prompts |
| 生态兼容 | 单模型 | 跨模型/跨框架 |

## 题目 4：[框架/AI工程化] 请对比 Spring AI 与 LangChain4j 两大 Java 大模型集成框架，并阐述 Java 后端如何集成大模型 API

**难度**：⭐⭐⭐
**考点来源**：2026-06-24 早间报告 — "Java开发者应尽快补齐AI工程化能力（Spring AI、LangChain4j）" + "Java+AI+云原生复合人才薪资逆势上涨"
**相关岗位**：Java后端 / AI应用开发 / 全栈

### 📖 参考答案

#### 一、两大框架概述

**Spring AI**：Spring 官方生态下的大模型集成框架，核心目标是简化 Spring 应用与各类大模型的集成。类比理解——Spring AI 之于大模型，就像 Spring Data 之于数据库。

**LangChain4j**：LangChain 的 Java 移植版，对标 Python 生态的 LangChain，提供 Chain、Agent、Memory 等抽象。

#### 二、核心对比

| 对比维度 | Spring AI | LangChain4j |
|---------|-----------|-------------|
| **出身** | Spring 官方（VMware） | 社区驱动（LangChain 生态） |
| **设计哲学** | Spring 生态优先，Advisor 链模式（AOP 思想） | LangChain 风格，Chain 模式 |
| **与 Spring 集成** | ⭐⭐⭐⭐⭐ 深度集成 Security/Data/Actuator | ⭐⭐⭐ 需手动配置 |
| **国产模型支持** | 通义千问、文心一言（官方 Starter） | 通义千问（dashscope 适配器） |
| **RAG 支持** | VectorStore + DocumentReader | DocumentSplitter + EmbeddingStore |
| **Function Calling** | @Tool 注解 | ToolSpecification |

#### 一、为什么需要分布式锁？

单体应用用 `synchronized` 或 `ReentrantLock` 即可解决并发问题。但在微服务/分布式环境下，多个 JVM 进程需要**跨进程互斥访问共享资源**（如库存扣减、订单号生成、定时任务调度），这时就需要分布式锁。

```
单体应用：         分布式环境：
┌─────────┐       ┌─────────┐  ┌─────────┐  ┌─────────┐
│ JVM 1   │       │ JVM 1   │  │ JVM 2   │  │ JVM 3   │
│ 线程A→锁│       │ 进程A→锁│  │ 进程B→锁│  │ 进程C→锁│
│ 线程B→等│       │   ↓     │  │   ↓     │  │   ↓     │
└─────────┘       └─────────┘  └─────────┘  └─────────┘
                      ↓            ↓            ↓
                   ┌─────────────────────────────┐
                   │       分布式锁中间件          │
                   │   (Redis / ZooKeeper / DB)   │
                   └─────────────────────────────┘
```

#### 二、三大方案详解

**方案 1：Redis 分布式锁（SETNX + Lua）**

```java
// 正确姿势：SET NX EX + Lua 原子释放
public class RedisDistributedLock {
    private final StringRedisTemplate redisTemplate;
    
    /**
     * 获取锁
     * @param key 锁的键
     * @param value 唯一标识（UUID，用于安全释放）
     * @param expireMs 过期时间（毫秒）
     */
    public boolean tryLock(String key, String value, long expireMs) {
        return Boolean.TRUE.equals(
            redisTemplate.opsForValue()
                .setIfAbsent(key, value, expireMs, TimeUnit.MILLISECONDS)
        );
    }
    
    /**
     * 安全释放锁（Lua 脚本保证原子性）
     * 必须检查 value 是否匹配，防止释放别人的锁
     */
    public boolean unlock(String key, String value) {
        String luaScript = """
            if redis.call('get', KEYS[1]) == ARGV[1] then
                return redis.call('del', KEYS[1])
            else
                return 0
            end
            """;
        Long result = redisTemplate.execute(
            new DefaultRedisScript<>(luaScript, Long.class),
            Collections.singletonList(key),
            value
        );
        return Long.valueOf(1).equals(result);
    }
}
```

**Redlock 算法（Redis 官方分布式锁方案）**：

当 Redis 是单节点时，存在**主从切换导致锁丢失**的问题（主节点宕机，从节点未同步锁信息）。Redlock 的解决思路：

```
Redlock 算法步骤：
1. 获取当前时间戳 T1
2. 依次向 N 个（通常 5 个）独立 Redis 节点尝试加锁
3. 计算获取锁消耗的时间 = T2 - T1
4. 如果成功获取超过半数节点（N/2+1）的锁，且总耗时 < 锁过期时间 → 加锁成功
5. 否则，向所有节点发送解锁请求
```

**优点**：性能极高（纯内存操作）
**缺点**：Redlock 存在争议（Martin Kleppmann 曾发文质疑其安全性）；依赖时钟同步

**方案 2：ZooKeeper 分布式锁**

基于 ZooKeeper 的**临时顺序节点（Ephemeral Sequential Node）**实现：

```
加锁流程：
  1. 在 /locks/ 下创建临时顺序节点 /locks/lock_000000001
  2. 获取 /locks/ 下所有子节点
  3. 如果自己是最小编号 → 获得锁
  4. 如果不是最小编号 → 监听前一个节点（Watch）
  5. 前一个节点释放后 → 收到通知 → 重新检查

释放锁：
  - 主动删除节点
  - 客户端断开连接 → 临时节点自动删除（避免死锁）
```

```java
// Curator 框架实现（推荐）
InterProcessMutex lock = new InterProcessMutex(client, "/locks/order_123");
try {
    if (lock.acquire(3, TimeUnit.SECONDS)) {
        // 执行业务逻辑
    }
} finally {
    lock.release();
}
```

**优点**：强一致性（ZAB 协议）、无超时问题、Watch 机制避免轮询
**缺点**：性能低于 Redis（磁盘写入）、需要维护 ZK 集群

**方案 3：数据库乐观锁**

```sql
-- 基于版本号的乐观锁
UPDATE product 
SET stock = stock - 1, version = version + 1 
WHERE id = 1 AND stock > 0 AND version = #{oldVersion};

-- 或基于条件（库存扣减）
UPDATE product 
SET stock = stock - 1 
WHERE id = 1 AND stock > 0;
```

**优点**：无需额外中间件、实现简单
**缺点**：性能最低（数据库 IO）、存在单点问题、不适合高并发
