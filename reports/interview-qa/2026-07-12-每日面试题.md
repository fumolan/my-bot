## 题目 1：[缓存/Redis] Redis 缓存雪崩、缓存穿透、缓存击穿的区别及各自的解决方案

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-12 日报 — "Redis 三个经典问题（穿透/击穿/雪崩）成为面试必考点"
**相关岗位**：Java后端 / 全栈 / 中间件开发

### 📖 参考答案

#### 一、三个概念的本质区别

这三个问题都是缓存层失效导致请求直达数据库的场景，但**触发原因**完全不同：

```
请求路径对比：

正常流程：
  客户端 → Redis（命中）→ 返回 ← 数据库无压力 ❄️

缓存穿透（查不存在的数据）：
  客户端 → Redis（未命中，key不存在）→ DB查询（也不存在）
  → 每次请求都穿透缓存打DB → 数据库压力爆炸 💥

缓存击穿（热点key过期）：
  客户端 → Redis（某个热点key刚过期）→ 大量并发请求同时打DB
  → 数据库被同一热点瞬时打垮 💥

缓存雪崩（大面积key同时过期/Redis宕机）：
  客户端 → Redis（大量key同时过期）→ 所有请求涌入DB
  → 数据库瞬间被打垮，可能引发雪崩连锁反应 💥💥💥
```

| 问题 | 触发条件 | 影响范围 | 现象 |
|------|---------|---------|------|
| **缓存穿透** | 查询一个**不存在**的数据 | 单个key反复穿透 | 缓存永远空，DB压力持续 |
| **缓存击穿** | **热点key**恰好过期，大量并发同时访问 | 单个热点key | 瞬时DB打爆，但恢复快 |
| **缓存雪崩** | **大量key同时过期**或Redis宕机 | 大面积key | 灾难性，可能引发服务雪崩 |

#### 二、缓存穿透（Cache Penetration）解决方案

**方案 1：空值缓存（最常用）**
```java
// 核心思路：即使数据库查不到，也缓存一个空值（短过期时间）
public User getUserById(String userId) {
    // 1. 查缓存
    String cacheKey = "user:" + userId;
    String cacheValue = redis.get(cacheKey);
    
    if (cacheValue != null) {
        // 命中缓存（包括空值缓存）
        if ("NULL_VALUE".equals(cacheValue)) {
            return null;  // 之前已确认不存在
        }
        return JSON.parse(cacheValue, User.class);
    }
    
    // 2. 查数据库
    User user = userMapper.selectById(userId);
    
    // 3. 回写缓存
    if (user == null) {
        // 空值也缓存，过期时间设为短时间（60秒）
        redis.setex(cacheKey, 60, "NULL_VALUE");
    } else {
        redis.setex(cacheKey, 3600, JSON.toJson(user));
    }
    
    return user;
}
```

**方案 2：布隆过滤器（Bloom Filter）**
```java
// 布隆过滤器：判断"一定不存在" vs "可能存在"
// 提前将所有合法 userId 加载到布隆过滤器

@Component
public class UserBloomFilter {
    
    private final BloomFilter<String> bloomFilter;
    
    @PostConstruct
    public void init() {
        // 创建布隆过滤器：预计100万数据，误判率1%
        bloomFilter = BloomFilter.create(
            Funnels.stringFunnels(), 1_000_000, 0.01);
        
        // 加载所有合法用户ID到布隆过滤器
        List<String> allUserIds = userMapper.selectAllIds();
        allUserIds.forEach(bloomFilter::put);
    }
    
    public boolean mightContain(String userId) {
        return bloomFilter.mightContain(userId);
    }
}

// 使用：查缓存前先过布隆过滤器
public User getUserById(String userId) {
    // 布隆过滤器拦截：不存在的ID直接返回
    if (!bloomFilter.mightContain(userId)) {
        return null;  // 100% 不存在
    }
    // 继续查缓存 → 查DB流程...
    // 布隆过滤器说"可能存在"（可能误判），但误判率仅1%
}
```

**布隆过滤器原理：**
```
布隆过滤器 = 一个大型位数组 + 多个哈希函数

添加元素：用 k 个哈希函数计算位置 → 对应位设为 1
查询元素：用 k 个哈希函数计算位置 → 检查是否全部为 1
  - 有任意一位为 0 → 一定不存在 ✅
  - 全部为 1 → 可能存在（有误判率）⚠️

特点：绝对不漏报（不存在就是不存在），但可能误报（说存在但实际不存在）
```

#### 三、缓存击穿（Cache Breakdown）解决方案

**方案 1：互斥锁（Mutex Key）**
```java
public User getUserById(String userId) {
    String cacheKey = "user:" + userId;
    
    // 1. 查缓存
    String cacheValue = redis.get(cacheKey);
    if (cacheValue != null) {
        return JSON.parse(cacheValue, User.class);
    }
    
    // 2. 缓存未命中 → 加锁，只允许一个线程查DB
    String lockKey = "lock:user:" + userId;
    String lockValue = UUID.randomUUID().toString();
    
    // 尝试获取锁（SET NX EX 3秒）
    boolean locked = redis.setnx(lockKey, lockValue, 3);
    
    if (locked) {
        try {
            // 双重检查：可能其他线程已重建缓存
            cacheValue = redis.get(cacheKey);
            if (cacheValue != null) {
                return JSON.parse(cacheValue, User.class);
            }
            
            // 查数据库
            User user = userMapper.selectById(userId);
            redis.setex(cacheKey, 3600, JSON.toJson(user));
            return user;
        } finally {
            // 释放锁（Lua脚本保证原子性）
            unlock(lockKey, lockValue);
        }
    } else {
        // 未获取到锁：等待后重试
        Thread.sleep(50);
        return getUserById(userId);  // 递归重试
    }
}
```

**方案 2：热点 key 永不过期 + 异步更新**
```java
// 物理上不设置过期时间
// 逻辑过期：value 中存过期时间，后台线程异步刷新

public User getUserById(String userId) {
    String cacheKey = "user:" + userId;
    String json = redis.get(cacheKey);
    
    if (json == null) {
        return null;  // 缓存彻底不存在（重建）
    }
    
    // 解析缓存数据，检查逻辑过期时间
    CacheWrapper<User> wrapper = JSON.parse(json, new TypeReference<>(){});
    
    if (wrapper.isExpired()) {
        // 逻辑过期 → 异步重建缓存
        asyncRebuildCache(userId);
        // 但此时仍然返回旧数据（避免等待）
        return wrapper.getData();
    }
    
    return wrapper.getData();
}

// 后台线程池异步重建
@Async("cacheRebuildExecutor")
public void asyncRebuildCache(String userId) {
    String lockKey = "lock:rebuild:" + userId;
    if (redis.setnx(lockKey, "1", 5)) {
        try {
            User user = userMapper.selectById(userId);
            CacheWrapper<User> wrapper = new CacheWrapper<>(user, 3600);
            redis.set("user:" + userId, JSON.toJson(wrapper));
        } finally {
            redis.del(lockKey);
        }
    }
}
```

**方案 3：本地缓存兜底（Caffeine + Redis 多级缓存）**
```java
// Caffeine 本地缓存（毫秒级访问）
@Bean
public Cache<String, User> localCache() {
    return Caffeine.newBuilder()
        .maximumSize(10_000)
        .expireAfterWrite(5, TimeUnit.SECONDS)  // 短过期
        .build();
}

public User getUserById(String userId) {
    // 1. 查本地缓存（最快）
    User user = localCache.getIfPresent(userId);
    if (user != null) return user;
    
    // 2. 查 Redis
    String json = redis.get("user:" + userId);
    if (json != null) {
        user = JSON.parse(json, User.class);
        localCache.put(userId, user);  // 回写本地缓存
        return user;
    }
    
    // 3. 查 DB（加互斥锁）
    // ...（同方案 1）
}
```

#### 四、缓存雪崩（Cache Avalanche）解决方案

| 方案 | 说明 | 代码示例 |
|------|------|---------|
| **过期时间加随机值** | 避免大量key同时过期 | `setex(key, baseTime + random(300), value)` |
| **多级缓存** | 本地缓存 + Redis 分层兜底 | Caffeine（本地）+ Redis（分布式） |
| **Redis 集群高可用** | 主从 + 哨兵 / Cluster，防止宕机 | Redis Sentinel / Cluster |
| **服务熔断降级** | DB 压力过大时直接降级返回兜底数据 | Sentinel / Resilience4j |
| **提前预热** | 大促前主动加载热点数据到缓存 | 定时任务 + 批量加载 |

```java
// 核心方案：过期时间加随机值
public void setCacheWithRandomExpire(String key, String value, int baseSeconds) {
    // 在基础过期时间上增加 0-300 秒随机值
    int random = ThreadLocalRandom.current().nextInt(300);
    redis.setex(key, baseSeconds + random, value);
}

// 批量初始化缓存时尤为重要
public void batchPreheat(List<Product> products) {
    products.forEach(product -> {
        String key = "product:" + product.getId();
        String value = JSON.toJson(product);
        // 每个key的过期时间都不同，错峰过期
        setCacheWithRandomExpire(key, value, 3600);
    });
}
```

```
3. 补充生产经验（面试加分）：

```

### 💡 延伸思考
1. **布隆过滤器支持删除吗？** — 标准布隆过滤器不支持删除（因为多个元素可能共享同一位）。如果需要删除，可以用计数布隆过滤器（Counting Bloom Filter），每个位改为计数器，但空间消耗更大。
2. **多级缓存的数据一致性问题怎么解决？** — 本地缓存+Redis的常见策略：本地缓存设短过期（5-10秒），Redis更新时主动失效本地缓存（通过消息队列广播失效事件）。强一致性场景不适合多级缓存。

## 题目 2：[JVM调优] 生产环境 JVM OOM（内存溢出）的完整排查流程与实战分析

### 📖 参考答案

#### 一、JVM 四大常见 OOM 场景

| OOM 类型 | 触发原因 | 典型场景 | JVM 参数 |
|---------|---------|---------|---------|
| **Heap OOM**（堆溢出） | 对象无法被 GC 回收，堆空间耗尽 | 内存泄漏（集合未清空）、大对象分配 | `-Xmx` |
| **Metaspace OOM**（元空间溢出） | 类元数据过多 | 动态生成大量类（CGLIB/热部署）、大量 JSP | `-XX:MaxMetaspaceSize` |
| **Direct Memory OOM**（直接内存溢出） | NIO 的 ByteBuffer 未释放 | Netty 请求堆积、手动分配 DirectBuffer 未回收 | `-XX:MaxDirectMemorySize` |
| **Stack OOM**（栈溢出） | 线程栈过多或递归过深 | 无限递归、线程数量超过 OS 限制 | `-Xss` |


#### 二、OOM 排查完整流程（五步法）

```
Step 1: 确认 OOM 类型
┌─────────────────────────────────────────────────────────┐

│                                                         │

└─────────────────────────────────────────────────────────┘

Step 5: 定位代码问题并修复
┌─────────────────────────────────────────────────────────┐
```

#### 三、实战案例：一次完整的 OOM 排查

**背景**：某订单服务上线后，运行 2 小时后出现 `OutOfMemoryError: Java heap space`，服务重启。

**排查过程：**

```bash
# Step 1: 添加 JVM 参数，复现问题
java -Xmx2g -Xms2g \
     -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/app/dumps/ \
     -Xlog:gc*:file=/app/logs/gc.log:time,uptime,level,tags \
     -jar order-service.jar
```

**MAT 分析结果：**
```
Leak Suspects Report 输出：
- Problem Suspect 1: 
  一个 java.util.HashMap 实例占用了 1.2GB 堆内存（占总堆的 60%）
  由 com.example.OrderService.orderCache 持有
  包含 200 万个 Entry，key 为 OrderId，value 为 OrderDetail 对象
  
- Path to GC Root:
  com.example.OrderService → orderCache (HashMap)
  → 被 static 引用 → GC Root (类加载器)
```

**根因分析：**
```java
// ❌ 问题代码：缓存无上限 + 未设置过期策略
@Service
public class OrderService {
    // 静态 Map 作为缓存，无大小限制
    private static Map<String, OrderDetail> orderCache = new HashMap<>();
    
    public OrderDetail getOrderDetail(String orderId) {
        // 先查本地缓存
        OrderDetail detail = orderCache.get(orderId);
        if (detail != null) return detail;
        
        // 查 DB，然后放入缓存
        detail = orderMapper.selectById(orderId);
        orderCache.put(orderId, detail);  // ❌ 只增不减！
        return detail;
    }
}
```

**修复方案：**
```java
// ✅ 修复：使用 Guava Cache 设置大小上限和过期策略
@Service
public class OrderService {
    private final Cache<String, OrderDetail> orderCache = Caffeine.newBuilder()
        .maximumSize(10_000)           // 最多缓存 1 万条
        .expireAfterWrite(30, TimeUnit.MINUTES)  // 30 分钟过期
        .recordStats()                 // 记录缓存统计
        .build();
    
    public OrderDetail getOrderDetail(String orderId) {
        try {
```

## 题目 4：[数据库/MySQL] 生产级慢 SQL 优化实战：从定位、分析到优化的完整方法论

#### 一、慢 SQL 定位：四种手段

| 手段 | 命令/工具 | 适用场景 |
|------|-----------|---------|
| **慢查询日志** | `slow_query_log` + `long_query_time` | 离线分析，历史数据 |
| **performance_schema** | `SELECT * FROM events_statements_summary_by_digest` | 实时查看 TOP SQL |
| **sys 库** | `SELECT * FROM sys.statement_analysis` | 一键分析，最方便 |
| **APM 工具** | SkyWalking / Cat / Arthas | 分布式链路追踪 |

```sql
-- 方式一：开启慢查询日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;      -- 超过 1 秒记录
SET GLOBAL log_queries_not_using_indexes = ON;

-- 查看 TOP 10 慢 SQL
mysqldumpslow -s t -t 10 /var/lib/mysql/slow.log
-- -s t: 按查询时间排序
-- -t 10: 取前 10 条

-- 方式二：performance_schema（MySQL 5.7+）
SELECT DIGEST_TEXT, COUNT_STAR, AVG_TIMER_WAIT/1000000000 AS avg_ms,
       SUM_ROWS_EXAMINED, SUM_ROWS_SENT
FROM performance_schema.events_statements_summary_by_digest
ORDER BY AVG_TIMER_WAIT DESC
LIMIT 10;

-- 方式三：sys 库（最方便）
SELECT * FROM sys.statement_analysis
ORDER BY avg_latency DESC
LIMIT 10;
```

#### 二、EXPLAIN 执行计划深度解读

```sql
EXPLAIN SELECT o.id, o.amount, u.name
FROM order o
LEFT JOIN user u ON o.user_id = u.id
WHERE o.status = 'PAID'
  AND o.create_time > '2026-07-01'
ORDER BY o.create_time DESC
LIMIT 20;
```

**输出解读：**

```
id | select_type | table | type   | possible_keys        | key         | key_len | ref | rows   | Extra
---|------------|-------|--------|---------------------|-------------|---------|-----|--------|----------------------------
1  | SIMPLE     | o     | ALL    | idx_status,idx_ctime| NULL        | NULL    | NULL| 500000 | Using where; Using filesort
1  | SIMPLE     | u     | eq_ref | PRIMARY             | PRIMARY     | 8       | o.user_id | 1 | Using index
```

**问题诊断：**
- `o` 表 **type=ALL**（全表扫描！扫描 50 万行）
- `o` 表 **Extra=Using filesort**（文件排序！排序未用索引）
- `o` 表 **possible_keys** 有索引但没使用

**优化方案：**
```sql
-- 1. 建立联合索引（覆盖 WHERE 和 ORDER BY）
ALTER TABLE `order` ADD INDEX idx_status_ctime (status, create_time);

-- 优化后 EXPLAIN：
-- type=ref, key=idx_status_ctime, rows=10000, Extra=Using index condition
-- 扫描行数从 50 万降到 1 万，Using filesort 消失 ✅
```

#### 三、十大索引失效场景及实战修复

| 序号 | 场景 | 错误写法 | 正确写法 | 优化效果 |
|------|------|---------|---------|---------|
| 1 | LIKE 前缀模糊 | `LIKE '%关键字'` | `LIKE '关键字%'` | 全表扫描→范围扫描 |
| 2 | 索引列运算 | `WHERE age + 1 = 30` | `WHERE age = 29` | 全表扫描→索引查找 |
| 3 | 索引列函数 | `WHERE SUBSTR(phone,1,3)='138'` | `WHERE phone LIKE '138%'` | 全表扫描→范围扫描 |
| 4 | 隐式类型转换 | `WHERE phone = 13800138000` | `WHERE phone = '13800138000'` | 全表扫描→索引查找 |
| 5 | OR 含无索引列 | `WHERE name='张' OR age=30` | `UNION ALL` 或加索引 | 全表扫描→索引合并 |
| 6 | 违反最左前缀 | 索引(a,b,c) 查 `WHERE b=1` | 加 b 的单列索引 | 全表扫描→索引查找 |
| 7 | NOT IN 大范围 | `WHERE id NOT IN (1,2,3)` | `LEFT JOIN` 反连接 | 全表扫描→索引扫描 |
| 8 | != 或 <> | `WHERE status != 'SUCCESS'` | `IN ('FAILED','PENDING')` | 全表扫描→索引查找 |
| 9 | IS NOT NULL 高比例 | `WHERE deleted IS NOT NULL`（90%数据） | 改为覆盖索引 | 优化器倾向全表 |
| 10 | 统计信息过期 | 数据变化大但 ANALYZE 未执行 | `ANALYZE TABLE xxx` | 优化器选错计划→正确 |

**最左前缀原则实战案例：**
```sql
-- 联合索引 idx_city_status_ctime (city, status, create_time)

-- ✅ 能用索引的查询：
WHERE city = '北京'                         -- 用到 city
WHERE city = '北京' AND status = 'PAID'     -- 用到 city, status
WHERE city = '北京' AND status = 'PAID' 
  AND create_time > '2026-07-01'            -- 用到全部三列
WHERE city LIKE '北%'                        -- 用到 city（范围查询）

-- ❌ 不能完全用索引的查询：
WHERE status = 'PAID'                        -- 没 city，全表扫描
WHERE create_time > '2026-07-01'             -- 没 city, status
WHERE city = '北京' AND create_time > '2026-07-01'  -- 跳过 status，只有 city 用索引
```

#### 四、深分页优化

```sql
-- ❌ 传统分页：offset 越大越慢
SELECT * FROM `order` WHERE status = 'PAID' 
ORDER BY id LIMIT 1000000, 20;
-- → 扫描 100 万行后丢弃前 100 万行，极其浪费

-- ✅ 方案一：子查询分页（利用覆盖索引）
SELECT * FROM `order`
WHERE id >= (
    SELECT id FROM `order`
    WHERE status = 'PAID'
    ORDER BY id
    LIMIT 1000000, 1
)
LIMIT 20;
-- → 子查询走覆盖索引，只扫描 20 行

-- ✅ 方案二：游标分页（推荐，适用于前端滚动场景）
-- 前端传 lastId（上一页最后一条的 ID）
SELECT * FROM `order`
WHERE status = 'PAID' AND id > #{lastId}
ORDER BY id
LIMIT 20;
-- → 利用主键索引直接定位，效率最高

-- ✅ 方案三：业务限制（最粗暴有效）
-- "用户只能查看前 100 页数据"
-- 超过 100 页提示"请使用搜索条件缩小范围"
```

#### 五、实战案例：一个慢 SQL 的完整优化

**原始 SQL：**
```sql
-- 查询"过去 7 天支付金额 > 1000 元的用户"
SELECT DISTINCT u.id, u.name, u.phone
FROM user u
JOIN `order` o ON u.id = o.user_id
WHERE o.status = 'PAID'
  AND o.pay_amount > 1000
  AND o.pay_time > DATE_SUB(NOW(), INTERVAL 7 DAY)
ORDER BY u.id;
```

**问题分析（EXPLAIN）：**
- `o` 表全表扫描（500 万行）
- `DISTINCT` 导致临时表
- 连接查询未使用索引

**优化方案：**
```sql
-- Step 1: 给 order 表加联合索引
ALTER TABLE `order` ADD INDEX idx_status_paytime_amount 
    (status, pay_time, pay_amount, user_id);
-- 覆盖索引：包含所有查询列，无需回表

-- Step 2: 去掉 DISTINCT（用 EXISTS 替代子查询更高效）
SELECT u.id, u.name, u.phone
FROM user u
WHERE EXISTS (
    SELECT 1 FROM `order` o
    WHERE o.user_id = u.id
      AND o.status = 'PAID'
      AND o.pay_amount > 1000
      AND o.pay_time > DATE_SUB(NOW(), INTERVAL 7 DAY)
)
ORDER BY u.id;

-- Step 3: 最终优化效果
-- 优化前：500万行全表扫描 + Using temporary + Using filesort → 12秒
-- 优化后：索引覆盖 + 子查询 → 0.03秒
-- 性能提升 400 倍 ✅
```

### 💡 延伸思考
1. **分库分表后如何做慢 SQL 优化？** — 分库分表后单表数据量下降，但跨分片查询（如 `ORDER BY create_time LIMIT 20`）需要在应用层做归并排序，复杂度更高。建议用 ES 或 TiDB 替代复杂的分库分表查询。
2. **MySQL 8.0 的倒序索引优化了什么？** — 传统索引只能按 ASC 排序，`ORDER BY create_time DESC` 需要文件排序。MySQL 8.0 支持倒序索引 `INDEX idx_ctime_desc (create_time DESC)`，可直接用于降序排序，消除 filesort。

#### 四、Kubernetes 资源优化最佳实践

**1. 资源请求与限制（Resource Requests & Limits）**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # 最大额外 Pod 数
      maxUnavailable: 0  # 保证可用 Pod 数
  template:
    spec:
      containers:
      - name: order-service
        image: myapp:latest
        ports:
        - containerPort: 8080
        # === 核心：资源管理 ===
        resources:
          requests:          # 调度保证（K8s 按此值调度）
            cpu: 500m        # 0.5 核 CPU
            memory: 512Mi    # 512MB 内存
          limits:            # 硬限制（超过会被 OOMKill）
            cpu: 1000m       # 最多 1 核
            memory: 768Mi    # 最多 768MB
        # === 健康检查 ===
        livenessProbe:       # 存活检查（失败重启 Pod）
          httpGet:
            path: /actuator/health/liveness
            port: 8080
          initialDelaySeconds: 10
          periodSeconds: 10
        readinessProbe:      # 就绪检查（失败从 Service 移除）
          httpGet:
            path: /actuator/health/readiness
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 5
        # === 优雅关闭 ===
        lifecycle:
          preStop:
            exec:
              command: ["sh", "-c", "sleep 10"]
```
