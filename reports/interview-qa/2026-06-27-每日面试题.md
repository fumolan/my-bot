## 题目 1：[AI/大模型] 请详细阐述 Spring AI 2.0 的架构设计，以及 MCP（Model Context Protocol）协议如何实现工具调用的标准化

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-27 早间&午间报告 — "Spring AI 2.0.0 GA 发布，Tool Calling 成为一等公民，MCP 协议原生集成" + "AI Agent 面试高频考点"
**相关岗位**：AI应用开发 / Java后端（AI方向） / 全栈

### 📖 参考答案

#### 一、Spring AI 2.0 的整体定位

Spring AI 2.0 不是"Java 版 LangChain"，而是 Spring 生态对 AI 时代的完整回答。它建立在 **Spring Boot 4.0/4.1 + Spring Framework 7.0** 的基线之上，深度融入 Spring 的 IoC、自动配置、可观测性体系。

**四层架构**：

```
┌──────────────────────────────────────────────┐
│              应用层（Application）              │
│   ChatClient / Agent / RAG Pipeline           │
├──────────────────────────────────────────────┤
│            抽象层（AI Abstraction）             │
│   ChatModel / EmbeddingModel / ToolService    │
├──────────────────────────────────────────────┤
│           协议层（MCP Protocol）                │
│   MCP Client / MCP Server / Transport         │
├──────────────────────────────────────────────┤
│           模型适配层（Model Adapters）           │
│   OpenAI / DeepSeek / Claude / 通义千问...     │
└──────────────────────────────────────────────┘
```

#### 二、MCP 协议的核心原理

MCP（Model Context Protocol）由 Anthropic 提出，目标是解决工具接入的"碎片化"问题——不同模型（OpenAI tools、Google function_declarations、阿里百炼 plugin）各有各的接口规范，开发者需要为每个工具单独编写适配代码。

**MCP 的三大核心能力**：

| 能力类型 | 说明 | 类比 |
|---------|------|------|
| **Tools（工具）** | 可被 AI 调用的函数，执行具体操作 | 遥控器按钮 |
| **Resources（资源）** | 结构化数据，供 AI 读取上下文 | 参考书 |
| **Prompts（提示模板）** | 预定义的提示词模板 | 对话开场白 |

**三层架构**：

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   Host       │     │   Client     │     │   Server     │
│ (AI 应用)     │────▶│ (MCP SDK)    │────▶│ (工具提供方)   │
│              │     │              │     │              │
│ 管理连接      │     │ 协议转换      │     │ 注册工具      │
│ 处理用户输入   │     │ 请求路由      │     │ 执行操作      │
└──────────────┘     └──────────────┘     └──────────────┘
```

**两种传输方式**：
- **stdio**：本地进程间通信，适合开发环境
- **SSE（Server-Sent Events）**：远程 HTTP 通信，适合生产环境
- **Streamable HTTP**（Spring AI 推荐）：支持流式响应的 HTTP 传输

#### 三、Spring AI 2.0 中的 MCP 集成

```java
// 1. 注解式声明 MCP 工具
@Tool(description = "查询天气")
public String getWeather(@ToolParam(description = "城市名") String city) {
    return weatherService.query(city);
}

// 2. MCP Server 端 Starter 配置
@Configuration
@EnableMcpServer
public class McpServerConfig {
    @Bean
    public McpServer mcpServer(McpSchema.SchemaRegistry registry) {
        return McpServer.using(registry)
            .transport(new StdioServerTransport())
            .build();
    }
}

// 3. MCP Client 端调用
McpClient client = McpClient.using(httpTransport("http://localhost:8080/mcp"))
    .build();
List<Tool> tools = client.listTools();  // 发现工具
client.callTool("getWeather", Map.of("city", "北京"));  // 调用工具
```

#### 四、MCP vs 传统 Function Calling

| 维度 | 传统 Function Calling | MCP 协议 |
|------|---------------------|----------|
| **标准化** | 各模型各自定义 | 统一协议标准 |
| **工具发现** | 硬编码工具列表 | 动态发现（listTools） |
| **传输协议** | HTTP 自定义 | stdio / SSE / Streamable HTTP |
| **跨模型** | 需适配不同模型 | 一次接入，到处可用 |
| **Spring 集成** | 手动封装 | Spring AI Starter 原生支持 |
| **生态** | 碎片化 | 微软/Anthropic/Databricks 联合推动 |

#### 五、2026 年面试重点

面试官常问的追问点：
1. **MCP 和 Function Calling 的本质区别是什么？** → MCP 是协议层标准化，Function Calling 是模型层能力
2. **Spring AI 的 Tool Calling 如何实现？** → 通过 `@Tool` 注解 + `ToolService` 注册 + MCP 协议传输
3. **Agent 死循环怎么处理？** → 设置最大迭代次数、超时控制、人工干预回调

## 题目 2：[Java基础/JVM] JDK 25 LTS 引入了哪些核心新特性？请详细说明 Valhalla 值类型和虚拟线程 2.0 的原理与实战价值

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-27 午间报告 — "JDK 25 LTS 新特性实战" + "Spring Boot 4.1 要求 Java 25 最低版本"
**相关岗位**：Java后端 / 基础架构 / 全栈

### 📖 参考答案

#### 一、JDK 25 LTS 的定位

JDK 25 是继 JDK 21 之后的第二个 LTS（长期支持）版本，2025 年 9 月正式发布。它标志着 Java 平台从"增量改进"进入"代际跨越"阶段——**Valhalla 项目落地、虚拟线程 2.0、结构化并发正式 GA**。

#### 二、Valhalla 值类型（Value Types）

**核心问题**：传统 Java 对象有对象头（mark word + klass pointer，约 16 字节），大量小对象（如电商 SKU、订单行）的内存开销中，对象头占比高达 30%-60%。

**解决方案**：值类型（`value` 关键字）——零对象头开销，直接内联存储。

```java
// 传统写法 — 每个对象 24 字节（16 字节对象头 + 8 字节数据）
record MoneyObj(long cents) {}

// JDK 25 值类型 — 仅 8 字节，零对象头
value record Money(long cents) {}
```

**性能收益**：

| 维度 | 传统对象 | 值类型 | 提升 |
|------|---------|--------|------|
| 内存占用 | 24 字节/个 | 8 字节/个 | **-67%** |
| CPU 缓存命中 | 差（间接引用） | 好（连续内存） | 显著 |
| GC 压力 | 需要 GC 回收 | 栈分配，无需 GC | **大幅降低** |
| 批量处理（100 万） | ~24 MB | ~8 MB | **-67%** |

**实战场景**：
- 电商 SKU、订单行、价格快照等纯数据载体
- 高频数值计算（金融、量化交易）
- 缓存中的不可变值对象

#### 三、虚拟线程 2.0（Project Loom 第二阶段）

JDK 21 引入虚拟线程（Virtual Threads），JDK 25 将其推向 2.0 时代：

**核心改进**：

| 特性 | JDK 21（1.0） | JDK 25（2.0） |
|------|--------------|--------------|
| **调度器** | ForkJoinPool（固定并行度） | 自适应调度器 |
| **pinned 问题** | synchronized 会导致 pinned | 大幅减少 pinned 场景 |
| **监控** | 基础 | 完整 JMX + Flight Recorder |
| **与 NIO 集成** | 部分 | 全面深度集成 |
| **内存开销** | ~2KB/线程 | ~1KB/线程 |

```java
// 虚拟线程 2.0 — 百万级并发
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    // 提交 10 万个任务
    List<Future<Result>> futures = IntStream.range(0, 100_000)
        .mapToObj(i -> executor.submit(() -> processOrder(i)))
        .toList();
    
    // 所有任务并行执行，但只占用 ~10 个 OS 线程
    for (var future : futures) {
        future.get();  // 阻塞不占 OS 线程
    }
}
```

**与 Spring Boot 4.1 的配合**：
Spring Boot 4.x 默认启用虚拟线程，配合 `LazyConnection` 数据源代理，解决"虚拟线程 + 连接池"的冲突问题——虚拟线程阻塞时不再占用连接池线程，吞吐量提升 3-5 倍。

#### 四、结构化并发（JEP 453）

```java
// 传统写法 — 异常处理繁琐
Future<String> user = executor.submit(() -> fetchUser());
Future<String> order = executor.submit(() -> fetchOrder());
try {
    String result = user.get() + order.get();
} catch (Exception e) { /* 需要手动取消另一个 */ }

// JDK 25 结构化并发
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Future<String> user = scope.fork(() -> fetchUser());
    Future<String> order = scope.fork(() -> fetchOrder());
    scope.join();            // 等待所有任务
    scope.throwIfFailed();   // 任一失败则取消所有
    return user.resultNow() + order.resultNow();
}
// scope.close() 自动取消未完成的任务
```

## 题目 3：[框架/Spring] Spring Boot 4.1 被称作"4.x 系列的稳定之锚"，请说明其核心升级内容、迁移注意事项以及虚拟线程 + LazyConnection 的配合原理

**难度**：⭐⭐⭐⭐

**相关岗位**：Java后端 / 基础架构 / 全栈

### 📖 参考答案

#### 一、Spring Boot 4.1 的核心升级

Spring Boot 4.1 是 4.x 系列的第一个功能增强版本，包含 **113 个改进**，被视为"稳定之锚"。

**7 大重点变化**：

| 变化 | 详细说明 | 影响等级 |
|------|---------|---------|
| **废弃 API 移除** | 4.0 中标记废弃的 API 在 4.1 中正式移除 | ⚠️ 破坏性 |

#### 二、迁移注意事项

**环境要求**：
```
JDK: ≥ Java 25（推荐 Oracle JDK 25 或 OpenJDK 25）
Maven: ≥ 3.9.6
Gradle: ≥ 8.8
Jakarta EE: 11（Servlet 6.1, JPA 3.2, Bean Validation 4.0）
Web 容器: Tomcat 11.0 / Jetty 12.1（Undertow 暂不支持）
```

**关键迁移步骤**：

```java
// 1. javax.* → jakarta.* 包名迁移
// javax.persistence → jakarta.persistence
// javax.servlet → jakarta.servlet
// javax.validation → jakarta.validation

// 2. 检查废弃 API 使用
// Spring Boot 4.0 中 @Deprecated 的 API 在 4.1 中已移除

// 3. 虚拟线程适配 — 调低连接池大小
spring:
  threads:
    virtual:
      enabled: true  # 4.1 默认值
  datasource:
    hikari:
      maximum-pool-size: 10  # 虚拟线程下建议从 50 调低到 10-20
```

#### 三、虚拟线程 + LazyConnection 原理

**问题背景**：虚拟线程阻塞时不占 OS 线程，但传统连接池的设计假设是"一个线程持有一个连接"。当虚拟线程在等待数据库响应时被挂起，连接池中的连接仍然被占用，导致连接池快速耗尽。

**LazyConnection 解决方案**：

```
传统模式：
  请求 → 获取连接 → 执行 SQL → 返回结果 → 释放连接
         ↑ 连接被占用整个请求周期

LazyConnection 模式：
  请求 → 获取代理连接（不真正获取） → 执行 SQL 时 → 真正获取连接
         ↑ 仅在真正执行 SQL 时才占用连接
```

```java
// Spring Boot 4.1 自动配置
@Configuration
@ConditionalOnVirtualThread  // 虚拟线程启用时自动生效
public class LazyConnectionConfig {
    @Bean
    public DataSource lazyConnectionDataSource(DataSource target) {
        return new LazyConnectionDataSourceProxy(target);
        // 仅在 Statement.execute() 时才真正获取连接
    }
}
```

**性能对比**（社区实测数据）：

| 配置 | 吞吐量（QPS） | 连接池使用率 | 平均延迟 |
|------|-------------|-------------|---------|
| Spring Boot 3.x + 物理线程 | 1,200 | 85% | 45ms |
| Spring Boot 4.0 + 虚拟线程 | 3,500 | 100%（瓶颈） | 38ms |
| Spring Boot 4.1 + 虚拟线程 + LazyConnection | **5,800** | **40%** | **22ms** |

#### 四、面试追问点

1. **为什么 Spring Boot 4.1 要求 Java 25？** → 虚拟线程 2.0 的 pinned 问题大幅减少 + Valhalla 值类型的内存收益
2. **虚拟线程下连接池该设多大？** → 传统 N+1 公式失效，建议从 `maximumPoolSize=10` 开始压测调整
3. **Undertow 为什么被移除？** → 未适配 Servlet 6.1 规范

## 题目 4：[全栈/框架选型] FastAPI 与 Spring Boot 在生产环境中实测 6 个月后，结论是什么？请从性能、开发效率、团队协作、运维成本等维度进行对比分析

**难度**：⭐⭐⭐
**考点来源**：2026-06-27 早间&午间报告 — "FastAPI 与 Spring Boot 生产环境实测对比热议，6 个月真流量对碰"
**相关岗位**：Java后端 / Python后端 / 全栈 / 技术负责人

### 📖 参考答案

#### 一、实验背景

2025-2026 年，某团队针对同一个电商 REST API 服务，分别用 FastAPI 和 Spring Boot 各写一套，上线运行 6 个月，真流量对碰。**最终 Spring Boot 胜出**，但原因与大多数人想的不一样。

#### 二、多维度对比

| 维度 | FastAPI | Spring Boot | 胜出方 |
|------|---------|-------------|--------|
| **开发效率（MVP 阶段）** | ⭐⭐⭐⭐⭐ 类型注解自动生成文档，热重载秒级生效 | ⭐⭐⭐ 启动慢，编译耗时 | **FastAPI** |
| **性能（纯 API 响应）** | ⭐⭐⭐⭐ 异步原生，I/O 密集型场景出色 | ⭐⭐⭐⭐ 虚拟线程 2.0 加持后持平 | **持平** |
| **复杂业务逻辑** | ⭐⭐⭐ 类型系统弱，大型项目易失控 | ⭐⭐⭐⭐⭐ 强类型 + 编译期检查 | **Spring Boot** |
| **事务管理** | ⭐⭐⭐ 需手动管理 | ⭐⭐⭐⭐⭐ @Transactional 声明式事务 | **Spring Boot** |
| **团队协作** | ⭐⭐⭐ 缺乏统一规范，多人协作易混乱 | ⭐⭐⭐⭐⭐ 约定优于配置，规范统一 | **Spring Boot** |
| **生态成熟度** | ⭐⭐⭐ 依赖第三方库 | ⭐⭐⭐⭐⭐ 全栈生态（Security/Data/Cloud） | **Spring Boot** |
| **运维监控** | ⭐⭐⭐ 需额外集成 | ⭐⭐⭐⭐⭐ Actuator + Micrometer 原生 | **Spring Boot** |
| **AI 生态集成** | ⭐⭐⭐⭐⭐ Python 原生调用 PyTorch/TF | ⭐⭐⭐⭐ Spring AI 2.0 追赶中 | **FastAPI** |
| **长期维护成本** | ⭐⭐⭐ 随代码量增长维护成本上升快 | ⭐⭐⭐⭐⭐ 结构清晰，维护成本线性增长 | **Spring Boot** |

#### 三、核心结论

**Spring Boot 胜出的三个关键原因**：

1. **复杂业务的事务管理**：电商订单涉及库存扣减、支付、物流等多个数据源的事务一致性，Spring 的声明式事务 + 分布式事务（Seata）支持远优于 FastAPI 的手动管理方案。

2. **团队协作的规范约束**：6 个月后，FastAPI 版本出现了"同一个接口三种写法"的问题（有人用 sync、有人用 async、有人混用），而 Spring Boot 的约定优于配置让代码风格高度统一。

3. **长期维护的可控性**：Spring Boot 的依赖管理（BOM）、版本升级、安全补丁更新都有成熟的工具链支持，而 FastAPI 项目在迭代 3 个月后依赖冲突开始频繁出现。

**FastAPI 的适用场景**：
- 原型快速验证（MVP）
- 中小型 API 服务（< 50 个接口）
- AI/ML 模型服务（Python 生态优势）
- 个人项目或小团队（< 5 人）

**Spring Boot 的适用场景**：
- 复杂业务系统（订单、支付、库存）
- 大型团队协作（> 10 人）
- 长期维护的企业级项目
- 需要严格事务保证的场景

#### 四、2026 年的新变化

Spring AI 2.0 的发布正在缩小 Java 在 AI 生态上的差距。通过 Spring AI + MCP 协议，Java 后端可以无缝调用大模型能力，而不再需要额外搭建 Python 服务层。

## 题目 5：[AI/微服务] 请详细解释 AI Agent 工程中的三层结构：Tool Calling、MCP 协议和 Agent 分别是什么？它们之间的关系和分工是怎样的？

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-27 早间&午间报告 — "大厂更偏好大模型研发+Agent开发+工程化部署复合型人才" + "AI Agent 面试风向标"
**相关岗位**：AI应用开发 / Java后端（AI方向） / 全栈

### 📖 参考答案

#### 一、三层结构的直观理解

用"三层楼"的比喻来理解：

| 层级 | 角色 | 一句话解释 | 类比 |
|------|------|-----------|------|
| **Agent（智能体）** | 大脑 + 执行者 | 自主思考、规划、执行、反思 | 项目经理 |
| **MCP（协议层）** | 标准化接口 | 统一工具接入规范，即插即用 | USB 接口标准 |
| **Tool Calling（工具调用）** | 原子能力 | 让 AI 能调用外部函数获取信息或执行操作 | 具体工具 |

#### 二、第一层：Tool Calling（工具调用）

**定义**：大模型在生成回复时，能够调用预定义的函数/工具来获取实时信息或执行操作。

**工作流程**：

```
用户："北京今天天气怎么样？"
    │
    ▼
LLM 分析意图 → 判断需要调用 getWeather 工具
    │
    ▼
生成工具调用请求：getWeather(city="北京")
    │
    ▼
应用层执行工具 → 返回 {"temperature": 28, "condition": "晴"}
    │
    ▼
LLM 将结果组织成自然语言回复
```

```json
// OpenAI 格式的 Tool Calling
{
  "tool_calls": [{
    "id": "call_xxx",
    "type": "function",
    "function": {
      "name": "get_weather",
      "arguments": "{\"city\": \"北京\"}"
    }
  }]
}
```

**核心价值**：让 LLM 从"只能说话"进化到"能做事"。

#### 三、第二层：MCP 协议（标准化层）

**解决的问题**：不同模型（OpenAI/Claude/DeepSeek）和不同工具提供方各有各的接口规范，开发者需要为每个组合写适配代码。

**MCP 的标准化方案**：

```
传统模式（碎片化）：
  OpenAI 工具规范 → 天气 API（自定义）
  Claude 工具规范 → 天气 API（重写适配）
  DeepSeek 工具规范 → 天气 API（再重写）

MCP 模式（标准化）：
  MCP 统一协议 → 天气 MCP Server（写一次）
    ├── OpenAI Client → 自动适配
    ├── Claude Client → 自动适配
    └── DeepSeek Client → 自动适配
```

**MCP 的三类能力**：

| 能力 | 说明 | 类比 |
|------|------|------|
| **Tools** | 可执行的操作函数 | 遥控器按钮 |
| **Resources** | 可供读取的结构化数据 | 参考书 |
| **Prompts** | 预定义的提示模板 | 对话模板 |

#### 四、第三层：Agent（智能体）

**定义**：Agent = LLM + 规划能力 + 工具使用 + 记忆系统，能够自主完成复杂任务。

**Agentic Loop（智能体循环）**：

```
┌─────────────────────────────────────────────────┐
│                 Agentic Loop                      │
│                                                   │
│  ① 感知（Perceive）                                │
│     └─ 接收用户输入 + 获取上下文 + 读取记忆          │
│                                                   │
│  ② 思考（Think）                                   │
│     └─ ReAct 推理：分析当前状态，决定下一步          │
│        Thought: 用户想查天气，我需要调用工具          │
│                                                   │
│  ③ 行动（Act）                                     │
│     └─ 调用工具 / 查询知识库 / 生成回复              │
│        Action: getWeather(city="北京")             │
│                                                   │
│  ④ 观察（Observe）                                  │
│     └─ 获取工具执行结果                              │
│        Observation: {"temperature": 28}            │
│                                                   │
│  ⑤ 循环/结束                                       │
│     └─ 如果任务未完成 → 回到②                       │
│     └─ 如果任务完成 → 生成最终回复                    │
│                                                   │
└─────────────────────────────────────────────────┘
```

**三种推理框架对比**：

| 框架 | 思路 | 适用场景 | 缺点 |
|------|------|---------|------|
| **ReAct** | 思考→行动→观察 循环 | 大多数通用场景 | 可能陷入死循环 |
| **Plan-and-Execute** | 先制定完整计划，再逐步执行 | 复杂多步骤任务 | 计划可能偏离实际 |
| **ToT（思维树）** | 同时探索多条推理路径 | 需要创造性解决的问题 | 成本高 |

#### 五、三层关系总结

```
Agent（大脑）
  │  制定计划、调用策略、异常处理
  ▼
MCP（协议总线）
  │  标准化工具发现、调用、数据传输
  ▼
Tool Calling（执行层）
  │  具体执行：查天气、读数据库、发邮件
```

**面试常问追问**：
1. **Agent 死循环怎么处理？** → 最大迭代次数（通常 10-15 次）+ 超时控制 + 人工干预回调
2. **MCP 和 Function Calling 能互相替代吗？** → 不能。Function Calling 是模型能力，MCP 是协议标准，两者是不同层级的互补关系
3. **多 Agent 如何协作？** → 通过 MCP 协议互相发现和调用，或通过 Orchestrator Agent 统一调度
