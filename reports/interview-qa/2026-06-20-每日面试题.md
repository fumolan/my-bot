**一、JVM 运行时数据区域——五大组成部分**

Java 虚拟机在执行 Java 程序时会把它管理的内存划分为若干个不同的数据区域，各有各的职责。

```
JVM 运行时数据区域全景图（JDK 8+）：

  ┌──────────────────────────────────────────────────┐
  │                   JVM 内存结构                     │
  │                                                   │
  │  ┌──────────┐  ┌──────────┐  ┌──────────┐        │
  │  │ 程序计数器 │  │ 虚拟机栈  │  │本地方法栈 │        │
  │  │ (线程私有) │  │ (线程私有) │  │ (线程私有) │        │
  │  │ 极小内存   │  │ StackFrame│  │  Native   │        │
  │  └──────────┘  └──────────┘  └──────────┘        │
  │                                                   │
  │  ┌──────────────────────────────────────────┐     │
  │  │               堆 (Heap)                   │     │
  │  │  ★ 线程共享，GC 主战场 ★                   │     │
  │  │  ┌─────────────────────────────────┐     │     │
  │  │  │  新生代 (Young Gen)             │     │     │
  │  │  │  ┌──────┬──────┬──────┐        │     │     │
  │  │  │  │ Eden │  S0  │  S1  │        │     │     │
  │  │  │  │ 8/10 │ 1/10 │ 1/10 │        │     │     │
  │  │  │  └──────┴──────┴──────┘        │     │     │
  │  │  └─────────────────────────────────┘     │     │
  │  │  ┌─────────────────────────────────┐     │     │
  │  │  │  老年代 (Old Gen)               │     │     │
  │  │  └─────────────────────────────────┘     │     │
  │  └──────────────────────────────────────────┘     │
  │                                                   │
  │  ┌──────────────────────────────────────────┐     │
  │  │         元空间 (Metaspace)                │     │
  │  │  ★ 线程共享，本地内存，替代永久代 ★        │     │
  │  │  - 类元数据/方法字节码/运行时常量池          │     │
  │  └──────────────────────────────────────────┘     │
  │                                                   │
  │  ┌──────────────────────────────────────────┐     │
  │  │  直接内存 (Direct Memory)                 │     │
  │  │  - NIO 使用                               │     │
  │  └──────────────────────────────────────────┘     │
  └──────────────────────────────────────────────────┘
```

```
五大区域详解：

  ① 程序计数器（Program Counter Register）：
     - 线程私有，当前线程所执行的字节码行号指示器
     - 分支、循环、跳转、异常处理、线程恢复都依赖它
     - 唯一不会抛出 OutOfMemoryError 的区域
     - 执行 native 方法时值为 undefined

  ② 虚拟机栈（JVM Stack）：
     - 线程私有，每个方法调用创建一个栈帧
     - 栈帧包含：局部变量表、操作数栈、动态链接、返回地址
     - 异常：StackOverflowError（栈深度超限）/ OutOfMemoryError（栈扩展失败）
     - 生命周期与线程相同

  ③ 本地方法栈（Native Method Stack）：
     - 线程私有，为 Native 方法服务
     - HotSpot 中将虚拟机栈和本地方法栈合二为一

  ④ 堆（Heap）：
     - 线程共享，存放对象实例和数组
     - GC 管理的主要区域
     - 分代：新生代（Eden + S0 + S1）+ 老年代
     - 异常：OutOfMemoryError: Java heap space

  ⑤ 方法区 / 元空间（Method Area / Metaspace）：
     - 线程共享，存储类元数据、方法字节码、运行时常量池
     - JDK 7 及之前：永久代（PermGen，JVM 内存内）
     - JDK 8+：元空间（Metaspace，本地内存），OOM 概率更低
     - 为什么替换？永久代大小固定、GC 复杂度高、与 JRockit 合并后无此概念
```

**二、堆空间的分代结构——对象的一生**

```
对象从出生到消亡的完整旅程：

  ① 对象优先在 Eden 区分配
     ↓
  ② Eden 满了 → 触发 Minor GC (Young GC)
     ↓ 存活对象
  ③ 复制到 Survivor 区（S0 或 S1），年龄 = 1
     ↓
  ④ 每次 Minor GC 存活 → 年龄 +1，在 S0 和 S1 之间来回拷贝
     ↓
  ⑤ 年龄达到阈值（默认 15）→ 晋升到老年代（Promotion）
     ↓
  ⑥ 老年代满了 → 触发 Major GC / Full GC
     ↓
  ⑦ 对象被回收或继续存活

  注意：阈值不一定到 15！存在动态年龄判断：
  - HotSpot 遍历所有年龄对象，按年龄从小到大累加其大小
  - 当累加到某个年龄时，所累加的大小超过 Survivor 区的 50%
  - 取这个年龄和 MaxTenuringThreshold 中更小的值作为晋升阈值
  - 这就是为什么实际项目中对象往往在 6-8 岁就晋升了
```

```
特殊情况——直接进入老年代：

  ① 大对象：需要大量连续内存的对象（如大数组）
     G1 中根据 -XX:G1HeapRegionSize 和 G1MixedGCLiveThresholdPercent 决定

  ② 空间分配担保失败：
     Survivor 区放不下 → 直接进入老年代
```

**三、可达性分析算法——判断对象生死**

```
主流 JVM 不使用引用计数法（无法解决循环引用），而是使用可达性分析算法。

  可达性分析的核心思想：
  从 GC Roots 出发，沿着引用链向下搜索，不可达的对象标记为可回收。

  GC Roots 包括：
  ① 虚拟机栈（栈帧中局部变量表）中引用的对象
  ② 本地方法栈中 JNI 引用的对象
  ③ 方法区中类静态属性引用的对象
  ④ 方法区中常量引用的对象
  ⑤ 所有被同步锁（synchronized）持有的对象
  ⑥ JVM 内部的引用（Class 对象、异常对象、ClassLoader 等）

  两次标记过程：
  第一次标记：可达性分析发现不可达 → 筛选是否要执行 finalize()
  第二次标记：放在 F-Queue 中，Finalizer 线程执行 finalize()
  → 如果 finalize() 中重新与 GC Roots 建立关联，则"复活"
  → 否则正式回收
  ⚠️ JDK 9+ 已弃用 finalize()，忘掉它的存在！
```

**四、G1 垃圾回收器——2026 年服务端主流选择**

```
G1（Garbage-First）从 JDK 9 开始成为默认垃圾回收器，2026 年已是绝对主流。

  G1 的核心设计：Region 分区

  传统分代回收器：一整块 Eden + 一整块 Survivor + 一整块 Old
  G1：堆被划分为多个大小相等的 Region（默认 2048 个）

  ┌────────────────────────────────────────────────────┐
  │  ┌──────┬──────┬──────┬──────┬──────┬──────┐       │
  │  │  E   │  E   │  S   │  O   │  H   │  O   │       │
  │  ├──────┼──────┼──────┼──────┼──────┼──────┤       │
  │  │  E   │  O   │  O   │  S   │  E   │  O   │       │
  │  ├──────┼──────┼──────┼──────┼──────┼──────┤       │
  │  │  O   │  E   │  F   │  E   │  O   │  O   │       │
  │  └──────┴──────┴──────┴──────┴──────┴──────┘       │
  │   E=Eden  S=Survivor  O=Old  H=Humongous  F=Free   │
  └────────────────────────────────────────────────────┘

  G1 关键概念：

  ① Region：堆内存的最小管理单元，大小通过 -XX:G1HeapRegionSize（1-32MB）
  ② CSet（Collection Set）：本次 GC 要回收的 Region 集合
  ③ RSet（Remembered Set）：记录"谁引用了我"的跨 Region 引用
  ④ Humongous Object：超过 Region 大小 50% 的大对象，独占连续 Region
  ⑤ SATB（Snapshot-At-The-Beginning）：并发标记阶段的一致性快照

  G1 的 GC 类型：

  ① Young GC：
     - 只回收 Eden + Survivor Region
     - 存活对象复制到新的 Survivor Region 或晋升到 Old Region
     - STW（Stop The World），但时间很短

  ② Mixed GC：
     - 回收所有 Young Region + 部分 Old Region（垃圾最多的）
     - 这就是 "Garbage First" 的由来——优先回收垃圾最多的 Region
     - 通过 -XX:InitiatingHeapOccupancyPercent（默认 45%）触发
     - 控制参数：-XX:G1MixedGCCountTarget（Mixed GC 次数）

  ③ Full GC：
     - 回收整个堆，当 Mixed GC 跟不上分配速度时触发
     - 单线程，STW 时间长，严重影响性能
     - 调优目标：避免 Full GC！
```

```
G1 常用调优参数：

  ┌────────────────────────────────┬──────────────────────────────────┐
  │ 参数                            │ 含义                             │
  ├────────────────────────────────┼──────────────────────────────────┤
  │ -XX:+UseG1GC                   │ 启用 G1 垃圾回收器（JDK 9+ 默认）│
  │ -XX:MaxGCPauseMillis=200       │ 期望的最大 GC 暂停时间（毫秒）     │
  │ -XX:G1HeapRegionSize=4m        │ Region 大小（1-32MB，2 的幂）     │
  │ -XX:InitiatingHeapOccupancyPercent=45 │ 触发 Mixed GC 的堆占用阈值 │
  │ -XX:G1NewSizePercent=5         │ 新生代最小占比（默认 5%）          │
  │ -XX:G1MaxNewSizePercent=60     │ 新生代最大占比（默认 60%）         │
  │ -XX:G1MixedGCCountTarget=8    │ Mixed GC 的预期次数               │
  │ -XX:ParallelGCThreads=n       │ 并行 GC 线程数                    │
  │ -XX:ConcGCThreads=n           │ 并发 GC 线程数                    │
  └────────────────────────────────┴──────────────────────────────────┘

  核心调优思路：
  ① 设置 MaxGCPauseMillis（如 200ms）→ G1 自动调整新生代大小
  ② 监控 Mixed GC 和 Full GC 的频率 → 调 IHOP 和 Region 大小
  ③ 大对象（Humongous）是 G1 的克星：避免频繁创建超大对象
  ④ 不要随便调：G1 的默认参数已经很好，大多数场景不需要动
```

### 💡 延伸思考

1. **G1 和 CMS 的核心区别？为什么 CMS 被废弃了？** — CMS 是"标记-清除"算法，会产生内存碎片，碎片严重时触发 Full GC（Serial Old 单线程）导致长停顿。而 G1 是"标记-整理"算法，整体上看避免了碎片问题。CMS 在 JDK 14 被正式移除，原因：碎片化严重、并发模式失败导致退化为 Serial Old、对浮动垃圾处理不够好。

2. **ZGC 是什么？和 G1 的区别？** — ZGC（JDK 11 引入，JDK 15 生产可用）主打超低延迟，GC 暂停时间不超过 1ms，支持 TB 级堆。G1 的暂停目标是 200ms 级别，ZGC 是 10ms 以下。ZGC 使用着色指针（Colored Pointers）和读屏障技术，并发处理几乎所有 GC 阶段。如果对延迟要求极高（如金融交易），选 ZGC；一般场景 G1 够用。

**一、Spring 事务管理基础——AOP 代理的秘密**

Spring 事务本质上是 AOP 的典型应用。@Transactional 注解的方法会被 Spring 生成代理对象，在方法前后织入事务管理逻辑（开启事务 → 执行方法 → 提交/回滚）。

```
声明式事务的执行流程：

  调用方 ──→ 代理对象（增强）──→ 目标对象（原始方法）
             │
             ① 开启事务（PlatformTransactionManager.getTransaction）
             ② 执行目标方法
             ③ 提交事务（commit）或回滚（rollback）

  关键：事务传播行为决定了"当前有事务时怎么办"和"当前没有事务时怎么办"
```

**二、7 种事务传播行为——面试必考的核心**

Spring 定义了 7 种传播行为，其中 REQUIRED、REQUIRES_NEW、NESTED 是最核心的 3 种。

```
传播行为全览：

  ┌─────────────────────┬──────────────────────────────────────────┐
  │     传播行为          │              行为描述                    │
  ├─────────────────────┼──────────────────────────────────────────┤
  │ REQUIRED（默认）     │ 有事务则加入，无事务则创建新事务            │
  │                     │ 最常用！90% 场景用这个                     │
  ├─────────────────────┼──────────────────────────────────────────┤
  │ REQUIRES_NEW        │ 无论有无事务，都创建新事务                 │
  │                     │ 当前事务挂起，新事务独立提交/回滚           │
  ├─────────────────────┼──────────────────────────────────────────┤
  │ NESTED              │ 有事务则创建嵌套事务（Savepoint 机制）     │
  │                     │ 无事务则同 REQUIRED                       │
  │                     │ 外层回滚 → 内层一定回滚；内层回滚不影响外层 │
  ├─────────────────────┼──────────────────────────────────────────┤
  │ SUPPORTS            │ 有事务则加入，无事务则以非事务方式运行       │
  │                     │ 查询方法常用                              │
  ├─────────────────────┼──────────────────────────────────────────┤
  │ NOT_SUPPORTED       │ 以非事务方式运行，有事务则挂起              │
  │                     │ 极少使用                                  │
  ├─────────────────────┼──────────────────────────────────────────┤
  │ MANDATORY           │ 必须有事务，否则抛异常                     │
  │                     │ 强制调用方必须在事务中                      │
  ├─────────────────────┼──────────────────────────────────────────┤
  │ NEVER               │ 必须没有事务，否则抛异常                    │
  │                     │ 极少使用                                  │
  └─────────────────────┴──────────────────────────────────────────┘
```

### 核心三种传播行为深入对比

```
REQUIRED vs REQUIRES_NEW vs NESTED：

  场景：外层方法 A 调用内层方法 B

  ┌──────────────────────────────────────────────────────────────┐
  │  REQUIRED（默认）：                                          │
  │                                                              │
  │  A() {                         B() {                        │
  │    // 开启事务 T1                // 加入事务 T1               │
  │    doSomething();    ────→       doSomething();              │
  │    B();                          // 如果 B 抛异常              │
  │    // 继续执行                   // → T1 回滚 → A 也回滚      │
  │  }                             }                             │
  │                                                              │
  │  特点：A 和 B 是同一个事务，同生共死                           │
  ├──────────────────────────────────────────────────────────────┤
  │  REQUIRES_NEW：                                              │
  │                                                              │
  │  A() {                         B() {                        │
  │    // 开启事务 T1                // 挂起 T1，创建新事务 T2     │
  │    doSomething();    ────→       doSomething();              │
  │    B();                          // B 提交/回滚 T2            │
  │    // T1 继续执行                // 恢复 T1                   │
  │  }                             }                             │
  │                                                              │
  │  特点：A 和 B 是两个独立的事务，互不影响                         │
  │  B 抛异常回滚 → 不影响 A；A 抛异常回滚 → 不影响已提交的 B       │
  ├──────────────────────────────────────────────────────────────┤
  │  NESTED（嵌套事务）：                                         │
  │                                                              │
  │  A() {                         B() {                        │
  │    // 开启事务 T1                // 创建 Savepoint SP1        │
  │    doSomething();    ────→       doSomething();              │
  │    B();                          // B 抛异常                  │
  │    // 继续执行                   // → 回滚到 SP1（B 回滚）     │
  │  }                             }                             │
  │                                                              │
  │  特点：B 回滚不影响 A，但 A 回滚 → B 一定回滚（整体回滚）       │
  │  注意：NESTED 需要 JDBC 3.0 Savepoint 支持                   │
  │        且只在 JpaTransactionManager 中生效，                  │
  │        DataSourceTransactionManager 不原生支持 NESTED        │
  └──────────────────────────────────────────────────────────────┘
```

```java
// 实战代码示例
@Service
public class OrderService {
    
    @Autowired
    private OrderMapper orderMapper;
    @Autowired
    private LogService logService;
    
    // ① REQUIRED（默认）：创建订单 + 记日志，同生共死
    @Transactional
    public void createOrder(Order order) {
        orderMapper.insert(order);       // 主业务
        logService.recordLog(order);     // 日志（也在同一个事务中）
        // 如果 recordLog 抛异常 → 订单也不会保存
    }
    
    // ② REQUIRES_NEW：主业务失败不影响日志
    @Transactional
    public void createOrderWithLog(Order order) {
        try {
            orderMapper.insert(order);
        } catch (Exception e) {
            // 订单创建失败，但日志必须记录
            logService.recordErrorLog(order, e);  // REQUIRES_NEW
        }
    }
}

@Service
public class LogService {
    
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void recordErrorLog(Order order, Exception e) {
        // 独立事务，即使调用方事务回滚，这个日志也会保存
        errorLogMapper.insert(new ErrorLog(order.getId(), e.getMessage()));
    }
}
```

**三、4 种事务隔离级别——与 MySQL 的对应关系**

```
隔离级别从低到高：

  ┌──────────────────────┬──────────────────────────────┬──────────────────┐
  │      隔离级别         │          解决的问题           │    MySQL 默认     │
  ├──────────────────────┼──────────────────────────────┼──────────────────┤
  │ READ_UNCOMMITTED     │ 几乎不隔离                    │ ❌ 不使用         │
  │ (读未提交)           │ 脏读 ✓ 不可重复读 ✓ 幻读 ✓    │                  │
  ├──────────────────────┼──────────────────────────────┼──────────────────┤
  │ READ_COMMITTED       │ 解决脏读                      │ ❌ Oracle默认    │
  │ (读已提交)           │ 不可重复读 ✓ 幻读 ✓           │                  │
  ├──────────────────────┼──────────────────────────────┼──────────────────┤
  │ REPEATABLE_READ      │ 解决脏读+不可重复读            │ ✅ MySQL默认     │
  │ (可重复读)           │ 幻读 ✓（InnoDB 用间隙锁解决）   │                  │
  ├──────────────────────┼──────────────────────────────┼──────────────────┤
  │ SERIALIZABLE         │ 全部解决（串行化）             │ ❌ 性能极差      │
  │ (串行化)             │ 性能最差                      │                  │
  └──────────────────────┴──────────────────────────────┴──────────────────┘

  三个并发问题：
  ① 脏读：读到其他事务未提交的数据
  ② 不可重复读：同一事务内两次读取结果不同（其他事务修改并提交了）
  ③ 幻读：同一事务内两次查询结果集不同（其他事务插入/删除了数据）

  Spring 事务隔离级别设置：
  @Transactional(isolation = Isolation.REPEATABLE_READ)
  // 默认是 Isolation.DEFAULT，使用数据库默认隔离级别
```

**四、@Transactional 失效的 6 大场景——面试高频追问**

这是面试中"Spring 事务"话题下追问最多的问题。

```
失效场景 1：自调用（类内部方法调用）——最常见！

  @Service
  public class UserService {
      
      public void methodA() {
          // 直接调用 this.methodB()，没有经过代理！
          this.methodB();  // ❌ 事务不生效！
      }
      
      @Transactional
      public void methodB() {
          // 事务不会生效，因为调用绕过了 AOP 代理
      }
  }

  原因：Spring AOP 基于代理，只有外部通过代理对象调用才会触发事务。
        this.methodB() 是目标对象内部的直接调用，绕过了代理。
  
  解决方案：
  ① 注入自己：@Autowired private UserService self; self.methodB();
  ② 将 methodB 抽到另一个 Service 中
  ③ 使用 AopContext.currentProxy()（需开启 exposeProxy=true）

失效场景 2：方法不是 public 的

  @Transactional
  private void internalMethod() {  // ❌ private 方法事务不生效！
      // ...
  }
  
  @Transactional
  protected void protectedMethod() {  // ❌ 默认 JDK 代理也不生效
      // ...
  }

  原因：Spring 默认使用 JDK 动态代理（基于接口）或 CGLIB 代理（基于继承）。
        private 方法无法被代理；protected 方法在 JDK 代理下不生效。
  
  解决方案：方法必须是 public 的，或使用 AspectJ 编译时织入。

失效场景 3：异常被 try-catch 捕获了

  @Transactional
  public void createOrder() {
      try {
          orderMapper.insert(order);
          int i = 1 / 0;  // 抛出 ArithmeticException
      } catch (Exception e) {
          log.error("error", e);
          // ❌ 异常被捕获，Spring 感知不到，事务正常提交！
      }
  }

  原因：Spring 事务通过捕获 RuntimeException 和 Error 来触发回滚。
        如果业务代码捕获了异常且没有重新抛出，Spring 感知不到。
  
  解决方案：
  ① 在 catch 块中重新抛出 RuntimeException
  ② 手动回滚：TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
  ③ 指定回滚异常：@Transactional(rollbackFor = Exception.class)

失效场景 4：数据库引擎不支持事务

  CREATE TABLE test (...) ENGINE=MyISAM;  // ❌ MyISAM 不支持事务！
  
  无论怎么配 @Transactional，MyISAM 引擎下都没有事务效果。

失效场景 5：多线程调用

  @Transactional
  public void mainMethod() {
      new Thread(() -> {
          orderMapper.insert(order);  // ❌ 不在当前事务中！
      }).start();
  }

  原因：Spring 事务通过 ThreadLocal 绑定数据库连接，新线程无法获取当前事务。

失效场景 6：@Transactional 注解在非 Spring 管理的类上

  // 如果类没有被 Spring 管理（没有 @Service/@Component 等）
  // @Transactional 不会生效
```

### 💡 延伸思考

1. **为什么 REQUIRES_NEW 和 NESTED 看起来很像，实际有什么本质区别？** — 最大区别在于：REQUIRES_NEW 创建的是两个完全独立的物理事务，各自持有不同的数据库连接，各自提交。NESTED 使用的是同一个数据库连接的 Savepoint 机制，外层事务回滚 → 内层事务一定回滚。而 REQUIRES_NEW 的外层回滚不会影响内层已提交的事务。选择：如果内层操作必须独立持久化（如写审计日志），用 REQUIRES_NEW；如果只是"内层失败不影响外层"，用 NESTED。

2. **Spring 事务的 timeout 是做什么用的？** — @Transactional(timeout = 5) 表示事务最长执行 5 秒，超时后自动回滚。这个 timeout 是通过数据库连接的超时机制实现的，不是 Spring 层面的定时器。注意：timeout 只在新建事务时生效（REQUIRED 无事务时、REQUIRES_NEW 时），加入已有事务时 timeout 无效。

**一、索引为什么失效？——理解 B+ 树的有序性**

在分析索引失效之前，先理解一个核心原理：**B+ 树索引是按照索引列的值有序存储的**。所有索引失效的根本原因，都是"破坏了索引的有序性"或"让 MySQL 无法在索引树上定位数据"。

```
InnoDB 索引结构回顾：

  聚簇索引（主键索引）：
  叶子节点存储完整数据行

  二级索引（普通索引）：
  叶子节点存储主键值
  查询流程：二级索引找主键 → 聚簇索引回表找到数据

  索引失效的排查利器：EXPLAIN
  - type = ALL：全表扫描，索引失效！（最明显的信号）
  - type = index：索引全扫描，也说明索引没被有效利用
  - key = NULL：没有使用任何索引
```

**二、6 种索引失效场景详解**

### 场景 1：左模糊/左右模糊匹配

```sql
-- ❌ 索引失效！type = ALL
SELECT * FROM user WHERE name LIKE '%林';

-- ❌ 索引失效！type = ALL
SELECT * FROM user WHERE name LIKE '%林%';

-- ✅ 索引有效！type = range
SELECT * FROM user WHERE name LIKE '林%';
```

```
为什么 LIKE '%林' 不走索引？

  B+ 树中 name 字段按字典序排列：
  陈 → 林 → 刘 → 王 → 张 → 周

  如果查询 LIKE '林%'：
  从"林"字开始扫描，直到不再以"林"开头 → 可以确定范围

  如果查询 LIKE '%林'：
  后缀是"林"的可能是"陈林"、"张林"、"周林"……
  在 B+ 树中完全分散，无法确定扫描范围
  → 只能全表扫描
```

### 场景 2：索引列使用函数

```sql
-- ❌ 索引失效！type = ALL
SELECT * FROM user WHERE LENGTH(name) = 6;

-- ❌ 索引失效！type = ALL
SELECT * FROM orders WHERE DATE(create_time) = '2026-06-20';

-- ✅ 索引有效！type = range
SELECT * FROM orders 
WHERE create_time >= '2026-06-20 00:00:00' 
  AND create_time < '2026-06-21 00:00:00';
```

```
为什么对索引列使用函数会导致索引失效？

  索引保存的是 name 的原始值，而不是 LENGTH(name) 计算后的值。
  MySQL 无法根据 LENGTH(name)=6 在索引树上定位数据，
  只能全表扫描后对每一行计算 LENGTH。

  解决方案（MySQL 8.0+）：
  -- 创建函数索引
  CREATE INDEX idx_name_length ON user((LENGTH(name)));
  -- 之后 LENGTH(name) = 6 就可以走索引了
```

### 场景 3：索引列进行表达式计算

```sql
-- ❌ 索引失效！type = ALL
SELECT * FROM user WHERE id + 1 = 10;

-- ✅ 索引有效！type = const
SELECT * FROM user WHERE id = 10 - 1;
```

```
原因同场景 2：索引保存的是 id 的原始值，不是 id + 1 的值。
MySQL 没有将 id + 1 = 10 优化为 id = 9，所以只能全表扫描。

解决方案：把表达式计算从索引列移到常量一侧。
```

### 场景 4：隐式类型转换——最隐蔽的坑

```sql
-- 假设 phone 字段是 VARCHAR 类型，有索引

-- ❌ 索引失效！type = ALL
SELECT * FROM user WHERE phone = 13800138000;  -- 数字！

-- ✅ 索引有效！type = ref
SELECT * FROM user WHERE phone = '13800138000';  -- 字符串！
```

```
为什么 phone = 13800138000（数字）会导致索引失效？

  MySQL 类型转换规则：字符串和数字比较时，会将字符串转为数字！

  所以 phone = 13800138000 实际执行的是：
  CAST(phone AS UNSIGNED) = 13800138000

  这相当于对索引列使用了函数！→ 索引失效！

  验证规则：
  SELECT "10" > 9;  -- 结果 1，说明 "10" 被转为数字 10

  反过来：
  -- id 是 INT 类型，有索引
  SELECT * FROM user WHERE id = '10';  -- ✅ 不会失效！
  -- 相当于 CAST('10' AS UNSIGNED) = id → 函数在常量侧，索引 OK
```

### 场景 5：联合索引不遵循最左匹配原则

```sql
-- 假设有联合索引 idx_abc(a, b, c)

-- ✅ 走索引
SELECT * FROM t WHERE a = 1;
SELECT * FROM t WHERE a = 1 AND b = 2;
SELECT * FROM t WHERE a = 1 AND b = 2 AND c = 3;
SELECT * FROM t WHERE b = 2 AND a = 1;  -- 优化器会调整顺序

-- ❌ 索引失效！（最左列 a 缺失）
SELECT * FROM t WHERE b = 2;
SELECT * FROM t WHERE c = 3;
SELECT * FROM t WHERE b = 2 AND c = 3;

-- ⚠️ 部分失效（a 走索引，c 通过 ICP 过滤）
SELECT * FROM t WHERE a = 1 AND c = 3;
-- Extra = Using index condition（索引下推）
```

```
为什么联合索引必须遵循最左匹配？

  联合索引 (a, b, c) 在 B+ 树中的排序规则：
  ① 先按 a 排序
  ② a 相同按 b 排序
  ③ b 相同按 c 排序

  如果查询条件中没有 a，就无法确定 b 或 c 在索引树中的位置范围。
  就像一本按"省→市→区"排序的电话簿，你不知道"省"就无法定位"市"。
```

### 场景 6：WHERE 子句中 OR 连接非索引列

```sql
-- 假设 id 有索引，age 没有索引

-- ❌ 索引失效！type = ALL
SELECT * FROM user WHERE id = 1 OR age = 25;

-- ✅ 解决方案：给 age 也加索引
CREATE INDEX idx_age ON user(age);
-- 之后 EXPLAIN 显示 type = index_merge（索引合并）
```

```
为什么 OR 会导致索引失效？

  只有 id 有索引，age 没有索引。
  OR 的含义是"满足任一条件即可"。
  即使 id=1 走索引查到了结果，还需要确定 age=25 的数据。
  而 age 没有索引 → 必须全表扫描 → 索引失效。

  解决方案：
  ① 给 age 加索引（变为 index_merge）
  ② 改写为 UNION：
     SELECT * FROM user WHERE id = 1
     UNION
     SELECT * FROM user WHERE age = 25;
```

**三、索引失效排查实战——EXPLAIN 分析**

```
EXPLAIN 分析索引失效的关键字段：

  ① type = ALL（全表扫描）→ 索引完全失效，必须优化！
  ② key = NULL → 没有使用任何索引
  ③ rows 很大 → 扫描了大量行
  ④ Extra = Using where → 在 Server 层过滤，没用上索引

  实例：排查一条慢 SQL

  EXPLAIN SELECT * FROM orders 
  WHERE phone = 13800138000 
    AND status = 1 
  ORDER BY create_time DESC;

  -- 输出分析：
  -- type: ALL（全表扫描！）
  -- key: NULL
  -- Extra: Using where; Using filesort

  排查步骤：
  ① type=ALL → 索引完全失效
  ② 检查 phone 字段：VARCHAR 类型，但传了数字 → 隐式类型转换！
  ③ 改：phone = '13800138000'
  ④ 检查 status 字段：没有索引
  ⑤ 检查 create_time 排序：没有索引 → filesort

  优化方案：
  ① 改 phone = '13800138000'（解决隐式转换）
  ② 创建联合索引 (phone, status, create_time)
  ③ 优化后 EXPLAIN：type=ref, key=idx_phone_status_time, Extra=Using index condition
```

### 💡 延伸思考

1. **"走了索引为什么还慢？"——索引覆盖 vs 回表开销** — 即使 EXPLAIN 显示 key 有值，如果 SELECT * 需要大量回表，查询仍然很慢。例如索引 idx_user_id 扫描了 100 万行，回表 100 万次，每次都是随机 IO。解决方案：覆盖索引（SELECT 只查需要的列，且都在索引中）、MRR 优化（主键排序后批量回表）、ICP 优化（引擎层过滤减少回表次数）。

2. **MySQL 8.0 的函数索引能解决所有"对索引使用函数"的问题吗？** — 不能。函数索引需要额外存储空间，且表达式必须精确匹配（DETERMINISTIC）。如果函数是动态的（如 NOW()），就不能创建函数索引。另外，函数索引会增加写入开销（每次 INSERT/UPDATE 都要计算函数值）。

**一、为什么需要分布式锁？——单机锁的局限**

单机环境下，synchronized / ReentrantLock 可以保证线程安全。但在分布式环境下，多个服务实例运行在不同的 JVM 中，本地锁无法跨 JVM 工作。

```
分布式锁需要解决的问题：

  ┌──────────┐     ┌──────────┐     ┌──────────┐
  │ 服务实例 A │     │ 服务实例 B │     │ 服务实例 C │
  │ JVM-1     │     │ JVM-2     │     │ JVM-3     │
  │           │     │           │     │           │
  │ synchronized  │ │ synchronized  │ │ synchronized  │
  │ (仅锁 JVM-1)  │ │ (仅锁 JVM-2)  │ │ (仅锁 JVM-3)  │
  └─────┬─────┘     └─────┬─────┘     └─────┬─────┘
        │                 │                 │
        └─────────────────┼─────────────────┘
                          │
                  ┌───────▼───────┐
                  │   共享资源     │
                  │  (DB/Redis)   │
                  └───────────────┘
  
  需要一把"跨 JVM 的锁"来保证所有实例互斥访问共享资源
```

**二、基于 Redis 的分布式锁——演进路线**

### 第一阶段：最简易的 SETNX 锁

```java
// ❌ 最简易版本——有严重问题
public boolean tryLock(String key, String value) {
    Boolean success = redisTemplate.opsForValue()
        .setIfAbsent(key, value);  // SETNX
    return Boolean.TRUE.equals(success);
}

public void unlock(String key) {
    redisTemplate.delete(key);  // 直接删除，可能误删！
}

// 问题 1：没有过期时间 → 持有锁的线程挂了 → 死锁！
// 问题 2：直接 DEL 可能误删其他客户端的锁
```

### 第二阶段：SETNX + 过期时间 + 唯一标识

```java
// ✅ 改进版：原子设置 + 过期时间 + Lua 脚本释放
public boolean tryLock(String key, String value, long expireTime) {
    // SET key value NX EX expireTime（原子操作！）
    Boolean success = redisTemplate.opsForValue()
        .setIfAbsent(key, value, expireTime, TimeUnit.SECONDS);
    return Boolean.TRUE.equals(success);
}

public void unlock(String key, String value) {
    // Lua 脚本保证原子性：先判断 value 是否是自己设的，再删除
    String script = 
        "if redis.call('get', KEYS[1]) == ARGV[1] then " +
        "   return redis.call('del', KEYS[1]) " +
        "else " +
        "   return 0 " +
        "end";
    redisTemplate.execute(
        new DefaultRedisScript<>(script, Long.class),
        Collections.singletonList(key), value);
}

// 问题：如果业务执行时间 > 锁过期时间，锁自动释放了，其他线程获取到锁
// → 并发问题！
```

### 第三阶段：Redisson + Watch Dog 自动续期

```java
// ✅ Redisson 方案——推荐！自动续期 + 可重入 + 公平锁
@Autowired
private RedissonClient redisson;

public void doBusiness() {
    RLock lock = redisson.getLock("order:lock:123");
    try {
        // ① 加锁，不指定过期时间 → Watch Dog 自动续期
        lock.lock();
        // lock.lock(10, TimeUnit.SECONDS); // 手动指定过期时间 → 不会自动续期！
        
        // ② 执行业务逻辑
        doSomething();
    } finally {
        // ③ 释放锁
        lock.unlock();
    }
}
```

```
Redisson Watch Dog 原理：

  ① 加锁成功后，启动一个后台定时任务（Watch Dog）
  ② 默认每 10 秒（internalLockLeaseTime / 3 = 30s / 3）续期一次
  ③ 续期操作：将锁的过期时间重置为 30 秒
  ④ 业务完成 → unlock() → 取消 Watch Dog 定时任务
  ⑤ 如果业务线程挂了，Watch Dog 停止 → 锁 30 秒后自动过期释放

  Lua 续期脚本：
  if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then
      redis.call('pexpire', KEYS[1], ARGV[1]);  -- 续期到 30 秒
      return 1;
  end;
  return 0;

  注意：只有不指定过期时间时，Watch Dog 才生效！
  lock.lock(10, TimeUnit.SECONDS);  // 手动指定 → 无 Watch Dog
```

**三、基于 ZooKeeper 的分布式锁——公平锁方案**

```
ZooKeeper 分布式锁基于临时顺序节点 + Watcher 机制：

  /locks（持久节点）
  ├── /lock-0000000001  ← 客户端 A 创建，序号最小，获取锁
  ├── /lock-0000000002  ← 客户端 B 创建，监听 lock-0000000001
  └── /lock-0000000003  ← 客户端 C 创建，监听 lock-0000000002

  获取锁流程：
  ① 所有客户端在 /locks 下创建临时顺序节点
  ② 判断自己是否是序号最小的节点
  ③ 是 → 获取锁成功
  ④ 否 → 在前一个节点上注册 Watcher，等待通知
  ⑤ 前一个节点释放（客户端断开/主动删除）→ Watcher 通知 → 重新判断

  释放锁：
  ① 主动删除节点
  ② 客户端会话断开（Session 超时）→ 临时节点自动删除

  优点：
  ✅ 公平锁（按创建顺序获取）
  ✅ 自动释放（客户端宕机 → Session 超时 → 临时节点删除）
  ✅ 强一致性（CP 系统，基于 ZAB 协议）
  ✅ 不需要设置过期时间（临时节点生命周期 = Session 生命周期）

  缺点：
  ❌ 性能较低（比 Redis 慢 1-2 个数量级）
  ❌ 需要维护 ZooKeeper 集群
  ❌ 羊群效应（高并发下多个 Watcher 同时触发）
```

```
├──────────────────┼──────────────────────┼──────────────────────┤

```

**五、分布式锁的四大坑——生产环境血泪教训**

```
坑 1：锁超时释放导致并发问题

  场景：线程 A 获取锁，执行业务耗时 5 秒，锁过期时间 3 秒
  → 锁在 3 秒后自动释放 → 线程 B 获取到锁
  → 线程 A 和 B 同时操作共享资源 → 并发问题！

  解决：
  ① Redisson Watch Dog 自动续期（推荐）
  ② 设置合理的过期时间（业务时间的 3-5 倍）
  ③ Fencing Token：每次获取锁时生成递增 Token，写入共享资源时校验

坑 2：主从切换导致锁丢失

  场景：Redis 主节点写入锁成功 → 返回 OK → 异步同步给从节点
  → 主节点宕机（同步未完成）→ 从节点提升为新主
  → 锁数据丢失！→ 其他客户端可以再次获取同一把锁

  解决：
  ① Redlock 算法（向多个独立 Redis 加锁，多数派成功才算获取）
  ② 对一致性要求高的场景用 ZooKeeper 或 etcd
  ③ 评估业务是否容忍极低概率的锁丢失（大多数场景可以）

坑 3：锁的误删除

  场景：线程 A 持有锁，锁过期释放 → 线程 B 获取锁
  → 线程 A 业务完成，调用 unlock() → 删除了线程 B 的锁！

  解决：Lua 脚本先校验 value（唯一标识）再删除（已在第二阶段解决）

坑 4：GC 停顿导致锁过期

  场景：线程 A 持有锁，JVM 发生 Full GC，停顿 5 秒
  → 锁过期释放 → 线程 B 获取锁
  → GC 结束，线程 A 和 B 同时操作共享资源

  解决：
  ① Fencing Token（唯一可靠方案）
  ② 调优 GC，减少停顿时间（换 G1/ZGC）
  ③ 评估：GC 停顿概率极低，多数场景可接受
```

### 💡 延伸思考

1. **Redlock 到底该不该用？** — 这是分布式系统领域的经典争议。Martin Kleppmann 认为 Redlock 依赖的"有界时钟漂移"和"有界网络延迟"假设不成立，GC 停顿会破坏安全性。antirez 的反驳是：工程实践中时钟漂移影响有限，且大多数场景下锁的用途是"效率优化"而非"正确性保证"。务实建议：如果锁失效会导致资金损失，用 ZK/etcd 而不是 Redis；如果只是避免重复计算，Redis 足够。

2. **etcd 分布式锁相比 ZK 有什么优势？** — etcd 使用 Raft 协议（比 ZK 的 ZAB 更简洁），Go 语言实现（性能优于 ZK），原生支持 Lease（租约）机制，自动续约。Kubernetes 生态标配，云原生项目首选。但 Java 生态的 Curator 框架（ZK）比 Jetcd（etcd 的 Java 客户端）更成熟。

**一、秒杀系统的核心挑战——为什么难？**

秒杀不是一般的"高并发"，而是在极短时间内产生**数百倍乃至数千倍**于日常的流量脉冲。

```
秒杀系统的四大核心挑战：

  挑战 1：瞬时高并发
  - 秒杀开始瞬间，数以万计的请求涌入
  - 日常 QPS 100 → 秒杀 QPS 100,000+（1000 倍）
  - 如果每个请求都打到数据库 → DB 瞬间崩溃

  挑战 2：超卖
  - 库存只有 100 件，但卖出了 1000 件
  - 根本原因：并发写操作覆盖了彼此的结果
  - 典型场景：两个请求同时读到 stock=1，都执行 stock-1

  挑战 3：恶意请求
  - 黄牛用脚本秒杀（比正常用户快 1000 倍）
  - 同一个用户重复提交
  - 攻击性流量（DDoS）

  挑战 4：数据库压力
  - 即使只有 1% 的请求穿透到数据库，也是上千 QPS
  - 数据库连接池耗尽 → 整个系统不可用
```

**四、Redis 预减库存——核心性能保障**

这是秒杀系统最关键的优化，将库存扣减从数据库前置到 Redis，大幅降低数据库压力。

```java
@Service
public class SeckillService {
    
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    @Autowired
    private RocketMQTemplate rocketMQTemplate;
    
    // 内存标记：商品是否已售罄
    private final ConcurrentHashMap<Long, Boolean> soldOutMap = new ConcurrentHashMap<>();
    
    /**
     * 秒杀核心流程
     */
    public Result seckill(Long goodsId, Long userId) {
        
        // ① 内存标记判断（最快！）
        if (soldOutMap.containsKey(goodsId)) {
            return Result.fail("已售罄");
        }
        
        // ② Redis 预减库存（原子操作）
        String stockKey = "seckill:stock:" + goodsId;
        Long stock = redisTemplate.opsForValue().decrement(stockKey);
        
        if (stock == null || stock < 0) {
            // 库存不足，恢复库存 + 标记售罄
            redisTemplate.opsForValue().increment(stockKey);
            soldOutMap.put(goodsId, true);
            return Result.fail("已售罄");
        }
        
        // ③ 判断是否重复秒杀（同一用户同一商品只能秒杀一次）
        String orderKey = "seckill:order:" + goodsId + ":" + userId;
        Boolean exists = redisTemplate.opsForValue()
            .setIfAbsent(orderKey, "1", 1, TimeUnit.HOURS);
        if (Boolean.FALSE.equals(exists)) {
            // 已秒杀过，恢复库存
            redisTemplate.opsForValue().increment(stockKey);
            return Result.fail("请勿重复秒杀");
        }
        
        // ④ 发送消息到 RocketMQ，异步下单
        SeckillMessage message = new SeckillMessage(goodsId, userId);
        rocketMQTemplate.asyncSend("seckill-order-topic", message, 
            new SendCallback() {
                @Override
                public void onSuccess(SendResult result) {
                    // 消息发送成功
                }
                @Override
                public void onException(Throwable e) {
                    // 发送失败 → 补偿：恢复库存 + 删除重复标记
                    redisTemplate.opsForValue().increment(stockKey);
                    redisTemplate.delete(orderKey);
                }
            });
        
        // ⑤ 返回"排队中"（不阻塞用户）
        return Result.success("正在排队中，请稍后查看订单");
    }
}
```

**六、超卖防护——三重保障**

```
超卖防护的逐层保障：

  第一层：Redis 原子操作（DECR）
  - 利用 Redis 单线程特性，DECR 是原子操作
  - 预减库存 < 0 时直接拦截
  - 拦截了 99% 的超卖可能

  第二层：数据库乐观锁
  UPDATE seckill_goods 
  SET stock = stock - 1 
  WHERE id = #{goodsId} AND stock > 0;
  - 利用数据库行锁 + WHERE 条件
  - 即使 Redis 有漏网之鱼，数据库也能拦截
```

### 💡 延伸思考

1. **秒杀系统为什么不用"数据库行锁"来防超卖？** — 数据库行锁（SELECT ... FOR UPDATE）在秒杀场景下会导致严重的性能问题：所有请求串行等待同一行锁，数据库连接池瞬间耗尽，拖垮整个系统。Redis 预减库存 + 乐观锁是更务实的选择——Redis 扛住 99% 的流量，乐观锁兜底。

2. **如果消息队列也积压了怎么办？** — ① 增加消费者实例（水平扩展），消费速度线性提升；② 如果消息积压已经很大，可以紧急扩容消费者，或临时跳过非核心逻辑（如不发送通知短信）；③ 最重要的事前预防：保持消费者和生产者速率匹配，监控消费延迟。
