## 题目 1：[缓存/分布式] Redis 分布式锁深度解析：从 SETNX 到 Redisson 看门狗与 Redlock 红锁

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-17 午间日报 — "Redis 分布式锁热度最高，几乎必问，含看门狗续期、主从切换锁丢失"
**相关岗位**：Java后端 / 全栈 / 架构师

### 📖 参考答案

#### 一、分布式锁的本质与基本要求

分布式锁是在分布式系统中协调多个节点对共享资源互斥访问的机制。

```
一把合格的分布式锁需要满足四个条件：

1. 互斥性（Mutual Exclusion）
   → 同一时刻只有一个客户端持有锁

2. 防死锁（Deadlock Free）
   → 持有锁的客户端崩溃后，锁能自动释放
   → 实现：设置过期时间（TTL）

3. 解铃还须系铃人（Owner Identification）
   → 只有持锁的客户端才能释放锁
   → 实现：value 存唯一标识（UUID/请求ID），释放前校验

4. 高可用与容错（High Availability）
   → 锁服务不是单点，部分节点故障不影响加解锁
   → 实现：主从 / 集群 / Redlock
```

#### 二、从 SETNX 到生产级方案：一步步填坑

**第 1 版：简单 SETNX（有坑）**

```java
// ❌ 问题 1：没有过期时间 → 宕机就死锁
Boolean locked = redis.setIfAbsent("lock:product:123", "1");
if (locked) {
    // 业务逻辑...
    redis.delete("lock:product:123");  // 如果这里宕机，锁永远不会释放
}

// ❌ 问题 2：SETNX + EXPIRE 不是原子操作
Boolean locked = redis.setIfAbsent("lock:product:123", "1");
redis.expire("lock:product:123", 30);  // 如果这一步之前宕机，还是死锁
```

**第 2 版：SET NX EX（原子操作，仍有坑）**

```java
// ✅ 原子操作：SET key value NX EX 30
String uuid = UUID.randomUUID().toString();
Boolean locked = redis.opsForValue()
    .setIfAbsent("lock:product:123", uuid, 30, TimeUnit.SECONDS);

if (locked) {
    try {
        // 业务逻辑... 可能耗时超过 30 秒
        doBusiness();
    } finally {
        // ❌ 问题 3：可能误删别人的锁
        // 场景：业务执行超过 30 秒，锁自动过期
        // 另一个线程获取了锁
        // 当前线程执行到这里 → 删了别人的锁！
        redis.delete("lock:product:123");
    }
}
```

**第 3 版：Lua 脚本保证释放锁的原子性**

```lua
-- 释放锁的 Lua 脚本（保证比较和删除是原子操作）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

```java
// ✅ 正确的释放锁方式
String script = "if redis.call('get', KEYS[1]) == ARGV[1] " +
                "then return redis.call('del', KEYS[1]) " +
                "else return 0 end";

redis.executeScript(script, 
    Arrays.asList("lock:product:123"), 
    Arrays.asList(uuid));
```

**第 4 版：锁续期（看门狗 Watchdog）**

```java
// ❌ 核心问题：业务执行时间不可控
// SET NX EX 30 → 业务执行 40 秒 → 锁在 30 秒时过期
// 另一个线程拿到锁 → 两个线程同时操作 → 数据不一致

// ✅ Redisson 的看门狗机制（Watchdog）
// 原理：后台线程每隔 10 秒检查一次
//       如果锁还在，自动续期到 30 秒
//       如果业务完成释放锁，停止续期
//       如果业务宕机，不再续期，锁自然过期

// Redisson 使用示例
RLock lock = redissonClient.getLock("lock:product:123");

// 看门狗默认参数：
//   lockWatchdogTimeout = 30000ms（续期间隔）
//   每 10 秒续期一次（timeout / 3）
//   业务完成调用 unlock() 时取消续期
lock.lock();  // 自动启动看门狗

try {
    doBusiness();  // 哪怕执行 5 分钟，锁也不会过期
} finally {
    lock.unlock();  // 释放锁，停止看门狗
}

// 也可指定持有时间（不启动看门狗）
lock.lock(10, TimeUnit.SECONDS);  // 10 秒后自动释放，不续期
```

**看门狗（Watchdog）的工作原理：**

```
Redisson 看门狗时序图：

Client A                  Redis                      Client B
  │                         │                          │
  │── lock(key) ──────────→│  SET key UUID PX 30000   │
  │←──── success ──────────│                          │
  │                         │                          │
  │  [每 10 秒]             │                          │
  │── Lua续期脚本 ────────→│  PEXPIRE key 30000       │
  │←──── 续期成功 ─────────│                          │
  │                         │                          │
  │  [业务执行 40 秒]       │                          │
  │── 续期 ───────────────→│  续期成功                 │
  │                         │                          │
  │  [业务完成]             │                          │
  │── unlock() ───────────→│  删除 key                 │
  │                         │                          │  now → tryLock()
  │                         │                          │  ← 获取成功 ✅
  │                         │                          │
  │  如果 Client A 宕机：    │                          │
  │  30 秒后 key 过期       │  key 自动删除             │
  │                         │                          │  now → tryLock()
  │                         │                          │  ← 获取成功 ✅
```

#### 三、主从切换导致锁丢失与 Redlock 红锁

**问题：主从架构下的锁丢失**

```
Redis 主从复制是异步的，存在以下风险：

                    ┌──────────┐
  Client A ──SET──→ │  Master  │ ← 锁写入成功
                    └────┬─────┘
                         │ 异步复制（未同步！）
                         │
                    ┌────▼─────┐
                    │  Slave   │ ← 没有锁数据
                    └──────────┘

  ① Client A 在 Master 上成功加锁
  ② 锁数据尚未同步到 Slave，Master 宕机
  ③ 哨兵选举 Slave 为新 Master
  ④ 新 Master 上没有锁数据 → Client B 也能加锁成功
  ⑤ 两个客户端同时持有锁 → 数据不一致！

  Redis 官方文档也承认：
  "This is not a theoretical issue. This is a real problem."
```

**Redlock 红锁算法（Redis 官方分布式锁方案）**

Redlock 的核心思路：**不在一个 Redis 上加锁，在多个独立 Redis 实例上同时加锁**。

```
Redlock 算法流程（N = 5 个独立 Redis 实例）：

  ① 获取当前时间戳 T1
  ② 依次向 N 个 Redis 实例尝试加锁（SET NX EX）
     每个加锁操作的超时时间 < 锁自动释放时间（如 10ms < 500ms）
  ③ 计算加锁耗时：elapsed = 当前时间 - T1
  ④ 成功条件：
     - 成功在多数节点上加锁（> N/2，即至少 3/5）
     - 且总耗时 < 锁自动释放时间 - elapsed
  ⑤ 如果加锁成功，锁的有效时间 = TTL - elapsed
  ⑥ 如果加锁失败，向所有节点发送解锁请求

  释放锁：向所有 5 个节点发送 Lua 解锁脚本（不管之前是否成功）
```

```java
// Redisson 的 Redlock 实现
RedissonClient client1 = Redisson.create(config1);
RedissonClient client2 = Redisson.create(config2);
RedissonClient client3 = Redisson.create(config3);

RedissonRedLock redLock = new RedissonRedLock(
    client1.getLock("lock:product:123"),
    client2.getLock("lock:product:123"),
    client3.getLock("lock:product:123")
);

// 尝试加锁，等待时间 1 秒，锁持有时间 30 秒
boolean locked = redLock.tryLock(1, 30, TimeUnit.SECONDS);

if (locked) {
    try {
        doBusiness();
    } finally {
        redLock.unlock();  // 向所有实例发送解锁
    }
}
```

**Redlock 的争议（2026 年大厂实际选择）：**

```
| 观点                     | 支持方                           | 理由                                           |
|-------------------------|----------------------------------|------------------------------------------------|
| Redlock 太复杂，不用     | Martin Kleppmann（DDIA 作者）     | 加锁时间戳依赖时钟，时钟漂移会破坏安全性           |
| Redlock 是正确方案        | Redis 作者 antirez                | 时钟漂移概率极低，可用 fencing token 兜底         |
| 大厂实际选择             | 大部分互联网公司                   | 不用 Redlock，用 Redisson + 主从就够             |

大厂实际做法：
  - 99% 场景：Redisson 单实例 + 看门狗（够用了）
  - 0.9% 场景：Redisson + 主从哨兵/Cluster（主从切换概率低）
  - 0.1% 场景：对一致性要求极高（如金融），用 ZooKeeper 分布式锁
  
  核心原则：不要为了 0.1% 的场景增加 100% 的复杂度。
  如果你的业务允许锁偶尔失效（用数据库兜底），
  单实例 Redisson + 看门狗是最佳选择。
```

### 💡 延伸思考
1. **Redlock 的 fencing token 机制是什么？** — 每次加锁时递增一个 token 序号，资源服务校验 token 是否过期。即使锁失效导致两个客户端同时持有锁，fencing token 也能保证只有最新 token 的客户端能操作资源。Martin Kleppmann 认为这才是解决分布式锁安全问题的正确方式。
2. **ZooKeeper 分布式锁和 Redis 分布式锁的本质区别？** — ZK 基于顺序临时节点 + Watch 机制，没有锁过期时间问题，但性能低于 Redis（ZK 是 CP 系统，写操作需要半数确认）。选型建议：对一致性要求极高用 ZK，对性能要求高用 Redis。

## 题目 2：[数据库/MySQL] MySQL InnoDB 索引底层原理：为什么选 B+ 树？聚簇索引与回表、覆盖索引与索引下推

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-17 早间日报 — "MySQL 索引优化为 Top 25 面试高频题" + "2026 年 Java 社招高频 80 题 MySQL 占 11 题"
**相关岗位**：Java后端 / 全栈 / DBA

### 📖 参考答案

#### 一、为什么 MySQL InnoDB 选择了 B+ 树？

数据库的核心瓶颈是磁盘 I/O，所有数据结构的选型都是为了**减少磁盘 I/O 次数**。

```
常见数据结构的 I/O 对比（以 1000 万行数据为例）：

| 数据结构          | 树高（层数） | 最坏 I/O 次数 | 范围查询      |
|------------------|:----------:|:------------:|:------------:|
| 二叉搜索树        | log₂(10⁷)≈24 | 24 次        | 差（需回溯）  |
| 红黑树            | log₂(10⁷)≈24 | 24 次        | 差（需回溯）  |
| 哈希表            | —           | 1-2 次       | ❌ 不支持     |
| B 树              | log₃₀₀(10⁷)≈3 | 3 次         | 差（中序遍历）|
| B+ 树（InnoDB）   | log₃₀₀(10⁷)≈3 | 3 次         | ✅ 极好       |

B+ 树的三大核心优势：

1. 树高极低（3-4 层存千万行）
   → InnoDB 每个页 16KB，假设 key 8B + 指针 6B ≈ 14B
   → 一个非叶子节点可存 16384/14 ≈ 1170 个 key
   → 3 层 B+ 树可存 1170 × 1170 × 16 ≈ 2100 万行数据
   → 查询任意一行只需 3 次 I/O！

2. 所有数据在叶子节点
   → 非叶子节点只存 key + 指针，不存数据
   → 同样的空间可存更多 key → 树更矮 → I/O 更少

3. 叶子节点双向链表连接
   → 范围查询只需找到起点，沿链表顺序扫描
   → 无需像 B 树那样中序遍历（多次回溯）
   → SELECT * FROM t WHERE id BETWEEN 100 AND 200 → 极快
```

**B+ 树 vs B 树的核心区别：**

```
B 树（数据存在所有节点）：     B+ 树（数据只在叶子节点）：
     [10|20|30]                    [10|20|30]
    /    |    \                   /    |    \
 [1|5] [15] [25|28]         [1|5] [15] [25|28]
 数据在内部节点                  内部节点只存 key
                                叶子节点存完整数据
                              叶子节点间双向链表连接

B 树范围查询（差）：
  查 15-25 → 找到 15（内部节点）→ 回溯到父节点 → 找 20 → ...

B+ 树范围查询（好）：
  查 15-25 → 找到 15（叶子节点）→ 沿 next 指针 → 到 25
```

#### 二、聚簇索引（Clustered Index）vs 二级索引（Secondary Index）

InnoDB 的索引分为两种，这是面试必问的核心概念。

```
InnoDB 索引类型：

1. 聚簇索引（Clustered Index）—— 表即索引
   → 每张表只有一个聚簇索引
   → 叶子节点存完整行数据
   → 默认用主键作为聚簇索引
   → 如果没有主键，用第一个 UNIQUE 列
   → 如果都没有，InnoDB 自动生成 6 字节的 ROWID

2. 二级索引（Secondary Index）—— 非聚簇索引
   → 每张表可以有多个二级索引
   → 叶子节点存索引列 + 主键值
   → 查找非索引列需要"回表"（回到聚簇索引再查一次）

聚簇索引示意图：

     ┌─────────────┐
     │  非叶子节点   │ ← 只存主键值 + 指针
     │  id: 1-500  │
     └──────┬──────┘
            │
     ┌──────▼──────┐
     │   叶子节点    │ ← 存完整行数据
     │  id=1        │
     │  name=张三   │
     │  age=25      │
     │  ...         │
     └──────────────┘

二级索引示意图（idx_name）：

     ┌─────────────┐
     │  非叶子节点   │ ← 只存 name 值 + 指针
     │ a-j          │
     └──────┬──────┘
            │
     ┌──────▼──────┐
     │   叶子节点    │ ← 存 name + 主键 id
     │ name=张三    │
     │ id=1         │ ← 指向聚簇索引的"书签"
     └──────────────┘
```

**回表查询（Bookmark Lookup）：**

```sql
-- 表结构
CREATE TABLE `user` (
  `id` int PRIMARY KEY,          -- 聚簇索引
  `name` varchar(20),
  `age` int,
  `city` varchar(20),
  KEY `idx_name` (`name`)        -- 二级索引
);

-- 查询 1：走二级索引 idx_name，需要回表
SELECT * FROM user WHERE name = '张三';
-- 执行流程：
--   ① 在 idx_name 中找到 name='张三' → 拿到主键 id=1
--   ② 回到聚簇索引（主键索引）查找 id=1 → 拿到完整行数据
--   ③ 这个过程叫"回表"

-- 查询 2：覆盖索引，不需要回表
SELECT id, name FROM user WHERE name = '张三';
-- 执行流程：
--   ① 在 idx_name 中找到 name='张三' → 拿到主键 id=1
--   ② idx_name 的叶子节点已经包含 id 和 name
--   ③ 直接返回，无需回表！
```

#### 三、覆盖索引（Covering Index）

**覆盖索引是减少回表的最有效手段。**

```sql
-- 假设我们经常按 name 查询 age
-- 普通二级索引：idx_name(name)
-- 查询需要回表（因为 age 不在索引中）
SELECT age FROM user WHERE name = '张三';
-- ↑ 需要回表

-- ✅ 联合索引实现覆盖索引
CREATE INDEX idx_name_age ON user(name, age);

-- 现在 name 和 age 都在索引中
-- 查询不需要回表！
SELECT age FROM user WHERE name = '张三';
-- ↑ 索引覆盖，不用回表

-- EXPLAIN 输出 Extra 列会显示：
-- "Using index"  → 表示使用了覆盖索引（不用回表）
-- "Using index condition" → 表示索引下推
```

#### 四、索引下推（Index Condition Pushdown, ICP）

**ICP 是 MySQL 5.6 引入的优化，减少回表次数。**

```
没有 ICP 的执行流程：

联合索引 idx_name_age(name, age)
查询：SELECT * FROM user WHERE name LIKE '张%' AND age = 25

① 在 idx_name_age 中定位到第一个 name LIKE '张%' 的行
② 回表（到聚簇索引）获取完整行数据
③ 在服务层判断 age = 25 是否成立
④ 不成立 → 丢弃
⑤ 回到索引，取下一条 name LIKE '张%' 的行
⑥ 重复 ②-④

问题：所有 name LIKE '张%' 的行都要回表！
如果 name LIKE '张%' 匹配了 10 万行，就要回表 10 万次！

有 ICP 的执行流程：

① 在 idx_name_age 中定位到第一个 name LIKE '张%' 的行
② 直接在索引层判断 age = 25（索引包含 age 列！）
③ 不成立 → 直接跳过（不回表！）
④ 成立 → 回表获取完整数据
⑤ 继续下一条

效果：只有 age=25 的行才回表，可能只需回表 100 次！
I/O 从 10 万次降到 100 次，性能提升 1000 倍！

EXPLAIN 显示：
Extra: "Using index condition"  → 表示使用了 ICP
```

#### 五、索引失效的 10 大场景

面试高频追问：**"建了索引但查询还是慢，可能是什么原因？"**

```sql
-- 1. 违反最左前缀原则
CREATE INDEX idx_a_b_c ON t(a, b, c);
-- ✅ 有效：WHERE a=1 AND b=2 AND c=3
-- ✅ 有效：WHERE a=1 AND b=2
-- ✅ 有效：WHERE a=1
-- ❌ 失效：WHERE b=2          （跳过了 a）
-- ❌ 失效：WHERE a=1 AND c=3  （跳过了 b）

-- 2. 对索引列使用函数
-- ❌ 失效
SELECT * FROM user WHERE YEAR(create_time) = 2026;
-- ✅ 改写成范围查询
SELECT * FROM user WHERE create_time >= '2026-01-01' AND create_time < '2027-01-01';

-- 3. 隐式类型转换
-- ❌ 失效（name 是 VARCHAR，用了整数）
SELECT * FROM user WHERE name = 123;
-- ✅ 有效
SELECT * FROM user WHERE name = '123';

-- 4. LIKE 以通配符开头
-- ❌ 失效
SELECT * FROM user WHERE name LIKE '%张三%';
-- ✅ 有效（但只能利用到第一个字）
SELECT * FROM user WHERE name LIKE '张%';

-- 5. OR 条件中有非索引列
-- ❌ 失效（age 没有索引）
SELECT * FROM user WHERE name = '张三' OR age = 25;
-- ✅ 改成 UNION
SELECT * FROM user WHERE name = '张三'
UNION
SELECT * FROM user WHERE age = 25;

-- 6. NOT IN / NOT EXISTS
-- ❌ 失效
SELECT * FROM user WHERE id NOT IN (1, 2, 3);
-- ✅ 改成 LEFT JOIN ... IS NULL
```

#### 六、面试答题模板

```
"InnoDB 选择 B+ 树的核心原因是磁盘 I/O 优化。

B+ 树树高极低（3 层存千万行），
非叶子节点只存 key（不存数据），
叶子节点存完整数据并通过双向链表连接。

相比 B 树，B+ 树有两个关键优势：
1. 非叶子节点可存更多 key，树更矮，I/O 更少
2. 叶子节点链表结构，范围查询极快

索引优化的核心思路是减少回表：
覆盖索引让查询列全部在索引中，不用回表；
索引下推（ICP）在索引层就过滤掉不满足条件的行，
减少回表次数，这是 MySQL 5.6 引入的关键优化。

最左前缀原则决定了联合索引的列顺序：
把等值条件列放前面，范围条件列放后面。"
```

### 💡 延伸思考
1. **为什么建议使用自增主键而不是 UUID 作为聚簇索引？** — 自增主键是顺序插入，B+ 树叶子节点直接追加写入，没有页分裂开销；UUID 是随机插入，会导致频繁的页分裂和碎片，写入性能下降 50%+。这也是为什么 InnoDB 推荐使用自增主键的原因。
2. **MySQL 8.0 的"降序索引"有什么用？** — 以前 MySQL 的索引默认升序，`ORDER BY DESC` 会导致文件排序。8.0 支持降序索引，`CREATE INDEX idx ON t(a ASC, b DESC)` 让 `ORDER BY a ASC, b DESC` 直接走索引，无需额外排序。

#### 一、JVM 内存区域划分（2026 版）

#### 二、4 种 OOM 类型及排查方法

**1. Java heap space（堆内存溢出）**

```
症状：java.lang.OutOfMemoryError: Java heap space
原因：
  - 内存泄漏（最常见）：对象被持续引用，GC 无法回收
  - 一次性加载超大批量数据（未分页查询、大文件读取）
  - -Xmx 设置过小

排查步骤：
  Step 1: 确认是内存泄漏还是内存不足
    → 启动时加 JVM 参数，OOM 时自动 dump
    -XX:+HeapDumpOnOutOfMemoryError
    -XX:HeapDumpPath=/path/to/dump.hprof
    
  Step 2: 分析 Heap Dump
    → 用 MAT（Memory Analyzer Tool）或 JProfiler
    → 找 GC Roots 引用链，定位泄漏点
    
  Step 3: 常见泄漏模式
    → 集合类无限增长（HashMap 只增不减）
    → 未关闭的资源（InputStream、数据库连接）
    → 内部类持有外部类引用（匿名内部类隐式持有 this）
    → ThreadLocal 未 remove()（虚拟线程场景尤其严重）
```

**2. Metaspace（元空间溢出）**

```
症状：java.lang.OutOfMemoryError: Metaspace
原因：
  - 频繁动态生成 Class（CGLib 代理、Spring AOP、热部署）
  - 大量反射调用产生动态类
  - 每个类加载器对应一个独立空间，类加载器泄漏

排查：
  -XX:MaxMetaspaceSize=256m 限制元空间大小
  -XX:+TraceClassLoading 查看加载的类
```

**3. GC overhead limit exceeded（GC 开销超限）**

```
症状：java.lang.OutOfMemoryError: GC overhead limit exceeded
原因：98% 的时间花在 GC，但只回收了不到 2% 的堆
      → 系统处于"濒死状态"，做了大量无用 GC

排查：
  → 用 jstat -gcutil <pid> 1s 查看 GC 频率
  → 确认堆大小是否足够，是否有内存泄漏
```

**4. Unable to create new native thread（无法创建线程）**

```
症状：java.lang.OutOfMemoryError: Unable to create new native thread
原因：
  - 线程数超过操作系统限制（ulimit -u）
  - 线程栈内存耗尽（-Xss 太大）
  - 虚拟线程场景下 ThreadLocal 内存泄漏

排查：
  ulimit -a 查看系统限制
  ps -eLf | grep java | wc -l 查看线程数
```

#### 三、G1 GC 与 ZGC 调优实战

**G1 GC（JDK 9+ 默认）—— 平衡吞吐量和延迟**

```
G1 核心原理：Region 化 + 并发标记 + 预测停顿模型

┌────────────────────────────────────────────┐
│              G1 Heap 布局                   │
│                                            │
│  ┌─────┬─────┬─────┬─────┬─────┬─────┐    │
│  │ E   │ E   │ E   │ S   │ O   │ O   │    │
│  ├─────┼─────┼─────┼─────┼─────┼─────┤    │
│  │ E   │ O   │ H   │ E   │ S   │ O   │    │
│  ├─────┼─────┼─────┼─────┼─────┼─────┤    │
│  │ O   │ E   │ E   │ H   │ O   │ O   │    │
│  └─────┴─────┴─────┴─────┴─────┴─────┘    │
│                                            │
│  E = Eden Region（新生代）                   │
│  S = Survivor Region                        │
│  O = Old Region（老年代）                    │
│  H = Humongous Region（大对象 > Region 50%） │
└────────────────────────────────────────────┘
```

```bash
# G1 生产推荐配置（2026 版）
-Xms8g -Xmx8g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200          # 目标停顿时间（默认 200ms）
-XX:G1HeapRegionSize=4m            # Region 大小（4-32MB）
-XX:G1NewSizePercent=5             # 新生代初始占比
-XX:G1MaxNewSizePercent=60         # 新生代最大占比
-XX:InitiatingHeapOccupancyPercent=45  # 触发并发标记的堆占比
-XX:+ParallelRefProcEnabled        # 并行处理软引用
-XX:G1HeapWastePercent=5           # 允许的堆浪费
```

**ZGC（JDK 17+ 生产可用）—— 追求极低延迟**

```
ZGC 的核心创新：染色指针（Colored Pointer）+ 读屏障（Load Barrier）

ZGC 的 STW 时间不超过 1ms，与堆大小无关！
无论 4GB 还是 512GB 堆，STW 都 < 1ms

ZGC 三个阶段（全并发）：

阶段 1：并发标记（Concurrent Mark）
  → 遍历 GC Roots，标记存活对象
  → 用读屏障处理标记期间的引用变更
  → STW 时间 = 0（完全并发）

阶段 2：并发转移准备（Concurrent Prepare for Relocation）
  → 分析哪些 Region 需要转移
  → 建立转发表（Forwarding Table）
  → STW 时间 = 0（完全并发）

阶段 3：并发转移（Concurrent Relocation）
  → 将存活对象转移到新 Region
  → 更新转发表
  → 用读屏障保证访问正确性
  → STW 时间 = 0（完全并发）

唯一短暂的 STW 阶段：
  初始标记（GC Roots 扫描）→ < 1ms
  最终标记（处理引用、弱引用）→ < 1ms
```

```bash
# ZGC 生产推荐配置
-Xms8g -Xmx8g
-XX:+UseZGC
-XX:ZAllocationSpikeTolerance=2.0   # 分配尖峰容忍度
-XX:+ZGenerational                  # 分代 ZGC（JDK 21+）
-XX:ZCollectionInterval=120         # 强制 GC 间隔（秒）
-Xlog:gc*:file=gclog.log:time,uptime,level,tags  # GC 日志
```

```
生产环境 FullGC 排查 5 步法：

Step 1：确认是否真的 FullGC
```

## 题目 4：[框架/Spring] Spring 循环依赖的底层原理：三级缓存为什么不能简化为二级？AOP 代理如何保持一致性？

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-17 早间日报 — "Spring 循环依赖为 Top 25 面试高频题" + 2026 年 Java 社招高频 80 题 Spring 占 12 题
**相关岗位**：Java后端 / 全栈

### 📖 参考答案

#### 一、什么是循环依赖？Spring 能解决什么类型的循环依赖？

```
循环依赖的定义：

@Service
public class AService {
    @Autowired
    private BService bService;
}

@Service
public class BService {
    @Autowired
    private AService aService;
}

依赖关系：AService → BService → AService（闭环）

Spring 能解决的：
  ✅ 单例 Bean + Setter 注入（最常用）
  ✅ 单例 Bean + field 注入（@Autowired）
  
Spring 不能解决的：
  ❌ 构造器注入（创建时必须拿到依赖，无法提前暴露）
  ❌ 原型作用域（每次创建新对象，无缓存）
  ❌ 循环依赖中有 @Async（AOP 代理拦截提前）
```

#### 二、三级缓存的定义与工作原理

Spring 通过三级缓存来解决单例 Bean 的循环依赖，定义在 `DefaultSingletonBeanRegistry` 中。

```java
// Spring 三级缓存（DefaultSingletonBeanRegistry）
public class DefaultSingletonBeanRegistry {
    
    // 一级缓存：完全初始化好的 Bean（成品）
    // Map<beanName, 完整Bean实例>
    private final Map<String, Object> singletonObjects = new ConcurrentHashMap<>(256);
    
    // 二级缓存：早期暴露的 Bean（半成品）
    // Map<beanName, 未完成属性注入的Bean实例>
    private final Map<String, Object> earlySingletonObjects = new ConcurrentHashMap<>(16);
    
    // 三级缓存：存放 ObjectFactory（工厂）
    // Map<beanName, ObjectFactory>
    // 用于生成 Bean 的早期引用（必要时创建 AOP 代理）
    private final Map<String, ObjectFactory<?>> singletonFactories = new HashMap<>(16);
}
```

**三级缓存的工作流程（以 AService → BService → AService 为例）：**

```
第 1 步：开始创建 AService
  → getSingleton("aService") → 三级缓存都没有
  → 调用 createBean("aService")
  → 通过反射创建 AService 实例（此时属性都为空）
  → 将 AService 的 ObjectFactory 放入三级缓存
    singletonFactories["aService"] = () -> getEarlyBeanReference("aService")
  
  此时缓存状态：
  三级缓存：{aService: ObjectFactory}
  二级缓存：{}  
  一级缓存：{}

第 2 步：填充 AService 的属性
  → 发现需要注入 BService
  → 调用 getSingleton("bService")

第 3 步：开始创建 BService
  → 三级缓存都没有
  → 调用 createBean("bService")
  → 通过反射创建 BService 实例
  → 将 BService 的 ObjectFactory 放入三级缓存
  
  此时缓存状态：
  三级缓存：{aService: ObjectFactory, bService: ObjectFactory}
  二级缓存：{}  
  一级缓存：{}

第 4 步：填充 BService 的属性
  → 发现需要注入 AService
  → 调用 getSingleton("aService")
  
  getSingleton 执行流程：
  ① 查一级缓存 → 没有
  ② 查二级缓存 → 没有
  ③ 查三级缓存 → 有！
     → 执行 ObjectFactory.getObject()
     → 如果是普通 Bean，直接返回原始对象
     → 如果有 AOP，创建 AOP 代理对象
     → 将结果放入二级缓存（earlySingletonObjects）
     → 从三级缓存中移除

  此时缓存状态：
  三级缓存：{bService: ObjectFactory}
  二级缓存：{aService: AService的早期引用（可能是代理对象）}
  一级缓存：{}

第 5 步：BService 获取到 AService 的早期引用
  → 注入到 BService 的 aService 属性
  → BService 完成属性注入
  → BService 执行初始化方法（afterPropertiesSet、init-method）
  → 将 BService 放入一级缓存（singletonObjects）
  → 从二级/三级缓存中移除 BService

  此时缓存状态：
  三级缓存：{}
  二级缓存：{aService: 早期引用}
  一级缓存：{bService: 完整Bean}

第 6 步：回到 AService 的创建
  → BService 创建完成，AService 成功注入 bService 属性
  → AService 执行初始化方法
  → 将 AService 放入一级缓存（singletonObjects）
  → 从二级/三级缓存中移除

  此时缓存状态：
  三级缓存：{}
  二级缓存：{}
  一级缓存：{aService: 完整Bean, bService: 完整Bean}
  
  ✅ 循环依赖解决！
```

#### 三、为什么需要三级缓存？不能简化为二级缓存？

**这是面试中最高频的追问：为什么需要三级缓存，二级不够吗？**

```
核心原因：AOP 代理

如果没有 AOP（没有 @Transactional、@Async 等），
二级缓存就够了。

流程会变成：
  ① 创建 AService 原始对象 → 放入二级缓存
  ② BService 从二级缓存拿到 AService 原始对象
  ③ BService 完成创建
  ④ AService 继续属性注入、初始化

但有了 AOP 就复杂了：
  ① AService 需要创建 AOP 代理对象
  ② 但 AOP 代理需要在 Bean 初始化之后才能创建
     （因为 AbstractAutoProxyCreator 在 postProcessAfterInitialization 中创建代理）
  ③ 这就产生了矛盾：
     - BService 在 AService 初始化之前就需要 AService
     - 但 AService 的 AOP 代理要初始化之后才能创建
     - BService 拿到的是原始对象，不是代理对象！

三级缓存解决这个矛盾的方式：

三级缓存不存 Bean 实例，存 ObjectFactory。
ObjectFactory.getObject() 的调用时机是"被需要的时候"。

流程变成：
  ① AService 实例化 → 放入三级缓存（ObjectFactory）
  ② BService 需要 AService → 执行 ObjectFactory.getObject()
     → 此时判断：如果有 Advice（AOP 通知），就创建代理对象
     → BService 拿到的是 AService 的代理对象 ✅
  ③ BService 完成创建
  ④ AService 继续初始化
  ⑤ AService 初始化完成后，发现已经有代理对象了
     → 直接用三级缓存创建的代理对象，不再重新创建
     → 保证整个容器中 AService 的代理对象是同一个 ✅
```

**如果没有三级缓存（只有二级缓存）会怎样？**

```
如果只有二级缓存：

方案 A：二级缓存存原始对象
  → BService 拿到原始对象，不是代理对象
  → AService 初始化后创建代理对象
  → 容器中 AService 是代理对象，但 BService 持有的还是原始对象
  → AService 的方法调用不走代理！@Transactional 失效！❌

方案 B：二级缓存存代理对象（在实例化后立即创建代理）
  → 但此时 AService 还未初始化，@PostConstruct 未执行
  → 代理对象中注入的属性也不完整
  → 如果 AOP 切面逻辑需要用到初始化后的状态 → 出错 ❌

三级缓存的精妙之处：
  延迟代理创建时机——等到真正需要的时候才创建，
  而且保证容器中所有引用都是同一个代理对象。
```

### 📖 参考答案

#### 一、synchronized 锁升级机制（JDK 6+ 优化）

synchronized 在 JDK 6 之前是重量级锁（依赖操作系统的 Mutex Lock），JDK 6 做了大量优化，引入了**锁升级**机制：无锁 → 偏向锁 → 轻量级锁 → 重量级锁。

```
锁升级是单向的：只能升级，不能降级。

锁状态                      Mark Word 内容
──────────────────────────────────────────────────
无锁（001）                  hashCode + 分代年龄 + 0

偏向锁（101）               线程ID + 时间戳 + 分代年龄 + 1

轻量级锁（00）              指向栈中锁记录的指针

重量级锁（10）              指向 Monitor 对象的指针

GC 标记（11）               GC 标记信息
```

**1. 偏向锁（Biased Locking）—— 同一个线程反复获取**

```
偏向锁的核心思想：锁不仅没有竞争，而且总是被同一个线程获取。

原理：
  ① 线程第一次获取锁时，在对象头 Mark Word 中记录线程 ID
  ② 下次同一线程再来获取锁 → 检查线程 ID 是否匹配
  ③ 匹配 → 直接进入，无需任何 CAS 操作（性能极高）
  
适用场景：单线程访问同步块（如 Vector、StringBuffer 的同步方法）
撤销条件：另一个线程尝试获取锁

JDK 15 默认禁用偏向锁（因为维护成本高、代码复杂度大）：
  -XX:-UseBiasedLocking  # JDK 15+ 默认禁用
  # 原因：偏向锁的撤销需要全局安全点，可能比轻量级锁还慢
```

**2. 轻量级锁（Lightweight Locking）—— 少量线程交替执行**

```
触发条件：第二个线程尝试获取偏向锁 → 偏向锁升级为轻量级锁

原理：
  ① 在栈帧中创建 Lock Record 空间
  ② 用 CAS 尝试将对象头 Mark Word 替换为指向 Lock Record 的指针
  ③ CAS 成功 → 获取锁成功
  ④ CAS 失败 → 自旋（Spin）重试
  ⑤ 自旋超过阈值（JDK 6 默认 10 次，JDK 7+ 自适应）→ 升级为重量级锁

特点：用 CAS 代替互斥量，避免用户态/内核态切换
适用场景：线程竞争不激烈，锁持有时间短
```

**3. 重量级锁（Heavyweight Locking）—— 多线程激烈竞争**

```
触发条件：自旋超过阈值 或 同时有多个线程在等待

原理：
  ① 通过操作系统 Mutex Lock 实现
  ② 未获取到锁的线程进入阻塞队列（BLOCKED 状态）
  ③ 需要用户态/内核态切换（开销大，约 1-10μs）
  ④ 依赖操作系统的线程调度

特点：真正的互斥，线程阻塞不消耗 CPU
适用场景：锁竞争激烈，锁持有时间长
```

**锁升级的完整流程：**

```
线程 A 获取锁：             线程 B 尝试获取锁：
    │                          │
    ▼                          │
┌──────────┐                   │
│  无锁    │                   │
│ (001)    │                   │
└────┬─────┘                   │
     │ 线程 A 获取              │
     ▼                          │
┌──────────┐   线程 B 尝试获取   │
│  偏向锁  │─────────────────── │
│ (101)    │   检查线程 ID      │
└────┬─────┘   不匹配 → 撤销偏向 │
     │                          │
     ▼                          ▼
┌──────────┐     ┌──────────┐
│ 轻量级锁 │◄───→│ CAS 自旋  │
│ (00)     │     │ 重试      │
└────┬─────┘     └──────────┘
     │ 自旋失败或同时多线程竞争
     ▼
┌──────────┐
│ 重量级锁 │
│ (10)     │
└──────────┘
```

#### 二、AQS（AbstractQueuedSynchronizer）原理

AQS 是 JUC 包的基石，ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock 都基于它实现。

```
AQS 的核心结构：

┌────────────────────────────────────────────────────┐
│                    AQS                              │
│                                                    │
│  state（volatile int）：同步状态                    │
│    ├── ReentrantLock：获取锁的次数（0=未持有）      │
│    ├── Semaphore：剩余许可数                       │
│    └── CountDownLatch：剩余计数                    │
│                                                    │
│  CLH 队列（双向链表）：等待获取锁的线程队列           │
│                                                    │
│    头节点          Node1           Node2            │
│  ┌────────┐    ┌────────┐    ┌────────┐            │
│  │ dummy  │◄──►│ Thread │◄──►│ Thread │            │
│  │        │    │   A    │    │   B    │            │
│  └────────┘    └────────┘    └────────┘            │
│     ↑              ↑              ↑                 │
│  持有锁的线程    等待获取锁     等待获取锁           │
└────────────────────────────────────────────────────┘

AQS 的模板方法设计模式：

│ 需要子类实现的 try 方法    │ AQS 框架提供的模板方法    │
│──────────────────────────│─────────────────────────│
│ tryAcquire(int)          │ acquire(int)            │
│ tryRelease(int)          │ release(int)            │
│ tryAcquireShared(int)    │ acquireShared(int)      │
│ tryReleaseShared(int)    │ releaseShared(int)      │
│ isHeldExclusively()      │                         │
```

**ReentrantLock 基于 AQS 的实现：**

```java
// ReentrantLock 内部 Sync 继承 AQS
abstract static class Sync extends AbstractQueuedSynchronizer {
    
    // 非公平锁的 tryAcquire
    final boolean nonfairTryAcquire(int acquires) {
        final Thread current = Thread.currentThread();
        int c = getState();
        
        if (c == 0) {  // 锁未被持有
            // CAS 尝试获取锁
            if (compareAndSetState(0, acquires)) {
                setExclusiveOwnerThread(current);  // 设置持有线程
                return true;
            }
        }
        else if (current == getExclusiveOwnerThread()) {  // 可重入
            int nextc = c + acquires;
            if (nextc < 0) throw new Error("Maximum lock count exceeded");
            setState(nextc);  // state + 1
            return true;
        }
        return false;  // 获取失败，加入等待队列
    }
}

// 加锁流程
// lock() → acquire(1) → tryAcquire(1)
//   ├── 成功 → 执行业务代码
//   └── 失败 → 加入 CLH 队列 → 挂起线程（park）→ 被唤醒后重试

// 解锁流程
// unlock() → release(1) → tryRelease(1)
//   → state - 1
//   → state == 0 → 释放锁 → 唤醒队列中第一个等待线程
```

#### 三、synchronized vs ReentrantLock 8 大维度对比

```
| 对比维度         | synchronized                   | ReentrantLock                    |
|-----------------|-------------------------------|----------------------------------|
| 底层实现         | JVM 级别（C++ 实现）            | JDK 级别（AQS 实现）              |
| 锁获取方式       | 自动获取/释放（finally 隐式）   | 手动 lock()/unlock()             |
| 锁升级           | 偏向锁→轻量级→重量级（单向）     | 无锁升级（直接 CAS + 队列）        |
| 可重入性         | ✅ 隐式可重入                   | ✅ 显式可重入（state 计数）        |
| 可中断性         | ❌ 不可中断                     | ✅ lockInterruptibly()            |
| 超时获取         | ❌ 不支持                       | ✅ tryLock(timeout, unit)         |
| 公平性           | ❌ 非公平                       | ✅ 可指定公平/非公平               |
| 条件变量         | ❌ 只有 wait/notify             | ✅ Condition（多个等待队列）       |
| JDK 21 虚拟线程  | ⚠️ 可能 Pinning                 | ✅ 不会 Pinning                   |
```

**选择建议：**

```
什么时候用 synchronized：
  - 简单的同步块，不需要超时、中断
  - 代码简洁，不需要手动释放锁
  - JDK 6+ 性能已和 ReentrantLock 相当
  - 新代码首选（Java 官方推荐）

什么时候用 ReentrantLock：
  - 需要超时获取锁（tryLock）
  - 需要可中断的锁获取（lockInterruptibly）
  - 需要公平锁
  - 需要多个 Condition 等待队列
  - 虚拟线程场景（避免 synchronized 的 Pinning）
```
