**一、RocketMQ 事务消息——分布式事务的最终一致性利器**

RocketMQ 事务消息解决的核心问题：**本地事务执行与消息发送的原子性**——本地事务成功则消息一定发送成功，本地事务失败则消息一定不发送。

```
为什么需要事务消息？

  场景：用户下单 → 需要同时完成"扣减库存"和"发送下单成功通知"
  
  问题：
  ① 先扣库存，再发消息 → 发消息失败 → 库存扣了但用户没收到通知
  ② 先发消息，再扣库存 → 扣库存失败 → 用户收到通知但库存没扣
  
  事务消息的解决方案：
  将"扣库存"和"发消息"绑定为一个原子操作
  → 扣库存成功 ⇔ 消息一定发送成功
  → 扣库存失败 ⇔ 消息一定不发送
```

**二、半消息 + 两阶段提交——核心机制**

RocketMQ 事务消息基于 **半消息（Half Message）+ 两阶段提交 + 事务回查** 实现：

```
事务消息三阶段流程：

  ┌──────────────────────────────────────────────────────────────┐
  │                    阶段 1：发送半消息                          │
  │                                                              │
  │  Producer → Broker：发送 Half Message                        │
  │  Broker 将消息写入 RMQ_SYS_TRANS_HALF_TOPIC（内部 Topic）     │
  │  此时消息对 Consumer 不可见！                                 │
  │  Broker 返回"半消息发送成功"                                  │
  ├──────────────────────────────────────────────────────────────┤
  │                    阶段 2：执行本地事务                        │
  │                                                              │
  │  Producer 收到半消息发送成功 → 执行本地事务（如扣库存）         │
  │  本地事务成功 → 向 Broker 发送 Commit                        │
  │  本地事务失败 → 向 Broker 发送 Rollback                      │
  │                                                              │
  │  Commit：消息从 HALF_TOPIC 移到目标 Topic → Consumer 可见     │
  │  Rollback：消息从 HALF_TOPIC 删除 → 永远不会被消费            │
  ├──────────────────────────────────────────────────────────────┤
  │                    阶段 3：事务回查（兜底）                    │
  │                                                              │
  │  如果 Broker 长时间未收到 Commit/Rollback（如 Producer 宕机）  │
  │  → Broker 主动回调 Producer 的 checkLocalTransaction()       │
  │  → Producer 检查本地事务状态，返回 Commit 或 Rollback         │
  │  → 回查最多 15 次，间隔递增                                   │
  └──────────────────────────────────────────────────────────────┘
```

```java
// RocketMQ 事务消息生产者实现
@Service
public class OrderTransactionProducer {
    
    @Autowired
    private RocketMQTemplate rocketMQTemplate;
    
    public void sendOrderMessage(Order order) {
        // 构建消息
        Message<String> message = MessageBuilder
            .withPayload(JSON.toJSONString(order))
            .build();
        
        // 发送事务消息
        TransactionSendResult result = rocketMQTemplate.sendMessageInTransaction(
            "order-topic",           // 目标 Topic
            message,                 // 消息体
            order.getOrderId()       // 业务参数（传给 executeLocalTransaction）
        );
        
        if (result.getLocalTransactionState() == LocalTransactionState.COMMIT_MESSAGE) {
            log.info("订单事务消息提交成功，订单ID：{}", order.getOrderId());
        }
    }
}

// 事务监听器——实现本地事务 + 回查逻辑
@RocketMQTransactionListener
public class OrderTransactionListener implements RocketMQLocalTransactionListener {
    
    @Autowired
    private OrderService orderService;
    
    /**
     * 执行本地事务
     */
    @Override
    public RocketMQLocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        Long orderId = (Long) arg;
        try {
            // 执行本地事务：扣库存
            orderService.createOrder(orderId);
            log.info("本地事务执行成功，订单ID：{}", orderId);
            return RocketMQLocalTransactionState.COMMIT;
        } catch (Exception e) {
            log.error("本地事务执行失败，订单ID：{}", orderId, e);
            return RocketMQLocalTransactionState.ROLLBACK;
        }
    }
    
    /**
     * 事务回查：Broker 主动回调，确认本地事务状态
     */
    @Override
    public RocketMQLocalTransactionState checkLocalTransaction(Message msg) {
        Long orderId = parseOrderId(msg);
        // 查询数据库，确认订单是否创建成功
        Order order = orderService.getById(orderId);
        if (order != null) {
            log.info("回查确认：订单已创建，订单ID：{}", orderId);
            return RocketMQLocalTransactionState.COMMIT;
        } else {
            log.info("回查确认：订单不存在，订单ID：{}", orderId);
            return RocketMQLocalTransactionState.ROLLBACK;
        }
    }
}
```

**事务回查的触发条件与处理细节**：

```
回查机制的关键点：

  ① 触发条件：Broker 在收到半消息后，超过一定时间未收到 Commit/Rollback
     （默认 6 秒开始第一次回查）
  
  ② 回查策略：递增间隔重试
     第 1 次：6s → 第 2 次：30s → 第 3 次：1min → ... → 最多 15 次
  
  ③ Producer 端要求：
     - checkLocalTransaction() 必须幂等（可能被多次调用）
     - 必须能准确判断本地事务的最终状态（查数据库，不要依赖内存状态）
     - 不能执行新的业务逻辑（只查询，不修改）
  
  ④ 为什么需要回查？
     - Producer 在执行本地事务时宕机 → 半消息永远卡在 HALF_TOPIC
     - Producer 发送 Commit/Rollback 时网络超时 → Broker 不确定状态
     - 回查是分布式事务"最终一致性"的兜底保障
```

**三、三大 MQ 事务消息对比**

| 维度 | RocketMQ | Kafka | RabbitMQ |
|------|----------|-------|----------|
| **事务实现** | 半消息 + 回查 | 事务 Coordinator + Transactional ID | 基于 AMQP 的 TX 协议（性能差） |
| **一致性** | 最终一致 | 精确一次（Exactly-Once） | 弱一致 |
| **回查机制** | ✅ Broker 主动回查 Producer | ✅ 通过 Transaction Coordinator 恢复 | ❌ 无回查 |
| **性能** | ⭐⭐⭐⭐ 高 | ⭐⭐⭐ 中（事务开销大） | ⭐⭐ 低 |
| **适用场景** | 电商订单、金融交易 | 流处理（消费-处理-生产） | 简单事务场景 |
| **实现复杂度** | ⭐⭐ 低（注解驱动） | ⭐⭐⭐ 中 | ⭐⭐⭐ 中 |

**四、顺序消息——全局顺序 vs 分区顺序**

RocketMQ 通过 **队列分区 + 消费队列绑定** 保证消息顺序。

```
顺序消息的实现原理：

  ① 全局顺序消息（单队列）：
     所有消息发送到同一个队列 → 一个消费者线程消费
     ✅ 严格全局有序
     ❌ 性能差（单队列瓶颈）

  ② 分区顺序消息（推荐）：
     同一业务 Key（如订单号）的消息发送到同一个队列
     → 每个队列内有序，不同队列间无序
     ✅ 局部有序 + 高性能
     
  生产者端：
  SendResult result = producer.send(
      message,
      new MessageQueueSelector() {
          @Override
          public MessageQueue select(List<MessageQueue> mqs, Message msg, Object arg) {
              Long orderId = (Long) arg;
              int index = (int) (orderId % mqs.size());  // 按订单号取模
              return mqs.get(index);  // 同一订单的消息进同一队列
          }
      },
      order.getOrderId()  // 业务 Key
  );
  
  消费者端：
  consumer.registerMessageListener(new MessageListenerOrderly() {
      @Override
      public ConsumeOrderlyStatus consumeMessage(List<MessageExt> msgs, ...) {
          // 同一队列的消息由同一个线程顺序消费
          for (MessageExt msg : msgs) {
              processOrder(msg);
          }
          return ConsumeOrderlyStatus.SUCCESS;
      }
  });
```

**五、消息积压——紧急处理方案**

```
消息积压的排查与处理流程：

  ① 快速定位原因：
     - 消费者宕机？→ 重启消费者
     - 消费速度跟不上生产速度？→ 扩容消费者
     - 消费逻辑变慢（如数据库慢查询）？→ 优化消费逻辑
     - 消费者线程阻塞（如死锁）？→ 排查线程栈

  ② 临时应急措施（紧急扩容）：
     - 增加消费者实例（Queue 数量限制了最大并发度）
     - 如果 Queue 数量不够 → 新建 Topic，扩容 Queue，部署新消费者
     - 临时跳过非关键消息（如日志、埋点）
     
  ③ 长期优化方案：
     - 消费逻辑异步化：耗时操作（如发邮件）异步处理
     - 批量消费：一次拉取多条消息，减少网络开销
     - 增加分区数：Queue 数量 ≥ Consumer 数量，充分利用并发
     - 监控告警：设置积压阈值告警（如积压 > 10 万条）

  ④ 极端情况处理：
     - 积压消息量巨大（亿级）→ 写临时程序批量迁移到新 Topic
     - 原消费者不变，新 Topic 用更多消费者快速消费
     - 消费完成后切回流
```

### 💡 延伸思考

1. **事务消息的回查会不会导致消息重复消费？** — 会。如果 Producer 本地事务已提交但 Commit 请求网络超时，Broker 回查后会再次确认提交，消息最终会被投递。但此时 Consumer 可能已经通过之前的重试消费过一次。所以 Consumer 端必须做幂等处理——这是分布式系统的基本要求。
2. **为什么 RocketMQ 事务消息不用 2PC？** — 2PC 是同步阻塞协议，协调者宕机会导致所有参与者阻塞。RocketMQ 用"半消息 + 回查"实现异步解耦，即使 Producer 宕机，Broker 也能通过回查最终确定状态，不会阻塞其他服务。

### 📖 参考答案

**一、从单体到微服务——事务的本质变化**

在单体架构中，一个 `@Transactional` 就能搞定 ACID。但微服务拆分后，一个下单流程可能涉及订单服务、库存服务、账户服务、支付服务——每个服务有自己的数据库，本地事务无法跨库。

```
分布式事务的核心矛盾：

  CAP 理论：分布式系统最多同时满足一致性(C)、可用性(A)、分区容错性(P)中的两个
  
  由于网络分区(P)不可避免，只能在 C 和 A 之间取舍：
  - CP 系统（强一致）：牺牲可用性，如 ZooKeeper
  - AP 系统（高可用）：牺牲强一致性，如 Eureka
  
  BASE 理论（对 CAP 的实践补充）：
  - Basically Available（基本可用）
  - Soft State（软状态/中间状态）
  - Eventually Consistent（最终一致）
  
  分布式事务的目标：在 AP 的基础上追求最终一致性
```

**二、Seata 四大模式全景对比**

Seata（Simple Extensible Autonomous Transaction Architecture）是阿里开源的分布式事务中间件，提供四种事务模式：

```
Seata 架构三大角色：

  ┌─────────────────────────────────────────────────────────┐
  │  TC（Transaction Coordinator）—— 事务协调器              │
  │  独立部署的 Server，维护全局事务状态，驱动提交/回滚       │
  ├─────────────────────────────────────────────────────────┤
  │  TM（Transaction Manager）—— 事务管理器                  │
  │  定义事务边界：@GlobalTransactional 标注的方法           │
  ├─────────────────────────────────────────────────────────┤
  │  RM（Resource Manager）—— 资源管理器                     │
  │  管理分支事务的资源（数据库连接），注册分支事务、上报状态  │
  └─────────────────────────────────────────────────────────┘
```

| 模式 | 一致性 | 性能 | 业务侵入 | 回滚方式 | 适用场景 |
|------|--------|------|---------|---------|---------|
| **AT** | 最终一致 | ⭐⭐⭐⭐ | ⭐ 极低（加注解即可） | 自动生成反向 SQL | 通用业务（订单、库存） |
| **TCC** | 最终一致 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ 高（需实现三接口） | 手动实现 Cancel | 高性能金融、支付 |
| **Saga** | 最终一致 | ⭐⭐⭐⭐ | ⭐⭐⭐ 中（需实现补偿） | 正向补偿 | 长事务、跨系统（老系统对接） |
| **XA** | 强一致 | ⭐⭐ | ⭐ 极低 | 数据库原生回滚 | 强一致性要求（极少用） |

**三、AT 模式——Seata 的默认模式，零侵入首选**

AT 模式是 Seata 最具创新性的模式，核心思想：**自动记录数据快照，自动生成反向 SQL 回滚**。

```
AT 模式两阶段流程：

  一阶段（执行 + 记录快照）：
  ① 拦截业务 SQL → 解析 SQL 语义（表名、条件、修改前后的值）
  ② 执行原始 SQL（如 UPDATE product SET stock = stock - 1 WHERE id = 100）
  ③ 将修改前后的数据快照保存到 undo_log 表
  ④ 注册分支事务到 TC
  
  二阶段（提交或回滚）：
  - 全局提交：异步删除 undo_log（轻量级，性能高）
  - 全局回滚：读取 undo_log 中的前镜像 → 生成反向 SQL → 执行回滚 → 删除 undo_log
```

```sql
-- undo_log 表结构（每个业务数据库都需要创建）
CREATE TABLE undo_log (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    branch_id BIGINT NOT NULL,        -- 分支事务 ID
    xid VARCHAR(100) NOT NULL,        -- 全局事务 ID
    context VARCHAR(128),             -- 序列化后的上下文
    rollback_info LONGBLOB,           -- 回滚信息（前后镜像数据）
    log_status INT NOT NULL,          -- 日志状态
    log_created DATETIME NOT NULL,
    log_modified DATETIME NOT NULL,
    UNIQUE KEY ux_undo_log (xid, branch_id)
);
```

```
AT 模式的核心设计：

  ① 前镜像（Before Image）：UPDATE 之前的数据快照
     例：UPDATE product SET stock=99 WHERE id=100
     → 前镜像：{id: 100, stock: 100}
  
  ② 后镜像（After Image）：UPDATE 之后的数据快照
     → 后镜像：{id: 100, stock: 99}
  
  ③ 回滚时：用前镜像生成反向 SQL
     → UPDATE product SET stock=100 WHERE id=100
  
  ④ 全局锁：一阶段提交时，对修改的数据行加全局锁
     → 防止其他事务在 AT 事务未完成时修改同一行数据
     → 全局锁在二阶段完成后释放
```

```java
// AT 模式使用——几乎零侵入
@Service
public class OrderService {
    
    @Autowired
    private OrderMapper orderMapper;
    @Autowired
    private InventoryFeignClient inventoryClient;
    
    @GlobalTransactional  // 只需要这一个注解！
    public void createOrder(Order order) {
        // ① 创建订单（本地事务）
        orderMapper.insert(order);
        
        // ② 扣减库存（远程调用，Seata 自动管理分布式事务）
        inventoryClient.deduct(order.getProductId(), order.getQuantity());
        
        // ③ 扣减余额（远程调用）
        accountClient.deduct(order.getUserId(), order.getAmount());
        
        // 任何一步失败 → Seata 自动回滚所有步骤
    }
}
```

**四、TCC 模式——高性能场景首选**

TCC（Try-Confirm-Cancel）是两阶段提交的业务层实现，需要开发者手动实现三个接口。

```
TCC 三阶段：

  Try（预留资源）：
  - 检查资源是否可用，预留资源（冻结，不真正扣减）
  - 例：冻结库存、冻结余额
  - 必须幂等！

  Confirm（确认提交）：
  - 真正执行业务操作
  - 例：真正扣减库存、真正扣减余额
  - 必须幂等！Try 成功则 Confirm 一定能成功

  Cancel（取消回滚）：
  - 释放 Try 阶段预留的资源
  - 例：解冻库存、解冻余额
  - 必须幂等！允许空回滚（Try 没执行时 Cancel 被调用）
```

```java
// TCC 模式实现示例——扣减库存
@Service
public class InventoryTccService {
    
    @Autowired
    private InventoryMapper inventoryMapper;
    
    /**
     * Try：冻结库存
     */
    public boolean tryDeduct(Long productId, int quantity) {
        // 检查库存是否充足
        Inventory inv = inventoryMapper.selectById(productId);
        if (inv.getAvailableStock() < quantity) {
            return false;  // 库存不足
        }
        // 冻结库存（available_stock 减少，frozen_stock 增加）
        int rows = inventoryMapper.freezeStock(productId, quantity);
        return rows > 0;
    }
    
    /**
     * Confirm：真正扣减
     */
    public boolean confirmDeduct(Long productId, int quantity) {
        // 将冻结库存转为已扣减
        int rows = inventoryMapper.confirmDeduct(productId, quantity);
        return rows > 0;
    }
    
    /**
     * Cancel：解冻库存
     */
    public boolean cancelDeduct(Long productId, int quantity) {
        // 释放冻结库存
        int rows = inventoryMapper.unfreezeStock(productId, quantity);
        return rows > 0;  // 允许空回滚（rows 可能为 0）
    }
}
```

**TCC 三大难题——空回滚、悬挂、幂等**：

```
① 空回滚（Empty Rollback）：
   Try 请求因网络超时未到达 → TC 发起 Cancel
   → Cancel 执行时发现没有可释放的资源
   解决：Cancel 方法允许 rows=0 的情况，不做异常处理

② 悬挂（Suspension）：
   Try 请求因网络拥塞延迟到达 → TC 超时发起 Cancel（先执行）
   → Cancel 执行后 Try 才到达 → 资源被"悬挂"（冻结了但事务已结束）
   解决：Cancel 执行时记录状态，Try 执行前检查是否已被 Cancel

③ 幂等：
   Confirm/Cancel 可能因网络重试被多次调用
   解决：通过事务 ID + 状态机保证同一操作只执行一次
```

**五、Saga 模式——长事务与异构系统**

Saga 适用于长事务（如跨天流程）和无法改造的老系统。

```
Saga 模式：

  正向流程：服务 A → 服务 B → 服务 C（依次执行）
  补偿流程：服务 C 补偿 → 服务 B 补偿 → 服务 A 补偿（逆序回滚）

  与 TCC 的区别：
  - TCC：先预留资源再确认（有冻结阶段）
  - Saga：直接执行，失败后补偿（没有冻结阶段）
  
  适用场景：
  ✅ 长事务（如审批流程跨天）
  ✅ 老系统对接（无法改造为 TCC）
  ✅ 跨公司/跨系统调用
  ❌ 不适合需要资源隔离的场景（如秒杀）
```

### 💡 延伸思考

1. **AT 模式的全局锁会不会成为性能瓶颈？** — 全局锁的持有时间很短（从一阶段提交到二阶段完成），默认超时 60 秒自动释放。在标准业务流程中，二阶段通常在毫秒级完成，所以全局锁的影响很小。但如果 TC 宕机导致二阶段长时间未执行，全局锁会阻塞其他事务——这就是为什么 TC 必须集群部署。
2. **AT 模式和 TCC 模式可以混用吗？** — 可以。Seata 支持在一个全局事务中混合使用不同模式。比如订单服务用 AT（简单），支付服务用 TCC（高性能）。这是 Seata 设计的灵活性所在。

### 📖 参考答案

**一、synchronized 为什么需要锁升级？——从重量级到自适应**

JDK 1.6 之前，synchronized 直接使用操作系统的互斥量（Mutex Lock）实现，每次加锁都需要从用户态切换到内核态，性能开销巨大。JDK 1.6 引入了锁升级机制，JVM 根据并发竞争程度动态调整锁的状态。

```
锁升级的核心思想：

  "大多数锁在大多数时间内都不存在竞争" —— 基于这个观察，
  JVM 不会一上来就用重量级锁，而是根据竞争情况逐步升级：
  
  无竞争 → 偏向锁（几乎零开销）
  轻竞争 → 轻量级锁（CAS 自旋）
  重竞争 → 重量级锁（OS 互斥，线程阻塞）
```

**二、对象头（Mark Word）——锁信息的载体**

synchronized 锁的是对象，所有锁状态都存储在对象头的 Mark Word 中。

```
Java 对象内存布局：

  ┌──────────────────────────────────────────────┐
  │              对象头（Object Header）           │
  │  ┌────────────────────┬────────────────────┐ │
  │  │   Mark Word (8B)   │  Klass Pointer (4B)│ │
  │  │   锁状态/GC信息     │   指向类元数据       │ │
  │  └────────────────────┴────────────────────┘ │
  ├──────────────────────────────────────────────┤
  │              实例数据（Instance Data）         │
  ├──────────────────────────────────────────────┤
  │              对齐填充（Padding）               │
  └──────────────────────────────────────────────┘

Mark Word 在不同锁状态下的存储内容（64 位 JVM）：

  | 锁状态   | 存储内容                                    | 锁标志位 |
  |---------|--------------------------------------------|---------|
  | 无锁     | 哈希码(31bit) + 分代年龄(4bit) + 偏向标志(1bit) | 01    |
  | 偏向锁   | 线程ID(54bit) + Epoch(2bit) + 分代年龄(4bit)  | 01    |
  | 轻量级锁 | 指向栈中锁记录(Lock Record)的指针(62bit)        | 00    |
  | 重量级锁 | 指向 ObjectMonitor 的指针(62bit)               | 10    |
  | GC标记   | 空                                          | 11    |
```

**三、锁升级完整流程——从无锁到重量级锁**

```
锁升级路线图（单向不可逆）：

  无锁 ──→ 偏向锁 ──→ 轻量级锁 ──→ 重量级锁
  (001)    (101)      (00)        (10)

  注意：JDK 15+ 默认禁用偏向锁，升级路径简化为：
  无锁 ──→ 轻量级锁 ──→ 重量级锁
```

### 阶段 1：偏向锁（Biased Locking）

```
偏向锁的核心思想：
  如果一个锁总是被同一个线程获取，那就让这个线程"永久"持有它，
  不需要任何同步操作——连 CAS 都不需要。

偏向锁获取流程：
  ① 检查 Mark Word 中的偏向锁标志是否为 1，锁标志位是否为 01
  ② 如果 Mark Word 中的 Thread ID 是当前线程 → 直接进入同步块（零开销！）
  ③ 如果 Thread ID 为空 → CAS 将当前线程 ID 写入 Mark Word
     - CAS 成功 → 获取偏向锁
     - CAS 失败 → 说明有竞争 → 撤销偏向锁 → 升级为轻量级锁
  ④ 如果 Thread ID 是其他线程 → 撤销偏向锁 → 升级为轻量级锁

偏向锁的撤销（开销较大，需要在 SafePoint 进行）：
  ① 等待全局安全点（所有线程暂停）
  ② 检查原持有偏向锁的线程是否还存活
  ③ 如果已退出同步块 → 偏向锁撤销为无锁状态
  ④ 如果还在同步块中 → 升级为轻量级锁
```

### 阶段 2：轻量级锁（Lightweight Locking）

```
轻量级锁的核心思想：
  假设竞争不激烈，线程不会长时间持有锁，
  等待的线程用 CAS 自旋（忙等待），不进入阻塞状态。

轻量级锁获取流程：
  ① 在当前线程的栈帧中创建 Lock Record（锁记录）
  ② 将对象头的 Mark Word 复制到 Lock Record 中（Displaced Mark Word）
  ③ CAS 尝试将对象头的 Mark Word 替换为指向 Lock Record 的指针
     - CAS 成功 → 获取轻量级锁
     - CAS 失败 → 自旋重试
  ④ 自旋超过一定次数（默认 10 次，或自适应）→ 膨胀为重量级锁

轻量级锁释放：
  ① CAS 将 Displaced Mark Word 写回对象头
  ② 成功 → 释放完成
  ③ 失败 → 说明已经膨胀为重量级锁 → 唤醒阻塞线程
```

### 阶段 3：重量级锁（Heavyweight Locking）

```
重量级锁的核心机制——ObjectMonitor：

  每个重量级锁对象关联一个 ObjectMonitor 对象（C++ 实现）：

  ┌─────────────────────────────────────────┐
  │            ObjectMonitor                │
  │                                         │
  │  _owner：当前持有锁的线程               │
  │  _EntryList：等待获取锁的线程队列       │
  │  _WaitSet：调用了 wait() 的线程队列     │
  │  _recursions：重入次数                  │
  └─────────────────────────────────────────┘

  线程状态流转：
  ① 竞争锁失败 → 进入 _EntryList → 线程阻塞（BLOCKED）
  ② 获取锁成功 → _owner = 当前线程
  ③ 调用 wait() → 进入 _WaitSet → 释放锁 → 线程等待（WAITING）
  ④ 调用 notify() → 从 _WaitSet 移到 _EntryList → 重新竞争锁
```

**四、批量重偏向与批量撤销**

JVM 对偏向锁有更精细的优化：

```
批量重偏向（Bulk Rebias）：
  当某个类的偏向锁撤销次数达到阈值（默认 20 次）
  → JVM 认为这个类的对象可能偏向错了线程
  → 允许将这些对象的偏向锁重新偏向到新线程
  → 减少撤销开销

批量撤销（Bulk Revocation）：
  当批量重偏向后，撤销次数继续增加达到更高阈值（默认 40 次）
  → JVM 认为这个类的对象不适合偏向锁
  → 将该类的所有对象的偏向锁全部撤销
  → 新创建的对象直接为无锁状态（不再启用偏向锁）

相关 JVM 参数：
  -XX:BiasedLockingStartupDelay=0      # 偏向锁启动延迟（默认 4 秒）
  -XX:BiasedLockingBulkRebiasThreshold=20   # 批量重偏向阈值
  -XX:BiasedLockingBulkRevokeThreshold=40   # 批量撤销阈值
```

**五、JDK 15+ 为什么默认禁用偏向锁？**

```
偏向锁被禁用的原因：

  ① 维护成本高：偏向锁的撤销需要在 SafePoint 进行（STW），
     在高并发场景下，频繁的撤销反而拖累性能

  ② 收益递减：现代应用大多使用线程池，锁的持有者频繁切换，
     "总是同一个线程获取锁"的场景越来越少

  ③ 硬件进步：CAS 操作的性能已经很高，偏向锁省下的 CAS 开销
     在现代 CPU 上几乎可以忽略

  ④ 简化实现：去掉偏向锁让 JVM 的锁逻辑更简单、更可预测

  结论：JDK 15+ 默认 -XX:-UseBiasedLocking
```

| 维度 | synchronized | ReentrantLock |
|------|-------------|---------------|
| **实现** | JVM 内置，关键字 | JDK 类库（AQS） |
| **锁获取** | 隐式（进入/退出同步块） | 显式（lock()/unlock()） |
| **可中断** | ❌ 不可中断 | ✅ lockInterruptibly() |

### 💡 延伸思考

1. **轻量级锁的自旋为什么不能一直持续？** — 自旋会消耗 CPU 时间。如果锁被长时间持有，自旋的线程白白浪费 CPU。自适应自旋会根据上一次自旋的结果动态调整：如果上次自旋成功获取了锁，这次就多自旋一会儿；如果上次自旋失败，这次就少自旋或直接阻塞。
2. **synchronized 在虚拟线程中的 pinning 问题有多严重？** — 非常严重。虚拟线程在 synchronized 块内阻塞时无法 unmount，会"钉住"载体线程。如果一个载体线程被钉住，它就无法执行其他虚拟线程，导致整个虚拟线程调度器退化。所以 Oracle 强烈建议在虚拟线程环境中用 ReentrantLock 替代 synchronized。

```
  - 无记忆：每次对话独立，不记得之前说过什么
  - 无行动：只能生成文本，不能操作外部系统
  - 单轮：一问一答，不会主动追问或拆解任务
  
  Agent（智能体）：
  - 主动执行：用户给目标，Agent 自主完成全过程
  - 有记忆：短期上下文 + 长期知识存储
  - 能行动：调用工具（搜索、写代码、操作数据库、发邮件）
  - 多轮循环：感知→决策→行动→反思，循环直到任务完成

  一句话概括：Chatbot 是"你问我答"，Agent 是"你给目标，我搞定全过程"
```

**二、ReAct 是什么？——Agent 的核心工作模式**

ReAct（Reasoning + Acting）由 Google Research 与普林斯顿大学在 2022 年提出，是 AI Agent 最经典的执行框架。核心思想：**推理和行动必须交替进行，互相校正**。

```
ReAct 循环：Thought → Action → Observation → Thought → ...

  ┌─────────────────────────────────────────────────────────┐
  │                     ReAct Loop                          │
  │                                                         │
  │  用户输入："帮我查一下北京今天的天气，如果下雨就提醒我带伞" │
  │                                                         │
  │  ┌──────────────────────────────────────────────┐       │
  │  │ Thought 1：用户想知道北京天气，我需要先查询     │       │
  │  │ Action 1：调用 weather_api("北京")            │       │
  │  │ Observation 1：北京今天多云转小雨，15-22°C     │       │
  │  ├──────────────────────────────────────────────┤       │
  │  │ Thought 2：天气有小雨，需要提醒用户带伞         │       │
  │  │ Action 2：无需额外工具调用，直接生成回复        │       │
  │  │ Final Answer："北京今天多云转小雨，15-22°C，    │       │
  │  │               记得带伞哦！☂️"                   │       │
  │  └──────────────────────────────────────────────┘       │
  └─────────────────────────────────────────────────────────┘
```

**三、为什么必须保留 Thought？——直接输出 Tool Call JSON 的致命缺陷**

这是字节跳动 2026 年面试的高频追问。

```
面试官：为什么不能直接让 LLM 输出 Tool Call JSON，去掉 Thought？
        这样不是更快、更省 Token 吗？

致命缺陷：

  ① 缺乏推理验证——LLM 可能选错工具
     用户："帮我取消最近的一笔订单"
     没有 Thought：LLM 直接调用 cancelOrder()，但参数填什么？最近是哪笔？
     有 Thought："用户要取消最近订单，我需要先查订单列表，找到最近的一笔，
                确认状态可取消，再执行取消操作"
     → Thought 让 LLM 先理清逻辑，再精准调用工具

  ② 无法处理工具调用失败
     没有 Thought：工具返回错误 → LLM 不知道下一步怎么办
     有 Thought："查询订单失败，可能是订单号不对。
                 让我换个方式，用用户 ID 查询最近的订单"
     → Thought 让 Agent 具备自我纠错能力

  ③ 多步任务无法串联
     用户："帮我订一张明天去上海的机票，然后发邮件给张经理"
     没有 Thought：LLM 可能同时输出两个 Tool Call，但订票结果未知时无法写邮件
     有 Thought："先查航班 → 确认有票 → 订票 → 拿到航班号 → 写邮件"
     → Thought 让 Agent 按正确顺序执行多步任务

  ④ 幻觉无法被自我发现
     没有 Thought：LLM 可能编造一个工具名直接调用 → 报错 → 用户困惑
     有 Thought："我需要查询天气，应该用 weather_api 工具。
                 让我检查一下是否有这个工具..."
     → Thought 让 Agent 在行动前自我审查
```

**四、ReAct vs CoT vs 纯 Action——实验对比**

Google 的原始论文通过实验证明了三者的差异：

```
实验对比（HotpotQA 和 Fever 数据集）：

  ┌──────────────┬──────────┬──────────┐
  │    方法       │ 准确率    │ 幻觉率    │
  ├──────────────┼──────────┼──────────┤
  │ 纯 CoT       │  33%     │  高      │
  │ （只推理不动手）│          │ （编造事实）│
  ├──────────────┼──────────┼──────────┤
  │ 纯 Action    │  25%     │  高      │
  │ （只动手不推理）│          │ （迷失方向）│
  ├──────────────┼──────────┼──────────┤
  │ ReAct        │  35%     │  低      │
  │ （推理+行动）  │          │ （有据可查）│
  └──────────────┴──────────┴──────────┘

  结论：
  - 纯 CoT：在自己的"内心独白"里打转，无法获取外部信息，容易编造
  - 纯 Action：缺乏对任务目标的整体把握，容易迷失方向
  - ReAct：推理和行动交替推进、互相校正，准确率最高
```

**五、ReAct 的工程实现**

```java
// ReAct Agent 的 Java 实现（基于 Spring AI）
@Service
public class ReActAgent {
    
    @Autowired
    private ChatClient chatClient;
    
    private static final int MAX_ITERATIONS = 10;  // 防止无限循环
    
    public String execute(String userGoal) {
        StringBuilder context = new StringBuilder();
        context.append("目标：").append(userGoal).append("\n\n");
        
        for (int i = 0; i < MAX_ITERATIONS; i++) {
            // 构建 ReAct Prompt
            String prompt = buildReActPrompt(context.toString());
            
            // 调用 LLM 获取 Thought + Action
            String response = chatClient.prompt()
                .user(prompt)
                .call()
                .content();
            
            // 解析 LLM 输出
            ReActOutput output = parseReActOutput(response);
            
            // 记录 Thought
            context.append("Thought: ").append(output.getThought()).append("\n");
            
            // 如果是最终答案
            if (output.isFinalAnswer()) {
                return output.getFinalAnswer();
            }
            
            // 执行 Action
            context.append("Action: ").append(output.getAction()).append("\n");
            String observation = executeAction(output.getAction(), output.getActionInput());
            context.append("Observation: ").append(observation).append("\n\n");
        }
        
        return "任务超过最大执行步数，未能完成。";
    }
    
    private String buildReActPrompt(String context) {
        return """
            你是一个 AI Agent，使用 ReAct 模式完成任务。
            
            可用工具：
            - search(query)：搜索互联网信息
            - calculate(expression)：执行数学计算
            - get_weather(city)：查询天气
            
            请按以下格式回复：
            Thought: [你对当前情况的推理分析]
            Action: [要调用的工具名称]
            Action Input: [工具的输入参数]
            
            或者如果任务已完成：
            Thought: [最终推理]
            Final Answer: [最终答案]
            
            当前上下文：
            %s
            """.formatted(context);
    }
}
```

**六、ReAct 的局限性——2026 年的新进展**

```
ReAct 的局限：

  ① 上下文爆炸：每轮 Thought/Action/Observation 都追加到上下文，
     长任务会超出 LLM 的 Context Window
     → 解决方案：上下文压缩、摘要中间步骤

  ② 过早停止：Agent 可能"自认为"完成了任务，实际结果有缺陷
     → 解决方案：增加自我验证步骤、设置明确的任务完成标准

  ③ 单次提示脆弱：复杂任务无法通过一次提示完成
     → 解决方案：Ralph Loop（强制持续迭代直到满足条件）

  ④ 缺乏规划：ReAct 是"走一步看一步"，没有全局规划
     → 解决方案：Plan-and-Execute（先规划再执行）
```

### 💡 延伸思考

1. **ReAct 和 Function Calling 是什么关系？** — Function Calling 是 ReAct 中 Action 环节的具体实现方式。ReAct 定义了"推理→行动→观察"的循环框架，Function Calling 负责"行动"环节——LLM 输出结构化的工具调用请求，框架执行并返回结果。ReAct 是上层设计模式，Function Calling 是底层实现机制。
2. **2026 年 ReAct 还够用吗？** — 基础 ReAct 仍然是入门必学，但生产级 Agent 需要更多优化：Ralph Loop（强制迭代）、Plan-and-Execute（先规划后执行）、Self-Reflection（自我评估）、Multi-Agent（多 Agent 协作）。面试时提到这些进阶模式会是加分项。

```
Advisor 机制：

  ┌─────────────────────────────────────────────────────────┐

  │  用户请求 → [记忆Advisor] → [RAG Advisor] → [安全Advisor] → LLM
```

```java
// Advisor 配置——声明式组合 AI 能力
@Configuration
public class AiConfig {
    
    @Bean
    public ChatClient chatClient(ChatModel chatModel, VectorStore vectorStore) {
        return ChatClient.builder(chatModel)
            .defaultAdvisors(
                new MessageChatMemoryAdvisor(new InMemoryChatMemory()),  // 对话记忆
                new QuestionAnswerAdvisor(vectorStore),                  // RAG 检索
                new SafeGuardAdvisor()                                   // 安全审核
            )
            .build();
    }
}

// 使用——业务代码完全无感知
@GetMapping("/ask")
public String ask(@RequestParam String question) {
```
