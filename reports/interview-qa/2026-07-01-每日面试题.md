## 题目 1：[Java并发/线程池] 请详细说明 ThreadPoolExecutor 的七大核心参数、执行流程及拒绝策略，并结合 JUC 锁机制分析生产环境中的线程池配置策略

**相关岗位**：Java后端 / 基础架构 / 全栈

### 📖 参考答案

#### 一、ThreadPoolExecutor 七大核心参数

```java
public ThreadPoolExecutor(
    int corePoolSize,          // ① 核心线程数——长期维持的最小线程数
    int maximumPoolSize,       // ② 最大线程数——线程池允许创建的最大线程数
    long keepAliveTime,        // ③ 空闲线程存活时间——超出核心线程数的空闲线程最大存活时间
    TimeUnit unit,             // ④ 时间单位——keepAliveTime 的时间单位
    BlockingQueue<Runnable> workQueue,  // ⑤ 任务队列——存放等待执行的任务
    ThreadFactory threadFactory,        // ⑥ 线程工厂——创建新线程的工厂
    RejectedExecutionHandler handler    // ⑦ 拒绝策略——任务无法执行时的处理方式
)
```

| 参数 | 说明 | 最佳实践 |
|------|------|---------|
| **corePoolSize** | 常备线程数，即使空闲也不回收（除非设置 allowCoreThreadTimeOut=true） | CPU 密集型：CPU 核数；IO 密集型：2×CPU 核数或更高 |
| **maximumPoolSize** | 线程池能容纳的最大线程数 | 一般不超过 corePoolSize 的 2-4 倍 |
| **keepAliveTime** | 超出 corePoolSize 的空闲线程存活时间 | 默认 60s，短任务可设为 30s |
| **workQueue** | 存放等待执行的任务 | 见下方队列选择策略 |
| **threadFactory** | 创建线程的工厂 | 必须设置有意义的名字（便于排查） |
| **handler** | 拒绝策略 | 根据业务场景选择 |

#### 二、线程池执行流程（核心考点！）

```
提交新任务时，ThreadPoolExecutor 的执行顺序：

① 当前线程数 < corePoolSize？
   ├─ 是 → 创建新核心线程执行任务
   └─ 否 → 进入步骤②

② 任务队列 workQueue 未满？
   ├─ 是 → 将任务放入队列等待
   └─ 否 → 进入步骤③

③ 当前线程数 < maximumPoolSize？
   ├─ 是 → 创建新非核心线程执行任务
   └─ 否 → 执行拒绝策略 handler.rejectedExecution()

注意：核心线程不是"先创建完再排队的"！
corePoolSize 是"当有新任务且线程数不足时创建新线程"的门槛。
```

#### 三、四大拒绝策略

| 拒绝策略 | 行为 | 适用场景 |
|---------|------|---------|
| **AbortPolicy**（默认） | 抛出 RejectedExecutionException | 必须处理的非降级任务 |
| **CallerRunsPolicy** | 由提交任务的线程自己执行 | 降级兜底，减缓提交速度 |
| **DiscardPolicy** | 直接丢弃，不抛异常 | 可丢弃的非关键任务 |
| **DiscardOldestPolicy** | 丢弃队列中最旧的任务，重试提交 | 实时性要求高的场景 |

#### 四、任务队列的选择

| 队列类型 | 特点 | 适用场景 |
|---------|------|---------|
| **SynchronousQueue** | 不存储任务，直接转交线程 | CachedThreadPool 适用，大并发时易创建大量线程 |
| **LinkedBlockingQueue** | 无界队列（默认 Integer.MAX_VALUE） | FixedThreadPool 适用，但队列堆积可能 OOM |
| **ArrayBlockingQueue** | 有界队列，容量固定 | 推荐！防止任务堆积导致 OOM |
| **PriorityBlockingQueue** | 优先级队列，任务按优先级执行 | 有优先级需求的场景 |

#### 五、生产环境线程池配置策略

**CPU 密集型任务**（计算密集）：
```java
// CPU 核数 = Runtime.getRuntime().availableProcessors()
int cpuCores = Runtime.getRuntime().availableProcessors();
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    cpuCores,           // corePoolSize = CPU 核数
    cpuCores,           // maximumPoolSize = CPU 核数（避免线程切换开销）
    0L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(1000),  // 有界队列
    new NamedThreadFactory("compute-worker"),
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

**IO 密集型任务**（数据库查询、HTTP 调用、文件读写）：
```java
// IO 密集型：线程数可设为 CPU 核数的 2-4 倍
// 公式：线程数 = CPU核数 × (1 + 等待时间/计算时间)
int cpuCores = Runtime.getRuntime().availableProcessors();
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    cpuCores * 2,       // corePoolSize
    cpuCores * 4,       // maximumPoolSize
    60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(500),  // 有界队列防 OOM
    new NamedThreadFactory("io-worker"),
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

**为什么不建议用 Executors 创建线程池？**

| Executors 方法 | 问题 | 风险 |
|---------------|------|------|
| `Executors.newFixedThreadPool` | 使用无界 LinkedBlockingQueue | 任务堆积导致 OOM |
| `Executors.newCachedThreadPool` | maximumPoolSize 为 Integer.MAX_VALUE | 创建过多线程导致 OOM |
| `Executors.newScheduledThreadPool` | 同上 | 同上 |

#### 六、JUC 锁机制与线程池的配合

线程池中处理共享资源时，需要 JUC 锁来保证线程安全：

```java
// 推荐使用 ReentrantLock（可中断、可超时、可公平）
public class ThreadPoolTaskProcessor {
    
    private final ReentrantLock lock = new ReentrantLock();
    private final Map<String, TaskResult> resultCache = new ConcurrentHashMap<>();
    
    public TaskResult processTask(String taskId) {
        // 先检查缓存（无锁）
        TaskResult cached = resultCache.get(taskId);
        if (cached != null) return cached;
        
        // 加锁处理临界区
        lock.lock();
        try {
            // 双重检查
            cached = resultCache.get(taskId);
            if (cached != null) return cached;
            
            // 执行实际任务
            TaskResult result = doHeavyWork(taskId);
            resultCache.put(taskId, result);
            return result;
        } finally {
            lock.unlock();
        }
    }
    
    // 使用 CompletableFuture 编排线程池任务
    public CompletableFuture<List<TaskResult>> batchProcess(List<String> taskIds) {
        List<CompletableFuture<TaskResult>> futures = taskIds.stream()
            .map(id -> CompletableFuture.supplyAsync(
                () -> processTask(id), 
                threadPoolExecutor
            ))
            .collect(Collectors.toList());
        
        return CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]))
            .thenApply(v -> futures.stream()
                .map(CompletableFuture::join)
                .collect(Collectors.toList()));
    }
}
```

#### 二、EXPLAIN 执行计划分析（面试必考！）

**EXPLAIN 的核心输出列：**

| 列名 | 含义 | 关键值 |
|------|------|--------|
| **type** | 扫描方式（最重要！） | system > const > eq_ref > ref > range > index > **ALL** |
| **possible_keys** | 可能用到的索引 | 与实际使用的 key 对比 |
| **key** | 实际使用的索引 | 为 NULL 表示没走索引 |
| **key_len** | 索引使用的字节数 | 联合索引中用了几个字段 |
| **rows** | 预估扫描行数 | 越小越好 |
| **Extra** | 额外信息 | Using index（覆盖索引）、Using filesort（需优化）、Using temporary |

**type 扫描方式详解（从优到劣）：**

```
const        → 主键或唯一索引查一行，速度最快
eq_ref       → 唯一索引关联查询，多表 JOIN 时最优
ref          → 非唯一索引等值查询，常见于普通索引
range        → 索引范围扫描（>、<、BETWEEN、IN）
index        → 全索引扫描（遍历整个索引树）
ALL          → 全表扫描（⚠️ 必须优化！）
```

**Extra 高频信号：**

| Extra 信息 | 含义 | 优化方向 |
|-----------|------|---------|
| Using index | 覆盖索引，不回表 | ✅ 理想状态 |
| Using where | 先扫索引再过滤 | 检查能否优化索引 |
| **Using filesort** | 文件排序（磁盘） | ❌ 必须在索引中包含 ORDER BY 字段 |
| **Using temporary** | 使用临时表 | ❌ 通常是 GROUP BY 或 DISTINCT 没走索引 |
| Using index condition | 索引下推 | ✅ 5.6+ 优化特性 |

#### 三、常见索引失效场景（7 大场景）

| 场景 | 错误写法 | 正确写法 | 失效原因 |
|------|---------|---------|---------|
| **① 函数操作** | `WHERE UPPER(name) = 'ABC'` | `WHERE name = 'ABC'` | 索引存的是原始值，函数破坏有序性 |
| **② 隐式类型转换** | `WHERE phone = 13800138000` | `WHERE phone = '13800138000'` | phone 是 varchar，数字比较触发隐式转换 |
| **③ LIKE 左模糊** | `WHERE name LIKE '%张三'` | `WHERE name LIKE '张三%'` | 无法确定前缀，B+树无法定位 |
| **④ OR 连接不同索引列** | `WHERE age=20 OR phone='138'` | 拆分为 UNION 或建联合索引 | OR 两边索引列不同，优化器放弃 |
| **⑤ 违反最左前缀** | 索引(a,b,c) 但 `WHERE b=1 AND c=2` | 补上 a 条件 | 缺最左列，无法定位起始位置 |
| **⑥ 不等于/ NOT IN** | `WHERE status != 'ACTIVE'` | 业务逻辑改写 | 不等值无法利用索引有序性 |
| **⑦ 数据量太小** | 100 条数据走全表扫描 | 无（优化器判断正确） | 优化器认为全表扫描更快 |

#### 四、慢 SQL 优化实战流程

**优化链路（面试回答模板）：**

```
Step 1：定位慢 SQL
   开启慢查询日志 → 找到具体 SQL → 记录执行时间和扫描行数

Step 2：EXPLAIN 分析
   查看 type → 是 ALL 或 index 则需要优化
   查看 Extra → 有 Using filesort / Using temporary 则需要优化
   查看 key → 是否为 NULL（完全没走索引）

Step 3：索引优化
   检查是否违反最左前缀原则
   检查 WHERE 条件字段是否有索引
   检查 ORDER BY 字段是否在索引中
   考虑覆盖索引（减少回表）

Step 4：SQL 改写
   避免函数操作、隐式类型转换、LIKE 左模糊
   大 IN 查询拆分为分批查询
   OR 改写为 UNION

Step 5：架构优化
   读写分离（主库写、从库读）
   分库分表（数据量超过千万级）
   引入缓存（Redis 缓存热点数据）
```

## 题目 3：[Java集合/并发] ConcurrentHashMap 是 Java 面试必考点，请详细对比 JDK 1.7 的 Segment 分段锁与 JDK 1.8 的 CAS + synchronized 实现，并说明为什么 JDK 1.8 要放弃分段锁

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-01 早间报告 — "ConcurrentHashMap/HashMap 安全标注：JDK1.7分段锁 vs JDK1.8 CAS+synchronized" + "HashMap 多线程死循环（1.7遗留）" + "JUC 锁机制"
**相关岗位**：Java后端 / 基础架构

### 📖 参考答案

#### 一、JDK 1.7 ConcurrentHashMap：Segment 分段锁

**数据结构：**

```
ConcurrentHashMap (JDK 1.7)
┌─────────────────────────────────────────────┐
│               Segment[] 数组                   │
│  ┌──────────┐ ┌──────────┐     ┌──────────┐  │
│  │Segment[0]│ │Segment[1]│ ... │Segment[15]│ │  ← 默认 16 个 Segment
│  └────┬─────┘ └────┬─────┘     └────┬─────┘  │
│       │             │               │         │
│  ┌────▼────┐  ┌────▼────┐     ┌────▼────┐   │
│  │HashEntry│  │HashEntry│     │HashEntry│    │
│  │[] table │  │[] table │     │[] table │    │
│  └─────────┘  └─────────┘     └─────────┘   │
└─────────────────────────────────────────────┘
```

**核心原理：**

```
每个 Segment 继承自 ReentrantLock
put 时：定位到 Segment → 对 Segment 加锁 → 在 Segment 内部操作
get 时：定位到 Segment → 直接读（不加锁，靠 volatile 保证可见性）

并发度：默认 16（Segment 数量初始化后不可变）
        最多支持 16 个线程同时写入不同 Segment
```

**put 流程：**

```java
// JDK 1.7 伪代码
public V put(K key, V value) {
    int hash = hash(key);
    Segment<K,V> segment = segments[hash & segmentMask];
    return segment.put(key, hash, value, false);
}

// Segment.put()
final V put(K key, int hash, V value, boolean onlyIfAbsent) {
    // 加锁（ReentrantLock）
    segment.lock();
    try {
        // 在 Segment 内部的 HashEntry[] 中操作
        // 与 HashMap 1.7 相同：数组 + 链表（头插法）
        // 扩容：Segment 内部扩容，不影响其他 Segment
    } finally {
        segment.unlock();
    }
}
```

**优点与缺点：**

| 维度 | 分析 |
|------|------|
| ✅ 优点 | 不同 Segment 可并发访问，提升吞吐量；一个 Segment 扩容不影响其他 |
| ❌ 缺点 | 并发度固定为 Segment 数量（默认 16），无法随 CPU 核数增加而提升；锁粒度仍不够细（一个 Segment 内所有操作互斥）；get 操作无锁但弱一致性；Segment 数量初始化后不可变 |

#### 二、JDK 1.8 ConcurrentHashMap：CAS + synchronized

**数据结构：**

```
ConcurrentHashMap (JDK 1.8)
┌──────────────────────────────────────────────┐
│              Node[] table（桶数组）              │
│ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐    │
│ │  │ │  │ │  │ │  │ │  │ │  │ │  │ │  │ ... │
│ └▲─┘ └──┘ └▲─┘ └──┘ └──┘ └──┘ └▲─┘ └──┘    │
│  │          │                   │             │
│ Node        Node                TreeNode     │
│ (链表)       (链表)              (红黑树)      │
└──────────────────────────────────────────────┘
```

**核心原理：**

```
put 流程：
  ① 计算 hash，定位桶位置
  ② 桶为空 → CAS 无锁插入
  ③ 桶非空 → synchronized 锁住桶的头节点
  ④ 链表长度 > 8 → 转为红黑树（优化查询性能）

get 流程：
  完全无锁（Node 的 val 和 next 用 volatile 保证可见性）
  直接定位桶 → 遍历链表/红黑树查找

扩容：
  多线程协助扩容（transfer 方法）
  每个线程负责一部分桶的迁移
```

**JDK 1.8 关键代码逻辑：**

```java
// JDK 1.8 put 流程（简化伪代码）
final V putVal(K key, V value, boolean onlyIfAbsent) {
    int hash = spread(key.hashCode());
    
    for (Node<K,V>[] tab = table;;) {
        int n = tab.length;
        int i = (n - 1) & hash;
        Node<K,V> f = tabAt(tab, i);  // 获取桶头节点
        
        if (f == null) {
            // ① 桶为空 → CAS 无锁插入
            if (casTabAt(tab, i, null, new Node<K,V>(hash, key, value))) {
                break;
            }
        } else if (f.hash == MOVED) {
            // ② 正在扩容 → 协助迁移
            tab = helpTransfer(tab, f);
        } else {
            // ③ 桶非空 → synchronized 锁头节点
            synchronized (f) {
                // 在链表或红黑树中插入
                if (binCount >= TREEIFY_THRESHOLD) {
                    treeifyBin(tab, i);  // 链表转红黑树
                }
            }
        }
    }
}
```

#### 三、核心对比：JDK 1.7 vs JDK 1.8

| 对比维度 | JDK 1.7（分段锁） | JDK 1.8（CAS + synchronized） |
|---------|------------------|------------------------------|
| **数据结构** | Segment[] + HashEntry[] | Node[] + 链表/红黑树 |
| **锁机制** | ReentrantLock（锁 Segment） | CAS（无锁）+ synchronized（锁桶头） |
| **锁粒度** | 锁一个 Segment（含多个桶） | 锁一个桶（单链表/红黑树） |
| **并发度** | 固定 16（Segment 数量） | 动态（等于桶数组长度） |
| **扩容** | Segment 内独立扩容 | 多线程协助扩容 |
| **查询优化** | 仅链表 | 链表（≤8）→ 红黑树（>8） |
| **get 操作** | 无锁（弱一致性） | 无锁（弱一致性，但更优） |
| **内存占用** | 较高（两层结构） | 较低（单层结构） |

#### 四、为什么 JDK 1.8 要放弃分段锁？

```
核心原因（面试必答）：

① 锁粒度更细——从 Segment 级别（默认 16 个锁）
   细化到每个桶级别（桶数量 = 数组长度，可动态扩容）
   并发度从固定 16 提升到数万级别

② synchronized 已经优化
   JDK 1.6 之后 synchronized 引入了偏向锁、轻量级锁、重量级锁的自适应升级
   在低竞争场景下，synchronized 的开销已经低于 ReentrantLock
   且 synchronized 是 JVM 原生支持的，无需用户态→内核态切换

③ CAS 无锁插入
   当桶为空时，使用 CAS 无锁插入，完全避免锁竞争
   这是分段锁无法做到的（分段锁必须加锁才能操作）

④ 红黑树优化
   当链表长度超过 8 时转为红黑树
   查询复杂度从 O(n) 降为 O(log n)
   解决了哈希碰撞攻击导致的性能退化问题
```

## 题目 4：[框架/Spring] Spring 循环依赖是 Java 面试必问的压轴题，请详细说明 Spring 三级缓存解决循环依赖的原理，以及为什么构造方法注入的循环依赖无法解决

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-01 午间报告 — "Spring框架：循环依赖、Bean生命周期、AOP代理" + "2026年高频面试题，聚焦线上故障排查"
**相关岗位**：Java后端 / 基础架构 / 全栈

### 📖 参考答案

#### 一、什么是循环依赖？

```java
@Service
public class AService {
    @Autowired
    private BService bService;  // A 依赖 B
}

@Service
public class BService {
    @Autowired
    private AService aService;  // B 依赖 A
}
```

```
A 的创建需要 B → 创建 B 需要 A → 无限递归 → BeanCurrentlyInCreationException
```

**Spring 三级缓存仅能解决：**
- ✅ 单例（Singleton）Bean
- ✅ Setter/字段注入（@Autowired）
- ✅ 循环依赖链（A→B→A 或 A→B→C→A）

**无法解决的场景：**
- ❌ 构造方法注入（实例化阶段就必须完成，三级缓存尚未建立）
- ❌ 多例（Prototype）Bean（不进入缓存）
- ❌ 部分工厂方法 / @Lookup 动态依赖

#### 二、三级缓存的结构

Spring 在 `DefaultSingletonBeanRegistry` 中维护了三层缓存：

```java
/** 一级缓存：成品库——存储完全初始化好的单例 Bean */
Map<String, Object> singletonObjects = new ConcurrentHashMap<>(256);

/** 二级缓存：半成品库——存储已实例化但尚未完成属性注入的 Bean（原始对象） */
Map<String, Object> earlySingletonObjects = new ConcurrentHashMap<>(16);

/** 三级缓存：工厂库——存储创建 Bean 的 ObjectFactory，用于生成提前曝光的对象 */
Map<String, ObjectFactory<?>> singletonFactories = new HashMap<>(16);
```

| 缓存级别 | 名称 | 存储内容 | 用途 |
|---------|------|---------|------|
| **一级** | singletonObjects | 完全初始化好的成品 Bean | 最终对外暴露 |
| **二级** | earlySingletonObjects | 已实例化但未完成初始化的半成品 | 提前暴露给依赖方 |
| **三级** | singletonFactories | ObjectFactory 工厂 | 生成代理对象（AOP 关键） |

#### 三、三级缓存解决循环依赖的完整流程

以 AService 和 BService 互相依赖为例：

```
Step 1：创建 AService
  ① 实例化 AService（调用构造方法，生成原始对象）
  ② 将 AService 的 ObjectFactory 放入三级缓存
     singletonFactories["aService"] = () -> getEarlyBeanReference("aService", ...)
     → 这一步是关键！提前暴露"半成品"的工厂

Step 2：填充 AService 的属性（发现依赖 BService）
  ③ 发现 AService 需要注入 BService
  ④ 去缓存中查找 BService：一级→二级→三级，都没找到
  ⑤ 开始创建 BService

Step 3：创建 BService
  ⑥ 实例化 BService（生成原始对象）
  ⑦ 将 BService 的 ObjectFactory 放入三级缓存
     singletonFactories["bService"] = () -> getEarlyBeanReference(...)

Step 4：填充 BService 的属性（发现依赖 AService）
  ⑧ 发现 BService 需要注入 AService
  ⑨ 去缓存中查找 AService：
     一级 → 没有（AService 还没完成初始化）
     二级 → 没有（还没从三级提升到二级）
     三级 → 找到了！singletonFactories["aService"]
  ⑩ 执行 ObjectFactory，获取 AService 的"提前引用"
     ⚠️ 如果有 AOP，这里会生成 AService 的代理对象！
  ⑪ 将提前引用放入二级缓存（earlySingletonObjects）
  ⑫ 从三级缓存中移除 ObjectFactory

Step 5：完成 BService 的初始化
  ⑬ 将 AService 的提前引用注入 BService 的 aService 属性
  ⑭ 完成 BService 的其他初始化（BeanPostProcessor 等）
  ⑮ 将成品 BService 放入一级缓存（singletonObjects）
  ⑯ 从二级/三级缓存中移除 BService

Step 6：回到 AService
  ⑰ AService 拿到已经创建好的 BService，注入 bService 属性
  ⑱ 完成 AService 的其他初始化
  ⑲ 将成品 AService 放入一级缓存（singletonObjects）
  ⑳ 从二级/三级缓存中移除 AService
```

#### 四、为什么必须三级缓存？两级不行吗？

**这是面试中最常被追问的问题！**

```
回答思路：

如果只要解决循环依赖，两级缓存就够了：
  一级 → 存放成品 Bean
  二级 → 存放提前曝光的半成品对象

但三级缓存的存在是为了解决一个关键问题：
  AOP 代理！

流程分析（有 AOP 的情况）：

假设 AService 被 @Transactional 或 @Async 标记，
Spring 需要在初始化最后一步通过 BeanPostProcessor 创建 AOP 代理。

如果只有两级缓存：
  BService 拿到的 AService 引用是原始对象（不是 AOP 代理）
  当 AService 最终生成代理对象后，BService 持有的还是原始对象
  → 代理失效！事务/异步等功能无法正常工作！

三级缓存的解决方案：
  singletonFactories 中存储的是 ObjectFactory
  该工厂在 getEarlyBeanReference() 中判断：
    - 如果 Bean 需要 AOP → 返回代理对象
    - 如果不需要 AOP → 返回原始对象

  BService 从三级缓存获取时，就直接拿到了 AOP 代理对象
  后续 AService 完成初始化后，Spring 发现代理已生成，直接使用该代理
  → 对象一致性保证！

一句话总结：
  二级缓存解决循环依赖问题
  三级缓存解决「循环依赖 + AOP 代理」的对象一致性问题
```

#### 五、为什么构造方法注入无法解决？

```java
@Service
public class AService {
    private final BService bService;
    
    // 构造方法注入
    public AService(BService bService) {  // ← 实例化阶段就需要 B
        this.bService = bService;
    }
}
```

```
原因：

Spring Bean 创建分为两个阶段：
  ① 实例化（调用构造方法）→ 生成原始对象
  ② 初始化（属性注入、BeanPostProcessor）

三级缓存的时机：
  实例化完成后 → 放入三级缓存

构造方法注入的问题：
  实例化阶段就需要注入依赖 → 此时三级缓存尚未建立
  → 无法提前暴露半成品 → 循环依赖无法打破

解决方案：
  改用 @Autowired（字段注入）或 Setter 注入
  或者使用 @Lazy 延迟加载
```

#### 二、Nacos 配置动态刷新的核心机制

**整体架构：**

```
┌─────────────────────────────────────────────┐
│               Nacos Server                    │
│  配置存储 → 配置变更 → 推送通知                │

│       ↓                                       │
│  @RefreshScope Bean 被销毁并重新创建            │
└─────────────────────────────────────────────┘
```

**关键流程：**

```
① 客户端启动时：
   NacosConfigService 发起 HTTP 长轮询（Long Polling）
   请求配置内容，并注册监听器

② 配置变更时（Nacos Server）：
   服务端收到配置修改请求
   立即返回长轮询响应（不再等待超时）
   客户端收到变更通知

③ 客户端处理变更：
   NacosContextRefresher 监听变更事件
   发布 RefreshEvent 事件
   RefreshEventListener 调用 ContextRefresher.refresh()

   @RefreshScope 注解的 Bean 被销毁并重新创建
   Bean 重新注入新的配置值
```

#### 三、@RefreshScope 的工作原理

```java
@RefreshScope  // ← 关键注解！
@Component
public class DynamicConfig {
    
    @Value("${order.timeout:5000}")
    private int orderTimeout;
    
    @Value("${order.max-count:100}")
    private int maxCount;
    
    public int getOrderTimeout() {
        return orderTimeout;
    }
}
```

**@RefreshScope 的本质：**

```
@RefreshScope 是 @Scope("refresh") 的别名
它创建的是一个"懒加载"的代理 Bean

工作原理：
  ① 首次创建：生成代理对象，从 Environment 中读取配置值
  ② 配置变更：销毁当前 Bean 实例
  ③ 重新获取：下次调用时，通过代理创建新的 Bean 实例
  ④ 新实例从更新后的 Environment 中读取新配置值

关键：
  @RefreshScope Bean 必须是单例的（默认）
  配置值通过 Environment 传递（PropertySource）
```
