## 题目 1：[Java并发] 请详细阐述 ConcurrentHashMap 的底层实现原理，以及 JDK 7 与 JDK 8 的核心区别（场景化面试版）

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-26 早间&午间报告 — "不再问 HashMap put流程，改问并发下 HashMap 有什么问题？ConcurrentHashMap 怎么解决的？你遇到过 size() 不准确吗？"
**相关岗位**：Java后端 / 高并发系统 / 基础架构

### 📖 参考答案

#### 一、HashMap 在并发场景下的三大问题

```
问题 1：死循环（JDK 7 头插法）
  - 多线程同时 put 触发扩容，链表形成环
  - 后果：get 操作死循环，CPU 100%

问题 2：数据丢失
  - 两个线程同时 put，后一个覆盖前一个的 Entry
  - 或扩容时多个线程同时操作，数据被覆盖

问题 3：modCount 不一致
  - 迭代时其他线程修改结构 → ConcurrentModificationException
```

**面试回答框架**：先指出 HashMap 的并发问题，再引出 ConcurrentHashMap 的解决方案。

#### 二、JDK 7 分段锁（Segment）实现

```java
// JDK 7 ConcurrentHashMap 结构
// ┌─────────────────────────────────────────────┐
// │              ConcurrentHashMap               │
// │  ┌────────┐ ┌────────┐      ┌────────┐      │
// │  │Segment0│ │Segment1│ ...  │SegmentN│      │
// │  │ HashEntry[] │ HashEntry[] │ HashEntry[]   │
// │  └────────┘ └────────┘      └────────┘      │
// └─────────────────────────────────────────────┘

// 核心设计：分段锁（Segment 继承 ReentrantLock）
// 默认 16 个 Segment → 理论并发度 16
// 每个 Segment 内部维护一个 HashEntry[] 数组
```

| 维度 | JDK 7 实现 |
|------|-----------|
| **数据结构** | Segment（继承 ReentrantLock）+ HashEntry[] |
| **并发机制** | 分段锁，不同 Segment 互不影响 |
| **并发度** | 默认 16（可通过 concurrencyLevel 调整） |
| **get 操作** | 不加锁（volatile 保证可见性） |
| **put 操作** | 锁定当前 Segment |
| **size()** | 先无锁统计 2 次，不一致则锁所有 Segment |

**JDK 7 的缺陷**：
- Segment 数量固定，扩容后并发度不变
- 分段锁粒度较粗，一个 Segment 内的所有操作互斥
- 空间浪费（Segment 数量固定为 2 的幂次）

#### 三、JDK 8 彻底重构：CAS + synchronized

```java
// JDK 8 ConcurrentHashMap 结构
// ┌─────────────────────────────────────────────┐
// │              ConcurrentHashMap               │
// │  ┌────┬────┬────┬────┬────┬────┬────┬────┐ │
// │  │Node│Node│Node│Node│Node│Node│Node│Node│ │
// │  ├────┼────┼────┼────┼────┼────┼────┼────┤ │
// │  │null│ →  │null│RB  │null│ →  │null│null│ │
// │  │    │ K-V│    │树  │    │ K-V│    │    │ │
// │  └────┴────┴────┴────┴────┴────┴────┴────┘ │
// │              Node[] (table)                  │
// └─────────────────────────────────────────────┘
```

**核心变化**：

| 对比维度 | JDK 7（Segment） | JDK 8（CAS+synchronized） |
|---------|-----------------|--------------------------|
| **数据结构** | Segment + HashEntry | Node + TreeNode（红黑树） |
| **并发控制** | ReentrantLock 分段锁 | CAS（插入）+ synchronized（扩容/树化） |
| **锁粒度** | Segment 级别（粗） | 桶（bucket）级别（细） |
| **扩容** | 每个 Segment 独立扩容 | 多线程协同扩容（transfer） |
| **size()** | 锁所有 Segment | CounterCell 分段计数 |

#### 四、JDK 8 核心源码分析

**1. put 操作（CAS + synchronized）**

```java
final V putVal(K key, V value, boolean onlyIfAbsent) {
    // ① 计算 hash
    int hash = spread(key.hashCode());
    int binCount = 0;
    
    for (Node<K,V>[] tab = table;;) { // 自旋
        Node<K,V> f; int n, i, fh;
        
        // ② 懒初始化：首次 put 时创建 table
        if (tab == null || (n = tab.length) == 0)
            tab = initTable();
        
        // ③ 当前桶为空 → CAS 无锁插入
        else if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
            if (casTabAt(tab, i, null, new Node<K,V>(hash, key, value, null)))
                break;  // CAS 成功，退出循环
        }
        
        // ④ 正在扩容 → 协助扩容（多线程协同）
        else if ((fh = f.hash) == MOVED)
            tab = helpTransfer(tab, f);
        
        // ⑤ 桶不为空 → synchronized 锁住桶头节点
        else {
            V oldVal = null;
            synchronized (f) { // 锁粒度：单个桶
                // 链表插入 / 红黑树插入
                if (fh >= 0) {
                    // 遍历链表
                    binCount = 1;
                    for (Node<K,V> e = f;; ++binCount) {
                        K ek;
                        if (e.hash == hash && 
                            ((ek = e.key) == key || (ek != null && key.equals(ek)))) {
                            oldVal = e.val;
                            if (!onlyIfAbsent)
                                e.val = value;
                            break;
                        }
                        Node<K,V> pred = e;
                        if ((e = e.next) == null) {
                            pred.next = new Node<K,V>(hash, key, value, null);
                            break;
                        }
                    }
                }
                // 红黑树插入
                else if (f instanceof TreeBin)
                    // ...
            }
            // 链表长度 ≥ 8 → 树化
            if (binCount >= TREEIFY_THRESHOLD)
                treeifyBin(tab, i);
        }
    }
    // ⑥ 计数（CounterCell 分段累加）
    addCount(1L, binCount);
    return null;
}
```

**2. get 操作（无锁，volatile 保证可见性）**

```java
public V get(Object key) {
    Node<K,V>[] tab; Node<K,V> e, p; int n, eh; K ek;
    int h = spread(key.hashCode());
    
    // ① 定位桶
    if ((tab = table) != null && (n = tab.length) > 0 &&
        (e = tabAt(tab, (n - 1) & h)) != null) {
        
        // ② 检查桶头节点
        if ((eh = e.hash) == h) {
            if ((ek = e.key) == key || (ek != null && key.equals(ek)))
                return e.val;
        }
        // ③ 红黑树查找
        else if (eh < 0)
            return (p = e.find(h, key)) != null ? p.val : null;
        
        // ④ 链表遍历
        while ((e = e.next) != null) {
            if (e.hash == h &&
                ((ek = e.key) == key || (ek != null && key.equals(ek))))
                return e.val;
        }
    }
    return null;
}
```

**get 为什么不需要加锁？**
- Node 的 val 和 next 都用 `volatile` 修饰
- `tabAt()` 使用 `Unsafe.getObjectVolatile()` 保证读取的是最新值
- put 操作在 synchronized 块内完成，释放锁时会将修改刷入主存（happens-before）

#### 五、size() 为什么不准确？

```java
// JDK 8 的 size() 实现
public int size() {
    long n = sumCount();  // 累加 CounterCell[] 中的值
    return ((n < 0L) ? 0 :
            (n > (long)Integer.MAX_VALUE) ? Integer.MAX_VALUE :
            (int)n);
}

// CounterCell 分段计数
// 多个线程同时 put，各自更新自己的 CounterCell
// sumCount() 遍历所有 CounterCell 累加
// 由于累加过程不是原子的，所以 size() 是近似值
```

**为什么设计成不准确？**
- 如果每次 size() 都加锁，高并发下性能急剧下降
- 大多数场景不需要精确的 size（如判断是否为空用 `isEmpty()`）
- 需要精确计数时，用 `mappingCount()` 或自行维护计数器

**面试追问**：如果你需要精确的 size，怎么办？
- 方案 1：加全局锁（性能差）
- 方案 2：用 LongAdder 自行维护计数器
- 方案 3：用数据库/Redis 维护精确计数

#### 六、多线程协同扩容（transfer）

JDK 8 最大的亮点：**扩容时多个线程可以协同工作**。

```
单线程扩容（HashMap）：
  新建 2 倍大小的数组 → 逐个 rehash → 完成

多线程协同扩容（ConcurrentHashMap）：
  ① 第一个线程发现需要扩容，创建新数组（2倍）
  ② 将旧数组分成多个"任务区间"
  ③ 其他线程 put 时发现正在扩容（MOVED 标志）
  ④ 主动加入帮忙迁移数据
  ⑤ 迁移完成，所有线程退出
```

### 📖 参考答案

#### 一、快速瓶颈预判框架

当收到 CPU 飙高告警时，不要盲目开始查，先用 4 个指标做**快速分类**：

```
┌─────────────────────────────────────────────────┐
│               CPU 飙高预判矩阵                    │
│                                                   │
│  CPU高 + wa≈0（IO等待低）                         │
│    → 业务代码计算密集 / 死循环 / 频繁GC           │
│                                                   │
│  CPU高 + 频繁GC                                   │
│    → JVM 内存不足 / 内存泄漏                      │
│                                                   │
│  CPU正常 + wa高（IO等待高）                       │
│    → 磁盘IO瓶颈 / 数据库慢查询                    │
│                                                   │
│  线程状态含大量 epollWait                          │
│    → 网络IO等待（HTTP/RPC 调用超时）              │
└─────────────────────────────────────────────────┘
```

**K8s 环境的特殊之处**：
- 容器限制了 CPU 资源（`requests`/`limits`），但 JVM 默认看不到容器限制
- 容器内的 `/proc/cpuinfo` 可能显示宿主机 CPU 数，导致 JVM 启动过多线程
- 需要显式配置 `-XX:ActiveProcessorCount=` 或使用 JDK 10+（默认支持容器 CPU 限制）

#### 二、定位流程（5 步法）

**Step 1：确认 CPU 消耗进程**

```bash
# 进入容器
kubectl exec -it <pod-name> -n <namespace> -- bash

# 查看 CPU 消耗最高的进程
top -H -p <pid>
# 或
ps -eo pid,ppid,%cpu,%mem,cmd --sort=-%cpu | head -10

# 确认 Java 进程
jps -l
```

**Step 2：定位 CPU 消耗最高的线程**

```bash
# 查看 Java 进程中 CPU 消耗最高的线程（十进制 PID）
top -H -p $(pgrep java) | head -20

# 将线程 PID 转为十六进制（jstack 使用十六进制）
printf "%x\n" <thread-pid>
# 输出：0x7f23
```

**Step 3：获取线程堆栈**

```bash
# 方式一：jstack（推荐）
jstack <java-pid> | grep -A 30 "0x7f23"

# 方式二：jcmd（JDK 8u60+）
jcmd <java-pid> Thread.print | grep -A 30 "0x7f23"

# 方式三：Arthas（生产推荐，无需重启）
# 安装 Arthas
curl -O https://arthas.aliyun.com/arthas-boot.jar
java -jar arthas-boot.jar <java-pid>
# 在 Arthas 中执行
thread -n 5  # 查看最忙的 5 个线程
thread <thread-id>  # 查看具体线程堆栈
```

**Step 4：分析堆栈状态**

```
常见 CPU 飙高原因及堆栈特征：

① 死循环 / 空转
  堆栈特征：重复执行同一个方法，无 IO 等待
  典型场景：while(true) 无 sleep、HashMap 死循环（JDK 7）
  排查：Arthas `stack <class> <method>` 查看调用次数

② 频繁 GC（GC 线程占 CPU）
  堆栈特征：GC 线程（G1 Young/Concurrent Mark）持续运行
  排查：jstat -gcutil <pid> 1000 10 查看 GC 频率
        GC 间隔 < 1s → 内存不足 / 泄漏

③ 锁竞争（线程阻塞+上下文切换）
  堆栈特征：大量线程 BLOCKED / WAITING
  排查：Arthas `thread -b` 查看阻塞的线程
        jstack 搜索 "waiting to lock" 和 "locked"

④ 大量线程创建（线程泄漏）
  堆栈特征：线程数异常高（> 1000）
  排查：Arthas `thread` 查看线程总数
        top -H 查看线程数
```

**Step 5：根因定位与修复**

```bash
# 场景 1：GC 频繁 → 分析堆内存
jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>
# 用 MAT / JProfiler 分析大对象和 GC Root

# 场景 2：死循环 → 用 Arthas 热修复
# 先用 vmtool 临时替换方法（Arthas）

# 场景 3：锁竞争 → 分析锁代码
# 使用 Arthas 查看锁信息

```


```java
    -- KEYS[1]: 库存 key
    -- ARGV[1]: 扣减数量
    local stock = redis.call('GET', KEYS[1])
    if not stock then
        return -1  -- 商品不存在
    end
    if tonumber(stock) < tonumber(ARGV[1]) then
        return 0   -- 库存不足
    end
    redis.call('DECRBY', KEYS[1], ARGV[1])
    return 1       -- 扣减成功
    """;

public boolean deductStock(Long skuId, int quantity) {
    Long result = redisTemplate.execute(
        new DefaultRedisScript<>(STOCK_SCRIPT, Long.class),
        Arrays.asList("seckill:stock:" + skuId),
        String.valueOf(quantity)
    );
    return Long.valueOf(1).equals(result);
}
```

**相关岗位**：Java后端 / 高并发系统 / AI应用开发

### 📖 参考答案

#### 一、虚拟线程是什么？

虚拟线程（Virtual Threads）是 JDK 21（LTS）正式发布的**轻量级线程**，由 JVM 管理而非操作系统管理。它的核心目标：**用极低的成本创建海量线程，解决传统线程池的痛点**。

```
传统线程（平台线程 / Platform Thread）：
  ┌─────────────────────┐
  │  OS 线程（1:1 映射）  │  ← 创建成本高（1MB 栈）
  │  内核态调度           │  ← 上下文切换成本高
  │  数量有限（~4000）    │  ← 受限于内存
  └─────────────────────┘

虚拟线程（Virtual Thread）：
  ┌─────────────────────┐
  │  JVM 管理            │  ← 创建成本极低（几百字节）
  │  用户态调度           │  ← 无内核切换
  │  数量巨大（百万级）    │  ← 几乎无限制
  └─────────────────────┘
```

#### 二、工作原理：M:N 调度

```
虚拟线程的调度模型（M:N 调度）：

┌─────────────────────────────────────────────┐
│            JVM 虚拟线程调度器                  │
│                                              │
│  虚拟线程 1  虚拟线程 2  ...  虚拟线程 N      │
│      │           │              │            │
│      ▼           ▼              ▼            │
│  ┌───────────────────────────────────────┐   │
│  │          Carrier Thread Pool           │   │
│  │     （平台线程池，通常 = CPU 核数）      │   │
│  └───────────────────────────────────────┘   │
│      │           │              │            │
│      ▼           ▼              ▼            │
│  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐    │
│  │ CPU1 │  │ CPU2 │  │ CPU3 │  │ CPU4 │    │
│  └──────┘  └──────┘  └──────┘  └──────┘    │
└─────────────────────────────────────────────┘

关键机制：虚拟线程在遇到阻塞操作（IO、锁、sleep）时，
会自动从 Carrier Thread 上"卸载"（yield），
Carrier Thread 转而执行其他虚拟线程。
```

**类比理解**：
- 平台线程 = 每个顾客配一个专属服务员（1:1，成本高）
- 虚拟线程 = 一个服务员服务多个顾客（M:N，高效）
- 阻塞操作 = 顾客在思考/吃饭，服务员先去服务其他顾客

#### 三、与传统线程池的对比

| 对比维度 | 平台线程（Thread） | 虚拟线程（Virtual Thread） |
|---------|------------------|--------------------------|
| **创建成本** | ~1MB 栈内存 | ~几百字节 |
| **最大数量** | ~4000（16GB 内存） | 数百万 |
| **调度** | 内核态（OS 调度） | 用户态（JVM 调度） |
| **上下文切换** | ~1-10μs（内核切换） | ~0.1μs（用户态切换） |
| **适用场景** | CPU 密集型 | IO 密集型 |
| **API 兼容性** | 完全兼容 | 完全兼容（`Thread` 子类） |

#### 六、注意事项与限制

```
⚠️ 虚拟线程不适合的场景：
  1. CPU 密集型计算（加密、压缩、视频编码）
     → 虚拟线程的 yield 优势用不上，反而增加调度开销
  2. synchronized 块内长时间操作
     → 虚拟线程在 synchronized 块内不会 yield（固定到 Carrier Thread）
     → 用 ReentrantLock 替代 synchronized
  3. ThreadLocal 大量使用
     → 虚拟线程数量巨大，ThreadLocal 内存开销不可忽视

✅ 虚拟线程最适合的场景：
  1. IO 密集型（HTTP 调用、DB 查询、文件读写）
  2. 高并发请求处理（Web 服务器、API 网关）
  3. AI 推理服务（大量并行调用 LLM API）
  4. 微服务间 RPC 调用
```

**相关岗位**：Java后端 / 微服务架构 / 分布式系统

### 📖 参考答案

#### 一、分布式事务的由来

```
单体应用：一个 @Transactional 搞定
  ┌─────────────────────────────┐
  │  订单服务（单体）              │
  │  BEGIN TRANSACTION           │
  │    INSERT INTO orders        │
  │    UPDATE stock SET stock-1  │
  │    INSERT INTO payment       │
  │  COMMIT                      │
  └─────────────────────────────┘

微服务架构：每个服务独立数据库
  ┌──────────┐  ┌──────────┐  ┌──────────┐
  │ 订单服务  │  │ 库存服务  │  │ 支付服务  │
  │ 订单 DB  │  │ 库存 DB  │  │ 支付 DB  │
  └──────────┘  └──────────┘  └──────────┘
  → 本地事务无法跨服务 → 需要分布式事务
```

#### 二、三大方案详解

##### 方案 1：可靠消息 + 最终一致性（最常用）

```
核心思想：利用消息队列保证"本地事务 + 消息发送"的原子性，
         消费者端保证幂等消费。

下单流程：
┌──────────┐     ┌──────────┐     ┌──────────┐
│ 订单服务  │     │ 消息队列  │     │ 库存服务  │
│          │     │ (Kafka)  │     │          │
│ ① 开启本地事务   │          │     │          │
│ ② 插入订单      │          │     │          │
│ ③ 发送消息 ───→ │ ④ 持久化  │ ──→ │ ⑤ 消费消息 │
│ ④ 提交事务      │          │     │ ⑥ 扣减库存 │
│          │     │          │     │ ⑦ 提交本地  │
└──────────┘     └──────────┘     └──────────┘
```

**关键设计：本地消息表**

```java
// 订单服务：本地事务 + 消息发送
@Transactional
public Order createOrder(CreateOrderRequest request) {
    // ① 插入订单
    Order order = orderMapper.insert(request);
    
    // ② 插入本地消息表（同 DB 事务）
    LocalMessage message = new LocalMessage();
    message.setBizId(order.getId());
    message.setTopic("order_created");
    message.setPayload(JSON.toJSONString(order));
    message.setStatus(MessageStatus.PENDING);
    localMessageMapper.insert(message);
    
    return order;
}

// ③ 定时任务：扫描未发送的消息，发送到 MQ
@Scheduled(fixedDelay = 5000)
public void sendPendingMessages() {
    List<LocalMessage> pending = localMessageMapper
        .selectByStatus(MessageStatus.PENDING, PageRequest.of(0, 100));
    
    for (LocalMessage msg : pending) {
        try {
            kafkaTemplate.send(msg.getTopic(), msg.getPayload()).get(3, TimeUnit.SECONDS);
            localMessageMapper.updateStatus(msg.getId(), MessageStatus.SENT);
        } catch (Exception e) {
            log.error("发送消息失败，id={}", msg.getId(), e);
            // 下次定时任务重试
        }
    }
}

// 库存服务：幂等消费
@KafkaListener(topics = "order_created")
public void handleOrderCreated(String payload) {
    Order order = JSON.parseObject(payload, Order.class);
    
    // 幂等检查（关键！）
    if (idempotentService.isProcessed("stock:" + order.getId())) {
        return;
    }
    
    // 扣减库存
    stockService.deduct(order.getSkuId(), order.getQuantity());
    
    // 标记已处理
    idempotentService.markProcessed("stock:" + order.getId());
}
```

**幂等性实现方案**：

| 方案 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| **唯一键** | 业务 ID 作为 DB 唯一索引 | 简单可靠 | 需额外字段 |
| **Redis 标记** | `SETNX biz_id 1` | 性能高 | Redis 可能丢数据 |
| **状态机** | 订单状态流转（已创建→已支付） | 业务语义清晰 | 需设计状态图 |
| **去重表** | 单独的去重表 + 唯一索引 | 可靠 | 多一次 DB 查询 |

##### 方案 2：TCC（Try-Confirm-Cancel）

```
TCC 三阶段：

Try（预留资源）：
  订单服务：创建"预订单"（状态=待确认）
  库存服务：冻结库存（不可用，但未扣减）
  支付服务：冻结资金（不可用，但未划转）

Confirm（确认执行）：
  订单服务：预订单 → 正式订单
  库存服务：冻结库存 → 扣减
  支付服务：冻结资金 → 划转

Cancel（回滚）：
  订单服务：预订单 → 取消
  库存服务：冻结库存 → 解冻
  支付服务：冻结资金 → 解冻
```

```java
// TCC 接口定义
public interface OrderTccService {
    
    @TwoPhaseBusinessAction(
        name = "orderTcc",
        commitMethod = "confirm",
        rollbackMethod = "cancel"
    )
    void tryCreateOrder(OrderContext context);
    
    void confirm(OrderContext context);
    
    void cancel(OrderContext context);
}

// Try 阶段：预留资源
@Transactional
public void tryCreateOrder(OrderContext ctx) {
    // 创建预订单（状态=PENDING）
    orderMapper.insert(new Order(ctx.getUserId(), OrderStatus.PENDING));
    
    // 调用库存服务的 Try
    stockTccService.tryDeduct(ctx.getSkuId(), ctx.getQuantity());
    
    // 调用支付服务的 Try
    paymentTccService.tryFreeze(ctx.getUserId(), ctx.getAmount());
}
```

| 维度 | TCC |
|------|-----|
| **一致性** | 强一致（两阶段提交变体） |
| **性能** | 中（每个阶段都要网络调用） |
| **复杂度** | ⭐⭐⭐⭐⭐（每个服务需实现 Try/Confirm/Cancel） |
| **空回滚** | 需处理 Try 未执行但 Cancel 已调用的情况 |
| **幂等** | Confirm/Cancel 必须幂等 |
| **适用场景** | 资金类、对一致性要求极高的场景 |

##### 方案 3：Saga（长事务补偿）

```
Saga 的核心思想：将一个大事务拆成多个本地事务，
每个本地事务都有对应的"补偿事务"。

正向流程：
  Order Service: 创建订单
      ↓
  Stock Service: 扣减库存
      ↓
  Payment Service: 扣款
      ↓
  → 全部成功 ✓

补偿流程（如果扣款失败）：
  Payment Service: 扣款失败 ✗
      ↓
  Stock Service: 补偿 → 回滚库存（加回库存）
      ↓
  Order Service: 补偿 → 取消订单
```

```java
// Saga 编排（Orchestration 模式）
@Component
public class OrderSagaOrchestrator {
    
    @Autowired
    private KafkaTemplate<String, Object> kafkaTemplate;
    
    public void createOrderSaga(CreateOrderRequest request) {
        // ① 创建订单
        Order order = orderService.create(request);
        
        // ② 发送"扣减库存"命令
        kafkaTemplate.send("stock_deduct", 
            new StockDeductCommand(order.getSkuId(), order.getQuantity()));
    }
    
    // 监听库存扣减结果
    @KafkaListener(topics = "stock_deduct_result")
    public void onStockDeductResult(StockDeductResult result) {
        if (result.isSuccess()) {
            // ③ 库存扣减成功 → 发起支付
            kafkaTemplate.send("payment_charge", 
                new PaymentCommand(result.getOrderId(), result.getAmount()));
        } else {
            // ③ 库存扣减失败 → 取消订单（补偿）
            kafkaTemplate.send("order_cancel", 
                new OrderCancelCommand(result.getOrderId()));
        }
    }
    
    // 监听支付结果
    @KafkaListener(topics = "payment_result")
    public void onPaymentResult(PaymentResult result) {
        if (!result.isSuccess()) {
            // 支付失败 → 补偿：回滚库存 + 取消订单
            kafkaTemplate.send("stock_rollback", 
                new StockRollbackCommand(result.getOrderId()));
            kafkaTemplate.send("order_cancel", 
                new OrderCancelCommand(result.getOrderId()));
        }
    }
}
```
