**一、为什么需要 GC？——Java 的灵魂特性**

C/C++ 需要手动管理内存（malloc/free、new/delete），容易出现内存泄漏和野指针。Java 的自动垃圾回收（Garbage Collection）让开发者从内存管理中解放，专注于业务逻辑。但"自动化"不是"无代价"——GC 会引发 STW（Stop The World），所有用户线程暂停，是系统延迟的最大不确定因素。

```
GC 的核心矛盾：

  吞吐量（Throughput） ⟷ 延迟（Latency） ⟷ 内存占用（Footprint）
  
  三者不可兼得！调优的本质是在三者之间找到平衡。
  
  吞吐量优先：适合批处理、离线计算（如 Parallel GC）
  延迟优先：适合在线服务、实时系统（如 G1/ZGC）
  内存受限：适合嵌入式、微服务小容器（如 Serial GC + 小堆）
```

**二、堆内存分代模型——为什么分代？**

HotSpot JVM 将堆分为新生代和老年代，基于"弱分代假说"：大多数对象朝生夕灭，少数对象长期存活。

```
JVM 堆内存结构（JDK 8+）：

  ┌─────────────────────────────────────────────────────────┐
  │                        Heap                             │
  │  ┌──────────────────────────────────────────────────┐   │
  │  │                  Young Generation                │   │
  │  │  ┌──────────┬──────────┬──────────┐              │   │
  │  │  │   Eden   │ Survivor │ Survivor │              │   │
  │  │  │   (8/10) │   S0     │   S1     │              │   │
  │  │  │          │  (1/10)  │  (1/10)  │              │   │
  │  │  └──────────┴──────────┴──────────┘              │   │
  │  └──────────────────────────────────────────────────┘   │
  │  ┌──────────────────────────────────────────────────┐   │
  │  │               Old Generation                     │   │
  │  │              （Tenured Space）                     │   │
  │  └──────────────────────────────────────────────────┘   │
  └─────────────────────────────────────────────────────────┘
  
  ┌─────────────────────────────────────────────────────────┐
  │        Metaspace（元空间，直接内存，替代永久代）           │
  │         存储类元数据、方法信息、常量池                     │
  └─────────────────────────────────────────────────────────┘

  分代比例：新生代:老年代 = 1:2（默认）
  Eden:S0:S1 = 8:1:1（默认）
```

```
对象分配与晋升流程：

  ① new 对象 → Eden 区分配
  ② Eden 满 → Minor GC（Young GC）
     → 存活对象 → S0/S1（年龄+1）
     → Eden 清空，S0 和 S1 角色互换（始终有一个为空）
  ③ 对象年龄达到阈值（默认 15）→ 晋升老年代
  ④ 老年代满 → Full GC（Major GC，通常伴随 STW）
  
  特殊情况：
  - 大对象（如大数组）直接进入老年代（避免在 Eden/Survivor 间拷贝）
  - 动态年龄判断：同龄对象总大小 > Survivor 的 50% → 提前晋升
```

**三、三种垃圾回收算法——理论基石**

```
① 标记-清除（Mark-Sweep）：
   ① 标记所有可达对象（GC Roots 可达性分析）
   ② 清除未标记对象
   
   优点：不需要移动对象
   缺点：产生内存碎片（碎片化严重时可能触发 Full GC）
   
   适用：老年代（CMS 的"标记-清除"阶段）

② 标记-复制（Mark-Copy）：
   ① 标记所有可达对象
   ② 将存活对象复制到另一块区域
   ③ 清空原区域
   
   优点：无碎片，分配简单（指针碰撞）
   缺点：浪费一半内存
   
   适用：新生代（Eden + Survivor 天然符合复制模型）

③ 标记-整理（Mark-Compact）：
   ① 标记所有可达对象
   ② 将存活对象向一端移动（整理）
   ③ 清理边界外的内存
   
   优点：无碎片，不浪费内存
   缺点：移动对象需要 STW，耗时较长
   
   适用：老年代（G1 的 Mixed GC 包含整理）
```

**四、主流垃圾回收器对比——面试核心**

```
垃圾回收器演进史：

  Serial → Parallel → CMS → G1 → ZGC / Shenandoah
  (串行)   (并行)    (并发)  (分区)  (超低延迟)
  
  发展方向：更低延迟、更大堆、更少 STW
```

| 回收器 | 新生代 | 老年代 | 特点 | 目标 |
|--------|--------|--------|------|------|
| **Serial** | 单线程复制 | 单线程整理 | 最简单，单核 | 客户端/小堆 |
| **Parallel** | 多线程复制 | 多线程整理 | 吞吐量优先 | 批处理/离线 |
| **CMS** | ParNew(并行) | 并发标记清除 | 低延迟，老牌 | ~~已废弃~~ JDK14 |
| **G1** | 分区回收 | Mixed GC | 可预测停顿 | **当前主流** ⭐ |
| **ZGC** | 不分代 | 并发整理 | 亚毫秒级 STW | 超大堆/低延迟 |
| **Shenandoah** | 不分代 | 并发整理 | 与 ZGC 类似 | 超大堆/低延迟 |

**CMS 详细原理——虽已废弃但面试必问**

```
CMS（Concurrent Mark Sweep）四阶段：

  ① 初始标记（Initial Mark）—— STW，极短
     标记 GC Roots 直接可达的对象
     
  ② 并发标记（Concurrent Mark）—— 并发，最长
     从 GC Roots 出发，遍历整个对象图
     与用户线程并发执行，不影响应用
     
  ③ 重新标记（Remark）—— STW，较短
     修正并发标记期间发生变化的对象引用
     使用增量更新（Incremental Update）算法
     
  ④ 并发清除（Concurrent Sweep）—— 并发
     清除未标记的垃圾对象
     与用户线程并发执行

  CMS 三大致命缺陷：
  ① 标记-清除产生内存碎片 → 碎片化严重时退化为 Serial Old（单线程整理）
  ② 浮动垃圾：并发标记期间新产生的垃圾无法回收 → 需要预留空间
  ③ 对 CPU 资源敏感：并发标记和清除占用 CPU → 影响用户线程性能

  这也是 CMS 在 JDK 14 被正式废弃的原因。
```

**G1 详细原理——当前主流，2026 面试必考**

```
G1（Garbage First）核心思想：

  将堆划分为多个大小相等的 Region（默认约 2048 个），
  每个 Region 可以在 Eden/Survivor/Old/Humongous 之间动态切换。
  优先回收垃圾最多的 Region（Garbage First 名字的由来）。

  Region 类型：
  - Eden Region：新生代
  - Survivor Region：存活区
  - Old Region：老年代
  - Humongous Region：大对象（超过 Region 的 50%）
  
  RSet（Remembered Set）：
  每个 Region 都有一个 RSet，记录其他 Region 中指向本 Region 的引用。
  作用：GC 时不需要扫描整个堆，只需检查 RSet 即可。

  G1 的 Mixed GC 流程：
  ① 初始标记（STW）→ 伴随 Young GC
  ② 根区域扫描（并发）
  ③ 并发标记（并发）
  ④ 重新标记（STW）→ 使用 SATB（Snapshot At The Beginning）算法
  ⑤ 筛选回收（STW）→ 选择垃圾最多的 Old Region 进行回收+整理

  G1 的核心优势：
  ✅ 可预测的停顿时间：通过 -XX:MaxGCPauseMillis 设置目标
  ✅ 无内存碎片：回收时进行整理（Compact）
  ✅ 自动调优：根据历史数据自适应调整
  ✅ 支持超大堆：TB 级堆也能管理
```

**五、GC 调优实战——面试中的"杀手问题"**

```
GC 调优的基本思路：

  ① 明确目标：
     - 高吞吐？→ Parallel GC + 大堆
     - 低延迟？→ G1/ZGC + 合理堆大小
     - 小内存？→ Serial GC（微服务容器）

  ② 收集 GC 日志（必备参数）：
     -Xlog:gc*:file=gc.log:time,level,tags  # JDK 9+
     -XX:+PrintGCDetails -XX:+PrintGCDateStamps  # JDK 8

  ③ 分析 GC 日志：
     - Minor GC 频率和耗时（正常：几十ms，不频繁）
     - Full GC 频率（理想：极少甚至没有）
     - 晋升速率（Survivor 到 Old 的速率）
     - 老年代增长速率

  ④ 调优参数：
     - 堆大小：-Xms -Xmx（建议设为相同值，避免动态扩展）
     - 新生代大小：-Xmn 或 -XX:NewRatio
     - Survivor 比例：-XX:SurvivorRatio
     - 晋升阈值：-XX:MaxTenuringThreshold
     - GC 停顿目标（G1）：-XX:MaxGCPauseMillis=200

  ⑤ 常见问题与对策：
     - Minor GC 频繁 → 增大新生代 / 检查短命对象
     - Full GC 频繁 → 增大老年代 / 排查内存泄漏 / 检查大对象
     - 单次 GC 时间过长 → 换 G1（设置停顿目标）/ ZGC
     - 晋升失败（Promotion Failed）→ 增大老年代 / 增大 Survivor
```

```bash
# 典型生产环境 JVM 参数（G1）
java -Xms4g -Xmx4g \
     -XX:+UseG1GC \
     -XX:MaxGCPauseMillis=200 \
     -XX:InitiatingHeapOccupancyPercent=45 \
     -XX:G1HeapRegionSize=4m \
     -XX:+PrintGCDetails \
     -XX:+PrintGCDateStamps \
     -Xloggc:/var/log/app/gc.log \
     -XX:+UseGCLogFileRotation \
     -XX:NumberOfGCLogFiles=10 \
     -XX:GCLogFileSize=100M \
     -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/var/log/app/heapdump.hprof \
     -jar app.jar

# 参数说明：
# -XX:MaxGCPauseMillis=200    → G1 目标停顿 ≤ 200ms
# -XX:InitiatingHeapOccupancyPercent=45 → 老年代占 45% 触发 Mixed GC
# -XX:G1HeapRegionSize=4m     → Region 大小 4MB（堆 ≤ 8G 时推荐）
```

```
   "CMS 四阶段：初始标记→并发标记→重新标记→并发清除。致命缺陷：碎片化、

④ ZGC 特点（10秒）：
   "ZGC 不分代，基于染色指针和读屏障实现并发整理，

   "先定目标（吞吐/延迟/内存），收集 GC 日志分析。频繁 Young GC → 调大新生代；
    频繁 Full GC → 排查内存泄漏或调大老年代；单次 GC 长 → 换 G1 或 ZGC。
    生产必备参数：GC 日志 + OOM 时 HeapDump + 监控（Prometheus JVM Exporter）"
```

### 💡 延伸思考

1. **为什么 G1 被称为"Garbage First"？** — G1 的核心策略是"优先回收垃圾最多的 Region"，通过维护每个 Region 的"回收价值"（回收能释放多少空间 / 回收耗时），选择收益最大的 Region 进行回收。这样可以用最小的 STW 时间回收最多的垃圾，最大化 GC 效率。这也是 G1 能实现可预测停顿的关键。
2. **ZGC 为什么能做到亚毫秒级 STW？** — ZGC 使用染色指针（Colored Pointers）技术，在 64 位指针中借用几位元数据标记对象状态。配合读屏障（Load Barrier），ZGC 可以在用户线程运行的同时进行对象整理，不需要 STW 来移动对象。唯一的 STW 发生在根扫描阶段，但时间极短（< 1ms）。JDK 21 引入分代 ZGC，进一步优化吞吐量。

```java
@RestController
public class AiController {
    
    private final ChatClient chatClient;
    
    public AiController(ChatClient.Builder builder) {

    }
```

**一、为什么需要分库分表？——单库单表的物理极限**

MySQL 单表在超过一定数据量后，即使索引优化也无法满足性能需求。这是因为 B+ 树的高度增加、磁盘 IO 增加、Buffer Pool 缓存效率下降、DDL 操作风险增大。

```
单库单表的瓶颈：

  ① 数据量瓶颈：
     单表 2000 万行后，B+ 树高度 ≈ 4 层 → 每次查询 4 次磁盘 IO
     单表上亿行 → 索引维护开销巨大 → 写入性能急剧下降
  
  ② 并发瓶颈：
     单库最大连接数有限（通常 2000-5000）
     高并发下连接池耗尽 → 请求排队 → 超时
  
  ③ 存储瓶颈：
     单实例磁盘容量有限（单库几百 GB 到几 TB）
     
  ④ DDL 瓶颈：
     大表 ALTER TABLE 可能需要数小时，期间业务不可用

  结论：当单表 > 2000 万行 或 单库 QPS > 5000，就需要考虑分库分表。
```

**二、垂直拆分 vs 水平拆分——两种策略**

```
垂直拆分（按业务模块）：

  ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
  │  商品数据     │     │  订单数据     │     │  用户数据     │
  │  product_db  │     │  order_db    │     │  user_db     │
  │              │     │              │     │              │
  │ product      │     │ orders       │     │ users        │
  │ sku          │     │ order_items  │     │ addresses    │
  │ category     │     │ payments     │     │ accounts     │
  └──────────────┘     └──────────────┘     └──────────────┘

  优点：解耦业务，各模块独立扩展
  缺点：跨库 JOIN 需要应用层处理

水平拆分（按数据行分片）：

  ┌─────────────────────────────────────────────────────────┐
  │                     orders 表                           │
  │                                                         │
  │  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  │
  │  │   orders_0   │  │   orders_1   │  │   orders_2   │  │
  │  │ user_id % 4  │  │ user_id % 4  │  │ user_id % 4  │  │
  │  │   = 0        │  │   = 1        │  │   = 2        │  │
  │  └──────────────┘  └──────────────┘  └──────────────┘  │
  │                                                         │
  │  分片键：user_id                                        │
  │  分片算法：user_id % 4                                  │
  │  分片数：4                                              │
  └─────────────────────────────────────────────────────────┘

  优点：突破单表数据量限制，线性扩展
  缺点：跨分片查询复杂、分布式事务、全局 ID 生成
```

**三、分片键选择——分库分表的核心决策**

```
分片键选择原则：

  ① 高频查询的 WHERE 条件列 → 避免跨分片查询
  ② 数据分布均匀 → 避免热点分片
  ③ 不可变 → 分片键一旦确定不能改（否则数据要迁移）

  电商系统常见分片键：
  - 订单表 → user_id（按用户查订单是最高频场景）
  - 用户表 → user_id（天然主键）
  - 商品表 → category_id + business_id（按类目 + 商家查）
  
  反例：
  - 按 create_time 分片 → 新数据全落在一个分片，热点集中
  - 按 status 分片 → 数据极不均匀
```

**四、ShardingSphere-JDBC——Java 生态的事实标准**

ShardingSphere 是 Apache 顶级项目，提供 JDBC 层面的分库分表中间件，对应用代码零侵入。

```
ShardingSphere 产品矩阵：

  ShardingSphere-JDBC（轻量级，推荐）
  ┌──────────┐    ┌──────────────────┐    ┌──────────┐
  │ Java App │───→│ ShardingSphere-  │───→│  MySQL   │
  │          │    │ JDBC (内嵌)      │    │  (多个)  │
  └──────────┘    └──────────────────┘    └──────────┘
  
  优点：零部署、零网络开销、与 ORM 框架无缝集成
  缺点：仅支持 Java、升级需要重启应用

  ShardingSphere-Proxy（独立部署）
  ┌──────────┐    ┌──────────────────┐    ┌──────────┐
  │ Any App  │───→│ ShardingSphere-  │───→│  MySQL   │
  │          │    │ Proxy (独立进程)  │    │  (多个)  │
  └──────────┘    └──────────────────┘    └──────────┘
  
  优点：多语言支持、独立升级、对应用完全透明
  缺点：额外网络开销、运维成本增加
```

**ShardingSphere 四大核心功能**：

| 功能 | 说明 |
|------|------|
| **Sharding** | 分库分表核心——数据分片 |
| **Readwrite-splitting** | 读写分离——一主多从 |
| **Data Encryption** | 数据加密——字段级加密 |
| **Shadow DB** | 影子库——全链路压测 |

### 分片策略详解

```yaml
# ShardingSphere 配置示例（Spring Boot）
spring:
  shardingsphere:
    datasource:
      names: ds0, ds1  # 两个数据库
      ds0:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        url: jdbc:mysql://localhost:3306/order_db_0
      ds1:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        url: jdbc:mysql://localhost:3306/order_db_1
    
    rules:
      sharding:
        tables:
          t_order:
            # 分库策略：user_id % 2
            actual-data-nodes: ds$->{0..1}.t_order_$->{0..3}
            database-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: database-inline
            # 分表策略：order_id % 4
            table-strategy:
              standard:
                sharding-column: order_id
                sharding-algorithm-name: table-inline
        
        sharding-algorithms:
          database-inline:
            type: INLINE
            props:
              algorithm-expression: ds$->{user_id % 2}
          table-inline:
            type: INLINE
            props:
              algorithm-expression: t_order_$->{order_id % 4}
```

```
四种分片算法：

  ① Standard（标准分片）—— 最常用
     单个分片键，精确 = / IN / BETWEEN / > / < 都支持
     
  ② Complex（复合分片）—— 多分片键
     多个分片键联合判断路由
     
  ③ Hint（强制路由）—— 手动指定
     应用代码中通过 HintManager 强制指定分片
     
  ④ Inline（行表达式）—— 简单场景
     直接写表达式：ds$->{user_id % 2}
```

**五、分库分表的四大挑战与解决方案**

```
挑战 ① 分布式主键生成
  ┌──────────────┬──────────────────────────────────────┐
  │     方案      │                特点                   │
  ├──────────────┼──────────────────────────────────────┤
  │ 雪花算法      │ ⭐ 推荐！64位：时间戳+机器ID+序列号    │
  │ (Snowflake)  │ 趋势递增、不依赖DB、缺点是时钟回拨     │
  ├──────────────┼──────────────────────────────────────┤
  │ 号段模式      │ 从DB批量取号段（如每次取1000个）       │
  │ (Leaf)       │ 美团开源，性能好，依赖DB               │
  ├──────────────┼──────────────────────────────────────┤
  │ Redis 自增   │ 简单，但Redis挂了有单点问题            │
  ├──────────────┼──────────────────────────────────────┤
  │ UUID         │ 绝对不重复，但无序→索引分裂严重        │
  └──────────────┴──────────────────────────────────────┘

挑战 ② 跨分片查询
  方案一：应用层聚合
    查询 → 广播到所有分片 → 应用层合并排序 → 返回
    ShardingSphere 自动处理！
    
  方案二：建立中间表（冗余）
    将需要跨分片查询的维度建一张全局表（不拆分）
    
  方案三：搜索引擎同步（ES）
    MySQL 数据同步到 ES → 复杂查询走 ES → 回查 MySQL

挑战 ③ 分布式事务
  方案一：Seata AT 模式（推荐，对业务零侵入）
  方案二：本地消息表 + MQ 最终一致性
  方案三：TCC（Try-Confirm-Cancel，业务侵入大但强一致）
  
  ⚠️ 原则：尽量避免跨分片事务！通过分片键设计让大部分事务在单分片内完成

挑战 ④ 数据迁移与扩容
  方案：ShardingSphere Scaling（数据弹性伸缩）
  流程：旧集群 → 增量同步 → 数据校验 → 切换 → 清理
```

**一、分布式锁——从单机到分布式的同步问题**

在单机应用中，`synchronized` 或 `ReentrantLock` 可以解决并发安全问题。但在分布式环境中，多个服务实例运行在不同的 JVM 中，JVM 级别的锁无法跨进程生效。分布式锁是解决这个问题的关键。

```
分布式锁的需求场景：

  ┌──────────┐    ┌──────────┐    ┌──────────┐
  │ 订单服务1 │    │ 订单服务2 │    │ 订单服务3 │
  └─────┬────┘    └─────┬────┘    └─────┬────┘
        │               │               │
        └───────────────┼───────────────┘
                        │
                        ▼
        ┌───────────────────────────────┐
        │         Redis                 │
        │  SET lock:order:123 value NX  │
        │  EX 30                        │
        └───────────────────────────────┘
        
  场景：多个服务实例同时处理同一个订单的退款 → 必须用分布式锁串行化
```

**二、从 SETNX 到 Redisson——分布式锁的进化之路**

### 阶段 1：简单 SETNX 实现（有严重缺陷）

```java
// ❌ 最简单的分布式锁——问题很多
public class SimpleRedisLock {
    
    public boolean tryLock(String key, String value, long expireTime) {
        // SET key value NX EX expireTime
        String result = jedis.set(key, value, "NX", "EX", expireTime);
        return "OK".equals(result);
    }
    
    public void unlock(String key, String value) {
        // 先查再删 —— 不是原子操作！有并发问题
        String currentValue = jedis.get(key);
        if (value.equals(currentValue)) {
            jedis.del(key);  // ⚠️ 如果这里锁刚好过期，删除的是别人的锁！
        }
    }
}
```

```
简单 SETNX 的四大缺陷：

  ① 不可重入：同一个线程多次获取同一把锁会死锁
  ② 不可重试：获取失败后只能直接返回，无法自旋等待
  ③ 超时自动释放：业务执行时间 > 锁过期时间 → 锁被自动释放 → 其他线程获取锁 → 并发安全问题
  ④ 主从一致性：主节点宕机，锁数据未同步到从节点 → 新主没有锁 → 多个客户端同时获取到锁
```

### 阶段 2：Lua 脚本优化（解决释放原子性）

```lua
-- ✅ Lua 脚本保证原子性
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

```java
// 使用 Lua 脚本保证释放的原子性
private static final String UNLOCK_SCRIPT = 
    "if redis.call('get', KEYS[1]) == ARGV[1] then " +
    "    return redis.call('del', KEYS[1]) " +
    "else " +
    "    return 0 " +
    "end";

public void unlock(String key, String value) {
    jedis.eval(UNLOCK_SCRIPT, Collections.singletonList(key), 
               Collections.singletonList(value));
}
```

### 阶段 3：Redisson——企业级分布式锁（推荐方案）⭐

Redisson 4.6.0 是 Java 生态最成熟的 Redis 客户端，通过看门狗机制和可重入设计解决了简单实现的所有缺陷。

**Redisson 分布式锁的核心设计**：

```
Redisson RLock 的数据结构（使用 Redis Hash）：

  Key: lock:order:123
  Hash:
    field: "thread-1-uuid"  ← 锁持有者标识（UUID:线程ID）
    value: 1                ← 重入计数（每重入一次 +1）
  
  为什么用 Hash 而不是 String？
  → Hash 可以存储重入计数！同一个线程每次 lock() 计数 +1，每次 unlock() 计数 -1

  可重入实现原理：
  ① 第一次 lock()：field="thread-1-uuid", value=1
  ② 第二次 lock()（同一线程）：检查 field 是否为自己 → value=2
  ③ 第一次 unlock()：value=2 → 1
  ④ 第二次 unlock()：value=1 → 0 → 删除 key
```

```java
// Redisson 分布式锁使用——非常简单
@Service
public class OrderService {
    
    @Autowired
    private RedissonClient redisson;
    
    public void refund(String orderId) {
        String lockKey = "lock:order:refund:" + orderId;
        RLock lock = redisson.getLock(lockKey);
        
        try {
            // ① 尝试加锁，最多等待 10 秒，锁自动过期时间 30 秒
            // 实际看门狗会自动续期，30 秒是"万一续期失败"的兜底
            if (lock.tryLock(10, 30, TimeUnit.SECONDS)) {
                // ② 执行业务逻辑
                doRefund(orderId);
            } else {
                throw new BusinessException("获取锁失败，请稍后重试");
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            // ③ 释放锁（Redisson 会自动判断是否为锁持有者）
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}

// 注解方式——更简洁
@RLock(value = "lock:order:refund:#{#orderId}", waitTime = 10, leaseTime = -1)
public void refund(@RLockKey String orderId) {
    doRefund(orderId);
}
```

**三、看门狗（Watchdog）机制——Redisson 的灵魂**

看门狗是 Redisson 最精妙的设计，解决了"业务执行时间超过锁过期时间"的问题：

```
看门狗工作原理：

  ① 加锁成功时：
     - 如果 leaseTime = -1（默认），启动看门狗定时器
     - 锁的初始过期时间设为 30 秒（默认 lockWatchdogTimeout）
     
  ② 看门狗定时续期：
     - 每隔 10 秒（lockWatchdogTimeout / 3）检查一次
     - 如果锁仍被当前客户端持有 → 续期到 30 秒
     - 无限续期，直到客户端主动 unlock 或宕机
     
  ③ 客户端宕机时：
     - 看门狗线程随 JVM 进程终止 → 锁在 30 秒后自动过期
     - 不会造成死锁

  ④ 手动指定 leaseTime 时：
     - 看门狗不会启动
     - 锁到期自动释放（适合执行时间可预估的场景）

  时序图：
  t=0s:  加锁成功，过期时间 30s，启动看门狗
  t=10s: 看门狗检查 → 锁仍被持有 → 续期到 30s
  t=20s: 看门狗检查 → 锁仍被持有 → 续期到 30s
  ...    (无限续期)
  t=Ns:  业务完成 → unlock → 看门狗停止
```

**四、RedLock 算法——Redis 官方推荐的分布式锁方案**

当 Redis 以主从模式部署时，单节点的分布式锁存在主从一致性问题。RedLock 通过多个独立的 Redis 节点来解决。

```
主从一致性问题的场景：

  ① 客户端 A 在 Master 上获取锁
  ② Master 宕机，锁数据未同步到 Slave
  ③ Slave 提升为新 Master
  ④ 客户端 B 在新 Master 上获取同一把锁 → 成功！
  → 两个客户端同时持有同一把锁！❌

RedLock 算法（需要至少 5 个独立 Redis 实例）：

  加锁流程：
  ① 获取当前时间戳（毫秒）
  ② 依次向 N 个 Redis 实例尝试获取锁（相同的 key + random value）
     - 每个实例的超时时间远小于锁的 TTL（如锁 TTL=10s，请求超时=50ms）
  ③ 计算获取锁的总耗时 = 当前时间 - 步骤①的时间
  ④ 如果获取到锁的实例数 ≥ N/2 + 1（多数），且总耗时 < 锁 TTL
     → 加锁成功
  ⑤ 锁的实际有效时间 = 锁 TTL - 总耗时
  ⑥ 如果加锁失败 → 向所有实例发送释放锁命令

  释放锁：
  向所有 Redis 实例发送释放锁命令（无论是否成功获取）
```

```
RedLock 的争议：

  支持方（Redis 作者 antirez）：
  - 提高分布式锁的可靠性
  - 不依赖主从复制
  
  反对方（分布式系统专家 Martin Kleppmann）：
  - RedLock 依赖时钟同步，不适用于需要绝对正确性的场景
  - 如果 GC STW 导致锁过期，RedLock 也无法解决
  - 对于"需要绝对正确"的场景（如转账），应该用 ZooKeeper 或数据库锁
  
  业界共识（2026）：
  - 对于"性能优化"场景（如防止缓存击穿）→ Redisson 单节点足够
  - 对于"需要强一致性"的场景 → 用 ZooKeeper/etcd 的分布式锁
  - RedLock 是一个"比单节点更可靠，但非绝对可靠"的中间方案
```

### 💡 延伸思考

1. **分布式锁和数据库悲观锁怎么选？** — Redis 分布式锁适合高并发、锁持有时间短的场景（如防重复提交、防缓存击穿），性能高但有丢失风险。数据库悲观锁（SELECT FOR UPDATE）适合强一致性场景（如库存扣减），绝对可靠但性能较低。折中方案：Redis 锁 + 数据库乐观锁（版本号）双重校验。
2. **如果业务执行时间不可预估，看门狗会无限续期——这有问题吗？** — 理论上没问题，只要 JVM 正常运行且没死锁。但实践中如果业务代码出现死循环或长时间阻塞，看门狗会一直续期，锁永远不释放。建议：① 给业务执行设置超时（如 2 分钟）；② 监控锁持有时间，超过阈值告警；③ 紧急情况下可以手动删除 Redis key 强制释放。

**四、点赞与取消点赞——核心流程**

```java
@Service
public class LikeService {
    
    @Autowired
    private RedisTemplate<String, String> redisTemplate;
    @Autowired
    private KafkaTemplate<String, LikeEvent> kafkaTemplate;
    
    private static final String LUA_LIKE = """
        local content_key = KEYS[1]    -- like:content:{contentId}
        local count_key = KEYS[2]      -- like:count:{contentId}
        local user_key = KEYS[3]       -- user:likes:{userId}
        local user_id = ARGV[1]
        
        -- 检查是否已点赞
        local is_member = redis.call('SISMEMBER', content_key, user_id)
        
        if is_member == 1 then
            -- 已点赞 → 取消点赞
            redis.call('SREM', content_key, user_id)
            redis.call('SREM', user_key, KEYS[1])
            redis.call('DECR', count_key)
            return 0  -- 返回 0 表示取消

        else
            -- 未点赞 → 点赞
            redis.call('SADD', content_key, user_id)
            redis.call('SADD', user_key, KEYS[1])
            redis.call('INCR', count_key)
            return 1  -- 返回 1 表示点赞
        end
        """;
    
    /**
     * 点赞/取消点赞（Lua 脚本保证原子性）
     */
    public LikeResult toggleLike(Long userId, Long contentId) {
        List<String> keys = Arrays.asList(
            "like:content:" + contentId,
            "like:count:" + contentId,
            "user:likes:" + userId
        );
        
        Long result = redisTemplate.execute(
            new DefaultRedisScript<>(LUA_LIKE, Long.class),
            keys,
            String.valueOf(userId)
        );
        
        boolean isLike = result == 1;
        
        // 异步发送事件（通知 + 持久化）
        kafkaTemplate.send("like-events", new LikeEvent(userId, contentId, isLike));
        
        return new LikeResult(isLike);
    }
    
    /**
     * 获取点赞数（带本地缓存降级）
     */
    public Long getLikeCount(Long contentId) {
        String countKey = "like:count:" + contentId;
        String count = redisTemplate.opsForValue().get(countKey);
        
        if (count != null) {
            return Long.parseLong(count);
        }
        
        // Redis 未命中 → 查 MySQL 兜底
        return likeMapper.selectCountByContentId(contentId);
    }
    
    /**
     * 批量获取点赞状态（判断当前用户是否点赞了多个内容）
     */
    public Map<Long, Boolean> getLikeStatus(Long userId, List<Long> contentIds) {
        // Pipeline 批量查询
        List<Object> results = redisTemplate.executePipelined(
            (RedisCallback<Object>) connection -> {
                for (Long contentId : contentIds) {
                    connection.sIsMember(
                        ("like:content:" + contentId).getBytes(),
                        String.valueOf(userId).getBytes()
                    );
                }
                return null;
            }
        );
        
        Map<Long, Boolean> statusMap = new HashMap<>();
        for (int i = 0; i < contentIds.size(); i++) {
            statusMap.put(contentIds.get(i), (Boolean) results.get(i));
        }
        return statusMap;
    }
}
```

```
冷热分离策略：

  │          │     │like-events│    │          │     │          │
  └──────────┘     └──────────┘     └──────────┘     └──────────┘
  
  优势：
  ① 写入路径短（Redis 即返回）→ 低延迟
  ② Kafka 异步解耦 → 不影响点赞体验
```

```java
public class LikeEventConsumer {

    private LikeRecordMapper mapper;
    
    private static final int BATCH_SIZE = 100;
    private final List<LikeEvent> buffer = new ArrayList<>();
    
    @KafkaListener(topics = "like-events")
    public void consume(LikeEvent event) {
        buffer.add(event);
        
        if (buffer.size() >= BATCH_SIZE) {
            // 批量 INSERT（使用 INSERT IGNORE 保证幂等）
            mapper.batchInsertOrDelete(buffer);
            buffer.clear();
        }
    }

        if (!buffer.isEmpty()) {
            mapper.batchInsertOrDelete(buffer);
            buffer.clear();
        }
    }
}
```

### 💡 延伸思考

1. **点赞系统如果用关系型数据库实现，瓶颈在哪里？** — 最主要瓶颈是写操作的锁竞争和磁盘 IO。热点内容每秒数万次写 → 行锁竞争严重 → 主库压力巨大。如果 INCR 也走数据库，MVCC 会导致 Undo Log 膨胀，且每次写入都是随机 IO。所以高并发点赞场景必须引入 Redis 作为写入缓冲。
2. **如果 Redis 宕机了怎么办？** — ① Redis Cluster 自动故障转移（Sentinel/Cluster 模式）；② 应用层降级：Redis 不可用 → 限流 → 仅允许查询（读降级）→ 写入到本地队列 → Redis 恢复后重放；③ 多级缓存兜底：本地 Caffeine Cache → Redis → MySQL，层层降级。
