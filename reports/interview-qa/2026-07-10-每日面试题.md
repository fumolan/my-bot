## 题目 1：[Java并发/JUC] 请详细说明 Java 线程池的核心参数、execute() 完整执行流程、常见拒绝策略以及动态调整线程池的最佳实践

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-10 午间报告 — "并发编程：线程池核心参数 ← 必考"
**相关岗位**：Java后端 / 全栈

### 📖 参考答案

#### 一、线程池核心参数（ThreadPoolExecutor 7大参数）

```java
public ThreadPoolExecutor(int corePoolSize,      // 核心线程数
                          int maximumPoolSize,   // 最大线程数
                          long keepAliveTime,    // 非核心线程空闲存活时间
                          TimeUnit unit,         // 时间单位
                          BlockingQueue<Runnable> workQueue, // 任务队列
                          ThreadFactory threadFactory,      // 线程工厂
                          RejectedExecutionHandler handler)  // 拒绝策略
```

**参数详解：**

| 参数 | 作用 | 默认值/常见选择 |
|------|------|----------------|
| corePoolSize | 核心线程数，即使空闲也不会回收 | CPU密集型：N+1；IO密集型：2N |
| maximumPoolSize | 最大线程数，线程池允许创建的最大线程数 | 根据系统资源估算 |
| keepAliveTime | 非核心线程空闲存活时间 | 通常 60s |
| workQueue | 阻塞队列，存放等待执行的任务 | 见下方队列对比 |
| threadFactory | 创建线程的工厂 | 自定义命名、守护线程 |
| handler | 拒绝策略 | 见下方拒绝策略对比 |

#### 二、工作队列对比

| 队列类型 | 特点 | 适用场景 |
|---------|------|---------|
| **SynchronousQueue** | 不存储任务，直接提交给线程 | 无界线程池场景 |
| **LinkedBlockingQueue** | 链表实现，默认无界（Integer.MAX_VALUE） | 任务较多且稳定的场景 |
| **ArrayBlockingQueue** | 数组实现，有界，需指定容量 | 防止任务堆积 |
| **PriorityBlockingQueue** | 支持优先级排序 | 任务有优先级需求 |
| **DelayQueue** | 延迟执行 | 定时任务场景 |

#### 三、execute() 完整执行流程

```
调用 execute(Runnable task)
       │
       ▼
  ① 判断当前工作线程数 < corePoolSize？
       ├─ 是 → 创建新核心线程执行任务
       └─ 否 → 进入步骤②
       
  ② 尝试将任务加入 workQueue（队列 offer）
       ├─ 成功 → 等待线程从队列中获取执行
       └─ 失败（队列已满）→ 进入步骤③
       
  ③ 判断当前工作线程数 < maximumPoolSize？
       ├─ 是 → 创建新非核心线程执行任务
       └─ 否 → 执行拒绝策略（handler.rejectedExecution）
```

**核心源码逻辑（JDK 17）：**

```java
public void execute(Runnable command) {
    if (command == null) throw new NullPointerException();
    
    int c = ctl.get();
    // 步骤①：工作线程 < corePoolSize
    if (workerCountOf(c) < corePoolSize) {
        if (addWorker(command, true))
            return;
        c = ctl.get();
    }
    // 步骤②：尝试入队
    if (isRunning(c) && workQueue.offer(command)) {
        int recheck = ctl.get();
        if (!isRunning(recheck) && remove(command))
            reject(command);
        else if (workerCountOf(recheck) == 0)
            addWorker(null, false);
    }
    // 步骤③：尝试创建非核心线程，失败则拒绝
    else if (!addWorker(command, false))
        reject(command);
}
```

#### 四、四大拒绝策略

| 拒绝策略 | 行为 | 风险 |
|---------|------|------|
| **AbortPolicy**（默认） | 直接抛出 RejectedExecutionException | 业务中断 |
| **CallerRunsPolicy** | 由提交任务的线程直接执行 | 阻塞调用方，降低提交速率 |
| **DiscardPolicy** | 静默丢弃任务 | 数据丢失 |
| **DiscardOldestPolicy** | 丢弃队列头部最旧任务，然后重试提交 | 旧任务丢失 |

#### 五、动态调整线程池（实战最佳实践）

**1. 线程数估算公式：**
- CPU密集型：`corePoolSize = CPU核数 + 1`
- IO密集型：`corePoolSize = CPU核数 × (1 + 等待时间/计算时间)`，通常 2N ~ 3N

**2. 动态调整方案：**
```java
// 允许核心线程超时回收（适用于突发流量场景）
threadPoolExecutor.allowCoreThreadTimeOut(true);

// 动态调整核心/最大线程数
ThreadPoolExecutor executor = (ThreadPoolExecutor) service;
executor.setCorePoolSize(newCoreSize);      // 调整核心线程
executor.setMaximumPoolSize(newMaxSize);    // 调整最大线程
executor.setKeepAliveTime(30, TimeUnit.SECONDS); // 调整空闲存活时间
```

**3. 监控指标（JMX/Micrometer）：**
```java
// 通过 ThreadPoolExecutor 的以下方法获取监控数据
executor.getPoolSize();          // 当前线程数
executor.getActiveCount();       // 活跃线程数
executor.getQueue().size();      // 队列积压数
executor.getCompletedTaskCount(); // 已完成任务数
executor.getTaskCount();         // 总任务数
executor.getLargestPoolSize();   // 历史最大线程数
```

**4. 最佳实践：**
- **禁止使用 Executors.newFixedThreadPool()** — 默认无界队列可能 OOM
- **禁止使用 Executors.newCachedThreadPool()** — 最大线程数 Integer.MAX_VALUE
- 推荐手动 new ThreadPoolExecutor，显式指定有界队列和拒绝策略
- 生产环境建议配合 ThreadPoolTaskExecutor + 自定义 RejectedExecutionHandler

## 题目 2：[框架/Spring Boot] Spring Boot 3.5 + GraalVM 原生镜像的原理是什么？请详细说明 AOT 编译的工作机制、与 JIT 的区别，以及反射/动态代理在原生镜像中的适配方案

**难度**：⭐⭐⭐⭐⭐
**考点来源**：2026-07-10 早间报告 — "Spring Boot 3.5正式普及：虚拟线程+GraalVM原生镜像，启动仅0.3秒，面试高频：AOT编译、反射/动态代理坑"
**相关岗位**：Java后端 / 全栈 / 基础架构

### 📖 参考答案

#### 一、JIT vs AOT：两种编译方式的核心区别

```
传统 JIT（Just-In-Time）模式：
┌─────────────────────────────────────────────────────────┐
│  Java源码 → 字节码(.class) → JVM加载 → 解释执行          │
│                                   ↓                      │
│                         热点代码 → JIT编译为机器码         │
│                         （运行时边跑边编译）               │
│  特点：启动慢（需预热），运行峰值性能高                      │
│  启动时间：2-5秒（Spring Boot 应用）                      │
│  内存占用：300-500MB                                     │
└─────────────────────────────────────────────────────────┘

GraalVM AOT（Ahead-Of-Time）模式：
┌─────────────────────────────────────────────────────────┐
│  Java源码 → 字节码(.class) → AOT编译 → 原生可执行文件     │
│                               （构建时静态编译为机器码）    │
│  特点：启动极快（毫秒级），无预热，内存占用低               │
│  启动时间：0.05-0.3秒（Spring Boot 3.5 原生镜像）         │
│  内存占用：80-120MB                                     │
│  缺点：编译慢（需静态分析），反射/动态代理受限              │
└─────────────────────────────────────────────────────────┘
```

#### 二、GraalVM AOT 编译的底层原理

**1. 闭合世界分析（Closed World Analysis）**

GraalVM 的 `native-image` 工具在构建时会执行**静态分析**，扫描所有可达的代码路径：

```
native-image 构建流程：
① 从 main() 方法入口开始
② 遍历所有方法调用链（包括反射调用声明）
③ 标记所有"可达"的类、方法、字段
④ 将这些代码一次性 AOT 编译为机器码
⑤ 生成不依赖 JVM 的可执行文件
```

**关键：** GraalVM 必须**在构建时就知道所有要使用的类**。运行时通过 Class.forName() 加载的类如果没有提前声明，在原生镜像中会直接报 ClassNotFoundException。

**2. 编译时 vs 运行时信息**

| 信息类型 | JIT 模式 | AOT 模式 |
|---------|---------|---------|
| 类加载 | 运行时按需加载 | 构建时全部确定 |
| 内联优化 | 运行时根据 profiling 信息 | 构建时静态推断 |
| 分支预测 | 运行时收集实际数据 | 无运行时 profiling |
| 反射 | 任意运行时可用 | 需提前注册 |

#### 三、反射和动态代理的"坑"及适配方案

**最大挑战：** Spring 重度依赖反射和动态代理，AOT 编译时需要提前"告知"GraalVM 哪些类会被反射/代理。

**适配方案 1：@RegisterReflectionForBinding**
```java
import org.springframework.aot.hint.annotation.RegisterReflectionForBinding;

@RegisterReflectionForBinding({UserDTO.class, OrderDTO.class, Result.class})
@SpringBootApplication
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}
```

**适配方案 2：RuntimeHints 注册**
```java
@Configuration
public class MyRuntimeHints implements RuntimeHintsRegistrar {
    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
        // 注册反射
        hints.reflection()
            .registerType(MyEntity.class, MemberCategory.INVOKE_PUBLIC_METHODS);
        
        // 注册资源文件
        hints.resources()
            .registerPattern("my-config/*");
        
        // 注册序列化
        hints.serialization()
            .registerType(MySerializable.class);
    }
}
```

**适配方案 3：reflect-config.json 配置文件**
```json
[
  {
    "name": "com.example.UserDTO",
    "methods": [
      {"name": "getName", "parameterTypes": []},
      {"name": "setName", "parameterTypes": ["java.lang.String"]}
    ],
    "fields": [
      {"name": "name"}
    ]
  }
]
```

**Spring Boot 3.5 的自动适配：**
Spring Boot 3.x 的 AOT 引擎已经内置了大部分自动配置类的反射提示。当你使用 `@EnableAutoConfiguration`、`@Controller`、`@Service` 等注解时，Spring 的 AOT 编译插件会自动生成对应的反射配置。但在以下场景仍需手动处理：
- 自定义序列化/反序列化（Jackson 自定义序列化器）
- 第三方库的反射调用（如 MyBatis 的 Mapper 代理）
- 动态类加载（Class.forName / ServiceLoader）
- 基于条件注解的自定义配置类

## 题目 3：[数据库/MySQL] 请详细说明 MySQL InnoDB 的事务隔离级别实现原理，包括四种隔离级别分别解决了什么问题，以及行锁、间隙锁（Gap Lock）和 Next-Key Lock 的工作机制

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-10 午间报告 — "MySQL：B+树索引、事务隔离级别、索引优化 ← 高频"
**相关岗位**：Java后端 / 全栈 / 数据库

### 📖 参考答案

#### 一、事务的四大隔离级别

SQL 标准定义了四种隔离级别，MySQL InnoDB 默认使用 **REPEATABLE READ（可重复读）**。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现机制 |
|---------|:----:|:---------:|:----:|---------|
| READ UNCOMMITTED（读未提交） | ❌ | ❌ | ❌ | 直接读最新数据，不加锁 |
| READ COMMITTED（读已提交） | ✅ | ❌ | ❌ | 每次查询生成新的 ReadView |
| REPEATABLE READ（可重复读） | ✅ | ✅ | ❌* | 事务开始时生成 ReadView，MVCC + Next-Key Lock |
| SERIALIZABLE（串行化） | ✅ | ✅ | ✅ | 所有读加行锁，并发极低 |

> *InnoDB 的 REPEATABLE READ 通过 Next-Key Lock 解决了大部分幻读问题，但并非绝对（如插入新数据时仍可能产生幻读）

#### 二、MVCC 与 ReadView 工作机制

**MVCC（多版本并发控制）** 是 InnoDB 实现隔离级别的核心机制。

**隐藏字段：**
```
每行数据包含三个隐藏列：
┌─────────────┬──────────────┬──────────────┐
│ DB_TRX_ID   │ DB_ROLL_PTR  │ DB_ROW_ID    │
│ (最后修改    │ (回滚指针，   │ (行ID，      │
│  事务ID)    │  指向Undo Log)│  自增)       │
└─────────────┴──────────────┴──────────────┘
```

**ReadView 判断规则：**
```
ReadView 包含：
┌──────────────────────────────┐
│ m_ids:    活跃事务ID列表     │
│ min_trx_id: 最小活跃事务ID    │
│ max_trx_id: 最大活跃事务ID+1  │
│ creator_trx_id: 创建该       │
│               ReadView的事务ID │
└──────────────────────────────┘

可见性判断（对某行数据的事务ID trx_id）：
① trx_id == creator_trx_id → 可见（自己修改的）
② trx_id < min_trx_id → 可见（已提交的旧事务）
③ trx_id >= max_trx_id → 不可见（未来事务）
④ trx_id 在 m_ids 中 → 不可见（活跃事务）
⑤ trx_id 不在 m_ids 中 → 可见（已提交）
```

**READ COMMITTED vs REPEATABLE READ 的 ReadView 区别：**
```
READ COMMITTED：
  每执行一次 SELECT 就生成一个新的 ReadView
  → 可以看到其他事务已提交的最新修改
  → 导致不可重复读

REPEATABLE READ：
  只在事务中第一次 SELECT 时生成 ReadView
  后续所有 SELECT 复用同一个 ReadView
  → 始终看到事务开始时的数据快照
  → 实现可重复读
```

#### 三、行锁（Record Lock）、间隙锁（Gap Lock）、Next-Key Lock

**1. Record Lock（行锁）**
```sql
-- 对索引记录加锁
SELECT * FROM user WHERE id = 10 FOR UPDATE;
-- 锁定 id=10 这条记录（主键索引上的行锁）
```

**2. Gap Lock（间隙锁）**
```sql
-- 锁定一个范围，但不包含记录本身
SELECT * FROM user WHERE age BETWEEN 20 AND 30 FOR UPDATE;
-- 锁定 (20,30) 这个区间，阻止其他事务在此区间插入新记录
```

**3. Next-Key Lock（临键锁）= Record Lock + Gap Lock**
```
InnoDB 默认使用 Next-Key Lock 解决幻读。

假设表中有数据：id: 5, 10, 15, 20

Next-Key Lock 锁定的范围：
(-∞, 5]
(5, 10]
(10, 15]
(15, 20]
(20, +∞)

当执行：SELECT * FROM user WHERE id = 10 FOR UPDATE;
锁定的范围是 (5, 10] —— 即 gap lock(5,10) + record lock(10)
阻止其他事务插入 id=6,7,8,9 的新行（防止幻读）
```

#### 四、不同隔离级别的锁策略对比

| 隔离级别 | 读操作 | 写操作 |
|---------|-------|-------|
| READ UNCOMMITTED | 不加锁 | 行锁 |
| READ COMMITTED | 不加锁（MVCC） | 行锁（间隙锁关闭） |
| REPEATABLE READ | 不加锁（MVCC） | 行锁 + 间隙锁 + Next-Key Lock |
| SERIALIZABLE | 所有 SELECT 隐式加共享锁 | 行锁 + 间隙锁 + Next-Key Lock |

**特别说明：**
- InnoDB 的间隙锁**只在 REPEATABLE READ 及以上级别生效**
- READ COMMITTED 级别下，间隙锁被禁用，因此可能出现幻读
- 如果查询条件使用了唯一索引且能精确匹配到记录，Next-Key Lock 退化为 Record Lock

#### 五、死锁案例分析

**常见死锁场景：并发下单**
```sql
-- 事务A
UPDATE inventory SET stock = stock - 1 WHERE product_id = 1;
UPDATE inventory SET stock = stock - 1 WHERE product_id = 2;

-- 事务B
UPDATE inventory SET stock = stock - 1 WHERE product_id = 2;
UPDATE inventory SET stock = stock - 1 WHERE product_id = 1;

-- 如果 A 锁了 product_id=1，B 锁了 product_id=2
-- A 等待 B 释放 2，B 等待 A 释放 1 → 死锁！
```

**排查方法：**
```sql
-- 查看最近一个死锁日志
SHOW ENGINE INNODB STATUS;

-- 查看当前锁信息
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;
```

**预防策略：**
1. 统一资源访问顺序（如按 product_id 升序加锁）
2. 拆分大事务为小事务
3. 使用 `lock_timeout` 设置超时
4. 在低峰期执行批量更新操作

## 题目 4：[微服务/分布式] 请详细说明分布式事务的核心解决方案，包括 Seata AT、TCC、Saga 和 XA 四种模式的工作原理、适用场景和优劣势对比

**难度**：⭐⭐⭐⭐⭐
**考点来源**：2026-07-10 午间报告 — "分布式系统：分布式事务 ← 高频"
**相关岗位**：Java后端 / 全栈 / 微服务架构

### 📖 参考答案

#### 一、为什么需要分布式事务？

微服务架构下，一个业务操作可能跨越多个服务、多个数据库：

```
用户下单场景（跨服务）：
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ 订单服务  │   │ 库存服务  │   │ 账户服务  │   │ 积分服务  │
│ 创建订单  │   │ 扣减库存  │   │ 扣减余额  │   │ 增加积分  │
└──────────┘   └──────────┘   └──────────┘   └──────────┘
     ↓              ↓              ↓              ↓
  ┌─────────────────────────────────────────────────────┐
  │  需要保证：要么全部成功，要么全部回滚                 │
  │  （分布式事务的一致性要求）                           │
  └─────────────────────────────────────────────────────┘
```

#### 二、四种分布式事务方案详解

##### 方案一：XA 协议（强一致性）

**原理：** 基于数据库层的 XA 协议，两阶段提交（2PC）

```
第一阶段（Prepare）：
协调者 → 参与者1：预备提交？
协调者 → 参与者2：预备提交？
参与者 → 协调者：OK / 失败

第二阶段（Commit/Rollback）：
协调者 → 所有参与者：提交！（如果第一阶段全部OK）
协调者 → 所有参与者：回滚！（如果第一阶段有失败）
```

| 优势 | 劣势 |
|------|------|
| 强一致性（ACID） | 性能差（需要锁定资源直到事务结束） |
| 对业务代码侵入小 | 协调者是单点风险 |
| 数据库原生支持 | 阻塞协议，可用性低 |
| 适合短事务 | 不适合高并发场景 |

##### 方案二：Seata AT 模式（自动补偿）

**原理：** 自动生成回滚 SQL，对业务代码几乎无侵入

```
Seata AT 执行流程：
① 执行业务 SQL：UPDATE inventory SET stock = stock - 1 WHERE id = 1
② Seata 自动记录"前镜像"和"后镜像"到 undo_log 表
   ┌──────────────────┐
   │ 前镜像（before）   │ stock=10
   │ 后镜像（after）    │ stock=9
   └──────────────────┘
③ 正常提交业务 SQL
④ 全局提交 → 删除 undo_log
⑤ 全局回滚 → 用"前镜像"数据生成逆向 SQL 恢复
```

**Seata AT 工作流程：**
```
┌─────────┐     ┌──────────┐     ┌──────────┐
│  TM     │     │  RM-订单  │     │  RM-库存  │
│ (事务   │     │ (资源    │     │ (资源    │
│  发起者)│     │  管理器1) │     │  管理器2) │
└────┬────┘     └────┬─────┘     └────┬─────┘
     │                │                │
     │ 1. 开始全局事务 │                │
     │────────────────→ TC(事务协调者)  │
     │                │                │
     │ 2. 执行业务     │                │
     │────────────────→                │
     │                │ 3. 注册分支     │
     │                │───────────────→│
     │                │ 4. 执行业务     │
     │                │───────────────→│
     │                │                │
     │ 5. 全局提交     │                │
     │────────────────→ TC             │
     │                │                │
     │                │ 6. 通知各RM提交 │
     │                │←──────────────→│
```

| 优势 | 劣势 |
|------|------|
| 对业务代码几乎零侵入 | 需要全局锁，长事务下性能下降 |
| 自动生成逆向 SQL | undo_log 表会占用额外存储 |
| 性能优于 XA（非阻塞） | 不适用于跨语言的异构系统 |

##### 方案三：TCC 模式（补偿型）

**原理：** 业务层面实现 Try-Confirm-Cancel 三个接口

```
TCC 三阶段：
┌───────────────────────────────────────────┐
│ Try（预留资源）                            │
│   ├─ 订单服务：创建"待支付"订单             │
│   ├─ 库存服务：预扣库存（冻结库存）          │
│   └─ 账户服务：冻结金额                    │
│                                           │
│ Confirm（确认执行）—— 如果所有 Try 成功     │
│   ├─ 订单服务：订单状态改为"已支付"          │
│   ├─ 库存服务：实际扣减冻结库存              │
│   └─ 账户服务：实际扣减冻结金额              │
│                                           │
│ Cancel（取消回滚）—— 如果有 Try 失败        │
│   ├─ 订单服务：删除"待支付"订单              │
│   ├─ 库存服务：释放冻结库存                  │
│   └─ 账户服务：解冻金额                     │
└───────────────────────────────────────────┘
```

**TCC 接口示例（Java）：**
```java
@TwoPhaseBusinessAction(name = "orderTcc", 
    commitMethod = "confirm", rollbackMethod = "cancel")
public boolean try(@BusinessActionContextParameter(paramName = "orderId") 
                   Long orderId,
                   @BusinessActionContextParameter(paramName = "amount") 
                   BigDecimal amount) {
    // Try：创建待支付订单，冻结库存
    return orderService.freezeOrder(orderId, amount);
}

public boolean confirm(BusinessActionContext context) {
    // Confirm：确认订单
    return orderService.confirmOrder(context.getActionContext("orderId"));
}

public boolean cancel(BusinessActionContext context) {
    // Cancel：取消订单，释放冻结资源
    return orderService.cancelOrder(context.getActionContext("orderId"));
}
```

| 优势 | 劣势 |
|------|------|
| 性能极高（无全局锁） | 业务侵入大，需实现三个接口 |
| 资源释放及时 | 幂等性设计复杂 |
| 适合长事务、高并发 | 空回滚、悬挂问题需额外处理 |

##### 方案四：Saga 模式（事件驱动）

**原理：** 长事务拆分为多个本地事务，每个事务有对应的补偿操作

```
Saga 执行流程（串行/并行）：

正向操作链：
  T1（订单创建）→ T2（库存扣减）→ T3（支付扣款）→ T4（积分增加）
  
异常回滚链（从失败点开始反向补偿）：
                 C3（退款）← C2（加回库存）← C1（取消订单）
```

**Saga 的两种实现方式：**

| 方式 | 描述 | 优点 | 缺点 |
|-----|------|------|------|
| **编排（Choreography）** | 每个服务完成后发消息触发下一个服务 | 去中心化，简单 | 服务耦合度高 |
| **协调（Orchestrator）** | 中央协调器负责编排各服务的调用顺序 | 可管理性强 | 协调器单点风险 |

| 优势 | 劣势 |
|------|------|
| 适合长事务（秒级到分钟级） | 不保证隔离性（中间结果可见） |
| 高可用，无阻塞 | 补偿逻辑复杂 |
| 适合事件驱动架构 | 需要处理最终一致性带来的业务复杂度 |

#### 三、四种方案对比总结

| 维度 | XA | Seata AT | TCC | Saga |
|-----|:---:|:--------:|:---:|:----:|
| **一致性** | 强一致性 | 最终一致性 | 最终一致性 | 最终一致性 |
| **业务侵入** | 低 | 极低 | 高 | 中 |
| **性能** | 差 | 中 | 高 | 高 |
| **适用场景** | 短事务、强一致性要求 | 对一致性要求高的微服务 | 高并发、资源预留型 | 长事务、事件驱动 |
| **典型框架** | Atomikos | Seata | Seata / ByteTCC | Seata / ServiceComb |
| **复杂度** | 低 | 低 | 高 | 中 |

#### 一、什么是 Function Calling？

Function Calling（函数调用/工具调用）是大模型与外部系统交互的核心能力。它允许大模型**识别用户意图并输出结构化的函数调用参数**，而不是直接执行函数——实际执行仍由应用程序完成。

```
Function Calling 流程：

用户：明天北京天气怎么样？
       │
       ▼
① 大模型判断意图 → 输出结构化调用
   {
     "function": "get_weather",
     "arguments": {
       "city": "北京",
       "date": "2026-07-11"
     }
   }
       │
       ▼
② 应用程序收到参数 → 调用真实 API
   get_weather(city="北京", date="2026-07-11")
       │
       ▼
③ 返回结果给大模型
   {"temperature": "28-35°C", "condition": "晴"}
       │
       ▼
④ 大模型生成最终回复
   "明天北京天气晴朗，气温28-35°C，记得防暑哦！"
```

**关键认知：** 大模型**不执行函数**，它只是根据用户的自然语言输入，判断需要调用哪个函数，并**生成符合函数签名的 JSON 参数**。实际调用由业务系统完成。

**Python 实现（OpenAI SDK）：**

```python
import json
from openai import OpenAI

client = OpenAI()

# 定义工具函数
def get_weather(city: str, date: str) -> str:
    """模拟获取天气"""
    return json.dumps({"temperature": "28-35", "condition": "晴"})

# 注册工具 Schema
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "获取指定城市的天气预报",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string"},
                "date": {"type": "string"}
            },
            "required": ["city", "date"]
        }
    }
}]

# 主循环
def chat_with_tools(messages):
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=messages,
        tools=tools,
        tool_choice="auto"
    )
    
    message = response.choices[0].message
    
    # 检查是否有工具调用
    if message.tool_calls:
        for tool_call in message.tool_calls:
            if tool_call.function.name == "get_weather":
                args = json.loads(tool_call.function.arguments)
                result = get_weather(**args)
                messages.append(message)
                messages.append({
                    "role": "tool",
                    "tool_call_id": tool_call.id,
                    "content": result
                })
        # 将工具结果送回模型生成最终回答
        return chat_with_tools(messages)
    
    return message.content
```
