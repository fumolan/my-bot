## 题目 1：[JVM/并发] Java 21/25 虚拟线程（Project Loom）原理与实战：请详细阐述虚拟线程的 M:N 调度模型、Continuation 挂起机制、与平台线程的底层差异、如何用虚拟线程重构 IO 密集型服务，以及 CPU 密集型场景下为什么不能无脑替换线程池

**难度**：⭐⭐⭐⭐⭐
**考点来源**：2026-05-30 午间+晚间日报 — "Java虚拟线程（Project Loom）面试必问" + "JDK 21/25 LTS 正式落地"  
**相关岗位**：Java后端 / 中间件开发 / 高性能系统

### 📖 参考答案

**一、虚拟线程解决了什么问题？**

传统 Java 并发模型中，一个线程 = 一个 OS 线程（JVM 与 OS 是 1:1 映射）。这意味着：
- OS 线程创建开销大（栈空间 ~1MB，创建耗时 ~1ms）
- 上下文切换涉及内核态切换（昂贵）
- 一台普通服务器最多只能支撑数千个线程

而 2026 年微服务场景下，一个服务可能同时处理数万个 WebSocket 连接、HTTP 长轮询或 gRPC Stream——传统线程模型根本无法承载。虚拟线程（Virtual Threads）的答案是：**让线程变成轻量级的 JVM 对象，不再与 OS 线程一一对应**。

**二、M:N 调度模型**

```
传统线程模型（1:1）：
  Thread → OS Thread（Pthread / LWP）→ CPU Core

虚拟线程模型（M:N）：
  Virtual Thread（N 个）→ Carrier Thread / Platform Thread（M 个）→ CPU Core
  ↑ 轻量级，JVM管理         ↑ 真正占 OS 资源的线程（线程池）
```

| 维度 | 平台线程 (Platform Thread) | 虚拟线程 (Virtual Thread) |
|------|--------------------------|------------------------|
| 映射 | 1:1 绑定 OS 线程 | M:N 多路复用到平台线程 |
| 创建耗时 | ~1ms（OS 级） | ~1μs（纯 Java 对象） |
| 栈空间 | ~1MB（预分配） | 动态增长，从几百字节开始 |
| 最大数量 | 数千（受 OS 限制） | 百万级（受堆内存限制） |
| 上下文切换 | 内核态（昂贵） | 用户态（JVM 级别，极快） |

**三、Continuation 挂起机制（核心原理）**

虚拟线程的"轻量"秘密在于 **Continuation**（延续点）。当虚拟线程执行 IO 阻塞操作时：

```java
// 伪代码：虚拟线程执行流
public void run() {
    // ① 正常执行
    readFromNetwork();  // ← 遇到阻塞 IO
    
    // ② JVM 检测到阻塞 → 触发 Continuation.yield()
    //    保存当前线程栈到堆内存（序列化为字节数组）
    
    // ③ 释放 Carrier Thread（平台线程可以执行其他虚拟线程）
    
    // ④ IO 完成 → Continuation 从堆内存恢复栈 → 继续执行
    //    注意：可能被分配到不同的 Carrier Thread！
}
```

**关键**：虚拟线程的 yield 是**协作式**的——只有在执行阻塞操作时才会挂起。纯 CPU 计算从不 yield（因为不需要等待）。

**四、创建虚拟线程的 3 种方式**

```java
// 方式 1：Thread.ofVirtual()
Thread vt = Thread.ofVirtual()
    .name("vt-handler")
    .start(() -> {
        // 每个请求一个虚拟线程，不需要线程池！
        handleRequest();
    });

// 方式 2：Executors.newVirtualThreadPerTaskExecutor()
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    // 提交百万级任务不阻塞！
    IntStream.range(0, 1_000_000).forEach(i -> {
        executor.submit(() -> processTask(i));
    });
}

// 方式 3：Spring Boot 3.x 开启虚拟线程
// application.yml
spring:
  threads:
    virtual:
      enabled: true  // Spring Boot 3.2+ → Tomcat 每个请求一个虚拟线程
```

**五、实战场景：用虚拟线程重构高并发 IO 服务**

```java
// ❌ 传统方案：固定线程池
@GetMapping("/fetch-multi")
public List<Result> fetchMultiple(@RequestParam List<String> urls) {
    ThreadPoolExecutor executor = new ThreadPoolExecutor(
        200, 200, 60, SECONDS, new LinkedBlockingQueue<>(1000)
    );
    // 200 个线程 → 最多同时支持 200 并发
    // 每个线程阻塞等待 HTTP 响应 → 资源浪费
    return urls.stream()
        .map(url -> CompletableFuture.supplyAsync(() -> fetch(url), executor))
        .map(CompletableFuture::join)
        .collect(toList());
}

// ✅ 虚拟线程方案：不需要线程池！
@GetMapping("/fetch-multi-vt")
public List<Result> fetchMultipleVt(@RequestParam List<String> urls) {
    try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
        return urls.stream()
            .map(url -> CompletableFuture.supplyAsync(() -> fetch(url), executor))
            .map(CompletableFuture::join)
            .collect(toList());
    }
    // 随时可处理 10 万并行请求！
}
```

**六、虚拟线程的陷阱与限制**

| 场景 | 是否适合虚拟线程 | 原因 |
|------|----------------|------|
| Web 服务器（Tomcat/Jetty） | ✅ 非常适合 | 每个请求一个 VT，减少线程池配置 |
| 数据库访问（JDBC 阻塞） | ✅ 非常适合 | 阻塞时释放 Carrier Thread |
| HTTP 调用（RestTemplate） | ✅ 非常适合 | 同上 |
| **CPU 密集型计算**（加密/压缩） | ❌ **不适合** | 不阻塞就不 yield，增加调度开销 |
| **synchronized 同步块** | ⚠️ 可能 pinned | JDK 21 中 synchronized 会固定 Carrier Thread |
| **JNI 调用** | ⚠️ 可能 pinned | 原生代码无法 yield |

**陷阱预警**：如果在虚拟线程中使用 `synchronized` 或 `ReentrantLock`（JDK 21 默认），虚拟线程会被 **pinned** 到 Carrier Thread，丧失轻量级优势。生产环境建议用 `ReentrantLock` + 虚拟线程或 `Semaphore` 替代 `synchronized`。

调试开关：
```bash
# 检测被 pinned 的虚拟线程
-Djdk.tracePinnedThreads=full   # 打印完整栈，高亮 pinned 位置
-Djdk.virtualThreadScheduler.parallelism=16  # 调整 Carrier Thread 数量
```

## 题目 2：[框架/Spring] 请详细阐述 GraalVM Native Image + Spring Boot 3.x AOT 编译原理：包括 AOT 与 JIT 的核心差异、Spring AOT 引擎如何在构建阶段解决反射/动态代理/资源解析等封闭世界假设问题、GraalVM 原生镜像构建流程与配置文件生成机制，以及生产环境下使用原生镜像的收益与代价

**难度**：⭐⭐⭐⭐
**考点来源**：2026-05-30 晚间日报 — "GraalVM原生编译：Spring Boot 3.x + GraalVM 已稳定生产使用"  
**相关岗位**：Java后端 / 云原生架构 / 微服务开发

### 📖 参考答案

**一、JIT vs AOT：两种编译哲学的对比**

传统 Java 应用 == Java 字节码 + JVM + JIT 编译。而 AOT（Ahead-of-Time）是在**应用启动前**就编译成机器码——直接生成可执行文件。

| 维度 | JIT（HotSpot） | AOT（GraalVM Native Image） |
|------|---------------|---------------------------|
| 编译时机 | 运行时，按热点编译 | 构建时，全量编译 |
| 启动速度 | 1~10 秒（含 JVM 初始化 + 类加载 + JIT 预热） | **毫秒级**（如 0.07 秒 vs 传统 1 秒） |
| 内存占用 | 大（JVM 本身占用 + Code Cache + Metaspace） | **低 50%~80%**（不含 JVM） |
| 峰值性能 | ⭐⭐⭐⭐⭐ （热点代码优化极致） | ⭐⭐⭐ （缺少运行时 profiling） |
| 构建时长 | 秒级 | **分钟级**（需要全量分析 + 编译） |
| 反射/动态代理 | 运行时天然支持 | ❌ 需要构建时提前声明（封闭世界假设） |
| 部署方式 | java -jar xxx.jar（依赖 JRE） | 独立可执行文件（几十 MB，轻量） |

**二、封闭世界假设（Closed World Assumption）—— AOT 的最大挑战**

GraalVM 在构建时必须知道**应用所有用到的类、方法、字段**，这就叫"封闭世界假设"。但 Java 生态天生是"开放的"：

```java
// ① 反射：运行前根本不知道会加载哪个类
Class<?> clazz = Class.forName("com.example." + className);
Method method = clazz.getMethod("execute");
method.invoke(obj);

// ② 动态代理：由 JVM 运行时生成代理类
Proxy.newProxyInstance(loader, interfaces, handler);

// ③ SPI / ServiceLoader：运行时扫描 classpath
ServiceLoader.load(DataSource.class);

// ④ CGLIB 动态代理：Spring AOP 的基础
Enhancer enhancer = new Enhancer();
enhancer.setSuperclass(UserService.class);
```

这些"运行时才知道"的行为，在 GraalVM 构建时**全部不可见**。如果不提前告诉 GraalVM，编译出来的原生镜像运行时就会报 `ClassNotFoundException`。

**三、Spring AOT 引擎如何解决？**

Spring Boot 3.x 引入的 **Spring AOT 引擎**，在构建阶段提前完成了三件事：

```
构建阶段（mvn package -Pnative）：
  ① 分析 Bean 定义
     ↓
  ② 生成反射配置（reflect-config.json）
  ③ 生成动态代理配置（proxy-config.json）
  ④ 生成资源配置（resource-config.json）
  ⑤ 生成序列化配置（serialization-config.json）
     ↓
GraalVM 读取配置 → 所有"运行时动态"被提前确认 → 编译为原生镜像
```

```java
// Spring AOT 在构建时自动生成的配置（位于 target/ 下）
// reflect-config.json 示例（自动生成）：
[
    {
        "name": "com.example.UserService",
        "methods": [{"name": "findUser", "parameterTypes": ["java.lang.Long"]}]
    }
]
```

**核心机制**：Spring AOT 引擎在构建时**完整执行一次 ApplicationContext 的初始化流程**，扫描所有 Bean 定义、注解、配置属性——把此次扫描发现的反射、代理、资源调用全部记录下来，生成 GraalVM 需要的配置文件。

```xml
<!-- Maven 配置：一条命令搞定 AOT 编译 -->
<plugin>
    <groupId>org.graalvm.buildtools</groupId>
    <artifactId>native-maven-plugin</artifactId>
    <configuration>
        <buildArgs>
            <arg>--enable-url-protocols=https</arg>
            <arg>--no-fallback</arg>
            <arg>--static</arg>
            <arg>-H:+ReportExceptionStackTraces</arg>
        </buildArgs>
    </configuration>
</plugin>
```

```bash
# 构建原生镜像（耗时 2~10 分钟）
mvn -Pnative native:compile

# 运行（毫秒级启动！）
./target/my-app
```

**四、Spring AOT 在 Bean 注册阶段的优化**

除了生成配置，Spring AOT 还会**在构建时生成 Bean 注册代码**：

```java
// 传统 Spring Boot 启动过程：
// 1. 扫描 @Configuration
// 2. 解析 @Bean 方法
// 3. 处理 @Conditional
// 4. 反射调用工厂方法
// 5. 依赖注入

// Spring AOT 优化后（构建阶段）： 
// 生成 BeanDefinitionRegistriesInitializer 类
// 直接在代码中"硬编码"所有 Bean 创建逻辑
// 运行时跳过了扫描、反射、条件判断 → 启动速度极快
```

```java
// AOT 生成的优化代码（运行时不再需要反射）：
@Generated
public class MainApplication__BeanDefinitions {
    public static UserService userService() {
        return new UserService(userRepository());
    }
    public static UserRepository userRepository() {
        return new JdbcUserRepository(dataSource());
    }
    // 所有 Bean 的工厂方法都在这里了！
}
```

**五、生产环境收益与代价**

| 项目 | 传统 JAR | GraalVM Native Image |
|------|---------|---------------------|
| 启动时间 | 3~8 秒 | **30~80 毫秒** |
| 内存占用（空载） | 150~300 MB | **25~60 MB** |
| 镜像大小 | 20 MB（JAR） | **40~80 MB（可执行文件）** |
| 首次请求延迟 | 需 JIT 预热（可能有秒级延迟） | **即时响应** |
| 云原生/Serverless 适配 | 差（启动慢 → 冷启动延迟高） | **极适合** |

**适用场景**：
- ✅ **Serverless / FaaS**：Lambda 函数冷启动从秒级降到毫秒级
- ✅ **边缘计算 / IoT**：低内存设备，无 JRE 环境
- ✅ **容器化部署**：Docker 镜像从 200MB 降到 50MB
- ✅ **微服务动态扩缩容**：弹出一个新实例只需要 100ms
- ❌ **长期运行的单体应用**：JIT 预热后性能反而优于 AOT

**不适用于**：
- 大量使用反射、动态代理的遗留系统（改造成本高）
- 需要运行时类加载的场景（如热部署、插件系统）
- 构建时间敏感的场景（AOT 构建 2~10 分钟，比普通编译慢百倍）

## 题目 3：[数据库/MySQL] 请详细解释 MySQL InnoDB 的 MVCC（多版本并发控制）原理：包括行隐藏字段（DB_TRX_ID / DB_ROLL_PTR）、undo log 版本链的构建流程、ReadView 的可见性判断算法、以及 RC 与 RR 隔离级别下 ReadView 生成时机的差异

**难度**：⭐⭐⭐⭐
**考点来源**：2026-05-30 午间+晚间日报 — "数据库：MySQL索引优化、慢查询、分库分表"技能风向 + "并发编程"作为面试高频考点  
**相关岗位**：Java后端 / DBA / 全栈开发

### 📖 参考答案

**一、MVCC 要解决什么问题？**

在没有 MVCC 的数据库中，如果一个事务正在写数据，其他事务读这个数据必须等待写锁释放——读和写互斥。MVCC 的答案：**每个事务都能看到数据的"快照"版本，读不阻塞写，写不阻塞读**。

**二、InnoDB 行记录的三个隐藏字段**

InnoDB 每行数据除了用户定义的字段外，还有三个隐式字段：

```sql
-- InnoDB 行记录的真正结构（隐藏字段 + 用户字段）
+------------+---------------+----------------+---------------------+
| DB_TRX_ID  | DB_ROLL_PTR   | DB_ROW_ID*     | 用户自定义字段...   |
+------------+---------------+----------------+---------------------+

DB_TRX_ID（6字节）：最后修改该行的事务 ID
DB_ROLL_PTR（7字节）：指向该行的 undo log 记录（回滚指针）
DB_ROW_ID（6字节）：自增行 ID（仅当没有主键时存在）
*说明：①表中一定有一个 row_id。如果用户没定义主键且没有非空唯一键，InnoDB 用这个；
        ②如果定义了主键或非空唯一键，则用于聚簇索引排序，但不作为隐藏字段暴露
```

**三、undo log 版本链的构建**

每当一个事务修改一行数据，InnoDB 不是直接覆盖旧的记录，而是：

```sql
-- 初始状态（事务 T100 插入）：
INSERT INTO user(id, name) VALUES(1, '张三');
-- 行数据：DB_TRX_ID=100, name='张三', roll_pointer=null

-- 事务 T200 更新（不覆盖，而是创建新版本）：
UPDATE user SET name='李四' WHERE id=1;
-- undo log 记录：记下"把李四改回张三"的回滚信息
-- 新行：DB_TRX_ID=200, name='李四'
--        roll_pointer ─────→ 旧版：DB_TRX_ID=100, name='张三', roll_pointer=null
--                               ↑ 这就是 undo log 版本链！

-- 事务 T300 再更新：
UPDATE user SET name='王五' WHERE id=1;
-- undo log 记录：记下"把王五改回李四"
-- 新行：DB_TRX_ID=300, name='王五'
--        roll_pointer ─────→ DB_TRX_ID=200, name='李四'
--                              roll_pointer ─────→ DB_TRX_ID=100, name='张三'
```

```
版本链可视化：

最新记录                    undo log 链
┌─────────────┐    ┌──────────────┐    ┌──────────────┐
│ trx_id=300  │ →  │ trx_id=200  │ →  │ trx_id=100  │
│ name='王五' │    │ name='李四'  │    │ name='张三'  │
│ roll_pointer│    │ roll_pointer│    │ roll_pointer│→ null
└─────────────┘    └──────────────┘    └──────────────┘
  最新版本           历史版本1           历史版本2
```

**四、ReadView 可见性判断算法（面试画图题）**

ReadView 是 MVCC 判断"当前事务能看到哪些版本"的核心数据结构。它包含四个核心字段：

```java
class ReadView {
    // 当前活跃事务 ID 列表（执行中未提交的）
    Set<Long> m_ids;                 
    
    // 下一个将要分配的事务 ID（系统上限）
    // 所有 trx_id ≥ up_limit_id 的事务，在 ReadView 创建时都还没开始
    long m_low_limit_id;             
    
    // 活跃事务中的最小 ID
    // 所有 trx_id < low_limit_id 的事务，在 ReadView 创建时已提交
    long m_up_limit_id;              
    
    // 创建 ReadView 的事务自己的 ID
    long m_creator_trx_id;           
}
```

**可见性判断算法（面试必背）**：

```
判断某版本（trx_id）对当前 ReadView 是否可见：

  ① trx_id == m_creator_trx_id？
     └─ 是 → 就是自己修改的，可见 ✅
  
  ② trx_id < m_up_limit_id？
     └─ 是 → 该事务在 ReadView 创建前已提交，可见 ✅
  
  ③ trx_id ≥ m_low_limit_id？
     └─ 是 → 该事务在 ReadView 创建后才开始，不可见 ❌
  
  ④ m_ids.contains(trx_id)？
     └─ 是 → 该事务创建 ReadView 时还在活跃（未提交），不可见 ❌
     └─ 否 → 该事务已提交，可见 ✅

  如果当前版本不可见 → 沿 roll_pointer 找上一个版本 → 递归判断
  直到找到可见版本 或 版本链到尽头（说明数据被删除了）
```

**五、RC 与 RR 的核心差异：ReadView 生成时机**

| 隔离级别 | ReadView 生成时机 | 效果 |
|---------|-----------------|------|
| RC（读已提交） | **每条 SQL 执行前都生成新的 ReadView** | 每次查询都能看到其他事务最新提交的数据 |
| RR（可重复读） | **事务中第一次 SELECT 时生成，整个事务复用** | 事务内多次查询看到相同快照，保证可重复读 |

```sql
-- RC 隔离级别下：
事务 A：
  BEGIN;
  SELECT * FROM user WHERE id = 1;  -- 生成 ReadView_1 → 看到 name='张三'
  -- 此时事务 B 提交：UPDATE user SET name='李四' WHERE id=1; COMMIT;
  SELECT * FROM user WHERE id = 1;  -- 生成 ReadView_2 → 看到 name='李四'！
  -- ↑ RC 的特性：可能读到其他事务已提交的最新数据

-- RR 隔离级别下：
事务 A：
  BEGIN;
  SELECT * FROM user WHERE id = 1;  -- 生成 ReadView → 看到 name='张三'
  -- 此时事务 B 提交：UPDATE user SET name='李四' WHERE id=1; COMMIT;
  SELECT * FROM user WHERE id = 1;  -- 复用之前的 ReadView → 仍然看到 name='张三'！
  -- ↑ RR 的特性：同一事务内多次读结果不变
```

**六、RR 如何解决幻读？**

MVCC 的 ReadView 只能解决**快照读**（普通的 SELECT）的幻读。对于**当前读**（SELECT ... FOR UPDATE / UPDATE / DELETE），MVCC 不够用，需要配合 **Next-Key Lock（间隙锁 + 行锁）**：

```
当前读时的 Gap Lock 示例：
  SELECT * FROM user WHERE age BETWEEN 20 AND 30 FOR UPDATE;
  
  锁定的区间：
  (-∞, 20] → (20, 30] → (30, +∞)
   ↑              ↑          ↑
  记录锁      间隙锁+记录锁   记录锁
  
  其他事务无法在此区间插入新行 → 防止幻读
```

**七、小结：MVCC 完整工作流程**

```
一个 SELECT 请求到来：

  读操作类型？
  ├─ 快照读（普通 SELECT）
  │    ↓
  │  RC: 创建 ReadView → 沿版本链查找可见版本 → 返回
  │  RR: 复用事务首个 ReadView → 沿版本链查找 → 返回（保证可重复读）
  │
  └─ 当前读（SELECT FOR UPDATE / UPDATE / DELETE）
       ↓
      加锁（Next-Key Lock / 行锁）
      ↓
      读取最新版本的数据（不使用 MVCC 快照）
```

## 题目 4：[微服务/分布式] Seata 分布式事务四种事务模式深入对比：请详细阐述 Seata AT（自动补偿）、TCC（编程式补偿）、SAGA（长事务）、XA（数据库原生）四种模式的核心原理、执行流程、一致性保证级别，以及生产环境下不同业务场景的选型策略

**难度**：⭐⭐⭐⭐
**考点来源**：2026-05-30 晚间日报 — "分布式：Redis、Kafka、分布式事务、微服务"面试高频考点  
**相关岗位**：Java后端 / 微服务架构 / 分布式系统

### 📖 参考答案

**一、Seata 的核心架构（三大角色）**

```
Seata 架构：
┌─────────────────────────────────────────────────────────────────┐
│  客户端                                      │    服务端         │
│  TM（事务管理器）←──────────────────→ TC（事务协调器）          │
│    ↑ 定义全局事务的边界                        │  维护全局事务状态 │
│    ↓                                        │  处理提交/回滚     │
│  RM（资源管理器）←──────────────────→        │                    │
│   操作 DB/Kafka 等资源，报告分支状态           │                    │
└─────────────────────────────────────────────────────────────────┘
```

- **TC（Transaction Coordinator）**：事务协调器，独立部署的服务端，维护全局事务的运行状态
- **TM（Transaction Manager）**：事务管理器（业务方），定义全局事务的边界（@GlobalTransactional）
- **RM（Resource Manager）**：资源管理器（业务方），管理分支事务资源，报告分支状态

**二、四种事务模式详解**

### AT 模式（自动补偿）—— 最常用，无侵入

AT 模式的核心是**自动生成回滚 SQL**，业务代码零侵入。

```
AT 模式执行流程：
① TM 向 TC 注册全局事务 → 拿到 XID
② RM 执行业务 SQL（如 UPDATE account SET balance=balance-100 WHERE id=1）
   ├─ 执行前：解析 SQL → 获取修改前的数据快照（Before Image）
   ├─ 执行中：执行目标 SQL
   └─ 执行后：获取修改后的数据快照（After Image）
       → Before Image + After Image 写入 undo_log 表
③ RM 向 TC 报告分支事务状态
④ 正常情况 → TM 通知 TC 全局提交 → TC 协调所有 RM 提交 → 清理 undo_log
⑤ 异常情况 → TM 通知 TC 全局回滚 → TC 协调 RM 回滚
   → RM 读取 undo_log 中的 Before Image → 自动生成反向 SQL 恢复数据
```

```java
// AT 模式：只需一个注解，零代码侵入
@GlobalTransactional
public void createOrder(OrderDTO order) {
    orderService.create(order);           // 插入订单表
    inventoryService.deduct(order);       // 扣减库存（远程调用）
    accountService.debit(order);          // 扣减账户（远程调用）
}
```

**优点**：无侵入、自动生成反向 SQL、使用简单  
**缺点**：需数据库支持 SQL 解析、加全局锁性能稍低、适合同一个数据库实例内的多表操作

### TCC 模式（编程式补偿）—— 高性能，灵活但侵入

TCC 要求业务方实现三个方法：Try（尝试预留）、Confirm（确认执行）、Cancel（取消回滚）。

```
TCC 执行流程：
① TM 向 TC 注册全局事务 → XID
② Try 阶段：预留业务资源（不真正提交业务）
   示例：账户服务 Try → 创建转账单状态"冻结中" + 冻结金额
        库存服务 Try → 预留库存，状态"已锁定"
③ Confirm 阶段：所有 Try 成功 → 执行 Confirm
   示例：账户服务 → 冻结状态改为"已转账"
        库存服务 → 锁定状态改为"已扣除"
④ Cancel 阶段：任一 Try 失败 → 执行所有已成功的 Cancel
   示例：账户服务 → 释放冻结金额 + 删除转账单
```

```java
public class AccountTccService {

    @TwoPhaseBusinessAction(
        name = "accountTcc",
        commitMethod = "confirm",
        rollbackMethod = "cancel"
    )
    public void tryDebit(BusinessActionContext ctx, 
                         @BusinessActionContextParameter("accountId") Long accountId,
                         @BusinessActionContextParameter("amount") BigDecimal amount) {
        // Try：冻结金额，状态置为"TCC-冻结中"
        accountService.freezeBalance(accountId, amount);
    }

    public boolean confirm(BusinessActionContext ctx) {
        // Confirm：真正扣减
        accountService.confirmDebit(ctx.getActionContext("accountId"), ctx.getActionContext("amount"));
        return true;
    }

    public boolean cancel(BusinessActionContext ctx) {
        // Cancel：释放冻结
        accountService.unfreezeBalance(ctx.getActionContext("accountId"), ctx.getActionContext("amount"));
        return true;
    }
}
```

**优点**：无数据库锁、性能高、跨存储支持（Redis/MongoDB）  
**缺点**：业务侵入性大、需要手动实现 Cancel（幂等性很重要）、Try 阶段预留资源增加业务复杂度

### SAGA 模式（长事务）—— 最终一致性

SAGA 将长事务拆分为多个本地事务，每个本地事务有对应的**补偿事务**。

```
SAGA 执行流程（链式/编排）：

正向流程：T1 → T2 → T3 → T4 → 完成
补偿流程：T1 → T2 → T3 → T4 失败
                                  ↓
                  T3 补偿 ← T3 正向已提交
                  ↓
          T2 补偿 ← T2 正向已提交
          ↓
  T1 补偿 ← T1 正向已提交
```

**特点**：
- 一阶段直接提交本地事务（不加锁，性能最好）
- 通过补偿事务实现回滚（需要业务实现 Compensating Transaction）
- 适合长流程（如多个外部系统调用、审批流）
- **不保证隔离性**：中间状态对外可见

### XA 模式（数据库原生）—— 强一致性

基于数据库原生 XA 协议的标准两阶段提交（2PC）。

```
XA 2PC 流程：
Phase 1（准备阶段）：所有 RM 执行 PREPARE（数据库写 redo log，事务可恢复）
Phase 2（提交阶段）：TC 通知所有 RM COMMIT（或 ROLLBACK）
```

**优点**：强一致性、数据库原生支持、无需业务改造  
**缺点**：锁资源期间长（直到 Phase 2 才释放）、性能最低、数据库需支持 XA

**三、四种模式对比总结**

| 维度 | AT | TCC | SAGA | XA |
|------|----|-----|------|----|
| 一致性强度 | 🔵 最终一致 | 🟢 强一致 | 🟡 最终一致 | 🟢 **强一致** |
| 业务侵入性 | 🟢 **无侵入** | 🔴 高（三个方法） | 🟡 中等（补偿接口） | 🟢 无侵入 |
| 性能 | 🟡 中等（全局锁） | 🟢 **最高** | 🟢 **最高** | 🔴 最慢（2PC锁） |
| 隔离性 | 🟡 Phantom reads | 🟢 自定义 | 🔴 无隔离 | 🟢 强隔离 |
| 跨数据库 | ⚠️ 同库 | 🟢 任何存储 | 🟢 任何存储 | ⚠️ 同库 |
| 典型场景 | 单库多表 | 跨库高并发 | 长流程/外部 | 金融强一致 |

**四、生产选型策略**

```java
// 选型决策树
if (业务能接受最终一致性) {
    if (需要跨数据库 + 高性能) {
        if (长流程多外部调用) {
            // ✅ SAGA（如：下单→支付→物流→评价）
        } else {
            // ✅ TCC（如：跨库转账）
        }
    } else {
        // ✅ AT（如：订单服务内部多表操作）
    }
} else {
    if (同一个数据库) {
        // ✅ XA（如：金融强一致场景）
    } else {
        // ⚠️ 需要分布式强一致 → 考虑别用微服务
    }
}
```

## 题目 5：[AI/大模型] 请详细阐述 MCP 协议（Model Context Protocol）的核心架构与原理：包括 MCP 的 C/S 架构设计（Host / Client / Server 三层角色）、Resource / Tool / Prompt 三大核心原语的生命周期管理、MCP 与 Function Calling 的本质区别与演进关系，以及 2026 年 MCP 成为 AI Agent 行业标准的背后逻辑

**难度**：⭐⭐⭐⭐
**考点来源**：2026-05-30 晚间日报 — "AI场景题成为大厂必考：MCP协议、LangChain4j集成"  
**相关岗位**：AI 应用开发 / Java后端 / 全栈 / 大模型工程

### 📖 参考答案

**一、MCP 要解决什么问题？—— 从 Function Calling 的碎片化说起**

在 MCP 诞生前，让大模型调用外部工具（查询数据库、调用 API、读写文件）是一件极其痛苦的事：

```
2024年：Function Calling 的碎片化噩梦
  工具 A → OpenAI Function Calling 格式
  工具 B → LangChain Tool 格式
  工具 C → Claude 自定义 Tool Use 格式
  工具 D → 每个 AI 客户端都要重新适配一遍

  结果：
  - 每对接一个新模型 → 重写所有工具的 Schema
  - 每新增一个工具 → 投到所有 AI 平台的适配器
  - 工具调用逻辑与业务代码高度耦合
```

**MCP（Model Context Protocol）的答案**：像 USB-C 接口一样标准化 AI 与工具的交互——**一次定义工具，所有 AI 模型都能用**。

2026 年的现状：MCP 已被 OpenAI、Claude、Google、通义千问等主流模型原生支持，生态超过 3000 个开源 Server 实现，并已被捐赠给 Linux 基金会下属的 AAIF（Agentic AI Foundation）进行中立治理。

**二、MCP 三层架构**

```
MCP 架构（类比：USB-C 协议）：
┌─────────────────────────────────────────────────────────────┐
│  Host（AI 客户端）                                           │
│  如：Claude Desktop / ChatGPT / Cursor / 自研 Agent         │
│  角色：发起请求、展示结果                                     │
│  类比：USB 主机（电脑）                                       │
├─────────────────────────────────────────────────────────────┤
│  Client（MCP 客户端，每个 Server 一个）                       │
│  角色：维护与 Server 的连接、管理会话状态                      │
│  类比：USB 控制器                                            │
├─────────────────────────────────────────────────────────────┤
│  Server（MCP 服务端，暴露工具）                               │
│  如：MySQL MCP Server / Filesystem MCP Server / 自定义       │
│  角色：提供 Resource、Tool、Prompt 三大能力                   │
│  类比：U盘/键盘/打印机                                        │
│                                                             │
│  连接方式：                                                   │
│  ├─ HTTP/SSE（远程模式）→ 适合云端微服务                      │
│  └─ stdio（本地模式）→ 适合本地工具（文件系统、Shell）         │
└─────────────────────────────────────────────────────────────┘
```

**三、三大核心原语**

MCP 定义了三种标准化的交互方式：

### 1. Tool（工具 —— 让 AI 有"手"）

类似于 Function Calling，但是标准化的：

```python
# MCP Tool 定义（Python SDK 示例）
@mcp.tool()
def query_order(order_id: str) -> list[Order]:
    """根据订单ID查询订单详情"""
    # 所有 MCP Client 都可以自动发现这个工具
    return db.orders.find_by_id(order_id)

# 任何支持 MCP 的 AI 都能自动调用它
# → Claude / ChatGPT / DeepSeek 不需要写适配器！
```

### 2. Resource（资源 —— 让 AI 有"眼"）

AI 可以像读文件一样读取数据和上下文，不再需要手动拼接：

```python
# 将数据库查询注册为 Resource
@mcp.resource("mysql://user/{user_id}/profile")
def get_user_profile(user_id: str) -> str:
    """读取用户信息，AI可以直接引用"""
    return json.dumps(user_service.get_profile(user_id))

# AI 使用场景：
# "给我看看这个用户的订单历史"
# → MCP Client 自动调用 resource://mysql/user/123/profile
```

### 3. Prompt（提示模板 —— 让 AI 有"模板"）

预设的交互模板：

```python
@mcp.prompt("system-tpl")
def system_prompt(user_level: str) -> str:
    return f"你是一个{user_level}级别的客服助手..."
```

**四、MCP 完整交互流程**

```
用户： "帮我查一下上周的订单，然后发邮件给客户"

Host (AI Client):
  ↓
① 调用 MCP Server.list_tools() → 发现【query_order】【send_email】工具
② LLM 判断意图 → 决定先查订单再发邮件
③ MCP Client 调用【query_order】工具 → 返回订单数据
④ LLM 组织回复 → 调用【send_email】工具 → 发送成功
⑤ 向用户展示结果
```

```python
# 用户只需要一句自然语言
# "帮我查一下最近三天的异常订单，然后生成报告"
```

**五、MCP 对比 Function Calling**

|------|------------------------|---------|

**六、MCP 采样（Sampling）—— 高级 Agent 行为**

```
场景：MCP Server 在处理请求时，需要 LLM 帮忙判断
  Server → Host: "帮我分析这段文本的情感倾向"
```
