**一、HashMap 底层数据结构——JDK7 vs JDK8**

```
JDK1.8 之前：
  数组 + 链表（拉链法）
  - 数组是主体
  - 链表解决哈希冲突
  - 头插法插入新节点
  
JDK1.8 之后：
  数组 + 链表 + 红黑树
  - 链表长度 ≥ 8 且数组长度 ≥ 64 → 树化为红黑树
  - 链表长度 ≤ 6 → 退化为链表（UNTREEIFY_THRESHOLD = 6）
  - 尾插法插入新节点
  - 扩容时 JDK7 头插法会产生死循环 → JDK8 尾插法消除此问题
```

```java
// HashMap 核心属性（JDK8+）
static final int DEFAULT_INITIAL_CAPACITY = 1 << 4;  // 16
static final int MAXIMUM_CAPACITY = 1 << 30;
static final float DEFAULT_LOAD_FACTOR = 0.75f;
static final int TREEIFY_THRESHOLD = 8;      // 树化阈值
static final int UNTREEIFY_THRESHOLD = 6;    // 退化阈值
static final int MIN_TREEIFY_CAPACITY = 64;  // 最小树化容量
```

**二、为什么红黑树转换阈值是 8 且要求数组长度 ≥ 64？**

```
阈值 8 的设计依据（Poisson 分布）：

  HashMap 源码注释给出了关键理论依据：
  在随机哈希码下，链表长度服从泊松分布。
  当负载因子 0.75 时：
  - 链表长度 = 8 的概率 ≈ 0.00000006（六亿分之一）
  - 链表长度 = 10 的概率已经低于 1/10 亿

  所以：
  - 链表长度 ≥ 8：说明哈希冲突严重，发生了哈希攻击或 hashCode() 实现极差
  - 此时树化以空间换时间：O(n) → O(log n)

  为什么要求数组长度 ≥ 64？
  - 如果数组长度 < 64（即容量太小），应该先扩容（resize）而不是树化
  - 扩容后哈希值重新分布（rehash），冲突自然缓解
  - 这是"先扩容后树化"的设计哲学——扩容比树化开销更小

  为什么退化阈值是 6 而不是 7？
  - 避免链表和红黑树频繁切换
  - 如果阈值设为 7：链表长度在 7 和 8 之间震荡 → 反复树化和退化
  - 6 < 8 的间隙（差 2）提供了缓冲
```

**三、HashMap 的扩容机制——为什么是 2 的幂次方？**

```java
// 扩容核心逻辑（resize 方法简化）
final Node<K,V>[] resize() {
    // ① 容量翻倍：oldCap << 1
    // ② 数据迁移：不是全部 rehash，而是判断 hash & oldCap == 0
    //    → 0：留在原位置
    //    → 1：迁移到 "原位置 + oldCap"
}

// 为什么容量必须是 2 的幂次方？
// 原因：计算数组下标时用 (n - 1) & hash，等价于 hash % n（取模运算）
// 但位运算比取模快得多！
// 如果 n 是 2 的幂次方，n-1 的二进制全是 1，与运算结果就是 hash 的低位值

// 例：n = 16（0x10000），n-1 = 15（0x01111）
// (n - 1) & hash 取的是 hash 的后 4 位 → 范围 0~15

// 扩容后的位置判断：
// 原 hash & oldCap（10000）：
// → 0：保持原位       ← 高位是 0
// → 16：原位置 + 16    ← 高位是 1
// 这就是"容量为 2 的幂"带来的优化——不需要重新计算所有 hash！
```

**四、HashMap 线程安全问题**

```
JDK7 死循环问题：
  - 扩容时采用头插法（transfer 方法）
  - 多线程并发扩容 → 链表成环 → get() 陷入死循环
  - 这是 JDK7 HashMap 被诟病最多的问题

JDK8 数据覆盖问题：
  - putVal 方法中，没有加锁
  - 线程 A 和 B 同时执行 if (p = tab[i]) == null → tab[i] = newNode(...)
  - 后写的会覆盖先写的数据

  结论：HashMap 从来就不是线程安全的！
  → 多线程场景用 ConcurrentHashMap
```

**五、ConcurrentHashMap——JDK7 分段锁 vs JDK8 CAS + synchronized**

```
JDK7 实现：分段锁（Segment，继承 ReentrantLock）

  ┌─────────────────────────────────────────┐
  │          ConcurrentHashMap               │
  │  ┌──────┐ ┌──────┐      ┌──────┐       │
  │  │Seg-0 │ │Seg-1 │ ... │Seg-15│ ← 16个  │
  │  └──┬───┘ └──┬───┘      └──┬───┘       │
  │     ▼        ▼             ▼            │
  │  ┌──────┐ ┌──────┐      ┌──────┐       │
  │  │Hash  │ │Hash  │      │Hash  │ 每个   │
  │  │Entry │ │Entry │      │Entry │  类似  │
  │  │数组  │ │数组  │      │数组  │ HashMap│
  │  └──────┘ └──────┘      └──────┘       │
  └─────────────────────────────────────────┘

  核心设计：
  - Segment 个数固定（默认 16），初始化后不可变
  - 每个 Segment 内部是一个 HashMap
  - 写操作只需锁住一个 Segment → 并发度 = 16
  - 用 ReentrantLock + tryLock 自旋获取锁

  缺点：
  - Segment 个数固定，扩容复杂
  - 并发度最大 16，大并发场景不够用
  - 存储开销大（每个 Segment 维护独立的锁和数组）

JDK8 实现：CAS + synchronized + 红黑树

  核心设计：
  - 去掉 Segment 结构，使用 Node[] + CAS + synchronized
  - 数组 + 链表 + 红黑树（与 HashMap 一致）
  - 并发度远高于 JDK7（几乎无限制）

  put 流程：
  ① 计算 hash → 定位数组位置
  ② 位置为空 → CAS 插入（无锁！）
  ③ 位置有数据 → synchronized 锁住链表头节点或树根节点
  ④ 数据迁移时用 CAS（无锁扩容）

  get 流程：完全无锁！
  - Node 的 value 和 next 用 volatile 修饰
  - 保证可见性，不需要加锁
  - 这是 JDK8 最大的性能提升

  size 计算：
  - 用 CounterCell[] + baseCount 累加
  - 通过 CAS 更新
  - 避免 JDK7 中需要锁定全部 Segment 的笨重设计
```

| 对比维度 | JDK7 ConcurrentHashMap | JDK8 ConcurrentHashMap |
|---------|----------------------|----------------------|
| 并发控制 | Segment + ReentrantLock | CAS + synchronized |
| 数据结构 | Segment[] → HashEntry[] | Node[] |
| 链表 | 头插法 | 尾插法 + 红黑树 |
| get 操作 | 需要锁 | 无锁（volatile） |
| 并发度 | 最大 16 | 数组长度 |
| put 并发 | Segment 内串行 | 更细粒度锁 |

### 💡 延伸思考

1. **为什么 JDK8 ConcurrentHashMap 使用 synchronized 而不是 ReentrantLock？** — 因为 JDK8 对 synchronized 做了大幅优化（偏向锁→轻量级锁→重量级锁的升级过程），在低竞争场景下 synchronized 的性能甚至优于 ReentrantLock。同时 synchronized 不需要手动解锁，减少了死锁风险。
2. **红黑树在 HashMap 中的实际效果如何？** — 红黑树查询 O(log n) vs 链表 O(n)。极端情况下（如 hash 被恶意构造碰撞），10 万个元素的链表查询需要 10 万次，树化后仅需 ~17 次。

**二、详细流程与回调顺序——面试核心**

```java
// 演示 Bean 生命周期回调的完整顺序
@Component
public class LifecycleDemo implements BeanNameAware, BeanFactoryAware,
        InitializingBean, DisposableBean {

    private String beanName;
    private BeanFactory beanFactory;

    public LifecycleDemo() {
        System.out.println("① 构造器：实例化");
    }

    // ----- ② 属性填充（Spring 自动注入 @Autowired） -----

    // ----- ③ Aware 接口回调（有严格顺序） -----
    @Override
    public void setBeanName(String name) {
        // 第1步：注入 Bean 名称
        this.beanName = name;
        System.out.println("③-1 BeanNameAware: " + name);
    }

    @Override
    public void setBeanFactory(BeanFactory beanFactory) {
        // 第2步：注入 BeanFactory
        this.beanFactory = beanFactory;
        System.out.println("③-2 BeanFactoryAware");
    }

    // 如果要注入 ApplicationContext，需要实现 ApplicationContextAware
    // 在 BeanFactoryAware 之后调用

    // ----- ④ BeanPostProcessor#postProcessBeforeInitialization -----
    @PostConstruct
    public void postConstruct() {
        // 实际上 @PostConstruct 是通过 InitDestroyAnnotationBeanPostProcessor
        // 在 postProcessBeforeInitialization 中调用的
        System.out.println("④ @PostConstruct 执行");
    }

    // ----- ⑤ InitializingBean -----
    @Override
    public void afterPropertiesSet() {
        System.out.println("⑤ InitializingBean#afterPropertiesSet");
    }

    // ----- ⑥ init-method -----
    @Bean(initMethod = "customInit")
    public void customInit() {
        System.out.println("⑥ init-method 执行");
    }

    // ----- ⑦ BeanPostProcessor#postProcessAfterInitialization -----
    // AOP 代理在这里创建：如果 Bean 需要 AOP，这里返回代理对象

    // ----- 销毁阶段 -----
    @PreDestroy
    public void preDestroy() {
        System.out.println("⑧ @PreDestroy");
    }

    @Override
    public void destroy() {
        System.out.println("⑨ DisposableBean#destroy");
    }

    @Bean(destroyMethod = "customDestroy")
    public void customDestroy() {
        System.out.println("⑩ destroy-method");
    }
}

// 输出顺序（关键！面试考点）：
// ① 构造器：实例化
// ② 属性填充（@Autowired）
// ③-1 BeanNameAware
// ③-2 BeanFactoryAware
// ③-3 ApplicationContextAware（如果有）
// ④ @PostConstruct  ← 实际上在 BeanPostProcessor#postProcessBeforeInitialization 中
// ⑤ InitializingBean#afterPropertiesSet
// ⑥ init-method
// 👆 到这里 Bean 就初始化完成了
// ↓ 下面才是真正创建 AOP 代理的地方
// ⑦ BeanPostProcessor#postProcessAfterInitialization（AOP 代理！）
// ...
// ⑧ @PreDestroy
// ⑨ DisposableBean#destroy
// ⑩ destroy-method
```

**三、三大初始化方式的执行顺序——面试必问**

```
初始化方式执行顺序（严格执行）：

  ① @PostConstruct（注解方式）—— 最先
  ② InitializingBean#afterPropertiesSet（接口方式）—— 次之
  ③ @Bean(initMethod="xx") 或 XML init-method（配置方式）—— 最后

  为什么是这个顺序？
  - @PostConstruct 由 JSR-250 规范定义，Spring 通过 BeanPostProcessor 调用
  - InitializingBean 是 Spring 框架接口，在 @PostConstruct 之后调用
  - init-method 是一种 XML/配置方式，优先级最低

  《阿里巴巴 Java 开发手册》推荐：
  - 统一使用 @PostConstruct 注解
  - 或者在 @Bean 中指定 initMethod
  - 不建议同时使用三种方式（容易搞混执行顺序）
```

**四、BeanPostProcessor——AOP 代理的创建时机**

```
BeanPostProcessor 是 Spring 扩展性最强的接口之一，
Spring 的 AOP 功能正是通过它实现的。

public interface BeanPostProcessor {
    // 在初始化之前执行
    default Object postProcessBeforeInitialization(Object bean, String beanName) {
        return bean;
    }
    
    // 在初始化之后执行——这里是 AOP 创建代理的时机！
    default Object postProcessAfterInitialization(Object bean, String beanName) {
        return bean;
    }
}

AOP 代理的创建时机：
  ① Bean 完成初始化（@PostConstruct + afterPropertiesSet + init-method）后
  ② 调用 postProcessAfterInitialization
  ③ 在此方法中，AbstractAutoProxyCreator 检查 Bean 是否需要 AOP
  ④ 如果需要，返回代理对象替代原始 Bean
  ⑤ 如果不需要，返回原始 Bean

关键约束：
  如果 Bean 需要 AOP 代理，它必须已经完成了初始化。
  这也是为什么"循环依赖 + AOP"需要三级缓存的原因——AOP 代理在初始化之后才创建。
```

**五、Bean 的作用域对生命周期的影响**

```
Singleton（默认）：
  - Bean 容器启动时创建（也可通过 @Lazy 延迟到首次使用）
  - 容器关闭时销毁
  - 管理完整的生命周期

Prototype：
  - 每次 getBean() 时创建
  - **容器不负责销毁！**（Spring 只调用初始化回调，不调用销毁回调）
  - 销毁需要使用者自己处理
  
Request/Session/Application（Web 作用域）：
  - 在对应的作用域生效时创建
  - 作用域结束时销毁
```

### 💡 延伸思考

1. **如果 Bean 实现了多个 Aware 接口，它们的执行顺序如何保证？** — Spring 在 invokeAwareMethods() 方法中按固定顺序调用：BeanNameAware → BeanClassLoaderAware → BeanFactoryAware，ApplicationContextAware 则在 ApplicationContextAwareProcessor（一个 BeanPostProcessor）中统一调用，执行在 BeanFactoryAware 之后、@PostConstruct 之前。
2. **为什么 String#trim() 和 String#intern() 不推荐在 @PostConstruct 中大量调用？** — 因为 @PostConstruct 执行在 BeanPostProcessor#postProcessBeforeInitialization 阶段，此时 Bean 的属性刚填充完。大量字符串操作会导致堆内存压力增大。但这只是一个编程习惯问题——更准确地说，不要在初始化回调中做耗时操作，会拖慢 Spring 容器启动。

### 📖 参考答案

**一、索引下推（ICP，Index Condition Pushdown）——MySQL 5.6 里程碑优化**

索引下推是 MySQL 5.6 引入的关键优化，每年面试都会考。

```
没有 ICP 时（MySQL 5.6 之前）的执行流程：

  假设索引 idx_name_age(name, age)，查询：
  SELECT * FROM t WHERE name LIKE '张%' AND age = 25;

  ① 通过 idx_name_age 找到 name LIKE '张%' 的记录
  ② 回表读取完整行
  ③ 在 Server 层检查 age = 25

  问题：name LIKE '张%' 可能匹配到 1000 条记录
        → 全部回表！全部 1000 次磁盘 IO！然后再过滤 age
        → 明明 age 条件可以通过索引过滤，却要回表后才做

有 ICP 时（MySQL 5.6+）的执行流程：

  ① 通过 idx_name_age 找到 name LIKE '张%' 的记录
  ② 直接在索引层面检查 age = 25（引擎层过滤！）
  ③ 只对满足 age = 25 的记录回表（可能只有 10 条）
  ④ Server 层几乎不需要再过滤

  优化效果：1000 次回表 → 10 次回表，提升近百倍！
```

```
ICP 的核心原理：

  传统的查询处理：
  ┌─────────┐    回表     ┌─────────┐     WHERE     ┌─────────┐
  │ 存储引擎 │ ────────→ │ 完整行   │ ──────────→ │ Server  │
  │ (索引)   │            │          │              │ (过滤)   │
  └─────────┘            └─────────┘              └─────────┘

  ICP 优化的查询处理：
  ┌─────────┐ 索引内过滤  ┌─────────┐  回表（少量） ┌─────────┐
  │ 存储引擎 │ ──────────→ │ 索引行   │ ──────────→ │ Server  │
  │ (ICP)    │  age=25     │ (满足的)  │             │ (仅投影) │
  └─────────┘              └─────────┘              └─────────┘

  ICP 的本质：将 WHERE 条件中"可以用索引过滤但不走索引"的部分，
             下推到存储引擎层执行，减少回表次数。
```

**二、ICP 的适用条件与限制**

```
✅ ICP 适用的场景：
  ① 联合索引中，查询条件包含索引的非最左列（跳过了某个列）
     例：索引(a, b, c)，查询 WHERE a = 1 AND c = 3
     → a 可以走索引，c 无法通过索引定位，但 ICP 可以在引擎层过滤 c
  
  ② 模糊查询 LIKE 前缀匹配 + 其他条件
     例：索引(name, age)，查询 WHERE name LIKE '张%' AND age = 25
     → name 可以走索引范围扫描，age 通过 ICP 在引擎层过滤

  ③ 范围查询后面的列条件
     例：索引(a, b, c)，查询 WHERE a > 10 AND b = 5
     → a 范围扫描，b 通过 ICP 过滤

❌ ICP 不适用的场景：
  ① 覆盖索引（Extra 显示 "Using index"）
     → 不需要回表，ICP 无作用对象
  
  ② 查询不走索引（全表扫描）
     → 没有索引可用
  
  ③ 条件本身就是索引的组成部分且能精确定位
     → 索引已经精确匹配了，不需要 ICP

EXPLAIN 中的标识：
  Extra = "Using index condition"  → ICP 已启用
  Extra = "Using index condition; Using MRR" → ICP + MRR 同时启用
```

**三、MRR（Multi-Range Read）——将随机 IO 变为顺序 IO**

```
MRR 的原理：

  如果通过二级索引查询大量数据，回表时主键 ID 是随机跳跃的。
  例如 WHERE create_time BETWEEN '2026-01-01' AND '2026-01-31'
  二级索引（create_time, ...）找到的主键 ID 可能是：
  1, 10001, 5, 2000, 300, 9999, 87, ...

  每次回表都是随机磁盘 IO → 极慢！

  MRR 的优化：
  ① 将查到的多个主键 ID 先缓存到 read_rnd_buffer
  ② 对主键 ID 排序：
     1, 5, 87, 300, 2000, 9999, 10001, ...
  ③ 按主键顺序批量回表
  ④ 磁盘 IO 从随机变为顺序（顺序读比随机读快 10-100 倍）

  MRR 的本质：用"排序+批量"将随机 IO 转化为顺序 IO
```

```
MRR 的触发条件：

  ① 查询必须使用二级索引（非主键索引）
  ② 查询需要回表的行数较多（非覆盖索引场景）
  ③ optimizer_switch 中 mrr=on（默认开启）
  ④ 系统认为 MRR 收益 > 排序成本

  控制开关：
  SET optimizer_switch = 'mrr=on,mrr_cost_based=off';
  // mrr_cost_based=off 强制使用 MRR（不管优化器是否认为划算）

  EXPLAIN 标识：
  Extra = "Using MRR" 或 "Using index condition; Using MRR"
```

**四、覆盖索引 vs 索引下推——面试对比题**

```
覆盖索引（Covering Index）：

  - 索引包含了查询需要的所有字段（无需回表）
  - EXPLAIN Extra = "Using index"
  - 这是最高效的查询方式！零回表零随机 IO

  例：SELECT name, age FROM t WHERE name = '张三'
      如果 (name, age) 是联合索引，name 和 age 都在索引中 → 覆盖索引

索引下推（ICP）：

  - 仍需要回表，但回表前在引擎层过滤，减少回表次数
  - EXPLAIN Extra = "Using index condition"
  - 需要回表，但回表次数大大降低

  例：SELECT * FROM t WHERE name LIKE '张%' AND age = 25
      ← 需要 *，无法覆盖索引，必须回表
      ← ICP 先在索引层过滤 age = 25，再回表
```

| 维度 | 覆盖索引 | 索引下推（ICP） |
|------|---------|---------------|
| 是否回表 | ❌ 不需要 | ✅ 需要，但次数减少 |
| 优化点 | 零回表 | 减少回表 |
| EXPLAIN | Using index | Using index condition |
| 适用场景 | select 列=索引列 | 索引非左列/范围后条件 |
| 优先级 | 🥇 最高效 | 🥈 次优解 |

**五、面试回答框架**

```
面试官问"说说 MySQL 索引下推（ICP）是什么？"

① 一句话（10秒）：
   "ICP 是 MySQL 5.6 引入的优化，把 WHERE 条件中可以用索引过滤的条件
    下推到存储引擎层执行，减少回表次数"

② 对比有/无 ICP（20秒）：
   "无 ICP：索引定位 → 回表 1000 行 → Server 层过滤 900 行
    有 ICP：索引定位 + 引擎层过滤 → 只回表 100 行"
   "本质：能早过滤就早过滤"

③ 适用条件（15秒）：
   "适用于联合索引中跳过某列的条件、模糊查询的后缀条件、范围查询后的条件"
   "不适用于覆盖索引（不需要回表）、全表扫描"

④ 和 MRR 的区别（15秒）：
   "ICP 减少回表次数，MRR 将回表的随机 IO 转为顺序 IO"
   "如果 SELECT * 且回表量大，两者可以一起用"

⑤ 和覆盖索引对比（10秒）：
   "覆盖索引零回表 > ICP 减少回表 > 无优化全回表"
```

### 💡 延伸思考

1. **ICP 和 MRR 可以同时启用吗？** — 可以。MySQL 的优化器会同时启用两者。执行流程：索引定位 → ICP 过滤（减少回表行数）→ MRR 对主键排序（优化回表 IO 模式）→ 批量回表。EXPLAIN 显示 "Using index condition; Using MRR"。
2. **MRR 有没有负面影响？** — 有。MRR 需要额外的内存（read_rnd_buffer_size），对主键排序本身有 CPU 开销。如果查询回表的行数很少（几十行），排序成本可能超过收益，此时优化器可能选择关闭 MRR（这就是 mrr_cost_based 存在的意义）。

**一、RocketMQ 四大组件——面试必画架构图**

```
RocketMQ 核心架构：

  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
  │  NameServer  │    │  NameServer  │    │  NameServer  │  ← 无状态集群
  │  （路由注册）  │    │  （路由注册）  │    │  （路由注册）  │
  └──────┬───────┘    └──────┬───────┘    └──────┬───────┘
         │                   │                   │
         └───────────────────┼───────────────────┘
                             │
         ┌───────────────────┴───────────────────┐
         │                                       │
  ┌──────▼──────┐                         ┌──────▼──────┐
  │  Producer   │                         │  Consumer   │  ← 提问：NameServer 挂了会影响吗？
  │  （生产者）  │                         │  （消费者）  │     → 不会！客户端有本地缓存路由
  └──────┬──────┘                         └──────▲──────┘
         │ 发送消息                              │ 拉取消息
         ▼                                       │
  ┌───────────────────────────────────────────────┴──┐
  │              Broker 集群（主从架构）                │
  │  ┌──────────┐  ┌──────────┐                      │
  │  │ Master-1 │  │ Master-2 │  ...（可以有多组）    │
  │  │   ↓      │  │   ↓      │                      │

  │  └──────────┘  └──────────┘                      │
  └──────────────────────────────────────────────────┘

  组件职责：

  NameServer（路由注册中心）：
  - 轻量级，无状态，每个节点独立
  - Broker 启动时注册 Topic 路由信息
  - Producer/Consumer 启动时获取路由
  - 各 NameServer 之间不通信

  Broker（消息服务器）：
  - 存储消息的核心（CommitLog + ConsumeQueue）
  - 支持主从同步（Master 写，Slave 读或冷备）
  - 单机 QPS 可达 10 万+

  Producer（生产者）：
  - 发送消息到 Topic
  - 支持同步/异步/单向三种发送模式

  Consumer（消费者）：
  - 从 Broker 拉取消息
  - 支持集群消费（负载均衡）和广播消费
```

**二、消息可靠性——四重确认机制**

```
一条消息从生产到消费，经历三个阶段，每个阶段都有保障机制：

  阶段一：Producer → Broker（发送确认）
  
  ✅ 同步发送（默认）：发送后等待 Broker 返回 SEND_OK
  ✅ 自动重试：发送失败默认重试 3 次
  ✅ 异步发送：通过回调函数接收结果
  ❌ 单向发送：不确认，仅用于日志等可丢失场景
  
  代码示例：
  // 同步发送（推荐）
  SendResult sendResult = producer.send(message);
  if (sendResult.getSendStatus() == SendStatus.SEND_OK) {
      // 发送成功
  }

  阶段二：Broker 存储（持久化确认）

  ✅ 同步刷盘（SYNC_FLUSH）：
     - 消息写入 CommitLog 磁盘后再返回 ACK
     - 可靠性最高，吞吐量略降
     - 配置：flushDiskType=SYNC_FLUSH

  ✅ 异步刷盘（ASYNC_FLUSH，默认）：
     - 消息写入内存 PageCache 即返回
     - 后台线程定时刷盘（默认 500ms）
     - 吞吐量高，宕机可能丢失少量数据

  ✅ 主从同步复制（SYNC_MASTER）：
     - Master 同步写入 Slave 后才返回 ACK
     - Master 宕机 → Slave 自动切换
     - 配置：brokerRole=SYNC_MASTER

  阶段三：Consumer 消费（消费确认）

  ✅ 手动 ACK（推荐）：
     - 业务处理完成后手动提交消费进度
     - 若处理失败，Broker 自动重试
     - 代码：return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
  
  ❌ 自动 ACK：
     - 消息到达即确认，不管业务是否处理完
     - 可能丢失消息（处理异常但已确认）
  
  💡 最佳实践：同步发送 + 同步刷盘 + 主从同步 + 手动 ACK = 金融级可靠性
```

**三、顺序消息——全局 vs 局部**

```
全局顺序：极其罕见，退化为单队列
局部顺序：同一业务实体的消息按序处理 ← **实际需求**

RocketMQ 顺序消息实现：

  生产端：MessageQueueSelector
  ┌─────────────────────────────────────────┐
  │ 订单 ID 取模 → 始终发到同一个 Queue      │
  │                                         │
  │ 订单 A (创建) ──→ Queue 0 ──→ Consumer A │
  │ 订单 A (支付) ──→ Queue 0 ──→ Consumer A │  ← 同一订单
  │ 订单 A (发货) ──→ Queue 0 ──→ Consumer A │     始终在
  │                                         │     同一队列
  │ 订单 B (创建) ──→ Queue 1 ──→ Consumer B │
  └─────────────────────────────────────────┘

  消费端：MessageListenerOrderly
  - 同一 Queue 加分布式锁，单线程串行消费
  - 消费失败 → 阻塞等待重试 → 不跳过下一条
  - 保证：同一个订单的消息按顺序处理

  代码实现：
  // 生产端：保证同一订单到同一 Queue
  producer.send(message, new MessageQueueSelector() {
      @Override
      public MessageQueue select(List<MessageQueue> mqs, Message msg, Object arg) {
          Long orderId = (Long) arg;
          int index = (int) (orderId % mqs.size());
          return mqs.get(index);
      }
  }, orderId);

  // 消费端：顺序消费
  consumer.registerMessageListener(new MessageListenerOrderly() {
      @Override
      public ConsumeOrderlyStatus consumeMessage(List<MessageExt> msgs, 
                                                  ConsumeOrderlyContext context) {
          for (MessageExt msg : msgs) {
              process(msg);  // 单线程，顺序处理
          }
          return ConsumeOrderlyStatus.SUCCESS;
      }
  });
```

**四、事务消息——分布式一致性方案**

```
RocketMQ 事务消息是 MySQL 两阶段提交思想在 MQ 中的实现。

  流程（以"下单送积分"为例）：

  应用服务                    RocketMQ  
    │                          │
    │ ① 发送半消息（Half Msg）  │
    │ ───────────────────────→ │
    │                          │
    │ ② 半消息发送成功         │  ← 消息此时不可见（半消息）
    │ ←────────────────────── │
    │                          │
    │ ③ 执行本地事务（下单）    │
    │    DB 操作 ...           │
    │                          │
    │ ④ 提交/回滚事务消息      │
    │ ───────────────────────→ │
    │                          │
    │ ⑤ 消息可见/删除          │  ← COMMIT：消费者可见
    │                          │     ROLLBACK：删除消息
    │                          │
    │ ⑥ [异常情况] 回查机制     │
    │ ←────── 回查请求 ──────── │  ← 半消息长时间未提交
    │ ────── 回查结果 ────────→ │     Broker 主动回查

  关键设计：回查（Check-back）机制

  如果步骤 ④ 因宕机未发送 → Broker 发现半消息长时间未提交
  → Broker 回调 Producer 的 checkLocalTransaction() 方法
  → Producer 根据本地事务状态返回：
    - COMMIT_MESSAGE：本地事务已提交 → 消息可见
    - ROLLBACK_MESSAGE：本地事务已回滚 → 删除消息
    - UNKNOWN：不确定 → 稍后再次回查

  回查次数：默认 15 次，超过则告警（需要人工介入）
```

```java
// 事务消息实现
public class TransactionListenerImpl implements TransactionListener {
    
    @Autowired
    private OrderService orderService;

    // 执行本地事务
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            // 执行本地业务逻辑（下单）
            orderService.createOrder((Long) arg);
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }

    // 回查（Broker 调用）
    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // 查询本地事务是否已提交
        String orderId = msg.getKeys();
        boolean committed = orderService.checkOrderExists(orderId);
        return committed ? COMMIT_MESSAGE : UNKNOWN;
    }
}
```

**五、消息积压——"10 倍扩容法"紧急处理**

```
消息积压的根因：生产速度 >> 消费速度

  原因：
  - 消费端代码 Bug（死循环、慢 SQL）
  - 下游服务（DB/第三方 API）响应变慢
  - 突发流量洪峰
  - 消费者实例不足

  紧急处理"10 倍扩容法"：

  ┌──────────────────────────────────────────────┐
  │  ① 发现积压：原 Topic（4 个 Queue）积压 1000 万  │
  │                                                │
  │  ② 新建临时 Topic-新（40 个 Queue = 10 倍）      │
  │                                                │
  │  ③ 修改消费者 A = "转发机器"                     │
  │     - 从原 Topic 拉取消息                       │
  │     - 不做业务处理，直接转发到新 Topic           │
  │                                                │
  │  ④ 部署 40 个消费者实例消费新 Topic              │
  │     - 每个实例处理 1 个 Queue                    │
  │     - 消费能力 = 原来的 10 倍                     │
  │                                                │
  │  ⑤ 积压清空后：恢复原架构                        │
  └──────────────────────────────────────────────┘

  注意：
  - 这是紧急方案（治标），事后需定位根因（治本）
  - 转发机器不能做复杂业务逻辑
  - 需要足够的机器资源
```

### 💡 延伸思考

1. **RocketMQ 和 Kafka 的核心区别？** — 定位不同：RocketMQ 是面向业务的消息中间件（事务消息、顺序消息、消息重试、死信队列等），Kafka 是面向日志/流处理的分布式流平台（高吞吐、分区有序、存储无限、Flink 集成）。选型建议：业务消息（订单、支付）用 RocketMQ；日志/大数据/流处理用 Kafka。
2. **RocketMQ 的消息堆积能力有多强？** — RocketMQ 的消息持久化在磁盘（CommitLog），单机可堆积几十亿条消息。且积压时间越久不影响实时消息的写入性能（因为 ConsumeQueue 和 CommitLog 分离设计）。这也是 RocketMQ 相比于 RabbitMQ 的一大优势——RabbitMQ 积压严重时性能会下降。

**三、文档切分策略——影响 RAG 效果的第一关**

```
切分方式决定了检索的"颗粒度"和"语义完整性"。

  ① 固定大小切分（Fixed-size Chunking）：
     ⚡ 简单粗暴，按固定字符数（如 500 字符）切分
     ✅ 实现简单、性能好
     ❌ 可能在句子中间断开 → 上下文断裂
     适用：日志处理、结构化的表格数据

  ② 递归字符切分（Recursive Character Text Splitter）：
     按优先级尝试不同分隔符：\n\n → \n → 。 → 空格 → 字符
     ✅ 尽量在自然边界切分
     ✅ LangChain 默认策略，通用性好
     适用：通用文档

  ③ 语义切分（Semantic Chunking）：
     计算句子之间的语义相似度
     相似度低的点作为切分点
     ✅ 保持语义完整性
     ❌ 计算成本高、耗时长
     适用：教科书、法律文档等高质量文档

  ④ Tokenizer 感知切分：
     按 LLM 的 Tokenizer 边界切分
     ✅ 精确控制 Token 数 → 不浪费上下文窗口
     ❌ 与具体模型耦合
     适用：需要精确控制 Token 成本的场景

  最佳实践：
  - Chunk Size：300-1000 token（平衡检索精度和上下文质量）
  - Chunk Overlap：10-20%（边界信息不丢失）
  - 策略选择：通用场景用递归字符切分，高质量文档用语义切分
```

### 💡 延伸思考

1. **RAG vs Fine-tuning 怎么选？** — RAG：适合知识频繁更新、需要引用原文、数据量大的场景（如客服问答、文档检索）。Fine-tuning：适合改变模型行为/风格/格式、需要少量高频知识的场景（如代码生成助手）。一线实践：两者可以叠加（先微调再 RAG），RAG 解决"知道什么"的问题，微调解决"怎么回答"的问题。
2. **Advanced RAG（高级 RAG）有哪些改进？** — 包括：Query 转换（Rewrite/分解/假设文档 Embedding HyDE）、多路召回（关键词+向量+图检索 GraphRAG）、多轮对话 RAG（保留历史检索结果）、Agentic RAG（Agent 根据问题类型选择不同检索策略）等。目前的 SOTA 方案是 Self-RAG（让 LLM 自己判断是否需要检索、检索结果是否相关）。
