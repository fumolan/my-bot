**一、为什么需要 Reactive Streams？—— 生产-消费速度不匹配的困境**

Reactive Streams 要解决的核心问题是**背压（Backpressure）**：

```
没有背压的灾难：

  生产者（每秒 10 万条）→ 消费者（每秒 1 万条）
  
  结果：消费者处理不过来 → 数据堆积 → 内存溢出 → 系统崩溃！

背压的解决思路：

  生产者（每秒 10 万条）→ "你慢点，我只能处理 1 万条/秒" ← 消费者
  结果：生产者降速 → 消费者从容处理 → 系统稳定
```

背压就是**下游告诉上游"我能处理多少"，上游按需生产**——把"推"模式变成"拉"模式。

**二、Reactive Streams 规范与 Flow API 的四大角色**

Java 9 在 `java.util.concurrent.Flow` 中引入了 Reactive Streams 规范的四个核心接口：

```
Flow API 四角色交互流程：

  Publisher（生产者）               Subscriber（消费者）
       │                                    │
       │──── subscribe(Subscriber) ────────→│
       │                                    │
       │←── onSubscribe(Subscription) ──────│
       │                                    │
       │←── request(N) ─────────────────────│  "我要 N 个数据"
       │                                    │
       │──── onNext(item) ────────────────→│  × N 次
       │──── onNext(item) ────────────────→│
       │──── onNext(item) ────────────────→│
       │                                    │
       │←── request(N) ─────────────────────│  "再要 N 个"
       │                                    │
       │──── onComplete() ────────────────→│  或
       │──── onError(Throwable) ──────────→│
```

```java
// 四大核心接口定义（Java 9 Flow API 源码简化）

@FunctionalInterface
public interface Publisher<T> {
    void subscribe(Subscriber<? super T> subscriber);
}

public interface Subscriber<T> {
    void onSubscribe(Subscription subscription);  // 订阅建立，拿到"令牌"
    void onNext(T item);                          // 收到新数据
    void onError(Throwable throwable);            // 出错
    void onComplete();                            // 完成
}

public interface Subscription {
    void request(long n);  // 下游请求 N 个数据（背压的核心！）
    void cancel();         // 取消订阅
}

public interface Processor<T, R> extends Subscriber<T>, Publisher<R> {
    // 既是消费者又是生产者——中间处理节点
}
```

**关键点**：`Subscription.request(n)` 就是背压的开关——下游通过它控制上游的生产速度。

**三、完整实现示例——理解背压全流程**

```java
// 自定义 Publisher
public class SimplePublisher implements Publisher<Integer> {
    
    @Override
    public void subscribe(Subscriber<? super Integer> subscriber) {
        // 创建 Subscription 并回调 onSubscribe
        Subscription subscription = new SimpleSubscription(subscriber);
        subscriber.onSubscribe(subscription);
    }
    
    // 核心：Subscription 控制数据流
    static class SimpleSubscription implements Subscription {
        private final Subscriber<? super Integer> subscriber;
        private final Iterator<Integer> data = 
            IntStream.range(1, 101).iterator();  // 100 个数据
        private boolean cancelled = false;
        
        SimpleSubscription(Subscriber<? super Integer> subscriber) {
            this.subscriber = subscriber;
        }
        
        @Override
        public void request(long n) {
            // 下游请求 n 个数据 → 上游发送最多 n 个
            for (int i = 0; i < n && !cancelled && data.hasNext(); i++) {
                subscriber.onNext(data.next());
            }
            if (!data.hasNext() && !cancelled) {
                subscriber.onComplete();  // 数据发完了
            }
        }
        
        @Override
        public void cancel() {
            cancelled = true;
        }
    }
}

// 自定义 Subscriber（消费者）
public class SlowSubscriber implements Subscriber<Integer> {
    private Subscription subscription;
    private static final int BATCH_SIZE = 5;  // 每次只处理 5 个
    
    @Override
    public void onSubscribe(Subscription subscription) {
        this.subscription = subscription;
        // 关键：先只要 5 个！不是一次性全要
        subscription.request(BATCH_SIZE);
    }
    
    @Override
    public void onNext(Integer item) {
        System.out.println("处理: " + item);
        // 模拟慢消费
        try { Thread.sleep(100); } catch (Exception e) {}
        
        // 每处理一个，如果接近批次末尾，再请求下一批
        // 这就是背压！消费者控制生产速度
    }
    
    @Override
    public void onError(Throwable throwable) {
        throwable.printStackTrace();
    }
    
    @Override
    public void onComplete() {
        System.out.println("全部处理完成");
    }
}

// 使用
Publisher<Integer> publisher = new SimplePublisher();
Subscriber<Integer> subscriber = new SlowSubscriber();
publisher.subscribe(subscriber);
// 100 个数据，每次只拉 5 个 → 需要 20 轮 → 背压生效！
```

**四、背压的实现策略**

| 策略 | 说明 | 实现 |
|------|------|------|
| **缓冲（Buffer）** | 上游数据存入缓冲区，下游慢慢取 | `onBackpressureBuffer()` |
| **丢弃最新（Drop Latest）** | 下游处理不过来，丢弃最新的数据 | `onBackpressureDrop()` |
| **丢弃最旧（Drop Oldest）** | 丢弃缓冲区中最旧的数据 | 自定义实现 |
| **报错（Error）** | 下游跟不上，直接报错 | `onBackpressureError()` |
| **无策略（None）** | 不处理背压 → 内存溢出风险 | 默认 |

**五、Flow API vs RxJava vs Reactor**

| 维度 | Flow API (JDK 9) | RxJava 3 | Reactor (Spring WebFlux) |
|------|-----------------|----------|--------------------------|
| 定位 | **JDK 标准接口** | 独立库 | Spring 官方响应式库 |
| 操作符 | 几乎没有（只有接口） | 极其丰富 | 丰富 |
| 调度器 | 无 | 有（IO/计算/自定义） | 有 |
| 生态 | 其他库实现它 | 独立生态 | Spring 生态深度绑定 |
| 使用方式 | 手动实现 | 链式调用 | 链式调用 |
| 学习曲线 | 低（理解规范） | 高 | 中 |

```
Flow API 是"规范"（Spec），不是"实现"（Implementation）。
RxJava 和 Reactor 都实现了 Reactive Streams 规范（即 Flow API 的接口）。

关系：
  Flow API（接口定义）← 实现了 ─ RxJava 3
                    ← 实现了 ─ Reactor
                    ← 实现了 ─ Akka Streams
                    ← 实现了 ─ Mutiny（Quarkus）
```

### 💡 延伸思考

1. **Flow API 为什么默认没有操作符（map/filter/reduce）？** — 这是 JDK 团队的有意设计。Flow API 定位是"最小化规范接口"，只定义最核心的交互协议。操作符属于"实现层"功能，由 RxJava/Reactor 等库提供。这样设计的好处是：① 保持 JDK 轻量；② 允许不同实现库竞争创新；③ 各库可以自由选择操作符的实现方式（如 Reactor 选择了熔断友好、高性能的操作符实现）。
2. **Reactor 的 flatMap 和 map 有什么区别？什么时候用哪个？** — map 是同步转换（1:1），flatMap 是异步转换（1:N）。举例：`map(userId -> findUser(userId))` 返回 `Mono<User>`，结果类型是 `Mono<Mono<User>>`，需要解套；`flatMap(userId -> findUser(userId))` 直接返回 `Mono<User>`，自动解套。flatMap 还会并发执行多个异步操作，适合批量调用场景。

**一、为什么需要多数据源？—— 三种典型场景**

```
场景 1：读写分离
  主库（写）→ 从库 1（读）、从库 2（读）
  → 写操作走主库，读操作走从库，分担压力

场景 2：业务分库
  订单库（MySQL-A）→ 订单服务
  用户库（MySQL-B）→ 用户服务
  → 一个服务需要同时访问多个数据库

场景 3：多租户/多数据源
  租户 A → 数据源 A
  租户 B → 数据源 B
  → 根据租户 ID 动态切换
```

**二、AbstractRoutingDataSource —— Spring 多数据源的核心**

`AbstractRoutingDataSource` 是 Spring 提供的抽象类，它持有一个 `Map<Object, DataSource>`（多个数据源），通过 `determineCurrentLookupKey()` 决定当前使用哪个数据源。

```java
// AbstractRoutingDataSource 核心源码（简化）
public abstract class AbstractRoutingDataSource extends AbstractDataSource {
    
    private Map<Object, DataSource> targetDataSources;  // 所有数据源
    private DataSource defaultTargetDataSource;          // 默认数据源
    
    @Override
    public Connection getConnection() throws SQLException {
        // ① 确定当前数据源 key
        Object lookupKey = determineCurrentLookupKey();
        // ② 根据 key 获取对应的 DataSource
        DataSource dataSource = determineTargetDataSource(lookupKey);
        // ③ 从该 DataSource 获取连接
        return dataSource.getConnection();
    }
    
    // 子类必须实现这个方法——返回当前使用哪个数据源
    protected abstract Object determineCurrentLookupKey();
}
```

```
AbstractRoutingDataSource 工作流程：

  Service 调用 userMapper.selectById()
       ↓
  SqlSession.getConnection()
       ↓
  AbstractRoutingDataSource.getConnection()
       ↓
  ① determineCurrentLookupKey() → "master" 或 "slave"
       ↓
  ② targetDataSources.get("master") → 主库 DataSource
       ↓
  ③ 返回主库连接 → 执行 SQL
```

**三、完整实现：动态数据源 + AOP 切换**

### Step 1：定义数据源类型和上下文持有者

```java
// 数据源类型枚举
public enum DataSourceType {
    MASTER,  // 主库（写）
    SLAVE    // 从库（读）
}

// ThreadLocal 持有当前线程的数据源类型
public class DynamicDataSourceContextHolder {
    private static final ThreadLocal<DataSourceType> CONTEXT = new ThreadLocal<>();
    
    public static void set(DataSourceType type) {
        CONTEXT.set(type);
    }
    
    public static DataSourceType get() {
        return CONTEXT.get();
    }
    
    public static void clear() {
        CONTEXT.remove();  // 防止内存泄漏！
    }
}
```

### Step 2：实现 AbstractRoutingDataSource

```java
@Component
public class DynamicDataSource extends AbstractRoutingDataSource {
    
    public DynamicDataSource(
            @Qualifier("masterDataSource") DataSource master,
            @Qualifier("slaveDataSource") DataSource slave) {
        
        // ① 设置所有数据源
        Map<Object, Object> targetDataSources = new HashMap<>();
        targetDataSources.put(DataSourceType.MASTER, master);
        targetDataSources.put(DataSourceType.SLAVE, slave);
        this.setTargetDataSources(targetDataSources);
        
        // ② 设置默认数据源（主库）
        this.setDefaultTargetDataSource(master);
        
        // ③ 必须调用！否则数据源不生效
        this.afterPropertiesSet();
    }
    
    @Override
    protected Object determineCurrentLookupKey() {
        // 从 ThreadLocal 获取当前数据源类型
        DataSourceType type = DynamicDataSourceContextHolder.get();
        return type != null ? type : DataSourceType.MASTER;  // 默认主库
    }
}
```

### Step 3：自定义注解 + AOP 切面

```java
// 自定义注解
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
public @interface DataSource {
    DataSourceType value() default DataSourceType.MASTER;
}

// AOP 切面：方法执行前切换数据源
@Aspect
@Component
@Order(1)  // 确保在 @Transactional 之前执行
public class DataSourceAspect {
    
    @Around("@annotation(dataSource)")
    public Object around(ProceedingJoinPoint point, DataSource dataSource) throws Throwable {
        DataSourceType type = dataSource.value();
        DynamicDataSourceContextHolder.set(type);
        try {
            return point.proceed();
        } finally {
            DynamicDataSourceContextHolder.clear();  // 必须清理！
        }
    }
}
```

### Step 4：使用

```java
@Service
public class OrderService {
    
    @Autowired
    private OrderMapper orderMapper;
    
    @DataSource(DataSourceType.SLAVE)  // 读操作走从库
    public Order getOrder(Long id) {
        return orderMapper.selectById(id);
    }
    
    @DataSource(DataSourceType.MASTER)  // 写操作走主库
    @Transactional
    public void createOrder(Order order) {
        orderMapper.insert(order);
    }
}
```

**五、多数据源事务管理——核心难点**

这是面试最常追问的"坑"：

```
问题：@Transactional 在动态数据源下为什么不生效？

根因：
  @Transactional 在方法开始时从 DataSource 获取 Connection
  → 此时如果数据源是 MASTER → 获取的是主库连接
  → 方法执行过程中，AOP 切换数据源到 SLAVE → 但事务已经绑定在主库连接上了！
  → SLAVE 的查询也在主库上执行了！

解决方案：AOP 切面必须在 @Transactional 之前执行
  @Order(1) → DataSourceAspect（先切换数据源）
  @Order(2) → TransactionInterceptor（再开启事务）
```

```java
// 多数据源事务的正确姿势

// ❌ 错误：跨数据源事务（本地事务管不了两个数据库）
@Service
public class OrderService {
    @Transactional  // 只能管一个数据源的事务！
    public void crossDatabaseOperation() {
        // 操作主库
        masterMapper.insert(order);
        // 操作另一个库 → 不在同一个事务中！回滚不了！
        anotherDbMapper.insert(log);
    }
}

// ✅ 方案 1：使用 JTA 分布式事务（Atomikos / Bitronix）
// 配置 XA 数据源，支持跨库事务
// 但性能差，不推荐

// ✅ 方案 2：最终一致性（推荐）
// 主库操作提交 → 发 MQ 消息 → 异步操作另一个库
// 配合本地消息表/补偿机制保证最终一致

// ✅ 方案 3：单数据源内事务 + 读写分离
// 读写分离的场景下，事务内的操作全部走主库
// 保证数据一致性
```

**六、读写分离的完整方案**

```
读写分离的最佳实践：

  ① 强制走主库的场景：
     - 事务内的所有操作（包括读操作）
     - 写操作后的立即读（如 insert 后马上 select）
     - 对实时性要求极高的查询

  ② 可以走从库的场景：
     - 报表查询、历史数据查询
     - 允许少量延迟的列表查询
     - 不要求强一致性的查询

  ③ 主从延迟的兜底：
     - 写操作返回主键 → 后续读用主键（走主库）
     - 核心业务强制走主库
     - 非核心业务允许从库，设置合理的延迟阈值告警
```

```
② 实现方案（20秒）：
   "三个步骤：① 配置多个数据源 Bean；② 用 ThreadLocal 持有当前数据源类型；
    ③ 通过自定义注解 @DataSource + AOP 切面，方法执行前设置数据源类型"

③ 事务陷阱（20秒）：
   "关键坑：AOP 切面必须在 @Transactional 之前执行（@Order(1)），
    否则事务绑定到错误的数据源连接上。
    跨数据源事务不能用本地事务，需要 JTA 或最终一致性方案"

④ 读写分离策略（15秒）：
   "写操作 + 事务内操作 → 主库；简单查询 → 从库。
    主从延迟的兜底：写后立即读走主库，核心业务强制主库"

⑤ 生产经验（10秒）：
   "从库连接池配置比主库大（读多写少），
    监控主从延迟，超过阈值自动切主库，保证数据一致性"
```

### 💡 延伸思考

1. **ShardingSphere 和 AbstractRoutingDataSource 有什么区别？** — AbstractRoutingDataSource 是 Spring 的基础设施，只做简单的数据源路由。ShardingSphere 是完整的数据库中间件，支持分库分表、读写分离、数据脱敏、分布式事务等。如果你的需求只是读写分离，AbstractRoutingDataSource 够用；如果需要分库分表 + 读写分离 + 治理，上 ShardingSphere。
2. **多数据源下，MyBatis-Plus 的 BaseMapper 怎么指定数据源？** — 配合 dynamic-datasource-spring-boot-starter（苞米豆开源），使用 `@DS("master")` 或 `@DS("slave")` 注解即可，比手写 AbstractRoutingDataSource 更简洁。但面试时面试官更想听你手写方案的原理，因为这考察你对 Spring 底层机制的理解。

**二、Explain 执行计划——读懂 MySQL 的"心思"**

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 'PAID' ORDER BY create_time DESC;
```

| 字段 | 说明 | 重点关注 |
|------|------|---------|
| **id** | 查询序号 | 越大越先执行，相同则从上到下 |
| **select_type** | 查询类型 | SIMPLE（简单查询）✅ / SUBQUERY / DERIVED（派生表）⚠️ |
| **table** | 访问的表 | — |
| **type** | **访问类型** | system > const > eq_ref > ref > range > index > **ALL** ❌ |
| **possible_keys** | 可能使用的索引 | 为 NULL 说明没有可用索引 |
| **key** | **实际使用的索引** | 为 NULL 说明没走索引 ❌ |
| **key_len** | 索引使用长度 | 越大说明联合索引用的列越多 |
| **ref** | 索引比较的列 | const（常量）/ 列名 |
| **rows** | **预估扫描行数** | 越小越好，超过万行要优化 |
| **filtered** | 按表条件过滤的行百分比 | 越小说明过滤条件越严格 |
| **Extra** | **额外信息** | Using index ✅ / Using filesort ❌ / Using temporary ❌❌ |

**Extra 字段速查表**：

| Extra 值 | 含义 | 严重程度 |
|----------|------|---------|
| **Using index** | 覆盖索引，不需要回表 | ✅ 最优 |
| **Using where** | 使用 WHERE 过滤，正常 | ✅ 正常 |
| **Using index condition** | 索引下推（ICP） | ✅ 优化 |
| **Using filesort** | 文件排序（无法用索引排序） | ⚠️ 需优化 |
| **Using temporary** | 使用临时表 | ❌ 严重，必须优化 |
| **Using join buffer** | JOIN 没有走索引 | ❌ 严重 |

**三、SQL 优化十大技巧**

### 1. 避免索引失效

```sql
-- ❌ 函数破坏索引
SELECT * FROM orders WHERE YEAR(create_time) = 2026;
-- ✅ 改为范围查询
SELECT * FROM orders WHERE create_time >= '2026-01-01' AND create_time < '2027-01-01';

-- ❌ 隐式类型转换（phone 是 VARCHAR）
SELECT * FROM users WHERE phone = 13800138000;  
-- MySQL 会把 phone 列转为数字再比较 → 索引失效！
-- ✅ 加引号
SELECT * FROM users WHERE phone = '13800138000';

-- ❌ LIKE 前置通配符
SELECT * FROM users WHERE name LIKE '%张三';
-- ✅ 使用全文索引或 Elasticsearch
```

### 2. 大分页优化

```sql
-- ❌ 传统分页：OFFSET 越大越慢
SELECT * FROM orders ORDER BY id LIMIT 1000000, 20;
-- 需要扫描前 1000020 行，丢弃前 1000000 行

-- ✅ 方案 1：延迟关联
SELECT * FROM orders 
INNER JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 20) AS tmp 
ON orders.id = tmp.id;

-- ✅ 方案 2：游标分页（基于上次查询的最大 ID）
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 20;
-- 前提：id 连续且有序

-- ✅ 方案 3：业务层限制（最多翻 100 页）
```

### 3. JOIN 优化

```sql
-- ❌ JOIN 字段类型不一致
SELECT * FROM orders o JOIN users u ON o.user_id = u.id;
-- orders.user_id 是 VARCHAR，users.id 是 INT → 索引失效

-- ✅ 小表驱动大表
-- LEFT JOIN 时，左表是驱动表
-- 把数据量小的表放在左边

-- ✅ JOIN 字段建索引
-- 被驱动表（JOIN 后面的表）的关联字段必须有索引
```

### 4. 子查询改写为 JOIN

```sql
-- ❌ 子查询（可能生成临时表）
SELECT * FROM orders WHERE user_id IN (
    SELECT id FROM users WHERE status = 'VIP'
);

-- ✅ JOIN（MySQL 8.0 优化器已改善，但 JOIN 更可控）
SELECT o.* FROM orders o 
INNER JOIN users u ON o.user_id = u.id 
WHERE u.status = 'VIP';
```

### 5. 避免 SELECT *

```sql
-- ❌ 全字段查询
SELECT * FROM orders WHERE user_id = 100;

-- ✅ 只查需要的字段（配合覆盖索引）
SELECT id, order_no, amount FROM orders WHERE user_id = 100;
-- 如果 (user_id, order_no, amount) 是联合索引 → 覆盖索引，无需回表
```

### 6. 合理使用 IN 和 EXISTS

```sql
-- IN：子查询结果集小 → 子查询先执行
SELECT * FROM orders WHERE user_id IN (SELECT id FROM users WHERE level = 5);

-- EXISTS：外表小 → 外表先遍历
SELECT * FROM orders o WHERE EXISTS (
    SELECT 1 FROM users u WHERE u.id = o.user_id AND u.level = 5
);
```

### 7. 批量操作代替循环

```java
// ❌ 循环单条插入
for (Order order : orders) {
    orderMapper.insert(order);  // 1000 次数据库交互
}

// ✅ 批量插入
orderMapper.batchInsert(orders);  // 1 次数据库交互
```

```sql
-- 批量 INSERT
INSERT INTO orders (user_id, amount) VALUES 
(1, 100), (2, 200), (3, 300);
```

### 8. 避免大事务

```sql
-- ❌ 大事务：锁持有时间长，阻塞其他事务
BEGIN;
UPDATE orders SET status = 'DONE' WHERE ...;  -- 更新 10 万行
DELETE FROM temp_logs WHERE ...;               -- 删除 100 万行
INSERT INTO archive SELECT * FROM temp_logs WHERE ...;
COMMIT;

-- ✅ 分批处理
-- 每次处理 1000 行，分批提交
```

### 9. 合理使用 DISTINCT / GROUP BY

```sql
-- ❌ 不必要的 DISTINCT（已经有了唯一键）
SELECT DISTINCT id, name FROM users WHERE id = 100;

-- ✅ GROUP BY 字段尽量走索引（避免 Using temporary; Using filesort）
```

### 10. 使用合适的字段类型

```sql
-- ❌ 用 VARCHAR 存 IP 地址
ip VARCHAR(15);  -- 无法高效比较

-- ✅ 用 INT UNSIGNED（通过 INET_ATON/INET_NTOA 转换）
ip INT UNSIGNED;
```

**二、String —— SDS（Simple Dynamic String）**

### 2.1 为什么不用 C 语言的字符串？

C 语言的字符串（`char*`，以 `\0` 结尾）有几个致命问题：

```
C 字符串的四大缺陷：

① 获取长度 O(n)
   C 字符串：strlen() 需要遍历到 \0
   SDS：len 字段直接读取，O(1)

② 缓冲区溢出
   C 字符串：strcat(s1, s2) 如果 s1 空间不够 → 溢出！
   SDS：自动检查空间，不够就扩容

③ 内存重分配频繁
   C 字符串：每次增长或缩短都需要重新分配内存
   SDS：预分配 + 惰性释放，减少重分配

④ 二进制不安全
   C 字符串：遇到 \0 就认为结束
   SDS：用 len 记录长度，可以存任意二进制数据（图片、序列化对象）
```

### 2.2 SDS 的核心设计

```c
// Redis SDS 结构（简化版）
struct sdshdr {
    int len;    // 已用长度（O(1) 获取）
    int free;   // 剩余空间
    char buf[]; // 实际数据
};

// 预分配策略：
// ① 新字符串长度 < 1MB → 分配 len + free = 2 × len
//    例如：SET key "hello" → len=5, free=5, buf 容量=10
// ② 新字符串长度 >= 1MB → 分配 len + 1MB
//    例如：SET key [1.5MB] → len=1.5MB, free=1MB, buf 容量=2.5MB

// 惰性释放：
// 缩短字符串时（如 TRIM），不立即释放内存，留给后续增长使用
```

### 2.3 String 的三种编码

| 编码 | 条件 | 数据结构 |
|------|------|---------|
| **int** | 值是整数且可用 long 表示 | 直接存整数，不存字符串 |
| **embstr** | 字符串长度 ≤ 44 字节 | SDS，内存一次分配（连续） |
| **raw** | 字符串长度 > 44 字节 | SDS，内存两次分配 |

**三、Hash —— ziplist 与 hashtable 的切换**

```
Hash 的两种编码：

① ziplist（压缩列表）：元素少 + 每个元素小
   - hash-max-ziplist-entries: 512（默认）
   - hash-max-ziplist-value: 64（默认）
   - 超过任一阈值 → 转为 hashtable

② hashtable（哈希表）：元素多或大
   - 标准哈希表，rehash 采用渐进式（分批迁移，不阻塞）
```

```
ziplist 的结构（紧凑连续内存）：

  [zlbytes][zltail][zllen][entry1][entry2][entry3]...[zlend]

  特点：
  ✅ 内存连续，无指针开销，内存利用率极高
  ❌ 插入/删除需要移动元素，O(n)
  ❌ 不适合大量元素

  适用场景：小 Hash（如用户信息缓存，10 个字段以内）
```

**四、List —— quicklist（Redis 3.2+）**

从 Redis 3.2 开始，List 统一使用 quicklist：

```
quicklist = 双向链表 + ziplist 的混合体

  quicklist 结构：
  ┌─────┐    ┌─────┐    ┌─────┐
  │Node1│←──→│Node2│←──→│Node3│  ← 双向链表
  └──┬──┘    └──┬──┘    └──┬──┘
     │          │          │
     ▼          ▼          ▼
  ┌──────┐  ┌──────┐  ┌──────┐
  │ziplist│ │ziplist│ │ziplist│  ← 每个节点是 ziplist
  │[A,B,C]│ │[D,E,F]│ │[G,H]  │
  └──────┘  └──────┘  └──────┘

  每个 ziplist 最多存 list-max-ziplist-size 个元素（默认 -2，即 8KB）
  ziplist 的压缩深度由 list-compress-depth 控制
```

**quicklist 的优势**：
- 相比纯 linkedlist：减少了指针开销（ziplist 紧凑存储）
- 相比纯 ziplist：避免了插入/删除时的全量拷贝（分段存储）
- 支持中间压缩（LZF 算法），节省内存

**五、Set —— intset 与 hashtable**

```
Set 的两种编码：

① intset（整数集合）：元素全是整数 + 元素数量 ≤ 512
   - 有序整数数组，二分查找 O(log n)
   - 内存紧凑，无指针开销

② hashtable：元素包含非整数 或 元素数量 > 512
   - 标准哈希表，value 为 NULL
   - 查找 O(1)
```

```
intset 的编码升级：

  intset 根据元素大小自动升级编码：
  
  [5, 10, 20] → int16（每个元素 2 字节）
  → 插入 70000（超出 int16 范围）→ 升级为 int32（4 字节）
  → 插入 5,000,000,000（超出 int32 范围）→ 升级为 int64（8 字节）

  注意：编码只升不降！一旦升级，不会降级
```

**六、Sorted Set —— skiplist + hashtable（最复杂的结构）**

ZSet 是 Redis 最"重"的数据结构，同时使用跳表和哈希表：

```
Sorted Set 的双重结构：

  ┌───────────────┐     ┌───────────────────┐
  │   hashtable    │     │     skiplist      │
  │  member → score│     │  score → member   │
  │  (按成员查找)   │     │  (按分数排序)      │
  └───────────────┘     └───────────────────┘

  为什么需要两个结构？
  → hashtable 保证按 member 查找 O(1)
  → skiplist 保证按 score 范围查询 O(log n)
  → 两者互补，但内存占用量 = 数据量 × 2
```

### 跳表（SkipList）的原理

```
跳表 = 多层索引的有序链表

  普通有序链表：查找元素需要遍历 O(n)
  1 → 3 → 5 → 7 → 9 → 11 → 13 → 15

  跳表：通过多层索引加速查找
  Level 3: 1 ──────────→ 9 ──────────→ 15
  Level 2: 1 ──→ 5 ──→ 9 ──→ 11 ──→ 15
  Level 1: 1 → 3 → 5 → 7 → 9 → 11 → 13 → 15
  Level 0: 1 → 3 → 5 → 7 → 9 → 11 → 13 → 15

  查找 11：
  ① 从 Level 3 开始：1 → 9 → 15（超过了 11，退回 9）
  ② 下降到 Level 2：9 → 11（找到了！）
  ③ 总共比较了 4 次，而不是 6 次（普通链表）
```

```c
// Redis 跳表节点结构
typedef struct zskiplistNode {
    sds ele;                    // 成员（member）
    double score;               // 分数
    struct zskiplistNode *backward;  // 后退指针（双向）
    struct zskiplistLevel {
        struct zskiplistNode *forward;  // 前进指针
        unsigned long span;             // 跨度（用于计算排名）
    } level[];  // 多层索引（随机生成层数）
} zskiplistNode;
```

**跳表 vs 平衡树（AVL/红黑树）**：

| 维度 | 跳表 | 平衡树 |
|------|------|--------|
| 实现复杂度 | **简单**（不需要旋转） | 复杂（需要旋转保持平衡） |
| 范围查询 | ✅ 天然支持（链表遍历） | 需要中序遍历 |
| 插入/删除 | O(log n)，概率平衡 | O(log n)，严格平衡 |
| 内存占用 | 多（多层索引指针） | 少（每个节点两个指针） |
| 并发友好 | ✅ 容易实现无锁跳表 | ❌ 旋转操作锁粒度大 |

**ZSet 的两种编码**：

| 编码 | 条件 | 数据结构 |
|------|------|---------|
| **ziplist** | 元素 ≤ 128 且 每个元素 ≤ 64 字节 | 紧凑连续存储 |
| **skiplist + hashtable** | 超过阈值 | 跳表 + 哈希表双结构 |

**七、五大数据类型应用场景速查**

| 类型 | 典型场景 | 示例 |
|------|---------|------|
| **String** | 缓存、计数器、分布式锁 | `SET order:1001 '{...}' EX 3600` |
| **Hash** | 对象缓存、用户信息 | `HSET user:1001 name "张三" age 25` |
| **List** | 消息队列、最新列表 | `LPUSH news:latest "article1"` |
| **Set** | 标签、共同好友、去重 | `SINTER user:1:friends user:2:friends` |
| **Sorted Set** | 排行榜、延时队列 | `ZADD leaderboard 100 user1` |

```
面试官问"Redis 的 String 底层是什么？为什么不用 C 字符串？"

① String 底层（15秒）：

```

### 💡 延伸思考

1. **Redis 的跳表为什么随机决定层数，而不是固定层数？** — 固定层数的话，插入时需要维护严格的平衡条件（类似红黑树的旋转），复杂度高。随机层数基于概率（每次晋升 25%），期望层数 = 1/(1-p) = 4/3 ≈ 1.33 层。这种方式实现简单，且概率上保证了 O(log n) 的查找效率。Redis 的跳表最多 32 层（ZSKIPLIST_MAXLEVEL）。
2. **ziplist 的"连锁更新"问题是什么？** — ziplist 中每个 entry 存储了前一个 entry 的长度。如果插入一个大的 entry，后续 entry 的"前长度"字段可能需要扩容（从 1 字节扩到 5 字节），这又可能导致再后面的 entry 扩容...形成连锁反应。Redis 通过 listpack（Redis 7.0+ 引入）替代 ziplist 来彻底解决这个问题——listpack 不存储前一个 entry 的长度。

**一、为什么 Agent 需要推理模式？—— 从"一步回答"到"多步思考"**

普通 LLM 调用是"一问一答"：输入问题 → 输出答案。但复杂问题需要多步推理、调用工具、验证结果。Agent 的推理模式就是让 LLM 像人类一样"思考→行动→观察→再思考"。

```
LLM 调用 vs Agent 推理：

  普通 LLM：用户问题 → 直接回答（可能错误）
  Agent：用户问题 → 思考 → 行动 → 观察 → 再思考 → ... → 最终回答

  举例："帮我查一下上周的订单总额，然后生成一份销售报告"
  
  普通 LLM：直接编一个数字和报告（幻觉！）
  Agent：
    ① 思考：需要先查订单数据
    ② 行动：调用 query_orders("上周")
    ③ 观察：收到 150 条订单，总额 50000
    ④ 思考：数据够了，可以生成报告
    ⑤ 行动：调用 generate_report(data)
    ⑥ 观察：报告已生成
    ⑦ 最终回答：报告已生成，总额 50000，请查收
```

**二、ReAct（Reasoning + Acting）—— 思考与行动交替**

ReAct 是 Agent 领域最经典的推理模式，由 Google 和 Princeton 在 2022 年提出。

```
ReAct 的核心循环：

  Thought → Action → Observation → Thought → Action → ... → Final Answer

  详细流程：
  ┌──────────────────────────────────────────────────┐
  │ Question: 北京今天适合户外运动吗？                   │
  ├──────────────────────────────────────────────────┤
  │ Thought: 我需要先查天气，再查空气质量                │
  │ Action: get_weather("北京")                       │
  │ Observation: 晴，25°C，风力 2 级                   │
  │                                                  │
  │ Thought: 天气不错，再看看空气质量                   │
  │ Action: get_air_quality("北京")                   │
  │ Observation: AQI 45，PM2.5 15                     │
  │                                                  │
  │ Thought: 天气和空气都很好，适合户外运动              │
  │ Final Answer: 北京今天晴天，25°C，AQI 45，           │
  │              非常适合户外运动！                      │
  └──────────────────────────────────────────────────┘
```

**ReAct 的 Prompt 模板**：

```
You have access to the following tools:
{tools}

Use the following format:
Question: the input question you must answer
Thought: you should always think about what to do
Action: the action to take, should be one of [{tool_names}]
Action Input: the input to the action
Observation: the result of the action
... (this Thought/Action/Action Input/Observation can repeat N times)
Thought: I now know the final answer
Final Answer: the final answer to the original input question

Begin!
Question: {input}
{agent_scratchpad}
```

```python
# ReAct Agent 实现（LangChain 风格）
from langchain.agents import create_react_agent, AgentExecutor

agent = create_react_agent(llm, tools, prompt)
agent_executor = AgentExecutor(
    agent=agent,
    tools=tools,
    max_iterations=10,     # 最多 10 轮思考-行动
    handle_parsing_errors=True,
    verbose=True
)
result = agent_executor.invoke({"input": "帮我查一下上周的订单总额"})
```

**ReAct 的优缺点**：

| 优点 | 缺点 |
|------|------|
| 灵活，能处理未知的复杂任务 | Token 消耗大（每轮思考-行动都要消耗） |
| 观察-调整循环，能自我纠错 | 可能陷入无限循环（需要设置 max_iterations） |
| 实现简单，LangChain 原生支持 | 不擅长需要长远规划的任务 |

**三、CoT（Chain-of-Thought）—— 思维链推理**

CoT 是让 LLM 在回答前**先展示推理过程**，主要用于数学、逻辑等需要多步推理的场景。

```
CoT 的核心思想：

  不用 CoT：
  Q: 小明有 5 个苹果，小红给了他 3 个，他又买了 2 个，吃了 1 个，还剩几个？
  A: 9 个  ← 可能对，但不可靠

  用 CoT（Few-shot）：
  Q: 小明有 5 个苹果，小红给了他 3 个，他又买了 2 个，吃了 1 个，还剩几个？
  A: 让我们一步一步思考：
     ① 小明最初有 5 个苹果
     ② 小红给了他 3 个 → 5 + 3 = 8 个
     ③ 他又买了 2 个 → 8 + 2 = 10 个
     ④ 他吃了 1 个 → 10 - 1 = 9 个
     所以还剩 9 个苹果。
```

**CoT 的多种变体**：

| 变体 | 说明 | 适用场景 |
|------|------|---------|
| **Zero-shot CoT** | 提示词加"Let's think step by step" | 简单推理 |
| **Few-shot CoT** | 提供几个带推理过程的示例 | 中等推理 |
| **Tree of Thoughts** | 多条推理路径并行探索，选最优 | 复杂规划/创作 |
| **Self-Consistency** | 多次 CoT 采样，投票选多数答案 | 提高准确性 |
| **CoT-SC** | CoT + Self-Consistency | 数学/逻辑推理 |

**ReAct vs CoT 的核心区别**：

| 维度 | ReAct | CoT |
|------|-------|-----|
| 核心机制 | **思考 + 行动 + 观察**循环 | **纯推理链条** |
| 是否调用工具 | ✅ 是（核心能力） | ❌ 否（纯推理） |
| 适用场景 | 需要外部工具/数据的任务 | 数学/逻辑/代码推理 |
| 纠错能力 | ✅ 通过观察结果纠错 | ❌ 推理链错了就全错 |
| Token 消耗 | 高（每轮都有工具调用） | 中（只有推理文本） |
| 2026 趋势 | Agent 开发标配 | Prompt Engineering 基础技能 |

```
2026 面试标准回答：

  "CoT 是让 LLM 展示推理过程，解决'一步到位容易出错'的问题；
   ReAct 是把 CoT 与工具调用结合，让 Agent 能思考→行动→观察→再思考。
   简单说：CoT 是'脑子里想'，ReAct 是'想了做，做了再想'。"
```

**四、Plan-and-Execute —— 先规划后执行**

对于复杂任务（如"帮我规划一次旅行"），ReAct 的逐步试错效率太低。Plan-and-Execute 先制定完整计划，再逐步执行。

```
Plan-and-Execute 流程：

  用户：帮我规划北京三日游
    ↓
  Planner（规划器）：
    制定计划：
    ① Day1：故宫 → 景山公园 → 南锣鼓巷
    ② Day2：长城 → 鸟巢/水立方
    ③ Day3：颐和园 → 圆明园 → 返程
    ↓
  Executor（执行器）：
    逐步执行每个步骤：
    - 查故宫开放时间
    - 查门票价格
    - 查交通路线
    - 查附近美食
    ↓
  Replanner（重新规划器）：
    如果某步失败（如故宫闭馆），重新规划 Day1
```

```python
# Plan-and-Execute 实现（LangChain 风格）
from langchain_experimental.plan_and_execute import (
    PlanAndExecute, load_agent_executor, load_chat_planner
)

planner = load_chat_planner(llm)
executor = load_agent_executor(llm, tools, verbose=True)
agent = PlanAndExecute(planner=planner, executor=executor)

result = agent.run("帮我规划北京三日游，预算 3000 元")
```

**三种推理模式对比**：

| 模式 | 适用场景 | 示例 | 2026 面试重点 |
|------|---------|------|-------------|
| **CoT** | 数学/逻辑推理、代码生成 | "解释这段代码的复杂度" | Prompt 工程基础 |
| **ReAct** | 需要工具调用的任务 | "查订单+发邮件" | **Agent 开发标配** |
| **Plan-and-Execute** | 复杂多步骤任务 | "规划旅行+预订" | 高级 Agent 架构 |

**五、Agent Memory —— 让 Agent 有"记忆"**

LLM 本身是无状态的，Memory 机制让 Agent 能记住对话历史和上下文。

```
Agent Memory 三层架构：

  ┌──────────────────────────────────────────────┐
  │              短期记忆（Short-term Memory）       │
  │  存储：最近 N 轮对话，直接放在 Prompt 上下文       │
  │  容量：受 LLM 上下文窗口限制（如 128K tokens）    │
  │  作用：当前对话的上下文理解                       │
  │  示例："用户刚才说要查订单，我现在需要知道订单号"   │
  ├──────────────────────────────────────────────┤
  │              长期记忆（Long-term Memory）        │
  │  存储：向量数据库 / 摘要存储                      │
  │  容量：近乎无限（向量数据库可扩展）                │
  │  作用：跨会话的知识保留                          │
  │  示例："用户三个月前说过喜欢红色，推荐红色商品"     │
  ├──────────────────────────────────────────────┤
  │              工作记忆（Working Memory）          │
  │  存储：当前任务的中间状态                         │
  │  容量：单次任务周期内                            │
  │  作用：多步骤任务的状态跟踪                       │
  │  示例：ReAct 循环中的 Thought-Action-Observation  │
  └──────────────────────────────────────────────┘
```

```python
# Agent Memory 实现（LangChain 风格）
from langchain.memory import (
    ConversationBufferMemory,       # 存全部对话
    ConversationSummaryMemory,      # 存摘要
    ConversationBufferWindowMemory, # 存最近 N 轮
    VectorStoreRetrieverMemory,     # 长期记忆（向量检索）
)

# 短期记忆：滑动窗口
memory = ConversationBufferWindowMemory(
    k=10,  # 只保留最近 10 轮对话
    return_messages=True
)

# 长期记忆：向量检索
vector_memory = VectorStoreRetrieverMemory(
    retriever=vector_store.as_retriever(k=5),
    memory_key="long_term_memory"
)

# 组合使用
agent = create_react_agent(
    llm, tools, prompt,
    memory=memory  # 短期记忆
)
# 长期记忆通过工具注入：retrieve_from_memory(query)
```

**六、生产级 Agent Memory 的挑战**

```
Agent Memory 的三大工程挑战：

① 记忆压缩（Memory Compression）
   问题：对话越来越长 → 超出上下文窗口
   方案：自动摘要 + 滑动窗口 + 只保留关键信息
   实现：用 LLM 定期生成对话摘要，替换原始对话

② 记忆检索（Memory Retrieval）
   问题：长期记忆存了 100 万条，怎么找到相关的？
   方案：向量检索 + 关键词检索 + 时间衰减
   实现：embedding 存向量库，检索时用混合搜索

③ 记忆遗忘（Memory Forgetting）
   问题：旧信息可能过时或不相关
   方案：时间衰减 + 重要性评分 + 定期清理
   实现：每条记忆带时间戳和重要性分数，低分自动淘汰
```

### 💡 延伸思考

1. **ReAct 和 Tool Calling 是一回事吗？** — 不是。Tool Calling 是 LLM 的底层能力（模型决定调用哪个工具、传什么参数），ReAct 是 Agent 的执行框架（如何组织思考-行动-观察的循环）。可以理解为：Tool Calling 是"手"，ReAct 是"大脑如何指挥手"。两者配合才能实现真正的 Agent。
2. **Agent Memory 和 RAG 有什么区别？** — RAG 是"从外部知识库检索信息来增强回答"，Memory 是"记住对话历史和用户偏好"。可以理解为：RAG 是"查资料"，Memory 是"记事情"。生产级 Agent 通常两者都集成——用 RAG 引入外部知识，用 Memory 维护对话上下文和用户画像。
