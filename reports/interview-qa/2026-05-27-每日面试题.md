**一、为什么 Java 开发者需要 Spring AI？—— 不用学 Python 也能玩 AI**

2026 年的面试中，"你用过 Spring AI 吗？"已经从加分题变成基础题。Spring AI 的核心价值：让 Java 开发者用熟悉的 Spring 生态方式（依赖注入、注解驱动、自动配置）快速集成大模型，无需手动封装 HTTP Client、管理 Token、处理流式响应。

```

    Function Calling → 需要自定义 JSON Schema + 回调逻辑
```

```java
// 业务代码完全不变！换个配置文件就换模型
@RestController
public class AiController {

    private final ChatClient chatClient;

    // Spring AI 自动注入，不管底层是 DeepSeek 还是 OpenAI
    public AiController(ChatClient.Builder builder) {
        this.chatClient = builder
            .defaultSystem("你是一个专业的 Java 后端技术顾问")
            .build();
    }

    @GetMapping("/ai/chat")
    public String chat(@RequestParam String question) {
        return chatClient.prompt()
            .user(question)
            .call()
            .content();  // 同步调用，返回完整响应
    }
}
```

**四、流式响应（Streaming）— 用户体验的关键**

```java
@GetMapping(value = "/ai/chat/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<String> chatStream(@RequestParam String question) {
    return chatClient.prompt()
        .user(question)
        .stream()                         // 返回 Flux<ChatResponse>
        .content()                         // 提取 content 部分
        .map(token -> "data: " + token + "\n\n");  // SSE 格式
}

// 或使用 Spring WebFlux + SSE：
@GetMapping("/ai/stream/webflux")
public Flux<ServerSentEvent<String>> streamChat(@RequestParam String question) {
    return chatClient.prompt()
        .user(question)
        .stream()
        .content()
        .map(token -> ServerSentEvent.<String>builder()
            .data(token)
            .build());
}
// 前端用 EventSource 逐字接收，实现 ChatGPT 式打字效果
```

**五、Function Calling — 让 AI 调用你的业务 API（面试高分点）**

这是 2026 年最核心的考点：如何让大模型调用你的 Java 后端能力。

```java
// ========== 步骤1：定义工具类，@Tool 注解声明 ==========
@Component
public class OrderTools {

    @Tool(description = "根据用户ID查询最近的订单列表，最多返回10条")
    public List<Order> queryUserOrders(
        @ToolParam(description = "用户ID") Long userId,
        @ToolParam(description = "查询最近多少天，默认30天") Integer days
    ) {
        // 实际的数据库查询逻辑
        return orderService.findByUserId(userId, days);
    }

    @Tool(description = "根据订单ID查询订单详情")
    public OrderDetail getOrderDetail(
        @ToolParam(description = "订单ID") String orderId
    ) {
        return orderService.findDetailById(orderId);
    }

    @Tool(description = "取消未支付的订单")
    public String cancelOrder(
        @ToolParam(description = "订单ID") String orderId
    ) {
        boolean success = orderService.cancelOrder(orderId);
        return success ? "订单已取消" : "订单状态不允许取消";
    }
}

// ========== 步骤2：注册工具到 ChatClient ==========
@Configuration
public class AiConfig {

    @Bean
    public ChatClient chatClient(ChatClient.Builder builder, OrderTools orderTools) {
        return builder
            .defaultTools(orderTools)  // 注册工具！LLM 会自动发现并调用
            .build();
    }
}

// ========== 步骤3：用户对话中自动触发工具调用 ==========
// 用户问："帮我查一下最近的订单"
// → LLM 自动识别 intent → 调用 queryUserOrders(userId, 30)
// → 返回订单列表 → LLM 基于结果组织回复："您最近30天有3笔订单：..."
```

**Function Calling 内部执行流程（面试时画出来加分）：**

```
用户提问 → ChatClient
  │
  ├─ 1. 发送消息到 LLM（附带所有已注册工具的 Schema）
  │
  ├─ 2. LLM 判断是否需要调用工具
  │   ├─ 不需要 → 直接返回文本回答 ✅
  │   └─ 需要 → 返回 function_call（工具名 + 参数）
  │       ↓
  ├─ 3. Spring AI 自动执行工具（调用 OrderTools.queryUserOrders）
  │    ↓ 返回结果（如订单列表）
  │
  ├─ 4. 工具结果 + 原对话历史 → 再次发送给 LLM
  │    ↓
  └─ 5. LLM 基于工具结果生成最终自然语言回复
     → 多轮自动完成，用户无感知！
```

### 💡 延伸思考

1. **Function Calling 中如果 LLM 传了错误的参数怎么办？** — 核心是防御性编程：① @ToolParam 中用 `required=true` 标记必填参数，Spring AI 会自动校验；② 工具方法内做参数二次校验和降级返回（如 userId 为 null → 返回"请先登录"）；③ 生产环境建议加上 ToolExecutionException 统一异常处理和 Fallback 工具。
2. **Spring AI 的流式响应底层用了什么技术？** — 基于 Project Reactor 的 Flux/Mono，本质是非阻塞 IO + 背压机制。LLM 每生成一个 token，Spring AI 立刻通过 SSE（Server-Sent Events）推送给前端，前端用 EventSource 逐字渲染。这种方式让用户感知延迟从 3-5 秒降到近乎实时。

**二、场景一：CPU 飙升到 100% 的排查全流程**

```
排查流程（5 步定位）：

  Step 1: top 找到高 CPU 的 Java 进程
    $ top
    PID   USER  %CPU  %MEM  COMMAND
    20260 java  98.5  45.2  java  ← CPU 快满了！

  Step 2: top -Hp 找到进程中哪条线程在吃 CPU

    20261  0.3
    ...

  Step 3: 线程 ID 转十六进制（jstack 输出的 nid 是十六进制）
    $ printf "%x\n" 20300
    → 4f4c

  Step 4: jstack 看这条线程在干嘛
    $ jstack 20260 | grep -A 20 "4f4c"
    "http-nio-8080-exec-5" #28 daemon prio=5 tid=0x... nid=0x4f4c runnable
      at com.example.OrderService.processOrder(OrderService.java:42)
      at com.example.OrderController.list(OrderController.java:18)
      ...
    → 定位到 OrderService.java:42 行！

  Step 5: 看源码定位根因
```

**常见 CPU 飙升原因及解决：**

| 原因 | jstack 表现 | 解决方案 |
|------|------------|---------|
| **死循环** | 线程状态 RUNNABLE，一直在某方法内 | 修复循环退出条件 |
| **正则表达式回溯** | 大量线程在 `java.util.regex.Matcher` | 优化正则，用预编译 Pattern |
| **频繁 GC** | 大量 GC 线程在运行 | 见场景三的排查 |
| **大量 JSON 序列化** | 线程在 Jackson/Gson 序列化方法 | 缓存序列化结果，减少大对象 |
| **HashMap 死循环** | JDK7 多线程扩容导致 | 升级 JDK，用 ConcurrentHashMap |

**三、场景二：OOM（内存溢出）排查全流程**

```
OOM 不是"堆不够了"这么简单。先看 OOM 的类型：

  java.lang.OutOfMemoryError: Java heap space
    → 堆内存真不够了 → 最常见
    → 原因：大对象、内存泄漏、堆设置太小

  java.lang.OutOfMemoryError: MetaSpace
    → 方法区/元空间溢出
    → 原因：动态生成大量类（CGLIB/动态代理）、ClassLoader 泄漏

  java.lang.OutOfMemoryError: unable to create new native thread
    → 无法创建新线程
    → 原因：线程数超 OS 限制（通常 ~4096）、线程未释放

  java.lang.OutOfMemoryError: Direct buffer memory
    → 直接内存溢出
    → 原因：NIO 大量使用堆外内存未释放

排查流程：

  ① 先确认是哪种 OOM（看错误信息和堆栈）
  
  ② 拿到 heap dump：
    # JVM 启动参数，OOM 时自动 dump：
    -XX:+HeapDumpOnOutOfMemoryError
    -XX:HeapDumpPath=/var/log/java/heap.hprof
    
    # 或手动 dump（生产环境慎用，会 STW 数秒）：
    jmap -dump:live,format=b,file=heap.hprof <pid>

  ③ 用 MAT 分析 heap.hprof：
    File → Open Heap Dump → Leak Suspects Report
    → MAT 自动分析出"疑似泄漏对象"及其引用链
    
    关键指标：
    - Dominator Tree：按保留内存大小排序的对象树
    - Histogram：各类的实例数和占用
    - Path to GC Roots：对象的 GC Root 引用链（找出"谁不让 GC 回收它"）

  ④ 常见 OOM 根因：
    → 大对象：某个 List/Map 无限增长（如缓存没设上限）
    → ThreadLocal 泄漏：线程池 + ThreadLocal 没 remove()
    → 连接泄漏：数据库连接/HTTP 连接池没关闭
    → MetaSpace：动态代理 + ClassLoader 未回收
```

**Memory Analyzer（MAT）实战技巧：**

```
打开 heap.hprof 后按以下顺序分析：

  ① Leak Suspects Report（泄漏疑点报告）
    → 如果提示"One instance of X occupies 80% heap" → 大概率就是它

  ② Histogram → 按 Retained Heap 排序
    → 找前几个类 → 看实例数是否异常大
    → 比如 byte[] 占 90% 堆 → 可能是大量字符串或文件缓存

  ③ Dominator Tree → 展开最大的对象 → Merge Shortest Paths to GC Roots
    → 看"谁引用了这个大对象"
    → 如果是 ThreadLocal → ThreadLocal 泄漏
    → 如果是 HashMap → 缓存没设上限

  ④ OQL 查询（Object Query Language）：
    SELECT * FROM com.example.User WHERE name LIKE "test.*"
    → 直接查询堆中的对象，按条件筛选
```

**四、场景三：频繁 Full GC 排查全流程**

```
排查四步法：

  Step 1: jstat 实时监控 GC
    $ jstat -gc <pid> 1000 10
    
    S0C    S1C    S0U    S1U      EC       EU        OC         OU
    0.0   5120.0  0.0   5120.0 204800.0 204799.0  524288.0   524287.0
    ...
    → OU(老年代使用) = 524287 / 524288 ≈ 100% ← 老年代满了！
    → YGC(Young GC次数) 很少但 FGC(Full GC次)很多
    → 问题：对象没有在新生代被回收，直接晋升到老年代

  Step 2: 启用 GC 日志
    -Xlog:gc*:file=/var/log/gc.log:time,level,tags
    
    # 分析 GC 日志：
    [GC (Allocation Failure) ...]     → 正常的 Young GC
    [Full GC (Ergonomics) ...]        → Full GC，需要关注
    [Full GC (Allocation Failure) ...] → 老年代也满了！

  Step 3: 分析 Full GC 频繁的原因
    ① 大对象直接进老年代（超过 -XX:PretenureSizeThreshold）
    ② 新生代太小 → 对象存活时间长 → 频繁晋升
    ③ 内存泄漏 → 老年代持续增长，GC 无法回收
    ④ MetaSpace 满了 → 触发 Full GC（JDK8: -XX:MetaspaceSize）

  Step 4: 调优方案
    方案A（最常见）：加大新生代
      -Xmn2g  或  -XX:NewRatio=2
    
    方案B：选择合适的 GC
      JDK 8: CMS / G1
      JDK 17+: G1（默认）/ ZGC（超低延迟）
      -XX:+UseG1GC -XX:MaxGCPauseMillis=200
    
    方案C：解决内存泄漏（根本方案）
      见场景二的 MAT 分析流程
```

**GC 选型速查：**

| GC | 特点 | 适用场景 | STW 时间 |
|-----|------|---------|---------|
| **Serial** | 单线程，最简单 | 客户端、小内存 | 百 ms |
| **Parallel** | 多线程，吞吐优先 | 批处理、科学计算 | 百 ms-秒 |

| **ZGC** | 超低延迟，染色指针 | JDK17+，16G+ 大堆 | <1ms |
| **Shenandoah** | 低延迟，并发压缩 | JDK17+，大堆 | <10ms |

**一、分库分表的"为什么"——单表的天花板**

```
  │  分库（Database Sharding）—— 解决"连接数压力"        │
  │  → 单库连接数上限 ~2000，热点业务分到不同库            │
  │  → 每库独立 MySQL 实例，物理隔离                     │
  │                                                     │
  │  分表（Table Sharding）—— 解决"单表数据量压力"        │
```

1. **垂直拆分 — 按业务模块拆库**

```
拆分前（单库）：
  订单库: t_order, t_order_item, t_user, t_product, t_payment, t_log, ...

拆分后（垂直分库）：
  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
  │  订单库      │  │  用户库      │  │  商品库      │
  │ ├ t_order   │  │ ├ t_user    │  │ ├ t_product │
  │ ├ t_order_  │  │ ├ t_address │  │ ├ t_category│
  │ │   item    │  │ └ t_account │  │ └ t_sku     │

  └─────────────┘
  核心理念：专库专用，各业务独立

缺点：跨库 Join 问题（解决：应用层聚合 / 数据冗余）
```

2. **水平拆分 — 按数据行拆表（核心重点）**

```
拆分前（单表 1 亿行）：
  t_order: 1 亿条数据在 1 张表里

拆分后（水平分表，Hash取模 4 张表）：
  DB:
    t_order_0: id%4==0 → 2500 万行
    t_order_1: id%4==1 → 2500 万行
    t_order_2: id%4==2 → 2500 万行
    t_order_3: id%4==3 → 2500 万行
  
  分片键：order_id（通常是主键或高频查询字段）
  路由算法：table_index = order_id % 4
```

**分片策略对比（最重要！）：**

| 策略 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **Hash 取模** | `分片 = key % N` | 数据均匀分布 | 扩容时需要重新 Hash（数据迁移） | N 确定不变的场景 |
| **一致性哈希** | 环形 Hash 空间 | 扩容只影响相邻节点 | 实现复杂，不够均匀 | 需要动态扩容 |
| **Range 范围** | 按时间/ID 范围 | 扩容简单（新数据自然路由） | 热点数据（最新数据集中） | 按时间查询多 |
| **复合分片** | Hash + Range 结合 | 取长补短 | 配置复杂 | 生产环境推荐 |

```yaml
      names: ds0, ds1
      ds0:

        password: root

      sharding:
        # 分库策略：user_id % 2 → 决定走哪个库

          standard:
            sharding-column: user_id
            sharding-algorithm-name: database-inline
        
        # 分表策略：order_id % 4 → 决定走哪张表
        tables:

              column: id
              key-generator-name: snowflake

        sharding-algorithms:
          database-inline:
            type: INLINE
            props:
              algorithm-expression: ds$->{user_id % 2}

            type: INLINE
            props:
              algorithm-expression: t_order_$->{order_id % 2}
```

**四、跨库 Join 问题 — 4 种解决方案**

| 方案 | 实现 | 适用场景 |
|------|------|---------|
| **字段冗余** | 把常用 join 字段在分表中冗余一份 | 字段少、不常变（如 user_name） |
| **应用层聚合** | 分两次查，应用层拼装结果 | 数据量不大（百级） |
| **全局表** | 小表在每个库都存一份（广播表） | 配置表、字典表 |
| **数据同步** | Canal 监听 binlog → ES → 多维度查询 | 复杂搜索场景 |

```java
// ShardingSphere 广播表（每个库都存一份全量数据）
// 配置：
t_config:
  actual-data-nodes: ds$->{0..1}.t_config  # 每个库都有
  table-strategy:
    none: {}  # 不分片

// 用法：SELECT * FROM t_config → 任意库都能查到完整数据

// 绑定表（关联表按相同分片键路由到同库，避免跨库 Join）
t_order:
  ...order_id 分片
t_order_item:
  ...order_id 分片（与 t_order 相同）
  
binding-tables:
  - t_order, t_order_item  # 绑定！保证同一订单的 order 和 item 在同一库
```

**五、跨分片分页 — 深分页的噩梦**

```sql
-- 问题：分库分表后 LIMIT offset, size 失效！
SELECT * FROM t_order ORDER BY create_time DESC LIMIT 100000, 10;

-- 假设 2 库 2 表共 4 张分表，ShardingSphere 的默认行为：
-- ① 从 4 张表各取 100010 条 → 共 400040 条！
-- ② 内存中排序 → 取第 100001-100010 条
-- ③ 前 400030 条被丢弃！大量内存和网络浪费！

-- ✅ 解决方案：禁止跳页，用"上一页最后一条 ID"替代
SELECT * FROM t_order 
WHERE id > #{lastId} AND create_time BETWEEN ? AND ?
ORDER BY id LIMIT 10;
-- 每张表只查 10 条 → 总共 40 条 → 内存排序 → 取前 10 条！
```

**六、分库分表后的分布式事务**

分库分表后，一个业务流程可能跨多个数据源。必须引入分布式事务：

```java
// Seata AT 模式 —— 最简单，加注解即可
@Service
public class OrderService {

    @GlobalTransactional  // Seata 全局事务注解
    @Transactional        // 本地事务
    public void createOrder(OrderDTO dto) {
        // ① 创建订单（走 ds0.t_order_1）
        orderMapper.insert(order);
        
        // ② 扣减库存（走 ds1.t_product_0）
        productMapper.deductStock(dto.getProductId(), dto.getQuantity());
        
        // ③ 扣减余额（走 ds0.t_account_0）
        accountMapper.deductBalance(dto.getUserId(), dto.getAmount());
        
        // 任意一步失败 → Seata 自动回滚所有操作
    }
}

// Seata AT 模式原理（二阶段提交的优化版）：
// 一阶段：各 RM 执行 SQL + 记录 undo_log（本地事务提交）
// 二阶段：全部成功 → TC 通知各 RM 删除 undo_log（异步）
//         任一失败 → TC 通知各 RM 根据 undo_log 回滚
// 关键优化：一阶段就提交本地事务，释放锁，性能远高于传统 2PC
```

**一、分布式锁的本质需求**

单机 `synchronized` / `ReentrantLock` 对多服务实例完全无效——锁在 JVM 内存里，另一个实例看不到。分布式锁需要**跨进程、跨 JVM** 的互斥机制。

```
分布式锁五大铁律：

  ① 互斥性：同一时刻只能有一个客户端持有锁
  ② 防死锁：锁必须有超时机制（客户端崩溃后自动释放）
  ③ 解铃还须系铃人：谁加锁谁解锁（防止误删别人的锁）
  ④ 可重入：同一客户端可以多次获取同一把锁
  ⑤ 高可用：锁服务本身不能是单点故障
```

**二、阶段一：手写 Redis 分布式锁（理解本质）**

```java
// ====== V1：SETNX + EXPIRE（❌ 有 Bug：非原子操作） ======
boolean lock1 = jedis.setnx("lock_key", "thread_1") == 1;
if (lock1) {
    jedis.expire("lock_key", 30);  // ← 如果这里进程崩溃，锁永不过期！死锁！
    // ... 业务逻辑 ...
    jedis.del("lock_key");
}
// Bug：setnx 和 expire 是两个命令 → 不是原子的！

// ====== V2：SET NX EX（✅ 原子操作，但解锁有 Bug） ======
String result = jedis.set("lock_key", "thread_1", 
    SetParams.setParams().nx().ex(30));  // nx + ex 原子！
if ("OK".equals(result)) {
    try {
        // ... 业务逻辑（假设执行了 40 秒） ...
    } finally {
        // ← 锁在 30 秒时已过期，被别的线程拿到了！
        jedis.del("lock_key");  // ← 误删了别人的锁！
    }
}

// ====== V3：Lua 脚本原子解锁（✅ 正确但简陋） ======
String lockValue = UUID.randomUUID().toString();  // 唯一标识
boolean locked = "OK".equals(
    jedis.set("lock_key", lockValue, SetParams.setParams().nx().ex(30))
);

if (locked) {
    try {
        // ... 业务逻辑 ...
    } finally {
        // Lua 脚本：先判断锁是否自己的，再删除（原子操作）
        String script = 
            "if redis.call('get', KEYS[1]) == ARGV[1] then " +
            "    return redis.call('del', KEYS[1]) " +
            "else " +
            "    return 0 " +
            "end";
        jedis.eval(script, Collections.singletonList("lock_key"),
                   Collections.singletonList(lockValue));
    }
}
// 问题：如果业务执行超过 30 秒，锁还是会过期 → 并发安全问题！
```

**三、阶段二：Redisson — 工业级分布式锁框架**

Redisson 在手写方案基础上，解决了三个核心问题：**可重入、自动续期、主从一致性保障**。

```java
// Redisson 使用（一行代码！）
RLock lock = redisson.getLock("order:lock:10086");
try {
    // ① tryLock：等待 3 秒获取锁，锁 30 秒自动过期（不设置 leaseTime 则启用看门狗）
    if (lock.tryLock(3, 30, TimeUnit.SECONDS)) {
        // 业务逻辑
    }
} finally {
    // ② 自动判断：是自己的锁才解锁
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

**Redisson 四大核心机制（源码级理解，面试高分！）：**

```
① 可重入机制 —— 基于 Redis Hash 结构

  Redisson 在 Redis 中存储的不是简单的 key-value，而是 Hash：
  
  Key: "order:lock:10086"
  Hash: {
    "UUID:threadId" → 2   ← 重入次数（同一线程 lock 两次 = 2）
  }

  伪代码：
  加锁时：hexists(key, uuid:threadId) → 存在 → hincrby(key, uuid:threadId, 1) → 重入成功
  解锁时：hincrby(key, uuid:threadId, -1) → counter == 0 → del(key) → 真正释放

② Watchdog 看门狗机制（核心黑科技！）

  触发条件：调用 lock() 时没有指定 leaseTime
  默认行为：
    → 加锁成功后，启动后台定时任务（每 10 秒执行）
    → 每次执行：将锁的过期时间重置为 30 秒（内部看门狗超时）
    → 只要客户端还持有锁，就一直续期 → 不会出现"业务没执行完锁就过期"
    → 客户端主动 unlock → 取消定时任务
    → 客户端崩溃 → 定时任务停止 → 30 秒后锁自动释放

  源码关键参数：
    lockWatchdogTimeout = 30 * 1000;  // 看门狗超时 30 秒
    续期间隔 = lockWatchdogTimeout / 3 = 10 秒  // 提前 1/3 续期

  为什么是 1/3 续期而不是快到 30 秒才续？
    → 1/3 间隔保证了高容错：即使某次续期失败（网络抖动），还有 2 次机会重试
    → 续期本身是异步的，主业务线程不受影响

③ 可重入 + Watchdog 的完整加锁交互时序：
  
  Client                          Redis
    │                               │
    │── EVAL 加锁 Lua ────────────→ │
    │   "if key不存在 → hset + pexpire" │
    │←── 成功 ────────────────────── │
    │                               │
    │  [启动 Watchdog 定时器]        │
    │                               │
    │  业务执行中... (可能存在 60 秒)    │
    │                               │
    │  10s: ── PEXPIRE 续期 30s ──→ │  ← 看门狗自动续期！
    │  20s: ── PEXPIRE 续期 30s ──→ │
    │  30s: ── PEXPIRE 续期 30s ──→ │
    │  ...                          │
    │                               │
    │── EVAL 解锁 Lua ────────────→ │
    │   "if 锁是我的 → hincrby -1"    │
    │   "if counter == 0 → del"     │
    │←── 成功 ────────────────────── │
    │                               │
    │  [停止 Watchdog 定时器]        │
```

**四、阶段三：RedLock（红锁）— 解决主从切换锁丢失**

```
问题场景（致命！）：
  ① Client-A 在 Redis Master 上获取锁成功
  ② Master 还没来得及同步给 Slave → Master 宕机
  ③ Slave 被哨兵提升为新 Master
  ④ 新 Master 上没有 Client-A 的锁数据！
  ⑤ Client-B 在新 Master 上获取同一把锁 → 成功！
  → 两个客户端同时持有同一把锁！💥

RedLock 算法思想（多数派投票）：
  ① 部署 N 个独立的 Redis Master 节点（通常 N=5，没有主从关系！）
  ② Client 依次向 N 个节点请求加锁
  ③ 当超过 N/2+1（即 ≥3）个节点返回成功时 → 加锁成功
  ④ 锁的实际有效时间 = 初始 TTL - 加锁过程总耗时
  ⑤ 解锁：向所有 N 个节点发送解锁请求（Lua 脚本）

  → 即使个别节点宕机，多数派存活 → 锁不丢失！
```

**Martin Kleppmann 对 RedLock 的经典质疑（面试加分项）：**

> RedLock 依赖系统时钟来保证安全。如果某个节点的时钟发生跳跃（如 NTP 跳跃），GC 导致进程暂停（STW），都会导致锁提前过期——而此时 Client 还以为锁在自己的手上，继续执行临界区。

```
典型攻击场景（时钟跳跃）：
  Client-A 在 5 个节点上获取锁，TTL=10s
  节点 3 时钟突然跳快了 15 秒 → 锁在节点 3 上提前过期
  Client-B 在节点 3 上获取锁 → 成功了！
  → Client-A 和 Client-B 同时认为自己持有锁！

Redisson 官方态度：
  从 Redisson 3.x 开始，RedLock 已标记为 @Deprecated
  官方推荐：使用 Redis Cluster 的单实例锁 + Watchdog
  实际生产中：绝大多数公司用 Redisson 的单实例锁就够了
```

**六、生产环境最佳实践**

```java
@Component
public class DistributedLockService {
    
    @Autowired
    private RedissonClient redisson;
    
    /**
     * 带自动续期的分布式锁（推荐方式）
     */
    public <T> T executeWithLock(String lockKey, long waitTime, 
                                  TimeUnit unit, Supplier<T> task) {
        RLock lock = redisson.getLock(lockKey);
        try {
            // 不指定 leaseTime → 自动启用看门狗续期
            if (lock.tryLock(waitTime, unit)) {
                return task.get();
            } else {
                throw new LockAcquireException("获取锁超时: " + lockKey);
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new LockAcquireException("获取锁被中断: " + lockKey);
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
    
    /**
     * 固定超时锁（不需要自动续期，执行快的场景）
     */
    public <T> T executeWithFixedTimeout(String lockKey, long waitTime,
                                          long leaseTime, TimeUnit unit,
                                          Supplier<T> task) {
        RLock lock = redisson.getLock(lockKey);
        try {
            if (lock.tryLock(waitTime, leaseTime, unit)) {
                return task.get();
            }
            throw new LockAcquireException("获取锁超时");
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new LockAcquireException("获取锁被中断");
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

### 💡 延伸思考

1. **为什么 Redisson 的锁 key 用 `UUID:ThreadId` 组合而不是只用 ThreadId？** — 只用 ThreadId 无法区分不同 JVM 实例中的同名线程（不同机器上 ThreadId 可能相同）。UUID 标识客户端实例，ThreadId 标识线程——两者组合才能保证全局唯一。
2. **能不能用 ZK 实现分布式锁？和 Redis 锁怎么选？** — ZK 通过临时顺序节点实现，天然支持锁的公平性（按创建顺序排队）和自动释放（客户端断开连接→临时节点自动删除）。ZK 是 CP 系统（强一致性），Redis 是 AP 系统（高可用）。选型原则：需要强一致性选 ZK，需要高性能选 Redis。

**难度**：⭐⭐⭐⭐⭐

### 📖 参考答案

**一、分布式事务的本质 — 没有银弹，只有权衡**

```
单体应用的本地事务（ACID）：
  BEGIN;
    UPDATE account SET balance = balance - 100 WHERE id = 1;
    UPDATE account SET balance = balance + 100 WHERE id = 2;
  COMMIT;
  → 数据库保证两个操作要么全成功，要么全回滚

微服务下事务"裂开"了：
  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
  │  订单服务      │    │  账户服务      │    │  库存服务      │
  │  创建订单 ✅   │    │  扣款 ✅       │    │  减库存 ❌     │
  └──────────────┘    └──────────────┘    └──────────────┘
         ↑                  ↑                   ↑
     订单库 DB1          账户库 DB2          库存库 DB3
     
  → 三个独立的数据库，怎么保证要么全成功要么全回滚？
  → CAP 定理：P（分区容错）必须满足 → 只能在 C（一致性）和 A（可用性）之间权衡
```

**二、CAP 与分布式事务选型**

```
C（强一致性）     vs     A（高可用性）
   │                        │
   ├─ 2PC / XA             ├─ 可靠消息最终一致性
   ├─ Seata AT             ├─ Saga（长事务）
   └─ TCC（偏 C）          └─ 本地消息表
   
   越往左：一致性越强，但性能越差
   越往右：性能越好，但一致性越弱
   
   BASE 理论（Basically Available, Soft state, Eventually consistent）：
   放弃强一致性，接受"短暂的不一致"，保证最终一致
```

**三、方案一：Seata AT 模式（阿里开源，最推荐 Java 微服务）**

Seata AT = **二阶段提交的优化版**，核心思路：在一阶段就提交本地事务（释放锁），二阶段异步提交或回滚。

```
Seata 三大角色：
  TC (Transaction Coordinator) — 事务协调器（服务端，独立部署）
  TM (Transaction Manager)      — 事务管理器（@GlobalTransactional 标注的方法）
  RM (Resource Manager)         — 资源管理器（各微服务的数据源）

AT 模式执行流程（以"下单+扣库存+扣款"为例）：

  ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
  │    TM   │    │    TC   │    │ 订单 RM │    │ 库存 RM │
  └────┬────┘    └────┬────┘    └────┬────┘    └────┬────┘
       │              │              │              │
  ① 开始全局事务      │              │              │
       │──────注册──────────────────→│              │
       │              │              │              │
       │ ② 执行本地事务+记录undo_log  │              │
       │              │              │──创建订单────→│
       │              │              │  (本地提交)   │
       │              │              │              │
       │ ③ 注册分支事务              │              │
       │              │←─注册分支1───│              │
       │              │              │              │
       │ ④ 执行本地事务+记录undo_log  │              │
       │              │              │     扣减库存 │
       │              │              │     (本地提交)│
       │              │              │              │
       │              │←─注册分支2───│──────────────│
       │              │              │              │
  ⑤ 全部成功 → 通知 TC 提交         │              │
       │─────提交────────────────→│              │
       │              │──删除undo_log───────────→│
       │              │──删除undo_log───────────→│
       │              │              │              │
     完成！           完成！          清理完成       清理完成

  AT 模式一阶段就提交本地事务！如果二阶段需要回滚 → 根据 undo_log 做逆向补偿
```

**AT 模式两个关键问题：**

```
问题1：脏读 —— AT 模式一阶段释放锁后有短暂窗口期
  
  一阶段：RM1 执行 UPDATE SET money = money - 100（本地提交，释放行锁）
          RM2 正在执行中...
  窗口期：另一个事务可以读到 money 已扣但"全局事务还未完成"的状态
          → 如果最终全局回滚，这个读到的数据就是"脏数据"
  
  Seata 的缓解：默认 READ COMMITTED 隔离级别 + SELECT FOR UPDATE 加锁
  
问题2：回滚补偿 —— undo_log 是什么？
  
  undo_log 表结构：
  ┌──────────┬───────────────┬──────────────┬─────────┐
  │ branch_id│     xid       │   rollback   │  status │
  ├──────────┼───────────────┼──────────────┼─────────┤
  │  123456  │  全局事务ID    │ 逆向SQL的快照│   0     │
  └──────────┴───────────────┴──────────────┴─────────┘

  一阶段执行 UPDATE account SET balance = 1000 → 900
  记录 undo_log:
    beforeImage: { "balance": 1000 }
    afterImage:  { "balance": 900 }
    rollback SQL: UPDATE account SET balance = 1000 WHERE id = 1 AND balance = 900
  
  二阶段回滚 → 执行 rollback SQL → 恢复到修改前的状态
  如果记录已被其他事务修改（balance != 900） → 回滚失败 → 需要人工介入
```

**四、方案二：TCC（Try-Confirm-Cancel）— 业务层补偿**

TCC 不依赖 undo_log，而要求**开发者手动实现**每个阶段的逻辑。

```java
// TCC 三阶段接口（每个参与方都要实现）
public interface TccService {
    
    // ① Try：预留资源（检查 + 冻结）
    boolean tryPhase(BusinessContext ctx);
    
    // ② Confirm：确认提交（使用已冻结的资源，幂等！）
    boolean confirmPhase(BusinessContext ctx);
    
    // ③ Cancel：取消回滚（释放冻结的资源，幂等！）
    boolean cancelPhase(BusinessContext ctx);
}

// 示例：账户扣款 TCC
@Service
public class AccountTccService implements TccService {
    
    @Override
    public boolean tryPhase(BusinessContext ctx) {
        // 冻结金额（不是直接扣款！）
        // UPDATE account SET frozen = frozen + 100, 
        //        available = available - 100
        // WHERE id = ? AND available >= 100
        // → available 扣了，但钱还在 frozen 字段里，没真正转账
    }
    
    @Override
    public boolean confirmPhase(BusinessContext ctx) {
        // 真正扣款：把冻结金额转走
        // UPDATE account SET frozen = frozen - 100
        // WHERE id = ?
    }
    
    @Override
    public boolean cancelPhase(BusinessContext ctx) {
        // 回滚：把冻结金额退回到可用余额
        // UPDATE account SET frozen = frozen - 100, 
        //        available = available + 100
        // WHERE id = ?
    }
}
```

**TCC 三大挑战（90% 的人答不上来）：**

| 挑战 | 场景 | 解决方案 |
|------|------|---------|
| **空回滚** | Try 没执行（网络超时未到达），但 Cancel 被调用 | Cancel 方法检查 Try 是否已执行，未执行则直接返回成功 |
| **防悬挂** | Cancel 先于 Try 到达（网络延迟）→ Try 后到 | Try 方法检查是否已被 Cancel，已取消则拒绝 |
| **幂等性** | Confirm/Cancel 被重复调用 | 每个阶段操作都带唯一业务 ID，数据库去重 |

```
空回滚示例：
  TM 发起全局事务 → 调用 Account 服务的 Try（网络超时）
  → TM 认为 Try 失败 → 回滚全局事务 → 调用 Account 的 Cancel
  → 但 Try 请求实际上没到达 Account！
  → Cancel 执行时发现"没有资源可释放" → 这就是空回滚
  → 处理：Cancel 查询 freeze_record 表，发现没有记录 → 直接返回 SUCCESS

防悬挂示例：
  TM 发起全局事务 → Try 请求发出（网络很慢，延迟了 30 秒）
  → TM 等待超时 → Cancel 请求发出（网络很快，1 秒到达）
  → Cancel 先执行（正常返回）
  → Try 后到（30 秒后到达！）
  → 如果不防悬挂：Try 会创建新的冻结记录 → 资源泄漏！
  → 处理：Try 检查"是否已被 Cancel"的记录，已取消 → 拒绝执行
```

**五、方案三：Saga 模式 — 长事务的编排与补偿**

Saga 把长事务拆成多个**本地事务** + 对应的**补偿事务**。

```
Saga = T1 → T2 → T3 → ... → Tn
        └─ C1 ← C2 ← C3 ← ... ← Cn（正向失败时逆序执行补偿）

场景：旅行预订（订机票 → 订酒店 → 租车）

  编排式 Saga（Choreography）：
    订单服务 → 事件 → 机票服务 → 事件 → 酒店服务
    → 每个服务独立决策并发布事件
    → 适合：简单流程、服务少

  协调式 Saga（Orchestration）：
    订单服务（协调器）→ 调用机票服务 → 调用酒店服务
    → 有一个总协调器控制流程
    → 适合：复杂流程、需要集中管理

Saga 核心原则：
  ① 每个正向操作都要有对应的补偿操作（语义回滚，非数据库回滚）
  ② 补偿操作必须幂等
  ③ 补偿操作允许最终失败 → 需要人工介入机制
```

**六、方案四：可靠消息最终一致性 — 最常用、最落地**

核心思想：**本地事务 + 消息队列事务消息**，保证"业务成功 → 消息必发"。

```
基于 RocketMQ 事务消息（半消息机制）：

  ┌──────────────┐                      ┌──────────────┐
  │   订单服务     │                      │  RocketMQ    │
  └──────┬───────┘                      └──────┬───────┘
         │                                     │
    ① 发送半消息（Half Message）               │
         │────────────────────────────────────→│
         │                                     │ 消息存入，但消费者不可见！
         │←──── 半消息发送成功 ────────────────│
         │                                     │
    ② 执行本地事务（创建订单）                   │
         │  INSERT INTO orders ...             │
         │                                     │
    ③ 根据本地事务结果，通知 MQ                  │
         │                                     │
    成功: │── Commit ────────────────────────→│ 消息对消费者可见！
    失败: │── Rollback ──────────────────────→│ 消息删除
         │                                     │
    超时: │  MQ 回调订单服务的 checkLocalTransaction()
         │  → 查询订单是否创建成功 → 决定 Commit 或 Rollback
         
  ┌──────────────┐
  │   库存服务     │ ← 消费"订单创建成功"消息
  │  扣减库存      │
  └──────────────┘

关键：半消息保证了"消息发送"和"本地事务"的原子性
```

### 💡 延伸思考

1. **Seata AT 和 TCC 的本质区别是什么？** — AT 是**资源层**补偿（基于 undo_log 自动生成回滚 SQL），TCC 是**业务层**补偿（开发者自己写补偿逻辑）。AT 的优势是简单（加注解就行），劣势是只支持关系型数据库。TCC 的优势是灵活（任何资源都可以，如 Redis/第三方 API），劣势是实现复杂度高。
2. **分布式事务失败后如何人工处理？** — 建立"事务监控与告警"体系：① 持久化全局事务日志（xid + 分支状态 + 业务上下文）；② RocketMQ 死信队列兜底；③ 管理后台提供"手动重试/手动补偿"按钮；④ 关键业务配备 OnCall 值班机制。
