**一、GC 知识体系全景图：先建骨架**

面试官问 JVM GC，不是要你背定义，而是要看你能否把知识点串成体系：

```
JVM 垃圾回收知识体系

① 判定标准：什么是垃圾？
   ├── 引用计数法（已被 JVM 抛弃）
   └── 可达性分析法（当前标准）→ GC Roots 枚举

② 基础回收算法（理论策略）
   ├── 标记-清除（Mark-Sweep）→ 碎片化问题
   ├── 标记-整理（Mark-Compact）→ 老年代常用
   └── 复制算法（Copying）→ 新生代常用

③ 并发标记理论（解决"标记期间对象引用变化"）
   └── 三色标记法 + 写屏障（增量更新 / SATB）

④ 具体收集器（落地实现）
   ├── 分代收集器：Serial / Parallel Scavenge / CMS
   └── 分区收集器：G1 / ZGC / Shenandoah

⑤ 调优实践
   └── GC 日志分析 / 参数调优 / 选择策略
```

**二、判定标准：怎么判断对象可回收？**

**(1) 引用计数法 — 已被 JVM 抛弃**

```
原理：每个对象维护一个引用计数器
  被引用 → 计数 +1
  引用失效 → 计数 -1
  计数为 0 → 可回收

致命缺陷：循环引用！
  class A { B b; }
  class B { A a; }
  A a = new A();  B b = new B();
  a.b = b;  b.a = a;
  a = null;  b = null;
  → a 和 b 互相引用，计数永远不为 0 → 内存泄漏！

目前只有 Python、Objective-C 等语言使用引用计数（Python 用标记-清除辅助处理循环引用）。
```

**(2) 可达性分析法 — JVM 当前标准**

```
原理：从一组"GC Roots"出发，沿引用链向下搜索
  可达的 → 存活
  不可达的 → 判定为垃圾，可回收

GC Roots 包括：
  ① 虚拟机栈（栈帧中的局部变量表）中引用的对象
  ② 方法区中静态属性引用的对象
  ③ 方法区中常量引用的对象（如 String Table）
  ④ 本地方法栈中 JNI 引用的对象
  ⑤ Java 虚拟机内部的引用（基本类型包装类、系统类加载器）
  ⑥ 所有被同步锁（synchronized）持有的对象
  ⑦ JVM 内部的 JMXBean、JVMTI 回调等
```

**三、三大基础 GC 算法**

| 算法 | 流程 | 优点 | 缺点 | 适用区域 |
|------|------|------|------|---------|
| **标记-清除** | ① 标记存活对象 ② 清除未标记对象 | 简单、不需要移动对象 | **内存碎片化**（大对象可能无法分配） | CMS 老年代 |
| **标记-整理** | ① 标记存活对象 ② 将存活对象向一端移动 ③ 清理边界外内存 | 无碎片 | 移动对象需要 STW，耗时较长 | Serial Old / Parallel Old 老年代 |
| **复制** | ① 将内存分为两块 ② 将存活对象复制到另一块 ③ 整体清理当前块 | 无碎片、速度快 | **浪费一半内存** | 新生代（Eden→Survivor） |

```
新生代为什么用复制算法？
  → 新生代 98% 对象"朝生夕灭"，存活对象少
  → 复制开销极低，但是预留空间利用率也高（Eden:Survivor = 8:1:1）
  → 10% 的"浪费"空间换来极高的回收效率

老年代为什么不用复制算法？
  → 老年代存活率高（多数对象长期存活）
  → 如果用复制算法 → 50% 空间被浪费，且复制开销极大
  → 所以用标记-清除（CMS）或标记-整理（Serial Old / G1）
```

**四、三色标记法 — 并发标记的理论基石**

CMS、G1、ZGC 都使用三色标记法来实现并发标记（用户线程和 GC 线程同时运行）：

```
三色含义：
  ⚪ 白色：尚未被访问的对象（标记结束后仍是白色 → 垃圾）
  ⬜ 灰色：自身被访问过，但其引用的子对象还没全部扫描
  ⬛ 黑色：自身及所有子对象都已被扫描（存活对象）

标记流程：
  ① 初始标记（STW）：GC Roots 直接关联对象 → 灰色
  ② 并发标记：从灰色对象出发，扫描子对象
     → 灰色对象扫描完变为黑色
     → 新发现的子对象变为灰色
  ③ 重复步骤 ②，直到没有灰色对象
  ④ 重新标记（STW）：处理并发期间变化
  ⑤ 白色对象 → 回收
```

**并发标记的核心问题：漏标与错标**

用户线程在并发标记期间修改引用关系，可能导致标记错误：

```
漏标（Missing Mark）— 最严重问题！
  条件（需同时满足）：
    ① 黑色对象新增了对白色对象的引用
    ② 灰色对象到该白色对象的引用被删除

  后果：白色对象被误判为垃圾 → 被回收 → 程序崩溃！

  示例：
    初始状态：A（黑）→ B（白，A的子对象已扫描完但没引用了）
                        C（灰）→ B（白）
    并发修改：A 新增引用 → B（A黑了，B不会被扫描！）
              C 删除引用 → B（C从灰变黑，B也不被扫描！）
    结果：B 实际是存活对象，但被漏标为垃圾！

错标（Floating Garbage）：
  对象原本是垃圾，并发期间又变成新的垃圾
  → 后果较轻：本次 GC 不回收，留到下次回收（浮动垃圾）
```

**解决方案：写屏障（Write Barrier）**

JVM 通过"写屏障"在引用关系变更时插入额外逻辑：

```
① 增量更新（Incremental Update）— CMS 采用
  → 当黑色对象新增引用时，将黑色对象重新标记为灰色
  → 破坏漏标条件 ①："新增引用"被拦截，黑色变灰色重新扫描
  → 实现：写后屏障（post-write barrier）

② SATB（Snapshot At The Beginning）— G1 采用
  → 在并发标记开始时，给当时的对象图拍"快照"
  → 当灰色对象删除引用时，将原引用目标记为存活（灰色）
  → 破坏漏标条件 ②："删除引用"被拦截，原引用对象保留
  → 实现：写前屏障（pre-write barrier）
  → 代价：可能产生更多浮动垃圾（但绝不会漏标！）

③ 读屏障 + 染色指针 — ZGC 采用
  → 在指针中存储 GC 状态信息，读操作时检查
  → 不需要写屏障，延迟极低
```

**五、三大垃圾收集器横向对比**

| 维度 | CMS | G1 | ZGC |
|------|-----|----|-----|
| **JDK 版本** | JDK 5 引入，JDK 9 弃用，JDK 14 移除 | JDK 7 引入，JDK 9 默认 | JDK 11 实验，JDK 15 生产，JDK 21 分代 |
| **设计目标** | 最短停顿时间 | 停顿时间可预测 | 亚毫秒级停顿 |
| **内存布局** | 分代（年轻代+老年代，连续） | 分区（Region） | 分区（Region/Page）+ 染色指针 |
| **回收算法** | 标记-清除 | 标记-整理（Region 间复制） | 标记-整理（并发整理） |
| **并发标记** | 三色标记 + 增量更新 | 三色标记 + SATB | 三色标记 + 染色指针 + 读屏障 |
| **STW 阶段** | 初始标记 + 重新标记 | 初始标记 + 重新标记 + 清理 | 仅初始标记（亚毫秒） |
| **碎片处理** | ❌ 产生碎片（并发模式失败时退化 Serial Old） | ✅ Region 间复制，无碎片 | ✅ 并发整理 |
| **停顿时间** | 几十~几百 ms | 默认 200ms（可调） | **< 1ms**（亚毫秒） |
| **适用堆大小** | < 8GB | 4GB ~ 64GB | **16GB ~ 16TB** |
| **内存开销** | 低 | 中（Remember Set ~5%） | 低（染色指针复用指针位） |
| **Full GC** | 可能触发（Serial Old 单线程，极慢） | 退化为 Serial Old（慢） | ⚠️ 理论上没有 Full GC！ |

**CMS 并发模式失败（Concurrent Mode Failure）的致命弱点：**

```
CMS 是老年代收集器，和用户线程并发执行。
问题：如果并发清理期间，老年代增长太快（新生代不断晋升对象）

  → 老年代满了，CMS 还没清理完
  → 触发 Concurrent Mode Failure
  → 退化为 Serial Old（单线程）→ 停顿数十秒甚至分钟级别！

这就是 CMS 被弃用的核心原因。
```

**G1 的核心设计：Region + Remember Set**

```
G1 将堆划分为大小相同的 Region（默认 2048 个，每个 1-32MB）

Region 四种类型：
  Eden Region  — 新生代 Eden
  Survivor Region — 新生代 Survivor
  Old Region — 老年代
  Humongous Region — 大对象（>= 50% Region 大小）

G1 Mixed GC（混合回收）：
  不是回收整个老年代，而是选择"回收收益最高"的若干 Old Region
  → 停顿时间可控（-XX:MaxGCPauseMillis=200）

Remember Set（记忆集）：
  记录"哪些 Region 引用了当前 Region 中的对象"
  → 避免了全堆扫描来确定跨 Region 引用
  → 占用约 5% 堆空间
```

**ZGC 的革命性创新：染色指针（Colored Pointers）**

```
ZGC 将 64 位指针中的 4 位用作 GC 状态标记：
  [42位地址][4位GC标记][18位未使用]

4 个标记位含义：
  → Finalizable：对象只能被 finalizer 访问
  → Remapped：指向对象的最新位置
  → Marked 0/1：交替使用，区分标记周期

核心优势：
  → 指针自带 GC 状态 → 读操作时就能知道对象状态
  → 不需要写屏障！单次读屏障即可完成并发整理
  → 对象移动时，保留旧的"转发表"（forwarding table）
  → 读屏障拦截 → 发现旧地址 → 修正为新地址（自愈！）
```

**六、选型决策与调优建议**

```
堆 < 4GB，JDK 8 → Parallel GC（吞吐量优先）
堆 < 4GB，JDK 11+ → G1（更好的停顿控制）

堆 4-64GB → G1（最成熟的平衡方案）
  -XX:MaxGCPauseMillis=200  目标停顿 200ms
  -XX:G1HeapRegionSize=4M   Region 大小

堆 > 64GB，JDK 15+ → ZGC
  -XX:+UseZGC
  -Xms64G -Xmx64G
  -XX:ConcGCThreads=4  并发 GC 线程数

堆 > 64GB，JDK 21+ → 分代 ZGC（Generational ZGC）
  -XX:+UseZGC -XX:+ZGenerational
  实现新生代和老年代分开回收，吞吐量比单代 ZGC 提升 10%+
```

**七、Full GC 触发条件（高频考点）**

```
① System.gc() — 显式调用（建议用 -XX:+DisableExplicitGC 禁止）
② 老年代空间不足 — 最常触发
③ 方法区（元空间）空间不足
④ 通过 Minor GC 后进入老年代的平均大小 > 老年代剩余空间
⑤ CMS GC 时出现 Concurrent Mode Failure
⑥ 担保失败：Minor GC 时 Survivor 放不下，老年代也放不下
```

### 💡 延伸思考

1. **为什么 G1 的 STW 时间可以"软实时"控制，而 CMS 不能？** — CMS 回收的是"整个老年代"，无法中断回收过程，一旦开始就必须等到结束。G1 回收的是"选中的若干个 Region"，通过 `MaxGCPauseMillis` 动态计算"本次可以回收多少个 Region"，中途达到时间目标可随时停止——剩下的下次再收。这就是增量式回收的思想。
2. **ZGC 的停顿为什么能做到亚毫秒？** — 三方面：① 染色指针 + 读屏障使得对象移动不需要 STW（自愈机制）；② 没有"Stop-the-World"的重新标记阶段（CMS/G1 有）；③ ZGC 将绝大部分工作都放在并发阶段，唯一需要 STW 的只有"初始标记"阶段，这个阶段只扫描 GC Roots 的直接引用，无论堆多大，工作量都极小。

## 题目 2：[Java并发] 请详细阐述 Java synchronized 关键字的底层原理：从对象头 MarkWord 结构与 Monitor 机制开始，完整讲解锁的四种状态（无锁→偏向锁→轻量级锁→重量级锁）的升级路径与触发条件，并说明为什么 JDK 15 默认关闭偏向锁、JDK 21 彻底废弃偏向锁

**难度**：⭐⭐⭐⭐
**考点来源**：2026-05-21 早间报告 — "后端Java面试：JVM 87道 + 多线程高并发108道" + CSDN大厂面试题汇总  
**相关岗位**：Java后端 / 高并发系统开发 / 中间件

### 📖 参考答案

**一、synchronized 是什么？为什么它是面试最高频的并发题？**

synchronized 是 Java 最基础的同步机制，但它的底层实现涵盖：对象内存布局、字节码指令、操作系统互斥量、JVM 锁优化策略——一条链路深挖下去，能精准考察候选人的底层功底。

```java
// 三种用法
// ① 实例方法 → 锁是 this
public synchronized void method1() { }

// ② 静态方法 → 锁是 Class 对象
public static synchronized void method2() { }

// ③ 代码块 → 锁是括号里的对象
synchronized (obj) { }
```

**字节码层面的实现：**

```
实例方法/静态方法：
  编译后在方法的 flags 中增加 ACC_SYNCHRONIZED 标记
  → JVM 检测到该标记 → 自动隐式 monitorenter/monitorexit

代码块：
  编译后在代码块前后插入 monitorenter 和 monitorexit 指令
  → monitorenter：尝试获取对象锁（Monitor）
  → monitorexit：释放对象锁（正常退出 + 异常退出各一个）
```

**二、对象头 MarkWord — 锁信息存储的物理载体**

HotSpot 虚拟机中，每个 Java 对象在堆内存中的布局：

```
┌──────────────────────────────────┐
│          Java 对象内存布局          │
├──────────┬──────────┬────────────┤
│ MarkWord │ Klass指针 │ 实例数据    │
│ (8字节)   │ (4/8字节) │ (不定长)    │
├──────────┴──────────┴────────────┤
│  对象头 (Object Header)          │  ← 锁信息全存在这里！
└──────────────────────────────────┘

MarkWord（64 位 JVM，8 字节）在不同锁状态下的结构：

无锁状态：
  [ unused:25 | hash:31 | unused:1 | age:4 | biased_lock:1 | lock:01 ]
  
偏向锁：
  [ thread_id:54 | epoch:2 | unused:1 | age:4 | biased_lock:1 | lock:01 ]

轻量级锁：
  [ ptr_to_lock_record:62 | lock:00 ]

重量级锁：
  [ ptr_to_heavyweight_monitor:62 | lock:10 ]

GC 标记：
  [ unused:62 | lock:11 ]

关键：最后 2 位（lock 标志位）决定锁状态：
  01 → 无锁 / 偏向锁（biased_lock 区分）
  00 → 轻量级锁
  10 → 重量级锁
  11 → GC 标记
```

**三、Monitor（管程）— 重量级锁的核心**

每个 Java 对象都可以关联一个 Monitor（由 C++ 的 ObjectMonitor 实现）：

```
ObjectMonitor 结构（简化）：
┌─────────────────────────────┐
│  _owner        → 持有锁的线程  │
│  _count        → 重入次数      │
│  _EntryList    → 等待获取锁的线程队列（阻塞队列）│
│  _WaitSet      → 调用 wait() 后的等待队列     │
└─────────────────────────────┘

线程获取锁流程：
  ① 进入 _EntryList 排队
  ② 竞争成功 → 成为 _owner → 进入临界区
  ③ 调用 wait() → 释放锁 → 进入 _WaitSet
  ④ 被 notify() → 从 _WaitSet 移到 _EntryList → 重新竞争
  ⑤ 执行完 → 释放锁 → _owner = null
```

**四、锁升级完整路径 — 为什么需要锁升级？**

synchronized 从 JDK 1.6 开始进行了大量优化——"锁升级"就是其中最核心的设计：

> **核心思想：大部分锁的竞争并不激烈，没必要每次都动用重量级锁（涉及内核态切换）。先用最轻量的方式加锁，竞争逐步升级。**

```
四种锁状态，只能升级不能降级：

  无锁 ──→ 偏向锁 ──→ 轻量级锁 ──→ 重量级锁
                ↑            ↑          ↑
          偏向撤销     自旋失败   涉及内核态切换
```

**阶段一：偏向锁（Biased Locking）—— "这门大概率还是我自己进"**

```
触发条件：同一个线程多次获取同一把锁（无竞争）

原理：
  ① 第一次获取锁：将 MarkWord 中的 thread_id 设置为当前线程 ID
  ② 之后该线程再次进入同步块：
     → 检查 MarkWord 中 thread_id == 当前线程？
     → 是 → 直接进入！（不需要 CAS！不需要加锁！）
  ③ 另一个线程尝试获取锁 → 触发偏向锁撤销

偏向锁撤销（代价高！）：
  需要在安全点（Safepoint）暂停原偏向线程
  → 检查原偏向线程是否还在同步块中
    → 不在：恢复无锁状态
    → 在：升级为轻量级锁（替换 MarkWord 为指向 Lock Record 的指针）

⚠️ 为什么 JDK 15+ 默认关闭偏向锁？
  ① 现代应用大量使用线程池，线程复用率极高
     → 偏向锁的"总是同一个线程"假设不再成立
  ② 偏向锁的撤销成本极高（需要全局安全点 STW）
  ③ 高并发场景下，偏向锁反而成为性能负担
     → 撤销次数越多，性能越差！

  JDK 15: -XX:-UseBiasedLocking（默认关闭）
  JDK 21: 彻底移除偏向锁实现
```

**阶段二：轻量级锁（Lightweight Locking）—— "我自旋等一下"**

```
触发条件：多线程交替执行（无实际竞争，只是时间上错开了）

原理：CAS 自旋
  ① 线程在自己的栈帧中创建 Lock Record
  ② 通过 CAS 将 MarkWord 替换为指向 Lock Record 的指针
     → 成功 → 获取轻量级锁
     → 失败 → 自旋等待（循环 CAS 尝试）

自旋等待的优化：
  自适应自旋（JDK 1.6+）：
    → 如果上次自旋成功了 → 这次多自旋一会
    → 如果上次自旋失败了 → 这次少自旋或直接升级

升级为重量级锁的条件：
  → 自旋超过阈值（JDK 6 默认 10 次，自适应后动态调整）
  → 或同一时刻有超过 1 个线程在竞争

Lock Record 结构：
  每个线程的栈帧中维护一个 Lock Record 列表
  ┌─────────────────┐
  │ Lock Record      │
  │ → displaced_hdr  │  ← 保存原有的 MarkWord
  │ → owner          │  ← 指向锁对象
  └─────────────────┘
```

**阶段三：重量级锁（Heavyweight Locking）—— "排大队，等就完了"**

```
触发条件：真正的多线程激烈竞争

原理：
  → Monitor（ObjectMonitor）接管
  → 未获取锁的线程进入 _EntryList 阻塞
  → 涉及内核态 Mutex → 线程挂起/唤醒成本高
  → 适合锁竞争激烈、临界区执行时间长的场景
```

**五、锁升级流程总结（一图胜千言）**

```
线程 A 第一次进入 synchronized(this)

① 检查 MarkWord → 无锁状态
   → CAS 将 thread_id 设为 A → 偏向锁 ✅
   
线程 A 再次进入同一个 synchronized(this)
   → thread_id == A → 直接进入！✅（不用任何同步操作！）

线程 A 退出 synchronized → 保持偏向锁状态（不会降级回无锁）

────────────────────────────────────

线程 B 尝试进入 synchronized(this)（A 已退出）

② MarkWord 中 thread_id == A ≠ B
   → 触发偏向锁撤销
   → 暂停 A（安全点）→ A 已退出同步块 → 撤销偏向
   → B 尝试 CAS 获取轻量级锁 → 成功 ✅ → 轻量级锁

────────────────────────────────────

线程 B 持有锁，线程 C 尝试进入

③ C 尝试 CAS → 失败 → 开始自旋
   循环 CAS 尝试获取锁...

④ B 很快释放锁 → C CAS 成功 → 轻量级锁 ✅
   如果 B 很长时间不释放 → C 自旋超时
   → 轻量级锁膨胀为重量级锁
   → C 进入 Monitor._EntryList 阻塞等待
   → B 释放时唤醒 C（内核态操作）
```

**六、synchronized vs ReentrantLock 选型**

| 维度 | synchronized | ReentrantLock |
|------|-------------|---------------|
| **实现** | JVM 内置（C++ ObjectMonitor） | Java AQS 实现 |
| **锁释放** | 自动（退出同步块/异常） | 手动（必须 finally unlock） |
| **公平性** | 非公平 | 可选公平/非公平 |
| **条件变量** | wait/notify（单一等待队列） | Condition（多等待队列） |
| **可中断** | ❌ 不支持 `lockInterruptibly` | ✅ 支持 |
| **tryLock** | ❌ 不支持 | ✅ 支持（尝试获取超时返回） |
| **性能** | JDK 6+ 优化后接近（锁升级 + 自适应自旋） | 略高（功能更多） |
| **推荐场景** | 简单同步、代码块锁 | 需要条件变量、可中断、超时等高级特性 |

### 💡 延伸思考

1. **偏向锁被废弃后，ThreadLocal 的 "线程绑定" 特性还重要吗？** — ThreadLocal 和偏向锁解决的是不同层面的问题。偏向锁解决的是"同一个锁被同一线程反复获取"的性能优化，而 ThreadLocal 解决的是"每个线程需要自己的数据副本"。偏向锁的废弃不影响 ThreadLocal 的价值——它们不是替代关系。
2. **锁粗化（Lock Coarsening）和锁消除（Lock Elimination）是什么？** — 锁粗化：JIT 编译器发现你连续对同一个对象加锁/释放锁多次 → 将多次加锁合并为一次（扩大锁的范围）。锁消除：JIT 编译器通过逃逸分析发现锁对象不会被其他线程访问 → 直接消除锁。这两项优化都在编译期完成，对性能影响显著。

## 题目 3：[数据库/MySQL] 请完整阐述 InnoDB 的 MVCC（多版本并发控制）原理：包括行记录的三个隐藏字段（DB_TRX_ID / DB_ROLL_PTR / DB_ROW_ID）、undo log 版本链的形成机制、ReadView 的结构与可见性判断算法，并重点说明 MVCC 在 READ COMMITTED 与 REPEATABLE READ 隔离级别下的实现差异（为什么 RR 能解决不可重复读但仍有幻读风险）

**难度**：⭐⭐⭐⭐⭐
**考点来源**：2026-05-21 早间报告 — "后端Java面试：MySQL 83道" + 2026大厂面试题汇总  
**相关岗位**：Java后端 / DBA / 数据库开发

### 📖 参考答案

**一、MVCC 解决的核心问题**

MySQL InnoDB 面临一个根本矛盾：**读操作和写操作冲突**——写的时候不能读（读到脏数据），读的时候不能写（写要加锁等读完）。

MVCC 的解决思路：**写操作创建新版本，读操作读取合适的旧版本——读写互不阻塞，大幅提升并发性能。**

> 一句话：MVCC 是一种"以空间换时间"的无锁并发控制机制——通过维护数据的多个历史版本，让读操作不需要加锁就能获取一致性快照。

**二、行记录的三个隐藏字段**

InnoDB 中每一行记录都包含三个隐藏的内部字段，它们支撑着 MVCC 的运作：

```
┌──────────────────────────────────────────────┐
│              InnoDB 行记录结构                  │
│                                              │
│  ┌──────────┬──────────┬──────────┬────────┐ │
│  │DB_TRX_ID │DB_ROLL_PTR│DB_ROW_ID│ 用户数据 │ │
│  │ (6字节)   │ (7字节)   │ (6字节)  │        │ │
│  └──────────┴──────────┴──────────┴────────┘ │
│      ↑           ↑           ↑               │
│  最后修改的   回滚指针指向  隐藏主键               │
│  事务ID       undo log    (无主键时自动生成)      │
└──────────────────────────────────────────────┘

DB_TRX_ID（6 字节）：
  → 最后修改该行记录的事务 ID
  → 事务 ID 是全局递增分配的
  → 作用：ReadView 通过比较此值判断版本可见性

DB_ROLL_PTR（7 字节）：
  → 指向 undo log 中该行记录的上一个版本
  → 构成版本链的"指针"

DB_ROW_ID（6 字节）：
  → 如果没有显式主键或唯一索引 → 自动生成隐藏主键
  → 聚簇索引 B+ 树需要主键来组织数据
```

**三、undo log 版本链 — 多版本存储机制**

```
每一次 update/delete 操作都会：
  ① 在 undo log 中保存旧版本数据
  ② 更新行记录的 DB_TRX_ID 为新事务 ID
  ③ DB_ROLL_PTR 指向 undo log 中的旧版本

示例：假设初始一行数据，经历 3 次事务修改：

事务 T1 (trx_id=100) INSERT：
  聚簇索引行：
  [ DB_TRX_ID=100 | DB_ROLL_PTR=null | name='张三' | age=20 ]
                      ↑ (没有旧版本)

事务 T2 (trx_id=200) UPDATE age=25：
  undo log: ← [ DB_TRX_ID=100 | DB_ROLL_PTR=null | age=20 ]
  ┌───────────┘
  聚簇索引行：
  [ DB_TRX_ID=200 | DB_ROLL_PTR=→undo1 | name='张三' | age=25 ]

事务 T3 (trx_id=300) UPDATE name='张三丰'：
  undo log: ← [ DB_TRX_ID=200 | DB_ROLL_PTR=→undo1 | name='张三' | age=25 ]
  ┌───────────┘                          ↑
  聚簇索引行：                           指向更早版本
  [ DB_TRX_ID=300 | DB_ROLL_PTR=→undo2 | name='张三丰' | age=25 ]

如今 undo log 版本链如下：
  当前版本(T3) → undo2(T2) → undo1(T1) → null
  
  不同事务可以沿版本链找到自己需要的版本！
```

**undo log 的两种类型：**

| 类型 | 对应操作 | 作用 |
|------|---------|------|
| **insert undo log** | INSERT | 事务提交后即可删除（插入的数据对其他事务不可见，没有历史版本需求） |
| **update undo log** | UPDATE / DELETE | MVCC 版本链的载体，事务提交后不能立即删除（其他事务可能还在读旧版本），由 purge 线程异步清理 |

**四、ReadView — "我该看到哪个版本？"**

ReadView 是事务执行快照读时创建的"数据可见性快照"，决定了当前事务能看到哪些版本：

```
ReadView 结构（核心属性）：
┌────────────────────────────────┐
│  m_ids       ← 当前活跃事务ID列表（未提交的事务）      │
│  min_trx_id  ← 活跃事务中最小的ID                    │
│  max_trx_id  ← 预分配的下一个事务ID（全局最大+1）       │
│  creator_trx_id ← 创建该 ReadView 的事务ID           │
└────────────────────────────────┘

可见性判断算法（对一个数据版本，检查其 DB_TRX_ID）：

  if (DB_TRX_ID == creator_trx_id) {
      // ① 自己修改的 → 可见（能看到自己的未提交修改）
      return 可见;
  }
  
  if (DB_TRX_ID < min_trx_id) {
      // ② 比最小活跃事务还小 → 在 ReadView 创建前就已提交 → 可见
      return 可见;
  }
  
  if (DB_TRX_ID >= max_trx_id) {
      // ③ 在 ReadView 创建之后才开始的事务 → 不可见
      return 不可见;  // 沿版本链向前找上一个版本
  }
  
  // ④ DB_TRX_ID 在 [min_trx_id, max_trx_id) 之间
  if (DB_TRX_ID ∈ m_ids) {
      // ④a 在活跃列表中 → 未提交 → 不可见
      return 不可见;
  } else {
      // ④b 不在活跃列表中 → 已提交（虽然区间内但已提交了）→ 可见
      return 可见;
  }
```

**五、RC vs RR 的核心差异：ReadView 的生成时机**

这是 MVCC 面试中最关键的区别点：

```
READ COMMITTED（读已提交）：
  每次快照读都生成一个新的 ReadView

  效果：
    事务 A（RR）两次读取期间：
      → 第一次读：生成 ReadView_1（m_ids = [A, B]）
      → 事务 B 提交了修改
      → 第二次读：生成 ReadView_2（m_ids = [A]）
      → ReadView_2 中 B 不在活跃列表 → B 的修改变为可见
      → 两次读结果不同 → 出现不可重复读！

REPEATABLE READ（可重复读）：
  仅在第一次快照读时生成 ReadView，之后复用

  效果：
    事务 A（RR）两次读取期间：
      → 第一次读：生成 ReadView_1（m_ids = [A, B]）
      → 事务 B 提交了修改
      → 第二次读：复用 ReadView_1（m_ids = [A, B]）
      → B 仍在活跃列表中 → B 的修改不可见！
      → 两次读结果相同 → 可重复读！✅
```

**示例验证：**

```sql
-- 初始数据：id=1, name='张三'

-- Session A (RR)
BEGIN;
SELECT * FROM users WHERE id=1;  -- 结果: 张三
-- 此时生成 ReadView_A: m_ids=[A], min_trx_id=A

-- Session B
BEGIN;
UPDATE users SET name='李四' WHERE id=1;
COMMIT;  -- B 的事务 ID 加入 m_ids? No，在 ReadView_A 的 m_ids 中吗？
         -- 如果 ReadView_A 是第一次查生成的，且 B 的 trx_id > max_trx_id → 不可见

-- Session A (RR)
SELECT * FROM users WHERE id=1;  -- 结果: 张三（复用 ReadView_A，不可重复读被阻止了！）
COMMIT;
```

**六、快照读 vs 当前读**

```
快照读（Snapshot Read）：
  → 读取的是 ReadView 决定的版本（可能是历史版本）
  → 不加锁（乐观）
  → SELECT（普通查询）
  → 基于 MVCC 实现

当前读（Current Read）：
  → 读取的是最新版本（已提交的最新数据）
  → 加锁（悲观）
  → SELECT ... FOR UPDATE / SELECT ... LOCK IN SHARE MODE
  → UPDATE / DELETE / INSERT
  → 基于 Next-Key Lock 实现
```

**七、为什么 RR 仍有幻读风险？**

```
RR 下 MVCC（快照读）能解决不可重复读和部分幻读：
  → 同一个事务内，快照读用的是同一个 ReadView
  → INSERT 的新数据不会影响已有 ReadView
  → ✅ 快照读不会出现幻读

BUT！

当前读会出现幻读：
  -- Session A (RR)
  BEGIN;
  SELECT * FROM users WHERE age > 18;  -- 快照读：2 条
  
  -- Session B
  INSERT INTO users VALUES (4, '王五', 25);
  COMMIT;
  
  -- Session A
  SELECT * FROM users WHERE age > 18 FOR UPDATE;  -- 当前读：3 条！
  -- ⚠️ 幻读出现了！FOR UPDATE 是当前读，读到最新数据

InnoDB 的解决方案：Next-Key Lock（记录锁 + 间隙锁）
  → 当前读时，对 WHERE 条件范围加 Next-Key Lock
  → 锁住已有记录 + 记录之间的间隙
  → 防止其他事务在这个范围内 INSERT
  → ✅ 当前读也解决了幻读
```

**八、MVCC 核心面试问答清单**

```
Q: MVCC 只在哪些隔离级别生效？
A: READ COMMITTED 和 REPEATABLE READ
   → READ UNCOMMITTED：不需要 MVCC，直接读最新（脏读）
   → SERIALIZABLE：所有读都是当前读，用锁实现

Q: MVCC 有没有解决幻读？
A: 快照读解决了，当前读没有——当前读用 Next-Key Lock 补充解决

Q: undo log 会不会无限膨胀？
A: 不会。purge 线程会定期清理不再被任何 ReadView 需要的旧版本

Q: 大事务为什么被诟病？
A: 长时间不提交 → ReadView 一直不释放 → undo log 不能清理
   → 版本链越来越长 → 查询越来越慢 + 磁盘空间爆炸
```

### 💡 延伸思考

1. **PostgreSQL 的 MVCC 和 MySQL InnoDB 有什么本质差异？** — PG 没有 undo log，旧版本直接存在数据页中（多版本存储），通过 VACUUM 回收。MySQL InnoDB 旧版本在 undo log 中，当前版本在数据页中。PG 的 MVCC 实现更"纯粹"但 VACUUM 代价高，MySQL InnoDB 的实现更"紧凑"但版本链遍历有开销。
2. **长事务导致 undo log 膨胀怎么排查？** — 查 `information_schema.innodb_trx` 找到运行时间最长的事务，查看 `trx_started` 时间。如果发现有小时级甚至天级的未提交事务 → 立即杀掉或通知业务方修复。同时建议配置 `innodb_undo_log_truncate=ON` 并设置合理的 `max_execution_time`。

**四、Redis 预减库存 — 秒杀系统的灵魂**

> 这是整个系统最关键的一环——如果这一步出问题，后面所有环节都白搭。

**为什么版本一（纯 Java 操作）会超卖？**

```java
// ❌ 版本一：先读再写——典型超卖代码！
int stock = redisTemplate.opsForValue().get("stock");
if (stock > 0) {
    redisTemplate.opsForValue().decrement("stock");
    // ...
}
// 问题：1000 个并发同时读到 stock=1 → 全部通过 → 超卖 999 件！
```

**✅ 正确方案：Redis + Lua 原子操作**

```java
@Service
public class SeckillService {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    @Autowired
    private RabbitTemplate rabbitTemplate;
    
    // Lua 脚本：原子性的"检查-扣减-记录"操作
    private static final String SECKILL_LUA = """
        -- KEYS[1]: 库存 key         (seckill:stock:{productId})
        -- KEYS[2]: 已购买集合 key    (seckill:bought:{productId})
        -- ARGV[1]: 用户 ID
        -- ARGV[2]: 秒杀地址 MD5 token
        
        -- ① 检查是否已购买（幂等性！）
        if redis.call('sismember', KEYS[2], ARGV[1]) == 1 then
            return -1  -- 已购买过
        end
        
        -- ② 检查库存
        local stock = tonumber(redis.call('get', KEYS[1]))
        if stock == nil or stock <= 0 then
            return 0  -- 库存不足
        end
        
        -- ③ 扣减库存（DECR 是原子操作！）
        redis.call('decr', KEYS[1])
        
        -- ④ 记录已购买（SET 集合的去重特性 = 天然幂等）
        redis.call('sadd', KEYS[2], ARGV[1])
        
        return 1  -- 秒杀成功
        """;
    
    private DefaultRedisScript<Long> seckillScript;
    
    @PostConstruct
    public void init() {
        seckillScript = new DefaultRedisScript<>();
        seckillScript.setScriptText(SECKILL_LUA);
        seckillScript.setResultType(Long.class);
    }
    
    /**
     * 秒杀核心逻辑（Redis + Lua 原子执行）
     */
    public SeckillResult executeSeckill(String productId, String userId, String md5) {
        // ① 校验秒杀地址（防脚本！防止用户绕过前端直接调 API）
        String correctMd5 = seckillMd5Cache.get(productId);
        if (!md5.equals(correctMd5)) {
            return SeckillResult.fail("秒杀地址无效");
        }
        
        // ② 执行 Lua 脚本（Redis 单线程执行，保证原子性）
        Long result = redisTemplate.execute(
            seckillScript,
            Arrays.asList(
                "seckill:stock:" + productId,
                "seckill:bought:" + productId
            ),
            userId, md5
        );
        
        // ③ 根据返回值处理
        if (result == 1) {
            // 秒杀成功 → 发送 MQ 消息异步下单
            SeckillMessage message = new SeckillMessage(productId, userId);
            rabbitTemplate.convertAndSend("seckill.order", message);
            return SeckillResult.success("秒杀成功，订单处理中...");
            
        } else if (result == -1) {
            return SeckillResult.fail("您已参与过本次秒杀");
        } else {
            return SeckillResult.fail("很遗憾，已售罄");
        }
    }
}
```

**Lua 脚本为什么能保证原子性？**

```
Redis 执行 Lua 脚本的两个保证：
  ① 单线程执行：Redis 是单线程模型，Lua 脚本执行期间不会插入其他命令
  ② 原子性：整个脚本要么全部执行，要么全部不执行
  → "读库存"和"减库存"之间不可能有另一个请求插入
  → 从根源上杜绝了超卖！
```

**五、MQ 异步下单 — 削峰填谷**

秒杀成功后不是直接写库，而是通过消息队列异步处理——这就是"削峰填谷"：

```
为什么不能同步写库？
  Redis 扛 10 万 QPS → 秒杀成功 1000 人
  如果 1000 个人同步写 MySQL → 数据库连接池 20 个
  → 后面的 980 个人干等 → 超时 → 失败 → 体验崩溃

MQ 的作用：
  1000 条消息 → RabbitMQ → 消费者逐个处理
  → 数据库从容不迫地写入（控制速率）
  → 用户秒杀时只需等 Redis 响应（1ms），不需要等 DB 响应（50ms+）
```

```java
// MQ 配置
@Configuration
public class SeckillMQConfig {
    
    // 秒杀订单队列
    @Bean
    public Queue seckillOrderQueue() {
        return QueueBuilder.durable("seckill.order.queue")
            .maxLength(5000)  // 队列最大长度（防止无限堆积）
            .build();
    }
    
    @Bean
    public DirectExchange seckillExchange() {
        return new DirectExchange("seckill.exchange");
    }
    
    @Bean
    public Binding binding() {
        return BindingBuilder.bind(seckillOrderQueue())
            .to(seckillExchange())
            .with("seckill.order");
    }
}

// MQ 消费者
@Component
public class SeckillOrderConsumer {
    
    @Autowired
    private OrderService orderService;
    
    @RabbitListener(queues = "seckill.order.queue")
    @RabbitHandler
    public void handleSeckillOrder(SeckillMessage message, 
                                    Channel channel, 
                                    @Header(AmqpHeaders.DELIVERY_TAG) long tag) {
        try {
            // ① 数据库最终扣减库存（乐观锁）
            boolean success = orderService.createSeckillOrder(
                message.getProductId(), 
                message.getUserId()
            );
            
            if (success) {
                // ② 成功 → 确认消息
                channel.basicAck(tag, false);
            } else {
                // ③ 库存扣减失败（异常情况，如 Redis 已扣但 DB 数据不一致）
                // → 死信队列 → 人工介入
                channel.basicNack(tag, false, false);
                log.error("秒杀DB扣减失败: {}", message);
            }
        } catch (Exception e) {
            // ④ 异常 → 不确认，等待重试
            try {
                channel.basicNack(tag, false, true);
            } catch (IOException ex) {
                log.error("消息确认异常", ex);
            }
        }
    }
}
```

**六、数据库最终扣减 — 乐观锁兜底**

```sql
-- 数据库库存表
CREATE TABLE seckill_stock (
    product_id BIGINT PRIMARY KEY,
    stock INT NOT NULL,
    version INT NOT NULL DEFAULT 0,  -- 乐观锁版本号
    CONSTRAINT chk_stock CHECK (stock >= 0)
);

-- 扣减库存（乐观锁）
-- 使用 version 字段保证幂等性和不超卖
UPDATE seckill_stock 
SET stock = stock - 1, version = version + 1
WHERE product_id = #{productId} 
  AND stock > 0              -- 库存充足
  AND version = #{version};  -- 乐观锁版本号匹配

-- 受影响行数 = 1 → 成功；= 0 → Redis 和 DB 数据不一致 → 告警！
```

```java
// 订单创建（数据库层面）
@Transactional
public boolean createSeckillOrder(Long productId, Long userId) {
    // ① 扣库存（乐观锁）
    SeckillStock stock = stockMapper.selectById(productId);
    int rows = stockMapper.deductStock(productId, stock.getVersion());
    
    if (rows == 0) {
        return false;  // 乐观锁失败 → 可能库存已空或数据不一致
    }
    
    // ② 创建订单（唯一索引防重：product_id + user_id）
    try {
        SeckillOrder order = new SeckillOrder();
        order.setProductId(productId);
        order.setUserId(userId);
        order.setCreateTime(new Date());
        orderMapper.insert(order);
        return true;
    } catch (DuplicateKeyException e) {
        // 唯一索引冲突 → 重复下单 → 不回滚库存（已扣过了）
        return false;
    }
}
```

**七、全链路降级与兜底方案**

```
① 限流降级
  当 QPS 超过 Nginx 阈值 → 返回"活动太火爆，请稍后再试"
  当网关发现下游超时率 > 50% → 熔断，直接返回降级页面

② 缓存兜底
  Redis 集群故障 → 降级为本地 Caffeine 缓存（库存数据）
  → 本地缓存数据可能不是最新的，但总比直接打到 DB 强

③ 库存兜底
  定时任务：每分钟检查一次 Redis 库存 vs DB 库存
  → 如果偏差 > 阈值 → 告警 + 人工介入
  → 如果 Redis 挂了 → 切到 DB 扣库存（限流到 100 QPS）

④ MQ 兜底
  消费者异常 → 消息进入死信队列
  → 定时任务扫描死信队列 → 重试 / 补偿

⑤ 数据库兜底
  主库压力大 → 读操作切到从库
  热点商品 → 拆分到独立的数据库实例（热点隔离）

⑥ 人工兜底
  秒杀结束后 → 数据核对（Redis 扣减数 = DB 扣减数 = 订单数）
  → 不一致 → 人工补偿（退款/补发）
```

### 💡 延伸思考

1. **如果秒杀系统依赖 Redis，Redis 挂了怎么办？** — 多级降级：① Redis Cluster（主从 + 哨兵，正常情况不会全挂）；② Redis 挂了 → 本地缓存降级（Caffeine），用过期前最后一次同步的库存数据，宁可少卖也不能超卖；③ 全部缓存都挂了 → 限流到 100 QPS 直连数据库，数据库加乐观锁防超卖——虽然很慢但还能用。
2. **秒杀系统的"秒杀地址隐藏"是什么意思？** — 秒杀开始前，前端显示"即将开始"，后台不暴露真实秒杀 URL。秒杀开始时刻，前端先请求 `/seckill/getMd5/{productId}` 获取一个动态生成的 MD5 token，然后带着这个 token 调真正的秒杀接口。这个设计防止了两件事：① 程序员通过抓包提前知道 URL → 写脚本提前请求；② 秒杀开始时所有人同一毫秒请求 → 通过 getMd5 的响应时间差异分散请求（自然限流）。

**一、为什么要讨论 Agent 安全？—— "AI 没说胡话，但它可能干了坏事"**

传统 AI 安全讨论聚焦于"模型输出质量"（幻觉、偏见、有害内容）。但 Agent 时代的安全风险完全不同：

```
传统 LLM 聊天应用的风险：
  → 模型说了错误的话（质量问题）

Agent 的增量风险：
  → 模型调用了不该调用的工具（安全问题！）
  → 模型被注入指令后删了数据库
  → 模型越权访问了其他用户的敏感数据
  → 攻击者通过精心构造的输入窃取了 API Key

一句话：Chat 是"内容风险"，Agent 是"执行风险"。
内容风险最多是声誉损失，执行风险可能造成真金白银的损失——甚至是安全事故。
```

**二、核心安全前提：LLM 是不可信的调用者**

> 这是 Agent 安全治理的"第一性原理"——LLM 的本质是概率模型，攻击者可以通过 Prompt Injection 诱导它执行任何操作。**任何来自 LLM 的工具调用请求，都必须经过服务端的安全校验。**

```
┌────────────────────────────────────────────┐
│          LLM 的特殊身份                       │
│                                            │
│  传统 API：调用方是经过认证的"自己人"           │
│  微信小程序 → API Gateway（JWT 签名校验）→ 后端  │
│  → 身份确定、权限明确、行为可预期               │
│                                            │
│  Agent 工具调用：调用方是 LLM                  │
│  LLM → MCP Server / Tool Gateway → 后端       │
│  → LLM 的身份 ≠ 用户的身份！                   │
│  → LLM 可能被诱导调用它本不该调用的工具！         │
│  → LLM 传的参数可能是被注入的恶意参数！          │
│                                            │
│  ⚠️ 结论：LLM 的所有输出（包括工具调用决策）          │
│     必须经过和外部用户输入同等级别的安全校验！       │
└────────────────────────────────────────────┘
```

**三、鉴权分层模型：三层权限控制**

有效的 Agent 安全不是"加个登录就行"，而是需要三层精细化的权限控制：

```
鉴权分层模型（由外到内）：

┌──────────────────────────────────────────────┐
│  Layer 1: 用户级鉴权（Who is calling?）         │
│  ───────────────────────────────────────     │
│  验证：这个请求来自哪个真实用户？                  │
│  手段：JWT Token / OAuth2 / API Key            │
│  粒度：整个服务 / 整个会话                      │
│                                              │
│  Layer 2: 会话级鉴权（In what context?）       │
│  ───────────────────────────────────────     │
│  验证：这个会话允许执行哪些操作？                  │
│  手段：Session Scope / 租户隔离                 │
│  粒度：单个对话/任务上下文                       │
│  示例：用户 A 在聊天1中说"查我的订单"              │
│        → 只能查用户 A 的订单，不能查用户 B 的      │
│                                              │
│  Layer 3: 工具级鉴权（What action?）            │
│  ───────────────────────────────────────     │
│  验证：这个具体操作是否被允许？                    │
│  手段：工具白名单 / 参数白名单 / 风险分级         │
│  粒度：每个工具调用的每个参数                     │
│  示例：LLM 想执行 DELETE FROM users             │
│        → 检查：DELETE 在用户的白名单中吗？        │
│        → 不在！拒绝执行！                        │
└──────────────────────────────────────────────┘
```

**实战代码：三层鉴权的 Java 实现**

```java
@Service
public class AgentSecurityGateway {
    
    // ========== Layer 1: 用户级鉴权 ==========
    public boolean authenticateUser(String sessionToken) {
        JwtClaims claims = jwtUtil.validateToken(sessionToken);
        if (claims == null) {
            throw new UnauthorizedException("无效的会话令牌");
        }
        // 将 userId 绑定到当前请求上下文
        RequestContext.setCurrentUserId(claims.getUserId());
        return true;
    }
    
    // ========== Layer 2: 会话级鉴权 ==========
    public boolean authorizeSession(String sessionId, String requestedUserId) {
        // 会话只能访问会话所属用户的数据
        String sessionOwner = sessionStore.getUserId(sessionId);
        return sessionOwner != null && sessionOwner.equals(requestedUserId);
    }
    
    // ========== Layer 3: 工具级鉴权 + 风险分级 ==========
    public ToolCallResult authorizeToolCall(ToolCallRequest request) {
        String toolName = request.getToolName();
        Map<String, Object> params = request.getParameters();
        String userId = RequestContext.getCurrentUserId();
        
        // ① 工具白名单检查
        Set<String> allowedTools = userToolWhitelist.getOrDefault(userId, 
            Set.of("query_users", "get_weather", "calculate"));
        if (!allowedTools.contains(toolName)) {
            auditLog.warn("工具调用被拒绝", userId, toolName, "不在白名单中");
            return ToolCallResult.deny("工具 " + toolName + " 未授权");
        }
        
        // ② 风险分级
        RiskLevel risk = classifyRisk(toolName, params);
        
        switch (risk) {
            case LOW:  // 读操作、查询天气、计算器 → 自动放行
                return ToolCallResult.allow();
                
            case MEDIUM:  // 创建订单、发送通知 → 参数校验后放行
                if (!validateParams(toolName, params)) {
                    return ToolCallResult.deny("参数校验失败");
                }
                return ToolCallResult.allow();
                
            case HIGH:  // 删除、修改权限、退款 → 需要人工确认
                // 返回"需要确认"，等待人工审批
                return ToolCallResult.needApproval(
                    "操作[" + toolName + "]需要人工确认", 
                    createApprovalTicket(toolName, params, userId)
                );
                
            case CRITICAL:  // DROP TABLE、关闭服务器 → 直接拒绝
                auditLog.critical("关键操作被自动拒绝", userId, toolName, params);
                return ToolCallResult.deny("关键操作不允许由 Agent 执行");
        }
        
        return ToolCallResult.deny("未知错误");
    }
    
    // 风险分级逻辑
    private RiskLevel classifyRisk(String toolName, Map<String, Object> params) {
        // 读操作 = LOW
        if (toolName.startsWith("query_") || toolName.startsWith("get_")) {
            return RiskLevel.LOW;
        }
        // 写操作但可逆 = MEDIUM
        if (toolName.startsWith("create_") || toolName.startsWith("update_")) {
            // 额外检查：如果更新的是权限表 → HIGH
            if (params.containsKey("table") && params.get("table").equals("permissions")) {
                return RiskLevel.HIGH;
            }
            return RiskLevel.MEDIUM;
        }
        // 删除操作 = HIGH（需要确认）
        if (toolName.startsWith("delete_") && isRecoverable(toolName)) {
            return RiskLevel.HIGH;
        }
        // 不可逆的系统操作 = CRITICAL
        return RiskLevel.CRITICAL;
    }
}
```

```java
    }
    
    // 循环检测：连续 5 次调用同一工具且无实质进展
    public boolean detectLoop(String sessionId, String toolName, String resultHash) {
        String key = "agent:session:loop:" + sessionId + ":" + toolName;
        
        // 记录最近的调用结果哈希
        redis.opsForList().leftPush(key, resultHash);
        redis.opsForList().trim(key, 0, 4);  // 只保留最近 5 次
        redis.expire(key, 10, TimeUnit.MINUTES);

        if (recent.size() >= 5 && new HashSet<>(recent).size() == 1) {
            log.warn("会话 {} 检测到工具调用循环: {}", sessionId, toolName);
            return true;  // 循环检测到！
        }
        return false;
    }
```
