## 题目 1：[框架/Spring Boot] 请详细解释 Spring Boot 的自动配置原理，包括 @EnableAutoConfiguration 和 AutoConfigurationImportSelector 的工作机制，以及如何自定义一个 Starter

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-05 午间报告 — "大厂面试高频考点：SpringBoot核心——自动配置原理、Starter机制、启动流程、内嵌容器"
**相关岗位**：Java后端 / 全栈

### 📖 参考答案

#### 一、什么是 Spring Boot 自动配置？

Spring Boot 自动配置（Auto-Configuration）的核心思想是**"约定大于配置"**：根据 classpath 下的依赖、配置文件和当前环境，自动注册合适的 Bean，而无需开发者手动编写 XML 或 @Configuration 类。

```java
@SpringBootApplication  // 等价于 @Configuration + @EnableAutoConfiguration + @ComponentScan
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}
```

#### 二、@EnableAutoConfiguration 的工作原理

`@EnableAutoConfiguration` 是自动配置的"总开关"，其核心通过 `@Import(AutoConfigurationImportSelector.class)` 导入一个 `ImportSelector` 实现类。

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Inherited
@AutoConfigurationPackage          // 注册当前包路径
@Import(AutoConfigurationImportSelector.class)  // 核心：导入选择器
public @interface EnableAutoConfiguration {
    String[] exclude() default {};
    String[] excludeName() default {};
}
```

#### 三、AutoConfigurationImportSelector 的执行流程（面试重点）

```
启动类 @SpringBootApplication
        │
        ▼
@EnableAutoConfiguration → @Import(AutoConfigurationImportSelector.class)
        │
        ▼
selectImports(AnnotationMetadata)
        │
        ▼
getAutoConfigurationEntry() 
        │
        ├── 1. 获取所有候选配置类
        │       └── 加载 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
        │            （Spring Boot 2.7+ 使用此文件，旧版用 spring.factories）
        │
        ├── 2. 按 @Conditional 条件过滤
        │       ├── @ConditionalOnClass       — classpath 中有指定类
        │       ├── @ConditionalOnMissingBean  — 容器中没有指定 Bean
        │       ├── @ConditionalOnProperty     — 配置文件中指定属性
        │       ├── @ConditionalOnWebApplication — 当前是 Web 环境
        │       └── @ConditionalOnExpression   — SpEL 表达式
        │
        └── 3. 返回最终需要加载的配置类列表
                └── Spring 将这些 @Configuration 类解析并注册 Bean
```

**关键文件路径**（Spring Boot 3.x）：

```
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

内容示例：
```
org.springframework.boot.autoconfigure.web.servlet.DispatcherServletAutoConfiguration
org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
org.springframework.boot.autoconfigure.data.redis.RedisAutoConfiguration
...
```

#### 四、如何自定义一个 Starter

自定义 Starter 的核心步骤：

**1. 创建自动配置类：**
```java
@Configuration
@ConditionalOnClass(MyService.class)
@EnableConfigurationProperties(MyProperties.class)
public class MyAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public MyService myService(MyProperties properties) {
        return new MyService(properties);
    }
}
```

**2. 创建属性绑定类：**
```java
@ConfigurationProperties(prefix = "my.service")
public class MyProperties {
    private String host = "localhost";
    private int port = 8080;
    // getters & setters
}
```

**3. 注册自动配置：**
在 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 中添加：
```
com.example.starter.MyAutoConfiguration
```

**4. 打包使用：** 引入 Maven 依赖后，Spring Boot 自动加载。

#### 💡 延伸思考

1. Spring Boot 2.7 之前使用 `spring.factories`，之后改用 `AutoConfiguration.imports` 文件，为什么？—— 为了解耦 spring-core 和自动配置，减少类路径扫描负担。
2. @Conditional 注解家族如何实现"按需加载"？—— 核心是 Condition 接口的 matches() 方法，Spring 在解析配置类时逐条检查。
3. 如何排查自动配置未生效的问题？—— 使用 `--debug` 启动查看 Positive/Negative matches 日志，或通过 `ApplicationContext.getBeanDefinitionNames()` 排查。

## 题目 2：[缓存/Redis] 请详细说明 Redis 分布式锁的实现方案，包括基于 SET 命令的基础方案和 Redlock 算法，并分析各自的优缺点和适用场景

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-05 报告 — "Redis缓存高频考点：分布式锁、集群" 
**相关岗位**：Java后端 / 架构师 / 全栈

### 📖 参考答案

#### 一、分布式锁的核心挑战

分布式锁需要解决四大问题：
1. **原子性**：加锁和设置过期时间必须原子执行
2. **死锁预防**：客户端崩溃后锁能自动释放
3. **锁安全**：只能释放自己持有的锁（通过唯一标识校验）
4. **容错性**：Redis 宕机不影响锁服务整体可用性

#### 二、基于 SET 命令的基础方案（最常用）

```java
public class RedisDistributedLock {

    private final StringRedisTemplate redisTemplate;
    private final String lockKey;
    private final String lockValue;  // UUID + threadId，用于安全释放

    // 加锁：SET key value NX EX timeout
    public boolean tryLock(String key, String value, long timeoutSec) {
        return Boolean.TRUE.equals(
            redisTemplate.opsForValue()
                .setIfAbsent(key, value, timeoutSec, TimeUnit.SECONDS)
        );
        // Redis 命令等价于：SET key value NX EX 30
        // NX = key 不存在才设置，EX = 过期时间（秒）
        // 原子性保证：一条命令完成 SET + EXPIRE
    }

    // 解锁：Lua 脚本保证原子性（先检查再删除）
    public boolean unlock(String key, String value) {
        String luaScript = 
            "if redis.call('get', KEYS[1]) == ARGV[1] " +
            "then return redis.call('del', KEYS[1]) " +
            "else return 0 end";
        Long result = redisTemplate.execute(
            new DefaultRedisScript<>(luaScript, Long.class),
            Collections.singletonList(key),
            value
        );
        return Long.valueOf(1).equals(result);
    }
}
```

**基础方案的优缺点：**

| 方面 | 说明 |
|------|------|
| 优点 | 实现简单、性能极高（单次操作微秒级） |
| 缺点 | 单点故障：Redis 主节点宕机后锁丢失；主从切换时锁状态不一致 |
| 适用 | 业务对一致性要求不高、可接受短暂锁丢失的场景 |

#### 三、Redlock 算法（分布式锁的高级方案）

Redlock 由 Redis 作者 Antirez 提出，**核心思想：在 N 个独立的 Redis 节点上同时加锁，多数成功才算加锁成功**。

**Redlock 加锁流程（N=5 为例）：**

```
客户端
  │
  ├── 1. 获取当前时间戳 T1
  │
  ├── 2. 依次向 5 个 Redis 节点发送 SET key value NX EX ttl
  │       ├── 节点1 ✅ (3ms)
  │       ├── 节点2 ✅ (2ms)
  │       ├── 节点3 ❌ (超时)
  │       ├── 节点4 ✅ (4ms)
  │       └── 节点5 ✅ (2ms)
  │
  ├── 3. 计算耗时 T2 - T1 = 11ms
  │
  ├── 4. 判断：成功数 4/5 ≥ N/2+1=3 ✅
  │        且总耗时 11ms < 锁过期时间 ttl ✅
  │
  └── 5. 加锁成功！锁有效时间 = ttl - 11ms
```

**Redlock 的 Java 实现核心逻辑：**
```java
public boolean tryLock(String key, String value, long ttlMs) {
    int successCount = 0;
    long start = System.currentTimeMillis();
    
    for (RedisClient client : redisNodes) {
        try {
            if (client.set(key, value, ttlMs, TimeUnit.MILLISECONDS)) {
                successCount++;
            }
        } catch (Exception e) {
            // 单个节点超时或不可用，继续尝试下一个
        }
    }
    
    long cost = System.currentTimeMillis() - start;
    
    // 多数节点加锁成功 + 总耗时小于过期时间
    return successCount >= redisNodes.size() / 2 + 1 && cost < ttlMs;
}
```

**Redlock 的争议：**
- Martin Kleppmann（《DDIA》作者）指出 Redlock 存在**时钟漂移问题**和**GC 暂停导致锁过期的安全问题**
- Redis 作者 Antirez 回应认为在合理时钟精度下问题可接受
- **实际生产建议**：大多数场景用基础 SET 方案 + 看门狗（Watch Dog）即可，Redlock 仅在金融级强一致性场景使用

#### 四、生产最佳实践：Redisson 看门狗机制

```java
// Redisson 自动续期（Watch Dog）
RLock lock = redissonClient.getLock("myLock");
lock.lock(30, TimeUnit.SECONDS);  // 默认锁超时 30s
// 看门狗每 10s 检查一次，锁未释放自动续期到 30s
try {
    // 业务逻辑
} finally {
    lock.unlock();
}
```

**看门狗原理**：加锁时启动一个定时任务（每 `lockWatchdogTimeout/3` 执行一次），锁未释放则续期，业务完成后取消定时器。

#### 💡 延伸思考

1. Redis 分布式锁与 ZooKeeper 锁的对比：ZK 通过临时顺序节点实现，强一致性但性能较低；Redis 性能高但一致性和可靠性弱于 ZK。
2. 如果 Redis 主节点加锁后异步复制到从节点之前主节点宕机，新主节点没有锁数据怎么办？—— Redlock 的多节点方案可以缓解，或使用 ZK/etcd 的共识协议保障。

## 题目 3：[数据库/MySQL] 请详细说明 MySQL InnoDB 为什么选择 B+ 树作为索引结构，并解释聚簇索引与二级索引的区别、回表查询和覆盖索引的概念

**难度**：⭐⭐⭐
**考点来源**：2026-07-05 报告 — "快手笔试覆盖数据库、数据结构与算法" + "大厂面试高频考点"
**相关岗位**：Java后端 / Python后端 / 全栈

### 📖 参考答案

#### 一、InnoDB 为什么选择 B+ 树？（面试高频）

数据库索引的核心需求：**在少量磁盘 IO 内完成数据查找**。

| 数据结构 | 为什么不选 |
|---------|-----------|
| 二叉树 | 有序数据退化为链表，O(n) 查询，百万数据需要 ~20 次 IO |
| 红黑树 | 平衡二叉树，但高度深（百万级数据 ~20 层），IO 次数多 |
| 哈希表 | 仅支持等值查询，不支持范围查询和排序 |
| B 树 | 非叶子节点也存数据，节点容量小，树更高；范围查询需回溯 |
| **B+ 树 ✅** | **仅叶子节点存数据，非叶子节点只存键 → 节点容量大 → 树低（百万级 3~4 层）；叶子节点链表 → 范围查询极快** |

**B+ 树的核心优势：**

```
B+ 树结构示意（简化的 3 层 B+ 树）：
        
         ┌─────── [50, 100] ───────┐         ← 非叶子节点（只存键，不存数据）
         │                          │
    ┌───[10,30,50]───┐       ┌──[70,90,100]───┐
    │                 │       │                │
  [1,5,10]─→[15,20,30]─→[40,45,50]─→[60,70]─→[80,90]   ← 叶子节点（存数据，双向链表）
   ↑                                                      ↑
   范围查询 1~100，找到 1 后顺序遍历即可，无需回溯           ← 范围查询极快
```

1. **树高度极低**：InnoDB 页大小 16KB，非叶子节点每个 key 约 8~16B，一个节点可存 ~1000 个 key，3 层 B+ 树可存储约 **10 亿条**数据，查询仅需 3~4 次磁盘 IO
2. **范围查询高效**：叶子节点通过双向链表连接，范围查询只需找到起始位置后顺序扫描
3. **查询效率稳定**：所有查询都必须走到叶子节点，时间复杂度始终为 O(log n)

#### 二、聚簇索引（Clustered Index）vs 二级索引（Secondary Index）

**聚簇索引：**
- **数据即索引，索引即数据**：叶子节点直接存储整行数据
- 每个 InnoDB 表**只有一个**聚簇索引
- 主键即聚簇索引；未定义主键时，MySQL 选择第一个唯一非空索引；都没有则自动生成 6 字节的 rowid

**二级索引（辅助索引/非聚簇索引）：**
- 叶子节点存储的是**主键值**，而非整行数据
- 通过二级索引查数据需要**两次查找**：先找到主键值，再回聚簇索引查完整行

```
聚簇索引（主键 id）              二级索引（name）
┌─────────────┐                ┌─────────────┐
│ id=1 │ 行A  │                │ Alice │ 1   │
│ id=2 │ 行B  │                │ Bob   │ 3   │
│ id=3 │ 行C  │     ←存储主键→ │ Carol │ 2   │
│ id=4 │ 行D  │                └─────────────┘
│ id=5 │ 行E  │                     │
└─────────────┘                     ▼
                             需要回表查询
                           SELECT * FROM t WHERE name='Alice';
                           步骤：1. 二级索引找到主键 1
                           步骤：2. 回聚簇索引查完整行
```

#### 三、回表查询 vs 覆盖索引

**回表查询**：通过二级索引查到主键值后，再回到聚簇索引查完整数据的过程。

**覆盖索引**：如果查询所需的列都在二级索引中，则无需回表，直接返回。

```sql
-- 假设有联合索引 (city, age)
-- 回表查询：需要 select * 中的其他列
SELECT * FROM user WHERE city = '北京';  -- 需要回表

-- 覆盖索引：查询列都在索引中
SELECT city, age FROM user WHERE city = '北京';  -- 无需回表
```

**覆盖索引的优化价值：** 减少磁盘 IO 约 30%~50%，是 MySQL 索引优化的核心手段。

#### 💡 延伸思考

1. 为什么 InnoDB 推荐使用自增主键？—— 自增主键插入时 B+ 树只在右侧新增，减少页分裂；UUID 主键插入随机，导致频繁页分裂和碎片。
2. 最左前缀原则是什么？—— 联合索引 (a, b, c)，查询条件必须从 a 开始，跳过 a 查 b 会导致索引失效。
3. 索引下推（ICP, Index Condition Pushdown）如何优化？—— MySQL 5.6+ 在存储引擎层直接过滤索引记录，减少回表次数。

## 题目 4：[Java并发/JUC] 请详细说明 AbstractQueuedSynchronizer（AQS）的核心原理，包括 state 状态管理、CLH 变种等待队列、独占/共享模式，以及 ReentrantLock 如何基于 AQS 实现可重入锁

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-05 报告 — "Java并发编程高频考点：线程生命周期、锁升级、CAS、线程池原理、JUC工具"
**相关岗位**：Java后端 / 基础架构

### 📖 参考答案

#### 一、AQS 的核心定位

AQS（AbstractQueuedSynchronizer）是 Java 并发包（JUC）的**基石**——ReentrantLock、CountDownLatch、Semaphore、CyclicBarrier 等全部基于 AQS 实现。理解 AQS = 掌握 JUC 同步工具的底层逻辑。

```
          ┌─────────────────────────┐
          │  AbstractQueuedSynchronizer │
          │  (JUC 同步器骨架)          │
          └──────────┬──────────────┘
                     │ 基于 AQS 实现
     ┌────────┬──────┼──────┬──────────┐
     ▼        ▼      ▼      ▼          ▼
ReentrantLock CountDownLatch Semaphore ThreadPoolExecutor (Worker)
```

#### 二、AQS 的三大核心设计

**1. 状态中心化 — volatile int state**

```java
// AQS 核心状态变量
private volatile int state;

// 三种访问方式
protected final int getState();
protected final void setState(int newState);
protected final boolean compareAndSetState(int expect, int update);  // CAS 更新
```

- **ReentrantLock 中**：state = 0 表示未锁定，state = 1 表示已锁定，state = N 表示重入 N 次
- **Semaphore 中**：state 表示剩余许可数
- **CountDownLatch 中**：state 表示待计数

**2. 队列规范化 — CLH 变种双向链表**

```java
static final class Node {
    volatile int waitStatus;     // 节点状态：0/CANCELLED(1)/SIGNAL(-1)/CONDITION(-2)/PROPAGATE(-3)
    volatile Node prev;          // 前驱节点
    volatile Node next;          // 后继节点
    volatile Thread thread;      // 当前等待线程
    Node nextWaiter;             // 标记独占/共享模式，或指向条件队列下一节点
}
```

**CLH 队列的 FIFO 特性：**
- 新节点通过 CAS 插入队尾（`compareAndSetTail`）
- 只有**头节点**（head）的线程可以尝试获取锁
- 线程通过 `LockSupport.park()/unpark()` 阻塞和唤醒

**3. 模板方法模式**

AQS 定义了通用的获取/释放模板，子类只需重写特定方法：

| 模板方法 | 子类需重写的方法 | 功能 |
|---------|-----------------|------|
| `acquire(int arg)` | `tryAcquire(int)` | 独占式获取 |
| `acquireShared(int arg)` | `tryAcquireShared(int)` | 共享式获取 |
| `release(int arg)` | `tryRelease(int)` | 独占式释放 |
| `releaseShared(int arg)` | `tryReleaseShared(int)` | 共享式释放 |

#### 三、独占模式获取锁的完整流程（以 ReentrantLock 为例）

```
线程调用 lock()
    │
    ▼
tryAcquire(1)  ← ReentrantLock 的 FairSync/NonfairSync 实现
    │
    ├── state == 0 → CAS 尝试获取锁 → 成功 ✅
    │
    ├── 当前线程已持有锁 → state + 1（重入） ✅
    │
    └── 失败 ❌ → 进入 acquireQueued()
                        │
                        ▼
                addWaiter(Node.EXCLUSIVE)
                        │
                        ▼
                将当前线程包装为 Node 插入 CLH 队尾
                        │
                        ▼
                acquireQueued(final Node node, int arg)
                        │
                        ├── 前驱是 head → 再次 tryAcquire → 成功则设为新 head
                        │
                        └── 前驱不是 head 或 tryAcquire 失败
                                │
                                ▼
                        shouldParkAfterFailedAcquire()
                        (将前驱 waitStatus 设为 SIGNAL)
                                │
                                ▼
                        LockSupport.park() 阻塞
                                │
                                ▼
                        被 unpark() 唤醒 → 重试
```

#### 四、ReentrantLock 的可重入实现

```java
// NonfairSync 的 tryAcquire 简化逻辑
protected final boolean tryAcquire(int acquires) {
    final Thread current = Thread.currentThread();
    int c = getState();
    if (c == 0) {
        // 非公平锁：直接 CAS 尝试（插队）
        if (compareAndSetState(0, acquires)) {
            setExclusiveOwnerThread(current);
            return true;
        }
    } else if (current == getExclusiveOwnerThread()) {
        // 重入：state + 1
        int nextc = c + acquires;
        if (nextc < 0) throw new Error("Maximum lock count exceeded");
        setState(nextc);
        return true;
    }
    return false;
}
```

**公平锁 vs 非公平锁**：
- **非公平锁**（默认）：tryAcquire 时直接 CAS 抢锁，抢不到才排队 → 吞吐量更高，可能导致线程饥饿
- **公平锁**：tryAcquire 检查队列中是否有等待者，有则直接排队 → 公平但吞吐量低

#### 💡 延伸思考

1. AQS 的 ConditionObject 是如何实现 `await()/signal()` 的？—— 每个 Condition 维护一个单独的条件队列，`await()` 时将线程从 CLH 队列移到条件队列并释放锁，`signal()` 时移回 CLH 队列。
2. AQS 的共享模式和独占模式有什么区别？—— 独占模式（如 ReentrantLock）一次只允许一个线程持有；共享模式（如 CountDownLatch/Semaphore）多个线程可以同时获取。

#### 一、LangGraph 是什么？

LangGraph 是 LangChain 团队开发的 **Agent 编排框架**，它将 Agent 的运行过程建模为**有向图（Directed Graph）**。LangChain 提供工具、模型、链等组件；LangGraph 负责**控制流编排**——两者是互补关系。

**为什么需要 LangGraph？**

传统 LLM 调用是线性 Chain（A→B→C），但真实 Agent 场景需要**条件分支、循环、并行执行**等复杂控制流，LangGraph 通过图结构天然支持这些需求。

#### 二、LangGraph 的三大核心概念

| 概念 | 说明 | 类比 |
|------|------|------|
| **State** | 贯穿全图的共享数据结构，用 TypedDict 定义，所有节点读写同一份 State | 类似 HTTP Session |
| **Node** | 图中的计算单元，是一个函数，接收 State 返回更新的字段（diff） | 类似 React 组件 |
| **Edge** | 节点间的连接，分固定边和条件边 | 类似路由 |

**1. State — 状态管理**
```python
from typing import TypedDict, Annotated, Sequence
from langgraph.graph import add_messages

class AgentState(TypedDict):
    messages: Annotated[Sequence, add_messages]  # 聊天历史（自动合并）
    next_action: str                              # 下一步动作
    tool_results: list                            # 工具调用结果
```

**2. Node — 节点函数**
```python

    """调用 LLM 生成回复"""
    response = llm.invoke(state["messages"])
    return {"messages": [response], "next_action": "decide"}
```

**3. Edge — 边与条件路由**
```python
def router(state: AgentState) -> str:
    """条件边：根据消息内容决定下一步"""
    last_msg = state["messages"][-1]
    if last_msg.tool_calls:
        return "tools"       # 有工具调用 → 执行工具
    elif state.get("task_complete"):
        return "end"         # 任务完成 → 结束
    else:
        return "continue"    # 继续对话
```

```python
    router,

)
```

#### 四、工具调用（Tool Calling）的设计

```python
from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """查询指定城市的天气"""
    # 调用天气 API
    return f"{city} 今天晴转多云，25~30°C"

@tool
def send_email(to: str, content: str) -> str:
    """发送邮件"""
    # 调用邮件服务

# 将工具绑定到 LLM
llm_with_tools = llm.bind_tools([get_weather, send_email])
```

**关键机制：**
1. LLM 输出结构化 tool_calls（函数名 + 参数 JSON）
2. LangGraph 将 tool_calls 路由到对应工具函数
3. 工具执行结果返回给 LLM 进行下一步决策
4. 循环直到 LLM 不再调用工具（ReAct 范式）
