**考点来源**：2026-07-16 早间日报 — "Spring Cloud 微服务仍是高频考点，但更关注'模块化单体'回归，DDD 成为核心考察点"
**相关岗位**：Java后端 / 全栈 / 架构师

### 📖 参考答案

#### 一、模块化单体回归的背景：为什么 2026 年面试官在聊"别拆太碎"？

2026 年的面试趋势出现了一个看似"倒退"的变化：面试官开始追问**模块化单体（Modular Monolith）**。这不是技术倒退，而是对过去十年"盲目微服务化"的反思。

```
微服务拆分的代价（中小团队的切肤之痛）：

| 问题 | 描述 | 影响 |
|------|------|------|
| 运维爆炸 | 10 个服务 → 10 个部署单元、10 个 CI/CD 流水线 | 小团队根本管不过来 |
| 分布式复杂性 | 服务间调用从方法调用变成 RPC/HTTP | 延迟增加、调试困难、事务问题 |
| 数据一致性 | 每个服务独立数据库 → 分布式事务难题 | 最终一致性+补偿逻辑复杂度飙升 |
| 团队效率 | 一个简单功能需要跨 3-5 个服务修改 | 开发效率下降 50%+ |
| 重构成本 | 拆分后不敢合并（政治+技术双重阻力） | 架构僵化 |

一句话总结：微服务解决的是"组织规模问题"，不是"技术问题"。
10 人以下的后端团队拆微服务，大概率弊大于利。
```

**"模块化单体"的定义：**

```
模块化单体 = 单体部署 + 模块化设计

            物理上是一个部署单元（一个 JAR/WAR）
            逻辑上按 DDD 限界上下文拆分为独立模块
            模块间通过接口（非 RPC）通信
            每个模块有自己的数据库表（逻辑隔离）
            未来可平滑拆分为独立微服务

优点：
  ✅ 运维简单（1 个应用，1 条流水线）
  ✅ 开发效率高（一次修改一个模块）
  ✅ 调用成本低（方法调用，非 RPC）
  ✅ 数据一致性好（同一个数据库事务）
  ✅ 可平滑演进（模块边界清晰，拆分不难）
```

#### 二、DDD（领域驱动设计）核心概念

DDD 由 Eric Evans 在其著作《Domain-Driven Design》中提出，核心思想是**让软件模型反映业务领域模型**。

**战略设计（Strategic Design）—— 划分业务边界：**

```
限界上下文（Bounded Context）：
  每个限界上下文是一个独立的业务领域边界
  内部有统一的领域语言（Ubiquitous Language）
  上下文之间通过上下文映射（Context Map）交互

电商系统的限界上下文划分示例：

┌─────────────────────┐     ┌─────────────────────┐
│   商品上下文          │     │   订单上下文          │
│  ProductContext      │     │  OrderContext        │
│                     │     │                     │
│  Product（聚合根）    │────→│  Order（聚合根）      │
│  Category           │     │  OrderItem          │
│  Inventory          │     │  Payment            │
└─────────────────────┘     └─────────────────────┘
         │                           │
         ▼                           ▼
┌─────────────────────┐     ┌─────────────────────┐
│   用户上下文          │     │   物流上下文          │
│  UserContext        │     │  LogisticsContext   │
│  User（聚合根）       │     │  Shipment（聚合根）   │
│  Address            │     │  Tracking           │
└─────────────────────┘     └─────────────────────┘
```

**战术设计（Tactical Design）—— 实现领域模型：**

| 概念 | 说明 | 特征 | 示例 |
|------|------|------|------|
| **实体（Entity）** | 有唯一标识，可变 | 有 ID，equals 按 ID 比较 | `User(id, name, email)` |
| **值对象（Value Object）** | 无标识，不可变，描述性 | 无 ID，equals 按属性比较 | `Address(city, street, zip)` |
| **聚合（Aggregate）** | 实体+值对象的组合，一致性边界 | 有聚合根（Aggregate Root），外部只能通过聚合根访问 | `Order`（聚合根）→ `OrderItem`、`Payment` |
| **领域事件（Domain Event）** | 领域中发生的重要事情 | 不可变，用过去时命名 | `OrderCreatedEvent` |
| **仓库（Repository）** | 聚合的持久化存储 | 每个聚合一个 Repository | `OrderRepository` |
| **领域服务（Domain Service）** | 无状态，处理跨聚合的业务逻辑 | 方法名反映业务能力 | `PaymentService.pay()` |

```java
// 战术设计代码示例

// 值对象（Value Object）—— 不可变
@Value
public class Address {
    String province;
    String city;
    String street;
    String zipCode;
}

// 实体（Entity）—— 有唯一标识
@Entity
@Table(name = "orders")
public class Order {
    @Id
    private OrderId orderId;    // 值对象作为 ID
    
    private UserId userId;      // 其他聚合的 ID 引用
    private Money totalAmount;  // 值对象
    
    @OneToMany(cascade = ALL)
    private List<OrderItem> items;  // 聚合内部实体
    
    private OrderStatus status;  // 值对象（枚举）
    
    // 行为封装在实体内部（不是贫血模型！）
    public void addItem(Product product, int quantity) {
        // 业务规则：同一商品不能重复添加
        if (items.stream().anyMatch(i -> i.getProductId().equals(product.getId()))) {
            throw new BusinessException("商品已在订单中");
        }
        items.add(new OrderItem(product, quantity));
        recalculateTotal();  // 重新计算总价
    }
    
    public void pay(PaymentMethod method) {
        if (status != OrderStatus.PENDING) {
            throw new BusinessException("订单状态不正确");
        }
        this.status = OrderStatus.PAID;
        // 注册领域事件
        registerEvent(new OrderPaidEvent(this.orderId, this.totalAmount));
    }
}

// 聚合根（Aggregate Root）—— 外部只能通过聚合根操作内部
// Order 是聚合根，OrderItem 只能通过 Order 访问
```

**贫血模型 vs 充血模型：**

```java
// ❌ 贫血模型（Anti-Pattern）—— 只有数据，没有行为
// 很多 Spring Boot 项目的"标准"写法，其实是反 DDD 的
@Entity
public class Order {
    private Long id;
    private BigDecimal amount;
    private String status;
    
    // 只有 getter/setter，没有业务行为
    public void setStatus(String status) { this.status = status; }
}

@Service
public class OrderService {
    @Transactional
    public void pay(Long orderId) {
        Order order = orderRepo.findById(orderId);
        order.setStatus("PAID");  // 业务逻辑在 Service 中
        orderRepo.save(order);
    }
}

// ✅ 充血模型（DDD 推荐）—— 行为在实体中
@Entity
public class Order {
    @Id private OrderId id;
    private Money amount;
    private OrderStatus status;
    
    // 业务行为封装在实体中
    public void pay(PaymentMethod method) {
        if (!this.status.canPay()) {
            throw new IllegalStateException("订单不能支付");
        }
        this.status = OrderStatus.PAID;
        this.paidAt = LocalDateTime.now();
    }
}

@Service
public class OrderApplicationService {
    @Transactional
    public void payOrder(PayOrderCommand cmd) {
        Order order = orderRepo.findById(cmd.getOrderId());
        order.pay(cmd.getMethod());  // 调用实体的业务方法
        // 领域事件由实体发出，Application Service 处理
        order.getEvents().forEach(eventBus::publish);
    }
}
```

**模块间通信原则：**

```
模块间通信规则（严格分层）：

同一模块内：      方法调用（直接依赖接口）
不同模块间：      通过 Application Service 接口
                或领域事件（异步解耦）
不允许：         跨模块直接访问 Repository 或 Entity

例子：订单模块需要用户信息
  ❌ 直接调用 userRepo.findById()
  ✅ 调用 UserApplicationService.getUserInfo()
  ✅ 监听 UserUpdatedEvent 同步本地缓存
```

#### 四、什么时候用模块化单体？什么时候用微服务？

```
选型决策树：

团队规模 < 15 人，或业务复杂度中等？
  ├── 是 → 模块化单体 ✅
  │       优点：开发快、运维简单、事务好做
  │       缺点：技术栈绑定、不能独立扩缩
  │
  └── 否 → 微服务 ✅
          优点：独立部署、独立扩缩、技术栈灵活
          缺点：运维复杂、分布式事务、调试困难

DDD 的核心价值：
  无论选模块化单体还是微服务，DDD 的限界上下文
  都是划分模块/服务边界的最佳方法。
  
  先 DDD 划分边界 → 小团队用模块化单体实现
                     大团队将每个限界上下文拆为独立服务
```

### 💡 延伸思考
1. **DDD 的"共享内核"（Shared Kernel）和"防腐层"（Anti-Corruption Layer）分别解决什么问题？** — 共享内核用于两个紧密耦合的限界上下文共享通用概念（如 Money、Address），防腐层用于隔离外部系统（如第三方 API）的模型污染，通过适配器模式将外部模型转换为内部领域模型。
2. **事件风暴（Event Storming）工作坊如何帮助发现限界上下文？** — 通过业务专家和技术人员一起在墙上贴便利贴的方式，按时间线梳理业务流程中的领域事件，自然涌现出聚合和限界上下文边界，是 DDD 落地最实用的启动方法。

**3. RAG 检索增强生成：**

```java
// 构建 RAG 应用
public class KnowledgeBaseChat {
    
    private final ChatLanguageModel model;
    private final EmbeddingStore<TextSegment> embeddingStore;
    private final EmbeddingModel embeddingModel;
    
    public KnowledgeBaseChat() {
        this.model = DeepSeekChatModel.builder()
            .apiKey(System.getenv("DEEPSEEK_API_KEY"))
            .build();
        this.embeddingModel = new OpenAiEmbeddingModel(
            System.getenv("OPENAI_API_KEY")
        );
        this.embeddingStore = new InMemoryEmbeddingStore<>();
    }
    
    // 导入文档
    public void ingest(List<String> documents) {
        for (String doc : documents) {
            // 1. 文档切片
            DocumentSplitter splitter = DocumentSplitters.recursive(500, 50);
            List<TextSegment> segments = splitter.split(
                TextSegment.from(doc)
            );
            
            // 2. 向量化并存储
            List<Embedding> embeddings = embeddingModel.embedAll(segments).content();
            embeddingStore.addAll(embeddings, segments);
        }
    }
    
    // 问答
    public String answer(String question) {
        // 1. 向量化问题
        Embedding questionEmbedding = embeddingModel.embed(question).content();
        
        // 2. 检索相关文档
        List<EmbeddingMatch<TextSegment>> relevant = embeddingStore
            .findRelevant(questionEmbedding, 3);  // Top-3
        
        // 3. 构建上下文
        String context = relevant.stream()
            .map(m -> m.embedded().text())
            .collect(Collectors.joining("\n---\n"));
        
        // 4. 生成回答
        return model.generate(
            SystemMessage.from("你是一个知识库助手，基于以下文档回答问题：\n" + context),
            UserMessage.from(question)
        );
    }
}
```

#### 三、LangGraph4j：复杂工作流编排

LangGraph4j 是 LangChain4j 的"升级版"，专门解决**有状态、多步骤、多 Agent** 的复杂场景。

**核心三要素：**

```
LangGraph4j 三要素（面试必问）：

1. StateGraph（状态图）
   → 工作流的"总图"
   → 注册节点（Node）、连线（Edge）
   → 编译后自动校验图结构

2. AgentState（状态容器）
   → 节点间共享的可变状态
   → 类似 React 的状态管理
   → 不可变更新保证数据不污染

3. Edge（边）
   → 普通边：顺序执行（Node A → Node B）
   → 条件边：根据条件动态路由（核心！）
   → 实现循环、动态路由，支撑 ReAct 智能体模式
```

```java
    @Override
    public AgentState apply(AgentState state) {
        Response<AiMessage> response = model.generate(
            state.getMessages(), 
            tools
        );
        
        List<ChatMessage> newMessages = new ArrayList<>(state.getMessages());
        newMessages.add(response.content());
        
        return new AgentState(newMessages, state.getMetadata());
    }
}

// 3. 构建工作流图
public class ReActAgent {
    
    public StateGraph<AgentState> buildGraph() {
        StateGraph<AgentState> graph = new StateGraph<>(AgentState::new);
        
        // 注册节点
        graph.addNode("agent", new AgentNode(model, tools));
        graph.addNode("action", new ActionNode());
        
        // 条件边：根据 AI 输出决定走工具调用还是结束
        graph.addConditionalEdge(
            "agent",
            state -> {
                AiMessage lastMessage = (AiMessage) state.getLastMessage();
                if (lastMessage.hasToolExecutionRequests()) {
                    return "action";  // 需要调用工具
                }
                return "__end__";     // 直接结束
            },
            Map.of("action", "action", "__end__", StateGraph.END)
        );
        
        // 工具执行后回到 agent 节点继续推理
        graph.addEdge("action", "agent");
        
        // 编译图
        return graph.compile();
    }
    
    public String execute(String userInput) {
        StateGraph<AgentState> graph = buildGraph();
        
        AgentState initialState = new AgentState(
            List.of(UserMessage.from(userInput)),
            new HashMap<>()
        );
        
        AgentState finalState = graph.run(initialState);
        return finalState.getLastMessage().text();
    }
}
```

#### 一、LRU 缓存的核心原理

LRU（Least Recently Used，最近最少使用）是一种缓存淘汰策略：**当缓存满时，淘汰最久未使用的数据**。

```
LRU 缓存的工作逻辑：

假设缓存容量 = 3，访问序列：A → B → C → D → A → E

初始状态：空
访问 A：  [A]                    ✅ 缓存未满，直接添加
访问 B：  [B → A]               ✅ 缓存未满，直接添加（最近使用的在最前面）
访问 C：  [C → B → A]           ✅ 缓存未满，直接添加
访问 D：  [D → C → B]           ⚠️ 缓存已满，淘汰 A（最久未使用）
访问 A：  [A → D → C]           ✅ A 已存在，移到最前面（标记为最近使用）
访问 E：  [E → A → D]           ⚠️ 缓存已满，淘汰 C（最久未使用）

核心操作：
  ① get(key)：如果存在，将节点移到链表头部（标记为最近使用）
  ② put(key, value)：如果存在，更新值并移到头部；
                      如果不存在，插入头部；如果超容量，删除尾部节点
```

**为什么用 LRU 而不是其他策略？**

```
| 策略 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| FIFO | 先进先出 | 简单 | 可能淘汰热点数据（刚放入就被淘汰） |
| LRU | 最近最少使用 | 命中率高，符合局部性原理 | 实现略复杂 |
| LFU | 最不经常使用 | 命中率更高（考虑频率） | 实现复杂，内存开销大 |
| 随机 | 随机淘汰 | 最简单 | 命中率低 |

LRU 是"性价比最高的选择"：实现复杂度可控，命中率满足大多数场景。
```

#### 二、Java 实现方案一：LinkedHashMap（生产推荐）

```java
// 方案一：继承 LinkedHashMap（最简洁）
// LinkedHashMap 默认维护插入顺序
// 设置 accessOrder=true 后，维护访问顺序（每次 get 把节点移到尾部）

public class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    
    public LRUCache(int capacity) {
        // accessOrder=true：按访问顺序排序
        // loadFactor=0.75f：默认加载因子
        super(capacity, 0.75f, true);
        this.capacity = capacity;
    }
    
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        // 当缓存大小超过容量时，删除最老的条目（即最少使用的）
        return size() > capacity;
    }
    
    public static void main(String[] args) {
        LRUCache<Integer, String> cache = new LRUCache<>(3);
        
        cache.put(1, "A");
        cache.put(2, "B");
        cache.put(3, "C");
        System.out.println(cache);  // {1=A, 2=B, 3=C}
        
        cache.get(1);  // 访问 1 → 1 被移到尾部（最近使用）
        System.out.println(cache);  // {2=B, 3=C, 1=A}
        
        cache.put(4, "D");  // 超过容量，淘汰 2（头部，最久未使用）
        System.out.println(cache);  // {3=C, 1=A, 4=D}
    }
}

// 使用：
// LRUCache<Integer, String> cache = new LRUCache<>(1000);
```

#### 三、Java 实现方案二：手写 HashMap + 双向链表（面试推荐）

面试官通常会加限制条件："不能用 LinkedHashMap，手写实现。"

```java
public class LRUCacheManual<K, V> {
    
    // 双向链表节点
    private static class Node<K, V> {
        K key;
        V value;
        Node<K, V> prev;
        Node<K, V> next;
        
        Node(K key, V value) {
            this.key = key;
            this.value = value;
        }
    }
    
    private final int capacity;
    private final Map<K, Node<K, V>> map;      // O(1) 查找
    private final Node<K, V> head;              // 虚拟头节点（最近使用）
    private final Node<K, V> tail;              // 虚拟尾节点（最久未使用）
    
    public LRUCacheManual(int capacity) {
        this.capacity = capacity;
        this.map = new HashMap<>(capacity);
        
        // 初始化虚拟头尾节点
        this.head = new Node<>(null, null);
        this.tail = new Node<>(null, null);
        head.next = tail;
        tail.prev = head;
    }
    
    // get：存在则移到头部，返回 value
    public V get(K key) {
        Node<K, V> node = map.get(key);
        if (node == null) {
            return null;
        }
        // 将节点移到头部（标记为最近使用）
        moveToHead(node);
        return node.value;
    }
    
    // put：存在则更新并移到头部；不存在则插入头部
    public void put(K key, V value) {
        Node<K, V> node = map.get(key);
        
        if (node != null) {
            // 更新已存在的节点
            node.value = value;
            moveToHead(node);
        } else {
            // 创建新节点
            Node<K, V> newNode = new Node<>(key, value);
            map.put(key, newNode);
            addToHead(newNode);
            
            // 超出容量，淘汰尾部节点
            if (map.size() > capacity) {
                Node<K, V> tailNode = removeTail();
                map.remove(tailNode.key);  // 同时从 map 中删除
            }
        }
    }
    
    // 将节点移到头部
    private void moveToHead(Node<K, V> node) {
        removeNode(node);   // 从当前位置移除
        addToHead(node);    // 添加到头部
    }
    
    // 在头部添加节点
    private void addToHead(Node<K, V> node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }
    
    // 移除节点
    private void removeNode(Node<K, V> node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }
    
    // 移除尾部节点（最久未使用）
    private Node<K, V> removeTail() {
        Node<K, V> node = tail.prev;
        removeNode(node);
        return node;
    }
    
    // 测试
    public static void main(String[] args) {
        LRUCacheManual<Integer, String> cache = new LRUCacheManual<>(3);
        
        cache.put(1, "A");
        cache.put(2, "B");
        cache.put(3, "C");
        // 状态：head ↔ 3 ↔ 2 ↔ 1 ↔ tail
        
        cache.get(1);  // 访问 1
        // 状态：head ↔ 1 ↔ 3 ↔ 2 ↔ tail
        
        cache.put(4, "D");
        // 状态：head ↔ 4 ↔ 1 ↔ 3 ↔ tail（淘汰了 2）
        
        System.out.println(cache.get(2));  // null（已被淘汰）
        System.out.println(cache.get(1));  // "A"
        System.out.println(cache.get(4));  // "D"
    }
}
```

```
"LRU 缓存的核心是 HashMap + 双向链表。

HashMap 提供 O(1) 的查找能力，
双向链表提供 O(1) 的节点移动和删除能力。

三个核心操作：
1. get(key)：从 HashMap 找到节点，移到链表头部
```

```java
            this.summary = newSummary;
        } else {
            this.summary = model.generate(
                "合并以下两段用户摘要：\n旧摘要：" + summary + "\n新信息：" + newSummary
            );
        }
    }
    
    public String getSummary() {
        return summary;
    }
}

// 3. 实体记忆：从对话中提取结构化信息
public class EntityMemory {
    private final Map<String, Map<String, String>> entities = new HashMap<>();
    
    public void extract(String userMessage, String aiResponse) {

        // → 提取 {order_id: "ORD001", user_intent: "查询订单"}

            .map(e -> e.getKey() + ": " + e.getValue())
            .collect(Collectors.joining("\n"));
```

**Token 优化：为什么大模型倾向于增大上下文窗口而不是压缩？**

```
面试追问："为什么现在大模型普遍选择增大上下文窗口，而不是做压缩？"

大模型厂商选择 128K/1M 超大上下文窗口而非压缩的原因：

1. 技术可行性：
   - Flash Attention + PagedAttention 等优化使长上下文推理
     的计算成本大幅下降（从 O(n²) 降到接近 O(n)）
   - 硬件（H100/B200）的显存和带宽在快速提升

2. 用户体验：
   - 压缩有信息损失（用户不知道丢了什么）
   - 大窗口是"无损"的，用户所有输入都在
   - 压缩后的推理质量下降（"检索式"压缩会丢失细节）

3. 工程简化：
   - 压缩需要额外的模型/规则（增加复杂度）
   - 大窗口是"暴力但简单"的方案

但超大窗口也有问题：
  - "大海捞针"效应：相关信息淹没在大量无关文本中
  - 推理成本仍随长度线性增长
  - 所以 RAG 仍然是企业级应用的首选方案
```

#### 三、工具调用（Tool Calling / Function Calling）

工具是 Agent 与外部世界交互的接口。

```
工具调用的完整流程（ReAct 模式）：

用户："帮我查订单 ORD001 的状态"
       │
       ▼
① Agent 接收请求，LLM 推理
   → "用户想查询订单状态，我需要调用 queryOrder 工具"
       │
       ▼
② Agent 生成 ToolExecutionRequest
   → tool: "queryOrder"
   → args: {"orderId": "ORD001"}
       │
       ▼
③ 宿主程序执行工具
   → orderService.query("ORD001")
   → 返回 "已发货，预计明天到达"
       │
       ▼
④ 将工具结果返回给 LLM
   → "工具返回：订单状态为已发货，预计明天到达"
       │
       ▼
⑤ LLM 基于工具结果生成最终回答
   → "您的订单 ORD001 已发货，预计明天到达。"
       │
       ▼
⑥ 如果还需要其他工具，重复 ②-⑤（ReAct 循环）
```

**工具设计原则：**

```
| 原则 | 说明 | 反例 | 正例 |
|------|------|------|------|
| 单一职责 | 一个工具只做一件事 | queryAndUpdateOrder() | queryOrder(), updateOrder() |
| 明确描述 | 描述告诉 AI 何时调用 | "查询" | "根据订单号查询订单当前状态和物流信息" |
| 参数清晰 | 参数名和描述让 AI 理解 | String id | @P("订单号，格式 ORD...") |
| 幂等设计 | 重复执行结果一致 | cancelOrder()（不可逆） | queryOrder()（天然幂等） |
| 错误处理 | 工具失败要返回明确错误 | throw Exception | 返回 "查询失败：订单号不存在" |
```

**生产级工具调用注意事项：**

```java
// 安全边界设计（重要！）
public class AgentSecurityGuard {
    
    // 原则：大模型只生成参数，不执行操作
    // 所有工具调用必须经过权限校验
    
    public ToolResult executeWithGuard(ToolExecutionRequest request, UserContext user) {
        // 1. 权限校验：用户是否有权调用此工具
        if (!hasPermission(user, request.toolName())) {
            return ToolResult.error("无权限执行此操作");
        }
        
        // 2. 参数白名单校验（防止注入）
        if (!validateParams(request)) {
            return ToolResult.error("参数校验失败");
        }
        
        // 3. 敏感操作需要用户确认
        if (isSensitiveOperation(request.toolName())) {
            return ToolResult.requireConfirmation(
                "请确认执行: " + request.toolName() 
                + " 参数: " + request.args()
            );
        }
        
        // 4. 执行工具
        return executeTool(request);
    }
    
    // 写操作（修改数据）→ 必须确认
    // 读操作（查询数据）→ 可直接执行
    private boolean isSensitiveOperation(String toolName) {
        return toolName.startsWith("delete") 
            || toolName.startsWith("cancel")
            || toolName.startsWith("update");
    }
}
```

#### 四、多 Agent 协作模式

小红书面经中提到"单 Agent 还是多 Agent"以及"主 Agent 和子 Agent 信息交互"是核心考点。

**三种主流多 Agent 协作模式：**

```
模式 1：主管-员工模式（Orchestrator-Worker）
  ┌──────────┐
  │  主管 Agent │  负责理解用户意图，拆解任务，分配子任务
  └─────┬─────┘
        │
  ┌─────┼─────┬──────┐
  │     │     │      │
  ▼     ▼     ▼      ▼
┌────┐ ┌────┐ ┌────┐ ┌────┐
│搜索 │ │分析 │ │代码 │ │写作 │
│Agent│ │Agent│ │Agent│ │Agent│
└────┘ └────┘ └────┘ └────┘

  主管 Agent 负责：
  - 子 Agent 的创建和调度
  - 感知子 Agent 的成功/失败/超时/重试
  - 汇总子 Agent 结果
  - 子 Agent 只返回"结果"，不感知其他 Agent 的存在

模式 2：协商模式（Debate/Collaboration）
  ┌──────┐    ┌──────┐
  │Agent A│◄──►│Agent B│
  └──┬───┘    └──┬───┘
     │           │
     └─────┬─────┘
           │
      ┌────▼────┐
      │ 仲裁者   │
      │ Agent C │
      └─────────┘

  适用于：需要多角度分析的场景（如：法律咨询、投资分析）

模式 3：流水线模式（Pipeline）
  数据 → Agent A → Agent B → Agent C → 结果
         (清洗)    (分析)    (报告)

  适用于：有固定处理流程的场景
```

**主 Agent 与子 Agent 的信息交互设计：**

```java
// 多 Agent 协作的核心设计
public class OrchestratorAgent {
    
    private final ChatLanguageModel model;
    private final Map<String, WorkerAgent> workers;
    
    // 子 Agent 需要返回的信息结构
    public record WorkerResult(
        String workerName,
        String status,      // SUCCESS / FAILURE / TIMEOUT
        String result,      // 核心结果（文本摘要）
        String rawOutput,   // 完整输出（可选，供主 Agent 深入分析）
        long durationMs,
        String error        // 失败原因
    );
    
    public String execute(String userRequest) {
        // 1. 主 Agent 分析用户意图，制定计划
        String plan = model.generate(
            "用户请求：" + userRequest + "\n"
            + "请将任务拆解为多个子任务，并指定每个子任务由哪个 Agent 执行。"
            + "可用的 Agent：" + workers.keySet()
        );
        
        // 2. 分发子任务给 Worker Agent
        List<WorkerResult> results = new ArrayList<>();
        for (SubTask task : parseTasks(plan)) {
            WorkerAgent worker = workers.get(task.agentType());
            
            // 子 Agent 执行（带超时控制）
            CompletableFuture<WorkerResult> future = 
                CompletableFuture.supplyAsync(() -> worker.execute(task));
            
            try {
                WorkerResult result = future.get(30, TimeUnit.SECONDS);
                results.add(result);
                
                // 子 Agent 失败 → 主 Agent 决定是否重试或调整方案
                if (result.status().equals("FAILURE")) {
                    String decision = model.generate(
                        "子任务 " + task.name() + " 失败，原因：" + result.error()
                        + "。请决定：重试 / 用其他方式替代 / 通知用户"
                    );
                    if (decision.contains("重试")) {
                        results.add(worker.execute(task));  // 重试
                    }
                }
            } catch (TimeoutException e) {
                results.add(new WorkerResult(task.agentType(), "TIMEOUT",
                    "", "", 30000, "执行超时"));
                future.cancel(true);
            }
        }
        
        // 3. 主 Agent 汇总结果，生成最终回答
        return model.generate(
            "用户请求：" + userRequest + "\n"
            + "子任务结果：\n" + formatResults(results) + "\n"
            + "请生成完整的最终回答。"
        );
    }
}
```

#### 一、Redis 5 种基本数据类型的底层实现

Redis 提供了 5 种基本数据类型，每种类型底层有 2-3 种编码实现。

```
Redis 数据类型与底层编码映射：

| 类型 | 底层编码（Redis 7.0+） | 说明 |
|------|----------------------|------|
| String | SDS（简单动态字符串） | 二进制安全，O(1) 长度获取 |
| List | QuickList（快速列表） | 多个 ZipList 组成的双向链表 |
| Hash | Dict + ListPack | 小数据量用 ListPack，大数据量用 Dict |
| Set | Dict + IntSet | 整数集合用 IntSet，否则用 Dict |
| ZSet | SkipList + ListPack | 跳跃表实现有序性 + 压缩列表优化小数据 |

注意：Redis 7.0 开始，ZipList 被 ListPack 取代。
```

**SDS（简单动态字符串）—— String 的底层：**

```c
// Redis 7.0 SDS 结构
struct sdshdr {
    int len;       // 已使用长度（O(1) 获取字符串长度）
    int alloc;     // 分配的总长度（避免缓冲区溢出）
    char buf[];    // 字节数组（二进制安全，可存图片等）
};

// 相比 C 字符串的优势：
// C 字符串：O(n) 获取长度，不能存 \0，可能缓冲区溢出
// SDS：O(1) 长度获取，二进制安全，自动扩容
```

**SkipList（跳跃表）—— ZSet 的核心：**

```
跳跃表 = 有序链表 + 多层索引

Level 3:  [1]─────────────────────────────→[12]→NULL
Level 2:  [1]──────────→[7]──────────────→[12]→NULL
Level 1:  [1]────→[4]──→[7]────→[9]─────→[12]→NULL
Level 0:  [1]→[3]→[4]→[6]→[7]→[8]→[9]→[10]→[12]→NULL

查找 10：
  ① Level 3: 1 → 12（过大，下降）
  ② Level 2: 1 → 7 → 12（过大，下降）
  ③ Level 1: 7 → 9 → 12（过大，下降）
  ④ Level 0: 9 → 10 ✅
  
  4 步找到，而有序链表需要 8 步！
  时间复杂度：平均 O(log n)，最坏 O(n)
```

#### 二、Redis 持久化：RDB vs AOF

| 对比维度 | RDB（快照） | AOF（追加文件） | Redis 7.0 混合 |
|---------|-----------|---------------|---------------|
| **原理** | 定期生成全量快照 | 记录每次写命令 | RDB 快照 + AOF 增量 |
| **数据完整性** | 可能丢失两次快照间的数据 | 根据 fsync 策略（1秒/每次/从不） | 接近 AOF 的完整性 |
| **恢复速度** | ⭐⭐⭐⭐⭐ 极快（直接加载） | ⭐⭐ 慢（重放所有命令） | ⭐⭐⭐⭐ 快 |
| **文件大小** | ⭐⭐⭐⭐ 紧凑（二进制） | ⭐ 大（文本协议） | ⭐⭐⭐ 适中 |
| **对性能影响** | ⭐⭐ fork 子进程可能阻塞 | ⭐⭐⭐ 取决于 fsync 频率 | ⭐⭐⭐ 折中 |
| **适用场景** | 允许少量数据丢失、快速恢复 | 对数据完整性要求高 | **推荐！兼顾两者** |

**RDB 工作原理：**

```
RDB 保存流程（非阻塞）：

主进程 → fork() → 子进程（写时复制）
  │                    │
  │ 继续处理请求        │ 写入临时 RDB 文件
  │                    │
  │                    ▼
  │              文件写入完成
  │                    │
  └────────────────────┤
                 用临时文件覆盖正式 RDB 文件

COW（Copy on Write）：
  fork 后父子进程共享内存页
  子进程读内存页写 RDB
  父进程收到写请求时，复制该内存页再修改
  → 子进程看到的是 fork 时刻的"数据快照"
```

**AOF 三种 fsync 策略：**

```bash
# appendfsync always    # 每次写命令都 fsync（最安全，最慢）
appendfsync everysec    # 每秒 fsync（推荐，最多丢 1 秒数据）
# appendfsync no       # 由操作系统决定（最快，最不安全）
```

**AOF 重写（Rewrite）机制：**

```
AOF 文件会不断增长，需要定期重写压缩。

AOF 重写原理（非阻塞）：
  1. fork 子进程
  2. 子进程将当前内存数据转换为写命令（合并相同 key 的操作）
  3. 主进程将重写期间的增量命令写入 AOF 重写缓冲区
  4. 重写完成后，将缓冲区内容追加到新 AOF 文件
  5. 用新文件替换旧文件

例子（重写前后的对比）：
  SET key value1
  SET key value2     →     SET key valueN（合并为一条）
  SET key value3
  ...
  SET key valueN
```

#### 三、生产级缓存设计：三大经典问题

**1. 缓存穿透（Cache Penetration）：**

```
问题：查询一个不存在的数据
  → 缓存 miss → 查数据库（也不存在）→ 不写缓存
  → 每次请求都穿透到数据库
  → 恶意攻击者利用不存在的 key 打垮数据库

解决方案：
┌──────────────────────────────────────────────┐
│ 方案一：缓存空值（推荐）                       │
│  查数据库不存在 → 缓存 null（设置短 TTL）      │
│  下次相同请求 → 直接返回 null（不查数据库）     │
│  缺点：需要额外的存储空间，TTL 内数据可能变真实  │
│                                              │
│ 方案二：布隆过滤器（Bloom Filter）             │
│  在缓存前加一层布隆过滤器                      │
│  不存在 → 直接返回（不查缓存，不查数据库）       │
│  存在 → 查缓存 → 查数据库                      │
│  缺点：有误判率（可能把不存在判为存在）          │
│                                              │
│ 方案三：参数校验                              │
│  对请求参数做基本校验（如 ID 格式、范围）        │
│  明显不合法的参数直接拒绝                      │
└──────────────────────────────────────────────┘
```

**2. 缓存击穿（Cache Breakdown）：**

```
问题：热点 key 过期
  → 大量请求同时查数据库
  → 数据库瞬间被打满

解决方案：
┌──────────────────────────────────────────────┐
│ 方案一：互斥锁（Mutex Lock）                   │
│  第一个请求获取锁，查数据库，写缓存            │
│  其他请求等待或返回旧值                        │
│  SETNX key lock → 只有一个线程能拿到锁         │
│                                              │
│ 方案二：逻辑过期（热点 key 永不过期）           │
│  缓存不设置 TTL，而是存一个逻辑过期时间         │
│  获取到"逻辑过期"的数据时，异步线程更新缓存      │
│  当前线程返回旧数据（保证可用性）               │
│                                              │
│ 方案三：分布式锁（Redisson）                   │
│  比 SETNX 更完善的分布式锁方案                 │
│  自动续期、可重入、公平锁等                    │
└──────────────────────────────────────────────┘
```

**3. 缓存雪崩（Cache Avalanche）：**

```
问题：大量 key 同时过期，或 Redis 宕机
  → 大量请求直击数据库
  → 数据库被打垮 → 服务雪崩

解决方案：
┌──────────────────────────────────────────────┐
│ 针对大量 key 同时过期：                        │
│  ① 过期时间加随机值（基础 TTL + 随机 1-5min） │
│  ② 热点数据永不过期（后台定时更新）            │
│  ③ 分散过期时间（不同业务不同 TTL）            │
│                                              │
│ 针对 Redis 宕机：                             │
│  ① Redis 集群 + 主从 + 哨兵                   │
│  ② 本地缓存兜底（Caffeine/Guava Cache）        │
│  ③ 限流 + 降级（Sentinel）                    │
│  ④ 数据库连接池限制（防止被打满）               │
└──────────────────────────────────────────────┘
```

```java
// 缓存穿透：布隆过滤器实现
public class BloomFilterCache {
    
    private final RedisTemplate<String, Object> redis;
    private final BloomFilter<String> bloomFilter;
    
    public BloomFilterCache(RedisTemplate<String, Object> redis) {
        this.redis = redis;
        // 初始化布隆过滤器：预期 1000 万数据，误判率 1%
        this.bloomFilter = BloomFilter.create(
            Funnels.stringFunnel(Charsets.UTF_8), 
            10_000_000, 
            0.01
        );
    }
    
    public Object get(String key) {

public Object getWithMutex(String key) {
    Object value = redis.opsForValue().get(key);
    if (value != null) {
        return value;
    }
    
    // 尝试获取分布式锁
    String lockKey = "lock:" + key;
    Boolean locked = redis.opsForValue()
        .setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS);
    
    if (Boolean.TRUE.equals(locked)) {
        try {
            // 双重检查（可能第一个线程已经写入了）
            value = redis.opsForValue().get(key);
            if (value != null) return value;
            
            // 查数据库
            value = queryDB(key);
            redis.opsForValue().set(key, value, 1, TimeUnit.HOURS);
            return value;
        } finally {
            redis.delete(lockKey);  // 释放锁
        }
```
