### 📖 参考答案

**一、LRU 是什么？为什么面试必考？**

LRU（Least Recently Used，最近最少使用）是一种基于"时间局部性"的缓存淘汰策略——如果数据最近被访问过，那么将来被访问的概率也更高。反之，最久未被访问的数据优先被淘汰。

这道题考察的不是"会不会调API"，而是：
- 数据结构选型能力（为什么选哈希表+双向链表？）
- 时间复杂度分析能力（get/put 如何做到 O(1)？）
- 源码阅读能力（LinkedHashMap 如何通过三个模板方法在不修改 HashMap 核心代码的条件下实现 LRU？）

**二、方案一：LinkedHashMap 一行代码实现（面试慎用，会被追问）**

```java
// LeetCode 146 的"天才解法"（一行核心代码）
public class LRUCache extends LinkedHashMap<Integer, Integer> {
    private final int capacity;
    
    public LRUCache(int capacity) {
        // accessOrder=true → 按访问顺序排序（不是插入顺序！）
        super(capacity, 0.75f, true);
        this.capacity = capacity;
    }
    
    @Override
    protected boolean removeEldestEntry(Map.Entry<Integer, Integer> eldest) {
        // 当 size > capacity 时，自动移除最旧的 Entry
        return size() > capacity;
    }
}
```

**LinkedHashMap 实现 LRU 的底层原理**：

LinkedHashMap 继承自 HashMap，但在 Entry 节点上附加了 `before` 和 `after` 两个指针，维护一条独立的双向链表：

```
LinkedHashMap 扩展的三个模板方法（HashMap 预置的钩子）：

afterNodeAccess(Node e)    ← get/put 访问节点时被调用
afterNodeInsertion(boolean evict)  ← 插入新节点后被调用
afterNodeRemoval(Node e)   ← 移除节点后被调用

关键调用链：
  get(key)
    → HashMap.getNode() 找到节点
    → if (accessOrder == true) afterNodeAccess(e)
        → 把该节点移到双向链表尾部（标记为"最近访问"）

  put(key, value)
    → HashMap.putVal() 插入节点
    → afterNodeInsertion(evict)
        → if (removeEldestEntry(first))
            → 移除双向链表头部节点（"最久未访问"）
```

**accessOrder 参数的作用**：
- `false`（默认）：链表按**插入顺序**排列
- `true`：链表按**访问顺序**排列——每次 get 或 put 已存在的 key 时，该 Entry 会被移到链表末尾

**三、方案二：哈希表 + 双向链表纯手工实现（面试推荐！）**

这是面试官真正想看到的版本——展示你对数据结构的理解：

```java
class LRUCache {
    // 双向链表节点
    class Node {
        int key, value;
        Node prev, next;
        Node() {}
        Node(int k, int v) { key = k; value = v; }
    }
    
    private final int capacity;
    private final Map<Integer, Node> map;  // key → 链表节点
    private final Node head;  // 哨兵头节点
    private final Node tail;  // 哨兵尾节点
    
    public LRUCache(int capacity) {
        this.capacity = capacity;
        this.map = new HashMap<>();
        // 哨兵节点简化边界处理
        head = new Node();
        tail = new Node();
        head.next = tail;
        tail.prev = head;
    }
    
    public int get(int key) {
        Node node = map.get(key);
        if (node == null) return -1;
        moveToTail(node);   // 访问 → 移到尾部（标记为最近使用）
        return node.value;
    }
    
    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {
            node.value = value;
            moveToTail(node);  // 更新 → 移到尾部
        } else {
            if (map.size() >= capacity) {
                // 淘汰头部节点（最久未使用）
                Node eldest = head.next;
                removeNode(eldest);
                map.remove(eldest.key);
            }
            Node newNode = new Node(key, value);
            map.put(key, newNode);
            addToTail(newNode);
        }
    }
    
    // --- 双向链表操作（4 个核心方法）---
    private void removeNode(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }
    
    private void addToTail(Node node) {
        node.prev = tail.prev;
        node.next = tail;
        tail.prev.next = node;
        tail.prev = node;
    }
    
    private void moveToTail(Node node) {
        removeNode(node);
        addToTail(node);
    }
}
```

**数据结构全景**：

```
  哈希表                             双向链表
┌──────────┐                    head ⇄ node ⇄ node ⇄ tail
│ key→Node │                    (哨兵) (最旧) (最新) (哨兵)
├──────────┤                       ↑                ↑
│ 1 → ●──┼────────────────────────→│                │
│ 2 → ●──┼────────────────────────────────────────→ │
│ 3 → ●──┼────────────────────────────→│            │
└──────────┘                    
  
  get(1) → map 中 O(1) 找到 Node → moveToTail → O(1) 移动到尾部
  put(4) → 如果满了 → remove head.next → O(1) → map.remove → O(1)
```

**时间复杂度**：get 和 put 都是 O(1)——HashMap 保证 O(1) 查找，双向链表保证 O(1) 插入/删除。

**四、从 LRU 到工业级：Caffeine 的 W-TinyLFU**

面试加分项——当面试官追问"LRU 有什么缺点？什么场景下会出问题？"：

| 策略 | 决策依据 | 缺点 |
|------|---------|------|
| **LRU** | 只看"最近访问时间" | 偶发性大量访问会冲掉真正热数据（如大促时老数据被新流量挤掉） |
| **LFU** | 只看"访问频率" | 历史高频数据永不过期，无法适应业务变化 |
| **W-TinyLFU**（Caffeine） | **频率 + 时间衰减** | 最均衡，但实现复杂 |

W-TinyLFU（Window Tiny Least Frequently Used）是 Caffeine 的核心算法，它是 LRU + LFU 的进化：
- **Window Cache**（1%）：新数据先进入窗口区（LRU 策略）
- **Main Cache**（99%）：主缓存区用 TinyLFU（频率统计 + 时间衰减）
- 窗口区的数据要被淘汰时，与主缓存区的数据进行 pk——频率高的留下

### 💡 延伸思考

1. **LRU 缓存为什么用双向链表而不是单向链表？** — 因为需要 O(1) 删除任意节点。单向链表删除一个节点需要找到它的前驱，必须遍历（O(n)）。双向链表每个节点持有前驱指针，删除 O(1)。对于 moveToTail 操作（先删除再插入尾部），双向链表也是 O(1)。
2. **如果让你实现线程安全的 LRU 缓存，怎么做？** — 思路①：用 `Collections.synchronizedMap(new LinkedHashMap(...))`，但需要外部同步 `removeEldestEntry` 的逻辑；思路②：用 `ConcurrentHashMap` + `ConcurrentLinkedDeque`，但需要处理 map 和链表的原子性（挑战大）；思路③：直接用 Caffeine，它内部解决了并发问题且性能最优。

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-02 午间报告 — "Spring Boot 4.0 正式发布（基于 Spring Framework 7.0）：内置弹性架构，@Retryable / @CircuitBreaker / @RateLimiter 开箱即用，内置声明式 REST 客户端减少 70% HTTP 层代码"

### 📖 参考答案

**一、背景：微服务容错的演进，Spring Boot 4.0 为什么"内置"弹性？**

```
容错框架的演进路线：

  2015: Hystrix（Netflix）
    ↓ @HystrixCommand → 线程池隔离 → 功能最全
  2018: Hystrix 进入维护期
    ↓
  2020: Resilience4j（轻量级）+ Sentinel（阿里）
    ↓ 需要额外依赖，注解不统一
  2026: Spring Boot 4.0 原生内置弹性
    ↓ @Retryable / @CircuitBreaker / @RateLimiter → 零依赖！
```

Spring Boot 4.0（基于 Spring Framework 7.0）的核心哲学转变：**弹性（Resilience）不再是"附加功能"，而是框架的一等公民**。这意味着不需要再引入 Resilience4j 或 Sentinel，就能用注解实现重试、熔断和限流。

**二、三大弹性注解详解**

### 1. @Retryable — 声明式重试

```java
@Service
public class PaymentService {
    
    @Retryable(
        maxAttempts = 3,                    // 最大重试 3 次
        backoff = @Backoff(
            delay = 1000,                   // 初始延迟 1 秒
            multiplier = 2.0,               // 指数退避：1s → 2s → 4s
            maxDelay = 10000                // 最大延迟 10 秒
        ),
        retryOn = {TimeoutException.class,  // 只重试这些异常
                   ConnectException.class},
        noRetryOn = {IllegalArgumentException.class}  // 参数错误不重试
    )
    public PaymentResult pay(Order order) {
        return paymentGateway.submit(order);
    }
    
    // 重试耗尽后的降级方法
    @Recover
    public PaymentResult payFallback(Exception e, Order order) {
        log.error("支付失败，已重试 3 次", e);
        return PaymentResult.fail("支付服务暂时不可用");
    }
}
```

**核心机制**：
- **指数退避**（Exponential Backoff）：避免重试风暴，多客户端同时重试时拉长间隔
- **retryOn / noRetryOn**：精确控制哪些异常值得重试（网络超时可重试，参数错误重试无意义）
- **@Recover**：重试耗尽后的兜底逻辑

### 2. @CircuitBreaker — 声明式熔断

```java
@Service
public class InventoryService {
    
    @CircuitBreaker(
        failureRateThreshold = 50,          // 失败率 > 50% 触发熔断
        waitDurationInOpenState = 30000,    // 熔断后 30 秒进入半开状态
        slidingWindowSize = 10,             // 滑动窗口大小（最近 10 次调用）
        minimumNumberOfCalls = 5,           // 最少 5 次调用后才计算失败率
        permittedNumberOfCallsInHalfOpenState = 3  // 半开状态放行 3 个请求探测
    )
    public StockResult checkStock(Long productId) {
        return stockApi.query(productId);
    }
    
    // 熔断期间的降级方法
    public StockResult checkStockFallback(Long productId, Exception e) {
        // 返回缓存中的库存数据
        return cacheService.getStock(productId);
    }
}
```

**断路器状态机**：

```
                   ┌──────────────┐
       正常调用    │   CLOSED     │  失败率超阈值
    ┌────────────→│   (闭合状态)  │──────────────┐
    │             └──────────────┘              │
    │                                           ▼
    │                                   ┌──────────────┐
    │         等待时间到                │    OPEN      │
    └────────── 探测成功                │   (熔断状态)  │
               ◄────────────────────   │  快速失败     │
    ┌──────────────┐                   └──────────────┘
    │  HALF_OPEN   │                          │
    │  (半开状态)   │◄─────────────────────────┘
    └──────────────┘   等待时间到期
          │
          │ 探测失败 → 重新熔断
```

### 3. @RateLimiter — 声明式限流

```java
@RestController
public class SeckillController {
    
    @RateLimiter(
        permitsPerSecond = 100,             // 每秒最多 100 个请求
        acquireTimeout = 500,               // 最多等 500ms 获取令牌
        failOnTimeout = true                // 超时直接失败（不走降级获取）
    )
    @PostMapping("/seckill")
    public Result seckill(@RequestBody SeckillRequest req) {
        return seckillService.execute(req);
    }
}
```

**三、与 Resilience4j / Sentinel 的架构差异**

| 维度 | Spring Boot 4.0 内置 | Resilience4j | Sentinel |
|------|----------------------|-------------|----------|
| 依赖 | **零额外依赖** | 需引入 starter | 需引入 starter + 控制台 |

**四、内置声明式 REST 客户端 —— 革命性变化**

这是 Spring Boot 4.0 的另一大杀器——把 HTTP 调用简化到极致：

```java
// ① 定义接口（声明式！）
@HttpExchange("https://api.example.com")
public interface UserClient {
    
    @GetExchange("/users/{id}")
    User getUser(@PathVariable Long id);
    
    @PostExchange("/users")
    User createUser(@RequestBody User user);
    
    @DeleteExchange("/users/{id}")
    void deleteUser(@PathVariable Long id);
}

// ② 创建代理（一行代码）
@Configuration
public class ClientConfig {
    @Bean
    public UserClient userClient() {
        return HttpServiceProxyFactory
            .builder(WebClientAdapter.forClient(WebClient.create()))
            .build()
            .createClient(UserClient.class);
    }
}

// ③ 使用（像调本地方法一样调远程接口！）
@Service
public class OrderService {
    @Autowired
    private UserClient userClient;
    
    public void createOrder(Long userId) {
        User user = userClient.getUser(userId);  // 自动发 HTTP 请求！
    }
}
```

**对比传统方式**：

| 方式 | 代码量 | 类型安全 | 集成弹性 |
|------|-------|---------|---------|
| **RestTemplate** | 多（手动拼接 URL + 反序列化） | 弱 | 需手动包装 |
| **Feign / OpenFeign** | 少（接口+注解） | 强 | 需 Feign + Resilience4j 配合 |
| **Spring Boot 4.0 声明式客户端** | **最少** | **最强** | **原生集成** @Retryable / @CircuitBreaker！ |

核心优势：声明式 REST 客户端可以**和前文的 @Retryable / @CircuitBreaker 无缝结合**：

```java

public interface PaymentClient {

}
```

**一、ThreadLocal 原理与内存泄漏**

### 1.1 核心设计——每个线程拥有独立副本

```
ThreadLocal 数据结构：

  Thread-1                    Thread-2
  ┌──────────┐               ┌──────────┐
  │ threadLocals │            │ threadLocals │
  │ (ThreadLocalMap) │        │ (ThreadLocalMap) │
  │  ┌─────┬───┐  │          │  ┌─────┬───┐  │
  │  │ TL1 │ v1│  │          │  │ TL1 │ v3│  │
  │  ├─────┼───┤  │          │  ├─────┼───┤  │
  │  │ TL2 │ v2│  │          │  │ TL2 │ v4│  │
  │  └─────┴───┘  │          │  └─────┴───┘  │
  └──────────┘               └──────────┘

  关键：ThreadLocal 对象本身是 key（弱引用），
        值存在 Thread 自己的 ThreadLocalMap 中
```

```java
// ThreadLocal 典型用法
public class UserContext {
    private static final ThreadLocal<User> currentUser = new ThreadLocal<>();
    
    public static void setUser(User user) { currentUser.set(user); }
    public static User getUser() { return currentUser.get(); }
    public static void clear() { currentUser.remove(); }  // 必须调用！
}
```

### 1.2 内存泄漏的根因——弱引用 + 线程池复用的致命组合

ThreadLocal 的 Entry 继承了 WeakReference：

```java
// ThreadLocalMap 的 Entry（源码简化）
static class Entry extends WeakReference<ThreadLocal<?>> {
    Object value;  // 强引用！
    Entry(ThreadLocal<?> k, Object v) {
        super(k);  // k 是弱引用
        value = v;  // v 是强引用
    }
}
```

**引用链分析（泄漏的全过程）**：

```
正常情况（线程短生命周期）：
  Thread Ref → Thread → ThreadLocalMap → Entry
                                                ├─ key → ThreadLocal（弱引用）
                                                └─ value → Object（强引用）
  线程结束 → 所有引用回收 ✅

泄漏场景（线程池复用）：
  ① ThreadLocal 对象的强引用被置 null（如 static 变量被清空）
  ② GC 发生 → Entry 的 key（弱引用）被回收 → key 变成 null
  ③ 但线程池线程不销毁 → ThreadLocalMap 仍在 
     → Entry 还在 → value 的强引用还在 → ❌ 内存泄漏！

  key = null 的 Entry 永远无法通过 key 访问，
  但 value 却一直占据内存！
```

```java
// 经典泄漏场景
public class LeakDemo {
    private static ThreadLocal<User> tl = new ThreadLocal<>();
    private static final ExecutorService pool = 
        Executors.newFixedThreadPool(10);
    
    public static void main(String[] args) {
        pool.execute(() -> {
            tl.set(new User("big object"));  // 在线程池线程中设置
            // ❌ 忘记调用 tl.remove()！
        });
        
        tl = null;  // ThreadLocal 强引用置 null
        // GC 后：key 被回收，但线程池线程不销毁 → value 泄漏！
    }
}
```

**解决方案**：

```java
// ✅ 铁律：ThreadLocal 使用完毕必须 remove()
pool.execute(() -> {
    try {
        tl.set(new User("big object"));
        // 业务逻辑...
    } finally {
        tl.remove();  // 必须！
    }
});

// ✅ JDK 的自动清理（不完全可靠）
// ThreadLocalMap 在 get/set/remove 时会触发 expungeStaleEntry()
// 探测式清理 key==null 的过期 Entry
// 但这只清理"被探测到的"，不是全量扫描
```

**ThreadLocalMap 的哈希冲突解决**：使用**线性探测法**（而不是 HashMap 的链表法）。因为 ThreadLocalMap 规模通常很小，且 ThreadLocal 对象的 hashCode 通过 `nextHashCode.getAndAdd(HASH_INCREMENT)` 递增（斐波那契散列），冲突概率低。

**二、ConcurrentHashMap JDK8 的锁粒度优化**

### 2.1 JDK7 vs JDK8 的核心变化

| 维度 | JDK7 | JDK8 |
|------|------|------|
| 数据结构 | Segment 分段锁（16 段） | Node 数组 + CAS + synchronized |
| 并发度 | 固定 16（不可改） | **等于数组长度** |
| 锁粒度 | 段级别（一个段锁多个桶） | **桶级别**（一个桶一把锁） |
| 查找 | 需要两次哈希（找段 → 找桶） | 一次哈希 |
| 红黑树 | 不支持 | 链表长 > 8 转红黑树 |

### 2.2 JDK8 的 CAS + synchronized 精妙配合

```java
// ConcurrentHashMap.put() 核心流程（简化）

final V putVal(K key, V value) {
    // ① 计算哈希 → 找到桶下标
    int hash = spread(key.hashCode());
    
    // ② 桶为空 → CAS 无锁插入（大多数场景！）
    if (tabAt(tab, i) == null) {
        if (casTabAt(tab, i, null, new Node(hash, key, value)))
            break;  // CAS 成功 → 无锁写入！
        // CAS 失败 → 说明其他线程抢先了 → 重新循环
    }
    // ③ 桶非空 → synchronized 锁住桶头节点
    else {
        synchronized (f) {  // f = tabAt(tab, i)，锁住的是头节点
            // 链表遍历 → 覆盖旧值 or 尾插新节点
            // 红黑树操作
        }
    }
}
```

```
写操作全景：

  table[0]  table[1]  table[2]  table[3]  ...  table[15]
    │          │          │          │
    CAS      sync锁    sync锁     CAS
   (无锁)   (桶锁)    (桶锁)    (无锁)
    │          │          │          │
    ↓          ↓          ↓          ↓
  线程1写   线程2写    线程3写    线程4写
  ────────────────────────────────────────────
  4 个线程操作 4 个不同的桶 → 完全并行！无锁竞争！
```

**get 操作全程无锁**：因为 `Node[] table`、`Node.val`、`Node.next` 都用了 `volatile` 修饰，保证内存可见性。

### 2.3 扩容——多线程协同

```
ConcurrentHashMap 扩容不是单线程：
  → transferIndex（扩容进度指针，volatile）
  → 每个线程分一段区间（stride 步长）去迁移
  → CAS 竞争 transferIndex → 保证不重复
  → 线程迁移完自己的区间后继续竞争下一段
  → 所有区间迁移完 → 扩容完成

  迁移中：原数组的桶被标记为 ForwardingNode
  → 读操作遇到 ForwardingNode → 去新数组读
  → 写操作遇到 ForwardingNode → helpTransfer 协助扩容
```

**三、synchronized 锁升级全流程**

JDK6 之后，synchronized 不再直接使用重量级锁（OS Mutex），而是经历了四次升级：

```
synchronized 锁升级历程（最重要的一张图）：

  new → 偏向锁 → 轻量级锁 → 重量级锁
   ↑       ↓         ↓          ↓
   无锁   单线程   多线程      多线程
         反复进入  交替执行   竞争激烈
                  (CAS)     (OS Mutex)

升级路径（不可逆，只能升不能降）：
  
  ① 无锁
     ↓ 一个线程首次获取锁
  ② 偏向锁（Biased Lock）
     对象头 Mark Word 记录线程 ID
     同一个线程再次进入 → 直接通过（不需要 CAS！）
     ↓ 另一个线程尝试获取锁 → 偏向锁撤销
  ③ 轻量级锁（Lightweight Lock）
     竞争线程通过 CAS 自旋尝试获取锁
     在持有锁线程的栈帧中创建 Lock Record
     ↓ 自旋超过阈值（默认 10 次）或等待线程数 > CPU/2
  ④ 重量级锁（Heavyweight Lock）
     向 OS 申请 Mutex
     未获取锁的线程进入 BLOCKED 状态（不消耗 CPU）
     由 OS 调度唤醒
```

**对象头 Mark Word 的变化**（64 位 JVM）：

| 锁状态 | 锁标志位 | 存储内容 |
|--------|---------|---------|
| 无锁 | 01 | hashCode + 分代年龄 |
| 偏向锁 | 01 | **线程 ID** + Epoch + 分代年龄 |
| 轻量级锁 | 00 | **指向栈中 Lock Record 的指针** |
| 重量级锁 | 10 | **指向 Monitor（ObjectMonitor）的指针** |
| GC 标记 | 11 | 空 |

```java
// 查看锁状态（需要 JDK 8 的偏向锁延迟参数）
// -XX:BiasedLockingStartupDelay=0  → 启动即开启偏向锁
// -XX:-UseBiasedLocking           → 关闭偏向锁

public class LockUpgradeDemo {
    public static void main(String[] args) throws Exception {
        Object lock = new Object();
        
        // ① 偏向锁
        synchronized (lock) {
            System.out.println("偏向锁");  // 记录线程ID到Mark Word
        }
        
        // ② 轻量级锁（另一个线程来争抢，偏向锁被撤销）
        new Thread(() -> {
            synchronized (lock) {
                System.out.println("轻量级锁");  // CAS自旋
            }
        }).start();
        Thread.sleep(100);
        
        // ③ 重量级锁（多线程持续竞争）
        for (int i = 0; i < 3; i++) {
            new Thread(() -> {
                synchronized (lock) {
                    try { Thread.sleep(1000); } catch (Exception e) {}
                }
            }).start();
        }
    }
}
```

**2026 年面试新动态**：JDK 21 已默认禁用偏向锁（因为现代应用很少存在"单线程反复获取同一锁"的场景，偏向锁的维护成本 > 收益）。面试时提到这个差异是加分项。

### 💡 延伸思考

1. **为什么 ThreadLocal 的 Entry 用弱引用？直接强引用不行吗？** — 如果用强引用，当外部的 ThreadLocal 对象被置 null 时，Entry 中的 key 仍然存在强引用 → ThreadLocal 对象永远不会被 GC → 更严重的内存泄漏。弱引用的本意是让 ThreadLocal 对象可以被 GC 回收——只是 value 的清理依赖额外的探测机制，所以 JDK 的设计不完美但不是错误。
2. **ConcurrentHashMap 在 JDK21 有什么改进？** — JDK21 对 ConcurrentHashMap 做了内部重构，主要是更好的 JIT 编译优化（`@jdk.internal.vm.annotation.Stable` 等），以及扩容算法的微调。功能层面没有大变化，因为 JDK8 的设计已经足够经典。

**Function Calling 的三大痛点**：

| 痛点 | 表现 | 后果 |
|------|------|------|
| **碎片化** | OpenAI / Claude / 通义千问各自定义了不同的工具格式 | 切换模型 = 重写所有工具定义 |

### 三、MCP——工具调用的 USB-C 接口

MCP（Model Context Protocol）是 Anthropic 推出的标准化协议——类比为 AI 界的 USB-C：一次定义工具，所有模型都能调用。

**MCP 的三层架构**：

```
┌──────────────────────────────────────────────────────┐
│  Host（AI 客户端）                                    │
│  如：Claude Desktop / ChatGPT / Cursor / 自研 Agent  │
│  角色：发起请求，展示结果                              │
│  类比：USB 主机（电脑）                                │
├──────────────────────────────────────────────────────┤
│  Client（每个 Server 一个连接）                        │
│  角色：维护连接，管理会话状态                           │
│  类比：USB 控制器                                     │
├──────────────────────────────────────────────────────┤
│  Server（独立部署的工具服务）                           │
│  角色：暴露 Tool / Resource / Prompt                  │
│  类比：USB 外设（U盘/键盘/打印机）                      │
│                                                      │
│  通信协议：JSON-RPC 2.0                               │
│  传输方式：HTTP/SSE（远程）或 stdio（本地）            │
└──────────────────────────────────────────────────────┘
```

**三大核心原语**：

| 原语 | 作用 | 类比 | 示例 |
|------|------|------|------|
| **Tool** | 让 AI 调用外部功能 | 让 AI 有 "手" | 查数据库、调 API、发邮件 |
| **Resource** | 让 AI 读取数据/上下文 | 让 AI 有 "眼" | 读取用户信息、查看订单详情 |
| **Prompt** | 预设交互模板 | 让 AI 有 "模板" | 客服话术、代码审查模板 |

```
MCP 的交互流程：

  用户: "帮我查一下上周的订单，然后发邮件给客户"
    ↓
  Host (AI Client):
    ① 调用 Server.list_tools() → 发现 [query_order, send_email] 工具
    ② LLM 判断意图 → 决定先查订单再发邮件
    ③ MCP Client 调用 query_order 工具 → 返回订单数据
    ④ LLM 组织内容 → 调用 send_email 工具 → 发送成功
    ⑤ 向用户展示结果
```

### 四、异构 tool_calls 统一处理——工程化的核心挑战

2026 年生产环境中的真实挑战：你的系统可能同时对接 OpenAI、Claude、通义千问——三个模型的 tool_calls 格式完全不同：

```python
# OpenAI 格式
tool_calls = [{
    "id": "call_abc",
    "type": "function",
    "function": {"name": "get_weather", "arguments": '{"city":"北京"}'}
}]

# Claude 格式（早期）
tool_use = {
    "type": "tool_use",
    "id": "toolu_abc",
    "name": "get_weather",
    "input": {"city": "北京"}
}

# 通义千问 格式
tool_calls = [{
    "function": {"name": "get_weather", "arguments": '{"city":"北京"}'}
}]
```

**统一处理方案——适配器模式**：

```python
from abc import ABC, abstractmethod

# ① 定义统一的工具调用接口
@dataclass
class UnifiedToolCall:
    id: str
    name: str
    arguments: dict

class ToolCallAdapter(ABC):
    """适配器抽象——屏蔽底层模型差异"""
    @abstractmethod
    def parse_response(self, raw_response: dict) -> List[UnifiedToolCall]:
        pass
    
    @abstractmethod
    def format_result(self, call_id: str, result: str) -> dict:
        pass

# ② OpenAI 适配器
class OpenAIToolCallAdapter(ToolCallAdapter):
    def parse_response(self, raw_response):
        return [
            UnifiedToolCall(
                id=tc["id"],
                name=tc["function"]["name"],
                arguments=json.loads(tc["function"]["arguments"])
            )
            for tc in raw_response.get("tool_calls", [])
        ]

# ③ Claude 适配器
class ClaudeToolCallAdapter(ToolCallAdapter):
    def parse_response(self, raw_response):
        # Claude 的 tool_use 是 content block 而非顶层字段
        ...

# ④ 统一调度器
class AgentToolDispatcher:
    def __init__(self):
        self.adapters = {
            "openai": OpenAIToolCallAdapter(),
            "claude": ClaudeToolCallAdapter(),
            "qwen": QwenToolCallAdapter(),
        }
        self.tools = {}  # 统一的工具注册表
    
    def dispatch(self, model: str, response: dict) -> List[str]:
        adapter = self.adapters[model]
        tool_calls = adapter.parse_response(response)
        
        results = []
        for call in tool_calls:
            tool_fn = self.tools.get(call.name)
            result = tool_fn(**call.arguments)
            results.append(result)
        return results
```

**二、限流（Rate Limiting）—— 控制流量入口**

### 2.1 四大限流算法

| 算法 | 原理 | 突发流量 | 实现复杂度 | 适用场景 |
|------|------|---------|-----------|---------|
| **计数器** | 固定时间窗口统计 | ❌ 临界点可能被击穿 | 低 | 简单场景 |
| **滑动窗口** | 时间窗口细粒度滑动 | ✅ 更平滑 | 中 | Sentinel 默认 |
| **漏桶** | 恒定速率处理请求 | ❌ 严格平滑 | 低 | 需强制匀速 |
| **令牌桶** | 固定速率放令牌，可累积 | ✅ **允许突发** | 中 | 最常用 |

### 2.2 令牌桶算法详解（最常用）

```
令牌桶的工作机制：

  ┌─────────────┐
  │ 令牌生成器    │  每秒产生 N 个令牌
  │ (固定速率)   │
  └──────┬──────┘
         ↓ 令牌放入桶中
  ┌─────────────┐
  │   令牌桶     │  最多存 M 个令牌（桶容量）
  │  [●][●][●]  │
  └──────┬──────┘
         ↓ 请求到达 → 获取令牌
  ┌─────────────┐        有令牌 → 放行 ✅
  │   请求       │        无令牌 → 拒绝 ❌（或排队）
  └─────────────┘

  关键公式：
  请求速率 = N（令牌生成速率）
  允许突发 = M（桶容量）— 桶中存储的令牌
```

```java
// Guava RateLimiter — 令牌桶的经典实现
RateLimiter limiter = RateLimiter.create(100.0);  // 每秒 100 个令牌

// ① 阻塞获取（等不到令牌就阻塞）
double waitTime = limiter.acquire();  // 返回等待时间

// ② 非阻塞获取（立即返回是否成功）
if (limiter.tryAcquire(500, TimeUnit.MILLISECONDS)) {
    handleRequest();  // 500ms 内拿到令牌
} else {
    return "系统繁忙，请稍后再试";  // 拿不到，直接拒绝
}
```

### 2.3 生产级限流的多级部署

```
网关层（Nginx/Kong/APISIX）
  → 全局 IP 限流 + 路径限流
  → 挡住 90% 的无效流量

应用层（Sentinel / Resilience4j）
  → 接口级 QPS 限流
  → 热点参数限流（防黄牛刷单）

业务层（自定义）
  → 用户级限流（每人每天最多 N 次）
  → 防羊毛党
```

**三、熔断（Circuit Breaker）—— 防止故障扩散**

### 3.1 断路器三态状态机

```
                  ┌──────────────┐
                  │   CLOSED     │  ← 正常状态
                  │   (闭合)      │    统计失败率
                  └──────┬───────┘
                         │ 失败率 ≥ threshold
                         ▼
                  ┌──────────────┐
                  │    OPEN      │  ← 熔断状态
                  │   (断开)      │    直接返回 fallback
                  └──────┬───────┘
                         │ 等待时间到
                         ▼
                  ┌──────────────┐
                  │  HALF_OPEN   │  ← 半开状态
                  │   (半开)      │    放行少量请求探测
                  └──────┬───────┘
           探测成功 ↙       ↘ 探测失败
    ┌──────────┐           ┌──────────┐
    │  CLOSED  │           │   OPEN   │
    └──────────┘           └──────────┘
```

### 3.2 熔断器关键配置参数

```yaml
# Resilience4j 熔断器配置
resilience4j:
  circuitbreaker:
    instances:
      paymentService:
        slidingWindowType: COUNT_BASED     # 基于调用次数统计
        slidingWindowSize: 10              # 最近 10 次调用
        minimumNumberOfCalls: 5            # 最少 5 次调用后才计算失败率
        failureRateThreshold: 50           # 失败率 > 50% → 熔断
        waitDurationInOpenState: 30s       # 熔断 30 秒后进入半开
        permittedNumberOfCallsInHalfOpenState: 3  # 半开放行 3 个请求
        slowCallRateThreshold: 50          # 慢调用率 > 50% → 熔断
        slowCallDurationThreshold: 2s      # 超过 2 秒算慢调用
```

**参数调优经验**：

| 参数 | 太小 | 太大 |
|------|------|------|
| `failureRateThreshold` | 网络抖动就熔断，频繁开关 | 下游已经崩了还不熔断 |
| `waitDurationInOpenState` | 频繁半开探测，下游还没恢复又被打 | 故障恢复后长时间不可用 |
| `slidingWindowSize` | 统计不够，偶发性误判 | 熔断响应慢，大量失败后才触发 |

**四、重试（Retry）—— 瞬时故障自愈**

### 4.1 重试的核心矛盾

重试能解决瞬时故障（网络抖动、DNS 解析延迟），但**重试本身是"放大器"**——如果下游已经过载，重试会让情况更糟。

```
重试的正确姿势 = 指数退避 + 随机抖动（Jitter）

  第 1 次重试：等 100ms
  第 2 次重试：等 200ms（100 × 2）
  第 3 次重试：等 400ms（200 × 2）
  
  加入随机抖动：
  第 1 次重试：等 100ms + random(0, 50)ms
  第 2 次重试：等 200ms + random(0, 100)ms
  
  为什么加随机抖动？
  → 防止"惊群效应"——如果 100 个客户端同时重试，
    没有随机抖动的话，它们的重试时间完全相同 → 下游瞬间被打爆
```

### 4.2 重试必须配合幂等性

```java
// ❌ 危险：非幂等操作 + 重试 = 重复扣款
@Retryable(maxAttempts = 3)
public void deductBalance(Long userId, BigDecimal amount) {
    accountMapper.deduct(userId, amount);  // 每次重试都会再扣一次！
}

// ✅ 安全：幂等设计
@Retryable(maxAttempts = 3)
public void deductBalance(String idempotentKey, Long userId, BigDecimal amount) {
    // ① 幂等性检查
    if (idempotentService.exists(idempotentKey)) {
        return;  // 已处理过，跳过
    }
    // ② 执行业务
    accountMapper.deduct(userId, amount);
    // ③ 记录已处理
    idempotentService.save(idempotentKey);
}
```

### 💡 延伸思考

1. **Sentinel 的滑动窗口为什么比固定窗口好？** — 固定窗口在窗口边界存在"临界突变"问题：比如 1 分钟窗口限制 100 个请求，在 10:00:59 和 10:01:00 两秒内可能涌入 200 个请求（前窗口最后 1 秒 + 后窗口第 1 秒），但两个窗口统计都是合规的。滑动窗口将窗口切成 N 个小格（细粒度），随时间滑动淘汰旧格子，避免了边界漏洞。Sentinel 默认使用 LeapArray 滑动窗口，并将统计信息存储在 `MetricBucket` 中以实现无锁化。
2. **服务网格（Service Mesh）的弹性治理能替代 Sentinel 吗？** — 部分可以，但不完全。Istio/Envoy 可以在 Sidecar 层做限流、熔断，优势是零代码侵入。但 Sidecar 的限流是粗粒度的（连接/请求级别），无法做到 Sentinel 的"热点参数限流"（如对同一个商品 ID 精准限流）。最佳实践是：基础设施层（网关/Sidecar）做通用限流，应用层（Sentinel）做业务精细限流，双层防护。
