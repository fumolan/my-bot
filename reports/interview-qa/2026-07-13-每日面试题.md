## 题目 1：[Java并发/集合] ConcurrentHashMap JDK 8 的计数机制：size() 方法为什么不准确？底层 CounterCell 与 baseCount 如何协同工作？

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-13 日报 — "HashMap不再问put流程，改问'并发下ConcurrentHashMap的size()为什么不准确'"
**相关岗位**：Java后端 / 全栈

### 📖 参考答案

#### 一、问题本质：size() 在高并发下为什么"不准确"？

ConcurrentHashMap 的 `size()` 方法返回的是一个**近似值（approximate count）**，而非实时精确值。原因在于：

- **不加全局锁**：size() 不会对全表加锁来获取精确计数（那样会阻塞所有写操作，违背并发设计的初衷）
- **非原子累加**：累加 baseCount + CounterCell[] 的过程中，其他线程可能正在并发插入/删除元素，导致遗漏或重复计数
- **扩容影响**：扩容期间数据结构在变化，遍历计数可能跳过部分桶或重复计算

```
size() 近似值的工作机制：

┌─────────────────────────────────────────────────────────┐
│  ConcurrentHashMap.size()                               │
│                                                         │
│  ① 读取 baseCount（volatile 变量）                       │
│     → 记录无竞争时的计数变化（CAS 更新）                  │
│                                                         │
│  ② 遍历 CounterCell[] 数组                              │
│     → 分散高并发 increment 操作的计数单元                │
│     → 累加每个 CounterCell 的 value                     │
│                                                         │
│  ③ 返回 sum = baseCount + 所有 CounterCell.value        │
│                                                         │
│  ⚠️ 在①→②的过程中，其他线程可能正在修改数据             │
│  所以返回的是"某一时刻的快照估计"，而非精确值            │
└─────────────────────────────────────────────────────────┘
```

#### 二、JDK 8 的核心计数机制：baseCount + CounterCell

**baseCount 基础计数器：**

```java
// 当没有线程竞争时，直接用 CAS 更新 baseCount
// 当 CAS 失败时（有竞争），转用 CounterCell 分散计数

// 增加计数
private final void addCount(long x, int check) {
    CounterCell[] cs; long b, s;
    // 尝试 CAS 更新 baseCount
    if ((cs = counterCells) != null ||
        !U.compareAndSetLong(this, BASECOUNT, b = baseCount, s = b + x)) {
        CounterCell c; long v; int m;
        boolean uncontended = true;
        
        // CAS 失败 → 进入 CounterCell 逻辑
        if (cs == null || (m = cs.length - 1) < 0 ||
            (c = cs[ThreadLocalRandom.getProbe() & m]) == null ||
            !(uncontended = U.compareAndSetLong(c, CELLVALUE, v = c.value, v + x))) {
            fullAddCount(x, uncontended);  // 完全竞争下的兜底逻辑
            return;
        }
        // ...
    }
}
```

**CounterCell 的工作原理：**

```
CounterCell 数组 = 多个计数单元，用于分散高并发下的竞争

无竞争时：baseCount += 1 (单次 CAS，最快)
                        ↓
CAS 失败时：随机选一个 CounterCell[i] += 1 (分散到不同槽位)
                        ↓
CounterCell 全部竞争 → fullAddCount() 兜底
  （创建新的 CounterCell 或扩容 CounterCell 数组）

类比理解：
  baseCount    = 便利店的主收银台
  CounterCell  = 高峰时段额外开放的多个自助收银台
  fullAddCount = 收银台全部排队 → 再开新的收银台
```

**CounterCell 定义：**
```java
@jdk.internal.vm.annotation.Contended  // 缓存行填充，防止伪共享
static final class CounterCell {
    volatile long value;  // 每个计数单元的值
    CounterCell(long x) { value = x; }
}
```

#### 三、size() 源码实现

```java
public int size() {
    long n = sumCount();
    return ((n < 0L) ? 0 :
            (n > (long)Integer.MAX_VALUE) ? Integer.MAX_VALUE :
            (int)n);
}

final long sumCount() {
    CounterCell[] cs = counterCells;
    long sum = baseCount;  // 1. 取 baseCount
    if (cs != null) {
        // 2. 遍历所有 CounterCell 累加
        for (CounterCell c : cs)
            if (c != null)
                sum += c.value;
    }
    return sum;
}
```

**不精确的原因：** `sumCount()` 在遍历 CounterCell 数组的过程中，没有对任何写入操作加锁。线程 A 刚读完某个 CounterCell，线程 B 就修改了它——这就是为什么说 size() 返回的是**近似值**。

#### 四、JDK 7 vs JDK 8 的计数对比

| 对比维度 | JDK 7（分段锁） | JDK 8（CAS+CAS辅助） |
|---------|----------------|---------------------|
| 计数方式 | 遍历所有 Segment，累加每个 Segment 的 count | baseCount + CounterCell[] |
| 锁机制 | 尝试两次不加锁累加，不一致则全表加锁 | 全程不加锁，CAS 分散竞争 |
| 性能 | 竞争激烈时全表锁，性能骤降 | 始终无阻塞，性能稳定 |
| 精确度 | 两次尝试可能不一致，全表锁时精确 | 始终近似，但误差可控 |

#### 五、面试答题模板

```
"ConcurrentHashMap 的 size() 返回的是近似值，不是精确值。

底层采用 baseCount + CounterCell 双计数机制：
- 无竞争时，CAS 更新 baseCount（高效）
- 有竞争时，将计数分散到 CounterCell 数组的不同槽位（减少锁冲突）
- size() 调用 sumCount() 累加 baseCount 和所有 CounterCell 的值

为什么不是精确值？因为 sumCount() 在遍历过程中不加锁，
可能漏掉或重复计算正在发生的修改。

实际项目中，如果需要精确计数，可以用 LongAdder 替代，
或者用数据库计数器。大多数场景下 size() 的近似值足够使用。"
```

### 💡 延伸思考
1. **LongAdder 和 ConcurrentHashMap 的计数机制是什么关系？** — 本质上是同一设计模式：热点分散（Striping）。ConcurrentHashMap 的 CounterCell 设计直接借鉴了 LongAdder 的思想。
2. **JDK 17 中 ConcurrentHashMap 的计数机制有变化吗？** — 核心机制相同，但 JDK 17 增加了 `@Contended` 注解避免 CounterCell 的伪共享（False Sharing）问题，并优化了 `fullAddCount` 中的自旋逻辑。

## 题目 2：[AI/大模型] Transformer 架构核心原理：Self-Attention、Multi-Head Attention 与 Positional Encoding 详解

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-13 日报 — "大模型/AI Agent面试必考12题，涵盖Transformer、RAG、Agent框架、模型微调等，出现概率超80%，无论算法岗还是工程岗都会问"
**相关岗位**：Java后端 / Python后端 / AI应用开发 / 全栈

### 📖 参考答案

#### 一、Transformer 为什么重要？

Transformer 是所有大模型（GPT、LLaMA、Qwen、DeepSeek 等）的共同底座。作为后端工程师，理解 Transformer 能帮你回答这些实际问题：

- Token 怎么计费的？
- 上下文窗口为什么有上限？
- 为什么长对话质量越来越差？
- Prompt 结构化为什么比大段文字效果好？

```
Transformer 整体架构：

输出序列
    ↑
┌─────────────────────┐
│  Softmax            │
│      ↑              │
│  Linear             │
│      ↑              │
│  Add & Norm         │  ← 残差连接 + 层归一化
│      ↑              │
│  Feed Forward       │  ← 前馈神经网络 (FFN)
│      ↑              │
│  Add & Norm         │
│      ↑              │
│  Multi-Head         │  ← 多头注意力机制（核心）
│  Attention          │
│      ↑              │
│  Positional         │  ← 位置编码
│  Encoding           │
│      ↑              │
│  Input Embedding    │  ← 词嵌入
│      ↑              │
输入序列
└─────────────────────┘
```

#### 二、Self-Attention（自注意力机制）—— Transformer 的灵魂

**一句话总结：** Attention 就是"加权求和"——对输入序列中的每个位置，根据与其他位置的"相关性"分配不同的权重，然后做加权聚合。

**数学公式：**

```
Attention(Q, K, V) = softmax(Q × K^T / √d_k) × V

其中：
Q (Query)     = 查询向量 —— "我在找什么？"
K (Key)       = 键向量   —— "我有什么信息？"
V (Value)     = 值向量   —— "我实际提供的内容？"
d_k           = 向量维度  —— 缩放因子，防止内积过大
√d_k          = 缩放因子
```

**计算过程（三步）：**

```
Step 1: 计算相似度得分
  每个 Token 的 Q 与所有 Token 的 K 做点积
  → 得到一个注意力分数矩阵
  → 分数越高，表示两个 Token 越相关

  "我"的 Q × "爱"的 K = 0.8（高相关）
  "我"的 Q × "苹果"的 K = 0.3（低相关）

Step 2: Softmax 归一化
  对每行的注意力分数做 softmax
  → 将分数转换为概率分布（和为1）
  → 概率高的位置获得更多"注意力"

Step 3: 加权求和
  用 softmax 后的权重对 V 做加权求和
  → 每个位置的输出 = 所有位置 V 的加权和
  → 权重由注意力分数决定
```

**为什么 Self-Attention 比 RNN 强？**

| 对比项 | RNN/LSTM | Self-Attention |
|--------|---------|---------------|
| 并行计算 | 必须串行（依赖上一时刻输出） | **完全并行** |
| 长距离依赖 | 路径长度 = 序列长度（信息衰减） | 路径长度 = **O(1)**（直接对话） |
| 计算复杂度 | O(n) | O(n²)（但可并行） |
| 长文本效果 | 差（梯度消失/爆炸） | **好**（全局视野） |

#### 三、Multi-Head Attention（多头注意力）

**为什么需要多头？** 单一注意力只能捕获一种"关系模式"，多头注意力让模型从**不同子空间**同时学习多种关系。

```
单头注意力：
  只关注"语法关系"（主语→谓语）

多头注意力（8个头）：
  头1：关注语法关系
  头2：关注语义相似性
  头3：关注位置距离
  头4：关注指代关系（"它"指代什么）
  ...
  头8：关注其他模式

最终将 8 个头的输出拼接起来，再经过线性变换。
```

**计算过程：**
```python
# 伪代码：多头注意力
def multi_head_attention(Q, K, V, num_heads=8):
    d_model = Q.shape[-1]
    d_k = d_model // num_heads  # 每个头的维度
    
    # 1. 将 Q/K/V 拆分为 num_heads 个
    Q = split_into_heads(Q, num_heads)  # [batch, heads, seq_len, d_k]
    K = split_into_heads(K, num_heads)
    V = split_into_heads(V, num_heads)
    
    # 2. 每个头独立计算 Self-Attention
    heads_output = []
    for i in range(num_heads):
        head_out = scaled_dot_product_attention(Q[i], K[i], V[i])
        heads_output.append(head_out)
    
    # 3. 拼接所有头的输出
    concat = concatenate(heads_output)  # [batch, seq_len, d_model]
    
    # 4. 线性变换
    output = linear(concat)
    return output
```

#### 四、Positional Encoding（位置编码）

**问题：** Self-Attention 本身是**位置无关**的——"我爱你"和"你爱我"在 Attention 看来是一样的，因为所有 Token 同时输入。

**解决方案：** 在输入 Embedding 中加入位置编码，让模型知道 Token 的顺序。

```
位置编码公式（正弦/余弦函数）：

PE(pos, 2i)   = sin(pos / 10000^(2i/d_model))
PE(pos, 2i+1) = cos(pos / 10000^(2i/d_model))

其中：
pos = Token 在序列中的位置
i   = 维度索引
d_model = 模型维度

为什么用正余弦？
- 有界性：值在 [-1, 1] 之间，易于训练
- 相对位置：PE(pos+k) 可以表示为 PE(pos) 的线性函数
  → 模型可以学习到"相对位置"关系
```

**可视化理解：**
```
位置 0: [sin(0), cos(0), sin(0), cos(0), ...]
位置 1: [sin(1), cos(1/100), sin(1/10000), ...]
位置 2: [sin(2), cos(2/100), sin(2/10000), ...]

不同维度的正余弦波频率不同：
- 低维度（i 小）：频率高，区分相邻位置
- 高维度（i 大）：频率低，区分远距离位置
```

#### 五、后端开发者面试答题要点

```
"Transformer 的核心是 Self-Attention 机制，
它通过 Q/K/V 三个矩阵计算序列中每个位置之间的相关性，
实现全局信息的并行捕获。

三个关键设计：

1. 缩放点积注意力（Scaled Dot-Product Attention）：
   softmax(QK^T/√d_k)V，用 √d_k 缩放防止 softmax 梯度消失

2. 多头注意力（Multi-Head Attention）：
   8-16 个头并行学习不同维度的关系模式，
   拼接后线性变换，增强模型表达能力

3. 位置编码（Positional Encoding）：
   用正余弦函数给每个 Token 注入位置信息，
   弥补 Self-Attention 位置无关的缺陷

理解这些能帮助我更好地使用大模型 API——
比如知道上下文窗口限制来源于 Self-Attention 的 O(n²) 计算复杂度，
以及为什么结构化的 Prompt 效果更好。"
```

### 💡 延伸思考
1. **为什么 GPT 只用 Decoder 不用 Encoder？** — GPT 是自回归模型，Decoder-only 架构天然适合文本生成。Decoder 中的 Masked Self-Attention 保证了生成时只能看到当前位置之前的 Token，符合因果规律。
2. **KV Cache 是什么？** — 推理时缓存历史 Token 的 K 和 V 矩阵，避免重复计算，是加速大模型推理的核心优化手段。但 KV Cache 会随序列长度线性增长，这就是长对话占用更多显存的原因。

## 题目 3：[数据库/MySQL] MySQL InnoDB 为什么选择 B+ 树作为索引结构？B+ 树与 B 树、红黑树的对比，聚簇索引与非聚簇索引的区别

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-13 日报 — "JVM调优、并发编程、MySQL索引全面场景化" + "索引优化是面试核心"
**相关岗位**：Java后端 / 全栈 / DBA

### 📖 参考答案

#### 一、为什么不用其他数据结构？

```
各数据结构在 MySQL 索引场景下的对比：

                    ┌─────────────────────┐
                    │   可用的索引结构      │
                    └──────────┬──────────┘
                               │
              ┌───────────────┬┴┬──────────────┐
              ▼               ▼ ▼              ▼
          哈希表          二叉树/红黑树        B+树
         ❌ 不支持        ❌ 树太高          ✅ 最优选
         范围查询         磁盘 IO 多

哈希表被淘汰的原因：
  - 只能等值查询（=），不支持范围查询（>、<、BETWEEN）
  - 不支持 ORDER BY 排序
  - 不支持联合索引的最左前缀匹配

红黑树被淘汰的原因：
  - 树高约 log₂(n)，1000 万数据 ≈ 24 层
  - 每次查找需要 24 次磁盘 IO（每次 IO ≈ 10ms）
  - 总耗时 ≈ 240ms，太慢

B+ 树的优势：
  - 树高仅 3-4 层（1000 万数据）
  - 每次查找仅 3-4 次磁盘 IO
  - 总耗时 ≈ 30-40ms
  - 叶子节点有序链表，支持高效范围查询
```

#### 二、B+ 树 vs B 树：核心差异

```
B 树：
┌─────────────┐
│  [键1][键2]  │  ← 非叶子节点也存数据
│   /    |    \ │
└─────────────┘

B+ 树：
┌─────────────┐
│  [键1][键2]  │  ← 非叶子节点只存键（不存数据）
│   /    |    \ │
└─────────────┘
      ...  → 所有数据都在叶子节点
┌───────────────────────────────────────┐
│ [键1][数据] → [键2][数据] → [键3][数据]│ ← 叶子节点有序链表
└───────────────────────────────────────┘
```

| 对比维度 | B 树 | B+ 树（InnoDB 使用） |
|---------|------|-------------------|
| 数据存储 | 非叶子节点也存数据 | **非叶子节点只存键**，所有数据在叶子节点 |
| 节点容量 | 小（每个节点存键+数据） | **大**（只存键，单个节点可存更多键） |
| 树高 | 较高 | **更低**（相同数据量，树更矮） |
| 范围查询 | 需要中序遍历（多次回溯） | **叶子节点链表遍历**（O(1) 定位后顺序扫描） |
| 磁盘 IO | 多 | **少**（树矮 + 非叶子节点一次读入更多） |

**B+ 树的两个核心优势：**

1. **非叶子节点只存键 → 节点容量更大 → 树更矮**
   ```
   MySQL 默认页大小 = 16KB
   假设键（bigint）= 8B，指针 = 6B
   每个非叶子节点可存：16KB / 14B ≈ 1170 个键
   
   3 层 B+ 树的存储能力：
   第 1 层：1170 个键
   第 2 层：1170 × 1170 ≈ 137 万个键
   第 3 层（叶子）：137万 × 1170 ≈ 16 亿条数据
   
   → 16 亿数据仅需 3 次磁盘 IO！
   ```

2. **叶子节点有序链表 → 范围查询极快**
   ```sql
   -- 范围查询：只需定位到起始位置，然后顺序遍历链表
   SELECT * FROM user WHERE id BETWEEN 100 AND 200;
   
   -- B+ 树：一次二分查找定位到 id=100，然后沿着链表读 100 条
   -- B 树：需要中序遍历，在非叶子节点间来回跳转
   -- 哈希表：无法做范围查询
   ```

#### 三、聚簇索引（Clustered Index）vs 非聚簇索引（Secondary Index）

**聚簇索引（主键索引）：**

```
聚簇索引的叶子节点 = 整行数据

┌─────────────────────────────────────┐
│ InnoDB 聚簇索引                      │
│                                     │
│  非叶子节点：                        │
│    [1] [4] [7] [10] ... (只存主键)   │
│            ↓                         │
│  叶子节点：                          │
│    [1][完整行数据] → [2][完整行数据]  │
│    → [3][完整行数据] → ...           │
│                                     │
│ 特点：数据物理存储顺序 = 主键顺序     │
│ 每个表只能有一个聚簇索引              │
└─────────────────────────────────────┘
```

**非聚簇索引（二级索引/辅助索引）：**

```
二级索引的叶子节点 = 主键值（不是整行数据）

┌─────────────────────────────────────┐
│ 二级索引（如 name 索引）              │
│                                     │
│  非叶子节点：                        │
│    ['Alice'] ['Bob'] ['Charlie']     │
│            ↓                         │
│  叶子节点：                          │
│    ['Alice' → id=1]                  │
│    ['Bob' → id=3]                    │
│    ['Charlie' → id=5]                │
│                                     │
│ 查询完整数据需要回表：                │
│  ① 二级索引找到主键 id=1             │
│  ② 聚簇索引回表查询完整行            │
└─────────────────────────────────────┘
```

**回表与覆盖索引：**

```sql
-- 表结构：user(id, name, age, email)
-- 索引：主键(id)，二级索引 idx_name(name)

-- 场景 1：回表查询
SELECT * FROM user WHERE name = 'Alice';
-- ① 从 idx_name 找到 name='Alice' 的主键 id=1
-- ② 根据 id=1 回聚簇索引查完整行 → 2 次索引查找 ✅

-- 场景 2：覆盖索引（无需回表）
SELECT name FROM user WHERE name = 'Alice';
-- ① 从 idx_name 找到 name='Alice'，name 字段直接在索引中
-- 不需要回表 → 1 次索引查找，更快 ✅

-- 场景 3：联合索引覆盖更多列
CREATE INDEX idx_name_age ON user(name, age);

SELECT name, age FROM user WHERE name = 'Alice';
-- 索引包含 name 和 age，无需回表 ✅
```

**聚簇索引 vs 非聚簇索引对比：**

| 对比维度 | 聚簇索引（主键索引） | 非聚簇索引（二级索引） |
|---------|-------------------|---------------------|
| 叶子节点内容 | **整行数据** | **主键值** |
| 每个表数量 | **1 个**（主键决定物理存储顺序） | **多个** |
| 查询速度 | 快（直接定位数据） | 慢（可能需回表） |
| 数据更新 | 插入可能导致页分裂（性能开销） | 更新索引列需维护 B+ 树 |
| 空间占用 | 数据本身，无额外空间 | 额外存储空间 |

#### 四、面试答题模板

```
"MySQL InnoDB 选择 B+ 树的核心原因有 4 点：

1. 树矮：非叶子节点只存键不存数据，16KB 一页可存约 1170 个键，
   3 层 B+ 树就能支撑 16 亿数据，查询只需 3-4 次磁盘 IO

2. 范围查询高效：叶子节点通过双向链表连接，
   找到起始位置后顺序遍历即可，时间复杂度 O(log n) + m

3. 磁盘友好：充分利用磁盘预读（每次 IO 读一页 16KB），
   节点大小 = 磁盘页大小，读取效率最高

4. 聚簇索引设计：数据按主键顺序物理存储，
   主键查找只需一次索引就能获取完整行数据

相比之下，B 树非叶子节点存数据导致树更高、范围查询需中序遍历；
红黑树树高 log₂n 导致磁盘 IO 过多；
哈希表不支持范围查询。"
```

### 💡 延伸思考
1. **为什么建议用自增 ID 作为主键？** — 自增 ID 插入时数据追加到 B+ 树末尾，无需页分裂；UUID 作为主键会导致随机插入，频繁页分裂和碎片化，性能下降 50% 以上。
2. **1000 万数据的 B+ 树有几层？** — 假设主键为 bigint（8B），每页 16KB，每页可存约 1170 个键。1000 万数据：第 3 层叶子节点约 1000万/1170 ≈ 8547 页，第 2 层需 8547/1170 ≈ 8 页，第 1 层 1 页。**共 3 层**，查询仅需 3 次磁盘 IO。

## 题目 4：[框架/Spring] Spring @Transactional 事务失效的 12 种场景及源码级原理分析

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-13 日报 — "场景化问题全面取代记忆题" + "事务管理是 Spring 面试必考"
**相关岗位**：Java后端 / 全栈

### 📖 参考答案

#### 一、事务失效的本质原因

Spring 声明式事务基于 **AOP 代理** 实现。理解失效原因，首先要理解事务拦截器的工作流程：

```
@Transactional 的底层执行链路：

调用方调用方法
       ↓
Spring AOP 代理拦截
       ↓
TransactionInterceptor.invoke()
       ↓
判断方法是否有 @Transactional
       ↓
创建事务（获取连接、设置 autoCommit=false）
       ↓
执行业务方法（目标方法）
       ↓
   ┌── 正常返回 → 提交事务 ──┐
   └── 抛出异常 → 回滚事务 ──┘
       ↓
关闭事务资源

关键源码（TransactionAspectSupport）：
protected Object invokeWithinTransaction(Method method, ...) {
    TransactionInfo txInfo = createTransactionIfNecessary(ptm, txAttr, joinpointIdentification);
    Object retVal;
    try {
        retVal = invocation.proceedWithInvocation();  // 执行目标方法
    } catch (Throwable ex) {
        completeTransactionAfterThrowing(txInfo, ex);  // 异常回滚
        throw ex;
    } finally {
        cleanupTransactionInfo(txInfo);
    }
    commitTransactionAfterReturning(txInfo);  // 正常提交
    return retVal;
}
```

**所有事务失效场景，本质上都是 AOP 代理无法正确拦截方法调用或异常。**

#### 二、12 种事务失效场景详解

##### 场景 1-3：访问权限问题（最常见）

```java
@Service
public class UserService {

    // ❌ 场景 1：private 方法 —— 事务完全失效
    @Transactional
    private void privateMethod() {
        // Spring 只拦截 public 方法
        // 源码：AbstractFallbackTransactionAttributeSource
        // if (!Modifier.isPublic(method.getModifiers())) return null;
    }

    // ❌ 场景 2：protected/默认方法 —— 同样失效
    @Transactional
    protected void protectedMethod() { }

    // ❌ 场景 3：final 方法 —— CGLIB 无法重写，事务失效
    @Transactional
    public final void finalMethod() { }
}
```

**源码分析：**
```java
// AbstractFallbackTransactionAttributeSource
protected TransactionAttribute computeTransactionAttribute(
        Method method, Class<?> targetClass) {
    // 非 public 方法直接返回 null —— 事务注解被忽略
    if (allowPublicMethodsOnly() && !Modifier.isPublic(method.getModifiers())) {
        return null;
    }
    // ...
}
```

##### 场景 4-5：方法内部自调用（最隐蔽）

```java
@Service
public class OrderService {

    // ❌ 场景 4：同类中普通方法调用 @Transactional 方法
    public void placeOrder(Order order) {
        saveOrder(order);  // 直接调用——绕过 AOP 代理
    }

    @Transactional
    public void saveOrder(Order order) {
        orderDao.insert(order);
        inventoryDao.deduct(order.getProductId());
    }

    // ✅ 正确做法：注入自身代理
    @Autowired
    private OrderService self;  // 注入代理对象

    public void placeOrderFixed(Order order) {
        self.saveOrder(order);  // 通过代理调用——事务生效
    }

    // ❌ 场景 5：this 调用
    public void placeOrderWrong(Order order) {
        this.saveOrder(order);  // this 是原始对象，不是代理
    }
}
```

**原理图解：**
```
容器中的代理对象 vs 原始对象：

容器注入 → OrderService$$EnhancerByCGLIB（代理对象）
              ↓ 方法调用
           TransactionInterceptor（事务拦截） ← 有事务
              ↓
           OrderService（原始对象，真实业务逻辑）
              ↓ this.method()  ← this 是原始对象，无事务

关键点：只有通过"代理对象"调用方法，事务才生效
       同类内部方法调用使用的是 this（原始对象），直接绕过代理
```

##### 场景 6：异常类型不对（受检异常不回滚）

```java
// ❌ 场景 6：抛出受检异常（Exception），默认不回滚
@Transactional
public void createOrder(Order order) throws Exception {
    orderDao.insert(order);
    if (order.getAmount() > 10000) {
        throw new Exception("金额超限");  // 受检异常 → 事务不回滚！
    }
}

// 原理：Spring 默认只回滚 RuntimeException 和 Error
// 源码：DefaultTransactionAttribute
// public boolean rollbackOn(Throwable ex) {
//     return (ex instanceof RuntimeException || ex instanceof Error);
// }

// ✅ 正确做法：指定回滚异常
@Transactional(rollbackFor = Exception.class)
public void createOrderFixed(Order order) throws Exception {
    orderDao.insert(order);
    if (order.getAmount() > 10000) {
        throw new Exception("金额超限");  // 现在会回滚
    }
}
```

##### 场景 7：try-catch 吞掉异常

```java
// ❌ 场景 7：catch 了异常没抛出
@Transactional
public void createOrder(Order order) {
    try {
        orderDao.insert(order);
        inventoryDao.deduct(order.getProductId());
    } catch (Exception e) {
        log.error("创建订单失败", e);
        // 异常被捕获，事务拦截器不知道有异常 → 不会回滚
    }
}

// ✅ 正确做法：catch 后重新抛出
@Transactional
public void createOrderFixed(Order order) {
    try {
        orderDao.insert(order);
        inventoryDao.deduct(order.getProductId());
    } catch (Exception e) {
        log.error("创建订单失败", e);
        throw new RuntimeException("订单创建失败", e);  // 重新抛出
    }
}
```

##### 场景 8：数据库引擎不支持事务

```sql
-- ❌ MyISAM 引擎不支持事务
CREATE TABLE `order` (
    id BIGINT PRIMARY KEY,
    amount DECIMAL(10,2)
) ENGINE=MyISAM;  -- MyISAM 不支持事务

-- ✅ InnoDB 支持事务
CREATE TABLE `order` (
    id BIGINT PRIMARY KEY,
    amount DECIMAL(10,2)
) ENGINE=InnoDB;  -- InnoDB 支持事务
```

##### 场景 9：@Transactional 注解在非 Spring 管理的类上

```java
// ❌ 没有 @Service/@Component 等注解，Spring 不管理
public class NotABean {
    @Transactional
    public void method() { }  // 没有代理 → 事务不生效
}
```

##### 场景 10：传播行为配置不当

```java
// ❌ REQUIRES_NEW 在嵌套事务中的问题
@Service
public class OrderService {

    @Autowired
    private LogService logService;

    @Transactional
    public void createOrder(Order order) {
        orderDao.insert(order);
        logService.saveLog(order);  // 子事务独立提交
        throw new RuntimeException("订单失败");  // 主事务回滚
        // logService.saveLog 已独立提交，不会回滚！
    }
}

@Service
public class LogService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveLog(Order order) {
        logDao.insert(order.getId(), "创建订单");
    }
}
```

##### 场景 11：多数据源事务未配置正确的 PlatformTransactionManager

```java
// ❌ 多数据源下默认使用第一个 TransactionManager
@Transactional  // 不知道用哪个数据源的事务管理器
public void crossDataSource() {
    orderDao.insert(order);     // 数据源 1
    userDao.update(user);       // 数据源 2（可能不在同一事务）
}

// ✅ 指定事务管理器
@Transactional("orderTransactionManager")
public void crossDataSource() { }
```

##### 场景 12：AOP 代理方式导致的问题

```java
// ❌ JDK 动态代理：接口方法才被代理
// 如果类没有实现接口，Spring 默认用 JDK 代理
// → 非接口方法上的 @Transactional 失效

// ✅ 强制使用 CGLIB
@SpringBootApplication
@EnableTransactionManagement(proxyTargetClass = true)  // 强制 CGLIB
public class Application { }
```

|:----:|---------|---------|---------|

| 2 | protected/默认方法 | 同上 | 改为 public |

1. **@Transactional 和 @Async 一起用时有什么坑？** — @Async 会创建新的代理，事务上下文无法传递到异步线程。解决方案：将异步方法和事务方法分离到不同 Bean。
2. **编程式事务（TransactionTemplate）和声明式事务（@Transactional）怎么选？** — 声明式事务适合绝大多数场景；编程式事务适用于需要细粒度事务控制（如事务中部分操作不回滚）的场景。

## 题目 5：[JVM调优] 生产环境 JVM GC 调优全流程：GC 日志分析方法论、G1 与 ZGC 选型对比及核心参数优化

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-13 日报 — "JVM调优、并发编程、MySQL索引全面场景化" + "三大必考板块"
**相关岗位**：Java后端 / 全栈 / SRE

### 📖 参考答案

#### 一、GC 调优的核心目标

GC 调优不是为了"消除 GC"，而是要在**吞吐量、延迟、内存占用**三者之间找到最佳平衡。

```
不可能三角（无法同时优化全部三项）：

          低延迟（STW 时间短）
              /\
             /  \
            /    \
           /______\
   高吞吐量        小内存占用
（GC 时间占比低）  （堆空间小）

- 追求低延迟 → ZGC（<10ms STW，但吞吐量略低）
- 追求高吞吐 → Parallel GC（吞吐量最高，但 STW 长）
- 追求小内存 → G1（可预测停顿 + 中等内存）
```

**调优的底线标准：**
| 指标 | 健康值 | 警戒值 | 危险值 |
|------|--------|--------|--------|
| Young GC 频率 | 10-60秒/次 | <5秒/次 | <1秒/次 |
| Full GC 频率 | 0次/天 | <1次/小时 | 持续 Full GC |
| GC 停顿时间 | <100ms | 200-500ms | >1秒 |
| GC 吞吐量 | >99% | 95-99% | <95% |
| 堆内存使用率 | 稳定在 60-80% | 持续增长 >80% | 持续增长 >95% |

#### 二、GC 日志分析方法论

**第一步：开启 GC 日志**

```bash
# JDK 8 格式
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/app/logs/gc.log

# JDK 17 统一日志格式（推荐）
-Xlog:gc*:file=/app/logs/gc.log:time,uptime,level,tags
-Xlog:gc+heap=debug:file=/app/logs/gc-heap.log:time,uptime
-Xlog:safepoint:file=/app/logs/safepoint.log:time,uptime
```

**第二步：分析 GC 日志**

```bash
# 使用 GCeasy（在线，推荐）或 GCViewer（本地）

# 关键指标解读
[2026-07-13T10:30:00.123+0800] [gc,start] GC(42) Pause Young (G1 Evacuation Pause)
  [2026-07-13T10:30:00.145+0800] [gc,heap] GC(42) Eden: 512.0M->0.0B(512.0M)
  [2026-07-13T10:30:00.145+0800] [gc,heap] GC(42) Survivor: 64.0M->16.0M(64.0M)
  [2026-07-13T10:30:00.145+0800] [gc,heap] GC(42) Old: 1024.0M->1040.0M(2048.0M)
  [2026-07-13T10:30:00.145+0800] [gc,metaspace] GC(42) Metaspace: 128.0M->128.0M(256.0M)
  [2026-07-13T10:30:00.145+0800] [gc,stats] GC(42) Pause Time: 22.0ms
```

**分析要点：**

```
异常模式 1：Young GC 过于频繁（<5秒/次）
  → 原因：Eden 区太小
  → 解决：增大 -Xmn 或调整 -XX:G1NewSizePercent

异常模式 2：Old 区持续增长，Full GC 频繁
  → 原因：对象晋升过快或内存泄漏
  → 解决：检查晋升阈值、排查泄漏

异常模式 3：GC 停顿时间过长（>500ms）
  → 原因：G1 的 Mixed GC 处理太多 Region
  → 解决：降低 -XX:G1MixedGCLiveThresholdPercent

异常模式 4：Metaspace 持续增长
  → 原因：动态类加载（CGLIB、热部署）
  → 解决：设置 -XX:MaxMetaspaceSize 上限
```

#### 三、G1 垃圾回收器详解（JDK 17 默认）

**G1 设计思想：将堆划分为 2048 个 Region，每次只回收部分 Region 来控制停顿时间。**

```
G1 堆结构：

┌────┬────┬────┬────┬────┬────┬────┬────┐
│  E │  E │  E │  E │  E │  E │  O │  O │  ← 每个格子是一个 Region
├────┼────┼────┼────┼────┼────┼────┼────┤     (1-32MB，共 2048 个)
│  O │  O │  O │  O │  H │  H │  S │  S │
├────┼────┼────┼────┼────┼────┼────┼────┤
│  E │  E │  E │  E │  O │  O │  O │  O │  E = Eden
├────┼────┼────┼────┼────┼────┼────┼────┤  O = Old
│  O │  O │  O │  O │  O │  O │  H │  H │  S = Survivor
└────┴────┴────┴────┴────┴────┴────┴────┘  H = Humongous(大对象)
```

**G1 回收过程：**
```
Young GC（只回收 Eden Region）：
  → 将存活对象复制到 Survivor 或 Old
  → STW 时间短（目标 < 200ms）

Mixed GC（回收部分 Old Region + Young）：
  → 根据停顿预测模型选择"性价比最高"的 Region
  → 优先回收垃圾最多的 Region（Garbage First 得名）
  → 通过 -XX:MaxGCPauseMillis 控制目标停顿时间

Full GC（Serial Old，单线程）：
  → G1 的兜底，发生说明调优有问题
  → 应尽量避免
```

**G1 核心参数：**
```bash
# G1 推荐配置（4C8G 服务）
-Xmx4g -Xms4g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200          # 目标停顿时间（默认 200ms）
-XX:ParallelGCThreads=4           # 并行 GC 线程数 = CPU 核数
-XX:ConcGCThreads=2               # 并发 GC 线程数 = ParallelGCThreads * 0.25
-XX:G1HeapRegionSize=4m           # Region 大小（1-32MB，大堆用大 Region）
-XX:G1NewSizePercent=5            # 新生代初始占比（默认 5%）
-XX:G1MaxNewSizePercent=60        # 新生代最大占比（默认 60%）
-XX:G1MixedGCLiveThresholdPercent=85  # Mixed GC 存活对象阈值
-XX:G1HeapWastePercent=5          # 可浪费堆百分比，触发 Mixed GC
```

#### 四、ZGC 垃圾回收器详解（JDK 17 正式支持）

**ZGC 设计目标：<10ms 停顿，且不随堆大小增长。**

```
ZGC 三大核心技术：

1. 染色指针（Colored Pointer）
   ┌────────────────────────────────────────────┐
   │ 64 位指针中的 4 位用于标志：                │
   │ bit 0-41: 对象地址（42 位，最大 4TB 堆）   │
   │ bit 42: Finalizable 标记                   │
   │ bit 43: Remapped 标记                      │
   │ bit 44: Marked1 标记                       │
   │ bit 45: Marked0 标记                       │
   │ bit 46-63: 保留                           │
   └────────────────────────────────────────────┘
   好处：无需对象头中的 GC 标记位，无需写屏障

2. 读屏障（Load Barrier）
   每次从堆中读取引用时，检查指针的染色位
   如果指向"旧地址"，通过读屏障修正（非常快）

3. 内存重定位（Relocation）
   并发进行，不暂停应用线程
   ZGC 先分配新 Region，再通过读屏障逐步修复引用
```

**ZGC 核心参数：**
```bash

-Xmx16g -Xms16g
-XX:+UseZGC
-XX:ParallelGCThreads=8
-XX:ConcGCThreads=3
-XX:ZCollectionInterval=120       # 强制 GC 间隔（秒）
-XX:ZAllocationSpikeTolerance=2.0 # 分配抖动容忍度
```

#### 五、G1 vs ZGC 选型决策

| 对比维度 | G1 | ZGC |
|---------|:---:|:---:|
| **JDK 版本** | JDK 9+（JDK 17 默认） | JDK 15+ 正式（JDK 21 分代） |
| **目标停顿** | 100-200ms | **<10ms** |
| **停顿与堆大小** | 随堆大小增长 | **不随堆大小增长** |
| **吞吐量** | **高** | 略低于 G1（读屏障开销） |
| **堆内存范围** | 4GB-64GB 最佳 | 8GB-4TB |
| **适用场景** | 通用微服务、中等堆 | 大堆、低延迟敏感 |
| **配置复杂度** | 参数较多 | 参数少（几乎 auto-tuned） |

**选型建议：**
```
堆大小 < 4GB：Parallel GC（吞吐量最高）
堆大小 4-16GB，停顿容忍 <200ms：G1（默认，最省心）
堆大小 >16GB，停顿要求 <10ms：ZGC（大堆低延迟）
堆大小 <4GB，但要求低延迟：ZGC（也可）
Serverless/冷启动敏感：ZGC（并发，预热快）
```

### 💡 延伸思考
1. **JDK 21 的分代 ZGC 解决了什么问题？** — 早期的 ZGC 不区分新生代和老年代，每次都要扫描整个堆。分代 ZGC 将堆分为年轻代和老年代，Young ZGC 只扫描年轻代区域，吞吐量提升 30-50%，同时保持了亚毫秒级停顿。
2. **OOM 和 GC 调优的关系是什么？** — OOM 不一定需要通过 GC 调优解决。如果是内存泄漏，GC 调优只是"治标不治本"；如果是内存不足，增大堆或优化对象大小才是正解。GC 调优的核心是"在有限的内存下，让 GC 停顿时间满足 SLA"。
