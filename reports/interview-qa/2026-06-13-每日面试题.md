**一、ThreadLocal 是什么？——线程级别的"私人储物柜"**

ThreadLocal 提供线程局部变量，每个线程拥有自己独立的变量副本，线程之间互不干扰。典型应用场景：数据库连接管理（每个线程持有自己的 Connection）、事务上下文传递、用户 Session 管理、链路追踪（TraceId）。

```java
// ThreadLocal 基本使用
public class RequestContext {
    private static final ThreadLocal<String> traceId = new ThreadLocal<>();
    private static final ThreadLocal<Long> userId = new ThreadLocal<>();
    
    public static void setTraceId(String id) { traceId.set(id); }
    public static String getTraceId() { return traceId.get(); }
    public static void clear() { 
        traceId.remove();  // ⚠️ 必须 remove，否则内存泄漏！
        userId.remove();
    }
}
```

**二、ThreadLocal 的数据结构——ThreadLocalMap**

每个 Thread 对象内部维护一个 `ThreadLocalMap`，这是 ThreadLocal 的静态内部类，是真正的数据存储容器。

```
ThreadLocal 的存储架构：

  Thread-1                         Thread-2
  ┌──────────────────┐            ┌──────────────────┐
  │ threadLocals     │            │ threadLocals     │
  │ (ThreadLocalMap) │            │ (ThreadLocalMap) │
  │                  │            │                  │
  │ ┌──────────────┐ │            │ ┌──────────────┐ │
  │ │ Entry[0]     │ │            │ │ Entry[0]     │ │
  │ │ Entry[1]     │ │            │ │ Entry[1]     │ │
  │ │ Entry[2] ────┼─┼──┐         │ │ Entry[2]     │ │
  │ │ ...          │ │  │         │ │ ...          │ │
  │ └──────────────┘ │  │         │ └──────────────┘ │
  └──────────────────┘  │         └──────────────────┘
                         │
          ┌──────────────┘
          ▼
    ┌─────────────────────────┐
    │ Entry (WeakReference)   │
    │  key → ThreadLocal@123  │  ← 弱引用！GC 时可能被回收
    │  value → "trace-abc"    │  ← 强引用！不会被自动回收
    └─────────────────────────┘
```

```java
// ThreadLocalMap 的核心结构
static class ThreadLocalMap {
    
    // Entry 继承 WeakReference，key 是弱引用
    static class Entry extends WeakReference<ThreadLocal<?>> {
        Object value;  // value 是强引用！
        Entry(ThreadLocal<?> k, Object v) {
            super(k);  // key 作为弱引用
            value = v;
        }
    }
    
    private Entry[] table;        // 数组存储，初始容量 16
    private int size = 0;         // 实际元素数量
    private int threshold;        // 扩容阈值（容量的 2/3）
}
```

**三、Hash 算法——0x61c88647 的魔法**

ThreadLocalMap 使用一个特殊的 Hash 增量：`0x61c88647`（斐波那契黄金分割数），让 Hash 分布极其均匀。

```java
// ThreadLocal 的 Hash 计算
private final int threadLocalHashCode = nextHashCode();
private static AtomicInteger nextHashCode = new AtomicInteger();
private static final int HASH_INCREMENT = 0x61c88647;

private static int nextHashCode() {
    return nextHashCode.getAndAdd(HASH_INCREMENT);  // 每次 + 0x61c88647
}

// 计算数组下标
int i = key.threadLocalHashCode & (table.length - 1);
```

```
为什么用 0x61c88647？

  这个数字是 2^32 * (黄金分割比) ≈ 2654435769 = 0x61c88647
  
  效果：连续创建的 ThreadLocal 对象，它们的 Hash 值在数组中
        均匀分布，相邻 ThreadLocal 的槽位间隔相等且最大。
  
  验证（容量 16）：
  ThreadLocal-1: hash & 15 = 0
  ThreadLocal-2: hash & 15 = 7
  ThreadLocal-3: hash & 15 = 14
  ThreadLocal-4: hash & 15 = 5
  ...完美均匀分布！
```

**四、线性探测法解决 Hash 冲突**

与 HashMap 的"链表+红黑树"不同，ThreadLocalMap 使用**线性探测法**（开放地址法）解决冲突。

```
线性探测法：

  如果计算出的槽位 i 已被占用：
  ① 检查 i+1 位置
  ② 如果还被占用，继续 i+2, i+3...
  ③ 直到找到空槽位（Entry 为 null）或遇到 key 相同的 Entry

  与 HashMap 的区别：
  ┌──────────────┬──────────────────┬──────────────────┐
  │    特性       │    HashMap       │  ThreadLocalMap  │
  ├──────────────┼──────────────────┼──────────────────┤
  │ 冲突解决      │ 链表 + 红黑树     │ 线性探测          │
  │ Key 引用      │ 强引用           │ 弱引用            │
  │ 扩容阈值      │ 0.75             │ 2/3              │
  │ 过期清理      │ 无               │ 探测式 + 启发式    │
  └──────────────┴──────────────────┴──────────────────┘
```

**五、set() 方法的完整流程**

```java
// ThreadLocal.set() → ThreadLocalMap.set()
private void set(ThreadLocal<?> key, Object value) {
    Entry[] tab = table;
    int len = tab.length;
    int i = key.threadLocalHashCode & (len - 1);  // 计算槽位
    
    // 线性探测
    for (Entry e = tab[i]; e != null; e = tab[i = nextIndex(i, len)]) {
        ThreadLocal<?> k = e.get();
        
        if (k == key) {
            // ① key 相同 → 直接更新 value
            e.value = value;
            return;
        }
        
        if (k == null) {
            // ② key 为 null（已被 GC）→ 替换过期 Entry
            replaceStaleEntry(key, value, i);
            return;
        }
    }
    
    // ③ 找到空槽位 → 新建 Entry
    tab[i] = new Entry(key, value);
    int sz = ++size;
    
    // ④ 清理过期 Entry，如果没清掉且超过阈值 → 扩容
    if (!cleanSomeSlots(i, sz) && sz >= threshold)
        rehash();
}
```

**六、过期 Key 的清理机制**

由于 Entry 的 key 是弱引用，GC 后 key 变为 null，但 value 仍然存在。ThreadLocalMap 有两种清理机制：

```
① 探测式清理（expungeStaleEntry）：
   从指定位置开始，向后遍历直到遇到 null 槽位
   → 清除所有 key=null 的 Entry
   → 同时将未过期的 Entry 重新 Hash（因为前面的槽位被清空了）

② 启发式清理（cleanSomeSlots）：
   从指定位置开始，对数级扫描（log2(n) 次）
   → 发现过期 Entry 就触发探测式清理
   → 比全量扫描更轻量，在 set/get 时顺便执行
```

**七、ThreadLocal 内存泄漏——面试高频追问**

这是 ThreadLocal 面试题的"灵魂拷问"。

```
内存泄漏的根本原因：

  引用链：
  Thread → ThreadLocalMap → Entry(key=弱引用, value=强引用) → Value

  关键问题：
  ① ThreadLocal 对象被 GC 回收 → Entry 的 key 变成 null
  ② 但 Entry 的 value 是强引用 → 只要 Thread 还活着，value 永远不会被回收！
  ③ 线程池中的线程是复用的 → Thread 长期存活 → 内存泄漏累积

  图解：
  ┌────────┐    强引用    ┌─────────────────┐    弱引用    ┌──────────────┐
  │ Thread │ ──────────→ │ ThreadLocalMap  │ ← ─ ─ ─ ─ │ ThreadLocal  │
  └────────┘             │                 │            └──────┬───────┘
                         │  Entry[0]       │                   │
                         │   key ──────────┼───────────────────┘ (GC 后 = null)
                         │   value ────────┼──→ Object (强引用！永远不释放！)
                         └─────────────────┘

  解决方案：
  ① 每次使用完 ThreadLocal 后必须调用 remove()
  ② 在线程池场景下，在 finally 块中调用 remove()
```

```java
// ✅ 正确使用方式
public void handleRequest() {
    try {
        RequestContext.setTraceId(generateTraceId());
        // 业务逻辑...
    } finally {
        RequestContext.clear();  // 必须 remove！
    }
}

// ❌ 错误使用方式——内存泄漏
public void handleRequest() {
    RequestContext.setTraceId(generateTraceId());
    // 业务逻辑...
    // 忘记 remove() → 线程复用时 value 永远不释放！
}
```

**八、面试回答框架**

```
面试官问"ThreadLocal 原理是什么？为什么会内存泄漏？"

① 数据结构（15秒）：
   "每个 Thread 内部有一个 ThreadLocalMap，key 是 ThreadLocal 的弱引用，
    value 是存储的值。通过 ThreadLocal 的 Hash 值定位数组槽位"

② Hash 与冲突（15秒）：
   "Hash 增量是 0x61c88647（黄金分割数），分布均匀。
    冲突用线性探测法解决——向后找空槽位，不像 HashMap 用链表"

③ set/get 流程（20秒）：
   "set：计算槽位 → 线性探测 → key 相同则更新，key 为 null 则替换过期 Entry，
    空槽位则新建。过程中触发探测式/启发式清理过期 Entry。
    get：同样线性探测，遇到过期 Entry 触发清理"

④ 内存泄漏原因（25秒）：
   "Entry 的 key 是弱引用，ThreadLocal 对象被 GC 后 key 变 null，
    但 value 是强引用，只要 Thread 存活就不会被回收。
    线程池场景下 Thread 长期复用 → 内存泄漏累积。
    虽然 get/set 时会清理过期 Entry，但不能保证及时清理"

⑤ 解决方案（10秒）：
   "每次使用完必须调用 remove()，放在 finally 块中。
    阿里巴巴规范强制要求：ThreadLocal 必须 remove"
```

### 💡 延伸思考

1. **为什么 Entry 的 key 要设计成弱引用？** — 如果 key 是强引用，即使业务代码中 ThreadLocal 对象的引用已经消失，只要 Thread 还存活，ThreadLocal 对象就永远不会被 GC。弱引用让 ThreadLocal 对象可以在没有外部引用时被回收，同时通过过期清理机制处理残留的 value。这是"尽力而为"的设计——弱引用降低泄漏风险，remove() 彻底杜绝泄漏。
2. **InheritableThreadLocal 和 TransmittableThreadLocal 有什么区别？** — InheritableThreadLocal 可以让子线程继承父线程的 ThreadLocal 值（通过 Thread 构造时复制），但线程池场景下线程是复用的，不会重复复制。TransmittableThreadLocal（阿里开源）解决了线程池场景下的上下文传递问题，在线程提交任务时自动复制上下文。

**一、IoC——从"自己造轮子"到"容器给轮子"**

IoC（Inversion of Control，控制反转）是一种设计思想：将对象的创建和管理权从程序代码转移给 IoC 容器。在传统开发中，类 A 依赖类 B 时需要用 `new B()` 手动创建；使用 IoC 后，只需要声明依赖，容器负责注入。

```
传统方式 vs IoC 方式：

  传统方式：
  public class UserService {
      private UserDao userDao = new UserDaoImpl();  // 自己 new，强耦合
  }
  
  IoC 方式：
  public class UserService {
      @Autowired
      private UserDao userDao;  // 容器注入，解耦
  }
  
  控制反转的含义：
  - "控制"：对象创建和管理的权力
  - "反转"：从程序代码 → IoC 容器
```

**IoC 容器的核心接口**：

| 接口 | 说明 |
|------|------|
| **BeanFactory** | 最底层的 IoC 容器，提供基本的 DI 功能，延迟加载 |
| **ApplicationContext** | BeanFactory 的子接口，提供更多企业级功能（国际化、事件发布、资源加载），启动时预加载单例 Bean |
| **BeanDefinition** | Bean 的定义信息（类名、作用域、依赖、初始化方法等） |

**二、Bean 的完整生命周期——面试高频追问**

```
Spring Bean 生命周期（简化版）：

  ① 实例化（Instantiation）
     通过反射调用构造方法创建 Bean 实例
     
  ② 属性填充（Populate Properties）
     注入 @Autowired、@Value 标注的依赖
     
  ③ Aware 回调
     BeanNameAware → BeanFactoryAware → ApplicationContextAware
     
  ④ BeanPostProcessor 前置处理
     postProcessBeforeInitialization()
     
  ⑤ 初始化（Initialization）
     @PostConstruct → InitializingBean.afterPropertiesSet() → init-method
     
  ⑥ BeanPostProcessor 后置处理
     postProcessAfterInitialization()（AOP 代理在这里生成！）
     
  ⑦ Bean 就绪，可以使用
     
  ⑧ 销毁（Destruction）
     @PreDestroy → DisposableBean.destroy() → destroy-method
```

```
关键面试点：

  Q: AOP 代理在哪个阶段生成？
  A: BeanPostProcessor 的 postProcessAfterInitialization() 阶段。
     AbstractAutoProxyCreator 在此阶段判断是否需要创建代理对象。

  Q: 为什么 @PostConstruct 在属性填充之后？
  A: 因为 @PostConstruct 方法中可能需要使用注入的依赖。
     如果依赖还没注入就执行初始化，会 NPE。

  Q: 三级缓存解决循环依赖，是哪三级？
  A: ① singletonObjects（一级，成品 Bean）
     ② earlySingletonObjects（二级，半成品 Bean 的代理）
     ③ singletonFactories（三级，ObjectFactory，可生成半成品 Bean）
```

**三、依赖注入的三种方式——优劣对比**

| 注入方式 | 示例 | 优点 | 缺点 |
|---------|------|------|------|
| **构造器注入** | `public UserService(UserDao dao)` | 不可变、依赖明确、易于测试 | 参数多时代码冗长 |
| **Setter 注入** | `setUserDao(UserDao dao)` | 可选依赖、可重新配置 | 对象可能处于不完整状态 |
| **字段注入** | `@Autowired private UserDao dao` | 代码最简洁 | 难以测试（需要反射）、隐藏依赖、违反单一职责 |

```
Spring 官方推荐：构造器注入（Constructor Injection）

  原因：
  ① 依赖不可变（final 字段）
  ② 依赖不为 null（构造时检查）
  ③ 完全初始化（构造完成即可用）
  ④ 单元测试友好（不需要 Spring 容器）

  字段注入的问题：
  - 依赖隐藏在字段中，类有 10 个 @Autowired 字段也难以察觉
  - 单元测试必须用 @SpringBootTest 或反射注入
  - 可能导致循环依赖（构造器注入会在启动时就发现）
```

**四、AOP——面向切面编程**

AOP（Aspect Oriented Programming）将横切关注点（日志、事务、权限、缓存）从核心业务逻辑中分离，通过动态代理实现代码复用和解耦。

```
AOP 核心概念：

  ┌─────────────────────────────────────────────────────────┐
  │                    切面（Aspect）                        │
  │  ┌─────────────────────────────────────────────────┐   │
  │  │              通知（Advice）                       │   │
  │  │  @Before  @After  @Around  @AfterReturning      │   │
  │  │  @AfterThrowing                                  │   │
  │  └─────────────────────────────────────────────────┘   │
  │                         │                               │
  │                         ▼                               │
  │  ┌─────────────────────────────────────────────────┐   │
  │  │            切入点（Pointcut）                     │   │
  │  │  execution(* com.example.service.*.*(..))       │   │
  │  └─────────────────────────────────────────────────┘   │
  │                         │                               │
  │                         ▼                               │
  │  ┌─────────────────────────────────────────────────┐   │
  │  │          连接点（JoinPoint）                      │   │
  │  │  目标方法执行时的特定时刻                          │   │
  │  └─────────────────────────────────────────────────┘   │
  └─────────────────────────────────────────────────────────┘
```

**五种通知类型**：

```java
@Aspect
@Component
public class LogAspect {
    
    @Pointcut("execution(* com.example.service.*.*(..))")
    public void serviceLayer() {}
    
    // ① 前置通知：方法执行前
    @Before("serviceLayer()")
    public void before(JoinPoint joinPoint) {
        log.info("开始执行: {}", joinPoint.getSignature().getName());
    }
    
    // ② 后置通知：方法执行后（无论成功或异常）
    @After("serviceLayer()")
    public void after(JoinPoint joinPoint) {
        log.info("执行完成: {}", joinPoint.getSignature().getName());
    }
    
    // ③ 返回通知：方法正常返回后
    @AfterReturning(pointcut = "serviceLayer()", returning = "result")
    public void afterReturning(JoinPoint joinPoint, Object result) {
        log.info("返回结果: {}", result);
    }
    
    // ④ 异常通知：方法抛出异常后
    @AfterThrowing(pointcut = "serviceLayer()", throwing = "ex")
    public void afterThrowing(JoinPoint joinPoint, Exception ex) {
        log.error("执行异常: {}", ex.getMessage());
    }
    
    // ⑤ 环绕通知：包裹整个方法执行（最强大）
    @Around("serviceLayer()")
    public Object around(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            Object result = joinPoint.proceed();  // 执行目标方法
            return result;
        } finally {
            long cost = System.currentTimeMillis() - start;
            log.info("{} 耗时: {}ms", joinPoint.getSignature().getName(), cost);
        }
    }
}
```

**五、JDK 动态代理 vs CGLIB——底层实现差异**

Spring AOP 的代理方式取决于目标对象是否实现了接口：

```
JDK 动态代理（基于接口）：
  要求：目标类必须实现接口
  原理：java.lang.reflect.Proxy 生成代理类，实现相同接口
  代理对象类型：$Proxy0 extends Proxy implements UserService
  
  ┌─────────┐      ┌──────────────────┐
  │ 调用者   │────→│ $Proxy0 (代理)    │
  └─────────┘     │ implements        │
                  │ UserService       │
                  │  ┌─────────────┐  │
                  │  │ Invocation  │  │
                  │  │ Handler     │──┼──→ 通知链 → 目标方法
                  │  └─────────────┘  │
                  └──────────────────┘

CGLIB 动态代理（基于继承）：
  要求：目标类不能是 final，方法不能是 final
  原理：生成目标类的子类，重写方法
  代理对象类型：UserService$$EnhancerByCGLIB extends UserService
  
  ┌─────────┐      ┌──────────────────────────┐
  │ 调用者   │────→│ UserService$$CGLIB (代理)  │
  └─────────┘     │ extends UserService       │
                  │  ┌──────────────────────┐ │
                  │  │ MethodInterceptor    │ │
                  │  │ intercept()          │─┼─→ 通知链 → super.方法()
                  │  └──────────────────────┘ │
                  └──────────────────────────┘
```

| 对比维度 | JDK 动态代理 | CGLIB |
|---------|------------|-------|
| **机制** | 基于接口，生成实现类 | 基于继承，生成子类 |
| **要求** | 必须有接口 | 不能是 final 类/方法 |
| **性能** | 创建快，调用略慢 | 创建慢（生成字节码），调用快 |
| **限制** | 只能代理接口方法 | 不能代理 final/static 方法 |
| **Spring 默认** | Spring Boot 1.x 默认 | Spring Boot 2.0+ 默认 |

**为什么 Spring Boot 2.0+ 默认用 CGLIB？**

```
原因：
① 不需要强制面向接口编程——很多开发者直接用 @Service 类，没有接口
② 避免 ClassCastException——如果 Bean 同时需要 JDK 代理和 CGLIB 代理，
   混用会导致类型转换异常
③ CGLIB 性能持续优化——现代 CGLIB 的调用性能已经接近 JDK 代理
④ 统一代理策略——减少开发者困惑（"为什么我的 @Transactional 不生效？"）

配置：
spring.aop.proxy-target-class=true   # 默认 true（CGLIB）
spring.aop.proxy-target-class=false  # 强制 JDK 动态代理
```

### 💡 延伸思考

1. **为什么同类方法调用 @Transactional 不生效？** — Spring AOP 基于代理，外部调用 `userService.methodA()` 时走的是代理对象，代理对象在调用前后织入事务逻辑。但同类内部 `this.methodB()` 走的是原始对象，不经过代理，所以事务不生效。解决方案：① 把方法拆分到不同类；② 通过 `AopContext.currentProxy()` 获取代理对象调用；③ 使用 AspectJ 编译期织入。
2. **Spring 如何解决循环依赖？** — 三级缓存：`singletonObjects`（成品）、`earlySingletonObjects`（半成品代理）、`singletonFactories`（ObjectFactory）。A 依赖 B、B 依赖 A：先创建 A 的半成品放入三级缓存 → 发现需要 B → 创建 B → B 需要 A → 从三级缓存获取 A 的半成品 → B 完成 → A 完成。注意：构造器注入无法解决循环依赖，因为构造器调用时对象还没创建出来。

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-13 午间报告 — "腾讯后端面经：MySQL 事务隔离" + "大厂面试八股文高频题"

### 📖 参考答案

**一、事务的 ACID 特性——基础回顾**

事务是数据库操作的最小逻辑单元，具有四个基本特性：

| 特性 | 含义 | 实现机制 |
|------|------|---------|
| **原子性 (Atomicity)** | 事务要么全部成功，要么全部失败 | Undo Log（回滚日志） |
| **一致性 (Consistency)** | 事务前后数据满足完整性约束 | 由其他三个特性共同保证 |
| **隔离性 (Isolation)** | 并发事务之间互不干扰 | MVCC + 锁机制 |
| **持久性 (Durability)** | 事务提交后数据永久保存 | Redo Log（重做日志） |

**二、四种事务隔离级别——从宽松到严格**

```
隔离级别与并发问题的关系：

  ┌────────────────────┬────────┬──────────┬────────┐
  │     隔离级别         │  脏读   │ 不可重复读 │  幻读   │
  ├────────────────────┼────────┼──────────┼────────┤
  │ READ UNCOMMITTED   │   ✅   │    ✅    │   ✅   │
  │ (读未提交)          │  可能   │   可能    │  可能   │
  ├────────────────────┼────────┼──────────┼────────┤
  │ READ COMMITTED     │   ❌   │    ✅    │   ✅   │
  │ (读已提交)          │  解决   │   可能    │  可能   │
  ├────────────────────┼────────┼──────────┼────────┤
  │ REPEATABLE READ    │   ❌   │    ❌    │ ≈ ❌   │
  │ (可重复读, MySQL默认)│  解决   │   解决    │ 基本解决 │
  ├────────────────────┼────────┼──────────┼────────┤
  │ SERIALIZABLE       │   ❌   │    ❌    │   ❌   │
  │ (串行化)            │  解决   │   解决    │  解决   │
  └────────────────────┴────────┴──────────┴────────┘
```

**三种并发问题的具体含义**：

```
① 脏读（Dirty Read）：
   事务 A 读到事务 B 未提交的数据，事务 B 回滚后，A 读到的就是"脏数据"
   
   事务 A：BEGIN → 读到 age=20（事务 B 未提交的修改）→ COMMIT
   事务 B：BEGIN → UPDATE age=20 → ROLLBACK
   事务 A 读到了不存在的数据！

② 不可重复读（Non-Repeatable Read）：
   事务 A 内两次读取同一行数据，结果不同（被事务 B 的 UPDATE 修改了）
   
   事务 A：BEGIN → SELECT age=18 → ... → SELECT age=20 → COMMIT
   事务 B：          BEGIN → UPDATE age=20 → COMMIT
   同一事务内两次读结果不一致！

③ 幻读（Phantom Read）：
   事务 A 内两次范围查询，结果集行数不同（被事务 B 的 INSERT 插入了新行）
   
   事务 A：BEGIN → SELECT COUNT(*)=10 → ... → SELECT COUNT(*)=11 → COMMIT
   事务 B：          BEGIN → INSERT ... → COMMIT
   同一事务内两次查询的行数变了！
```

**三、MVCC 是什么？——多版本并发控制**

MVCC（Multi-Version Concurrency Control）是 InnoDB 实现非锁定读（快照读）的核心机制，通过维护数据的多个版本，让读操作不加锁也能看到一致的数据。

```
MVCC 的核心思想：

  写操作不覆盖原数据，而是创建新版本
  读操作根据事务开始时间，选择可见的版本
  
  → 读写不冲突！写写才冲突！
  → 这是 InnoDB 高并发的核心秘密
```

**四、MVCC 的三大核心组件**

### 组件 1：隐藏列

InnoDB 每行数据都有三个隐藏列：

```
┌──────────┬──────────┬──────────┬──────────────┬──────────────┐
│  DB_ROW_ID │ DB_TRX_ID │ DB_ROLL_PTR │  列1  │  列2  │  ...  │
│  (6字节)   │  (6字节)   │  (7字节)    │       │       │       │
└──────────┴──────────┴──────────────┴───────┴───────┴───────┘

  DB_TRX_ID（事务 ID）：最近一次修改这行数据的事务 ID
  DB_ROLL_PTR（回滚指针）：指向 Undo Log 中上一个版本的指针
  DB_ROW_ID（行 ID）：如果没有主键，InnoDB 自动生成的隐藏主键
```

### 组件 2：Undo Log 版本链

每次修改数据时，InnoDB 会将旧版本写入 Undo Log，并通过 DB_ROLL_PTR 形成版本链。

```
Undo Log 版本链示意：

  当前记录（聚簇索引中）：
  ┌──────────────────────────────────────────┐
  │ name='C' │ DB_TRX_ID=300 │ DB_ROLL_PTR ──┼──→ Undo Log
  └──────────────────────────────────────────┘         │
                                                       ▼
                                              ┌──────────────────────┐
                                              │ name='B' │ trx_id=200│──→
                                              └──────────────────────┘  │
                                                                        ▼
                                                               ┌──────────────────────┐
                                                               │ name='A' │ trx_id=100│──→ NULL
                                                               └──────────────────────┘

  版本链：当前版本(trx=300) → 历史版本(trx=200) → 历史版本(trx=100)
```

### 组件 3：ReadView——可见性判断的核心

ReadView 是事务进行快照读时产生的"数据快照"，包含四个关键信息：

```
ReadView 结构：

  ┌─────────────────────────────────────────┐
  │  m_ids：当前活跃事务 ID 集合              │
  │  min_trx_id：m_ids 中的最小值             │
  │  max_trx_id：下一个要分配的事务 ID         │
  │  creator_trx_id：创建 ReadView 的事务 ID  │
  └─────────────────────────────────────────┘
```

**可见性判断规则**：

```
对于版本链中的某个版本（DB_TRX_ID = trx_id）：

  ① trx_id == creator_trx_id
     → 可见（自己修改的当然可见）

  ② trx_id < min_trx_id
     → 可见（修改该版本的事务在 ReadView 创建前已提交）

  ③ trx_id >= max_trx_id
     → 不可见（修改该版本的事务在 ReadView 创建后才开始）

  ④ min_trx_id <= trx_id < max_trx_id
     → 如果 trx_id 在 m_ids 中 → 不可见（事务未提交）
     → 如果 trx_id 不在 m_ids 中 → 可见（事务已提交）

  如果不可见 → 沿着 DB_ROLL_PTR 找上一个版本，重复判断
```

**五、RC 和 RR 的 ReadView 生成时机——关键区别**

这是面试中最容易被追问的细节：

```
READ COMMITTED（读已提交）：
  每次 SELECT 都生成新的 ReadView
  → 能看到其他事务已提交的修改
  → 无法避免不可重复读

REPEATABLE READ（可重复读）：
  只在第一次 SELECT 时生成 ReadView，后续复用
  → 整个事务期间看到的都是同一个快照
  → 避免了不可重复读

  示例：
  事务 A（RR）：BEGIN → SELECT age=18（生成 ReadView）→ ... → SELECT age=18（复用 ReadView）
  事务 B：          BEGIN → UPDATE age=20 → COMMIT
  事务 A 第二次读到的仍然是 18！
```

**六、InnoDB RR 如何解决幻读？——MVCC + Next-Key Lock**

```
幻读的两种场景：

  ① 快照读（普通 SELECT）→ MVCC 解决
     RR 级别下，快照读使用事务开始时生成的 ReadView
     → 其他事务 INSERT 的新行，trx_id 不满足可见性规则
     → 看不到新插入的行 → 不会幻读

  ② 当前读（SELECT ... FOR UPDATE / UPDATE / DELETE）→ Next-Key Lock 解决
     当前读总是读取最新版本，MVCC 无法解决幻读
     → InnoDB 使用 Next-Key Lock（Record Lock + Gap Lock）
     → 锁定查询范围 + 间隙，防止其他事务插入新行
     → 彻底杜绝幻读
```

```sql
-- 幻读演示：RR 级别下的当前读
-- 事务 A：
BEGIN;
SELECT * FROM t WHERE id > 10 FOR UPDATE;  -- 当前读，加 Next-Key Lock
-- 事务 B：
INSERT INTO t VALUES (15, 'xxx');  -- 阻塞！被 Gap Lock 挡住
-- 事务 A 不会出现幻读
```

**七、面试回答框架**

```
面试官问"MySQL 事务隔离级别有哪些？MVCC 是怎么实现的？"

① 四种隔离级别（15秒）：
   "RU（读未提交）→ RC（读已提交，Oracle 默认）→ RR（可重复读，MySQL 默认）→
    SERIALIZABLE（串行化）。分别解决脏读、不可重复读、幻读"

② MVCC 三大组件（25秒）：
   "① 隐藏列：DB_TRX_ID（事务ID）+ DB_ROLL_PTR（回滚指针）+ DB_ROW_ID；
    ② Undo Log 版本链：每次修改记录旧版本，通过回滚指针串联；
    ③ ReadView：包含活跃事务列表，判断版本可见性"

③ 可见性判断（20秒）：
   "trx_id < min_trx_id → 可见（已提交）；
    trx_id >= max_trx_id → 不可见（未开始）；
    在中间 → 检查是否在活跃列表中。
    不可见就沿版本链往前找"

④ RC vs RR 区别（15秒）：
   "RC 每次 SELECT 生成新 ReadView → 能看到已提交的修改；
    RR 只在第一次 SELECT 生成 ReadView → 整个事务看到同一快照。
    这就是不可重复读在 RR 下被解决的原因"

⑤ 幻读解决（10秒）：
   "快照读用 MVCC 解决幻读；当前读用 Next-Key Lock（Record+Gap）解决幻读。
    两者结合，InnoDB RR 基本解决了幻读问题"
```

### 💡 延伸思考

1. **RR 级别下真的完全解决了幻读吗？** — 不完全。如果事务 A 先快照读（SELECT），事务 B 插入新行并提交，事务 A 再执行 UPDATE 更新"所有行"（包括事务 B 插入的行），然后事务 A 再 SELECT，会发现多了一行。这是因为 UPDATE 是当前读，会更新事务 B 插入的行，导致该行的 DB_TRX_ID 变成事务 A 的 ID，后续快照读就能看到了。这是 RR 级别下的一种特殊"幻读"场景。
2. **为什么 MySQL 默认 RR 而不是 RC？** — 历史原因：MySQL 5.0 之前，Binlog 只有 STATEMENT 格式，RC 级别下会导致主从数据不一致。虽然现在 Binlog 默认 ROW 格式，但 RR 作为默认值保留了下来。实际上，很多互联网公司（如美团、阿里部分业务）使用 RC + ROW 格式 Binlog，因为 RC 下没有 Gap Lock，死锁概率更低。

**二、五种基本类型的底层编码——面试核心**

```
String 的三种编码：

  ┌────────────┬──────────────────────────────────┐
```

**三、SkipList（跳表）——ZSet 的核心数据结构**

跳表是一种多层链表结构，通过"空间换时间"实现 O(logN) 的查找效率。

```
跳表结构示意：

  Level 3:  HEAD ──────────────────────→ 50 ──────────→ NULL
  Level 2:  HEAD ────────→ 20 ────────→ 50 ──────────→ NULL
  Level 1:  HEAD ──→ 10 ──→ 20 ──→ 30 ──→ 50 ──→ 60 ──→ NULL
  Level 0:  HEAD → 5 → 10 → 15 → 20 → 25 → 30 → 50 → 60 → NULL

  查找 25 的过程：
  ① 从最高层 Level 3 开始：HEAD → 50（大于 25，下降一层）
  ② Level 2：HEAD → 20（小于 25，前进）→ 50（大于 25，下降）
  ③ Level 1：20 → 30（大于 25，下降）
  ④ Level 0：20 → 25 → 找到！
  
  时间复杂度：O(logN)
  空间复杂度：O(N)（每层约是下一层的一半，总节点数 ≈ 2N）
```

**为什么 ZSet 用跳表而不用红黑树？**

| 维度 | 跳表（SkipList） | 红黑树 |
|------|-----------------|--------|
| **实现复杂度** | ⭐⭐ 简单 | ⭐⭐⭐⭐ 复杂（旋转、变色） |
| **范围查询** | ✅ 天然支持（链表遍历） | ⚠️ 需要中序遍历 |
| **并发友好** | ✅ 容易实现无锁/细粒度锁 | ❌ 旋转影响整棵树 |
| **内存占用** | 略高（多层指针） | 较低 |
| **查找性能** | O(logN) | O(logN) |

```
Redis 作者 antirez 的解释：
  "跳表实现简单，且范围查找只需要在 Level 0 链表上遍历。
   红黑树实现复杂，调试困难，范围查找需要中序遍历。
   对于 Redis 这种追求简洁和可维护性的项目，跳表是更好的选择。"
```

**四、Redis 的三种过期删除策略**

Redis 同时使用惰性删除和定期删除两种策略：

```
① 惰性删除（Lazy Expiration）：
   访问 key 时检查是否过期，过期则删除
   
   优点：CPU 友好（只在访问时检查）
   缺点：内存不友好（过期 key 如果一直不被访问，永远不删除）
   
   源码：expireIfNeeded() 在每次读写 key 时调用

② 定期删除（Active Expiration）：
   每隔 100ms（默认 hz=10）随机抽取一批 key 检查并删除过期的
   
   流程：
   ① 从过期字典中随机取 20 个 key
   ② 删除其中过期的 key
   ③ 如果过期比例 > 25%，重复步骤①（防止过期 key 堆积）
   ④ 但每次执行时间不超过 25ms（防止阻塞主线程）
   
   优点：内存友好（主动清理）
   缺点：CPU 有一定开销

③ 内存淘汰策略（Eviction Policy）：
   当内存达到 maxmemory 时，根据配置的策略淘汰 key
```

**五、8 种内存淘汰策略**

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| **noeviction** | 不淘汰，写操作报错 | 不允许数据丢失的场景 |
| **allkeys-lru** | 所有 key 中 LRU 淘汰 | **通用缓存（推荐）** |
| **volatile-lru** | 有过期时间的 key 中 LRU 淘汰 | 混合持久+缓存数据 |
| **allkeys-random** | 所有 key 中随机淘汰 | 数据访问均匀 |
| **volatile-random** | 有过期时间的 key 中随机淘汰 | 同上 |
| **volatile-ttl** | 有过期时间的 key 中 TTL 最短的淘汰 | 优先淘汰即将过期的 |
| **allkeys-lfu**（4.0+） | 所有 key 中 LFU 淘汰 | 热点数据保护 |
| **volatile-lfu**（4.0+） | 有过期时间的 key 中 LFU 淘汰 | 同上 |

```
LRU vs LFU：

  LRU（Least Recently Used）：最近最少使用
  → 淘汰最久没被访问的 key
  → 问题：一个 key 曾经被访问 1000 次，但最近 1 小时没访问，可能被淘汰

  LFU（Least Frequently Used）：最不经常使用
  → 淘汰访问频率最低的 key
  → 优势：保护热点数据，即使它最近没被访问

  Redis 的 LRU 是近似 LRU（采样淘汰，不是精确 LRU）
  → 随机采样 N 个 key（默认 5），淘汰其中最久未访问的
  → 性能远高于精确 LRU，效果接近
```

### 💡 延伸思考

1. **为什么 Redis 6.0 引入了多线程？** — Redis 6.0 的多线程只用于网络 I/O 读写，核心命令执行仍然是单线程。原因是：随着网络硬件升级，单个主线程处理网络读写成为瓶颈（特别是 10Gbps+ 网卡），而命令执行本身在内存中非常快，单线程足够。多线程网络 I/O + 单线程命令执行 = 最佳性能平衡。
2. **ZipList 的连锁更新问题是什么？** — ZipList 中每个节点存储前一个节点的长度。如果前一个节点长度从 254 变成 255（跨越 1 字节到 5 字节的阈值），后续所有节点的长度字段都要更新，可能引发连锁反应。Redis 7.0 用 ListPack 替代了 ZipList，彻底解决了这个问题。

**一、RAG 是什么？——给 LLM 装上"外挂知识库"**

RAG（Retrieval-Augmented Generation，检索增强生成）是 2026 年最主流的 LLM 应用架构。核心思想：在 LLM 生成回答之前，先从外部知识库中检索相关信息，将检索结果作为上下文注入 Prompt，让 LLM 基于"事实"生成回答。

```
为什么需要 RAG？

  LLM 的三大缺陷：
  ① 知识截止日期：训练数据有截止时间，不知道最新信息
  ② 幻觉问题：可能编造不存在的事实
  ③ 私有知识盲区：不知道企业内部文档、业务数据

  RAG 的解决方案：
  用户问题 → 检索相关文档 → 将文档作为上下文 → LLM 基于文档生成回答
  → 回答有据可查，可以溯源，可以实时更新知识库
```

```

  ┌─────────────────────────────────────────────────────────┐
  │                    离线阶段（索引构建）                    │
  │                                                         │
  │  ① 文档加载（Document Loading）                          │

  │                                                         │
  │  ③ Embedding 向量化                                     │
  │     将每个 Chunk 转换为向量（如 1536 维）                 │
  │     存入向量数据库                                       │
  └─────────────────────────────────────────────────────────┘

  │  ④ 向量检索（Vector Search）                             │
  │     用户问题 → Embedding → 在向量数据库中搜索 Top-K 相似  │
  │                                                         │
  │  ⑤ 上下文增强生成（Augmented Generation）                │
  │     检索结果 + 用户问题 → 拼接 Prompt → LLM 生成回答      │
```

```java
// 基于 Spring AI 的 RAG 实现
@RestController
public class RagController {
    
    @Autowired
    private VectorStore vectorStore;  // 向量数据库
    @Autowired
    private ChatClient chatClient;
    
    @GetMapping("/rag/ask")
    public String ask(@RequestParam String question) {
        // ① 将问题向量化并检索 Top-5 相关文档
        List<Document> docs = vectorStore.similaritySearch(
            SearchRequest.query(question).withTopK(5)
        );
        
        // ② 拼接上下文
        String context = docs.stream()
            .map(Document::getContent)
            .collect(Collectors.joining("\n\n"));
        
        // ③ 构建增强 Prompt
        String prompt = """
            基于以下参考资料回答用户问题。
            如果参考资料中没有相关信息，请如实告知。
            
            参考资料：
            %s
            
            用户问题：%s
            """.formatted(context, question);
        
        // ④ 调用 LLM 生成回答
        return chatClient.prompt().user(prompt).call().content();
    }
}
```

**三、文本切分策略——RAG 效果的"第一关"**

切分策略直接影响检索质量，是 RAG 系统中最容易被忽视但最重要的环节：

```
切分策略对比：

  ① 固定大小切分（最常用）：
     Chunk Size = 500 tokens，Overlap = 50 tokens
     ✅ 简单可靠
     ❌ 可能切断完整语义

  ② 语义切分（推荐）：
     按段落/章节/语义边界切分
     ✅ 保持语义完整
     ❌ 实现复杂，需要 NLP 模型

  ③ 递归切分：
     先用大分隔符（\n\n），不够再用小分隔符（\n，。）
     ✅ 兼顾语义和大小控制
     ❌ 仍可能切断长句

  切分原则：
  - Chunk Size：太小（<200）信息不足，太大（>2000）检索精度下降
  - Overlap：10-20%，确保边界信息不丢失
  - 保留元数据：文档来源、页码、章节标题
```


### 💡 延伸思考

1. **RAG 的"Lost in the Middle"问题是什么？** — 研究发现 LLM 对 Prompt 开头和结尾的信息关注度最高，中间部分容易被忽略。如果检索返回 10 个文档，中间的文档可能被 LLM "无视"。解决方案：① 减少检索数量（Top-3 而非 Top-10）；② 按相关性降序排列（最重要的放最前面）；③ 对长文档做摘要压缩。
2. **Graph RAG 和传统 RAG 有什么区别？** — 传统 RAG 基于向量相似度检索，适合"找相似内容"；Graph RAG 基于知识图谱，适合"找关联关系"。例如"张三的老板是谁？"传统 RAG 可能找不到，Graph RAG 通过实体关系图可以推理出来。微软的 GraphRAG 在 2026 年已成为企业级 RAG 的重要方向。
