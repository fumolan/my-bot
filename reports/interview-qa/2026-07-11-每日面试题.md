## 题目 1：[JDK新特性] JDK 17 LTS 核心新特性详解：Records、Switch 模式匹配、密封类、文本块及 String 底层优化

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-11 早间报告 — "JDK17 + SpringBoot3 + AI集成 = 新三大考点"
**相关岗位**：Java后端 / 全栈 / 基础架构

### 📖 参考答案

JDK 17 作为自 JDK 11 后的第二个 LTS 版本，引入了大量改变编码方式的语法特性和底层优化。2026 年面试中，面试官不再只问 JDK 8，JDK 17 新特性已成为一面必考内容。

#### 一、Records（记录类）—— 不可变数据载体的最佳实践

```java
// JDK 8 传统写法：需要写构造器、getter、equals/hashCode/toString
public class Point {
    private final int x;
    private final int y;
    public Point(int x, int y) { this.x = x; this.y = y; }
    // getter、equals、hashCode、toString 几十行代码...
}

// JDK 17 Records：一行搞定
public record Point(int x, int y) {}
// 自动生成：全参构造器、accessor(x()/y())、equals、hashCode、toString
```

**核心特性：**
- **隐式 final**：Record 类本身 final，不可被继承；所有字段都是 `private final`
- **紧凑构造器**：可在构造器中做参数校验，无需显式赋值字段
- **适用场景**：DTO、VO、API 响应体、多值返回

```java
public record CreateUserRequest(String name, String email, int age) {
    // 紧凑构造器：参数校验
    public CreateUserRequest {
        if (age < 0 || age > 150) {
            throw new IllegalArgumentException("Invalid age: " + age);
        }
        // name/email/age 自动赋值，无需手动写 this.name = name
    }
}
```

#### 二、Switch 模式匹配（Pattern Matching for Switch）

JDK 17 正式预览（JDK 21 转正），彻底改变了 switch 的写法：

```java
// 传统 switch
String result;
switch (obj) {
    case Integer i:
        result = "Integer: " + i;
        break;
    case String s:
        result = "String: " + s;
        break;
    default:
        result = "Unknown";
}

// JDK 17+ Switch 模式匹配
String result = switch (obj) {
    case Integer i -> "Integer: " + i;
    case String s && s.length() > 5 -> "Long string: " + s;  // 守卫模式
    case String s -> "Short string: " + s;
    case null -> "null value";  // 支持 null 匹配
    default -> "Unknown";
};
```

**关键优化点：**
- 箭头语法 `->`：无需 break，不会穿透
- 守卫模式 `&&`：在模式匹配中增加条件判断
- null 匹配：不需要在外层单独判断 null
- 穷举性检查：编译器检查是否覆盖所有可能分支

#### 三、密封类（Sealed Classes）

控制继承的可见性，明确哪些子类可以继承：

```java
// 父类：只允许特定子类继承
public sealed class Shape permits Circle, Rectangle, Triangle { }

// 子类必须声明为 final、sealed 或 non-sealed
public final class Circle extends Shape { }       // 不可再继承
public sealed class Rectangle extends Shape permits Square { }
public non-sealed class Triangle extends Shape { } // 任意继承
```

**面试高频追问**：密封类 vs final 类 vs 访问修饰符的区别？
- final：完全禁止继承
- 密封类：允许有限继承，指定白名单
- 包级私有构造器：只允许同包继承，但不够精确

#### 四、文本块（Text Blocks）

```java
// JDK 8 多行字符串：极其痛苦
String json = "{\n" +
    "  \"name\": \"Alice\",\n" +
    "  \"age\": 30\n" +
    "}";

// JDK 17 文本块：直观
String json = """
    {
      "name": "Alice",
      "age": 30
    }
    """;
```

#### 五、String 底层优化（Compact Strings）

**JDK 9+ 关键优化：**
- 底层存储从 `char[]` 改为 `byte[]` + coder 标志位
- 纯拉丁字符（LATIN1）每个字符 1 字节，内存减少 50%
- 中文字符（UTF16）每个字符 2 字节，保持兼容

```java
// JDK 8: private final char value[];  // 每个char 2字节
// JDK 17: private final byte[] value; // LATIN1:1字节, UTF16:2字节
//         private final byte coder;    // 0=LATIN1, 1=UTF16
```

**拼接编译优化：**
- 常量拼接（如 `"a" + "b"`）编译期直接求值
- `StringTemplate`（JDK 21+）原生模板字符串，替代繁琐拼接

## 题目 2：[AI工程化] 后端对接大模型 API 的 SSE 流式响应实现原理与最佳实践

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-11 早间报告 — "后端对接AI大模型 + SSE流式响应 + 云原生轻量化部署 成为一面必问"

### 📖 参考答案

#### 一、什么是 SSE？

**SSE（Server-Sent Events，服务端推送事件）** 是一种基于 HTTP 长连接的轻量级流式传输协议。与 WebSocket 不同，SSE 是**单向**的（服务端 → 客户端），天然适配 AI 大模型"逐字输出"的场景。

```
SSE vs WebSocket 对比：

SSE（服务端推送）:
┌─────────┐   HTTP 长连接    ┌─────────┐
│ 后端服务 ├────────────────→ │  客户端  │
│         │   data: "你好"    │         │
│         │   data: "世界"    │         │
│         │   data: "[DONE]" │         │
└─────────┘                  └─────────┘
特点：基于HTTP，单向，自动重连，简单轻量

WebSocket（全双工）:
┌─────────┐                  ┌─────────┐
│ 后端服务 │←───────────────→ │  客户端  │
│         │    双向通信       │         │
└─────────┘                  └─────────┘
特点：独立协议，双向，需额外握手，功能更全面
```

**SSE 数据格式标准：**
```
data: {"content": "你好", "index": 0}

data: {"content": "世", "index": 1}

data: {"content": "界", "index": 2}

data: [DONE]
```

#### 二、Spring Boot 3 + WebFlux 实现 SSE 流式问答

```java
@RestController
@RequestMapping("/api/ai")
public class AIChatController {
    
    @Autowired
    private AIService aiService;
    
    /**
     * 流式对话接口：返回 SSE 流
     * produces = MediaType.TEXT_EVENT_STREAM_VALUE 是关键
     */
    @GetMapping(value = "/chat/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> streamChat(@RequestParam String prompt) {
        return aiService.streamChat(prompt)
            .map(content -> ServerSentEvent.<String>builder()
                .data(content)
                .event("message")    // 事件类型
                .id(UUID.randomUUID().toString())  // 事件ID，支持断点续传
                .build())
            .concatWithValues(ServerSentEvent.<String>builder()
                .data("[DONE]")
                .event("done")
                .build());
    }
}
```

#### 三、对接大模型 API 的核心代码

```java
@Service
public class AIService {
    
    // 方式一：基于 WebClient 的流式调用
    public Flux<String> streamChat(String prompt) {
        return webClient.post()
            .uri("https://api.deepseek.com/v1/chat/completions")
            .header("Authorization", "Bearer " + apiKey)
            .bodyValue(Map.of(
                "model", "deepseek-chat",
                "messages", List.of(Map.of("role", "user", "content", prompt)),
                "stream", true  // 开启流式
            ))
            .retrieve()
            .bodyToFlux(String.class)
            .filter(line -> line.startsWith("data: "))
            .map(line -> line.substring(6))  // 去掉 "data: " 前缀
            .filter(data -> !data.equals("[DONE]"))
            .map(this::parseContent);  // 解析 JSON 提取 content 字段
    }
    
    // 方式二：OkHttp + EventSource（更底层控制）
    public void streamWithOkHttp(String prompt, Consumer<String> onToken) {
        Request request = new Request.Builder()
            .url("https://api.deepseek.com/v1/chat/completions")
            .post(RequestBody.create(jsonBody, MediaType.get("application/json")))
            .build();
            
        EventSource.Factory factory = EventSources.createFactory(okHttpClient);
        EventSource eventSource = factory.newEventSource(request, new EventSourceListener() {
            @Override
            public void onEvent(EventSource es, String id, String type, String data) {
                if (!data.equals("[DONE]")) {
                    onToken.accept(parseContent(data));
                }
            }
        });
    }
}
```

## 题目 3：[JVM] JVM 锁竞争分析与调优实战：从偏向锁到重量级锁的完整链路

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-11 早间报告 — "三大必考板块：JVM 内存模型、OOM排查、GC调优、锁竞争分析"
**相关岗位**：Java后端 / 全栈 / 基础架构

### 📖 参考答案

#### 一、synchronized 锁升级完整链路

```
锁状态流转（JDK 8 完整链路）:
无锁 ──→ 偏向锁 ──→ 轻量级锁 ──→ 重量级锁
 (01)     (101)       (00)         (10)

JDK 17 默认链路（偏向锁已移除）:
无锁 ──→ 轻量级锁 ──→ 重量级锁
 (01)     (00)         (10)
```

**各锁状态详解：**

| 锁状态 | 标志位 | 触发条件 | 核心机制 | 性能 |
|--------|--------|---------|---------|------|
| **无锁** | 01 | 初始状态 | 无任何锁标记 | 最高 |
| **偏向锁** | 101 | 单线程反复获取同一锁 | 对象头记录线程ID，无需CAS | 高 |
| **轻量级锁** | 00 | 多线程交替执行 | CAS自旋，用户态，不阻塞 | 中 |
| **重量级锁** | 10 | 多线程竞争激烈 | 线程阻塞进入内核态 | 低 |

#### 二、JDK 17 锁优化重大变化

**偏向锁默认移除（JDK 15+）：**

```java
// JDK 8 默认开启偏向锁
-XX:+UseBiasedLocking

// JDK 17 已移除偏向锁默认开启
// 原因：偏向锁的撤销需要全局安全点（STW），
// 高并发场景下撤销成本 > 收益
// 可通过 -XX:BiasedLockingStartupDelay=0 手动开启
```

**JDK 17 重量级锁优化：**
- 引入自适应自旋：根据上次自旋成功率动态调整自旋次数
- 优化线程挂起/唤醒机制：减少内核态切换开销
- 锁粗化 + 锁消除：编译期自动优化

#### 四、锁优化实战策略

**1. 减小锁粒度（最常用）：**
```java
// ❻ 粗粒度：整个方法加锁
public synchronized void processOrder(Order order) {
    validate(order);
    deductStock(order);  // 真正需要加锁的部分
    sendNotification(order);  // 不需要加锁
}

// ✅ 细粒度：只锁必要代码块
public void processOrder(Order order) {
    validate(order);  // 无锁
    synchronized (stockLock) {
        deductStock(order);  // 仅此处加锁
    }
    sendNotification(order);  // 无锁
}
```

**2. 锁分离（读写分离）：**
```java
// ReadWriteLock：读不互斥，写互斥
private final ReadWriteLock rwLock = new ReentrantReadWriteLock();

public V get(K key) {
    rwLock.readLock().lock();
    try { return cache.get(key); }
    finally { rwLock.readLock().unlock(); }
}

public void put(K key, V value) {
    rwLock.writeLock().lock();
    try { cache.put(key, value); }
    finally { rwLock.writeLock().unlock(); }
}
```

**3. CAS 替代锁：**
```java
// 使用 AtomicInteger 替代 synchronized
private final AtomicInteger counter = new AtomicInteger(0);

public void increment() {
    counter.incrementAndGet();  // CAS 无锁操作
}
```

**4. 锁消除与锁粗化（JVM 自动优化，了解即可）：**
```java
// 锁消除：JVM 检测到锁对象不会被其他线程访问，自动消除
public String concat(String a, String b) {
    return new StringBuilder(a).append(b).toString();
    // StringBuffer 是线程安全的，但这里局部变量不会被共享
    // JVM 自动消除 append 方法中的锁
}

// 锁粗化：连续加锁解锁合并
public void batchProcess() {
    synchronized(lock) { doA(); }
    synchronized(lock) { doB(); }
    synchronized(lock) { doC(); }
    // JVM 粗化为一个锁：synchronized(lock) { doA(); doB(); doC(); }
}
```

## 题目 4：[框架/Spring] Spring Boot 3.x 自动配置原理详解：@EnableAutoConfiguration、AutoConfigurationImportSelector 与条件注解机制

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-11 早间报告 — "三大必考板块：SpringBoot3自动配置"
**相关岗位**：Java后端 / 全栈

### 📖 参考答案

#### 一、自动配置的本质

Spring Boot 自动配置（Auto-Configuration）的核心目标：**根据 classpath 中的依赖和配置属性，自动注册所需的 Bean**，让开发者从繁琐的 XML 配置中解放出来。

```
自动配置执行流程：

@SpringBootApplication
    └─ @EnableAutoConfiguration（核心入口）
            │
            ▼
    AutoConfigurationImportSelector
            │  实现 ImportSelector 接口
            │  selectImports() 方法
            │
            ▼
    SpringFactoriesLoader
            │  加载 META-INF/spring/xxx.imports
            │  (Spring Boot 3.x 使用 .imports 文件替代了 spring.factories)
            │
            ▼
    扫描到 N 个自动配置类（如 RedisAutoConfiguration、DataSourceAutoConfiguration）
            │
            ▼
    逐条检查 @Conditional 条件注解
            │  ┌─ @ConditionalOnClass：classpath 中是否有指定类
            │  ├─ @ConditionalOnMissingBean：容器中是否已有指定 Bean
            │  ├─ @ConditionalOnProperty：配置文件中是否有指定属性
            │  └─ @ConditionalOnResource：classpath 中是否有指定资源
            │
            ▼
    条件满足 → 创建 Bean
    条件不满足 → 跳过（不报错）
```

#### 二、核心源码解析

**1. @EnableAutoConfiguration 注解：**

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Inherited
@AutoConfigurationPackage          // 注册当前包路径
@Import(AutoConfigurationImportSelector.class)  // 核心！
public @interface EnableAutoConfiguration {
    String ENABLED_OVERRIDE_PROPERTY = "spring.boot.enableautoconfiguration";
    Class<?>[] exclude() default {};
    String[] excludeName() default {};
}
```

**关键点：** `@Import(AutoConfigurationImportSelector.class)` 是整个自动配置的入口，通过 `ImportSelector` 机制动态注册 Bean。

**2. AutoConfigurationImportSelector.selectImports()：**

```java
// 核心方法：返回需要自动注册的全限定类名数组
@Override
public String[] selectImports(AnnotationMetadata annotationMetadata) {
    if (!isEnabled(annotationMetadata)) {
        return NO_IMPORTS;
    }
    // 1. 获取所有自动配置类的名称
    AutoConfigurationEntry autoConfigurationEntry = getAutoConfigurationEntry(annotationMetadata);
    return StringUtils.toStringArray(autoConfigurationEntry.getConfigurations());
}

// 获取自动配置条目
protected AutoConfigurationEntry getAutoConfigurationEntry(AnnotationMetadata annotationMetadata) {
    // 1. 获取所有候选配置
    List<String> configurations = getCandidateConfigurations(annotationMetadata, attributes);
    // 2. 去重
    configurations = removeDuplicates(configurations);
    // 3. 排除指定的配置
    Set<String> exclusions = getExclusions(annotationMetadata, attributes);
    configurations.removeAll(exclusions);
    // 4. 过滤条件不满足的配置
    configurations = filter(configurations, autoConfigurationMetadata);
    return new AutoConfigurationEntry(configurations, exclusions);
}
```

## 题目 5：[AI/大模型] 大模型 Fine-tuning（微调）核心原理：LoRA、QLoRA 与 PEFT 参数高效微调对比

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-11 午间报告 — "大模型应用开发成硬通货，熟悉RAG/Agent/Fine-tuning已成JD标配"
**相关岗位**：Java后端 / Python后端 / AI应用开发 / 全栈

### 📖 参考答案

#### 一、为什么需要 Fine-tuning？

大模型（如 GPT-4、DeepSeek、Llama 3）虽然能力强大，但存在以下局限：
- **领域知识不足**：对特定业务场景（如医疗、金融、法律）了解不够
- **输出格式不固定**：难以保证输出符合特定 JSON 结构
- **成本过高**：每次 Prompt 都注入大量上下文（Few-shot）会浪费 token

Fine-tuning 通过对预训练模型进行**有监督微调**，让模型适应特定任务或领域。

```
全量微调 vs 参数高效微调：

全量微调（Full Fine-tuning）:
┌─────────────────────────┐
│   预训练模型 (7B/13B)    │  ← 所有参数参与训练
│  ┌───┐ ┌───┐ ┌───┐    │     需要 4-8 张 A100
│  │ W1 │ │ W2 │ │ W3 │    │     GPU 显存需求极大
│  └───┘ └───┘ └───┘    │
└─────────────────────────┘

LoRA 微调:
┌─────────────────────────┐
│   预训练模型 (7B/13B)    │  ← 原始权重冻结 ❄️
│  ┌───┐ ┌───┐ ┌───┐    │
│  │ W1 │ │ W2 │ │ W3 │    │     新增低秩矩阵 A×B
│  └───┘ └───┘ └───┘    │     参数量减少 10000×
│    ↓ A1×B1  ↓ A2×B2    │     1 张 RTX 4090 即可
└─────────────────────────┘
```

#### 二、LoRA（Low-Rank Adaptation）核心原理

**数学基础：** 预训练模型的权重矩阵 W ∈ ℝ^(d×k) 虽然是满秩的，但微调时的**增量 ΔW** 具有低秩性。

```python
# LoRA 的核心公式
# h = W₀x + ΔWx = W₀x + BAx
# 其中：
#   - W₀ ∈ ℝ^(d×k) ：原始权重（冻结，不训练）
#   - B ∈ ℝ^(d×r)  ：低秩矩阵（随机初始化）
#   - A ∈ ℝ^(r×k)  ：低秩矩阵（零初始化）
#   - r << min(d, k)：秩（通常 r=4,8,16,32）

# 参数量对比：
# 原始全量更新：d × k (如 4096×4096 ≈ 16M 参数)
# LoRA 更新：d×r + r×k = r × (d+k) (如 8×(4096+4096) ≈ 65K 参数)
# 参数减少约 250 倍！
```

**代码示例（HuggingFace PEFT）：**

```python
from peft import LoraConfig, get_peft_model, TaskType
from transformers import AutoModelForCausalLM

# 加载基础模型
model = AutoModelForCausalLM.from_pretrained("deepseek-ai/deepseek-llm-7b")

# 配置 LoRA
lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=8,                    # 秩的大小
    lora_alpha=32,          # 缩放系数
    lora_dropout=0.1,       # Dropout 率
    target_modules=["q_proj", "v_proj", "k_proj", "o_proj"],  # 应用 LoRA 的模块
    bias="none",            # 不训练偏置
)

# 应用 LoRA
peft_model = get_peft_model(model, lora_config)
print(f"可训练参数: {peft_model.num_parameters(only_trainable=True):,}")
# 输出: 可训练参数: 4,194,304 (约 4M，原模型 7B 的 0.06%)
```

#### 三、QLoRA：量化 + LoRA 的极致优化

**QLoRA = 4-bit NormalFloat 量化 + LoRA + 双重量化 + 分页优化**

| 对比项 | LoRA | QLoRA |
|--------|------|-------|
| 基础模型精度 | FP16/BF16 | **4-bit NF4**（量化） |
| GPU 显存需求（7B 模型） | ~16GB | **~6GB** |
| GPU 显存需求（13B 模型） | ~28GB | **~10GB** |
| 性能损失 | 无 | < 1% |
| 适用显卡 | RTX 3090/4090 | RTX 3060/4070 也可运行 |

**QLoRA 的三大创新：**

1. **4-bit NormalFloat（NF4）**：针对正态分布权重的量化方案，比普通 INT4 精度更高
2. **双重量化**：对量化常数再次量化，进一步节省显存
3. **分页优化**：利用 CPU 内存作为溢出缓冲区，防止 OOM

```python
# 4-bit 量化配置

    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",          # NF4 量化
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,     # 双重量化
)

# 加载量化模型

    device_map="auto",

```

#### 五、面试高频追问：微调 vs RAG 怎么选？

| 维度 | Fine-tuning（微调） | RAG（检索增强生成） |
|------|-------------------|-------------------|
| 知识更新 | 需要重新训练 | 只需更新知识库 |
| 幻觉控制 | 较好（内化知识） | 依赖检索质量 |
| 推理成本 | 不变 | 增加检索延迟 |
| 数据隐私 | 参数可能泄漏 | 知识不上传模型 |
| 实现复杂度 | 高（需要 GPU） | 低（纯工程） |
| 适用场景 | 输出格式固定、大量重复模式 | 知识频繁更新、需引用来源 |

**面试标准答案：** 实际项目中通常 RAG + Fine-tuning 组合使用。RAG 负责实时知识检索（如公司内部文档），Fine-tuning 负责输出格式和风格适配（如统一的回复模板）。
