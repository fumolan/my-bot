**一、AQS 是什么？——JUC 的"底层骨架"**

AQS（AbstractQueuedSynchronizer）是 `java.util.concurrent.locks` 包下的抽象类，是整个 JUC 并发工具包的基石。ReentrantLock、CountDownLatch、Semaphore、ReentrantReadWriteLock 等核心组件全部基于 AQS 实现。

```
AQS 的定位：

  ┌─────────────────────────────────────────────────────────┐
  │  ReentrantLock  CountDownLatch  Semaphore  CyclicBarrier│
  │         │            │            │            │        │
  │         └────────────┴────────────┴────────────┘        │
  │                         │                               │
  │                    ┌────▼─────────────────────┐         │
  │                    │   AQS (AbstractQueued    │         │
  │                    │   Synchronizer)          │         │
  │                    │   - 状态管理              │         │
  │                    │   - 线程排队              │         │
  │                    │   - 阻塞/唤醒             │         │
  │                    └──────────────────────────┘         │
  └─────────────────────────────────────────────────────────┘

  AQS 封装了"同步状态管理、线程排队、阻塞/唤醒"等底层逻辑，
  让开发者只需关注"如何获取/释放同步状态"，无需重复编写线程排队等通用逻辑。
```

**二、AQS 三大核心设计**

### 设计 1：volatile state —— 同步状态中心

```java
// AQS 核心字段
private volatile int state;  // 同步状态，volatile 保证可见性

// state 在不同组件中的含义：
// ReentrantLock：0=未锁，>0=已锁（值=重入次数）
// CountDownLatch：state=计数器初始值，减到 0 释放
// Semaphore：state=剩余许可数
```

所有对 state 的修改都通过 CAS 操作保证原子性：

```java
// CAS 修改 state（AQS 内部方法）
protected final boolean compareAndSetState(int expect, int update) {
    return U.compareAndSwapInt(this, STATE, expect, update);
}
```

### 设计 2：CLH 双向队列 —— 线程排队

AQS 内部维护一个基于 CLH 锁变体的 **FIFO 双向链表**，存放竞争锁失败的线程：

```
CLH 队列结构：

  head                                    tail
   │                                       │
   ▼                                       ▼
  ┌─────┐   ┌─────┐   ┌─────┐   ┌─────┐
  │Node │◄─►│Node │◄─►│Node │◄─►│Node │
  │(哨兵)│   │Thread│   │Thread│   │Thread│
  │     │   │  A  │   │  B  │   │  C  │
  └─────┘   └─────┘   └─────┘   └─────┘

  Node 节点关键字段：
  - thread：被阻塞的线程
  - waitStatus：节点状态（SIGNAL=-1 表示后继需要唤醒，CANCELLED=1 表示取消）
  - prev / next：前驱/后继指针

  关键规则：
  ① head 是哨兵节点（已获取锁的线程，或虚拟节点）
  ② 新来的线程封装为 Node 插入队尾（CAS 操作）
  ③ head 的后继节点是下一个要获取锁的线程
```

### 设计 3：模板方法模式 —— 子类只需实现"获取/释放"

AQS 使用模板方法模式，定义了获取锁的通用流程（`acquire()`/`release()`），子类只需实现具体的"尝试获取/释放"逻辑：

```java
// AQS 的模板方法（已实现，子类无需重写）
public final void acquire(int arg) {
    if (!tryAcquire(arg) &&           // ① 子类实现：尝试获取锁
        acquireQueued(addWaiter(Node.EXCLUSIVE), arg))  // ② 失败则入队排队
        selfInterrupt();              // ③ 被中断后补上中断标记
}

// 子类需要实现的方法
protected boolean tryAcquire(int arg) {
    throw new UnsupportedOperationException();  // 默认抛异常，子类重写
}
```

| 模式 | 需要重写的方法 | 代表组件 |
|------|-------------|---------|
| **独占模式** | `tryAcquire()` / `tryRelease()` | ReentrantLock |
| **共享模式** | `tryAcquireShared()` / `tryReleaseShared()` | CountDownLatch、Semaphore |

**三、ReentrantLock 的底层实现——公平锁 vs 非公平锁**

ReentrantLock 内部有三个核心内部类：

```
ReentrantLock 内部结构：

  ReentrantLock
       │
       ├── Sync extends AQS          ← 抽象同步器，定义通用逻辑
       │     │
       │     ├── NonfairSync         ← 非公平锁实现
       │     │
       │     └── FairSync            ← 公平锁实现
```

### 非公平锁的加锁流程（默认）

```java
// NonfairSync.lock() —— 非公平锁的"插队"机制
final void lock() {
    // ① 先 CAS 抢一次锁（不管有没有人排队！）
    if (compareAndSetState(0, 1))
        setExclusiveOwnerThread(Thread.currentThread());  // 抢到直接走
    else
        acquire(1);  // 抢不到走正规流程
}

// NonfairSync.tryAcquire()
protected final boolean tryAcquire(int acquires) {
    return nonfairTryAcquire(acquires);
}

// Sync.nonfairTryAcquire() —— 非公平锁的核心逻辑
final boolean nonfairTryAcquire(int acquires) {
    final Thread current = Thread.currentThread();
    int c = getState();
    
    if (c == 0) {
        // ② 锁空闲 → CAS 抢锁（不检查队列！这就是"非公平"）
        if (compareAndSetState(0, acquires)) {
            setExclusiveOwnerThread(current);
            return true;
        }
    }
    else if (current == getExclusiveOwnerThread()) {
        // ③ 重入：state += acquires
        int nextc = c + acquires;
        if (nextc < 0) throw new Error("Maximum lock count exceeded");
        setState(nextc);
        return true;
    }
    return false;  // ④ 抢不到，进入 AQS 队列排队
}
```

### 公平锁的加锁流程

```java
// FairSync.tryAcquire() —— 公平锁的关键差异
protected final boolean tryAcquire(int acquires) {
    final Thread current = Thread.currentThread();
    int c = getState();
    
    if (c == 0) {
        // ⭐ 关键差异：先检查队列里有没有人在等！
        if (!hasQueuedPredecessors() &&  // 队列为空或当前线程是队首
            compareAndSetState(0, acquires)) {
            setExclusiveOwnerThread(current);
            return true;
        }
    }
    else if (current == getExclusiveOwnerThread()) {
        // 重入逻辑相同
        int nextc = c + acquires;
        setState(nextc);
        return true;
    }
    return false;
}

// hasQueuedPredecessors() —— 公平锁的"排队检查"
public final boolean hasQueuedPredecessors() {
    Node t = tail;
    Node h = head;
    Node s;
    return h != t &&                      // 队列不为空
           ((s = h.next) == null ||       // 有后继节点
            s.thread != Thread.currentThread());  // 且不是当前线程
}
```

### 公平锁 vs 非公平锁对比

| 维度 | 公平锁（FairSync） | 非公平锁（NonfairSync，默认） |
|------|-------------------|---------------------------|
| **lock() 入口** | 直接走 acquire() | 先 CAS 抢一次，失败再 acquire() |
| **tryAcquire()** | 检查 `hasQueuedPredecessors()` | 不检查队列，直接 CAS 抢 |
| **性能** | 较低（每次都要检查队列） | 较高（减少线程切换） |
| **吞吐量** | 低 | 高 |
| **饥饿风险** | 无 | 有（新线程可能一直抢到锁） |
| **适用场景** | 对公平性要求高的场景 | 通用场景（默认选择） |

**四、state 与重入计数**

```java
// ReentrantLock 的重入机制
// 同一个线程多次 lock()，state 递增

lock.lock();    // state: 0 → 1
lock.lock();    // state: 1 → 2（重入）
lock.lock();    // state: 2 → 3（再次重入）
lock.unlock();  // state: 3 → 2
lock.unlock();  // state: 2 → 1
lock.unlock();  // state: 1 → 0 → 释放锁，唤醒后继节点

// tryRelease() 实现
protected final boolean tryRelease(int releases) {
    int c = getState() - releases;
    if (Thread.currentThread() != getExclusiveOwnerThread())
        throw new IllegalMonitorStateException();  // 不是持锁线程，抛异常
    boolean free = false;
    if (c == 0) {
        free = true;                     // state=0 才真正释放锁
        setExclusiveOwnerThread(null);
    }
    setState(c);
    return free;
}
```

**五、Condition 条件队列——await/signal 的线程流转**

ReentrantLock 通过 `newCondition()` 创建 Condition 对象，支持更精细的线程等待/唤醒（比 `synchronized` 的 `wait/notify` 更强大）。

```
AQS 的双队列模型：

  ┌─────────────────────────────────────────────────────────┐
  │                    同步队列（CLH 双向链表）                │
  │  等待获取锁的线程                                         │
  │  head ←→ Node(A) ←→ Node(B) ←→ Node(C) ← tail          │
  └─────────────────────────────────────────────────────────┘
                              │
                              │ signal()
                              ▼
  ┌─────────────────────────────────────────────────────────┐
  │                    条件队列（单向链表）                    │
  │  调用了 await() 的线程                                   │
  │  firstWaiter → Node(X) → Node(Y) → Node(Z)              │
  └─────────────────────────────────────────────────────────┘

  await() 流程：
  ① 当前线程必须持有锁
  ② 将当前线程封装为 Node 加入条件队列尾部
  ③ 完全释放锁（state 归零，唤醒同步队列的后继节点）
  ④ 线程阻塞，等待 signal

  signal() 流程：
  ① 将条件队列的头节点移到同步队列的尾部
  ② 该节点在同步队列中等待获取锁
  ③ 获取锁后，从 await() 返回继续执行
```

```java
// Condition 使用示例——生产者消费者
Lock lock = new ReentrantLock();
Condition notFull = lock.newCondition();   // 缓冲区不满
Condition notEmpty = lock.newCondition();  // 缓冲区不空

// 生产者
lock.lock();
try {
    while (count == MAX) {
        notFull.await();  // 缓冲区满，等待
    }
    // 生产...
    notEmpty.signal();    // 唤醒消费者
} finally {
    lock.unlock();
}

// 消费者
lock.lock();
try {
    while (count == 0) {
        notEmpty.await(); // 缓冲区空，等待
    }
    // 消费...
    notFull.signal();     // 唤醒生产者
} finally {
    lock.unlock();
}
```

```
面试官问"ReentrantLock 底层怎么实现的？公平锁和非公平锁有什么区别？"

① AQS 三大设计（15秒）：
   "AQS 是 JUC 的底层骨架，三大核心：volatile int state 存储同步状态、
    CLH 双向链表实现线程排队、模板方法模式让子类只需实现 tryAcquire/tryRelease"

② ReentrantLock 实现（20秒）：
   "内部 Sync 继承 AQS，state=0 未锁，>0 已锁（值=重入次数）。
    加锁：CAS 抢 state → 失败则封装 Node 入 CLH 队列 → park 阻塞。
    解锁：state 递减 → 归零则唤醒队列后继节点"

③ 公平 vs 非公平（20秒）：
   "非公平锁：lock() 先 CAS 抢一次，tryAcquire 不检查队列，新线程可能'插队'；
    公平锁：tryAcquire 先调用 hasQueuedPredecessors() 检查队列，
    有人排队就乖乖去队尾。非公平锁吞吐量高（默认），公平锁避免饥饿"

④ Condition（15秒）：
   "每个 ReentrantLock 可创建多个 Condition，底层是条件队列（单向链表）。
    await()：释放锁 + 入条件队列 + 阻塞；signal()：移到同步队列尾部。
    比 synchronized 的 wait/notify 更灵活（支持多条件、可中断、超时）"

⑤ 实战建议（10秒）：
   "日常优先 synchronized（简洁），需要 tryLock/可中断/多条件/公平锁时用 ReentrantLock。
    虚拟线程场景下 synchronized 会导致 pinning，必须用 ReentrantLock"
```

### 💡 延伸思考

1. **AQS 为什么用双向链表而不是单向链表？** — 双向链表方便在取消等待时从队列中移除节点（需要修改前驱的 next 指针）。单向链表删除节点需要遍历找到前驱，效率低。此外，唤醒后继节点时也需要通过 next 指针快速定位。
2. **非公平锁的"插队"真的不公平吗？** — 非公平锁只在 lock() 入口和 tryAcquire() 中尝试 CAS 抢锁，但如果抢失败，线程仍然会进入 CLH 队列排队。一旦进入队列，就是 FIFO 顺序了。所以"非公平"只体现在"刚来的线程可能抢在排队线程前面"，而不是"队列里的线程会被插队"。

**一、自动配置解决了什么问题？——从 XML 地狱到"约定优于配置"**

在 Spring Boot 之前，Spring 项目需要大量 XML 配置或 Java Config：数据源、事务管理器、视图解析器、消息转换器……每个组件都要手动配置。Spring Boot 的自动配置（Auto-Configuration）让这一切变得"开箱即用"——引入 `spring-boot-starter-web`，Tomcat、Spring MVC、Jackson 自动配好。

```
自动配置的本质：
  根据 classpath 中的依赖、已定义的 Bean、配置文件中的属性，
  智能推断并自动创建合适的 Bean 放入 IOC 容器。

  例：classpath 中有 HikariCP 的 jar → 自动创建 DataSource Bean
      classpath 中有 spring-webmvc → 自动配置 DispatcherServlet
      没有自定义 DataSource Bean → 使用默认 HikariCP 配置
```

**二、从 @SpringBootApplication 到自动配置类——完整调用链路**

```
调用链路全景：

  @SpringBootApplication
       │
       ├── @SpringBootConfiguration（标记配置类）
       ├── @ComponentScan（组件扫描）
       └── @EnableAutoConfiguration  ← 自动配置的入口！
              │
              └── @Import(AutoConfigurationImportSelector.class)
                     │
                     ▼
              AutoConfigurationImportSelector.selectImports()
                     │
                     ▼
              getAutoConfigurationEntry()
                     │
                     ├── getCandidateConfigurations()
                     │   从 META-INF/spring/...AutoConfiguration.imports 读取
                     │   所有候选自动配置类（Spring Boot 3.x 约 150+ 个）
                     │
                     ├── removeDuplicates() —— 去重
                     │
                     ├── filter(configurations, autoConfigurationMetadata)
                     │   通过 @Conditional 系列注解过滤：
                     │   - @ConditionalOnClass：classpath 中有指定类才生效
                     │   - @ConditionalOnMissingBean：容器中没有指定 Bean 才生效
                     │   - @ConditionalOnProperty：配置文件中指定属性才生效
                     │   - @ConditionalOnBean：容器中有指定 Bean 才生效
                     │   - @ConditionalOnMissingClass：classpath 中没有指定类才生效
                     │
                     └── 返回最终需要导入的配置类列表
```

```java
// 源码关键步骤（简化）

// ① @SpringBootApplication 是复合注解
@SpringBootConfiguration
@EnableAutoConfiguration        // ← 自动配置入口
@ComponentScan(excludeFilters = { ... })
public @interface SpringBootApplication { }

// ② @EnableAutoConfiguration 导入 AutoConfigurationImportSelector
@Import(AutoConfigurationImportSelector.class)
public @interface EnableAutoConfiguration { }

// ③ AutoConfigurationImportSelector 核心逻辑
public class AutoConfigurationImportSelector implements ... {
    
    @Override
    public String[] selectImports(AnnotationMetadata annotationMetadata) {
        AutoConfigurationEntry entry = getAutoConfigurationEntry(annotationMetadata);
        return StringUtils.toStringArray(entry.getConfigurations());
    }
    
    protected AutoConfigurationEntry getAutoConfigurationEntry(...) {
        // 1. 加载所有候选配置类
        List<String> configurations = getCandidateConfigurations(annotationMetadata, attributes);
        
        // 2. 去重
        configurations = removeDuplicates(configurations);
        
        // 3. 排除用户指定的类（@EnableAutoConfiguration 的 exclude 属性）
        Set<String> exclusions = getExclusions(annotationMetadata, attributes);
        configurations.removeAll(exclusions);
        
        // 4. 条件过滤（@ConditionalOnClass 等）
        configurations = filter(configurations, autoConfigurationMetadata);
        
        return new AutoConfigurationEntry(configurations, exclusions);
    }
}
```

**三、SPI 机制的演进——spring.factories → .imports 文件**

Spring Boot 2.x 和 3.x 在自动配置的加载方式上有重要变化：

| 版本 | 配置文件 | 格式 | 说明 |
|------|---------|------|------|
| **Spring Boot 2.x** | `META-INF/spring.factories` | key=value 多值 | 所有自动配置类写在一个文件里 |
| **Spring Boot 3.x** | `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` | 每行一个类名 | 更简洁，一行一个配置类 |

```
Spring Boot 2.x 的 spring.factories：
  org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
  org.springframework.boot.autoconfigure.web.servlet.WebMvcAutoConfiguration,\
  org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration,\
  ...

Spring Boot 3.x 的 .imports 文件：
  org.springframework.boot.autoconfigure.web.servlet.WebMvcAutoConfiguration
  org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
  ...

  优势：
  ① 更简洁：每行一个类名，不需要反斜杠续行
  ② 更高效：不需要解析 key=value 格式
  ③ 更安全：每个 Starter 独立文件，不会互相覆盖
```

**四、@Conditional 条件注解——自动配置的"开关"**

条件注解是自动配置的核心过滤机制，确保只有在条件满足时才创建对应的 Bean：

| 条件注解 | 作用 | 示例 |
|---------|------|------|
| `@ConditionalOnClass` | classpath 中存在指定类 | 有 HikariCP 才配置数据源 |
| `@ConditionalOnMissingClass` | classpath 中不存在指定类 | 没有 HikariCP 就用 Tomcat 连接池 |
| `@ConditionalOnBean` | 容器中存在指定 Bean | 有 DataSource 才配置 JdbcTemplate |
| `@ConditionalOnMissingBean` | 容器中不存在指定 Bean | 用户没自定义才用默认配置 |
| `@ConditionalOnProperty` | 配置文件中有指定属性 | `spring.cache.type=redis` 才启用 Redis 缓存 |
| `@ConditionalOnExpression` | SpEL 表达式为 true | 复杂条件组合 |
| `@ConditionalOnWebApplication` | 当前是 Web 应用 | Web 环境才配置 DispatcherServlet |

    }

### 📖 参考答案

**一、为什么是 B+Tree 而不是其他数据结构？**

MySQL InnoDB 的索引基于 B+Tree 实现，这个选择是经过深思熟虑的：

```
候选数据结构的对比：

  ① 哈希表：
     ✅ 等值查询 O(1)
     ❌ 不支持范围查询（WHERE id > 100）
     ❌ 不支持排序（ORDER BY）
     ❌ 哈希冲突导致性能退化
     → 只适合等值查询，不适合数据库通用场景

  ② 二叉搜索树 / AVL / 红黑树：
     ✅ 支持范围查询和排序
     ❌ 树太高！100 万数据 → 树高约 20 层 → 20 次磁盘 IO
     → 每个节点只存一个数据，磁盘 IO 次数太多

  ③ B-Tree（平衡多路搜索树）：
     ✅ 多叉树，树高大幅降低（100 万数据约 3-4 层）
     ✅ 每个节点存储多个 key，减少磁盘 IO
     ❌ 非叶子节点也存数据 → 每个节点能存的 key 更少 → 树更高
     ❌ 范围查询需要中序遍历，可能跨层回退

  ④ B+Tree（B-Tree 的升级版）：
     ✅ 只有叶子节点存数据，非叶子节点只存 key → 每个节点能存更多 key → 树更矮
     ✅ 叶子节点通过双向链表连接 → 范围查询只需遍历链表
     ✅ 所有数据都在叶子节点 → 查询性能稳定（每次都是 O(logN) 到叶子）
     ✅ 适合磁盘预读（每次 IO 读一页 = 16KB，正好是一个节点）
```

```
B+Tree 结构图：

                 ┌─────────┐
                 │ [30|60] │  ← 非叶子节点：只存 key（索引值）
                 └──┬───┬──┘
          ┌─────────┘   └─────────┐
          ▼                        ▼
    ┌──────────┐            ┌──────────┐
    │ [10|20]  │            │ [40|50]  │  ← 非叶子节点
    └──┬──┬───┘            └──┬──┬───┘
  ┌────┘  └────┐        ┌────┘  └────┐
  ▼            ▼        ▼            ▼
┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐
│ 10 │→│ 15 │→│ 20 │→│ 30 │→│ 40 │→│ 50 │→ ...  ← 叶子节点：存完整数据 + 双向链表
│data│ │data│ │data│ │data│ │data│ │data│
└────┘ └────┘ └────┘ └────┘ └────┘ └────┘
```

**二、聚簇索引 vs 二级索引——回表的本质**

InnoDB 的索引分为两类，它们的叶子节点存储的内容完全不同：

```
聚簇索引（Clustered Index / 主键索引）：
  叶子节点存储的是完整的行数据（所有列的值）
  
  创建规则：
  ① 有主键 → 主键就是聚簇索引
  ② 无主键但有唯一非空索引 → 第一个唯一非空索引
  ③ 都没有 → InnoDB 自动生成隐藏的 row_id（6 字节）

二级索引（Secondary Index / 辅助索引）：
  叶子节点存储的是主键值（不是完整行数据！）

  ┌─────────────────────────────────────────────────────────┐
  │  二级索引 B+Tree                聚簇索引 B+Tree          │
  │                                                         │
  │  按索引列排序                    按主键排序               │
  │  叶子节点存主键 ────回表────→   叶子节点存完整行数据      │
  └─────────────────────────────────────────────────────────┘
```

**回表（Back to Table）**：通过二级索引查询时，先在二级索引树中找到主键值，再拿着主键值去聚簇索引树中查找完整行数据。这个过程叫"回表"，需要两次 B+Tree 查找。

```sql
-- 假设表结构：users(id PK, name, age, email)
-- 二级索引：idx_name (name)

-- 回表查询
SELECT * FROM users WHERE name = '张三';
-- ① 在 idx_name 索引树中查找 '张三' → 找到主键 id=100
-- ② 拿着 id=100 去聚簇索引树中查找完整行 → 获取 age, email
-- 两次 B+Tree 查找 = 回表

-- 覆盖索引（避免回表）
SELECT id, name FROM users WHERE name = '张三';
-- ① 在 idx_name 索引树中查找 '张三' → 找到 id=100, name='张三'
-- ② 需要的列都在索引中 → 不需要回表！
-- Extra: Using index（覆盖索引）
```

**三、联合索引与最左前缀原则**

联合索引（Composite Index）是按多个列建立的索引，在 B+Tree 中按"复合键字典序"排序。

```sql
-- 联合索引：idx_abc (a, b, c)
-- B+Tree 中的排序：先按 a 排序，a 相同按 b 排序，b 相同按 c 排序

-- 索引结构示意：
-- (1, 1, 1) → (1, 1, 2) → (1, 2, 1) → (1, 2, 3) → (2, 1, 1) → (2, 3, 1) → ...

-- ✅ 能命中索引：
WHERE a = 1                          -- 命中 a
WHERE a = 1 AND b = 2                -- 命中 a, b
WHERE a = 1 AND b = 2 AND c = 3      -- 命中 a, b, c
WHERE a = 1 AND c = 3                -- 命中 a（c 不命中，因为跳过了 b）
WHERE b = 2 AND a = 1                -- 命中 a, b（优化器自动调整顺序）

-- ❌ 不能命中索引：
WHERE b = 2                          -- 不满足最左前缀（缺少 a）
WHERE c = 3                          -- 不满足最左前缀（缺少 a, b）
WHERE a > 1 AND b = 2                -- a 命中，b 不命中（范围查询截断！）
```

**范围查询"截断"原理**：

```
为什么 WHERE a > 1 AND b = 2 中 b 不命中索引？

  联合索引按 (a, b) 排序：
  (1, 1), (1, 5), (2, 1), (2, 3), (2, 8), (3, 2), ...

  a > 1 的结果是：(2, 1), (2, 3), (2, 8), (3, 2), ...
  在这些结果中，b 不是有序的！(2, 1), (2, 3), (2, 8) 中 b 有序，
  但到了 (3, 2) 又变了 → 无法利用索引对 b 进行精确查找。

  结论：范围查询后面的列，索引失效。
```

**四、索引下推（ICP, Index Condition Pushdown）——MySQL 5.6+ 的重要优化**

ICP 是 MySQL 5.6 引入的优化，将部分 WHERE 条件过滤从 Server 层"下推"到存储引擎层，减少回表次数。

```
没有 ICP（MySQL 5.6 之前）：

  SELECT * FROM users WHERE name LIKE '张%' AND age = 25;
  （联合索引 idx_name_age）

  ① 存储引擎：通过 idx_name_age 找到所有 name LIKE '张%' 的记录
  ② 逐条回表 → 获取完整行数据 → 返回给 Server 层
  ③ Server 层：过滤 age = 25
  → 如果 100 条 name LIKE '张%'，只有 3 条 age=25，则做了 100 次回表！

有 ICP（MySQL 5.6+）：

  ① 存储引擎：通过 idx_name_age 找到所有 name LIKE '张%' 的记录
  ② 存储引擎直接检查 age = 25（索引中有 age！）
  ③ 只有 age=25 的 3 条记录才回表
  → 回表次数从 100 降到 3！

  Extra: Using index condition（ICP 生效）
```

```sql
-- ICP 的触发条件：
-- ① 使用二级索引（聚簇索引不需要 ICP）
-- ② WHERE 条件中包含索引列，但无法直接用于索引查找
-- ③ 适用于 range/ref/eq_ref/ref_or_null 访问类型

-- ICP 不生效的场景：
-- ① 覆盖索引（不需要回表，ICP 无意义）
-- ② 使用主键查询（聚簇索引）
-- ③ 条件是子查询
-- ④ 调用了存储函数
```

**五、索引失效的 8 种经典场景**

| 场景 | 示例 | 原因 |
|------|------|------|
| **1. 不满足最左前缀** | `WHERE b = 1`（索引是 a,b,c） | 联合索引必须从最左列开始匹配 |
| **2. 索引列上做操作** | `WHERE age + 1 = 20` | 索引存的是 age 值，不是 age+1 |
| **3. 隐式类型转换** | `WHERE phone = 13800138000`（phone 是 VARCHAR） | MySQL 会将字符串转数字，等价于函数操作 |
| **4. LIKE 前置通配符** | `WHERE name LIKE '%张'` | B+Tree 只能前缀匹配，`%` 开头无法定位 |
| **5. 负向条件** | `WHERE id != 1` / `NOT IN` / `NOT EXISTS` | 负向条件需要扫描大部分数据，优化器可能放弃索引 |
| **6. OR 两边不全是索引** | `WHERE id = 1 OR name = '张三'`（name 无索引） | 需要全表扫描来满足 OR 的另一半 |
| **7. 范围条件截断** | `WHERE a > 1 AND b = 2`（索引 a,b） | a 的范围查询使 b 无法利用索引 |
| **8. 优化器觉得不值** | 小表全表扫描更快 | 优化器基于成本估算，可能选择全表扫描 |

### 💡 延伸思考

1. **为什么 InnoDB 推荐使用自增主键？** — 自增主键保证新数据总是追加到 B+Tree 的最右侧叶子节点，不会触发页分裂（Page Split）。如果用 UUID 等随机主键，新数据可能插入到已有页中间，导致频繁的页分裂，不仅写入变慢，还会产生大量碎片。
2. **覆盖索引这么好，为什么不把所有列都建索引？** — 索引不是免费的：① 占用磁盘空间（索引也是数据）；② 写入性能下降（每次 INSERT/UPDATE/DELETE 都要维护索引）；③ 优化器选择变多，可能选错索引。索引设计的原则是"够用就好"，用 EXPLAIN 验证效果。

## 题目 4：[网络/TCP] 请详细阐述 TCP 的三次握手与四次挥手机制：包括三次握手为什么不是两次或四次（SYN Flood 攻击与 SYN Cookie 防御）、TCP 11 种状态转换（CLOSED → LISTEN → SYN_SENT → ESTABLISHED → FIN_WAIT → TIME_WAIT → CLOSED）的完整状态机、TIME_WAIT 状态为什么需要 2MSL 以及大量 TIME_WAIT 的排查与优化方案，以及 CLOSE_WAIT 状态堆积的原因与排查方法

**难度**：⭐⭐⭐⭐
**考点来源**：2026-06-12 早间报告 — "TCP 三次握手/FIN_WAIT 状态转换" + "高频面试题热点"  
**相关岗位**：Java后端 / 网络编程 / 基础架构

### 📖 参考答案

**一、TCP 为什么需要"握手"和"挥手"？**

TCP 是面向连接的可靠传输协议。"连接"不是物理线路，而是通信双方在内存中维护的状态信息（序列号、窗口大小等）。握手是为了同步双方的初始状态，挥手是为了优雅地释放连接。

**二、三次握手——建立连接**

```
三次握手流程图：

  Client                              Server
    │                                   │
    │ ──── SYN, seq=x ──────────────→  │  ① 第一次握手
    │     (CLIENT → SYN_SENT)          │     (LISTEN → SYN_RCVD)
    │                                   │
    │ ←── SYN+ACK, seq=y, ack=x+1 ──── │  ② 第二次握手
    │     (SYN_SENT → ESTABLISHED)     │
    │                                   │
    │ ──── ACK, seq=x+1, ack=y+1 ───→  │  ③ 第三次握手
    │                                   │     (SYN_RCVD → ESTABLISHED)
    │                                   │
    ▼                                   ▼
  ESTABLISHED                        ESTABLISHED
```

```
每次握手的目的：

  第一次（Client → Server）：Client 告诉 Server"我想连接"，发送初始序列号 x
  第二次（Server → Client）：Server 回复"我收到了"，发送自己的初始序列号 y
  第三次（Client → Server）：Client 确认"我也收到了你的序列号"

  三次握手后：
  Client 确认：自己的发送和接收能力正常
  Server 确认：自己的发送和接收能力正常
  双方都确认对方的收发能力正常 → 可以开始可靠传输
```

**为什么不是两次握手？**

```
两次握手的问题：

  Client → Server: SYN
  Server → Client: SYN+ACK（Server 认为连接已建立！）
  
  问题 1：历史连接
  如果 Client 的第一个 SYN 因网络延迟，Client 超时重发第二个 SYN，
  连接建立、传输数据、关闭后，第一个 SYN 才到达 Server。
  Server 回复 SYN+ACK → 认为连接建立 → 分配资源等待数据。
  但 Client 已经关闭了 → Server 资源浪费（半开连接）

  问题 2：无法验证 Client 的接收能力
  Server 不知道 Client 是否能收到自己的消息。
  如果 Client 发送能力有问题，Server 发出的数据会全部丢失。

  三次握手解决：
  第三次 ACK 让 Server 确认 Client 收到了自己的 SYN+ACK，
  同时 Client 可以通过第三次握手携带数据（TCP Fast Open）
```

**为什么不是四次握手？**

四次握手可以（将第二次的 SYN 和 ACK 分开发送），但没必要——SYN 和 ACK 可以合并在一个报文中发送，三次是效率和安全的最优解。

**三、四次挥手——释放连接**

```
四次挥手流程图：

  Client                              Server
    │                                   │
    │ ──── FIN, seq=u ──────────────→  │  ① Client 主动关闭
    │     (ESTABLISHED → FIN_WAIT_1)   │     (ESTABLISHED → CLOSE_WAIT)
    │                                   │
    │ ←── ACK, seq=v, ack=u+1 ──────── │  ② Server 确认收到 FIN
    │     (FIN_WAIT_1 → FIN_WAIT_2)    │
    │                                   │
    │     ... Server 继续发送剩余数据 ...│
    │                                   │
    │ ←── FIN, seq=w, ack=u+1 ──────── │  ③ Server 也准备关闭
    │     (FIN_WAIT_2 → TIME_WAIT)     │     (CLOSE_WAIT → LAST_ACK)
    │                                   │
    │ ──── ACK, seq=u+1, ack=w+1 ───→  │  ④ Client 确认
    │     (等待 2MSL → CLOSED)         │     (LAST_ACK → CLOSED)
    │                                   │
    ▼                                   ▼
  CLOSED                             CLOSED
```

**为什么是四次挥手而不是三次？**

TCP 是全双工的，每个方向需要独立关闭。Server 收到 Client 的 FIN 后，可能还有数据要发送（② 只是 ACK，不是 FIN），等数据发完再发自己的 FIN（③）。所以 ACK 和 FIN 不能合并，需要四次。

**五、TIME_WAIT —— 为什么需要 2MSL？**

TIME_WAIT 是主动关闭方在发送最后一个 ACK 后进入的状态，持续 2MSL（Maximum Segment Lifetime，报文最大生存时间，Linux 默认 60 秒）。

```
TIME_WAIT 存在的两个原因：

  ① 确保最后一个 ACK 能被对方收到
     如果最后一个 ACK 丢失，Server 会重发 FIN。
     Client 在 TIME_WAIT 期间可以重发 ACK。
     如果 Client 直接 CLOSED，Server 重发的 FIN 会收到 RST（连接重置），
     Server 认为连接异常终止。

  ② 让旧连接的所有报文在网络中消失
     防止旧连接的延迟报文被新连接（相同四元组）误接收。
     2MSL = 报文一个来回的最大时间 × 2，
     足够让两个方向上的所有旧报文都消失。
```

**大量 TIME_WAIT 的排查与优化**：

```bash
# 查看 TIME_WAIT 数量
netstat -an | grep TIME_WAIT | wc -l
ss -tan state time-wait | wc -l

# 常见原因：
# ① 高并发短连接（如 HTTP 1.0 每次请求建新连接）
# ② 服务端主动关闭连接（如反向代理 Nginx → 后端）
# ③ 爬虫或压测工具频繁建连断连
```

```
优化方案：

  ① 开启 tcp_tw_reuse（复用 TIME_WAIT 连接）
     echo 1 > /proc/sys/net/ipv4/tcp_tw_reuse
     注意：只对客户端（主动连接方）有效

  ② 开启 tcp_timestamps
     echo 1 > /proc/sys/net/ipv4/tcp_timestamps
     配合 tcp_tw_reuse 使用，通过时间戳判断旧报文

  ③ 减小 TIME_WAIT 时长（不推荐，治标不治本）
     调整内核参数 net.ipv4.tcp_fin_timeout（默认 60s）

  ④ 使用长连接（HTTP Keep-Alive / 连接池）
     避免频繁建连断连

  ⑤ 调整 tcp_max_tw_buckets
     限制 TIME_WAIT 最大数量，超出后直接销毁
```

**六、CLOSE_WAIT 堆积——比 TIME_WAIT 更危险**

```
TIME_WAIT vs CLOSE_WAIT：

  TIME_WAIT：主动关闭方，持续 2MSL 后自动消失，通常无害
  CLOSE_WAIT：被动关闭方，等待应用层调用 close()，如果不调用就永远存在！

  CLOSE_WAIT 堆积的原因：
  ① 应用代码 Bug：收到 FIN 后没有调用 close()
  ② 连接泄漏：线程阻塞/死锁导致无法 close
  ③ 数据库连接池没有正确回收连接

  排查方法：
  netstat -an | grep CLOSE_WAIT | wc -l
  ss -tapn state close-wait  # 查看是哪个进程
  lsof -p <pid> | grep CLOSE_WAIT  # 查看文件描述符
```

### 💡 延伸思考

1. **SYN Flood 攻击怎么防御？** — 攻击者发送大量 SYN 但不回复最后的 ACK，导致 Server 大量连接处于 SYN_RCVD 状态，耗尽资源。防御方案：① SYN Cookie（不分配资源，用 Cookie 验证）；② 缩短 SYN Timeout；③ 增加 SYN 队列大小（tcp_max_syn_backlog）；④ 防火墙限流。
2. **TCP 同时打开/同时关闭可能吗？** — 可能。双方同时发 SYN → 双方都进入 SYN_SENT → 收到对方 SYN 后进入 SYN_RCVD → 双方都发 SYN+ACK → 建立连接。同时关闭类似，双方同时发 FIN → 进入 CLOSING 状态（一种特殊的中间状态），然后进入 TIME_WAIT。
