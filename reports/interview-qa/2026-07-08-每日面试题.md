## 题目 1：[框架/Spring] 请详细说明 Spring Bean 的完整生命周期，包括从实例化到销毁的每个阶段，以及三级缓存如何解决循环依赖问题

**难度**：⭐⭐⭐⭐⭐
**考点来源**：2026-07-08 午间报告 — "Spring Bean生命周期（三级缓存现场推导）"
**相关岗位**：Java后端 / 全栈

### 📖 参考答案

#### 一、Spring Bean 的完整生命周期

Spring Bean 的生命周期大致分为四个阶段：**实例化 → 属性赋值 → 初始化 → 销毁**。展开后共约 10+ 个关键步骤：

```
Bean 生命周期流程图：

容器启动（AbstractApplicationContext.refresh()）
        │
        ▼
① 实例化（Instantiation）
   └─ 通过反射创建 Bean 实例（调用构造器）
        │
        ▼
② 填充属性（Populate）
   └─ @Autowired / @Resource / @Value 等依赖注入
        │
        ▼
③ Aware 接口回调
   ├─ BeanNameAware.setBeanName()
   ├─ BeanClassLoaderAware.setBeanClassLoader()
   └─ BeanFactoryAware.setBeanFactory()
        │
        ▼
④ BeanPostProcessor#postProcessBeforeInitialization
   └─ 初始化前的预处理（如 @PostConstruct 扫描、AOP 前置处理）
        │
        ▼
⑤ 初始化（Initialization）
   ├─ @PostConstruct 标注方法
   ├─ InitializingBean#afterPropertiesSet()
   └─ @Bean(initMethod = "init") 指定初始化方法
        │
        ▼
⑥ BeanPostProcessor#postProcessAfterInitialization
   └─ 初始化后的后处理（核心！AOP 动态代理在此生成）
        │
        ▼
⑦ Bean 就绪——放入一级缓存（singletonObjects）
   └─ 可以被业务代码使用
        │
        ▼
⑧ 容器关闭时销毁
   ├─ @PreDestroy 标注方法
   ├─ DisposableBean#destroy()
   └─ @Bean(destroyMethod = "close") 指定销毁方法
```

#### 二、三级缓存解决循环依赖

**什么是循环依赖？**

```java
@Service
public class A {
    @Autowired
    private B b;  // A 依赖 B
}

@Service
public class B {
    @Autowired
    private A a;  // B 依赖 A（循环依赖）
}
```

**三级缓存的定义：**

| 缓存级别 | 名称 | 存储内容 | 作用 |
|---------|------|---------|------|
| **一级缓存** | `singletonObjects` | 完全初始化好的 Bean 实例（成品） | 最终使用的 Bean |
| **二级缓存** | `earlySingletonObjects` | 提前暴露的半成品 Bean（属性未完全填充） | 解决循环依赖的中间产物 |
| **三级缓存** | `singletonFactories` | `ObjectFactory<?>` 函数式工厂 | 生成代理对象 |

**三级缓存解决流程（以 A ↔ B 循环依赖为例）：**

```
1. A 开始创建
   ├─ 实例化 A（调用构造器，得到一个原始对象）
   ├─ 将 A 的 ObjectFactory 放入三级缓存（earlySingletonExposure）
   └─ 填充属性 → 发现依赖 B
        │
        ▼
2. B 开始创建
   ├─ 实例化 B
   ├─ 将 B 的 ObjectFactory 放入三级缓存
   └─ 填充属性 → 发现依赖 A
        │
        ▼
3. 从三级缓存获取 A 的半成品
   ├─ getSingleton("a", true)
   ├─ 三级缓存 → 调用 ObjectFactory.getObject()（可能生成 AOP 代理）
   ├─ 放入二级缓存（earlySingletonObjects）
   └─ 返回 A 的引用给 B
        │
        ▼
4. B 拿到 A 的引用 → B 初始化完成
   └─ B 放入一级缓存（singletonObjects）
        │
        ▼
5. A 继续填充属性
   ├─ 拿到完整的 B 实例
   └─ A 初始化完成 → 放入一级缓存
```

**为什么必须有三级缓存，二级不够吗？**

这是面试最常追问的点。核心原因：**AOP 代理对象的创建时机**。

- 如果只有二级缓存，B 在填充 A 时拿到的是原始对象 A
- 但后续 A 的后置处理器（BeanPostProcessor）可能生成 AOP 代理对象 A'
- 此时 B 中持有的还是原始 A，而一级缓存存的是 A' → **不一致！**
- 三级缓存通过 `ObjectFactory` 延迟代理创建：在 `getObject()` 时才判断是否需要代理
- 确保 B 拿到的引用和最终一级缓存中的引用是**同一个对象**

```java
// 三级缓存的核心代码（DefaultSingletonBeanRegistry）
// 三级缓存的 ObjectFactory
addSingletonFactory(beanName, () -> getEarlyBeanReference(beanName, mbd, bean));

// getEarlyBeanReference 会调用 SmartInstantiationAwareBeanPostProcessor
// → 如果 Bean 需要 AOP，这里返回代理对象；否则返回原始对象
protected Object getEarlyBeanReference(String beanName, RootBeanDefinition mbd, Object bean) {
    // 遍历所有 SmartInstantiationAwareBeanPostProcessor
    // 触发其 getEarlyBeanReference 方法（AOP 的入口）
}
```

**无法解决的循环依赖场景：**

| 场景 | 能否解决 | 原因 |
|------|---------|------|
| Setter/字段注入循环依赖 | ✅ 能解决 | 先实例化再暴露半成品 |
| 构造器注入循环依赖 | ❌ 不能解决 | 构造器执行前还没实例化，无法提前暴露 |
| 多例（Prototype）循环依赖 | ❌ 不能解决 | 原型 Bean 不缓存，每次新建 |
| @Async 注解的 Bean 循环依赖 | ❌ 不能解决 | 需要提前生成代理，但循环依赖导致冲突 |

### 💡 延伸思考
1. **为什么构造器注入推荐但循环依赖时反而用字段注入？** — 构造器注入在设计上更规范（保证依赖不可变），但遇到循环依赖只能降级为字段注入。更根本的解法是重构代码消除循环依赖。
2. **Spring Boot 2.6+ 默认禁止循环依赖** — 启动日志会报 `BeanCurrentlyInCreationException`，可设置 `spring.main.allow-circular-references=true` 恢复，但不建议。

## 题目 2：[JVM] 请详细说明 JVM 内存区域划分、常见 OOM 场景的排查流程以及 GC 调优的关键参数与思路

**难度**：⭐⭐⭐⭐
**考点来源**：2026-07-08 午间报告 — "JVM：内存模型、GC调优、类加载机制" + 早间报告 "JVM GC调优、OOM排查完整流程"
**相关岗位**：Java后端 / 全栈 / 基础架构

### 📖 参考答案

#### 一、JVM 内存区域划分（JDK 8+）

```
JVM 运行时数据区（JDK 8+，已移除永久代，引入元空间）：

┌─────────────────────────────────────────────────────────┐
│                    堆（Heap）                             │
│  ┌──────────────────┬──────────────────────────────────┐ │
│  │ 新生代（Young）    │      老年代（Old）                │ │
│  │ ┌───┬─────┬────┐ │                                  │ │
│  │ │ E │ S0  │ S1 │ │ → 长期存活的对象从 Survivor 晋升   │ │
│  │ └───┴─────┴────┘ │                                  │ │
│  │ Eden:Survivor=8:1 │  GC 频率：低但每次耗时较长        │ │
│  └──────────────────┴──────────────────────────────────┘ │
│  -Xms / -Xmx 指定堆大小                                   │
├─────────────────────────────────────────────────────────┤
│                    元空间（Metaspace）                     │
│  方法区实现：类信息、常量、静态变量、JIT 编译后的代码       │
│  使用本地内存（Native Memory），不再受 -XX:MaxPermSize 限制 │
│  -XX:MaxMetaspaceSize 可设上限                            │
├─────────────────────────────────────────────────────────┤
│  虚拟机栈（Stack）         │  本地方法栈（Native Stack）    │
│  每个方法对应一个栈帧       │  native 方法调用栈            │
│  栈帧：局部变量表、操作数栈  │                              │
│  线程私有，-Xss 设置大小     │                              │
├──────────────────┬──────────────────────────────────────┤
│  程序计数器（PC）  │  直接内存（Direct Memory）            │
│  线程私有          │  NIO 使用，-XX:MaxDirectMemorySize   │
└──────────────────┴──────────────────────────────────────┘
```

#### 二、常见 OOM 场景及排查

**场景 1：Java Heap Space OOM**

**原因**：堆内存不足，对象无法分配。常见于内存泄漏或大对象分配。

```java
// 典型泄漏：ThreadLocal 未 remove
public class ThreadLocalLeak {
    private static final ThreadLocal<byte[]> TL = new ThreadLocal<>();
    
    public void process() {
        TL.set(new byte[1024 * 1024 * 100]); // 100MB
        // ❌ 没有 TL.remove() → 线程复用导致内存泄漏
    }
}
```

**排查命令**：
```bash
# 1. 查看堆使用情况
jmap -heap <pid>

# 2. 生成堆转储文件
jmap -dump:live,format=b,file=heap.hprof <pid>
# 生产环境建议使用 -XX:+HeapDumpOnOutOfMemoryError 自动转储

# 3. 用 MAT 或 JProfiler 分析 heap.hprof
# → 查看 Largest Objects / GC Roots / Leak Suspects
```

**场景 2：Metaspace OOM**

**原因**：CGLIB 动态代理/ASM 生成大量类（常见于 Spring AOP 或热部署场景）。

```java
// 典型：CGLIB 动态生成大量代理类
for (int i = 0; i < 100000; i++) {
    Enhancer enhancer = new Enhancer();
    enhancer.setSuperclass(SomeClass.class);
    enhancer.setCallback((MethodInterceptor) (obj, method, args, proxy) -> proxy.invokeSuper(obj, args));
    enhancer.create(); // 不断生成新类 → Metaspace 撑爆
}
```

**排查**：`-XX:MaxMetaspaceSize=256m` 设上限 + 观察 `jstat -gc_metacapacity <pid>`。

**场景 3：StackOverflowError（非 OOM 但高频）**

**原因**：递归调用过深、无限循环、方法调用链过长。

```java
// 典型：递归没有终止条件
public int fibonacci(int n) {
    return fibonacci(n - 1) + fibonacci(n - 2); // 没有终止条件！
}
```

**排查**：`-Xss256k` 调整栈大小，看异常堆栈中的重复调用链。

**场景 4：Direct Buffer Memory OOM**

**原因**：NIO 的 `ByteBuffer.allocateDirect()` 未释放。

**排查**：`-XX:MaxDirectMemorySize=512m` + NMT（Native Memory Tracking）`-XX:NativeMemoryTracking=summary`。

#### 三、GC 调优关键参数与思路

**JDK 8+ 主流 GC 选择：**

| 场景 | 推荐 GC | 核心参数 |
|------|---------|---------|
| 响应优先（低延迟） | G1GC（默认） | `-XX:+UseG1GC` |
| 吞吐量优先（批处理） | ParallelGC | `-XX:+UseParallelGC` |
| 极低延迟（<10ms） | ZGC（JDK 11+） | `-XX:+UseZGC` |
| 超大堆（数百GB） | Shenandoah/ZGC | `-XX:+UseShenandoahGC` |

**G1GC 调优参数（最常用）：**

```bash
# 基础配置
-Xms8g -Xmx8g                          # 堆大小，建议 -Xms = -Xmx
-XX:+UseG1GC                            # 使用 G1 垃圾回收器
-XX:MaxGCPauseMillis=200                # 期望最大 GC 停顿时间（默认 200ms）
-XX:ParallelGCThreads=8                 # 并行 GC 线程数
-XX:ConcGCThreads=2                     # 并发标记线程数

# 调优关注指标
-XX:+PrintGCDetails                     # 打印 GC 详情
-XX:+PrintGCDateStamps                  # 打印 GC 时间戳
-Xloggc:/path/gc.log                    # GC 日志路径
-XX:+HeapDumpOnOutOfMemoryError         # OOM 自动 dump
-XX:HeapDumpPath=/path/heap.hprof       # dump 文件路径
```

**GC 调优通用思路（面试回答框架）：**

```
1. 明确目标
   ├─ 响应优先（低延迟）：关注 GC 停顿时间 → 优化 G1/ZGC
   └─ 吞吐量优先（高吞吐）：关注 CPU 利用率 → 优化 ParallelGC

2. 观察现状（通过监控工具）
   ├─ jstat -gcutil <pid> 1000 10     → 观察 GC 频率和耗时
   ├─ jmap -histo <pid>               → 查看对象分布
   ├─ GC 日志分析（GCeasy/GCEasy）     → 可视化分析
   └─ Prometheus + Grafana 监控        → 长期趋势

3. 定位问题
   ├─ Full GC 频繁 → 老年代不足 / 内存泄漏
   ├─ Young GC 过长 → Eden 过大 / 对象过大直接进老年代
   └─ CPU 飙高 → GC 线程竞争 / 频繁 GC

4. 针对性优化
   ├─ 调整堆大小（-Xms/-Xmx）
   ├─ 调整新生代比例（-XX:NewRatio / -Xmn）
   ├─ 调整晋升阈值（-XX:MaxTenuringThreshold）
   ├─ 大对象阈值（-XX:PretenureSizeThreshold）
   └─ 代码层面修复内存泄漏
```

### 💡 延伸思考
1. **JVM 调优是"先测量再优化"** — 没有测量就调优是盲人摸象。先建立监控（GC 日志 + 内存指标），发现明确问题后再调整参数。
2. **线上 OOM 如何快速止血？** — 保留现场（自动 dump）→ 重启恢复服务 → 离线分析 dump → 修复代码 → 灰度发布。不要在线 dump 大堆（卡死）。

## 题目 3：[数据库/MySQL] 请详细说明 MySQL InnoDB 的 MVCC（多版本并发控制）原理，包括 Undo Log、ReadView 和事务隔离级别的实现机制

**难度**：⭐⭐⭐⭐⭐
**考点来源**：2026-07-08 午间报告 — "MySQL：MVCC"
**相关岗位**：Java后端 / 全栈 / DBA

### 📖 参考答案

#### 一、什么是 MVCC？

**MVCC（Multi-Version Concurrency Control，多版本并发控制）** 是 InnoDB 实现**读-写不互斥**的核心机制——读事务读取数据时，写事务可以同时修改数据，读事务看到的是数据的历史快照。

**核心思想**：每一行数据维护多个版本，每个版本有对应的创建时间和过期时间（用事务 ID 标记），读操作只读取符合其可见性规则的版本。

#### 二、MVCC 的三大核心组件

**1. 隐藏字段（每行数据都有）**

| 字段 | 大小 | 说明 |
|------|------|------|
| `DB_TRX_ID` | 6 字节 | 最近一次修改（INSERT/UPDATE）该行的事务 ID |
| `DB_ROLL_PTR` | 7 字节 | 回滚指针，指向 Undo Log 中的上一个版本 |
| `DB_ROW_ID` | 6 字节 | 隐式自增 ROWID（无主键时生成聚簇索引用） |

```
一行数据在 MVCC 中的版本链：

行数据（当前最新版本，由事务 ID=100 修改）
┌─────────────────────────────────────────────┐
│ name="张三"  age=30  DB_TRX_ID=100          │
│ DB_ROLL_PTR ──────────────────────────┐     │
└─────────────────────────────────────────┼─────┘
                                         │
                                         ▼
Undo Log 中的历史版本（由事务 ID=80 修改）
┌─────────────────────────────────────────────┐
│ name="张三"  age=25  DB_TRX_ID=80           │
│ DB_ROLL_PTR ──────────────────────────┐     │
└─────────────────────────────────────────┼─────┘
                                         │
                                         ▼
Undo Log 中的历史版本（由事务 ID=50 插入）
┌─────────────────────────────────────────────┐
│ name="李四"  age=20  DB_TRX_ID=50           │
│ DB_ROLL_PTR = NULL（Insert Undo，用完可清理） │
└─────────────────────────────────────────────┘
```

**2. Undo Log（回滚日志）**

- **Insert Undo**：INSERT 操作产生的 Undo，事务回滚时用于删除插入的行，事务提交后可立即丢弃
- **Update Undo**：UPDATE/DELETE 操作产生的 Undo，用于 MVCC 快照读和事务回滚，**不能立即删除**（可能还有活跃事务需要读取旧版本）

**3. ReadView（读视图）—— MVCC 可见性判断的核心**

ReadView 是事务执行快照读（SELECT）时生成的"快照"，包含以下关键信息：

```sql
-- ReadView 核心结构
class ReadView {
    m_low_limit_id;     // 下一个待分配的事务 ID（系统最大事务 ID + 1）
    m_up_limit_id;      // 当前活跃事务的最小 ID
    m_ids;              // 当前活跃事务 ID 列表（Read Committed 每次重新生成）
    m_creator_trx_id;   // 创建该 ReadView 的事务 ID
}
```

**可见性判断规则**（面试常考推导）：

```
对于一行数据的 DB_TRX_ID = X：

┌─ X < m_up_limit_id（X 比所有活跃事务都早）┈┈→ ✅ 可见（已提交）
│
├─ X == m_creator_trx_id（当前事务自己修改的）┈┈→ ✅ 可见
│
├─ X >= m_low_limit_id（X 是未来事务修改的）┈┈┈→ ❌ 不可见（未开始）
│
├─ X 在 m_ids 列表中（X 是活跃事务修改的）┈┈┈→ ❌ 不可见（未提交）
│
└─ X 不在 m_ids 列表中（X 已提交）┈┈┈┈┈┈┈┈┈→ ✅ 可见
```

#### 三、MVCC 在不同隔离级别下的差异

| 隔离级别 | ReadView 生成时机 | 现象 |
|---------|-----------------|------|
| **READ UNCOMMITTED** | 不使用 MVCC，直接读最新版本 | 脏读 |
| **READ COMMITTED**（RC） | **每次 SELECT 都生成新的 ReadView** | 不可重复读（同一事务两次 SELECT 结果可能不同） |
| **REPEATABLE READ**（RR）✅ InnoDB 默认 | **事务第一次 SELECT 时生成 ReadView，复用到底** | 可重复读（解决了不可重复读 + 部分幻读） |
| **SERIALIZABLE** | 不使用 MVCC，所有读加锁 | 无并发问题，性能最差 |

**RR 级别下 MVCC 如何避免不可重复读？**

```
事务 A（TRX_ID=100）                   事务 B（TRX_ID=101）
│                                        │
├─ BEGIN;                                │
│                                        ├─ BEGIN;
├─ SELECT age FROM user WHERE id=1;     │
│   → 创建 ReadView: m_ids=[100,101]     │
│   → 查到 age=25（TRX_ID=50 已提交） ✅  │
│                                        ├─ UPDATE user SET age=30 WHERE id=1;
│                                        ├─ COMMIT;  -- TRX_ID=101 提交
│                                        │
├─ SELECT age FROM user WHERE id=1;     │
│   → **复用之前的 ReadView: m_ids=[100,101]**
│   → 101 在 m_ids 中（尽管已提交）→ 不可见
│   → 查 Undo Log 历史版本 → age=25 ✅   │
│   → 可重复读！                         │
```

#### 四、MVCC + Next-Key Lock 解决 RR 下的幻读

MVCC 解决**快照读（普通 SELECT）** 的幻读，但对于**当前读（SELECT ... FOR UPDATE / UPDATE / DELETE）**，需要配合 **Next-Key Lock**：

```sql
-- 事务 A
BEGIN;
SELECT * FROM user WHERE age > 20 FOR UPDATE;  -- 当前读，加 Next-Key Lock
-- 此时其他事务无法插入 age > 20 的新行（间隙锁）
COMMIT;
```

### 💡 延伸思考
1. **RC vs RR 如何选择？** — RC 在 MGR 或主从复制时可能导致主键冲突（因为无 gap lock），但并发性能更高；RR 默认使用 MVCC + Next-Key Lock 防止幻读，适合一致性要求高的场景。
2. **长事务为什么会导致 Undo Log 膨胀？** — 长事务一直持有 ReadView，导致 Undo Log 中的历史版本无法被 purge，可能撑爆 ibdata1。
3. **MySQL 8.0 对 MVCC 的优化** — 引入了 `read_only` 事务跳过 ReadView 生成，减少了元数据锁冲突。
